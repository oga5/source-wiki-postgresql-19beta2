contrib/pg_plan_advice/README

Plan Advice

このモジュールは、プランナの特定の重要な決定を制御できるようにする「プランアドバイス（plan advice）」用のミニ言語を実装しています。目標には、（1）プランの安定性の強制（以前のプランが良好であったため、同様のプランを維持したい場合）および（2）オプティマイザが好むプラン以外のプランをユーザーが実験できるようにすることが含まれます。非目標には、（1）考えられるすべてのプランナの決定を制御すること、および（2）コスト以外の理由でオプティマイザが拒否したプランの検討を強制することが含まれます。（この非目標が正確に何を意味するかについては、議論の余地があります。たとえば、あるケースにおいてコストで勝てないことが分かっているという理論に基づいてパス生成を完全にスキップした場合、コストが計算されなかったとしても、それはコストベースの拒否とみなされるでしょうか？）

一般に、プランアドバイスは空白で区切られた一連のアドバイス項目であり、各項目はアドバイス対象のリストにアドバイスタグを適用します。たとえば、"SEQ_SCAN(foo) HASH_JOIN(bar@ss)" には2つのアドバイス項目が含まれており、最初の項目は "foo" に SEQ_SCAN タグを適用し、2番目の項目は "bar@ss" に HASH_JOIN タグを適用します。この単純な例では、各対象は単一のリレーションを識別します。以下の「Relation Identifiers」を参照してください。アドバイスタグはリレーションのグループに適用することもできます。たとえば、"HASH_JOIN(baz (bletch quux))" は、単一のリレーション識別子 "baz" と、"bletch" と "quux" を含む2項目のリストの両方に HASH_JOIN タグを適用します。

極めて重要な点として、このモジュールは、既存のプランからプランアドバイスを生成する方法と、将来のプランニングサイクル中にそれを強制する方法の両方を知っています。このモジュールが行うすべてのことは「ラウンドトリップセーフ（往復安全）」であることを意図しています。つまり、あるプランからアドバイスを生成し、それを将来のプランニングサイクルにフィードバックした場合、各アドバイスは、曖昧さや推測なしに、それが生成されたクエリのまったく同じ部分に適用されることが保証され、最初にそれが生成される原因となったのと同じプランニングの決定を正常に強制する必要があります。なお、これらの保証は、間にDDLが介在する場合には保持されないことに注意してください。たとえば、サブクエリがインライン化されなくなるように関数のプロパティを変更したり、プランアドバイスで指定されているインデックスを削除したりした場合、アドバイスは機能しなくなります。これは想定内の動作です。

このモジュールは、提供されたアドバイスが優れたアドバイスであるか悪いアドバイスであるかに関係なく、プランナにそれに従うことを強制することを目指しています。ユーザーが、以前に生成されたプランから派生したものであれ、手動で作成したものであれ、悪いアドバイスを提供した場合、悪いプランが作成される可能性があります。私たちはこれをユーザーのエラーとみなし、このモジュールの欠陥とはみなしません。問題を回避するために本当に必要な場合にのみ、慎重にアドバイスを適用する方が、大雑把に適用するよりも成功する戦略である可能性が高いと思われますが、ユーザーは自分が最善と考えるどのような戦略でも自由に実験できます。

Relation Identifiers

特定のプランアドバイスが適用されるクエリの部分を一意に特定することは、言葉で言うほど簡単ではありません。私たちの基本的なアプローチは、リレーションのエイリアスを出発点として使用し、その後で曖昧さを排除することです。同じリレーションエイリアスが複数回発生する可能性は3つあります。

1. 複数のサブクエリに表示される場合。

2. 同じサブクエリ内に複数回表示される場合。 例：(foo JOIN bar) x JOIN foo

3. テーブルがパーティショニングされている場合。

これらの任意の組み合わせが同時に発生する可能性があります。したがって、リレーション識別子の一般的な構文は次のようになります。

alias_name#occurrence_number/partition_schema.partition_name@plan_name

alias_name 以外のすべてのコンポーネントはオプションであり、必要な場合にのみ含まれます。コンポーネントが省略される場合、関連する句読点も省略する必要があります。出現番号（occurrence_number）は、パーティションテーブルの子を無視してカウントされます。生成された出現番号が1の場合、出現番号は省略されます。パーティションスキーマ（partition_schema）とパーティション名（partition_name）は、パーティションテーブルの子に対してのみ含まれます。生成されたアドバイスでは、partition_name がある場合は常に partition_schema も含まれますが、ユーザーが作成したアドバイスでは、スキーマを省略して名前だけを指定することもできます。plan_name は、最上位の PlannerInfo では省略されます。

Scan Advice

多くの種類のスキャンでは、アドバイスは生成されず、不可能です。たとえば、サブクエリは常にサブクエリスキャンを使用してスキャンされます。そのスキャンは setrefs 処理によって省略される可能性がありますが、基本的なアプローチが1つしか存在しないという事実は変わりません。したがって、スキャンアドバイスは主に、複数の方法でスキャンできるリレーションに適用されます。

私たちは通常、スキャンが単一のリレーションを対象としていると考え、通常はそうなりますが、必ずしもそうである必要はありません。たとえば、結合が空であることが証明された場合、全体が単一の Result ノードに置き換えられる可能性があり、これは事実上、結合ツリーの折りたたまれた部分にあるすべてのリレーションの退化したスキャンになります。同様に、結合全体を置き換えるような方法でカスタムスキャンを注入することも可能です。これらのケースに対してアドバイスを出力する場合、括弧で囲まれたリレーション識別子のセットを対象とします。たとえば、SOME_SORT_OF_SCAN(foo (bar baz)) は、指定されたスキャンタイプが単一のリレーションとしての foo、および結合積としての bar と baz の組み合わせに対して使用されることを意味します。現在、そのようなケースはありません。

インデックススキャンおよびインデックスオンスキャン（index-only scan）の場合、スキャンされるリレーションと、使用されるインデックスの両方を指定する必要があります。たとえば、INDEX_SCAN(foo foo_a_idx bar bar_b_idx) は、foo をスキャンするときに foo_a_idx でインデックススキャン（インデックスオンスキャンではない）を使用し、bar をスキャンするときに bar_b_idx でインデックススキャンを使用することを示します。

ビットマップヒープスキャン（bitmap heap scan）は、現在インデックスの指定を許可していません。BITMAP_HEAP_SCAN(foo bar) は、単に foo と bar のそれぞれが何らかのビットマップヒープスキャンを使用する必要があることを意味します。

特定のリレーションをまったくスキャンすべきではないことを示す、特別な DO_NOT_SCAN() アドバイスタグがあります。これは、AlternativeSubPlan が解決されるときに2つの選択肢のどちらが選択されるか、および MinMaxAggPath が選択されるかどうかを制御するために使用されます。アッパープランナ（upper planner）の動作の制御は、現時点では一般にスコープ外ですが、ビルドファームでの test_plan_advice の失敗を防ぐために、これらのケースを処理する必要がありました。

Join Order Advice

JOIN_ORDER タグは、同じ結合問題の一部である複数のテーブルを結合する順序を指定します。各サブクエリ（インライン化されているものを除く）は、個別の結合問題です。サブクエリ内では、パーティション単位の結合（partitionwise join）によって、追加の個別の結合問題が作成される場合があります。したがって、パーティション単位の結合を伴うクエリでは、JOIN_ORDER() が何度も使用される可能性があります。

私たちは標準的な結合構造をアウターディープ（outer-deep）ツリーとみなしているため、JOIN_ORDER(t1 t2 t3) は、t1 が駆動テーブルであり、最初に t2、次に t3 に結合される必要があることを示します。結合問題に追加のテーブルが含まれている場合、それらは t1、t2、t3 の間の結合が構築された後、任意の順序で結合できます。生成された結合アドバイスは常に結合問題内のすべてのテーブルに言及しますが、手動で作成された結合アドバイスはそうする必要はありません。

アウターディープではないツリーの場合は、括弧を使用できます。たとえば、JOIN_ORDER(t1 (t2 t3)) は、最上位の結合の外側（outer side）に t1 を配置し、内側（inner side）に t2 と t3 の結合を配置する必要があることを示します。その結合は、t2 が外側、t3 が内側になるように構築される必要があります。

場合によっては、この方法で結合順序を完全に指定できないことがあります。たとえば、t2 と t3 が単一のカスタムスキャンまたは外部スキャンによってスキャンされている場合、またはそれらのテーブル間でパーティション単位の結合が実行されている場合、t2 が外側テーブルで t3 が内側テーブルである、またはその逆であると言うことは不可能です。それは単に未定義です。このような場合、順序付けの欠如を示すことを意図して、中括弧を使用した結合アドバイスを生成します。JOIN_ORDER(t1 {t2 t3}) は、最上位の結合の外側に t1 を配置し、内側に t2 と t3 の間の何らかの結合を配置する必要があることを示しますが、その結合をどのように実行する必要があるか、どのリレーションが結合のどちら側に表示されるべきか、あるいはこの種の結合に側があるかどうかについては何も言及しません。

Join Method Advice

NESTED_LOOP_PLAIN などのタグは、特定の結合を実行するために使用する必要があるメソッドを指定します。より具体的には、NESTED_LOOP_PLAIN(x (y z)) は、プランが識別子 "x" を持つリレーションをプレーンなネステッドループ（マテリアライズやメモ化を行わないもの）の内側に配置し、識別子 "y" を持つリレーションと識別子 "z" を持つリレーションの結合もネステッドループの内側に配置する必要があることを示します。したがって、N個のテーブルの結合問題の場合、N-1個の結合メソッドアドバイスが存在することになります。結合問題の最も外側のテーブルには、結合メソッドアドバイスは必要ありません。

結合順序アドバイスと結合メソッドアドバイスの両方があることを考えると、NESTED_LOOP_PLAIN(x) は、x が具体的に内側ではなく、ネステッドループのどちらか一方の側に単独で表示されるべきであることを意味するように再定義するのが自然であるように思われるかもしれませんが、この定義は実際には役に立たないようです。これにより、プランナに自由を与えすぎて、ユーザーが想定していたものとほとんど似ていない処理が行われることになります。これは、マージ結合やパラメータ化されていないネステッドループの場合には実用上の違いは限られていますが、パラメータ化されたネステッドループやハッシュ結合の場合、2つの側は非常に異なる方法で処理されるため、特定のリレーションがそれらの操作のいずれかに関与すべきであると、どちらの役割を担うべきかを言わずに述べることは、あまり意味がありません。

この定義の選択は、結合メソッドアドバイスがいくつかの結合順序の制約も課すことを意味します。たとえば、foo と bar の間の結合を考えると、HASH_JOIN(bar) は foo が駆動テーブルであることを意味します。そうでなければ、ハッシュ結合の内側の下に bar を配置することは不可能になります。

この定義を前提とすると、結合順序アドバイスを削除して結合メソッドアドバイスを適用することを検討するのは合理的であることに注意してください。たとえば、テーブル fact、dim1、dim2、dim3、dim4、dim5 を持つスター・スキーマを考えてみましょう。自動的に生成されるアドバイスは、JOIN_ORDER(fact dim1 dim3 dim4 dim2 dim5) HASH_JOIN(dim2 dim4) NESTED_LOOP_PLAIN(dim1 dim3 dim5) を指定するかもしれません。JOIN_ORDER アドバイスを削除すると、プランナは結合メソッドの同じ選択を強制しながら、結合を好きなように並べ替えることができます。これは潜在的に有用であると思われ、結合順序と結合メソッドの両方を単一の表現で制御する統一された構文が選択されなかった理由の1つです。

Advice Completeness

重要な基本原則は、アドバイスがないことに基づいて推論を行ってはならないということです。ユーザーは、生成されたアドバイスのうち不適切または逆効果であると判断した部分を削除する権利があり、その結果はプランナに与えられる柔軟性を高めるだけであるべきです。これは、アドバイスが特定の最適化や手法を使用すべきであると言えるのであれば、その最適化や手法を使用すべきではないとも言えるべきであることを意味します。特定のことを行うようにという指示がないことが、それを行うべきではないことを意味すると想定してはなりません。すべての指示は明示的でなければなりません。

Semijoin Uniqueness

セミ結合（semijoin）に直面すると、プランナは直接的な実装と、一方の側を一意にしてから内部結合を実行するプランの両方を検討します。この変換が発生した場合は SEMIJOIN_UNIQUE() アドバイスを出力し、発生しなかった場合は SEMIJOIN_NON_UNIQUE() アドバイスを出力します。これらの項目は結合メソッドアドバイスのように機能します。関連する結合の内側が指定され、選択された結合順序はアドバイスが何らかの効果を持つことと互換性がなければなりません。

Partitionwise

PARTITIONWISE() アドバイスを使用すると、実行すべきパーティションワイズ結合と実行すべきでないパーティションワイズ結合の両方を指定できます。このアイデアは、PARTITIONWISE の各引数が、相互に結合された後それ以外のものとは結合されずにパーティションワイズでスキャンされるべきリレーションのセットを指定するというものです。したがって、たとえば PARTITIONWISE((t1 t2) t3) は、クエリに t1 と t2 の間のパーティションワイズ結合が含まれるべきであり、t3 がいかなるパーティションワイズ結合の一部であってはならないことを指定します。クエリ内に他のリレーションが存在しない場合、単に PARTITIONWISE((t1 t2)) を指定しても同じ効果が得られます。これは、t3 がパーティションワイズ方式で結合できる他のリレーションが存在しなくなるためです。

並列クエリ (Gather など)

GATHER() または GATHER_MERGE() の各引数は、その上にそれぞれ Gather ノードまたは Gather Merge ノードが配置されるべき単一のリレーション、または正確なリレーションのセットです。NO_GATHER() の各引数は、どの Gather ノードまたは Gather Merge ノードの下にも出現してはならない（つまり、並列処理を使用すべきではない）単一のリレーションです。

暗黙的な結合順序の制約

特定の結合問題に対して JOIN_ORDER() アドバイスが提供されない場合でも、他のアドバイスが結果的に結合順序を制約する場合があります。たとえば、HASH_JOIN((foo bar)) を指定するユーザーは、内側に正確に foo と bar が配置されるハッシュ結合が存在するべきであると明示的に指定しているだけでなく、foo と bar のいずれかが他の何物かと結合される前に、それらが相互に結合されなければならないことも暗示しています。そうでなければ、ユーザーが制約しようとしている結合が実際にはクエリ内で発生せず、結果としてシステムがアドバイスを完全に無視することに決めたかのように見えてしまいます。
