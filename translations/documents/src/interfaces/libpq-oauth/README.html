libpq-oauthは、OAuthクライアント向けのデバイス認可フロー（RFC 8628）を実装するオプションのモジュールです。libcurlへの依存関係を分離するために、独自の共有ライブラリとしてメンテナンスされています。（Curlへの依存関係を望まないエンドユーザーは、単にこのモジュールをインストールしないことを選択できます。）

接続文字列でOAuthの使用が許可されており、サーバーがそれを要求し、かつlibpqクライアントが独自のカスタムOAuthフローをインストールしていない場合、libpqはdlopen()と以下のABIを使用してこのモジュールの遅延ロードを試みます。ロードに失敗すると、接続は失敗します。

= ロードタイムABI =

v19の時点で、このモジュールのABIは公開されており、エントリポイントも変更しない限り、互換性のない変更を行うことはできません。ライブラリのアップグレードはどちらの順序でも発生する可能性があるため、libpqとlibpq-oauthの両方が、もう一方のライブラリが過去または将来の異なるリリースバージョンである状況を適切に処理する必要があります。

（libpq-oauthからlibpqへのパッケージバージョンの依存関係によって状況が単純化されるとは仮定しないでください！ libpqはlibpq-oauthを遅延ロードするため、長期実行されているクライアントアプリケーションのlibpqが、新しくアップグレードされたプラグインよりも古い場合も処理する必要があります。）

モジュールは以下のシンボルをエクスポートします。

  • int pg_start_oauthbearer(PGconn *conn, PGoauthBearerRequestV2 *request);

その後、モジュールはPQauthDataHook APIを介してPQAUTHDATA_OAUTH_BEARER_TOKEN_V2リクエストを受信したかのように動作し、既存のトークンを入力するか、トークンを非同期に取得するために必要なコールバックを設定します。（PGoauthBearerRequestのドキュメントを参照してください。）この関数は、成功した場合はゼロを、失敗した場合はゼロ以外を返します。

さらに、libpq-oauthはlibpqのlibpq_gettext()に依存しており、フローが実行される前に、この初期化関数を使用してlibpqによって注入される必要があります。

  • void libpq_oauth_init(libpq_gettext_func gettext_impl);

= 静的ビルド =

静的ライブラリlibpq.aは動的ロードを実行しません。組み込みフローが有効になっている場合、アプリケーションは必要なシンボルを提供するためにlibpq-oauth.aとリンクするか、あるいはpg_start_oauthbearer()を自身で実装することが期待されます。
