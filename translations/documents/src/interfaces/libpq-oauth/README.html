libpq-oauthは、OAuthクライアント向けのデバイス認可フロー（RFC 8628）を実装するオプショナルなモジュールです。libcurlへの依存関係を隔離するために、独自の共有ライブラリとしてメンテナンスされています。（Curlへの依存関係を望まないエンドユーザーは、単にこのモジュールをインストールしないことを選択できます。）

接続文字列がOAuthの使用を許可しており、サーバーがそれを要求し、かつlibpqクライアントが独自のカスタムOAuthフローをインストールしていない場合、libpqはdlopen()と以下のABIを使用して、このモジュールの遅延ロードを試みます。ロードに失敗すると、接続は失敗します。

= Load-Time ABI =

v19の時点で、このモジュールABIは公開されており、エントリポイントも変更しない限り、互換性のない変更を行うことはできません。ライブラリのアップグレードはどちらの順序でも発生する可能性があるため、libpqとlibpq-oauthの両方が、もう一方のライブラリが過去または将来の異なるリリースバージョンである状況を適切に処理する必要があります。

（libpq-oauthからlibpqへのパッケージバージョンの依存関係によって状況が単純化されるとは仮定しないでください！ libpqはlibpq-oauthを遅延ロードするため、長期実行されているクライアントアプリケーションが、新しくアップグレードされたプラグインよりも古いlibpqを持っているケースを依然として処理する必要があります。）

モジュールは以下のシンボルをエクスポートします。

  • int pg_start_oauthbearer(PGconn *conn, PGoauthBearerRequestV2 *request);

その後、モジュールはPQauthDataHook APIを介してPQAUTHDATA_OAUTH_BEARER_TOKEN_V2リクエストを受信したかのように動作し、既存のトークンを設定するか、トークンを非同期に取得するために必要なコールバックを設定します。（PGoauthBearerRequestのドキュメントを参照してください。）この関数は、成功時にゼロを返し、失敗時にゼロ以外を返します。

さらに、libpq-oauthはlibpqのlibpq_gettext()に依存しており、フローが実行される前に、この初期化関数を使用してlibpqによって注入される必要があります。

  • void libpq_oauth_init(libpq_gettext_func gettext_impl);

= Static Build =

静的ライブラリlibpq.a does not perform any dynamic loading. If the builtin flow is enabled, the application is expected to link against libpq-oauth.a to provide the necessary symbol, or else implement pg_start_oauthbearer() itself.
