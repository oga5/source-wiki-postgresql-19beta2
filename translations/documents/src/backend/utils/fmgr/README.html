The V1 Function-Manager Interface

設計の核心は、関数検索の結果を表すデータ構造と、特定の関数呼び出しに渡されるパラメータを表すデータ構造です。（システムの多くの部分で同じ関数が何度も繰り返し適用されるため、関数検索と関数呼び出しは分離しておきたいと考えています。検索のオーバーヘッドは、タプルごとではなく、クエリごとに1回だけ支払われるべきです。）

関数がpg_procで検索されると、その結果は以下のように表されます。

typedef struct { PGFunction fn_addr; /* pointer to function or handler to be called */ Oid fn_oid; /* OID of function (NOT of handler, if any) */ short fn_nargs; /* number of input args (0..FUNC_MAX_ARGS) */ bool fn_strict; /* function is "strict" (NULL in => NULL out) */ bool fn_retset; /* function returns a set (over multiple calls) */ unsigned char fn_stats; /* collect stats if track_functions > this */ void *fn_extra; /* extra space for use by handler */ MemoryContext fn_mcxt; /* memory context to store fn_extra in */ Node *fn_expr; /* expression parse tree for call, or NULL */ } FmgrInfo;

通常の組み込み関数の場合、fn_addrは関数を実装するCルーチンのアドレスにすぎません。それ以外の場合は、対象の関数を含む関数クラスのハンドラのアドレスになります。ハンドラは、関数のOIDや、場合によってはfn_extraスロットを使用して、実行する特定のコードを見つけることができます。（fn_oid = InvalidOidは、まだ初期化されていないFmgrInfo構造体を示すために使用できます。FmgrInfoが関数検索コードによって最初に埋められるとき、fn_extraは常にNULLになりますが、クエリ中に同じFmgrInfoが繰り返し使用される場合に、関数ハンドラが独自の検索を繰り返すのを避けるためにこれを設定することができます。）fn_nargsは関数が期待する引数の数、fn_strictはその厳密性（strict）フラグ、fn_retsetはセットを返すかどうかを示します。これらの値はすべて、関数のpg_procエントリから取得されます。fn_statsも、この関数の呼び出しに関する実行時統計情報を追跡するかどうかを制御するために設定されます。

関数がSQL式の一部として呼び出されている場合、fn_exprは関数呼び出しの式パースツリーを指します。これを使用して、実際の引数に関するパース時の情報を抽出できます。このフィールドは、実際には関数に関する情報というよりも引数に関する情報ですが、論理的により適していると思われるFunctionCallInfoBaseDataよりも、FmgrInfoに保持する方が便利であることが分かっています。

関数の呼び出し中、以下のデータ構造が作成され、関数に渡されます。

typedef struct { FmgrInfo *flinfo; /* ptr to lookup info used for this call */ Node *context; /* pass info about context of call */ Node *resultinfo; /* pass or return extra info about result */ Oid fncollation; /* collation for function to use */ bool isnull; /* function must set true if result is NULL */ short nargs; /* # arguments actually passed */ NullableDatum args[]; /* Arguments passed to function */ } FunctionCallInfoBaseData; typedef FunctionCallInfoBaseData* FunctionCallInfo;

flinfoは、呼び出しを行うために使用された検索情報を指します。通常の関数はおそらくこのフィールドを無視しますが、関数クラスのハンドラは、呼び出されている特定の関数のOIDを特定するためにこれを必要とします。

contextは「通常の」関数呼び出しではNULLですが、特定のコンテキストで関数が呼び出される場合は、追加情報を指すことがあります。（たとえば、トリガーマネージャは現在のトリガーイベントに関する情報をここに渡します。）詳細については、以下の「Function Call Contexts」を参照してください。

resultinfoは、単純なDatumの結果が期待される関数を呼び出す場合はNULLです。関数がDatum以上のものを返す場合、Nodeの何らかのサブタイプを指すことがあります。（たとえば、以下で説明するように、セットを返す関数を呼び出すときにresultinfoが使用されます。）contextフィールドと同様に、resultinfoは拡張用のフックであり、fmgr自体はこのフィールドの使用を制限しません。

fncollationは、パーサーによって導出された入力照合順序（collation）です。照合可能な型の入力がない場合や、共通の照合順序を共有していない場合はInvalidOidになります。これは事実上、隠された追加の引数であり、照合順序に依存する関数がその動作を決定するために使用できます。

nargsとargs[]は、関数に渡される引数を保持します。関数に渡されるすべての引数（およびその結果値）は、一律にDatum型になることに注意してください。以下で説明するように、呼び出し側と呼び出される側は、特定の関数の実際の引数型に変換するために、標準のDatum相互変換マクロを適用する必要があります。args[i].isnullがtrueの場合、args[i].valueの値は未定義です。

渡される引数の数が呼び出される側の期待する数と一致することを確認するのは、一般的に呼び出し側の責任です。可変個の引数を取る場合を除き、呼び出される側は通常、nargsフィールドを無視してargs[]から値を取得するだけです。

isnullフィールドは、呼び出し前に「false」に初期化されます。関数からの復帰時、isnullは関数結果のnullフラグになります。これがtrueの場合、実際の関数の戻り値に関係なく、関数の結果はNULLになります。単純な「strict」関数は、args[].isnullにTRUE値が1つでもあると呼び出されさえしないため、isnullとargs[i].isnullの両方を無視できることに注意してください。

FunctionCallInfoは、FmgrValuesに加えて、多くのアドホックなパラメータ規約、グローバル変数（少なくともfmgr_pl_finfoとCurrentTriggerData）、およびその他の見苦しい部分を置き換えるものです。

呼び出される側は、個々の関数であれ関数ハンドラであれ、常に次のシグネチャを持つ必要があります。

Datum function (FunctionCallInfo fcinfo);

これは以下のtypedefで表されます。

typedef Datum (*PGFunction) (FunctionCallInfo fcinfo);

関数は、fcinfo->isnullを適切に設定するとともに、Datumとして表される結果を返す責任があります。すべての呼び出される側が完全に同じシグネチャを持つようになり、まさにそのシグネチャで宣言された関数ポインタを介して呼び出されるため、移植性や最適化の問題は発生しないはずです。

Function Coding Conventions

提案されているマクロとコーディング規約は以下の通りです。

fmgrから呼び出し可能な関数の定義は、常に次のようになります。

Datum function_name(PG_FUNCTION_ARGS) { ... }

"PG_FUNCTION_ARGS"は単に"FunctionCallInfo fcinfo"に展開されます。このマクロを使用する主な理由は、スクリプトが関数定義を容易に見つけられるようにするためです。しかし、将来的に呼び出し規約を再び変更することになった場合、このマクロが用意されていると便利かもしれません。

nonstrict関数は、個々の引数がnullであるかどうかをチェックする責任があり、これはPG_ARGISNULL(n)（単に"fcinfo->args[n].isnull"）で行うことができます。nullである引数の値を取得しようとすることは避けるべきです。

必要に応じて、strict関数とnonstrict関数の両方が、以下を使用してNULLを返すことができます。 PG_RETURN_NULL(); これは以下に展開されます。 { fcinfo->isnull = true; return (Datum) 0; }

引数の値は、通常、次のようなコードを使用して取得されます。 int32 name = PG_GETARG_INT32(number);

float4、float8、およびint8の場合、PG_GETARGマクロは、その型が値渡し（pass-by-value）か参照渡し（pass-by-reference）かを隠蔽します。たとえば、float8が参照渡しの場合、PG_GETARG_FLOAT8は以下に展開されます。 (* (float8 *) DatumGetPointer(fcinfo->args[number].value)) そして、通常は次のように呼び出されます。 float8 arg = PG_GETARG_FLOAT8(0); 現在では歴史的な理由により、浮動小数点関連のtypedefとマクロは型の幅をバイト数（4または8）で表していますが、整数型の幅はビット数でラベル付けすることを好みます。

null以外の値は、適切な型のPG_RETURN_XXXマクロを使用して返されます。たとえば、PG_RETURN_INT32は以下に展開されます。 return Int32GetDatum(x) PG_RETURN_FLOAT4、PG_RETURN_FLOAT8、およびPG_RETURN_INT64は、必要に応じてpallocを行うことで、それらのデータ型が値渡しであるか参照渡しであるかを隠蔽します。

fmgr.hは、すべての基本データ型に対してPG_GETARGおよびPG_RETURNマクロを提供します。特殊なSQLデータ型（例：timestamp）を定義するモジュールやヘッダーファイルは、それらの型に適したマクロを定義して、その型を操作する関数を標準的なスタイルで記述できるようにする必要があります。

プリミティブでないデータ型（特に可変長型）の場合、データ型の参照渡しの性質を隠蔽することはあまり実用的ではないため、それらの型に対するPG_GETARGおよびPG_RETURNマクロは、DatumGetPointer/PointerGetDatumと適切な型キャストを行う以上のことはほとんどしません（ただし、以下のTOASTに関する説明を参照してください）。このような型を返す関数は、結果の領域を明示的にpalloc()する必要があります。そのような型に対するGETARGおよびRETURNマクロの名前は、ポインタを生成または受け取ることを思い出させるために、末尾を「_P」にすることをお勧めします。たとえば、PG_GETARG_TEXT_Pは「text *」を生成します。

関数がfcinfo->flinfoやFunctionCallInfoの他の補助フィールドのいずれかにアクセスする必要がある場合は、単にアクセスすればよいだけです。これらのケースに対してシンタックスシュガーのマクロを提供することが有用であるとは思いません。

Support for TOAST-Able Data Types

TOAST可能なデータ型の場合、PG_GETARGマクロはde-TOAST（非TOAST）化されたデータ値を返します。まだTOASTされたままの値が必要なケースもいくつかあるかもしれませんが、圧倒的多数のケースではde-TOAST化された結果が必要とされるため、それがデフォルトになります。de-TOAST化を行わずに引数の値を取得するには、PG_GETARG_RAW_VARLENA_P(n)を使用します。

一部の関数は、入力値の変更可能なコピーを必要とします。このような場合、データをde-TOASTするためにいずれにせよコピーしたのであれば、さらなるコピー手順を行うのは無意味です。したがって、TOAST可能な各データ型には、追加の取得マクロ（たとえばPG_GETARG_TEXT_P_COPY(n)）があり、これは保証された新しいコピーを提供し、可能であればこれをde-TOAST化の手順と組み合わせます。

また、PG_FREE_IF_COPY(ptr,n)マクロもあります。これは、指定されたポインタがn番目の引数の元の値と異なる場合にのみ、そのポインタをpfreeします。これは、n番目の引数が実際にde-TOAST化されていた場合に、そのde-TOAST化された値を解放するために使用できます。現在、コアバックエンドコードが一時的な領域を定期的に解放するため、関数の実行でリークしたメモリは大きな問題にはならず、大半の関数でこれを行う必要はありません。しかし、7.1の時点では、インデックス検索から呼び出される関数でのメモリリークは、トランザクションの終了までクリーンアップされません。したがって、pg_amopまたはpg_amprocにリストされている関数は、de-TOAST化されたコピーをリークさせないように注意する必要があり、そのためこれらの関数はTOAST可能な入力に対してPG_FREE_IF_COPY()を使用する必要があります。

関数は、その結果値を再TOASTしようとしてはなりません。現在のメモリコンテキストでpallocされた、TOASTされていない結果を返すだけにすべきです。値が実際にタプルに格納される際、タプルトースターがTOASTが必要かどうかを判断します。

Function Call Contexts

呼び出し側がfcinfo->contextに非NULLポインタを渡す場合、それはNodeの何らかのサブタイプを指している必要があります。具体的なコンテキストの種類は、ノードタイプフィールドによって示されます。（呼び出される側は、どのようなコンテキストが渡されているかを想定する前に、常にIsA()を介してノードタイプを確認する必要があります。）fmgr自体は、このフィールドの使用に他に制限を設けません。

この規約の現在の用途には、以下が含まれます。

  • トリガー関数には、トリガーコンテキストに関する情報を含む struct TriggerData のインスタンスが渡されます（トリガー関数は通常の引数を受け取りません）。トリガー関数によって一般的に使用されるマクロや詳細については、commands/trigger.h を参照してください。
  • 集約関数（正確には、その遷移関数および最終関数）には、呼び出し側の Agg プランノードのエグゼキュータ状態ノードである struct AggState のインスタンスが渡されます。または、ウィンドウ関数として呼び出される場合は、struct WindowAggState のインスタンスが渡されます。これらのポインタは、fmgr.h で宣言されているものの、ソースコードである src/backend/executor/nodeAgg.c 内でのみ文書化されている AggCheckCallContext() および関連関数を介してのみ使用することが推奨されます。通常、これらのコンテキストノードは、遷移関数や最終関数が、独立した SQL 関数としてではなく集約内で使用されていることを認識して実行を最適化したい場合にのみ重要となります。
  • 真のウィンドウ関数には、struct WindowObject のインスタンスが渡されます（トリガー関数と同様に、通常の引数は受け取りません）。詳細については windowapi.h を参照してください。
  • プロシージャには、CALL 文のコンテキストに関する情報、特に「アトミック」な実行コンテキスト内にあるかどうかに関する情報を含む struct CallContext のインスタンスが渡されます。
  • データ型入力関数の一部の呼び出し側（および将来的には他のクラスの関数も）は、ErrorSaveContext のインスタンスを渡します。これは、呼び出し側がトランザクションを終了させる例外をスローせずに「ソフト」エラーを処理したい意向を示しています。代わりに、呼び出し先の関数はエラー原因に関する情報を ErrorSaveContext 構造体に格納し、ダミーの結果値を返すべきです。詳細については、後述の「ソフトエラーの処理」を参照してください。

ソフトエラーの処理

Postgres の標準的なエラー報告メカニズム（ereport() または elog()）は、あらゆる種類のエラー条件に使用されます。これは、ereport(ERROR) による例外のスローには、何が間違っていたかについて例外キャッチャが多くの仮定を置くことができないため、コストの高いトランザクション（またはサブトランザクション）の中止とクリーンアップが必要になることを意味します。完全なトランザクションクリーンアップを行わずに安全に回復できることがわかっているエラーに対処するための、より軽量なメカニズムが望ましい状況があります。SQL 呼び出し可能な関数は、ErrorSaveContext コンテキストメカニズムを使用してこのニーズをサポートできます。

「ソフト」エラーを報告するには、SQL 呼び出し可能な関数は以下を呼び出す必要があります。 errsave(fcinfo->context, ...) これは以前には次のように記述されていた場所です。 ereport(ERROR, ...) 渡された "context" が NULL であるか、ErrorSaveContext ノードではない場合、errsave は ereport(ERROR) とまったく同様に動作します。例外は longjmp を介してスローされるため、制御は戻りません。"context" が ErrorSaveContext ノードである場合、errsave の付属的な報告呼び出しに含まれるエラー情報はコンテキストノードに格納され、制御は通常どおり errsave から戻ります。その後、関数は呼び出し元にダミー値を返す必要があります（ダミー値としては SQL NULL が推奨されますが、呼び出し元が ErrorSaveContext ノードでエラーが報告されたことを確認した後は関数の戻り値を無視することが想定されているため、どのような値でも構いません）。

errsave() の呼び出し後に戻ること以外に何もしない場合は、次のように記述して 1、2 行を省略できます。 ereturn(fcinfo->context, dummy_value, ...) これにより errsave() が実行され、その後「return dummy_value」が実行されます。

「ソフトに」報告されるエラーは、トランザクションの通常の処理を継続できることに疑問の余地がないという意味において、安全でなければなりません。この方法で処理してはならないエラー条件には、メモリ不足、予期しない内部エラー、または簡単にクリーンアップできないものが含まれます。このような場合は、従来どおり ereport を使用してスローする必要があります。

データ型入力関数を例に取ると、一般的な「ソフト」エラー条件には、入力構文エラーや範囲外の値が含まれます。入力関数は通常、単純な if テストでそのようなケースを検出し、その後の ereport 呼び出しを errsave や ereturn に簡単に変更できます。この制限のため、低レベルの関数によって報告されるエラーは通常、内部的なものと見なすのが妥当であるため、ErrorSaveContext ポインタを非常に深い階層まで渡す必要は通常ありません。（この区別を別の表現で言い換えると、入力関数はすべての無効な入力条件をソフトに報告すべきであり、内部的な問題はハードエラーであるということです。）

トランザクションのクリーンアップは行われないため、errsave() が返った後に終了する関数は、リソースのクリーンアップの責任を負います。呼び出し元が短命なメモリコンテキストで関数を実行しているはずであるため、palloc されたメモリの小さな漏れについて気にする必要はありません。ただし、ロック、オープンされたファイル、バッファピンなどのリソースは、エラーが発生しないコードパスと同様に、クリーンにクローズされる必要があります。

エラーをトラップするために ErrorSaveContext メカニズムを使用する呼び出し側の規則については、nodes/miscnodes.h 内のその構造体の宣言とともに説明されています。

セットを受け取るまたは返す関数

関数が pg_proc 内でセットを返すものとしてマークされている場合、その関数は fcinfo->resultinfo が ReturnSetInfo 型の目を指している状態で呼び出されます。セットを返したい関数は、resultinfo が NULL であるか ReturnSetInfo ノードを指していない場合、「セットの結果を受け付けないコンテキストで呼び出されました」というエラーを発生させる必要があります。

現在、関数がセットの結果を返すモードには、値毎の呼び出し（value-per-call）とマテリアライズ（materialize）の 2 つがあります。値毎の呼び出しモードでは、関数は呼び出されるたびに 1 つの値を返し、返す値がなくなると最終的に「完了（done）」を報告します。マテリアライズモードでは、関数の出力セットが Tuplestore オブジェクト内にインスタンス化され、すべての値が 1 回の呼び出しで返されます。将来的に追加のモードが追加される可能性があります。

ReturnSetInfo には「allowedModes」というフィールドが含まれており、呼び出し側がサポートできるモードの OR であるビットマスクに（呼び出し側によって）設定されます。関数によって実際に使用されるモードは、別のフィールド「returnMode」で返されます。後方互換性の理由から、returnMode は値毎の呼び出しに初期化されており、関数が別のモードを使用したい場合にのみ変更する必要があります。関数は、呼び出し側がサポートするどのモードも使用できない場合に ereport() を行う必要があります。

値毎の呼び出しモードは次のように動作します。ReturnSetInfo には「isDone」というフィールドが含まれており、これはいずれかの値に設定される必要があります。

ExprSingleResult /* 式はセットを返さない */ ExprMultipleResult /* この結果はセットの要素である */ ExprEndResult /* セットにはこれ以上要素がない */

（呼び出し側はこれを ExprSingleResult に初期化します）。関数が ReturnSetInfo に触れずに単に Datum を返す場合、呼び出しは終了し、単一アイテムのセットが返されたことになります。セットを返すには、関数はセットの各要素に対して isDone を ExprMultipleResult に設定する必要があります。すべての要素が返された後、次の呼び出しで isDone を ExprEndResult に設定し、null の結果を返す必要があります（最初の呼び出しでこれを行って空のセットを返すことも可能です）。

値毎の呼び出しを行う関数は、完了まで実行されると仮定してはなりません。たとえば LIMIT のために、エグゼキュータが関数の呼び出しを突然停止させる可能性があるためです。したがって、最後の呼び出しでリソースのクリーンアップを試みることは安全ではありません。いずれにせよ、通常はメモリをクリーンアップする必要はありません。ファイル記述子などの他の種類のリソースをクリーンアップする必要がある場合は、ReturnSetInfo ノードが指す ExprContext にシャットダウンコールバック関数を登録できます（ただし、ファイル記述子は限られたリソースであるため、呼び出しをまたいでオープンしたままにすることは一般的に得策ではありません。ファイルアクセスを必要とする SRF は、Materialize モードを使用して 1 回の呼び出しで行うように記述する方が適切です）。

マテリアライズモードは次のように動作します。関数は（空の可能性もある）結果セットを保持する Tuplestore を作成し、それを返します。複数の呼び出しはありません。関数はまた、タプル構造を示す TupleDesc を返す必要があります。Tuplestore と TupleDesc は、コンテキスト econtext->ecxt_per_query_memory 内で作成される必要があります（これは関数が呼び出されるコンテキストとは *異なる* 点に注意してください）。関数は Tuplestore と TupleDesc へのポインタを ReturnSetInfo に格納し、returnMode をマテリアライズモードを示すように設定し、null を返します。isDone は使用されず、ExprSingleResult のままにしておく必要があります。

allowedModes で SFRM_Materialize_Random が設定されている場合、Tuplestore は randomAccess = true で作成されなければなりませんが、設定されていない場合は randomAccess = false で作成することができます（また、可能であればそうすべきです）。ValuePerCall と Materialize モードの両方をサポートできる呼び出し側は、好みのモードに応じて SFRM_Materialize_Preferred を設定するかどうかを選択します。

利用可能な場合、期待されるタプル記述子が ReturnSetInfo で渡されます。他のコンテキストでは、expectedDesc フィールドは NULL になります。関数は expectedDesc に注意を払う必要はありませんが、特殊なケースでは役立つ場合があります。

InitMaterializedSRF() は、1 回の呼び出しのために関数の ReturnSetInfo をセットアップし、マテリアライズモード用の適切な設定で Tuplestore と TupleDesc を埋めることができるヘルパー関数です。

セットを受け入れる関数のサポートはありません。代わりに、入力セットの各要素に対して 1 回ずつ、関数が複数回呼び出されます。

関数ハンドラーに関する注意事項

この設計では、関数のクラスのハンドラーにとって、実装がはるかに容易でクリーンになるはずです。呼び出された関数の OID は、渡されたパラメータから直接取得できます。グローバル変数 fmgr_pl_finfo はもう必要ありません。また、fcinfo->flinfo->fn_extra を変更することにより、ハンドラーはルックアップ情報をキャッシュし、同じ関数が何度も呼び出されるときの重複するルックアップを回避できます（呼び出し側が FmgrInfo 構造体を再利用することが義務付けられていないため、fn_extra はヒントとしてのみ使用できます。ただし、パフォーマンスが重要なパスでは、通常は再利用されます）。

ハンドラーが fn_extra データを保持するメモリを割り当てたい場合、CurrentMemoryContext 内で割り当てては *なりません*。現在のコンテキストは、FmgrInfo が存在するコンテキストよりも寿命がはるかに短い可能性があるためです。代わりに、コンテキスト flinfo->fn_mcxt、または長命なキャッシュコンテキストでメモリを割り当ててください。fn_mcxt は通常、FmgrInfo 構造体が作成された時点で CurrentMemoryContext であったコンテキストを指します。いずれにせよ、少なくとも FmgrInfo 自体と同程度に長命なコンテキストであることが要求されます。
