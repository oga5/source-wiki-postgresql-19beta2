src/backend/access/spgist/README

SP-GiST は space-partitioned GiST（空間分割 GiST）の略です。 これは、四分木、k-d 木、ラディックス木（トライ木）などの空間分割データ構造を実装するための 一般化されたインフラストラクチャを提供します。 主記憶（メインメモリ）に実装する場合、これらの構造は通常、 ポインタによってリンクされた動的に割り当てられたノードのセットとして設計されます。 ポインタのチェインがかなり長く、過剰なディスクアクセスを必要とするため、 これはディスク上に直接保存するには適していません。 対照的に、ディスクベースのデータ構造は、I/O を最小限に抑えるために高いファンアウトを持つべきです。 課題は、検索アルゴリズムが多くのノードを走査する場合でも、 わずか少数のディスクページしかアクセスしないように、ツリーノードをディスクページにマッピングすることです。

共通構造の説明

論理的には、SP-GiST ツリーはタプルの集合であり、 各タプルは内部タプルまたはリーフタプルのいずれかになります。 各内部タプルには「ノード」が含まれており、これらは (label, pointer) のペアです。 ここでポインタ (ItemPointerData) は、別の内部タプルまたはリーフタプルのリストの先頭へのポインタです。 内部タプルは、異なる数のノード（子）を持つことができます。 ブランチの深さは異なる場合があり（実際、バランスをサポートするための制御やコードはありません）、 これはツリーが非バランスであることを意味します。 ただし、リーフタプルと内部タプルを同じレベルで混在させることはできません。 内部タプルのノードからのダウンリンクは、1 つの内部タプル、またはリーフタプルのリストのいずれかに通じています。

SP-GiST コアでは、内部タプルとリーフタプルが 1 つのインデックスページに収まること、 さらに厳密には、単一の内部タプルノードから到達するリーフタプルのリストがすべて同じインデックスページに保存されることを要求します。 （このようなリストがページをまたがないように制限することでシークが減り、 リストのリンクをシンプルな 2 バイトの OffsetNumbers として保存できるようになります。） したがって、SP-GiST インデックス演算子クラスは、 1 つの内部タプルに必要となるノード数が多すぎないようにし、 また内部タプルのプレフィックスやリーフノードのデータ値が大きくなりすぎないようにする必要があります。

内部タプルとリーフタプルは別々に保存されます。 前者は「内部」ページにのみ保存され、後者は「リーフ」ページにのみ保存されます。 また、ルートページには特別な制限があります。 インデックスの寿命の初期段階で、1 ページ分のデータしかない場合、 ルートページには未整理のリーフタプルのセットが含まれます。 最初のページ分割が発生した後は、ルートにはちょうど 1 つの内部タプルが含まれている必要があります。

検索走査アルゴリズムが内部タプルに到達すると、 深さ方向のツリー走査を継続するノードのセットを選択します。 リーフページに到達すると、リーフタプルのリストをスキャンしてクエリに一致するものを探します。 SP-GiST は順序付き（最接近）検索もサポートしています。 つまり、スキャン中に保留中のノードが優先度付きキューに入れられるため、 走査は最接近優先モデルによって実行されます。

挿入アルゴリズムも同様にツリーを降下しますが、 各内部タプルから降下するノードを 1 つだけ選択しなければならない点が異なります。 また、挿入では降下する前に内部タプルを変更する必要が生じる場合もあります。 新しいノードを追加したり、挿入される値に一致させることができるより汎用性の低いプレフィックスを取得するためにタプルを「分割」したりする場合があります。 新しいリーフタプルをリストに追加する必要があり、ページに空き領域がない場合、 SP-GiST は新しい内部タプルを作成し、リーフタプルを、おそらく複数のページ上の、一連のリストに分散させます。

内部タプルは以下で構成されます。

オプションのプレフィックス値 - すべての後続要素はこれと矛盾してはなりません。 例： ラディックス木 - プレフィックス値は共通のプレフィックス文字列 四分木 - 重心 k-d 木 - 1 つの座標

ノードのリスト（ノードは (label, pointer) のペア）。 ラベルの例：ラディックス木における 1 文字

リーフタプルは以下で構成されます。

リーフ値 例： ラディックス木 - 文字列の残りの部分（ポストフィックス） 四分木および k-d 木 - ポイント自体

対応するヒープタプルへの ItemPointer リーフページ上のチェイン内の次のリーフタプルの nextOffset 番号

オプションの null ビットマスク オプションの INCLUDE 列の値

v14 より前のインデックスとの互換性のために、 リーフタプルは、(リーフ値と INCLUDE 値の中に) null 値が存在し、*かつ*少なくとも 1 つの INCLUDE 列が存在する場合にのみ、null ビットマスクを持ちます。 リーフ値が null であるかどうかは、タプルが「null ページ」にあるかどうかから推論できるため (下記参照)、 明示的に表現する必要はありません。 しかし、標準的なタプル分解コードを使用できるようにするため、INCLUDE 値で使用されるビットマスクに anyway（ともかく）含めています。

NULL の処理

SP-GiST インデックス可能な演算子は厳格である（null 入力に対して決して成功しない）と仮定します。 テーブル全体に対するインデックススキャンが可能になり、"x IS NULL" が SP-GiST インデックススキャンによって実装できるようにするためには、 それでも null をインデックスすることが望ましいです。 しかし、SP-GiST インデックス演算子クラスが null に対処しなくてよいようにすることが好ましいです。 したがって、SP-GiST インデックスのメインツリーには、null エントリは一切含まれません。 null エントリは、互いに排反なページのセット（特に独自のルートページ）を占有する、 別の SP-GiST ツリーに保存されます。 null ツリーにおける挿入および検索では、演算子クラスから提供される関数は一切使用せず、 通常のツリーにおける AllTheSame ケースと同等のハードワイヤードされたロジックを使用します。

挿入アルゴリズム

挿入アルゴリズムは、いつでもツリーを整合性のある状態に保つように設計されています。 以下は簡略化された挿入アルゴリズムの仕様です（番号は以下の注記に対応しています）。

ルートページの最初のタプルから開始する (1)

ループ: if (ページがリーフである) then if (十分な空きスペースがある) ページに挿入して終了する (5) else (7) PickSplitFn() を呼び出す (2) end if else switch (chooseFn()) case MatchNode - 選択したノードを通って降下する case AddNode - ノードを追加してから chooseFn をリトライする (3, 6) case SplitTuple - 内部タプルをプレフィックスとポストフィックスに分割し、 プレフィックスタプルで chooseFn をリトライする (4, 6) end if

注記：

(1) 最初は、ルートページがいっぱいになるまでリーフタプルを単にダンプし、その後分割します。 ルートがリーフページでなくなると、ルート上の空き容量をできるだけ大きく保つため、 内部タプルを 1 つだけ持つことができます。 これらのルールはいずれも、検索空間の最上位の分割を可能な限り適切に行えるように、 ルートに対する PickSplit の実行を可能な限り先延ばしにすることを目的としています。

(2) 現在の実装では、新しいリーフタプルのリストが 1 ページに収まる場合、 picksplit と新しいリーフタプルの挿入を 1 つの操作で行うことができます。 四分木や k-d 木のような小さなノードを持つツリーでは常に可能ですが、 ラディックス木では別の picksplit が必要になる場合があります。

(3) ノードの追加では、内部タプルのサイズをページに収まる十分に小さいサイズに維持する必要があります。 追加後、ページ上の他のタプルのために、内部タプルが現在のページに保存しきれないほど大きくなる可能性があります。 この場合、別の内部ページに移動されます（ページ管理についての注記を参照）。 タプルを別のページに移動する場合、ページ上の他のタプルの番号を変更することはできません。 変更すると、それらへのダウンリンクポインタが無効になってしまうためです。 それを防ぐため、SP-GiST は「プレースホルダー」タプルを残します。これは、 後で別のタプルがページに追加されたときにいつでも再利用できます。 以下の「並行性 (Concurrency)」および「バキューム (Vacuum)」セクションも参照してください。 現在、ノードをタプルに追加できるのはラディックス木だけです。 四分木および k-d 木は、PickSplitFn() の呼び出しで一度に可能なすべてのノードを作成します。

(4) プレフィックス値は新しい値に部分的にしか一致しない場合があるため、 SplitTuple アクションにより、現在のツリーのブランチを上部と下部のセクションに分割することができます。 別の言い方をすれば、現在の内部タプルを、着信する新しい値に一致させることができる「プレフィックス」部分と 「ポストフィックス」部分に分割できるということです。 ラディックス木への挿入の例を考えてみます。 タプルの ID は議論のためのものに過ぎない（そのような ID は実際には保存されない）以下の表記法を使用します：

内部タプル: {tuple id}(prefix string)[ カンマ区切りのノードラベルのリスト ] リーフタプル: {tuple id}<value>

文字列 'www.gogo.com' を次の内部タプルに挿入する必要があると仮定します。

{1}(www.google.com/)[a, i]

文字列がプレフィックスと一致しないため、降下することができません。 内部タプルを 2 つのタプルに分割する必要があります。

{2}(www.go)[o] - プレフィックスタプル | {3}(gle.com/)[a,i] - ポストフィックスタプル

ループの次の反復で、'www.gogo.com' がプレフィックスには一致するが、 どのノードラベルにも一致しないことが判明するため、ノード [g] をタプル {2} に追加します。

NIL (子はまだ存在しない) | {2}(www.go)[o, g] | {3}(gle.com/)[a,i]

これで [g] ノードを通って降下できるようになり、 これによりターゲット文字列が単に 'o.com' に更新されます。 最後に、その文字列を持つリーフタプルを挿入します。

{4}<o.com> | {2}(www.go)[o, g] | {3}(gle.com/)[a,i]

ご覧のとおり、元のタプルのノード配列は変更なしでポストフィックスタプルに移動します。 また、SP-GiST コアは、プレフィックスタプルが古い内部タプルより大きくないことを前提としていることにも注意してください。 これにより、古い内部タプルの代わりにプレフィックスタプルをインプレースで直接保存できるようになります。 SP-GiST コアは可能であれば同じページにポストフィックスタプルを保存しようとしますが、 十分な空き領域がない場合は別のページを使用します（注記 5 および 6 を参照）。 現在、四分木および k-d 木はこの機能を使用していません。 これは、新しい値に対してプレフィックスが「不整合」であるという概念を持たないためです。 これらは PickSplitFn() の呼び出しによってのみ深さを増やします。

(5) 親のノードからのポインタが NIL ポインタである場合、 アルゴリズムは保存先のリーフページを選択します。 まず、ディスクスペースをより有効活用するために、（各バックエンドで追跡している） 空き領域が最も大きい最後に使用したリーフページを使用しようとします。 それが十分な大きさでない場合、アルゴリズムは新しいページを割り当てます。

(6) 内部ページの管理は、(5) で説明したリーフページの管理と非常によく似ています。

(7) 実際、現在の実装では、リーフタプルのリストが十分に短い場合、 リーフタプルのリスト全体と新しいタプルを別のページに移動することができます。 これによりスペースの利用率は向上しますが、アルゴリズムの基本は変わりません。

並行性 (CONCURRENCY)

ツリーを降下している間、挿入アルゴリズムは一度に 2 つのツリーレベル（つまり、親ページと子ページの両方）に対して排他ロックを保持します （ただし、親ページと子ページが同じ場合もあります。上記の注記を参照）。 異なるブランチに相互参照されたページがある場合、2 つの挿入の間でデッドロックが発生する可能性があります。 つまり、ページ M上の内部タプルがページ N に子を持ち、 別のブランチのページ N 上の内部タプルがページ M に子を持つ場合、 2 つのブランチを降下する 2 つの挿入は、 それぞれ子ページのロックを取得しようとしながら親ページのロックを保持するため、デッドロックする可能性があります。

現在、我々はツリーを降下するときにバッファを条件付きでロックすることでこれに対処しています。 バッファのロック取得に失敗した場合、両方のバッファを解放し、挿入プロセスを再開します。 これは潜在的に非効率的ですが、より決定論的なアプローチのロックコストは非常に高いように思われます。

これが発生するケースの数を減らすために、我々はページの「トリプルパリティ (triple parity)」という概念を導入しています。 内部タプルが BlockNumber N のページにある場合、 その子タプルは同じページ、あるいは (N+1) mod 3 == M mod 3 となる BlockNumber M のページに配置されるべきです。 このルールにより、(M+1) mod 3 != N mod 3 であるため、 ページ M上のタプルはページ N に子を持たないことが保証されます。 これにより、2 つの挿入プロセスがツリーの降下中に競合することは起こりにくくなります。 ただし、これは完璧ではありません。 まず第一に、3 つ以上の挿入プロセス間で依然としてデッドロックが発生する可能性があり、 第二に、内部タプルを拡張または分割するすべてのケースでこの不変条件を維持することは実用的ではありません。 したがって、依然としてデッドロックを許容する必要があります。

挿入時、通過したページに十分な空きがない場合、正しいタイプのタプルを追加するために追加の内側ページやリーフページ（あるいはその両方）のロックを取得する必要が生じることもあります。しかし、追加するページがどれでなければならないかという厳密な指定はないため、追加のバッファを条件付きでロックすることでデッドロックを回避できます。追加のページのロック取得に失敗した場合は、別のページを試せばよいのです。

検索の走査アルゴリズムは比較的伝統的なものです。非リーフレベルごとに、そのページの共有ロックを取得し、現在の内側タプルのどのノードを訪問する必要があるかを特定し、それらのアドレスを後で調べるためのページのスタックにプッシュします。その後、次のスタック項目を訪問する前に、現在のバッファのロックを解放します。したがって、一度にロックされるページは1つだけであり、デッドロックが発生する余地はありません。その代わり、競合状態（レースコンディション）に対処する必要があります。指し示されたページに到着するころには、並行して行われた挿入によって、ターゲットの内側タプル（またはリーフタプルのチェイン）が別の場所に配置されたデータに置き換えられている可能性があるからです。これに対処するため、挿入アルゴリズムは、内側タプル内の空ではないダウンリンクを変更する際、そのリンクが以前指し示していた下位層の内側タプルまたはリーフタプルチェインの先頭の代わりに、「リダイレクトタプル」を配置します。スキャン（挿入とは異なり）は、そのようなリダイレクトに対応できるように作られている必要があります。親レベルをすでに訪問したスキャンのみがそのようなリダイレクトタプルに到達する可能性があるため、すべての有効なトランザクションがシステムからフラッシュアウトされた後であれば、リダイレクトを削除できます。

DEAD TUPLES

リーフページ上のタプルは、次の4つの状態のいずれかになります。

SPGIST_LIVE: ヒープタプルへの通常の生きたポインタ。

SPGIST_REDIRECT: インデックス内の別の場所へのリンクを含むプレースホルダー。リーフタプルのチェインを別のページに移動する必要がある場合、チェインの先頭タプルの代わりにリダイレクトタプルが挿入されます。これが発生すると親の内側タプルのダウンリンクが更新されますが、並行して実行されるスキャンは、子ページをロックしようとする前に親ページのロックを解放するため、親ページから子ページへと「飛行中（in flight）」である可能性があります。リダイレクトポインタは、そのようなスキャンに移動先を伝える役割を果たします。リダイレクトポインタが必要なのは、そのような並行スキャンが進行中である可能性がある間だけです。最終的に、これは VACUUM によって PLACEHOLDER デッドタプルに変換され、置換の候補となります。（チェインの一部になることは決してない）このようなタプルを見つけた検索は、リダイレクトタプルのことは忘れ、直ちに別の場所に処理を進めるべきです。有効なダウンリンクがこのようなタプルを指すべきではないため、このようなタプルに到達した挿入はエラーを発生させるべきです。

SPGIST_DEAD: タプルはデッドですが、インデックス内の他の場所にある何らかの内側タプルからそこへ向かうリンクが存在するため、ページ上で削除したり、別のオフセットに移動したりすることはできません。（インデックス内に生きた要素が残っていない場合を除き、このようなタプルがチェインの一部になることはありません。）検索はこのエントリを無視する必要があります。挿入処理がこのようなタプルに到着した場合、ページ上に所望の新しいリーフタプルを保持するだけの空きがあればその場で置き換えるか、新しいリーフタプルを配置する場所へのリダイレクトポインタで置き換える必要があります。

SPGIST_PLACEHOLDER: タプルはデッドであり、他の場所からのリンクは存在しないことがわかっています。生きたタプルが削除されたり移動されたりした際にリダイレクトポインタで置き換えられなかった場合、同じページ上の後続のタプルのオフセットが変化するのを防ぐためにプレースホルダーで置き換えられます。プレースホルダーは、新しいタプルをページに追加する際に自由にいじる（置き換える）ことができ、また VACUUM は有効なタプルオフセットの範囲の末尾にあるものをすべて削除します。他の場所からのリンクがプレースホルダータプルに導かれた場合、検索と挿入の両方がエラーを報告すべきです。

ルートページがリーフでもある場合、そのすべてのタプルは LIVE 状態である必要があります。リンクが存在せずオフセット番号を維持する必要もないため、他の状態は必要ありません。

内側ページ上のタプルは、LIVE、REDIRECT、あるいは PLACEHOLDER のいずれかの状態をとることができます。 REDIRECT 状態はリーフページの場合と同じ機能を持ち、内側タプルが別のページに移動された後、並行して行われた検索を必要な移動先に誘導します。期限切れの REDIRECT ポインタは VACUUM によって PLACEHOLDER ステータスに変換され、置換の候補となります。VACUUM は未使用の内側タプルの削除を行わないため、現在 DEAD 状態になることはありません。

VACUUM

VACUUM（より正確には spgbulkdelete）は、インデックス全体に対して単一の順次走査（シーケンシャルスキャン）を実行します。リーフページと内側ページの両方において、古い REDIRECT タプルを PLACEHOLDER ステータスに変換し、ページの末尾にある PLACEHOLDER を削除することができます（これらは生きたタプルのオフセットを維持するために必要ないためです）。リーフページでは、ヒープ TID がバキューム対象の TID と一致するために削除する必要があるタプルをスキャンします。

チェインの先頭にない削除可能なタプルが見つかった場合、単にそれを PLACEHOLDER で置き換え、チェインリンクを更新してチェインから外します。チェインの先頭にあるものの、チェイン内に少なくとも1つの生きたタプルが残っている場合は、その生きたタプルを先頭タプルのオフセットに移動し、他のタプルのオフセットを維持するために先頭タプルを PLACEHOLDER で置き換えます。これにより、親の内側タプルのダウンリンクが有効に保たれます。チェイン内のすべての生きたタプルを削除することになった場合は、先頭タプルを DEAD タプルに置き換え、残りを PLACEHOLDER に置き換えます。これにより、親の内側タプルのダウンリンクは DEAD タプルを指すことになり、前のセクションで説明したルールによってすべてが正常に動作します。

VACUUM は、どのタプルがチェインの先頭であるかを事前に知ることはできませんが、nextOffset リンクの逆マップである先行タプル配列（predecessor array）を構築することで、それを容易に把握できます（つまり、タプル x がタプル y を指しているのを見たら、predecessor[y] = x に設定します）。このとき、先行タプルを持たないものが先頭タプルになります。

VACUUM の実行中にも挿入が発生する可能性があるため、純粋なシーケンシャルスキャンでは、PickSplit や MoveLeafs 操作の結果として、まだ訪問していないリーフページからすでに訪問したリーフページへと移動させられてしまったために、一部のターゲットリーフタプルの削除を見落とす可能性があります。ターゲットの TID を削除し損ねることは許容されないため、このようなケースに対処できるようにアルゴリズムを拡張する必要があります。このような移動が発生した可能性があると認識するのは、VACUUM のスキャン開始後に作成された可能性を示す XID を持つリーフページの REDIRECT タプルを見つけたときです。リダイレクト先の TID を、再確認が必要な場所の「保留リスト（pending list）」に追加します。メインのシーケンシャルスキャンのページ間に、リストされている各 TID を訪問して保留リストを空にします。それが（PickSplit からの）内側タプルを指している場合は、各ダウンリンク TID を保留リストに追加します。リーフページを指している場合は、そのページをバキュームします。（指し示されている単一のチェインだけをバキュームすることも可能ですが、ページ全体をバキュームすればコードが簡素化され、VACUUM が同じページを複数回修正しなければならない確率が下がります。）並行して行われるインデックスの変更がある場合でも、保留リストの処理が無限ループに陥らないようにするため、リストのエントリは即座に削除せず、すべての保留リストの処理が完了した後にのみ削除します。その代わり、処理済みのアイテムには単に「処理済み」のマークを付けます。すでにリストに含まれている TID を追加しても、そのアイテムにすでに処理済みのマークが付いているかどうかにかかわらず、何も行われません（noop）。

spgbulkdelete は、インデックスの空き領域マップ（free space map）も更新します。

現在、spgbulkdelete が実行された場合、spgvacuumcleanup は何もすることがありません。そうでない場合は、リダイレクションとプレースホルダーのクリーンアップ、空き領域マップの更新、および統計情報の収集を行うために、空のターゲットリストを指定して spgbulkdelete スキャンを実行します。

LAST USED PAGE MANAGEMENT

最後に使用されたページのリストには、リーフページ1つと内側ページ3つ（「トリプルパリティ（triple parity）」グループからそれぞれ1つずつ）の計4つのページが含まれています。（実際には、メインツリー用に1つのこのようなリストがあり、NULLツリー用に別のリストがあります。）このリストはインデックスメタページ上の呼び出しの間に保存されますが、WAL トラフィックを減らすために更新が WAL 記録されることはありません。新しいページをいつでも割り当てることができるため、メタページ上の不正確なデータは致命的ではありません。
