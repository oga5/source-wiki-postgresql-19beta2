src/backend/access/rmgrdesc/README

WALリソースマネージャ記述関数

デバッグ目的のために、各WALリソースマネージャには「記述関数（description function）」、すなわちrmgrdesc関数が存在します。rmgrdesc関数はWALレコードを解析し、WALレコードの内容をある程度人間が読める形式で出力します。

すべてのリソースマネージャのrmgrdesc関数はこのディレクトリに集められています。これは、スタンドアロンのpg_waldumpプログラムでも使用されるためです。これらはツリー外のデバッグツールによって使用される可能性もありますが、記述関数も出力形式も安定したAPIの一部とはみなされるべきではありません。

rmgrdesc出力形式のガイドライン

これらのガイドラインの目的は、各rmgr間での不必要な不整合を避け、ユーザーがあまり苦労せずにdesc出力文字列を解析できるようにすることです。これはAPI仕様や交換フォーマットではありません。（いずれにせよ、現時点でこれらのガイドラインに従っているのはheapamとnbtreeのdescルーチンのみです。）

レコードの記述はJSONスタイルのキー/値オブジェクトに似ています。ただし、明示的な「文字列」型や文字列のエスケープはありません。最上位の { } ブラケットは省略する必要があります。例えば以下のようになります。

snapshotConflictHorizon: 0, flags: 0x03

レコードの記述には可変長配列が含まれる場合があります。例えば以下のようになります。

nunused: 5, unused: [1, 2, 3, 4, 5]

ネストされたオブジェクトは { } ブラケットを介してサポートされます。これらは通常、可変長配列の内部に現れます。例えば以下のようになります。

ndeleted: 0, nupdated: 1, deleted: [], updated: [{ off: 45, nptids: 1, ptids: [0] }]

基盤となる物理的なWALレコード構造体のフィールドの順序を忠実に表す順序で出力するようにしてください。解析を容易にするために、キー名は（同じネストレベルで）一意である必要があります。配列内の項目数が配列の前に表示されるようにすると良いでしょう。

個々のWALレコードタイプが独自の規則を考案しても問題ありません。例えば、Heap2のPRUNEレコード記述では、レコードの"redirected"フィールドにカスタム配列形式を使用しています。

... redirected: [1->4, 5->9], dead: [10, 11], unused: [3, 7, 8]

議論の余地はありますが、descルーチンはこれに対して代わりにオブジェクト表記を使用すべきかもしれません。しかし、基盤となる物理データ構造に関する有用な情報を伝える場合には、カスタム形式を使用することに価値があります。

このアドホックな形式には、"dead"および"unused"配列（これらはページオフセット番号配列の標準的なdesc規則に従います）に使用される形式に近いという利点があります。これは、表示されている"redirected"要素が単なるページオフセット番号のペアであることを示唆しています（実際にそのように動作します）。

rmgrdesc_utils.cには、この形式でデータを出力するためのヘルパー関数がいくつか含まれています。
