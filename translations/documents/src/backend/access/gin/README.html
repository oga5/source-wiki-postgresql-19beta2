src/backend/access/gin/README

PostgreSQL用Gin ===============

Ginはjfg://networks (http://www.jfg-networks.com/) のスポンサーシップにより開発されました。

GinはGeneralized Inverted Index（汎用逆インデックス）の略であり、飲み物ではなく、魔神（genie）と考えるべきです。

Generalized（汎用）とは、インデックスがどの演算を高速化するかを知らないことを意味します。代わりに、特定のデータ型に対して定義されたカスタムストラテジを使用して動作します（PostgreSQLドキュメントの「インデックスメソッドのストラテジ」を参照してください）。その意味で、GinはGiSTに似ており、事前定義された比較ベースの演算を持つbtreeインデックスとは異なります。

逆インデックス（inverted index）とは、(キー, ポスティングリスト)のペアの集合を格納するインデックス構造であり、ここで「ポスティングリスト」はキーが発生するヒープ行の集合です。（テキストドキュメントには通常、多くのキーが含まれます。）Ginインデックスの主な目的は、PostgreSQLにおける高度にスケーラブルな全文検索のサポートです。

Ginインデックスは、キー値に対して構築されたB-treeインデックスで構成されます。ここで、各キーはインデックス対象のアイテムの要素（配列の要素、tsvectorの語彙素など）であり、リーフページの各タプルには、アイテムポインタに対するB-treeへのポインタ（ポスティングツリー）、またはリストが十分に小さい場合はアイテムポインタの単純なリスト（ポスティングリスト）のいずれかが含まれます。

注意：キー（エントリ）ツリーには削除操作がありません。この理由は、私たちの経験上、大規模なコーパスにおける個別の単語の集合の変化は非常に緩やかであるためです。これにより、コードと同時実行アルゴリズムが大幅に簡素化されます。

PostgreSQLのコアには、一次元配列（例：integer[]、text[]）に対する組み込みのGinサポートが含まれています。以下の演算が利用可能です。

  • contains: value_array @> query_array
  • overlaps: value_array && query_array
  • is contained by: value_array <@ query_array

概要 ----

=# create index txt_idx on aa using gin(a);

機能 ----

  • 同時実行性
  • ライトアヘッドロギング（WAL）。（クラッシュからの回復性。）
  • ユーザ定義の演算子クラス（opclass）。（仕組みはGiSTに似ています。）
  • 最適化されたインデックス作成（maintenance_work_memを使用してメモリ内にポスティングを蓄積します。）
  • 演算子クラスを介したテキスト検索サポート
  • GUC変数を使用した、返される結果セットに対する緩やかな上限：

    • gin_fuzzy_search_limit

Ginのあいまい制限 -----------------

全文検索が非常に大きな結果セットを返す状況がよくあります。ディスクからタプルを読み込んでソートするのには多くの時間がかかる可能性があるため、これは本番環境では受け入れられません。（検索自体は非常に高速であることに注意してください。）

このようなクエリには通常、非常に出現頻度の高い語彙素が含まれているため、結果はあまり役に立ちません。このようなクエリの実行を容易にするために、Ginには返されるセットのサイズに対する設定可能な緩やかな上限があり、これは'gin_fuzzy_search_limit' GUC変数によって決定されます。デフォルトは0（制限なし）に設定されています。

ゼロ以外の検索制限が設定されている場合、返されるセットは、結果セット全体からランダムに選択されたサブセットになります。

「緩やか（Soft）」とは、クエリやシステムの乱数生成器の品質に応じて、実際に返される結果の数が指定された制限と異なる可能性があることを意味します。

経験上、'gin_fuzzy_search_limit'の値は数千（例：5000〜20000）にするとうまく機能します。これは、この数よりも少ないタプルの結果セットを返すクエリに対しては、'gin_fuzzy_search_limit'が効果を持たないことを意味します。

インデックス構造 ----------------

GINインデックスがインデックスを作成する「アイテム」は、0個以上の「キー」を含む複合値です。例えば、アイテムが整数配列である場合、キーは個々の整数値になります。インデックスは、アイテムそのものではなく、実際にはキー値を格納し、検索します。GIN opclassのpg_opclassエントリにおいて、opcintypeはアイテムのデータ型であり、opckeytypeはキーのデータ型です。GINは、アイテムが多くのキーを含み、同じキー値が多くの異なるアイテムに現れるケースに最適化されています。

GINインデックスには、メタページ、キーエントリのbtree、そして場合によっては「ポスティングツリー」ページが含まれます。ポスティングツリーページは、キーエントリがbtreeページに収まらないほど多くのヒープタプルポインタを取得したときに、オーバーフローを保持します。さらに、高速更新（fast-update）機能が有効な場合、メインのbtreeにまだマージされていない「保留中（pending）」のキーエントリを保持する「リストページ」が存在することがあります。検索を行う際、リストページは線形にスキャンされる必要があるため、保留中のエントリが多すぎることになる前にメインのbtreeにマージされるべきです。保留リストの利点は、数千のエントリの一括挿入が、個別の挿入よりもはるかに高速になる可能性があることです。（この利点は、主に同じキーが複数の新しいヒープタプルに現れる場合に、複数の検索/挿入を行う必要がないことから得られます。）

キーエントリは、名目的には他のインデックスタイプで使用されるものと同じIndexTupleフォーマットですが、リーフキーエントリは通常、複数のヒープタプルを参照するため、重要な違いがあります。（通常のインデックス型を構築してからそれを変更することで動作するGinFormTupleを参照してください。）知っておくべきポイントは以下の通りです。

  • 単一列インデックスでは、キータプルにはキーデータのみが含まれますが、複数列インデックスでは、キータプルにはペア（列番号, キーデータ）が含まれ、列番号はint2として格納されます。これは、異なる列で異なるキーデータ型をサポートするために必要です。タプルのこの部分は、通常のルールに従ってindex_form_tupleによって構築されます。列番号（存在する場合）がnullになることはありませんが、キーデータはnullになる可能性があり、その場合は通常通りnullビットマップが存在します。（インデックスタプルの通常通り、nullビットマップのサイズはINDEX_MAX_KEYSに固定されています。）
  • キーデータがnullである場合（すなわち、IndexTupleHasNulls()が真の場合）、名目上のインデックスデータの直後（すなわち、オフセットIndexInfoFindDataOffsetまたはIndexInfoFindDataOffset + sizeof(int2)）に、nullエントリの「カテゴリ」を示すバイトが存在します。考えられるカテゴリは以下の通りです。

    • 1 = インデックス可能なアイテムから抽出された通常のnullキー値 2 = ゼロキーのインデックス可能なアイテムのプレースホルダ 3 = nullのインデックス可能なアイテムのプレースホルダ プレースホルダのnullエントリがインデックスに挿入されるのは、そうしないと空またはnullのインデックス可能なアイテムに対するインデックスエントリがまったく存在しなくなり、フルインデックススキャンが実行できなくなったり、様々なコーナーケースで誤った答えが返されたりするためです。異なるカテゴリのnullエントリは、btreeによって個別のキーとして扱われますが、同じカテゴリのnullエントリに対するヒープのアイテムポインタは、通常のキーエントリと同様に1つのインデックスエントリにマージされます。

  • btreeリーフレベルのキーエントリでは、次のSHORTALIGN境界に、圧縮フォーマット（ポスティングリスト圧縮のセクションを参照）のアイテムポインタのリストがあり、インデックス可能なアイテムにこのキーが含まれるヒープタプルを指します。これは「ポスティングリスト」と呼ばれます。

リストが大きすぎてインデックスタプルがインデックスページに収まらない場合、ItemPointerは別の1つ以上のポスティングページに押し出され、キーエントリ自体には何も表示されません。この独立したページは「ポスティングツリー」と呼ばれます（以下を参照）。いずれの場合も、キーに関連付けられたItemPointerはソートされた順序で簡単に読み出すことができることに注意してください。これはスキャンアルゴリズムによって依存されています。

  • リーフキーエントリのインデックスタプルヘッダフィールドは、以下のように変則的に使用されます。

1) ポスティングリストの場合：

  • ItemPointerGetBlockNumber(&itup->t_tid)には、インデックスタプルの開始位置からポスティングリストへのオフセットが含まれます。

    • アクセス用マクロ：GinGetPostingOffset(itup) / GinSetPostingOffset(itup,n)

  • ItemPointerGetOffsetNumber(&itup->t_tid)には、ポスティングリスト内の要素数（ヒープのアイテムポインタの数）が含まれます。

    • アクセス用マクロ：GinGetNPosting(itup) / GinSetNPosting(itup,n)

  • IndexTupleHasNulls(itup)が真の場合、nullカテゴリバイトはGinGetNullCategory(itup,gs) / GinSetNullCategory(itup,gs,c)でアクセス/設定できます。
  • ポスティングリストはGinGetPosting(itup)でアクセスできます。
  • GinItupIsCompressed(itup)の場合、ポスティングリストは圧縮フォーマットで格納されます。そうでない場合は、単なるItemPointerの配列です。新しいタプルは常に圧縮フォーマットで格納されますが、データベースが9.3以前のバージョンから移行された場合は、非圧縮のアイテムが存在する可能性があります。

2) ポスティングツリーの場合：

  • ItemPointerGetBlockNumber(&itup->t_tid)には、ポスティングツリーのルートのインデックスブロック番号が含まれます。

    • アクセス用マクロ：GinGetPostingTree(itup) / GinSetPostingTree(itup, blkno)

  • ItemPointerGetOffsetNumber(&itup->t_tid)には、マジックナンバーGIN_TREE_POSTINGが含まれます。これにより、ポスティングリストの場合と区別されます（この値は十分に大きいため、それほど多くのヒープアイテムポインタがインデックスページに収まることはあり得ません）。この値は、GinSetPostingTreeマクロによって自動的に挿入されます。
  • IndexTupleHasNulls(itup)が真の場合、nullカテゴリバイトはGinGetNullCategory(itup,gs) / GinSetNullCategory(itup,gs,c)でアクセス/設定できます。
  • ポスティングリストは存在しないため、アクセスしてはなりません。

どちらのケースが適用されるかを判断するには、マクロGinIsPostingTree(itup)を使用します。

どちらの場合も、itup->t_info & INDEX_SIZE_MASKにはタプルの実際の合計サイズが含まれ、INDEX_VAR_MASKおよびINDEX_NULL_MASKビットは、index_form_tupleによって設定される通常の意味を持ちます。

btreeの非リーフレベルのインデックスタプルには、上記のようにオプションの列番号、キーデータ、およびnullカテゴリバイトが含まれます。これらにはポスティングリストは含まれません。ItemPointerGetBlockNumber(&itup->t_tid)は次の下位btreeレベルへのダウンリンクであり、ItemPointerGetOffsetNumber(&itup->t_tid)はInvalidOffsetNumberです。ダウンリンクの取得/設定には、アクセス用マクロGinGetDownlink/GinSetDownlinkを使用します。

「保留リスト（pending list）」ページに現れるインデックスエントリも、少し異なった動作をします。オプションの列番号、キーデータ、およびnullカテゴリバイトは、他のGINインデックスエントリと同様です。ただし、保留中のエントリに関連付けられたヒープのアイテムポインタは常に正確に1つであり、非GINインデックスと同様にt_tidヘッダフィールドに格納されます。ポスティングリストはありません。さらに、保留リストを検索するコードは、特定のヒープタプルに対するすべてのエントリが保留リスト内で連続して現れ、列番号プラスキーデータによってソートされていることを前提としています。GIN_LIST_FULLROWページフラグビットは、特定のヒープタプルのエントリが複数の保留リストページにまたがって分散しているかどうかを示します。GIN_LIST_FULLROWが設定されている場合、そのページには1つ以上のヒープタプルのすべてのエントリが含まれます。GIN_LIST_FULLROWがクリアされている場合、そのページには1つのヒープタプルのエントリのみが含まれ、*かつ*それらはそのタプルのすべてのエントリではありません。（したがって、エントリが1つの保留リストページにすべて収まらないヒープタプルは、そのタプルのためにそれらのページを占有しなければならず、たとえこれにより前のページやそのタプルの最後のページで多くのスペースが無駄になったとしても同様です。）

GINは、nbtreeとは異なる方法でダウンリンクとピボットキーを内部ページタプルにパックします。Lehman & Yaoはこれを以下のように定義しています。

P_0, K_1, P_1, K_2, P_2, ... , K_n, P_n, K_{n+1}

ここで、P_iはダウンリンク、K_iはキーです。K_iはP_{i-1}とP_iの間のキースペースを分割します（0 <= i <= n）。K_{n+1}はハイキー（high key）です。

内部ページタプルでは、キーとダウンリンクがグループ化されます。nbtreeは、キーとダウンリンクを以下のようにタプルにパックします。

(K_{n+1}, None), (-Inf, P_0), (K_1, P_1), ... , (K_n, P_n)

ここではタプルが括弧内に示されています。したがって、ハイキーは個別に格納されます。P_iはK_iとグループ化されます。P_0は-Infキーとグループ化されます。

GINは、異なる方法でキーとダウンリンクをタプルにパックします。

(P_0, K_1), (P_1, K_2), ... , (P_n, K_{n+1})

P_iはK_{i+1}とグループ化されます。-Infキーは不要です。

K_{n+1}キーに関しては、いくつかの追加の注意事項があります。 1) 最右端ページの入力ツリーでは、P_nと結合されたキーは実際には重要ではありません。ハイキーは無限大とみなされます。 2) ポスティングツリーでは、P_nと結合されたキーは常に重要ではありません。最右端以外のページのハイキーは個別に格納され、GinDataPageGetRightBound()を介してアクセスされます。

ポスティングツリー ------------------

ポスティングリストが大きすぎてキーエントリ内にインラインで格納できない場合、ポスティングツリーが作成されます。ポスティングツリーはB-tree構造であり、ItemPointerがキーとして使用されます。

内部ポスティングツリーページは、標準の PageHeader と、他の GIN ページと同じ「不透明な（opaque）」構造体を使用しますが、通常のインデックスツプルは含みません。代わりに、ページの内容は PostingItem 構造体の配列です。各 PostingItem は、子ページのブロック番号と、その子ページの右境界（ItemPointer として表される）で構成されます。ページの右境界は、ページヘッダーの直後、PostingItem 配列の前に格納されます。

ポスティングツリーのリーフページも、標準の PageHeader と不透明な構造体を使用し、ページの右境界はページヘッダーの直後に格納されますが、ページの内容は複数の圧縮されたポスティングリストで構成されます。圧縮されたポスティングリストは、ページヘッダーと pd_lower の間に、次々と連続して格納されます。pd_lower と pd_upper の間の領域は使用されないため、ポスティングツリーリーフページのフルページイメージでは、中央の未使用領域をスキップできます（XLogRecData で buffer_std = true）。

アイテムポインタは、1つの大きなリストではなく、複数の独立した圧縮ポスティングリスト（セグメントとも呼ばれます）に格納されます。これにより、特定のアイテムポインタへのランダムアクセスが高速化されます。圧縮リスト内のアイテムを見つけるには、リストを最初から読み込む必要がありますが、アイテムが複数のリストに分割されている場合は、まず探しているアイテムが含まれるリストまでスキップし、そのセグメントだけを読み込むことができます。また、更新時には影響を受けるセグメントのみを再エンコードするだけで済みます。

ポスティングリストの圧縮 ------------------------

1ページにできるだけ多くのアイテムポインタを収めるために、ポスティングツリーのリーフページや、エントリツリーのリーフツプル内にインラインで格納されるポスティングリストでは、軽量な形式の圧縮が使用されます。アイテムポインタがソートされた順序で格納されているという事実を利用します。各アイテムポインタのブロック番号とオフセット番号を個別に格納する代わりに、前のアイテムとの差分を格納します。それ自体では大した効果はありませんが、これにより、いわゆる varbyte エンコーディングを使用して圧縮できるようになります。

Varbyte エンコーディングは整数をエンコードする方法であり、大きな数値のスペースを犠牲にして、小さな数値のスペースを削減できます。各整数は可変バイト数で表されます。varbyte エンコーディングにおける各バイトの最上位ビットは、次のバイトがまだこの数値の一部であるかどうかを決定します。したがって、1つの varbyte エンコードされた数値を読み取るには、最上位ビットが設定されていないバイトが見つかるまでバイトを読み取る必要があります。

エンコード時、アイテムポインタを構成するブロック番号とオフセット番号は、1つの整数に結合されます。オフセット番号は下位11ビットに格納され（ginpostinglist.c の MaxHeapTuplesPerPageBits を参照）、ブロック番号は上位ビットに格納されます。これには合計43ビットが必要であり、都合よく最大6バイトに収まります。

圧縮されたポスティングリストは、GinPostingList 構造体でやり取りされ、ディスクに格納されます。リストの最初のアイテムは、通常の ItemPointerData として非圧縮で格納され、その後にバイト単位のリストの長さ、その後にパックされたアイテムが続きます。

並行性 -----------

エントリツリーと各ポスティングツリーはBツリーであり、同じレベルの兄弟ページを接続する右リンク（right-link）を持ちます。これは、通常のBツリー indexam（Lehman & Yao によって考案されたもの）で使用されているのと同じ構造ですが、GIN ツリーの逆方向スキャンはサポートしていないため、左リンク（left-link）は必要ありません。エントリツリーのリーフには専用のハイキー（high key）はなく、代わりに最大のリーフツプルがハイキーとして機能します。エントリツリーからツプルが削除されることはないため、これで機能します。

エントリツリーとポスティングツリーを操作するために使用されるアルゴリズムを以下に示します。

リーフページの特定

読み取りを実行するために GIN btree 内のリーフページを検索するとき、ダウンリンクを使用してルートページからリーフへと下降し、一度に1つのページに対してピンと共有ロックを取得します。したがって、次のページでピンと共有ロックを取得する前に、前のページのピンと共有ロックを解放します。

以下の図は、リーフページを見つけた後のツリーの状態を示しています。小文字はツリーのページを表します。'S' はページ上の共有ロックを表します。

a / | \ b c d / | \ | \ | \ eS f g h i j k

右への移動

並行するページの分割によってキースペースが右に移動するため、ダウンリンクをたどった後、探しているキーを実際に含んでいるページが、到達したページの右側のどこかにある可能性があります。その場合、探しているページが見つかるまで右リンクをたどります。

右に移動する際、現在のページからピンと共有ロックを解放する前に、右の兄弟ページでピンと共有ロックを取得します。このメカニズムは、削除されたページに移動してしまうのを防ぐために設計されました。そこを指している rightlink のロックを保持したまま、右の兄弟ページに移動します。したがって、誰も rightlink を並行して更新せず、それに応じて右の兄弟ページを削除しないことが保証されます。

以下の図は、右への移動中に一度に2つのページがロックされている状態を示しています。

a / | \ b c d / | \ | \ | \ eS fS g h i j k

挿入

挿入に適したリーフを見つける間も、一度に1つのページを共有ロックしながら、ルートからリーフへと下降します。しかし、挿入時にはルートページや内部ページのピンを解放しません。これにより、並行する分割によって親ページが変更されないと仮定すれば、ダウンリンク挿入のためのバッファハッシュテーブルのルックアップをいくらか節約できます。リーフに到達したら、そのページを排他モードで再ロックします。

以下の図は、排他モードでロックされ、挿入の準備ができているリーフページを示しています。'P' と 'E' はそれぞれピンと排他ロックを表します。

aP / | \ b cP d / | \ | \ | \ e f g hE i j k

挿入によってページの分割が発生する場合、左の子ページのロックを解除する前に、親ページが排他モードでロックされます。したがって、挿入アルゴリズムは、子ページから始めて、親ページと子ページの両方を一度に排他ロックできます。

以下の図は、リーフページの分割後のツリーの状態を示しています。'q' は分割によって生成された新しいページです。親 'c' にダウンリンクが挿入されようとしています。

aP / | \ b cE d / | \ / | \ | \ e f g hE q i j k

ページの削除

バキューム（Vacuum）がエントリツリーからツプルやページを削除することはありません。エントリツリーのリーフを rightlinks によって論理的な順序でトラバースし、ポスティングリストから削除可能な TID を削除します。ポスティングツリーは、エントリツリーのリーフからのリンクによって処理されます。これらは2つの段階でバキュームされます。第1段階では、削除可能な TID がリーフから削除されます。第1段階で少なくとも1つの空のページが検出された場合、第2段階で ginScanPostingTreeToDelete() が空のページを削除します。

ginScanPostingTreeToDelete() は、ツリー全体を深さ優先でトラバースします。これは、ツリーのルートに対する完全なクリーンアップロック（full cleanup lock）から始まります。このロックは、ページを削除している間、このツリーへのすべての並行挿入を防止します。ただし、ロックする前にルートをトラバースした、処理中のリーダーがまだ存在する可能性があります。

以下の図は、ページ削除アルゴリズムがツリーの最も左のリーフまでトラバースした後のツリーの状態を示しています。

aE / | \ bE c d / | \ | \ | \ eE f g h i j k

削除アルゴリズムは、現在調査中のパスを構成するページの左の兄弟ページに対する排他ロックを保持し続けます。したがって、現在のページが削除される場合、ダウンリンクと rightlink の両方を削除するために必要なすべてのページがすでにロックされています。これにより、並行する右への移動とデッドロックする可能性がある、右から左へのページロック順序を回避できます。

ページの削除と並行する検索が、削除対象のページへのポインタをすでに読み取っており、それをたどろうとしている可能性があります。ページには、その左の兄弟ページの right-link を経由するか、親ページ内のダウンリンクを経由して到達できます。

バックエンドが right-link を経由して削除されたページに到達するのを防ぐため、右への移動アルゴリズムは、右のページのロックが取得されるまで現在のページのロックを解放しません。

ダウンリンクはより複雑です。ツリーを下降する検索は、子ページをロックする前に親ページのロックを解放しなければなりません。さもないと、子ページの並行分割とデッドロックする可能性があります。ページの分割は、すでに子ページのロックを保持している状態で親ページをロックするためです。したがって、削除されたページをすぐに再利用することはできません。代わりに、このページを参照するために待機している可能性のあるすべてのトランザクションが終了するのを待つ必要があります。対応するプロセスは、ページが削除済みとしてマークされていることを観察し、それに応じて回復する必要があります。

以下の図は、ページ削除アルゴリズムがさらにツリーをトラバースした後のツリーの状態を示しています。現在調査中のパスは 'a-c-h' です。'c' と 'h' のそれぞれの左の兄弟ページである 'b' と 'g' も排他ロックされています。

aE / | \ bE cE d / | \ | \ | \ e f gE hE i j k

次の図は、ページ 'h' が削除された後のツリーの状態を示しています。このページには 'deleted' フラグと、このページを訪れる可能性のある最新の xid がマークされています。'c' から 'h' へのダウンリンクも削除されています。

aE / | \ bE cE d / | \ \ | \ e f gE hD iE j k

ただし、並行するリーダーが、削除する前に 'c' から 'h' へのダウンリンクを見ていた可能性は依然としてあります。その場合、このリーダーは削除されていないページが見つかるまで 'h' から右へ移動します。ページ 'h' の xid マークは、そのようなリーダーがすべていなくなるまで、このページが再利用されないことを保証します。次に調査されるリーフページは 'i' です。'g' は 'i' の左の兄弟ページになるため、ロックされたままになります。

次の図は、'i' と 'c' が削除された後のツリーの状態を示しています。内部ページ 'c' は、ダウンリンクがなくなったために削除されました。調査中のパスは 'a-d-j' です。ページ 'b' と 'g' は、'd' と 'j' の兄弟ページとしてロックされています。

aE / \ bE cD dE / | \ | \ e f gE hD iD jE k

スタンバイでのページ削除の再プレイ中、ページの左の兄弟ページ、対象ページ、およびその親ページがこの順序でロックされます。この順序により、並行する読み取りとのデッドロックが発生しないことが保証されます。

述語ロック -----------------

GIN は、シリアライザブルスナップショット分離のために述語ロック（predicate locking）をサポートしています。述語ロックは、スキャンが値の範囲をスキャンしたことを表します。これらは物理的なページそのものに関係するのではなく、論理的なキー値に関係します。ページ上の述語ロックは、現在そこに一致するツプルが存在するかどうかに関係なく、そのページに属するはずのキー範囲をカバーします。言い換えれば、インデックスページ上の述語ロックは、インデックスツプル間の「ギャップ（隙間）」をカバーします。偽陽性を最小限に抑えるため、述語ロックは可能な限り細かいレベルで取得されます。

  • Bツリーインデックスと同様に、すべての挿入はリーフレベルで行われるため、リーフページのみをロックするだけで十分です。
  • 完全一致検索（すなわち、部分一致検索ではない場合）において、キーエントリがポスティングツリーを持つ場合、そのキーエントリのみに対するロックを表すために、ポスティングツリーのルートページをロックします。そうでない場合は、エントリツリーページをロックします。また、一致するものが見つからない場合も、エントリが存在したはずの「ギャップ」をロックするために、エントリツリーページをロックします。
  • 部分一致検索では、値の間の「ギャップ」を表すために、ポスティングツリールートのロックに加えて、スキャンするすべてのエントリリーフページをロックします。
  • エントリリーフページとポスティングツリールートのロックに加えて、すべてのスキャンはメタページのロックを取得します。これは、高速更新（fast update）のペンディングリストへの挿入とインターロックするためです。ペンディングリストへの挿入はツリー内のどこにでも属する可能性があり、メタページのロックがそれを表します。

fastupdate ペンディングリストのインターロックは、fastupdate=on の場合、事実上常にフルインデックスロックを取得することを意味するため、多くの偽陽性が発生する可能性があります。

互換性 -------------

TID の圧縮は 9.4 で導入されました。9.3 以前のバージョンからの pg_upgrade により、一部の GIN インデックスは非圧縮形式のままになっている可能性があります。互換性のために、古い非圧縮形式もサポートされています。これを処理するために、以下のルールが使用されます。

  • GIN_ITUP_COMPRESSED フラグは、ポスティングリストを含むインデックスタプルを示します。

    • このフラグは ItemPointerGetBlockNumber(&itup->t_tid) の上位ビットに格納されます。 フラグの確認には GinItupIsCompressed(itup) を使用します。

  • 新しいフォーマットのポスティングツリーページには GIN_COMPRESSED フラグが付けられます。

    • このフラグの確認および設定には、マクロ GinPageIsCompressed(page) および GinPageSetCompressed(page) が使用されます。

  • すべてのスキャン操作はポスティングリストのフォーマットを確認し、対応するコードを使用してその内容を読み取ります。
  • 未圧縮のポスティングリストを含むインデックスタプルを更新する際、それは圧縮されたリストを含む新しいインデックスタプルに置き換えられます。
  • 未圧縮のポスティングツリーのリーフページを更新する際、それは圧縮されます。
  • vacuum が未圧縮のポスティングリスト内にデッドTIDを検出した場合、それらは圧縮されたポスティングリストに変換されます。これは、圧縮されたポスティングリストが、未圧縮のリストが占有していたスペースに収まることを前提としています。言い換えれば、デッドアイテムが削除された圧縮バージョンのページは、古い未圧縮のバージョンよりも占有スペースが少なくなると仮定しています。

制限事項 -----------

  • Gin は scan->kill_prior_tuple & scan->ignore_killed_tuples を使用しません
  • Gin は、等価一致、または「部分一致」機能を使用した単純な範囲一致によってのみエントリを検索します。
