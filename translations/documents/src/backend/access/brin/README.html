Block Range Indexes (BRIN) ==========================

BRINインデックスは、極めて大規模なテーブルの非常に高速なスキャンを可能にすることを目的としています。

BRINインデックスの基本的な考え方は、連続するヒープページのグループ（ページレンジ）における要約値を追跡することです。例えば、btree演算子クラスを持つデータ型における最小値と最大値、あるいは幾何データ型におけるバウンディングボックス（境界ボックス）などです。これらの値を使用することで、クエリの条件（quals）に応じて、テーブルスキャン中に該当するページのスキャンを回避できます。

これに対するコストは、タプルが挿入されるたびに、各ページレンジの格納された要約値を更新しなければならないことです。

Access Method Design --------------------

このタイプのインデックスの内部にはアイテムポインタが格納されないため、amgettupleインターフェースをサポートすることはできません。代わりに、amgetbitmapサポートのみを提供します。amgetbitmapルーチンは、クエリ条件に一致するページレンジ内のすべてのページを含む、損失あり（lossy）のTIDBitmapを返します。BitmapHeapScanノードでの再チェック（recheck）ステップにより、クエリ条件に従って可視でないタプルが取り除かれます。

演算子クラスは以下のエントリを持つ必要があります。

  • すべての演算子クラスで同一の、汎用サポートプロシージャ (pg_amproc):
  • "opcinfo" (BRIN_PROCNUM_OPCINFO) は、インデックスの作成またはスキャンのための構造体を初期化します。
  • "addValue" (BRIN_PROCNUM_ADDVALUE) は、インデックスのタプルとヒープのアイテムを受け取り、ヒープのアイテムの値が含まれるようにインデックスのタプルを変更する可能性があります。
  • "consistent" (BRIN_PROCNUM_CONSISTENT) は、インデックスのタプルとクエリ条件を受け取り、インデックスのタプルの値がクエリ条件に一致するかどうかを返します。
  • "union" (BRIN_PROCNUM_UNION) は、2つのインデックスのタプルを受け取り、最初のタプルが2つの和（union）を表すように変更します。

    • プロシージャ番号10までは、将来の拡張のために予約されています。

さらに、各演算子クラスには追加のサポート関数が必要です。

  • Minmaxスタイルの演算子クラス:
  • プロシージャ番号11〜14は、その型に対する不等号演算子を実装する関数に使用され、順に、未満（less than）、以下（less or equal）、以上（greater or equal）、超（greater than）となります。

異なる設計を使用する演算子クラスには、異なる追加のプロシージャ番号が必要になります。

また、プランナがクエリを実行するためにインデックスを選択できるように、演算子クラスは演算子 (pg_amop) エントリを持つ必要があります。

  • Minmaxスタイルの演算子クラス:
  • btreeと同じ演算子 (<=, <, =, >=, >)

各インデックスのタプルは、いくつかのNULLビットと、演算子クラス固有のいくつかの値を格納します。これらは、列数の2倍の長さを持つ単一のNULLビットマスクに格納されます。汎用のNULLビットは、各列について以下を示します。

  • bt_hasnulls: ページレンジ内にNULL値が1つでも存在するかどうか
  • bt_allnulls: ページレンジ内のすべての値がNULLであるかどうか

演算子クラス固有の値は以下の通りです。

  • Minmaxスタイルの演算子クラス
  • レンジ内のすべてのタプルにおける最小値
  • レンジ内のすべてのタプルにおける最大値

addValueおよびUnionサポートプロシージャは、メモリ上のBRINタプルに格納したい値を注意深くdatumCopy()する必要があり、古い値を置き換える際には古いコピーをpfree()しなければならないことに注意してください。タプルから参照される一部の値は存続し、他の値は消滅するため、これを自動化できるようなメモリコンテキストの明確に定義された生存期間は存在しません。

The Range Map -------------

特定のページレンジに対するインデックスのタプルを見つけるために、レンジマップ、略して「revmap」と呼ばれる内部構造があります。これはページレンジごとに1つのTIDを格納しており、そのレンジを要約するインデックスのタプルのアドレスを指します。マップのエントリは固定サイズであるため、簡単な算術演算によって、任意のヒープページに対するレンジマップエントリのアドレスを計算することができます。

要約済みのページレンジに新しいヒープタプルが挿入されると、既存のインデックスのタプルと新しいヒープタプルを比較します。いずれかのインデックス対象列において、ヒープタプルがインデックスのタプルによって提供される要約データの範囲外である場合（または、新しいヒープタプルにNULL値が含まれているが、インデックスのタプルがNULLなしを示している場合）、インデックスは新しい値で更新されます。多くの場合、インデックスのタプルをその場で（in-place）更新できますが、新しいインデックスのタプルが古いものより大きく、ページ内に十分な空きスペースがない場合は、新しい値を持つ新しいインデックスのタプルを作成する必要があります。レンジマップはそれを指すように迅速に更新され、古いインデックスのタプルは削除されます。

レンジマップが無効なTIDを指している場合、対応するページレンジは要約されていないとみなされます。要約されていないページにタプルが追加されても、何も行う必要はありません。

BRINインデックスに従ってテーブルをスキャンするには、レンジマップを順次スキャンします。これにより、ページレンジの昇順でインデックスのタプルが得られます。クエリ条件が各インデックスのタプルと照合され、一致する場合、そのページレンジ内の各ページが出力TIDビットマップの一部として返されます。一致しない場合はスキップされます。無効なインデックスTIDを返すレンジマップエントリ、すなわち要約されていないページレンジも、TIDビットマップに返されます。

revmapは、インデックスのメインフォークの最初の数ブロック、メタページの直後に格納されます。revmapを別のページで拡張する必要がある場合は常に、そのページにある既存のタプルが他のページに移動されます。

ヒープタプルは、制限なくどこからでも削除できます。ヒープタプルが要約データの制約値の1つ（すなわち、btree演算子クラスを持つデータ型の場合は最小値または最大値）である場合、将来そのレンジで要約を再実行する必要があることを認識し、要約値をより厳密に絞り込めるように、対応するインデックスのタプルに何らかのマークを付けておくことは有用かもしれません。

Summarization -------------

インデックス作成時には、テーブル全体がスキャンされます。ページレンジごとに、各インデックス対象列の要約値とNULLビットマップが収集され、インデックスに格納されます。テーブルの末尾にある、部分的に埋まったページレンジも要約されます。

テーブルの末尾に新しいタプルが挿入されると、末尾の部分的なページレンジを要約するインデックスのタプルが更新されることがあります。最終的にそのページレンジが満杯になると、新しいタプルはまだ要約されていない新しいページレンジに属することになります。これらの挿入では新しいインデックスエントリは作成されず、代わりに、そのページレンジは後で処理されるまで要約されないままになります。

テーブルに対してVACUUMが実行されると、要約されていないすべてのページレンジが要約されます。このアクションは、ユーザーがbrin_summarize_new_values()を介して呼び出すこともできます。これらのプロシージャは両方とも、要約されていないすべてのレンジをスキャンし、要約タプルを作成します。これも同様に、テーブルの末尾にある部分的に埋まったページレンジを含みます。

Vacuuming ---------

BRINインデックスにはヒープのTIDが格納されないため、ヒープタプルが削除されたときにインデックスをスキャンする必要はありません。ヒープタプルが削除された場合、一部の要約値をより厳密に絞り込める可能性がありますが、これは最適化の機会にすぎず、正確性の問題ではありません。既存の値から値を「差し引く」よりも、影響を受けるページレンジで要約を再実行する必要性としてこれを表現する方が単純です。これは現在実装されていません。

テーブルにBRINインデックス以外のインデックスがない場合、詳細なインデックススキャンを行う必要がないため（したがって、バキュームが削除対象のTIDを保存する必要がないため）、バキュームによるmaintenance_work_memの使用量を大幅に削減できることに注意してください。ただし、主キーはbtreeのみであるため、BRINがテーブル内の唯一のインデックスになる可能性は低く、そのためこの最適化は実装していません。

Optimizer ---------

オプティマイザは、列に対する演算子クラスのpg_amopエントリに基づいてインデックスを選択します。

Future improvements -------------------

  • 異なるサイズのページレンジ？

    • 現在の設計では、BRINインデックスの各「インデックスエントリ」は同じページ数をカバーしています。これには固執すべき理由はありません。要約値をよりコンパクトにできるのであれば、一部のインデックスエントリがより小さなページレンジをカバーするようにインデックスが自己調整できるようにすることは理にかなっているかもしれません。これにより、インデックス自体のBRINオーバーヘッドは大きくなりますが、スキャン中のページレンジの刈り込み（pruning）をより効果的に行える可能性があります。極端な例として、1ページあたり1つのインデックスのタプルがある場合、要約値が厳密になるため、ほとんどのヒープページの読み取りをスキップできるようになりますが、インデックス自体が過大なスペースを占有することになります。逆の極端な例として、テーブル全体を要約する単一のタプルの場合、インデックスは非常に小さくなりますが、何も刈り込むことができなくなります。これはおそらく、レンジマップ自体をインデックスとして使用することで機能させることができるでしょう。

  • TIDBitmapのよりコンパクトな表現？

    • TIDBitmapは、ビットマップスキャンを表現するために使用される構造体です。損失ありページレンジの表現は、私たちの目的には最適ではありません。なぜなら、レンジ内のページを表現するためにBitmapsetを使用しているからです。大きなレンジ内のすべてのページを返すことになるため、代わりに、開始ページ番号と終了ページ番号を使用してレンジを表現する構造体を許可する方が便利かもしれません。

  • より優れたバキューム処理？

    • バキューム処理中に、削除されたタプルに関するより有用な情報をBRINインデックスに渡せるようにすること、すなわち、コールバックが各タプルのTIDを渡す必要がないようにすることは有用かもしれません。例えば、TIDの代わりにブロック番号を渡すコールバックが必要になるかもしれません。これにより、多くのタプル削除が発生したブロックに対して、いつ要約を再実行すべきかを判断するのに役立ちます。
