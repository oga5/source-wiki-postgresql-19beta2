GiST インデックス

このディレクトリには、Postgres の GiST インデックスの実装が含まれています。

GiST は Generalized Search Tree (一般化検索木) の略です。これは、1995年の Joseph M. Hellerstein、Jeffrey F. Naughton、Avi Pfeffer による記念碑的な論文「Generalized Search Trees for Database Systems」で導入されました:

http://www.sai.msu.su/~megera/postgres/gist/papers/gist.ps

並行性サポートについては、1997年の Marcel Kornacker、C. Mohan、Joseph M. Hellerstein による「Concurrency and Recovery in Generalized Search Trees」に記述されています:

https://dsf.berkeley.edu/papers/sigmod97-gist.pdf

GiST は、PostgreSQL の初期バージョンにおいて J. Hellerstein と P. Aoki によって実装されました（詳細については、バークレー校の The GiST Indexing Project http://gist.cs.berkeley.edu/ を参照してください）。「大学発の」プロジェクトであったため、機能の数は限られており、使用されることはまれでした。

現在の GiST の実装は以下をサポートしています:

  • 可変長キー
  • 複合キー (マルチキー)
  • 順序付き検索 (最傍点検索)
  • GiST コアへの NULL セーフなインターフェースの提供
  • 並行性
  • WAL ロギングによるリカバリサポート
  • バッファリング構築アルゴリズム
  • ソート済み構築メソッド

PostgreSQL に実装されている並行性のサポートは、Marcel Kornacker による論文「Access Methods for Next-Generation Database Systems」に基づいて開発されました:

http://www.sai.msu.su/~megera/postgres/gist/papers/concurrency/access-methods-for-next-generation.pdf.gz

GiST のバッファリング構築アルゴリズムは、Lars Arge、Klaus Hinrichs、Jan Vahrenhold、Jeffrey Scott Vitter による論文「Efficient Bulk Operations on Dynamic R-trees」に基づいて開発されました。

http://citeseerx.ist.psu.edu/viewdoc/download?doi=10.1.1.135.9894&rep=rep1&type=pdf

元のアルゴリズムにはいくつかの変更が加えられています:

  • PostgreSQL の規則に適応させる必要がありました。例えば、PostgreSQL では検索関数がすべてのタプルを一度に返すのではなく、1つのタプル（次）を返す必要があるため、SEARCH アルゴリズムは大幅に変更されました。また、呼び出しの間にページロックを解放する必要があります。
  • 可変長キーのサポートを追加したため、分割後のページ上にすべてのキーに対して十分な空き領域があることを保証することはできません。ユーザー定義関数の picksplit は、タプルのサイズに関する情報を持っていません（各タプルはマルチカラムインデックスのように複数のキーを含む可能性がありますが、picksplit は1つのキーのみで動作する可能性があります）し、ページサイズについても同様です。
  • パフォーマンス上の理由から、元の INSERT アルゴリズムを修正しました。具体的には、現在ではシングルパスのアルゴリズムになっています。
  • 論文は理論的なものであったため、いくつかの詳細が省略されており、特定の問題をどのように解決するかを自力で見つけ出す必要がありました。
  • 上記の1997年の論文（1995年の論文ではなく）では、リーフページに元のキーを格納すべきであると述べられています。PostgreSQL ではそれを行うことも可能ですが、リーフページで圧縮表現を使用することも可能です。

上記の理由により、GiST コアと PostgreSQL の WAL システムの相互作用を見直しました。さらに、クラッシュからのリカバリ時に未完了の挿入の問題が発生し（そして解決し）ましたが、これは論文では触れられていませんでした。

検索アルゴリズム

検索コードは、訪問していないアイテムのキューを保持します。ここで「アイテム」とは、検索条件を満たすことが既知のヒープタプル、または親ページのダウンリンクアイテムの検査に従って検索条件と一致するインデックスページのいずれかです。初期状態では、ルートページが検索され、その中の未訪問のアイテムが検出されます。次に、キューからアイテムを取り出します。ヒープタプルポインタはそのまま即座に返されます。インデックスページエントリの場合はそのページが検索され、さらに多くのキューエントリが生成されます。

キューは、ヒープタプルアイテムが先頭に、その次にインデックスページエントリが来るように順序が保たれます。新しく追加されたインデックスページエントリは、既存のインデックスページエントリの前に挿入されます。これにより、インデックスの深さ優先探索（デプスファーストトラバーサル）が保証され、特に最初のいくつかのヒープタプルができるだけ早く返されるようになります。これは、少数のタプルのみを生成すればよい LIMIT が存在する場合に役立ちます。

最傍点検索を実装するために、キューエントリには距離データが追加されます。ヒープタプルエントリには検索引数からの実際の距離がラベル付けされ、インデックスページエントリには子要素のいずれかが持ち得る最小距離がラベル付けされなければなりません。そして、キューエントリは距離が最も小さい順に取り出され、同じ距離を持つエントリは前の段落で述べたように管理されます。

検索アルゴリズムは、インデックスページのエントリをスキャンし、検索条件を満たすものをキューに入れるのに必要な時間だけ、そのインデックスページをロックし続けます。挿入は検索と並行して発生する可能性があるため、インデックスの子ページ用のキューエントリを作成してから（親ページを訪問している間）、実際にその子ページに到達してスキャンするまでの間に、子ページが分割される可能性があります。右側のシブリング（兄弟）に移動したエントリを見逃さないようにするために、子ページの NSN（ノードシーケンス番号、特殊目的の LSN）と、訪問時に親が持っていた LSN を比較することで、分割が発生したかどうかを検出します。分割が発生していた場合は、シブリングページが即座にキューの先頭に追加され、元の子ページにまだ存在していたかのように同じ順序でそのアイテムがスキャンされることが保証されます。

Postgres で通常行われているように、検索アルゴリズムはスキャン開始前に存在していたインデックスエントリを見つけることしか保証しません。スキャン中に追加されたインデックスエントリは、訪問されることもあればされないこともあります。これは、すべての検索が MVCC スナップショットルールを使用して、スキャン開始時刻よりも新しいヒープタプルを拒否する限り問題ありません。特にこれは、親ページのダウンリンクキーが参照後に「拡大」されたケースについて心配する必要がないことを意味します。そのような拡大は、どうせ返す必要のない子アイテムを追加するためのものであるためです。

挿入アルゴリズム

INSERT は、GiST ツリーのバランスが保たれることを保証します。挿入するサブツリーを選択するためには、ユーザー定義のキーメソッド Penalty が使用されます。ノード分割アルゴリズムにはメソッド PickSplit が使用されます。ツリーのプロパティを維持するために変更を上方に伝播させるためにはメソッド Union が使用されます。

タプルを挿入するには、まず挿入に適したリーフページを見つける必要があります。アルゴリズムは、最小の Penalty のパスに沿って、ルートから始めてツリーを下っていきます。各ステップで以下の処理を行います:

1. このページは、親を見てから分割されたか？ もしそうなら、もう半分に挿入すべきである可能性があるため、親に退避します。 2. これがリーフノードであれば、ターゲットノードが見つかりました。 3. そうでなければ、Penalty を使用して新しいターゲットサブツリーを選択します。 4. ターゲットサブツリーを表すキーを確認します。挿入しようとしているキーがまだカバーされていない場合は、古いダウンリンクキーと挿入するキーの Union（和集合）に置き換えます。（実際には、常に Union を呼び出し、Union されたキーが既存のキーと同じ場合は置き換えをスキップします） 5. ステップ 4 でキーを置き換えると、ページが分割される可能性があります。その場合、変更を上方に伝播させ、分割される必要のなかった最初の親からアルゴリズムを再開します。 6. ターゲットサブツリーまで下り、1 に戻ります。

これは、元の論文の挿入アルゴリズムとは異なります。元の論文では、まずリーフページに到達するまでツリーを下り、次に親のダウンリンクを調整し、最悪の場合はルートに至るまですべて上方に調整を伝播させます。しかし私たちは、下る時点で新しいキーをカバーするようにダウンリンクをすでに調整するため、リーフページに到達した時点では、ページの分割が必要な場合にダウンリンクを挿入することを除いて、親を更新する必要がなくなります。これによりクラッシュリカバリがシンプルになります。ページにキーを挿入した後、親を更新しなくてもツリーは即座に自己一貫性を保ちます。ページを分割し、親へのダウンリンクを挿入する前にクラッシュした場合でも、分割の右半分は左ページ（元のページを置き換えたもの）の rightlink を介してアクセス可能であるため、ツリーは自己一貫性を保ちます。

新しいキーのダウンリンクを調整する際に出内部のページを分割する必要がある場合、リーフページに到達する前にアルゴリズムがツリーを上下に移動する可能性があることに注意してください。最終的には一番下に到達し、新しいタプルの挿入に進むはずです。

挿入するターゲットページが見つかったら、新しいタプル用の空き領域があるかどうかを確認します。空き領域があればタプルが挿入され、処理は完了です。しかし、収まらない場合は、ページを分割する必要があります。キーの長さが異なる場合や、一度に複数のキーが挿入される場合（下位レベルでのページ分割により2つ以上のページが生成された結果のダウンリンクを挿入するときに発生し得ます）、ページを2つ以上のページに分割する必要がある場合があることに注意してください。ページを分割した後、親ページを更新する必要があります。新しいページのダウンリンクを挿入し、分割の左半分になった古いページのダウンリンクは、左ページに残ったタプルのみをカバーするように更新する必要があります。親へのダウンリンクの挿入によって再びページ分割が発生し、最悪の場合はルートページまで再帰する可能性があります。

gistplacetopage は、挿入の1ステップを実行する作業馬（ワークホース）の関数です。タプルが収まる場合は指定されたページに挿入し、そうでない場合はページを分割して、分割されたページの新しいダウンリンクタプルを構築します。呼び出し元は、ダウンリンクタプルを挿入するために親ページに対して gistplacetopage() を呼び出さなければなりません。子へのダウンリンクを保持している親ページは、親の並行分割の結果として移動している可能性があるため、親ページを見つけるために gistFindCorrectParent() が使用されます。

ルートページの分割は少し異なる動作をします。ルート分割時に、gistplacetopage() は新しい子ページを割り当て、古いルートページを新しい子へのダウンリンクを含む新しいルートに置き換える処理を、すべて1つの操作で行います。

findPath は findParent のサブルーチンであり、親レベルの rightlink をたどって正しい親ページが見つからない場合に使用されます:

findPath( stack item ) push stack, [root, 0, 0] // page, LSN, parent while( stack ) ptr = top of stack latch( ptr->page, S-mode ) if ( ptr->parent->page->lsn < ptr->page->nsn ) push stack, [ ptr->page->rightlink, 0, ptr->parent ] end for( each tuple on page ) if ( tuple->pagepointer == item->page ) return stack else add to stack at the end [tuple->pagepointer,0, ptr] end end unlatch( ptr->page ) pop stack end

gistFindCorrectParent は、挿入中にページの親を再検出するために使用されます。ページ分割のためにツリーを下った後、右側に移動している可能性があります。

findParent( stack item ) parent = item->parent if ( parent->page->lsn != parent->lsn ) while(true) search parent tuple on parent->page, if found the return rightlink = parent->page->rightlink unlatch( parent->page ) if ( rightlink is incorrect ) break loop end parent->page = rightlink latch( parent->page, X-mode ) end newstack = findPath( item->parent ) replace part of stack to new one latch( parent->page X-mode ) return findParent( item ) end

pageSplit 関数は、ページ分割後に新しいページにキーをどのように分配するかを決定します:

pageSplit(page, allkeys) (lkeys, rkeys) = pickSplit( allkeys ) if ( page is root ) lpage = new page else lpage = page rpage = new page if ( no space left on rpage ) newkeys = pageSplit( rpage, rkeys ) else push newkeys, union(rkeys) end if ( no space left on lpage ) push newkeys, pageSplit( lpage, lkeys ) else push newkeys, union(lkeys) end return newkeys

並行性制御

経験則として、複数のページに対するロックを同時に保持する必要がある場合、ロックは次の順序で取得する必要があります: 親よりも子ページ、および同じレベルでは左から右へ。常に同じ順序でロックを取得することで、デッドロックを回避します。

検索アルゴリズムは一度に1つのページのみを参照し、ロックします。その結果、検索とページ分割の間に競合状態が発生します。ページ分割は2つのフェーズで行われます。1. ページが分割される、2. ダウンリンクが親に挿入される。もし検索がこれらのステップの間、すなわちダウンリンクが挿入される前に親ページを参照した場合、左半分のrightlinkをたどることで、新しい右半分を依然として見つけることができます。しかし、親ページでダウンリンクを見つけた場合は、rightlinkをたどってはなりません。さもないと、ページが2回訪問されてしまいます！

分割は、最初に左ページにF_FOLLOW_RIGHTフラグをマークします。スキャンがそのフラグがセットされているのを見つけた場合、右ページのダウンリンクが欠落していることを認識し、そこも訪問すべきであると判断します。分割処理が親にダウンリンクを挿入すると、子ページのF_FOLLOW_RIGHTフラグをクリアし、子ページのヘッダーにあるNSNフィールドを、親への挿入時のLSNと一致するように設定します。F_FOLLOW_RIGHTフラグがセットされていない場合、スキャンは子ページのNSNと親ページで確認したLSNを比較します。子ページのNSNが親ページで確認したLSNよりも大きい場合、スキャンはダウンリンクが挿入される前に親ページを参照したことになるため、rightlinkをたどる必要があります。そうでない場合、スキャンは親ページでダウンリンクを確認したことになるため、通常通りそれをたどります（またはすでにたどっています）。

スキャンは、ページ分割が親にダウンリンクが挿入されてフラグが再びクリアされるまで子ページをロックし続けるため、通常、F_FOLLOW_RIGHTフラグのセットされたページを見ることはありません。しかし、ページ分割の途中、親にダウンリンクが挿入される前にクラッシュが発生した場合、ツリー内にF_FOLLOW_RIGHTを持つページが残されることになります。スキャンはこれを問題なく処理できますが、パフォーマンス上の理由から、最終的にはこれを修復したいと考えます。さらに重要なことに、親にダウンリンクポインタが欠落しているページを処理することは、挿入アルゴリズムを複雑にします。そのため、挿入処理がF_FOLLOW_RIGHTのセットされたページを見つけた場合、親にダウンリンクを追加することで、途中でクラッシュした分割処理を即座に完了させようと試みます。

バッファリング構築アルゴリズム

バッファリングインデックス構築アルゴリズムでは、一部またはすべての内部ノードにバッファが割り当てられます。タプルが最上部で挿入されると、バッファに到達した時点でツリーの下降が停止し、タプルはバッファにプッシュされます。バッファが一杯になりすぎると、その中のすべてのタプルが下位レベルにフラッシュされ、そこで再び下位レベルのバッファまたはリーフページに到達します。これにより、挿入が深さ優先ではなく幅優先に近い順序で行われるようになり、必要なランダムI/Oの量が大幅に削減されます。

このアルゴリズムでは、リーフページがレベル0となり、内部ノードのレベルは1からカウントアップするようにレベルが番号付けされます。この番号付けにより、ルートページが分割された場合でも、ページのレベル番号が変化しないことが保証されます。

Level Tree

3 * / \ 2 * * / | \ / | \ 1 * * * * * * / \ / \ / \ / \ / \ / \ 0 o o o o o o o o o o o o

  • - 内部ページ

    • o - リーフページ

特定のレベルに属する内部ページには、バッファが関連付けられています。リーフページがバッファを持つことはありません。どのレベルがバッファを持つかは、"level step"パラメータによって制御されます。level_stepの倍数であるレベル番号がバッファを持ち、それ以外は持ちません。例えば、level_step = 2の場合、レベル2、4、6、...のページがバッファを持ちます。level_step = 1の場合、すべての内部ページがバッファを持ちます。

(b) - バッファ

論理的には、バッファは単なるタプルの集まりです。物理的には、一時ファイルに裏打ちされたページに分割されています。各バッファは、次の2つの状態のいずれかになります。 a) バッファの最後のページがメインメモリに保持されている状態。新しいインデックスタプルが追加されるか、タプルが削除されると、ノードバッファは自動的にこの状態に切り替わります。 b) バッファのすべてのページがディスクにスワップアウトされている状態。バッファが一杯になりすぎてフラッシュを開始すると、他のすべてのバッファがこの状態に切り替わります。

インデックスタプルが挿入されると、その初期処理は以下のいずれかの時点で終了します。 1) インデックスの深さ <= level_step の場合はリーフページ。これは、どの内部ページにもバッファが関連付けられていないことを意味します。 2) バッファを持つ最上位レベルのページのバッファ。

新しいインデックスタプルは、最上位のバッファリングされたレベルにあるバッファのいずれかが半分満たされるまで処理されます。バッファが半分満たされると、空き容量確保キュー（emptying queue）に追加され、新しいタプルが処理される前に空にされます。

バッファを空にするプロセスとは、バッファからのインデックスタプルを下位レベルのバッファまたはリーフページに移動することを意味します。まず、メモリを解放するために、他のすべてのバッファがディスクにスワップされます。次に、タプルがバッファから1つずつ取り出され、バッファリングされたノードの下にある次のバッファまたはリーフページへとツリーを段階的に下っていきます。

バッファを空にすることには、空にされるバッファと、その下にある次のバッファリングされたレベルまたはリーフレベルとの間にあるすべての中間ページがキャッシュされるという、興味深い動的な特性があります。ノードの下にそれ以上バッファがない場合、タプルが最終的に到達するリーフページもキャッシュされます。バッファがある場合、下にある各バッファの最後のバッファページがメモリに保持されます。これを以下の図に示します。

下位レベルのバッファへ 空にされているバッファ リーフページへ空にされているバッファ

+(fb) +(fb) / \ / \ + + + + / \ / \ / \ / \ *(ab) *(ab) *(ab) *(ab) x x x x

+ - キャッシュされた内部ページ x - キャッシュされたリーフページ

  • - キャッシュされていない内部ページ

    • (fb) - 空にされているバッファ (ab) - 追記中のバッファ（最後のページがメモリ内にある）

インデックス構築の開始時に、1つのバッファを空にするのに関与するすべてのページがキャッシュに収まるようにlevel-stepが選択されます。そのため、これらの各ページに一度アクセスしてキャッシュした後は、バッファを空にする処理でそれ以上のI/Oが発生しなくなります。この局所性こそが、バッファリングアルゴリズムの高速化をもたらす要因です。

1つのバッファを空にすることで、1つ以上の下位レベルのバッファが満たされ、それらも空にする処理がトリガーされることがあります。バッファが一杯になりすぎると、いつでも空き容量確保キューに追加され、現在のバッファが処理された後に空にされます。

最悪のシナリオでも各バッファのサイズを制限内に抑えるため、バッファが半分満たされるとすぐにバッファを空にする処理がスケジュールされ、公称バッファサイズの1/2に相当するタプルが空になるまで処理が継続されます。これにより、バッファを空にする処理が開始される時点で、すべての下位レベルのバッファが最大でも半分しか満たされていないことが保証されます。すべてのタプルが同じ下位レベルのバッファに段階的に移動するという最悪のケースでも、そのバッファには上位レベルのバッファから空にされたすべてのタプルを収容するのに十分なスペースがあります。ただし、使用されるデータ構造のいずれにも厳密なサイズ制限はないため、これはおおよそで十分です。一部のバッファがわずかに超過しても問題ありません。

バッファが関連付けられている内部ページが分割された場合、バッファも分割する必要があります。バッファ内のすべてのタプルがスキャンされ、ペナルティ関数を使用して各タプルがどのバッファに移動すべきかを決定し、正しい兄弟バッファに再配置されます。

ヒープからのすべてのタプルが処理された後も、バッファにはまだいくつかのインデックスタプルが残っています。この時点で、最終的なバッファの空き容量確保が開始されます。すべてのバッファはトップダウンの順序で空にされます。これは、ページ分割により、空にする処理の途中で新しいバッファが割り当てられる可能性があるため、少し複雑になります。しかし、新しいバッファは常に、まだ完全に空にされていないバッファの兄弟になります。タプルがツリー内を上方向に移動することはありません。最終的な空き容量確保処理は、特定のレベルのすべてのバッファが空になるまでそのレベルのバッファをループし、その後、次のレベルへと下っていきます。

ソート構築法

すべての入力タプルをソートし、ソートされた順序でGiSTリーフページに詰め込み、処理を進めながらダウンリンクと内部ページを作成します。この方法は、Bツリーインデックスの構築方法と同様に、ボトムアップでインデックスを構築します。

ソート法は、すべての列の演算子クラスに"sortsupport"が定義されている場合に使用されます。そうでない場合は、オプションのバッファリングを使用してタプルを1つずつ挿入する方法にフォールバックします。

GiST構築のソートには、ソート演算子クラスの優れた線形化が必要です。多次元データでは必ずしもそうとは限りません。この異例の事態に対処するため、インデックスタプルをバッファリングし、多次元を認識できるpicksplit関数を適用します。

一括削除アルゴリズム（VACUUM）

VACUUMは2つのステージで動作します。

第1ステージでは、インデックス全体を物理的な順序でスキャンします。並行するページ分割によって不要なタプルが移動し、それを見落とすことがないように、各ページのF_FOLLOW_RIGHTフラグとNSNをチェックして、ページが並行して分割されたかどうかを検出します。並行するページ分割が検出され、ページの片半分がすでにスキャン済みの位置に移動していた場合、ページを再度スキャンするために「後方にジャンプ」します。これはBツリーのVACUUMが使用するものと同じメカニズムですが、検索中のページ分割を検出するためにページ上にすでにNSNが存在するため、Bツリーのようにそのための「バキュームサイクルID」の概念は必要ありません。

すべてのページをスキャンする間に、完全に空のリーフページも記録しておきます。スキャン後に、それらをツリーからアンリンクすることを試みます。また、すべての内部ページのブロック番号も記録します。これらは、アンリンクする際に空のページの親を特定するために必要です。

空のリーフページをツリーからアンリンクして、そのスペースを再利用できるようにします。空のページを削除するには、そのダウンリンクを親から削除する必要があります。第1ステージで記憶したブロック番号を持つすべての内部ページをスキャンし、空であると記憶したページへのダウンリンクを探します。見つかるたびに、親ページと子ページのロックを取得し、子ページがまだ空であることを再確認します。その後、ダウンリンクを削除し、子ページに削除済みのマークを付け、ロックを解放します。

内部ページが完全に空になると、挿入アルゴリズムが混乱してしまいます。そのため、内部ページの最後の子ページは、たとえ空であっても削除しません。現在、リーフページの削除のみをサポートしています。

このページ削除アルゴリズムは、ベストエフォートベースで動作します。第1ステージの後に並行するページ分割によってダウンリンクが移動した場合、ダウンリンクを見つけられない可能性があります。その場合、すべての空のページを削除することはできません。これは問題ありません。頻繁に発生することは想定されておらず、次のVACUUMでクリーンアップされることが期待されます。

ページを削除したとき、削除する前にダウンリンクを確認していた場合、進行中の検索が依然としてそのページに下降してくる可能性があります。検索はそれが削除されていることを確認して無視しますが、そのようなことが起こり得る限り、ページを再利用することはできません。進行中の検索が「終了するのを待つ」ために、ページが削除されると、現在の次のトランザクションカウンタの値がラベル付けされます。そのXIDが誰からも見えなくなるまで、ページは再利用されません。これは必要以上に保守的ですが、シンプルにしておきましょう。
