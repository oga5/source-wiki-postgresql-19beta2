トランザクションシステム ======================

PostgreSQL のトランザクションシステムは3層構造になっています。最下層は 低レベルのトランザクションとサブトランザクションを実装し、その上に メインループの制御コードが置かれ、さらにそれがユーザーに公開される トランザクションとセーブポイントを実装しています。

中層のコードは、各クエリの処理前後に postgres.c から、あるいは エラーの検出後に呼び出されます：

StartTransactionCommand CommitTransactionCommand AbortCurrentTransaction

一方、ユーザーは SQL コマンドの BEGIN、COMMIT、ROLLBACK、SAVEPOINT、 ROLLBACK TO または RELEASE を発行して、システムの状態を変更できます。 トラフィックコップはこれらの呼び出しをそれぞれトップレベルルーチンへ リダイレクトします：

BeginTransactionBlock EndTransactionBlock UserAbortTransactionBlock DefineSavepoint RollbackToSavepoint ReleaseSavepoint

システムの現在の状態に応じて、これらの関数は低レベル関数を呼び出して 実際のトランザクションシステムを有効化します：

StartTransaction CommitTransaction AbortTransaction CleanupTransaction StartSubTransaction CommitSubTransaction AbortSubTransaction CleanupSubTransaction

さらに、トランザクション内では CommandCounterIncrement が呼び出されて コマンドカウンタがインクリメントされます。これにより、将来のコマンドは 同じトランザクション内の前のコマンドの効果を「見る」ことができるように なります。これは、トランザクションブロック内の各クエリの後に CommitTransactionCommand によって自動的に行われますが、一部のユーティリティ 関数でも内部的に行われ、特定の操作（通常はシステムカタログ内）が同じ ユーティリティコマンド内の将来の操作から見えるようにします。（たとえば、 DefineRelation ではヒープの作成後に行われるため、pg_class の行が可視に なり、それをロックできるようになります。）

たとえば、次のユーザーコマンドのシーケンスを考えてみます：

1) BEGIN 2) SELECT * FROM foo 3) INSERT INTO foo VALUES (...) 4) COMMIT

メインの処理ループでは、これにより次の関数呼び出しシーケンスが生成されます：

/ StartTransactionCommand; / StartTransaction; 1) < ProcessUtility; << BEGIN \ BeginTransactionBlock; \ CommitTransactionCommand;

/ StartTransactionCommand; 2) / PortalRunSelect; << SELECT ... \ CommitTransactionCommand; \ CommandCounterIncrement;

/ StartTransactionCommand; 3) / ProcessQuery; << INSERT ... \ CommitTransactionCommand; \ CommandCounterIncrement;

/ StartTransactionCommand; / ProcessUtility; << COMMIT 4) < EndTransactionBlock; \ CommitTransactionCommand; \ CommitTransaction;

この例のポイントは、StartTransactionCommand と CommitTransactionCommand が 状態を認識する必要があることを示すことです。それらは BeginTransactionBlock と EndTransactionBlock の呼び出しの間で CommandCounterIncrement を呼び出すべきであり、これらの呼び出しの外側では 通常の開始、コミット、またはアボート処理を行う必要があります。

さらに、「SELECT * FROM foo」がアボート状態を引き起こしたと仮定します。 この場合、AbortCurrentTransaction が呼び出され、トランザクションはアボート 状態に置かれます。この状態では、トランザクション終了文または ROLLBACK TO <savepoint> コマンドを除き、ユーザーからの入力はすべて無視されます。

トランザクションのアボートには2つの発生方法があります：

1) システムが何らかの内因（構文エラーなど）により停止する 2) ユーザーが ROLLBACK と入力する

これらを区別しなければならない理由は、次の2つの状況によって示されます：

ケース 1 ケース 2 ------ ------ 1) ユーザーが BEGIN と入力する 1) ユーザーが BEGIN と入力する 2) ユーザーが何らかの操作を行う 2) ユーザーが何らかの操作を行う 3) ユーザーがその結果を気に入らず 3) システムが何らかの理由（構文エラー ABORT と入力する など）でアボートする

ケース 1 では、トランザクションをアボートしてデフォルトの状態に戻したいと 考えます。 ケース 2 では、同じトランザクションブロックの一部である後続のコマンドが 届く可能性があります。COMMIT または ROLLBACK を見るまで、これらのコマンドを 無視しなければなりません。

内部的なアボートは AbortCurrentTransaction によって処理され、ユーザーによる アボートは UserAbortTransactionBlock によって処理されます。どちらも すべての実際の作業を AbortTransaction に依存しています。唯一の違いは、 AbortTransaction が作業を行った後に移行する状態です：

  • AbortCurrentTransaction は TBLOCK_ABORT 状態にします。
  • UserAbortTransactionBlock は TBLOCK_ABORT_END 状態にします。

低レベルのトランザクションアボート処理は2つのフェーズに分かれています：

  • AbortTransaction は、トランザクションが失敗したと認識した直後に

    • 実行されます。他のバックエンドを不必要に待たせないように、すべての 共有リソース（ロックなど）を解放する必要があります。

  • CleanupTransaction は、ユーザーの COMMIT または ROLLBACK コマンドを

    • 最終的に目撃したときに実行されます。クリーンアップを行い、トランザクション から完全に抜け出します。特に、この時点まで TopTransactionContext を 破棄してはなりません。

また、トランザクションがコミットされたとき、すぐにクローズされるわけでは ないことに注意してください。むしろそれは TBLOCK_END 状態に置かれます。 これは、クエリの処理が完了した後に CommitTransactionCommand が呼び出された ときに、トランザクションがクローズされなければならないことを意味します。 この区別は微妙ですが重要です。なぜなら、制御がトランザクションを開いたまま xact.c コードから離れ、メインループが同じトランザクション内で処理を 継続できることを意味するからです。したがって、ある意味で、トランザクション のコミットも2つのフェーズで処理されます。最初のフェーズは EndTransactionBlock であり、2番目のフェーズは CommitTransactionCommand （実際に CommitTransaction が呼び出される場所）です。

xact.c 内の残りのコードは、トランザクションとサブトランザクションの作成と 完了をサポートするルーチンです。たとえば、AtStart_Memory は、メイン トランザクションの開始時にメモリサブシステムの初期化を担当します。

サブトランザクションの処理 --------------------------

サブトランザクションは TransactionState 構造体のスタックを使用して 実装されており、各構造体は親トランザクションの構造体へのポインタを 持っています。新しいサブトランザクションを開くときは、 PushTransaction が呼び出されます。これにより、親リンクが現在の トランザクションを指す新しい TransactionState が作成されます。 StartSubTransaction は、新しい TransactionState を健全な値に初期化し、 他のサブシステムを適切に初期化する（AtSubStart ルーチン）役割を 担います。

サブトランザクションをクローズするときは、CommitSubTransaction（サブ トランザクションがコミットする場合）、または AbortSubTransaction と CleanupSubTransaction（アボートする場合）のいずれかを呼び出す必要が あります。いずれの場合も PopTransaction が呼び出され、システムは 親トランザクションに戻ります。

サブトランザクションの処理に関して重要な点の1つは、1つのユーザーコマンド への応答として複数のサブトランザクションをクローズする必要がある場合が あることです。これは、セーブポイントには名前があり、最後に開かれた ものとは限らない名前によってセーブポイントをコミットまたはロールバック できるためです。また、COMMIT または ROLLBACK コマンドはスタック全体を クローズできなければなりません。これを処理するために、ユーティリティ コマンドのサブルーチンにすべての状態スタックエントリにコミット保留中 またはアボート保留中のマークを付けさせ、メインループが CommitTransactionCommand に到達したときに実際の作業が行われるように します。このように処理する主な利点は、状態スタックエントリを ポップする際にエラーが発生した場合でも、残りのスタックエントリが 完了のために行うべきことを示し続けるという点です。

ROLLBACK TO <savepoint> の場合、セーブポイントによって識別される サブトランザクションまでのすべてのサブトランザクションをアボートし、 その後、同じ名前でそのサブトランザクションレベルを再作成します。 したがって、内部的な観点からは完全に新しいサブトランザクションとなります。

他のサブシステムは「内部」サブトランザクションを開始することが 許可されており、これは BeginInternalSubTransaction によって処理されます。 これは、PL/pgSQLなどで例外処理を実装できるようにするためです。 ReleaseCurrentSubTransaction と RollbackAndReleaseCurrentSubTransaction を使用すると、サブシステムは前述のサブトランザクションをクローズ できます。これとセーブポイント/リリースのパスとの主な違いは、 CommitTransactionCommand まで一部の作業を遅延させるのではなく、各 サブルーチンで完全な状態遷移を即座に実行する点です。もう一つの違いは、 明示的なトランザクションブロックが確立されていない場合でも BeginInternalSubTransaction は許可されるが、DefineSavepoint は 許可されない点です。

トランザクションとサブトランザクションの番号付け ----------------------------------------------

トランザクションとサブトランザクションには、最初にそれを必要とする 操作（通常はタプルの挿入/更新/削除ですが、XIDの割り当てを必要とする 他の場所もいくつかあります）を行うとき、あるいは行ったときにのみ、 永続的な XID が割り当てられます。サブトランザクションが XID を 必要とする場合、常に最初にその親に XID が割り当てられます。これにより、 子トランザクションの XID が親よりも大きくなるという不変条件が維持され、 これは多くの場所で前提とされています。

XID のロックを取得し、それを pg_subtrans および PGPROC に登録するという 付随的なアクションは、割り当て時に行われます。

XID を持たないトランザクションでも、主にロックの保持など、さまざまな 目的のために識別される必要があります。この目的のために、各トップレベル トランザクションに「仮想トランザクション ID (VXID)」を割り当てます。 VXID は、procNumber とバックエンドローカルなカウンタの2つのフィールドから 構成されます。この配置により、共有メモリ競合なしでトランザクション 開始時に新しい VXID を割り当てることができます。バックエンド終了後すぐに VXID が再利用されないようにするために、バックエンド終了時に最後の ローカルカウンタ値を共有メモリに保存し、バックエンド開始時に同じ PGPROC スロットの以前の値から初期化します。これらのカウンタはすべて 共有メモリの再初期化時にゼロに戻りますが、VXID がディスク上に現れる ことは決してないため、これで問題ありません。

内部的に、バックエンドには XID の有無に関わらずサブトランザクションを 識別する方法が必要ですが、この必要性は親のトップトランザクションが 存続している間だけ続きます。したがって、各トップトランザクションの 開始時にリセットするカウンタから生成されるという点で CommandId に 少し似ている SubTransactionId があります。トップレベルトランザクション 自体の SubTransactionId は 1であり、サブトランザクションの ID は 2 以降です。（ゼロは InvalidSubTransactionId のために予約されています。） サブトランザクションは独自の VXID を持たず、親のトップトランザクションの VXID を使用することに注意してください。

トランザクション開始、トランザクション終了、およびスナップショットのインターロック ----------------------------------------------------------------------------------

トランザクションの開始/終了やスナップショットの取得という頻繁なアクティビティ に関連するオーバーヘッドとロック競合の量を最小限に抑えるよう、私たちは 尽力しています。不運なことに、トランザクションのコミット順序に関する 一貫性を確保する必要があるため、これには何らかのインターロックが 必要になります。 たとえば、トランザクション A の UPDATE が、同じ行に対するトランザクション B の事前の更新によってブロックされており、トランザクション B がコミットを 行っている間に、トランザクション C がスナップショットを取得するとします。 トランザクション A は、B がロックを解放するとすぐに完了してコミット できます。もしトランザクション C の GetSnapshotData がトランザクション B をまだ実行中であると見なす場合、トランザクション A もまだ実行中であると 見なす必要があります。そうしないと、B によって削除されたものと A によって 挿入されたものの、2つのタプルバージョンを見ることになってしまいます。 これが望ましくないもう一つの理由は、C が（Aによって挿入された行の中で） B による以前の変更を見てしまい、データベース内の他の場所で B の変更を まったく見ないことと矛盾するためです。

形式的に、正当性の要件は「スナップショット A がトランザクション X を コミット済みと見なし、トランザクション X のスナップショットのいずれかが トランザクション Y をコミット済みと見なしている場合、スナップショット A はトランザクション Y をコミット済みと見なさなければならない」という ものです。

What we actually enforce is strict serialization of commits and rollbacks
with snapshot-taking: we do not allow any transaction to exit the set of
running transactions while a snapshot is being taken.  (This rule is
stronger than necessary for consistency, but is relatively simple to
enforce, and it assists with some other issues as explained below.)  The
implementation of this is that GetSnapshotData takes the ProcArrayLock in
shared mode (so that multiple backends can take snapshots in parallel),
but ProcArrayEndTransaction must take the ProcArrayLock in exclusive mode
while clearing the ProcGlobal->xids[] entry at transaction end (either
commit or abort). (To reduce context switching, when multiple transactions
commit nearly simultaneously, we have one backend take ProcArrayLock and
clear the XIDs of multiple processes at once.)

ProcArrayEndTransaction also holds the lock while advancing the shared
latestCompletedXid variable.  This allows GetSnapshotData to use
latestCompletedXid + 1 as xmax for its snapshot: there can be no
transaction >= this xid value that the snapshot needs to consider as
completed.

In short, then, the rule is that no transaction may exit the set of
currently-running transactions between the time we fetch latestCompletedXid
and the time we finish building our snapshot.  However, this restriction
only applies to transactions that have an XID --- read-only transactions
can end without acquiring ProcArrayLock, since they don't affect anyone
else's snapshot nor latestCompletedXid.

Transaction start, per se, doesn't have any interlocking with these
considerations, since we no longer assign an XID immediately at transaction
start.  But when we do decide to allocate an XID, GetNewTransactionId must
store the new XID into the shared ProcArray before releasing XidGenLock.
This ensures that all top-level XIDs <= latestCompletedXid are either
present in the ProcArray, or not running anymore.  (This guarantee doesn't
apply to subtransaction XIDs, because of the possibility that there's not
room for them in the subxid array; instead we guarantee that they are
present or the overflow flag is set.)  If a backend released XidGenLock
before storing its XID into ProcGlobal->xids[], then it would be possible for
another backend to allocate and commit a later XID, causing latestCompletedXid
to pass the first backend's XID, before that value became visible in the
ProcArray.  That would break ComputeXidHorizons, as discussed below.

We allow GetNewTransactionId to store the XID into ProcGlobal->xids[] (or the
subxid array) without taking ProcArrayLock.  This was once necessary to
avoid deadlock; while that is no longer the case, it's still beneficial for
performance.  We are thereby relying on fetch/store of an XID to be atomic,
else other backends might see a partially-set XID.  This also means that
readers of the ProcArray xid fields must be careful to fetch a value only
once, rather than assume they can read it multiple times and get the same
answer each time.  (Use volatile-qualified pointers when doing this, to
ensure that the C compiler does exactly what you tell it to.)

Another important activity that uses the shared ProcArray is
ComputeXidHorizons, which must determine a lower bound for the oldest xmin
of any active MVCC snapshot, system-wide.  Each individual backend
advertises the smallest xmin of its own snapshots in MyProc->xmin, or zero
if it currently has no live snapshots (eg, if it's between transactions or
hasn't yet set a snapshot for a new transaction).  ComputeXidHorizons takes
the MIN() of the valid xmin fields.  It does this with only shared lock on
ProcArrayLock, which means there is a potential race condition against other
backends doing GetSnapshotData concurrently: we must be certain that a
concurrent backend that is about to set its xmin does not compute an xmin
less than what ComputeXidHorizons determines.  We ensure that by including
all the active XIDs into the MIN() calculation, along with the valid xmins.
The rule that transactions can't exit without taking exclusive ProcArrayLock
ensures that concurrent holders of shared ProcArrayLock will compute the
same minimum of currently-active XIDs: no xact, in particular not the
oldest, can exit while we hold shared ProcArrayLock.  So
ComputeXidHorizons's view of the minimum active XID will be the same as that
of any concurrent GetSnapshotData, and so it can't produce an overestimate.
If there is no active transaction at all, ComputeXidHorizons uses
latestCompletedXid + 1, which is a lower bound for the xmin that might
be computed by concurrent or later GetSnapshotData calls.  (We know that no
XID less than this could be about to appear in the ProcArray, because of the
XidGenLock interlock discussed above.)

As GetSnapshotData is performance critical, it does not perform an accurate
oldest-xmin calculation (it used to, until v14). The contents of a snapshot
only depend on the xids of other backends, not their xmin. As backend's xmin
changes much more often than its xid, having GetSnapshotData look at xmins
can lead to a lot of unnecessary cacheline ping-pong.  Instead
GetSnapshotData updates approximate thresholds (one that guarantees that all
deleted rows older than it can be removed, another determining that deleted
rows newer than it can not be removed). GlobalVisTest* uses those thresholds
to make invisibility decision, falling back to ComputeXidHorizons if
necessary.

Note that while it is certain that two concurrent executions of
GetSnapshotData will compute the same xmin for their own snapshots, there is
no such guarantee for the horizons computed by ComputeXidHorizons.  This is
because we allow XID-less transactions to clear their MyProc->xmin
asynchronously (without taking ProcArrayLock), so one execution might see
what had been the oldest xmin, and another not.  This is OK since the
thresholds need only be a valid lower bound.  As noted above, we are already
assuming that fetch/store of the xid fields is atomic, so assuming it for
xmin as well is no extra risk.


pg_xact and pg_subtrans
-----------------------

pg_xact and pg_subtrans are permanent (on-disk) storage of transaction related
information.  There is a limited number of pages of each kept in memory, so
in many cases there is no need to actually read from disk.  However, if
there's a long running transaction or a backend sitting idle with an open
transaction, it may be necessary to be able to read and write this information
from disk.  They also allow information to be permanent across server restarts.

pg_xact records the commit status for each transaction that has been assigned
an XID.  A transaction can be in progress, committed, aborted, or
"sub-committed".  This last state means that it's a subtransaction that's no
longer running, but its parent has not updated its state yet.  It is not
necessary to update a subtransaction's transaction status to subcommit, so we
can just defer it until main transaction commit.  The main role of marking
transactions as sub-committed is to provide an atomic commit protocol when
transaction status is spread across multiple clog pages. As a result, whenever
transaction status spreads across multiple pages we must use a two-phase commit
protocol: the first phase is to mark the subtransactions as sub-committed, then
we mark the top level transaction and all its subtransactions committed (in
that order).  Thus, subtransactions that have not aborted appear as in-progress
even when they have already finished, and the subcommit status appears as a
very short transitory state during main transaction commit.  Subtransaction
abort is always marked in clog as soon as it occurs.  When the transaction
status all fit in a single CLOG page, we atomically mark them all as committed
without bothering with the intermediate sub-commit state.

Savepoints are implemented using subtransactions.  A subtransaction is a
transaction inside a transaction; its commit or abort status is not only
dependent on whether it committed itself, but also whether its parent
transaction committed.  To implement multiple savepoints in a transaction we
allow unlimited transaction nesting depth, so any particular subtransaction's
commit state is dependent on the commit status of each and every ancestor
transaction.

The "subtransaction parent" (pg_subtrans) mechanism records, for each
transaction with an XID, the TransactionId of its parent transaction.  This
information is stored as soon as the subtransaction is assigned an XID.
Top-level transactions do not have a parent, so they leave their pg_subtrans
entries set to the default value of zero (InvalidTransactionId).

pg_subtrans is used to check whether the transaction in question is still
running --- the main Xid of a transaction is recorded in ProcGlobal->xids[],
with a copy in PGPROC->xid, but since we allow arbitrary nesting of
subtransactions, we can't fit all Xids in shared memory, so we have to store
them on disk.  Note, however, that for each transaction we keep a "cache" of
Xids that are known to be part of the transaction tree, so we can skip looking
at pg_subtrans unless we know the cache has been overflowed.  See
storage/ipc/procarray.c for the gory details.

slru.c is the supporting mechanism for both pg_xact and pg_subtrans.  It
implements the LRU policy for in-memory buffer pages.  The high-level routines
for pg_xact are implemented in transam.c, while the low-level functions are in
clog.c.  pg_subtrans is contained completely in subtrans.c.


Write-Ahead Log Coding
----------------------

The WAL subsystem (also called XLOG in the code) exists to guarantee crash
recovery.  It can also be used to provide point-in-time recovery, as well as
hot-standby replication via log shipping.  Here are some notes about
non-obvious aspects of its design.

A basic assumption of a write AHEAD log is that log entries must reach stable
storage before the data-page changes they describe.  This ensures that
replaying the log to its end will bring us to a consistent state where there
are no partially-performed transactions.  To guarantee this, each data page
(either heap or index) is marked with the LSN (log sequence number --- in
practice, a WAL file location) of the latest XLOG record affecting the page.
Before the bufmgr can write out a dirty page, it must ensure that xlog has
been flushed to disk at least up to the page's LSN.  This low-level
interaction improves performance by not waiting for XLOG I/O until necessary.
The LSN check exists only in the shared-buffer manager, not in the local
buffer manager used for temp tables; hence operations on temp tables must not
be WAL-logged.

During WAL replay, we can check the LSN of a page to detect whether the change
recorded by the current log entry is already applied (it has been, if the page
LSN is >= the log entry's WAL location).

Usually, log entries contain just enough information to redo a single
incremental update on a page (or small group of pages).  This will work only
if the filesystem and hardware implement data page writes as atomic actions,
so that a page is never left in a corrupt partly-written state.  Since that's
often an untenable assumption in practice, we log additional information to
allow complete reconstruction of modified pages.  The first WAL record
affecting a given page after a checkpoint is made to contain a copy of the
entire page, and we implement replay by restoring that page copy instead of
redoing the update.  (This is more reliable than the data storage itself would
be because we can check the validity of the WAL record's CRC.)  We can detect
the "first change after checkpoint" by noting whether the page's old LSN
precedes the end of WAL as of the last checkpoint (the RedoRecPtr).

The general schema for executing a WAL-logged action is

1. Pin and exclusive-lock the shared buffer(s) containing the data page(s)
to be modified.

2. START_CRIT_SECTION() (共有バッファには未記録の変更が含まれており、これらがディスクに書き込まれないようにする必要があるため、次の3つのステップのいずれかのエラーはPANICを引き起こさなければなりません。当然ながら、クリティカルセクションを開始する前に、ページ上に十分な空き領域があるかどうかなどの条件を確認する必要があります。)

3. 必要な変更を共有バッファに適用します。

4. MarkBufferDirty()を使用して共有バッファをダーティとしてマークします。(これはWALレコードが挿入される前に行う必要があります。SyncOneBuffer()の注記を参照してください。) MarkBufferDirty()でバッファをダーティとしてマークするのは、WALレコードを書き込む場合にのみ行うべきであることに注意してください。以下の「ヒントの書き込み」を参照してください。

5. リレーションにWALロギングが必要な場合は、XLogBeginInsertおよびXLogRegister*関数を使用してWALレコードを構築し、それを挿入します。(以下の「WALレコードの構築」を参照してください。) その後、返されたXLOGロケーションを使用してページのLSNを更新します。例:

XLogBeginInsert(); XLogRegisterBuffer(...) XLogRegisterData(...) recptr = XLogInsert(rmgr_id, info);

PageSetLSN(dp, recptr);

6. END_CRIT_SECTION()

7. バッファのロックとピンを解除します。

マルチレベルインデックスの挿入などの複雑な変更は、通常、一連のアトミックアクションWALレコードによって記述される必要があります。中間状態は自己整合的である必要があり、2つのアクションの間でリプレイが中断された場合でも、システムが完全に機能するようにする必要があります。たとえば、btreeインデックスでは、ページ分割により新しいページの割り当てと親btreeレベルへの新しいキーの挿入が必要になりますが、ロックの理由から、これらは2つの個別のWALレコードとして反映される必要があります。最初のレコードをリプレイして新しいページを割り当て、そこにタプルを移動すると、キーがまだ親に挿入されていないことを示すフラグがページに設定されます。2番目のレコードをリプレイすると、そのフラグがクリアされます。この中間状態は、2つのアクションにわたって子ページのロックが保持されるため、通常の操作では他のバックエンドからは見られませんが、2番目のWALレコードが書き込まれる前に操作が中断された場合には見られます。検索アルゴリズムは通常どおり中間状態で動作しますが、挿入時に不完全分割フラグが設定されたページに遭遇した場合、処理を続行する前に、親にキーを挿入することで中断された分割を完了させます。

WALレコードの構築 -------------------------

WALレコードは、すべてのWALレコードタイプに共通するヘッダー、レコード固有のデータ、および変更されたデータブロックに関する情報で構成されます。変更された各データブロックはID番号で識別され、オプションでブロックに関連付けられたより多くのレコード固有のデータを持つことができます。XLogInsertがブロックのフルページイメージを取得する必要があると判断した場合、そのブロックに関連付けられたデータは含まれません。

WALレコードを構築するためのAPIは、XLogBeginInsert、XLogRegisterBuffer、XLogRegisterData、XLogRegisterBufData、およびXLogInsertの5つの関数で構成されます。まず、XLogBeginInsert()を呼び出します。次に、変更されたすべてのバッファと、変更をリプレイするために必要なデータを、XLogRegister*関数を使用して登録します。最後に、XLogInsert()を呼び出して構築したレコードをWALに挿入します。

XLogBeginInsert();

/* このWALログに記録されたアクションの一部として変更されたバッファを登録する */ XLogRegisterBuffer(0, lbuffer, REGBUF_STANDARD); XLogRegisterBuffer(1, rbuffer, REGBUF_STANDARD);

/* WALレコードに常に含まれるデータを登録する */ XLogRegisterData(&xlrec, SizeOfFictionalAction);

/*

  • バッファに関連付けられたデータを登録する。フルページイメージが
  • 取得された場合、これはレコードに含まれません。

    • */ XLogRegisterBufData(0, tuple->data, tuple->len);

/* バッファに関連付けられたその他のデータ */ XLogRegisterBufData(0, data2, len2);

/*

  • OK、WALレコードに含めるすべてのデータとバッファが登録されました。
  • レコードを挿入します。

    • */ recptr = XLogInsert(RM_FOO_ID, XLOG_FOOBAR_DO_STUFF);

API関数の詳細:

void XLogBeginInsert(void)

XLogRegisterBufferおよびXLogRegisterDataの前に呼び出す必要があります。

void XLogResetInsertion(void)

WALレコード構築ワークスペースから、現在登録されているデータとバッファをクリアします。これは、すでにXLogBeginInsert()を呼び出したものの、最終的にレコードを挿入しないことに決めた場合にのみ必要です。

void XLogEnsureRecordSpace(int max_block_id, int ndatas)

通常、WALレコード構築バッファには次の制限があります:

  • 使用できる最も高いブロックIDは4です（5つのブロック参照を許可）
  • 登録されたデータの最大チャンク数は20

これらのデフォルトの制限は、ディスク上の構造を変更するほとんどのレコードタイプに十分です。より多くのデータを必要とする場合や、より多くのバッファを変更する必要がある稀なケースでは、XLogEnsureRecordSpace()を呼び出すことでこれらの制限を引き上げることができます。XLogEnsureRecordSpace()は、XLogBeginInsert()の前に、かつクリティカルセクションの外で呼び出す必要があります。

void XLogRegisterBuffer(uint8 block_id, Buffer buf, uint8 flags);

XLogRegisterBufferは、データブロックに関する情報をWALレコードに追加します。block_idは、リドゥルーチンでこのページ参照を識別するために使用される任意の数値です。リドゥ時にページを再検索するために必要な情報（relfilelocator、フォーク、ブロック番号）がWALレコードに含まれます。

前回のチェックポイント以降にバッファが初めて変更された場合、XLogInsertは自動的にページ内容の完全なコピーを含めます。ティアードページ（torn-page）の危険性を回避するために、アクションによって変更されたすべてのバッファをXLogRegisterBufferで登録することが重要です。

フラグは、バッファの内容がWALレコードにいつ、どのように含まれるかを制御します。通常、フルページイメージは、前回のチェックポイント以降にページが変更されておらず、かつ full_page_writes=on であるかオンラインバックアップが進行中の場合にのみ取得されます。REGBUF_FORCE_IMAGEフラグを使用すると、フルページイメージが常に含まれるように強制できます。これは、たとえばページのほとんどを書き換える操作などで、詳細を追跡する価値がない場合に便利です。ティアードページから保護する必要がない稀なケースでは、REGBUF_NO_IMAGEフラグを使用して、フルページイメージの取得を抑制できます。REGBUF_WILL_INITもフルページイメージを抑制しますが、リドゥルーチンは古いページの内容を見ることなく、ゼロからページを再生成する必要があります。ページを再初期化することは、フルページイメージと同様にティアードページの危険から保護します。

REGBUF_STANDARDフラグを他のフラグと一緒に指定して、ページが標準のページレイアウトに従っていることを示すことができます。これにより、pd_lowerとpd_upperの間の領域がイメージから除外され、WALのボリュームが削減されます。

REGBUF_KEEP_DATAフラグが指定されている場合、フルページイメージが取得された場合でも、XLogRegisterBufData()で登録されたバッファごとのデータがWALレコードに含まれます。

void XLogRegisterData(const void *data, int len);

XLogRegisterDataは、任意のデータをWALレコードに含めるために使用されます。XLogRegisterData()が複数回呼び出された場合、データは追加され、1つの連続したチャンクとしてリドゥルーチンで使用可能になります。

void XLogRegisterBufData(uint8 block_id, const void *data, int len);

XLogRegisterBufDataは、事前にXLogRegisterBuffer()で登録された特定のバッファに関連付けられたデータを含めるために使用されます。同じブロックIDでXLogRegisterBufData()が複数回呼び出された場合、データは追加され、1つの連続したチャンクとしてリドゥルーチンで使用可能になります。

挿入時にバッファのフルページイメージが取得された場合、REGBUF_KEEP_DATAフラグが使用されない限り、データはWALレコードに含まれません。

REDOルーチンの記述 ----------------------

REDOルーチンは、WALレコードに含まれるデータとページ参照を使用して、ページの新しい状態を再構築します。xlogreader.c/hのレコードデコード関数とマクロを使用して、レコードからデータを抽出できます。

複数のページに対する変更を記述するWALレコードをリプレイする場合は、同時実行されるホットスタンバイ（Hot Standby）クエリが一貫性のない状態を見ないように、ページを適切にロックするよう注意する必要があります。これによって2つ以上のバッファロックを同時に保持する必要がある場合は、適切な順序でページをロックし、すべての変更が完了するまでロックを解放してはなりません。

アクションが直列化されていることがわかっている場合にのみ、PageSetLSN/PageGetLSN()を使用する必要があることに注意してください。リカバリ中にデータブロックを変更できるのはスタートアッププロセスのみであるため、スタートアッププロセスは直列化の問題を恐れることなくPageGetLSN()を実行できます。他のすべてのプロセスは、排他バッファロック、または共有ロックとバッファヘッダーロックの両方を保持している場合、あるいはリレーションに対するAccessExclusiveLockを保持しながら共有バッファ経由ではなく直接データブロックを書き込んでいる場合にのみ、PageSet/GetLSNを呼び出す必要があります。

ヒントの書き込み -------------

場合によっては、先行するWALレコードを書き込まずに、追加情報をデータブロックに書き込むことがあります。これは、クラッシュ後にデータを後で再構築でき、かつそのアクションが単なるパフォーマンス最適化の手段である場合にのみ発生するはずです。ヒントが書き込まれるときは、MarkBufferDirtyHint()を使用してブロックをダーティとしてマークします。

バッファがクリーンであり、チェックサムが使用されている場合、MarkBufferDirtyHint()はXLOG_FPI_FOR_HINTレコードを挿入して、ヒントを含むフルページイメージを確実に取得するようにします。これは、ダーティになったページを書き込む際に、部分的なページ書き込み（partial page write）を回避するために行われます。リカバリ中はWALが書き込まれないため、リカバリ中の場合はヒントによるブロックのダーティ化を単にスキップします。

WALレコードの最適化をやめることに決めた場合、MarkBufferDirty()の呼び出しはすべてMarkBufferDirtyHint()に置き換える必要があります。そうしないと、部分的なページ書き込みのリスクにさらされることになります。

ヒープページ内のすべて可視のヒント（PD_ALL_VISIBLE）は、ある観点では耐久性のある変更として扱われ、別の観点ではヒントとして扱われるため、特殊なケースです。これは、ヒープページの関連する可視性マップ（VM）ビットが設定されている場合、ヒープページ自体でもPD_ALL_VISIBLEが設定されているという不変条件を満たす必要があります。この不変条件を維持するため、PD_ALL_VISIBLEのクリアは常に完全に耐久性のある変更として扱われます。さらに、チェックサムまたはwal_log_hintsが有効な場合、ティアードページから保護するために、PD_ALL_VISIBLEの設定も完全に耐久性のある変更として扱われます。

ただし、チェックサムもwal_log_hintsも有効になっていない場合、変更がPD_ALL_VISIBLEのみであれば、ティアードページは問題になりません。そのため、ヒープのフルページイメージは取得されず、ヒープページのLSNは更新されません。注意: 関連するWALレコードが存在する場合でも、この最適化を適用するときにヒープページのLSNを更新することは不正確です。ページのその後の変更者（無関係なUPDATEなど）が、フルページイメージが不要であると誤って信じる可能性があるためです。

ファイルシステムアクションのための先行書き込みロギング（Write-Ahead Logging） ------------------------------------------

前のセクションでは、共有バッファ内のページ内容のみを変更するアクションのWALロギング方法について説明しました。その種のアクションでは、実際の変更を開始する前に、すべての可能性のあるエラーケース（ページ上の空き容量不足など）を一般的にチェックすることができます。したがって、変更と関連するWALログレコードの作成をクリティカルセクションでラップすることで「アトミック」にすることができます。途中で失敗する確率は十分に低いため、万が一発生した場合はPANICが許容されます。

明らかに、新しいファイルやデータベースの作成など、ログに記録されるアクション内で失敗する確率が高いケースでは、このアプローチは機能しません。PANICを起こしたくありませんし、特に、そのアクションを実行したことを示すWALレコードをすでに書き込んだ後にPANICを起こすことは絶対に避けたいです。もしそうしてしまった場合、レコードのリプレイはおそらく再び失敗し、再びPANICを起こすことになり、障害が回復不能になってしまいます。これは、「説明する変更の前にWALを書き込む」という通常のWAL規則が機能しないことを意味し、そのようなケースには異なる設計が必要となります。

この問題を持つファイルシステムアクションにはいくつかの基本タイプがあります。それぞれの対処方法は以下の通りです:

1. 既存のテーブルへのディスクページの追加。

このアクションは、WALには一切記録されません。テーブルの末尾にゼロ埋めされたページを書き込むことでテーブルを拡張します。ファイルシステムが領域を確実に割り当てたことを確認するため、実際にこの書き込みを行わなければなりません。書き込みが失敗した場合は、通常どおりエラー終了させることができます。領域の割り当てが確認されたら、1回以上の通常のWAL記録アクションを通じて、ページを初期化して埋めることができます。ファイルの拡張とWALエントリの書き出しの間にクラッシュが発生する可能性があるため、テーブルまたはインデックス内で全ゼロのページが発見されたことは、エラー以外の条件として扱わなければなりません。このような場合、再利用のために領域を回収するだけで問題ありません。

2. 新しいテーブルの作成。これにはファイルシステム内の新しいファイルが必要です。

ファイルの作成を試み、成功した場合は、その旨を記載したWALレコードを作成します。成功しなかった場合は、単にエラーをスローすることができます。ファイルを作成したものの、それに関するWALがまだディスクに書き込まれていないウィンドウが存在することに注意してください。このウィンドウの間にクラッシュが発生した場合、ファイルは「孤立ファイル (orphan)」としてディスクに残ります。pg_classにコミットされたエントリを持たないファイルをデータベースの再起動時に検索させることで、このような孤立ファイルをクリーンアップすることは可能ですが、クラッシュのフォレンジック分析に有用なデータを削除してしまう可能性があるため、現在は行われていません。孤立ファイルは無害であり（最悪でもディスク領域を少し無駄にするだけです）、新しいリファイル番号（relfilenumber）のOIDを割り当てる際にディスク上の衝突をチェックするためです。したがって、クリーンアップは実際には必要ありません。

3. テーブルの削除。これには失敗する可能性のある unlink() が必要です。

ここでのアプローチは、最初に操作をWAL記録しますが、実際の unlink() 呼び出しの失敗はエラー条件ではなく警告として扱うというものです。繰り返しますが、これにより孤立ファイルが残る可能性がありますが、代替手段に比べれば安価です。DROP TABLEトランザクションをコミットするまでは実際に unlink() を実行できないため、エラーをスローすることはそもそも論外です。（ファイル削除に関するWALエントリは、実際には削除トランザクションのコミットレコードの一部であることに注目する価値があるかもしれません。）

4. データベースおよびテーブルスペースの作成と削除。これにはディレクトリおよびディレクトリツリー全体の作成と削除が必要です。

これらのケースは、個別のファイルの作成と同様に処理されます。つまり、まずアクションの実行を試み、成功した場合はWALエントリを書き込みます。もちろん、無駄になる可能性のあるディスク領域の量はかなり大きくなります。作成の場合、無駄な領域のリスクを減らすために、作成が失敗した場合はディレクトリツリーの削除を再度試みます。削除操作の途中で失敗すると、データベースが破損した状態になります。すなわち、DROPは失敗したものの、データの一部はすでに失われています。しかし、これに対してできることはほとんどなく、いずれにせよそれはユーザーがもはや必要としていないデータだったと推定されます。

これらすべてのケースにおいて、WALのリプレイが元のアクションのredo（再実行）に失敗した場合、パニックを起こしてリカバリをアボート（中断）しなければなりません。DBAは手動でクリーンアップを行い（たとえば、ディスク領域を空ける、またはディレクトリのパーミッションを修正する）、その後リカバリを再起動する必要があります。これが、元のアクションを正常に完了させるまでWALエントリを書き込まない理由の一部です。

新規RelFileLocatorに対するWALのスキップ --------------------------------

wal_level=minimal の下で、ROLLBACKがunlinkするようなリファイル番号を変更する場合、ツリー内アクセスメソッドはその変更に対するWALを書き込みません。RelationNeedsWAL()を呼び出さずにWALを書き込むコードは、このケースをチェックする必要があります。このスキップは必須です。同じブロックに対してWAL書き込みを伴う変更がWALスキップを伴う変更に先行していた場合、REDOがWALスキップの変更を上書きする可能性があります。同じブロックに対してWALスキップを伴う変更の後にWAL書き込みを伴う変更が続いた場合も、同様の問題が発生します。WALレコードにフルページイメージが含まれていない場合、REDOはページの内容がレコード挿入の直前の状態と一致することを期待します。WALスキップを伴う変更はディスクにまったく到達しない可能性があり、full_page_writes=off の下でのREDOの期待に違反します。どのアクセスメソッドであっても、CommitTransaction()はコミットを記録する前に、影響を受けるブロックを書き込んでfsyncします。

将来のアクセスメソッドでも同様に行うことが望ましいです。ただし、他の2つのアプローチも機能します。第一に、アクセスメソッドは FlushRelationBuffers() および smgrimmedsync() を呼び出すことで、指定されたフォークをWALスキップからWAL書き込みへと不可逆的に移行させることができます。第二に、アクセスメソッドは永続リレーションに対して無条件でWALを書き込むことを選択できます。これらのアプローチの下では、アクセスメソッドのコールバックは RelationNeedsWAL() に反応する関数を呼び出してはなりません。

これは、そのリプレイが新しいリファイル番号に格納されたバイトを変更するWALレコードにのみ適用されます。XLOG_SMGR_CREATEなど、リファイル番号に関する他のレコードには適用されません。個々のリファイル番号のレベルで動作するため、RelationNeedsWAL() は密結合されたリレーションの間で異なる場合があります。「CREATE TABLE t (); BEGIN; ALTER TABLE t ADD c text; ...」を考えてみてください。この場合、ALTER TABLEはTOASTリレーションを追加します。TOASTリレーションはWALをスキップしますが、それを所有するテーブルはスキップしません。ALTER TABLE SET TABLESPACEはテーブルにWALをスキップさせますが、そのインデックスには影響しません。

非同期コミット -------------------

PostgreSQL 8.3以降、非同期コミットを実行できるようになりました。つまり、コミットのWALレコードがfsyncされるのを待たないということです。 非同期コミットは synchronous_commit = off のときに実行されます。コミットのLSNまで XLogFlush() を実行する代わりに、単に共有メモリ内にLSNを記録します。その後、バックエンドは他の作業を続行します。LSNはアボートではなく非同期コミットの場合にのみ記録されます。クラッシュ後の前提としてはどうせトランザクションがアボートしたとみなされるため、アボートレコードをフラッシュする必要は決してありません。

リレーションが削除されるトランザクションの場合、ファイルシステムからリレーションが削除される前にコミットレコードが確実にディスクに書き込まれるようにするため、常に同期コミットを強制します。また、ロールバック不可能な副作用（ファイルシステムの変更など）を持つ特定のユーティリティコマンドは、ファイルシステムの変更が行われたもののトランザクションのコミットが保証されていないウィンドウを最小限に抑えるために、同期コミットを強制します。

walwriterは定期的に（wal_writer_delayを介して）起床するか、または（非同期でコミットするバックエンドによって設定されるラッチを介して）起こされ、XLogBackgroundFlush()を実行します。これは、完全に満たされた最後のWALペー​​ジの位置をチェックします。それが前方に移動していれば、その時点までのすべての変更されたバッファを書き込みます。これにより、高負荷時には完全なバッファのみを書き込むことになります。アクティビティに途切れがあり、現在のWALページが以前と同じである場合は、最も最近の非同期コミットのLSNを見つけ、必要に応じて（つまり、それが現在のWALページ内にある場合）その時点まで書き込みを行います。最後のフラッシュから wal_writer_delay よりも長い時間が経過したか、あるいは wal_writer_flush_after ブロックよりも多くのブロックが書き込まれている場合、WALも現在の位置までフラッシュされます。この仕組み自体により、非同期コミットレコードは、トランザクション完了後せいぜい wal_writer_delay の2倍の時間が経過した後にディスクに到達することが保証されます。しかしながら、複数WALページがwalwriterの1サイクルで満たされるような高負荷時に発生する書き込みの数を最小限に抑えるため、XLogFlushがフルバッファを「柔軟に」（つまり、循環WALバッファ領域の末尾で折り返すことなく）書き込み/フラッシュすることも許可しています。これにより、ワーストケースの遅延は wal_writer_delay の3サイクルになります。

非同期コミットに関して考慮すべき微細な点が他にもいくつかあります。 第一に、通常のリレーションページに対して行うのと同じ「書き込み前WALフラッシュ」ルールを強制できるようにするため、CLOGの各ページについて、そのページに影響を与えた最新のコミットのLSNを記憶しておかなければなりません。そうしないと、コミットのレコードがWALレコードよりも先にディスクに到達する可能性があります。ここでも、アボートレコードはこの考慮事項に含める必要はありません。

実際には、各clogページに対して複数のLSNが格納されます。これは、可視性テスト中にトランザクションステータスヒントビットを設定する方法に関連しています。 リレーションページにトランザクションコミットのヒントビットを設定し、そのレコードをコミットのWALレコードよりも先にディスクに到達させてはなりません。可視性テストは通常​​バッファ共有ロックを保持した状態で行われるため、WAL同期を保証するためにページのLSNを変更するという選択肢はありません。その代わりに、トランザクションに関連付けられたLSNまでまだWALをフラッシュしていない場合、ヒントビットの設定を遅延させます。これには、フラッシュされていない各非同期コミットのLSNを追跡する必要があります。このデータをclogバッファに関連付けると便利です。clogページを書き込む前にWALをフラッシュするため、コミットステータスを保持するclogページがメモリ内に残っている期間よりも長くトランザクションのLSNを記憶する必要がないことがわかっているためです。しかしながら、clog位置ごとにLSNを格納するというナイーブなアプローチ魅力的ではありません。LSNは2ビットのコミットステータスフィールドよりも32倍大きいため、8Kのclogバッファページごとに256Kの追加の共有メモリが必要になります。その代わりに、ページごとに少数のLSNを格納する方法を選択します。ここで、各LSNはそのページ上のトランザクションIDの連続した範囲内の任意のトランザクションコミットに関連付けられた最も高いLSNです。これにより、トランザクションヒントビットの設定におけるおそらく不要な遅延の代償として、ストレージを節約できます。

同じキャッシュされたLSNを共有すべきトランザクションの数（N）はいくつにすべきでしょうか？システムのワークロードが小さな非同期コミットトランザクションのみで構成されている場合、Nをwalwriterの1サイクルあたりのトランザクション数と同程度にすることは妥当です。なぜなら、それがトランザクションが真にコミットされる（したがってヒント可能になる）粒度だからです。ワーストケースは、同期コミットのトランザクションが、少し遅れてコミットする非同期コミットのトランザクションとキャッシュされたLSNを共有する場合です。最初のトランザクションをディスクに同期させるためのコストを支払ったにもかかわらず、最大3つのwalwriterサイクル後に2番目のトランザクションが同期されるまで、その出力をヒントすることができません。このことは、N（グループサイズ）をできるだけ小さく保つことを支持しています。現時点では、グループサイズを32に設定しており、これによりLSNキャッシュスペースのサイズは（BLCKSZに関係なく）実際のclogバッファスペースと同じサイズになります。

同期コミットトランザクションと非同期コミットトランザクションの両方を同時に実行できることは有用ですが、その安全性はおそらく一見して自明というわけではありません。2つのトランザクションT1とT2があると仮定します。ログシーケンス番号（LSN）は、トランザクションのコミットが記録されるWALシーケンス内のポイントであるため、LSN1とLSN2はそれらのトランザクションのコミットレコードです。T2がT1による変更を確認できる場合、T2がコミットするとき、LSN2がLSN1の後に続く必要があります。したがって、T2がコミットするとき、T1によって行われたすべての変更もWALに記録されていることが確実です。これは、T1が非同期であったか同期であったかに関わらず当てはまります。その結果、非同期コミットと同期コミットが、同期コミットによって書き込まれたデータを危険にさらすことなく、並行して動作しても安全です。ディスクへの最終書き込みはトップレベルトランザクションのコミット時にのみ発生するため、サブトランザクションはここでは重要ではありません。

データブロックへの変更は、データブロックのLSNのポイントまでWALがフラッシュされていない限り、ディスクに到達できません。安全でないデータをディスクに書き込もうとすると、そのトランザクションおよびそれ以前のトランザクションによって書き込まれたすべてのデータの安全性を保証する書き込みがトリガーされます。データブロックとclogページはいずれもLSNによって保護されています。

一時テーブルへの変更はWAL記録されないため、T1のコミットよりも先にディスクに到達する可能性がありますが、一時テーブルの内容はクラッシュ後も生存しないため、問題にはなりません。

新しいリファイル番号に対するWALをスキップするデータベースの書き込みも安全です。これらのケースでは、T1が何らかのインターロックなしでディスクへとfsyncするため、データがT1のコミットよりも先にディスクに到達することは十分にあり得ます。しかしながら、これらすべてのパスは、T1がコミットするまで他のどのトランザクションも参照できないデータを書き込むように設計されています。したがって、この状況は通常のWAL記録された更新と変わりません。

リカバリ中のトランザクションのエミュレーション -------------------------------------

リカバリ中、トランザクションの変更は発生した順序で再生されます。 この再生の一部として、読み取り専用バックエンドがMVCCスナップショットを取得できるように、いくつかのトランザクション動作をエミュレートします。 これを行うには、再生中のトランザクションに属するXIDのリストを維持し、データベースへの書き込みに対するWALレコードを記録した各トランザクションが、コミットするまで配列内に存在するようにします。 詳細については、procarray.c内のコメントを参照してください。

読み取り専用トランザクションなど、多くの操作はWALレコードをまったく書き込みません。 これらはリカバリ中のMVCCには影響を与えないため、まったく発生しなかったかのように扱うことができます。 サブトランザクションのコミットもWALレコードを書き込まず、ロック待ちのプロセスは親トランザクションの完了を待つ必要があるため、影響はごくわずかです。

すべてのトランザクション動作がエミュレートされるわけではありません。たとえば、トランザクションエントリをロックテーブルに挿入せず、メモリ内のトランザクションスタックも維持しません。 Clog、multixact、およびcommit_tsのエントリは通常どおり作成されます。 Subtransはリカバリ中に維持されますが、トランザクションツリーの詳細化は無視され、すべてのサブトランザクションがトップレベルのTransactionIdを直接参照します。 コミットはアトミックであるため、これにより正しいロック待ち動作が提供される一方で、サブトランザクションのエミュレーションが大幅に簡素化されます。

リカバリにおけるロックのメカニズムの詳細については、Lock rmgrコードのコメントを参照してください。
