Walreceiver - libpqwalreceiver API

プライマリサーバへの接続、WALファイルの受信、およびメッセージの送信を担当するwalreceiverのトランスポート固有の部分は、メインのサーババイナリをlibpqとリンクするのを避けるために、動的にロードされます。動的にロードされるモジュールは、libpqwalreceiverサブディレクトリにあります。

動的にロードされるモジュールは一連の関数を実装しており、それぞれの詳細についてはsrc/include/replication/walreceiver.hで提供されています。

このAPIは現時点では内部的なものとみなされるべきですが、将来的にはサードパーティによるlibpqwalreceiverの代替に開放し、WALを受信するためのプラグイン可能な方法を許可することも可能です。

Walreceiver IPC

スタートアッププロセスにおけるWALの再生が、restore_commandを使用してリストア可能なアーカイブWALの終端に達すると、（ストリーミングレプリケーションが設定されている場合）さらにWALを取得するためにwalreceiverプロセスを起動します。

walreceiverはpostmasterのサブプロセスであるため、スタートアッププロセスが直接forkすることはできません。代わりに、postmasterにシグナルを送信して、起動を依頼します。しかし、その前に、スタートアッププロセスはWalRcvData->conninfoとWalRcvData->slotnameを設定し、WalRcvData->receiveStartに開始点を初期化します。

walreceiverはプライマリサーバからWALを受信し、それをディスク（pg_wal内）に書き込んでフラッシュすると、WalRcvData->flushedUptoを更新し、WALの再生をどこまで進められるかを知らせるためにスタートアッププロセスにシグナルを送信します。

walreceiverは、新しいWALを書き込むかフラッシュしたとき、または指定された間隔が経過したときに、レプリケーションの進行状況に関する情報をプライマリサーバに送信します。これはレポート目的で使用されます。

Walsender IPC

シャットダウン時、postmasterはwalsenderプロセスを通常のバックエンドとは異なる方法で処理します。postmasterは、シャットダウンチェックポイントを書き込み、pgarchやその他の補助プロセスを終了させる前に、通常のバックエンドが終了するのを待ちますが、walsenderに対してはそれは望ましくありません。なぜなら、プライマリがシャットダウンされる前に、スタンバイサーバがシャットダウンチェックポイントを含むすべてのWALを受信できるようにしたいためです。したがって、postmasterはwalsenderをpgarchプロセスのように扱い、すべての通常のバックエンドが終了し、checkpointerがシャットダウンチェックポイントを発行した後のPM_WAIT_XLOG_ARCHIVALフェーズで終了するように指示します。

postmasterが接続を受け入れると、ハンドシェイクと認証を処理するために即座に新しいプロセスをforkし、そのプロセスはバックエンドになるように初期化されます。postmasterはその時点では、そのプロセスが通常のバックエンドになるのかwalsenderプロセスになるのかを知りません（それは接続ハンドシェイクで示されます）。そのため、postmasterがwalsenderプロセスを識別できるように、追加のシグナル伝達が必要になります。

walsenderプロセスが起動すると、PMSignal配列内で自身をwalsenderプロセスとしてマークします。これにより、postmasterはそれを通常のバックエンドと区別することができます。

なお、postmasterがwalsenderを通常のバックエンドとみなしたとしても、大きな害はありません。シャットダウンフェーズのより早い段階でwalsenderを終了させるだけです。walsenderは、初期化が完了してPMSignal配列に自身をマークするまで、およびプロセス終了時にPMSignalスロットのマークを解除した後は、通常のバックエンドのように見えます。

各walsenderはWalSndCtl配列からエントリを割り当て、レプリケーションの進行状況に関する情報を追跡します。ユーザーは統計ビューを介してこれらを監視できます。
