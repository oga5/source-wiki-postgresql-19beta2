What is Just-in-Time Compilation? =================================

Just-in-Timeコンパイル（JIT）は、何らかの形式のインタープリターによるプログラム評価をネイティブプログラムへと変換するプロセスであり、実行時（ランタイム）に行われます。

例えば、WHERE a.col = 3のようなSQL述語を評価するために任意のSQL式を評価できる機能を使用する代わりに、その式のみを処理する、CPUによってネイティブに実行可能な関数を生成することが可能であり、これにより高速化がもたらされます。

これが事前（AOT: ahead-of-time）コンパイルではなくJITと呼ばれるのは、クエリの実行時に行われ、おそらくは関連するタスクが何回か繰り返される場合にのみ実行されるためです。PostgreSQLにおけるJITコンパイルの使用方法を考慮すると、インタープリテーション、AOT、およびJITの境界はやや曖昧です。

ネイティブプログラムに変換されるインタープリターによるプログラムは、必ずしも古典的な意味でのプログラムである必要はないことに注意してください。例えば、タプル変形は一般的に「プログラム」として理解されていないにもかかわらず、タプル変形を特定のタイプのテーブルのみを処理するネイティブ関数にJITコンパイルすることは非常に有益です。

Why JIT? ========

PostgreSQLの一部は、比較的小さなCPU集約型のコード片によってボトルネックになることがよくあります。多くの場合、これは関連するコードが非常に汎用的でなければならないためです（例：任意の拡張機能がインストールされた状態で、任意のテーブルに対して、任意のSQLレベルの式を処理するなど）。これは多くの場合、多数の間接ジャンプと予測不可能な分岐、そして一般的に特定のタスクに対する多数の命令につながります。例えば、データベース内の列と整数を比較する式を評価するだけでも、数百サイクルが必要になります。

ネイティブコードを生成することにより、間接呼び出しを直接分岐に変換する（例：SQL演算子の実装への間接呼び出しをその関数への直接呼び出しに置き換える）、または完全に削除する（例：入力が定数であるためコンパイル時に分岐を評価して削除する）ことによって、多数の間接ジャンプを削除できます。同様に、多くの分岐を完全に削除できます（例：入力が定数であるためコンパイル時に再び分岐を評価するなど）。後者は、タプル変形中の分岐を削除するのに特に有益です。

How to JIT ==========

PostgreSQLは、デフォルトでJITを実行するためにLLVMを使用します。LLVMが選ばれた理由は、複数の大企業によって開発されているため開発が中断される可能性が低いこと、PostgreSQLと互換性のあるライセンスを持っていること、そしてそのIRがClangコンパイラを使用してCから生成できるためです。

Shared Library Separation -------------------------

メインのPostgreSQLバイナリがLLVMに直接依存することを避けるため（これはOSのパッケージマネージャーによるLLVMサポートの独立したインストールを妨げることになります）、LLVMに依存するコードはオンデマンドでロードされる共有ライブラリ内に配置されています。

これを行うことのもう一つの利点は、JITコンパイルを提供するのに使用される共有ライブラリを切り替えることにより、LLVMを使用しないJITコンパイルを比較的容易に評価できることです。

これを達成するために、JITの実行を意図したコード（例：式評価）は、それを実行するためにjit.c内にあるLLVM非依存のラッパーを呼び出します。JITサポートを提供する共有ライブラリがロード可能である場合（つまり、PostgreSQLがLLVMサポート付きでコンパイルされ、共有ライブラリがインストールされている場合）、式をJITコンパイルするタスクは共有ライブラリに引き渡されます。これは当然のことながら、JITプロバイダがロードできない場合にjit.c内の関数が失敗することを許容する必要があることを意味します。

どの共有ライブラリがロードされるかは jit_provider GUCによって決定され、デフォルトは "llvmjit" です。

JITを実行するコードを共有ライブラリに隔離することは、不運なことに、コードのさまざまな部分のためにJITコンパイルを行うコードが、JITなしでそれを行うコードとは別に配置されなければならないことも意味します。例えば、execExprInterp.cのJITバージョンは executor/ ではなく jit/llvm/ に配置されます。

JIT Context -----------

パフォーマンスと利便性の理由から、JIT化された関数をまとめて生成および解放できるようにすることが有用です。例えば、クエリの初期化時に多数の関数を作成し、クエリの実行中にそれらを使用し、クエリの終了時にそれらすべてをまとめて解放することは非常に一般的です。

JIT化された関数のライフタイムは JITContext を介して管理されます。作成されたすべてのJIT化された関数が同じライフタイムを持つべき作業に対して、このようなコンテキストを正確に1つ作成する必要があります。例えば、実行される各クエリに対して、クエリの EState 内に正確に1つの JITContext が存在します。作成はJIT実装によってオンデマンドで行われるため、プロバイダ非依存の機能に公開されているのは JITContext の解放のみです。

個々の関数を個別に生成することは、複数の関数を一度に生成するよりもコストがかかり、それらをまとめて生成することは追加の最適化の機会を提供できます。これを容易にするために、LLVMプロバイダは、関数の定義を、関数の最適化および実行可能な形式での生成から分離しています。

現在の変更可能なモジュール（モジュールは本質的にCにおける翻訳単位のLLVMの同等物です）への関数の作成は、次を使用して行われます： extern LLVMModuleRef llvm_mutable_module(LLVMJitContext *context); この中で、LLVM APIを使用して必要なだけコードを生成できます。関数を実際に呼び出す必要があるときはいつでも、 extern void *llvm_get_function(LLVMJitContext *context, const char *funcname); がそれへのポインタを返します。

例えば、式評価の場合、この設定により、クエリ内のほとんどの関数を ExecInitNode() の実行中に生成し、関数が実際に初めて使用される時点まで関数の生成を遅らせることができます。

Error Handling --------------

エラー処理には2つの側面があります。まず、生成された関数（LLVM IR）および出力された関数（mmap()されたセグメント）は、クエリの実行が成功した後とエラーの後りの両方でクリーンアップされる必要があります。これは、作成された各 JITContext を現在のリソースオーナーに登録し、エラー時/トランザクション終了時にそれをクリーンアップすることによって行われます。リソースをより早く解放することが望ましい場合は、 jit_release_context() を使用できます。

エラー処理の2つ目の、あまり美しくない側面は、LLVM自体内部でのOOM（Out of Memory）処理です。上記のresownerベースのメカニズムは ERROR 発生時に出力されたコードのクリーンアップ処理を行いますが、LLVM自体がメモリ不足になる可能性もあります。LLVMはデフォルトではC++例外を*使用しません*。その割り当ては主に標準の「new」ハンドラーを介して行われ、malloc() および mmap() が直接使用されることもあります。前者に対しては「newハンドラー」が存在します： http://en.cppreference.com/w/cpp/memory/new/set_new_handler 後者について、LLVMは失敗時に呼び出されるコールバックを提供します（残念ながらmmap()の失敗はOOMエラーではなく致命的（fatal）として扱われます）。現時点で行うこととして選択したのは、LLVMを使用するコードが使用しなければならない2つの関数を用意することです： extern void llvm_enter_fatal_on_oom(void); extern void llvm_leave_fatal_on_oom(void); これらはLLVMコードと対話する前に呼び出します。

libstdc++のnewまたはLLVMのエラーが発生すると、上記の関数によって設定されたハンドラーが FATAL エラーを引き起こします。内部状態を破損させるリスクなしに外部ライブラリ内で信頼性高く ERROR をスローすることは*できない*ため、 ERROR ではなく FATAL を使用する必要があります。

上記のセクションのユーザーは PG_TRY/CATCH ブロックを使用する必要は*ありません*。代わりに、ハンドラーはトップレベルの sigsetjmp() レベルでリセットされます。

これらのハンドラーをグローバルに設定するのではなく、比較的小さなenter/leaveで保護されたコードセクションを使用することで、PostGISのようなC++を使用する可能性のある拡張機能との望ましくない相互作用を避けることができます。LLVMコード生成は任意のコードを実行すべきではないため、これらのハンドラーを一時的に設定するだけで十分なはずです。

Type Synchronization --------------------

「インタープリター型」のPostgreSQLによって行われるタスクを実行できるコードを生成できるようにするためには、コード生成が少なくともいくつかのPostgreSQLの型について認識していることが明らかに必要です。Cコード内で手動で再作成することによってLLVMに型定義を通知することは可能ですが、それは失敗しやすく、手間がかかります。

その代わりに、JITを行うために必要な各型を参照する小さなファイル（llvmjit_types.c）が1つあります。そのファイルはコンパイル時にビットコードに翻訳され、バックエンドでLLVMが初期化されるときにロードされます。

これは型定義を同期させるためには非常にうまくいきますが、残念ながらIRレベルの表現はフィールド名を認識していないため、オフセットは同期*されません*。その代わりに、必要なオフセットは次のように元の構造体定義内のdefineとして維持されます： #define FIELDNO_TUPLETABLESLOT_NVALID 9 int tts_nvalid; /* # of valid values in tts_values */ これは依然として定義される必要がありますが、比較的少数のフィールドに対してのみ必要であり、構造体定義と一緒にまとめられているため、簡単に同期を維持できます。

Inlining --------

式をJIT化する大きな利点の1つは、呼び出された関数/演算子の本体をインライン化することにより、PostgreSQLの拡張可能な関数/演算子メカニズムのオーバーヘッドを大幅に削減できることです。

インライン化の目的だけのために、よく使用される関数の2番目の実装を維持することは明らかに望ましくありません。その代わりに、ClangコンパイラがLLVM IRを出力できるという事実を利用します。

そうする能力があることにより、2つのコピーを維持することなく、すべての演算子（例：int8eq、float8plなど）のLLVM IRを取得できます。これらのビットコードファイルは、サーバーの $pkglibdir/bitcode/postgres/ にインストールされます。既存のLLVM機能（並列LTOコンパイル用）を使用して、さらにこれらに対するインデックスが $pkglibdir/bitcode/postgres.index.bc に保存されます。

同様に、拡張機能はコードを $pkglibdir/bitcode/[extension]/ に、 $pkglibdir/bitcode/[extension].index.bc とともに、実際のライブラリのすぐ隣にインストールできます。拡張機能のインデックスは、対応する共有ライブラリ内にあるときのシンボルを検索するために使用されます。拡張機能の内部で使用されるシンボルは、インライン化されるとき、最初にメインバイナリで検索され、次に拡張機能のバイナリで検索されます。

Caching -------

パフォーマンスの観点からは望ましいものの、現在、生成された関数をキャッシュすることはまだできません。問題は、生成された関数が通常、実行ごとのメモリへのポインタを含んでいることです。それを回避するために、式評価の仕組みを少し再設計する必要があります。基本的に、メモリへの絶対ポインタではなく、ExprStateに格納された1つのメモリブロックへのオフセットとして、実行ごとのすべてのメモリを参照する必要があります。

それが解決されれば、生成されたLLVM IRをキーとするLRUキャッシュを追加することで、より高速なクエリに対しても最適化された関数の使用が可能になります。

より長期的なプロジェクトは、式のコンパイルをプランナー段階に移行し、例えばコンパイルされた式をプリペアードステートメントに結び付けられるようにすることです。

さらに高度なアプローチは、最初は最適化をほとんど行わずにJITを使用し、バックグラウンドで最適化されたバージョンを構築することです。しかし、それはさらに先の話です。

What to JIT ===========

現在、式評価とタプル変形がJIT化されています。これらが選ばれた理由は、分析クエリにおいて主要なCPUボトルネックになることが多いためですが、潜在的に有益なケースはこれらに限定されません。

JIT化が有益であるためには、コードの断片がまず第一にCPUボトルネックである必要があります。しかし重要なことに、JIT化は、それを行うことでオーバーヘッドを削減できる場合にのみ有益です。例えば、タプル変形のケースでは、列の数とその型に関する知識によって多数の分岐を削除でき、式評価のケースでは多数の間接ジャンプ/呼び出しを削除できます。これらのいずれにも該当しない場合、JIT化はリソースの無駄遣いです。

JIT化の将来の方向性には、タプルソート、COPYパース/出力生成、そして後にはクエリのより大きな部分のコンパイルが含まれます。

When to JIT ===========

現在、JIT化に影響を与えるいくつかのGUCがあります：

  • jit_above_cost = -1, 0-DBL_MAX - これより高い総コストを持つすべてのクエリが、

    • 最適化（コストのかかる部分）*なし*で、-O0に相当するJITコンパイルを受けます。 式やデフォーミングがボトルネックである場合（主に動的な分岐を削除するため）、 これにより通常すでに大幅な高速化がもたらされます。

  • jit_optimize_above_cost = -1, 0-DBL_MAX - これより高い総コストを持つすべてのクエリが、

    • 最適化（コストのかかる部分）*あり*でJITコンパイルを受けます。

  • jit_inline_above_cost = -1, 0-DBL_MAX - クエリがより高いコストを持つ場合、

    • インライン化が試行されます。

クエリの総コストがこれらの制限値を超えると、常にJITコンパイルが実行されます。

cpu_*コストが低いクエリの部分に対して個別のパスを生成するなど、代替のコストモデルも 可能ですが、そうすることによるオーバーヘッドが割に合うかどうかは疑問です。 もう一つの代替案としては、個々の式が評価されると推計される回数をカウントし、 それらの個々の式をJITコンパイルすることが挙げられます。

一見して妥当と思われる、一定回数の実行後に式を個別にJITコンパイルするアプローチは、 あまりうまく機能しないことが判明しています。主に、多数の小さな関数を個別に 生成することに大きなオーバーヘッドがあるためです。第二に、JITコンパイルが発生するまでの 時間が相対的な速度低下を引き起こし、JITコンパイルによる利益を相殺してしまうためです。
