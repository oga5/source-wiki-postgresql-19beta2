Optimizer =========

これらのディレクトリは、パーサーから返されたQuery構造体を受け取り、エグゼキューターが使用するプランを生成します。/planディレクトリは実際の出力プランを生成し、/pathコードはテーブルを結合するためのすべての可能な方法を生成し、/prepは特殊なケースに対するさまざまな前処理ステップを処理します。/utilはユーティリティ関係です。/geqoは個別の「遺伝的最適化」プランナーです。これは、可能な結合ツリーをすべて網羅的に検討するのではなく、結合ツリー空間を半ランダムに検索します（ただし、/geqoによって検討される各結合は、パスを作成するために/pathに渡されるため、GEQOモードでも、特定の結合ペアごとに可能なすべての実装パスが検討されます）。

Paths and Join Pairs --------------------

計画/最適化のプロセス中に、クエリを実行するさまざまな方法を表す「Path」ツリーを構築します。目的のリレーションを生成する最もコストの低いPathを選択し、エグゼキューターに渡すPlanに変換します（PathツリーとPlanツリーの間にはほぼ1対1の対応関係がありますが、Pathノードには計画時には不要な情報が省略され、エグゼキューターには不要だが計画には必要な情報が含まれています）。

オプティマイザーは、クエリで使用される各ベースリレーションに対してRelOptInfo構造体を構築します。ベースリレーションは、プリミティブテーブル、またはプランナーの別の再帰的呼び出しによって計画されるサブクエリのサブセレクトのいずれかです。RelOptInfoは、計画中に検討される各結合リレーションに対しても構築されます。結合リレーションは、単にベースリレーションの組み合わせです。指定されたベースリレーションのセットに対して結合RelOptInfoは1つだけ存在します。たとえば、結合 {A B C} は、最初にAとBを結合してからCを追加した場合でも、最初にBとCを結合してからAを追加した場合でも、同じRelOptInfoで表されます。結合リレーションを構築するこれらの異なる手段は、Pathとして表されます。各RelOptInfoについて、そのリレーションのスキャンまたは結合を実装する妥当な方法を表すPathのリストを構築します。リレーションのすべての妥当なPathを検討したら、プランナーのコスト見積もりに従って最もコストの低いものを選択します。最終的なプランは、クエリのすべてのベースリレーションを含むRelOptInfoの最もコストの低いPathから導出されます。

プリミティブテーブルリレーションの可能なPathには、古き良きシーケンシャルスキャンに加え、テーブルに存在する任意のインデックスに対するインデックススキャン、さらに1つ以上のインデックスを使用したビットマップインデックススキャンが含まれます。関数RTEなどの特殊化されたRTEタイプには、可能なPathが1つしかない場合があります。

結合は常にかつて2つのRelOptInfoを使用して発生します。1つは外側、もう1つは内側です。外側は内側での値のルックアップを駆動します。ネストループでは、内側での値のルックアップは、一致する内側の行をそれぞれ見つけるために、外側のタプルごとに内側のパスを1回スキャンすることによって発生します。マージジョインでは、内側と外側の行が順序付けられ、順序通りにアクセスされるため、結合全体を実行するのに必要なスキャンは1回だけです。内側と外側の両方のパスが同期してスキャンされます（マージジョインでは内側と外側の間に大きな違いはありません...）。ハッシュジョインでは、最初に内側がスキャンされてそのすべての行がハッシュテーブルに登録され、次に外側がスキャンされて行ごとに結合キーがハッシュテーブルでルックアップされます。

結合リレーションのPathは、実際にはツリー構造であり、最上位のPathノードは最後に適用された結合メソッドを表します。これには、2つの入力リレーションに使用されるスキャンまたは結合メソッドを表す左サブパスと右サブパスがあります。

Join Tree Construction ----------------------

オプティマイザーは、クエリの実行方法を多かれ少なかれ網羅的に検索することにより、最適なクエリプランを生成します。最適なPathツリーは、再帰的なプロセスによって見つかります。

1) クエリ内の各ベースリレーションを取得し、そのRelOptInfo構造体を作成します。シーケンシャルスキャンやインデックススキャンなど、リレーションにアクセスする可能性のある有用な方法をすべて見つけ、それらの方法を表すPathを作成します。特定のリレーションに対して作成されたすべてのPathは、そのRelOptInfo.pathlistに配置されます。（実際には、パスリストに入る前に、明らかに劣る代替手段であるPathは破棄されます。パスリストに行き着くのは、リレーションの潜在的に有用なソート順序とパラメータ化のそれぞれを生成する最も安価な方法です。）また、このリレーションに関係するすべての結合句を含むRelOptInfo.joininfoリストを作成します。たとえば、WHERE句 "tab1.col1 = tab2.col1" は、tab1とtab2の両方のjoininfoリストのエントリを生成します。

クエリ内にベースリレーションが1つしかない場合は、これで完了です。それ以外の場合は、ベースリレーションを単一の結合リレーションに結合する方法を考え出す必要があります。

2) 通常、明示的なJOIN句は、結合するリレーションのリストを持つだけになるように「平坦化」されます。ただし、FULL OUTER JOIN句は決して平坦化されず、join_collapse_limitまたはfrom_collapse_limitの制限によって平坦化プロセスが停止された場合、他の種類のJOINも平坦化されない可能性があります。したがって、任意の順序で結合するリレーションのリストを含む計画問題に帰着します。ここで、個々のアイテムは、その兄弟と結合することを検討する前に結合する必要があるサブリストである可能性があります。これらのサブ問題は、ボトムアップで再帰的に処理します。結合リストの構造は可能な結合順序を制約しますが、各結合での結合実装方法（ネストループ、マージ、ハッシュ）を制約せず、各結合でどのリレーションが外側または内側と見なされるかも指定しません。Pathsを構築する際に、これらすべての可能性を検討します。実行可能な結合方法ごとにPathを生成し、最もコストの低いPathを選択します。

したがって、各計画問題について、ベースリレーションまたはサブ結合リストごとに構築された結合リレーションのいずれかであるリレーションのリストを持つことになります。プランナーが適切とみなす任意の順序で、これらのリレーションを結合できます。標準の（GEQOではない）プランナーは、これを次のように実行します。

使用可能な結合句がある各RelOptInfoを他の各RelOptInfoと結合することを検討し、そのような各ペアの可能な結合方法ごとにPathを生成します。（結合句のないRelOptInfoがある場合、句のないデカルト積結合を生成する以外の選択肢がないため、そのリレーションを使用可能な他の各リレーションと結合することを検討します。ただし、結合句が存在する場合は、使用可能な結合句を使用する結合のみを検討します。なお、外部結合やIN/EXISTS句によって誘発される結合順序の制限もチェックされ、それらの制限によって句のない結合を強制される場合に実行可能な結合順序が見つかるようにします。）

リスト内のリレーションが2つだけの場合は、これで完了です。結合RelOptInfoの最も安いパスを選択するだけです。3つ以上ある場合は、結合RelOptInfo同士を結合して、3つ以上のリストアイテムを表す結合RelOptInfoを作る方法を検討する必要があります。

結合ツリーは「動的計画法」アルゴリズムを使用して構築されます。最初のパス（すでに説明した）では、正確に2つのリストアイテムを表す結合リレーションを作成する方法を検討します。2回目のパスでは、正確に3つのリストアイテムを表す結合リレーションを作る方法を検討し、次のパスでは4つのアイテム、というようになります。最後のパスでは、すべてのリストアイテムを含む最終的な結合リレーションを作る方法を検討します。当然ながら、この最上位レベルの結合リレーションは1つしか存在できませんが、下位レベルでは複数の結合リレーションが存在する可能性があります。各レベルでは、最初のレベルで説明したように、可能であれば使用可能な結合句に従う結合を使用します。

例:

SELECT * FROM tab1, tab2, tab3, tab4 WHERE tab1.col = tab2.col AND tab2.col = tab3.col AND tab3.col = tab4.col

テーブル 1、2、3、4 は次のように結合されます: {1 2},{2 3},{3 4} {1 2 3},{2 3 4} {1 2 3 4}

SELECT * FROM tab1, tab2, tab3, tab4 WHERE tab1.col = tab2.col AND tab1.col = tab3.col AND tab1.col = tab4.col

テーブル 1、2、3、4 は次のように結合されます: {1 2},{1 3},{1 4} {1 2 3},{1 3 4},{1 2 4} {1 2 3 4}

これらの各例において、結合句がないため、他の結合順序の可能性は除外されます。（実際には、EquivalenceClassesを使用することで、より多くの結合順序を許可する追加の結合句を推論できますが、ここでは例の単純さを保つためにそれを無視しています。）

左偏向プラン（上位結合の外側リレーションは結合リレーションですが、内側は常に単一のリストアイテムです）、右偏向プラン（外側リレーションは常に単一のアイテムです）、および木構造プラン（内側と外側の両方がそれ自体で結合になり得ます）を検討します。たとえば、{1 2 3 4}を構築する場合、{1 2 3}と{4}の結合（左偏向）、{4}と{1 2 3}の結合（右偏向）、および{1 2}と{3 4}の結合（木構造）などを検討します。結合ツリー走査コードはこれらの潜在的な結合の組み合わせを1つずつ生成しますが、結合されたベースリレーションの同じセットを生成するすべての方法は同じRelOptInfoを共有するため、同等の結合リレーションを生成する異なる結合の組み合わせから生成されたパスはadd_path()で競合します。

動的計画法のアプローチには、すぐには分からない重要な特性があります。それは、そのリレーションを含むリレーションのパスを構築する前に、特定のリレーションのすべてのパスの構築が完了するということです。これは、高レベルのリレーションがそれを知る必要が生じる前に、各リレーションの「最も安いパス」を確実に対象として特定できることを意味します。また、同じリレーションの別のパスの方が優れていることが判明したときに、高レベルの結合パスにそのパスへの参照がすでに含まれているのではないかと心配することなく、パスを安全に破棄できます。これがないと、パスのメモリ管理ははるかに複雑になります。

最終的な結合リレーションを構築したら、その最も安いパスか、あるいは目的の順序を持つ最も安いパス（それが他の最も安いパスにソートを適用するよりも安い場合）を使用します。

クエリに片側外部結合（LEFTまたはRIGHT結合）、あるいはセミジョインまたはアンチジョインに変換されたINまたはEXISTS WHERE句が含まれている場合、可能な結合順序の一部が不正になる可能性があります。これらは、提案された結合が不正かどうかを確認するために、join_is_legalにそのような「特殊な」結合のサイドリストを参照させることで除外されます。（同じ参照により、有効な結合（つまりJOIN_INNER、JOIN_LEFTなど）に対してどの結合スタイルを適用すべきかを確認できます。）

Valid OUTER JOIN Optimizations ------------------------------

プランナーによる外部結合の並び替えの扱いは、次の同一性に基づいています。

1. (A leftjoin B on (Pab)) innerjoin C on (Pac) = (A innerjoin C on (Pac)) leftjoin B on (Pab)

ここで、PacはAとCなどを参照する述語です（この場合、PacがBを参照できないことは明らかです。そうでない場合、変換は無意味になります）。

2. (A leftjoin B on (Pab)) leftjoin C on (Pac) = (A leftjoin C on (Pac)) leftjoin B on (Pab)

3. (A leftjoin B on (Pab)) leftjoin C on (Pbc) = A leftjoin (B leftjoin C on (Pbc)) on (Pab)

同一性3は、述語Pbcがすべての値がNULLであるBの行に対して失敗する場合にのみ成り立ちます（つまり、PbcはBの少なくとも1つのカラムに対して厳密です）。Pbcが厳密でない場合、最初の形式では、2番目の形式ではそれらのエントリがNULLになる場所で、非NULLのCカラムを持ついくつかの行が生成される可能性があります。

RIGHT JOINは、2つの入力テーブルを入れ替えた後のLEFT JOINと同等であるため、右結合に対しても同じ同一性が機能します。

機能し*ない*ケースの例として、内部結合を外部結合のNULL許容側に移動したり、そこから外に移動したりすることが挙げられます。

A leftjoin (B join C on (Pbc)) on (Pab) != (A leftjoin B on (Pab)) join C on (Pbc)

セミジョインの動作は少し異なります。セミジョインは、別のセミジョイン、左結合、またはアンチジョインの左側の内部または外部に関連付け直すことはできますが、右側に関連付け直すことはできません。同様に、内部結合、左結合、またはアンチジョインは、セミジョインの左側に結びつけて関連付け直すことはできますが、右側に関連付け直すことはできません。

ANTI結合は、LEFT結合とほぼ同様に機能しますが、Cへの結合がアンチ結合である場合（Pbcが厳密（strict）である場合であっても、また、もう一方の結合がLEFT結合である場合とアンチ結合である場合の双方向において）、恒等式3が成立しなくなります。そのため、関連する節が厳密である場合であっても、アンチ結合をLEFT結合やアンチ結合のRHS（右辺）に移動したり、RHSから外へ並び替えたりすることはできません。

現在のコードでは、FULL JOINの並び替えをまったく試みません。 FULL JOINの順序付けは、ジョインツリーを「joinlist」表現に変換する際にFULL JOINノードを折り畳まないことで強制されます。他のタイプのJOINノードは、結合順序の探索に完全に参加できるよう、通常は折り畳まれます。不正な結合順序の生成を回避するため、プランナは非インナー結合ごとにSpecialJoinInfoノードを作成し、join_is_legalはこのリストをチェックして、提案された結合が合法であるかどうかを判断します。

SpecialJoinInfoノードに格納されるのは、アウター結合（OJ）を形成するために結合の両側に必要なRelidの最小セットです。これらは最小値であることに注意してください。明示的な最大値はありません。なぜなら、他のリレーションをOJの構文上のリレーションに結合することは合法である可能性があるからです。恒等式1および2に従い、非FULL結合はOJの左辺に自由に結合させることができますが、場合によっては右辺に結合させることができないこともあります。 したがって、join_is_legalによって強制される制限とは、提案された結合が、RHS境界の内側または部分的に内側にあるリレーションを、境界の外側にあるリレーションに結合してはならないというものです。ただし、その提案された結合が、恒等式3を使用してSpecialJoinInfoのRHSに結合できるLEFT結合である場合は除きます。

最小Relidセットの使用にはいくつかの落とし穴があります。例えば、次のようなクエリを考えてみてください。 A leftjoin (B leftjoin (C innerjoin D) on (Pbcd)) on Pa ここで、PaはB、C、Dにまったく言及していません。この場合、素朴な計算では、上側のleftjoinの最小LHSは{A}となり、最小RHSは{C,D}となります（インナー結合がleftjoinのRHSから外へ結合できないことが分かっているため、そのrelidをleftjoinの最小RHSに含めることでそれを強制するため）。そして、下側のleftjoinの最小LHSは{B}、最小RHSは{C,D}となります。このような情報が与えられると、join_is_legalは上側の結合を下側の結合のRHSに結合しても問題ないと判断し、クエリを次のように変換してしまいます。 B leftjoin (A leftjoin (C innerjoin D) on Pa) on (Pbcd) これにより、完全に誤った結果が生成されます。これを防ぐために、上側の結合の最小RHSにBを含めるよう強制します。これはおそらく制限が厳しすぎますが、そのようなケースは頻繁には発生しないため、より複雑なシステムを開発する価値があるかどうかは明確ではありません。

サブクエリのプルアップ ---------------------

前述したように、レンジテーブルに現れるサブクエリは個別に計画され、外部クエリの計画時には「ブラックボックス」として扱われます。これは、サブクエリが集約、GROUP、DISTINCTなどの機能を使用している場合には必須です。しかし、サブクエリが単なる単純なスキャンや結合である場合、サブクエリをブラックボックスとして扱うと、プラン全体の探索空間の一部として考慮する場合と比較して、質の低いプランが生成される可能性があります。 したがって、計画プロセスの開始時に、プランナは単純なサブクエリを探し出し、メインクエリのジョインツリーへとプルアップします。

サブクエリのプルアップにより、ジョインツリーの最上部より下にFROMリストの結合が現れる結果となることがあります。各FROMリストは、前述の動的計画法による探索手法を使用して計画されます。

サブクエリのプルアップによって、別のFROMリストの直接の子としてFROMリストが生成された場合、これら2つのFROMリストをマージすることができます。それが完了すると、サブクエリは外部クエリの完全に不可欠な一部となり、ジョインツリーの探索空間をまったく制約しなくなります。しかし、動的計画法による探索の実行時間が考慮対象のFROM項目の数に対して指数関数的であるため、これにより計画時間が好ましくない増大をする可能性があります。したがって、もしマージした結果1つのリスト内のFROM項目が多すぎることになる場合は、FROMリストをマージしません。

Vars と PlaceHolderVars ------------------------

Varノードは、テーブル列参照のパースツリー表現に過ぎません。しかし、アウター結合が存在する場合、その概念は一見して思われるよりも微妙です。Varを強制的にNULLにする可能性のあるアウター結合の「上」と「下」におけるVarの値を区別する必要があります。例として、次を考えてみてください。

SELECT * FROM t1 LEFT JOIN t2 ON (t1.x = t2.y) WHERE foo(t2.z)

（foo()は厳密（strict）ではないと仮定し、left joinを通常のjoinに縮小できないようにします。）素朴な実装では、foo(t2.z)の呼び出しをt2のスキャンまでプッシュダウンしようとするかもしれませんが、それは正しくありません。なぜなら、(a) NULL拡張された結合行に対してfoo()が実際に目にするべきなのはNULLであり、(b) foo()が偽を返す場合、t2がNULL拡張された行として出力するのではなく、結合からt1の行を完全に除外すべきだからです。一方で、もしクエリが次のようなものであれば、その呼び出しをスキャンレベルまでプッシュダウンすることは正しい（そして望ましい）ことです。

SELECT * FROM t1 LEFT JOIN t2 ON (t1.x = t2.y AND foo(t2.z))

このことから、left joinのON句内における「t2.z」は、JOIN句の外側における「t2.z」とは異なる値であるとみなす動機が生まれます。前者はリレーションスキャンレベルで見られるt2.zと同一視できますが、後者はできません。

もう一つの例は、（後述する）EquivalenceClassに関連して発生します。次が与えられたとき、 SELECT * FROM t1 LEFT JOIN t2 ON (t1.x = t2.y) WHERE t1.x = 42

EquivalenceClassのメカニズムを使用して「t2.y = 42」を導出し、それをt2のスキャンの制限句として使用したいと考えます（yが42と異なるt2行はクエリ結果に影響を与えないため、これは機能します）。しかし、結合されたすべての行においてt2.yがt1.xと等しくなると結論付けるのは誤りです。この問題の解決策の一部は、ON句内の「t2.y」がt2.yのリレーションスキャンレベルの値を指し、結合された行でyがt1.xと等しいのではなくNULLになる可能性がある値は指さないとみなすことです。

PlaceHolderVars (PHVs) are more complicated than Vars in another way: their original value might need to be calculated at a join, not a base-level relation scan. This can happen when a pulled-up subquery contains a join. Because of this, a PHV can create a join order constraint that wouldn't otherwise exist, to ensure that it can be calculated before it is used. Relation Identification and Qual Clause Placement -------------------------------------------------

A qual clause obtained from WHERE or JOIN/ON can be enforced at the lowest scan or join level that includes all relations used in the clause. For this purpose we consider that outer joins listed in varnullingrels or phnullingrels are used in the clause, since we can't compute the qual's result correctly until we know whether such Vars have gone to null.

The one exception to this general rule is that a non-degenerate outer JOIN/ON qual (one that references the non-nullable side of the join) cannot be enforced below that join, even if it doesn't reference the nullable side. Pushing it down into the non-nullable side would result in rows disappearing from the join's result, rather than appearing as null-extended rows. To handle that, when we identify such a qual we artificially add the join's minimum input relid set to the set of relations it is considered to use, forcing it to be evaluated exactly at that join level. The same happens for outer-join quals that mention no relations at all.

When attaching a qual clause to a join plan node that is performing an outer join, the qual clause is considered a "join clause" (that is, it is applied before the join performs null-extension) if it does not reference that outer join in any varnullingrels or phnullingrels set, or a "filter clause" (applied after null-extension) if it does reference that outer join. A qual clause that originally appeared in that outer join's JOIN/ON will fall into the first category, since the parser would not have marked any of its Vars as referencing the outer join. A qual clause that originally came from some upper ON clause or WHERE clause will be seen as referencing the outer join if it references any of the nullable side's Vars, since those Vars will be so marked by the parser. But, if such a qual does not reference any nullable-side Vars, it's okay to push it down into the non-nullable side, so it won't get attached to the join node in the first place.

These things lead us to identify join relations within the planner by the sets of base relation RT indexes plus outer join RT indexes that they include. In that way, the sets of relations used by qual clauses can be directly compared to join relations' relid sets to see where to place the clauses. These identifying sets are unique because, for any given collection of base relations, there is only one valid set of outer joins to have performed along the way to joining that set of base relations (although the order of applying them could vary, as discussed above).

SEMI joins do not have RT indexes, because they are artifacts made by the planner rather than the parser. (We could create rangetable entries for them, but there seems no need at present.) This does not cause a problem for qual placement, because the nullable side of a semijoin is not referenceable from above the join, so there is never a need to cite it in varnullingrels or phnullingrels. It does not cause a problem for join relation identification either, since whether a semijoin has been completed is again implicit in the set of base relations included in the join.

As usual, outer join identity 3 complicates matters. If we start with (A leftjoin B on (Pab)) leftjoin C on (Pbc) then the parser will have marked any C Vars appearing above these joins with the RT index of the B/C join. If we now transform to A leftjoin (B leftjoin C on (Pbc)) on (Pab) then it would appear that a clause using only such Vars could be pushed down and applied as a filter clause (not a join clause) at the lower B/C join. But *this might not give the right answer* since the clause might see a non-null value for the C Var that will be replaced by null once the A/B join is performed. We handle this by saying that the pushed-down join hasn't completely performed the work of the B/C join and hence is not entitled to include that outer join relid in its relid set. When we form the A/B join, both outer joins' relids will be added to its relid set, and then the upper clause will be applied at the correct join level. (Note there is no problem when identity 3 is applied in the other direction: if we started with the second form then upper C Vars are marked with both outer join relids, so they cannot drop below whichever join is applied second.) Similarly, Vars representing the output of a pushed-down join do not acquire nullingrel bits for that join until after the upper join is performed.

There is one additional complication for qual clause placement, which occurs when we have made multiple versions of an outer-join clause as described previously (that is, we have both "Pbc" and "Pb*c" forms of the same clause seen in outer join identity 3). When forming an outer join we only want to apply one of the redundant versions of the clause. If we are forming the B/C join without having yet computed the A/B join, it's easy to reject the "Pb*c" form since its required relid set includes the A/B join relid which is not in the input. However, if we form B/C after A/B, then both forms of the clause are applicable so far as that test can tell. We have to look more closely to notice that the "Pbc" clause form refers to relation B which is no longer directly accessible. While such a check could be performed using the per-relation RelOptInfo.nulling_relids data, it would be annoyingly expensive to do over and over as we consider different join paths. To make this simple and reliable, we compute an "incompatible_relids" set for each variant version (clone) of a redundant clause. A clone clause should not be applied if any of the outer-join relids listed in incompatible_relids has already been computed below the current join.

EquivalenceClasses
------------------

During the deconstruct_jointree() scan of the query's qual clauses, we
look for mergejoinable equality clauses A = B.  When we find one, we
create an EquivalenceClass containing the expressions A and B to record
that they are equal.  If we later find another equivalence clause B = C,
we add C to the existing EquivalenceClass for {A B}; this may require
merging two existing EquivalenceClasses.  At the end of the scan, we have
sets of values that are known all transitively equal to each other.  We can
therefore use a comparison of any pair of the values as a restriction or
join clause (when these values are available at the scan or join, of
course); furthermore, we need test only one such comparison, not all of
them.  Therefore, equivalence clauses are removed from the standard qual
distribution process.  Instead, when preparing a restriction or join clause
list, we examine each EquivalenceClass to see if it can contribute a
clause, and if so we select an appropriate pair of values to compare.  For
example, if we are trying to join A's relation to C's, we can generate the
clause A = C, even though this appeared nowhere explicitly in the original
query.  This may allow us to explore join paths that otherwise would have
been rejected as requiring Cartesian-product joins.

Sometimes an EquivalenceClass may contain a pseudo-constant expression
(i.e., one not containing Vars or Aggs of the current query level, nor
volatile functions).  In this case we do not follow the policy of
dynamically generating join clauses: instead, we dynamically generate
restriction clauses "var = const" wherever one of the variable members of
the class can first be computed.  For example, if we have A = B and B = 42,
we effectively generate the restriction clauses A = 42 and B = 42, and then
we need not bother with explicitly testing the join clause A = B when the
relations are joined.  In effect, all the class members can be tested at
relation-scan level and there's never a need for join tests.

The precise technical interpretation of an EquivalenceClass is that it
asserts that at any plan node where more than one of its member values
can be computed, output rows in which the values are not all equal may
be discarded without affecting the query result.  (We require all levels
of the plan to enforce EquivalenceClasses, hence a join need not recheck
equality of values that were computable by one of its children.)

Outer joins complicate this picture quite a bit, however.  While we could
theoretically use mergejoinable equality clauses that appear in outer-join
conditions as sources of EquivalenceClasses, there's a serious difficulty:
the resulting deductions are not valid everywhere.  For example, given

	SELECT * FROM a LEFT JOIN b ON (a.x = b.y AND a.x = 42);

we can safely derive b.y = 42 and use that in the scan of B, because B
rows not having b.y = 42 will not contribute to the join result.  However,
we cannot apply a.x = 42 at the scan of A, or we will remove rows that
should appear in the join result.  We could apply a.x = 42 as an outer join
condition (and then it would be unnecessary to also check a.x = b.y).
This is not yet implemented, however.

A related issue is that constants appearing below an outer join are
less constant than they appear.  Ordinarily, if we find "A = 1" and
"B = 1", it's okay to put A and B into the same EquivalenceClass.
But consider

	SELECT * FROM a
	  LEFT JOIN (SELECT * FROM b WHERE b.z = 1) b ON (a.x = b.y)
	WHERE a.x = 1;

It would be a serious error to conclude that a.x = b.z, so we cannot
form a single EquivalenceClass {a.x b.z 1}.

This leads to considering EquivalenceClasses as applying within "join
domains", which are sets of relations that are inner-joined to each other.
(We can treat semijoins as if they were inner joins for this purpose.)
There is a top-level join domain, and then each outer join in the query
creates a new join domain comprising its nullable side.  Full joins create
two join domains, one for each side.  EquivalenceClasses generated from
WHERE are associated with the top-level join domain.  EquivalenceClasses
generated from the ON clause of an outer join are associated with the
domain created by that outer join.  EquivalenceClasses generated from the
ON clause of an inner or semi join are associated with the syntactically
most closely nested join domain.

Having defined these domains, we can fix the not-so-constant-constants
problem by considering that constants only match EquivalenceClass members
when they come from clauses within the same join domain.  In the above
example, this means we keep {a.x 1} and {b.z 1} as separate
EquivalenceClasses and don't erroneously merge them.  We don't have to
worry about this for Vars (or expressions containing Vars), because
references to the "same" column from different join domains will have
different varnullingrels and thus won't be equal() anyway.

In the future, the join-domain concept may allow us to treat mergejoinable
outer-join conditions as sources of EquivalenceClasses.  The idea would be
that conditions derived from such classes could only be enforced at scans
or joins that are within the appropriate join domain.  This is not
implemented yet, however, as the details are trickier than they appear.

Another instructive example is:

	SELECT *
	  FROM a LEFT JOIN
	       (SELECT * FROM b JOIN c ON b.y = c.z WHERE b.y = 10) ss
	       ON a.x = ss.y
	  ORDER BY ss.y;

We can form the EquivalenceClass {b.y c.z 10} and thereby apply c.z = 10
while scanning C, as well as b.y = 10 while scanning B, so that no clause
needs to be checked at the inner join.  The left-join clause "a.x = ss.y"
(really "a.x = b.y") is not considered an equivalence clause, so we do
not insert a.x into that same EquivalenceClass; if we did, we'd falsely
conclude a.x = 10.  In the future though we might be able to do that,
if we can keep from applying a.x = 10 at the scan of A, which in principle
we could do by noting that the EquivalenceClass only applies within the
{B,C} join domain.

Also notice that ss.y in the ORDER BY is really b.y* (that is, the
possibly-nulled form of b.y), so we will not confuse it with the b.y member
of the lower EquivalenceClass.  Thus, we won't mistakenly conclude that
that ss.y is equal to a constant, which if true would lead us to think that
sorting for the ORDER BY is unnecessary (see discussion of PathKeys below).
Instead, there will be a separate EquivalenceClass containing only b.y*,
which will form the basis for the PathKey describing the required sort
order.

Also consider this variant:

	SELECT *
	  FROM a LEFT JOIN
	       (SELECT * FROM b JOIN c ON b.y = c.z WHERE b.y = 10) ss
	       ON a.x = ss.y
	  WHERE a.x = 42;

We still form the EquivalenceClass {b.y c.z 10}, and additionally
we have an EquivalenceClass {a.x 42} belonging to a different join domain.
We cannot use "a.x = b.y" to merge these classes.  However, we can compare
that outer join clause to the existing EquivalenceClasses and form the
derived clause "b.y = 42", which we can treat as a valid equivalence
within the lower join domain (since no row of that domain not having
b.y = 42 can contribute to the outer-join result).  That makes the lower
EquivalenceClass {42 b.y c.z 10}, resulting in the contradiction 10 = 42,
which lets the planner deduce that the B/C join need not be computed at
all: the result of that whole join domain can be forced to empty.
(This gets implemented as a gating Result filter, since more usually the
potential contradiction involves Param values rather than just Consts, and
thus it has to be checked at runtime.  We can use the join domain to
determine the join level at which to place the gating condition.)

There is an additional complication when re-ordering outer joins according
to identity 3.  Recall that the two choices we consider for such joins are

	A leftjoin (B leftjoin C on (Pbc)) on (Pab)
	(A leftjoin B on (Pab)) leftjoin C on (Pb*c)

where the star denotes varnullingrels markers on B's Vars.  When Pbc
is (or includes) a mergejoinable clause, we have something like

	A leftjoin (B leftjoin C on (b.b = c.c)) on (Pab)
	(A leftjoin B on (Pab)) leftjoin C on (b.b* = c.c)

We could generate an EquivalenceClause linking b.b and c.c, but if we
then also try to link b.b* and c.c, we end with a nonsensical conclusion
that b.b and b.b* are equal (at least in some parts of the plan tree).
In any case, the conclusions we could derive from such a thing would be
largely duplicative.  Conditions involving b.b* can't be computed below
this join nest, while any conditions that can be computed would be
duplicative of what we'd get from the b.b/c.c combination.  Therefore,
we choose to generate an EquivalenceClause linking b.b and c.c, but
"b.b* = c.c" is handled as just an ordinary clause.

To aid in determining the sort ordering(s) that can work with a mergejoin,
we mark each mergejoinable clause with the EquivalenceClasses of its left
and right inputs.  For an equivalence clause, these are of course the same
EquivalenceClass.  For a non-equivalence mergejoinable clause (such as an
outer-join qualification), we generate two separate EquivalenceClasses for
the left and right inputs.  This may result in creating single-item
equivalence "classes", though of course these are still subject to merging
if other equivalence clauses are later found to bear on the same
expressions.

Another way that we may form a single-item EquivalenceClass is in creation
of a PathKey to represent a desired sort order (see below).  This happens
if an ORDER BY or GROUP BY key is not mentioned in any equivalence
clause.  We need to reason about sort orders in such queries, and our
representation of sort ordering is a PathKey which depends on an
EquivalenceClass, so we have to make an EquivalenceClass.  This is a bit
different from the above cases because such an EquivalenceClass might
contain an aggregate function or volatile expression.  (A clause containing
a volatile function will never be considered mergejoinable, even if its top
operator is mergejoinable, so there is no way for a volatile expression to
get into EquivalenceClasses otherwise.  Aggregates are disallowed in WHERE
altogether, so will never be found in a mergejoinable clause.)  This is just
a convenience to maintain a uniform PathKey representation: such an
EquivalenceClass will never be merged with any other.  Note in particular
that a single-item EquivalenceClass {a.x} is *not* meant to imply an
assertion that a.x = a.x; the practical effect of this is that a.x could
be NULL.

PathKeys
--------

The PathKeys data structure represents what is known about the sort order
of the tuples generated by a particular Path.  A path's pathkeys field is a
list of PathKey nodes, where the n'th item represents the n'th sort key of
the result.  Each PathKey contains these fields:

	* a reference to an EquivalenceClass
	* a btree opfamily OID (must match one of those in the EC)
	* a sort direction (ascending or descending)
	* a nulls-first-or-last flag

The EquivalenceClass represents the value being sorted on.  Since the
various members of an EquivalenceClass are known equal according to the
opfamily, we can consider a path sorted by any one of them to be sorted by
any other too; this is what justifies referencing the whole
EquivalenceClass rather than just one member of it.

In single/base relation RelOptInfo's, the Paths represent various ways
of scanning the relation and the resulting ordering of the tuples.
Sequential scan Paths have NIL pathkeys, indicating no known ordering.
Index scans have Path.pathkeys that represent the chosen index's ordering,
if any.  A single-key index would create a single-PathKey list, while a
multi-column index generates a list with one element per key index column.
Non-key columns specified in the INCLUDE clause of covering indexes don't
have corresponding PathKeys in the list, because they have no influence on
index ordering.  (Actually, since an index can be scanned either forward or
backward, there are two possible sort orders and two possible PathKey lists
it can generate.)

Note that a bitmap scan has NIL pathkeys since we can say nothing about
the overall order of its result.  Also, an indexscan on an unordered type
of index generates NIL pathkeys.  However, we can always create a pathkey
by doing an explicit sort.  The pathkeys for a Sort plan's output just
represent the sort key fields and the ordering operators used.

Things get more interesting when we consider joins.  Suppose we do a
mergejoin between A and B using the mergeclause A.X = B.Y.  The output
of the mergejoin is sorted by X --- but it is also sorted by Y.  Again,
this can be represented by a PathKey referencing an EquivalenceClass
containing both X and Y.

With a little further thought, it becomes apparent that nestloop joins
can also produce sorted output.  For example, if we do a nestloop join
between outer relation A and inner relation B, then any pathkeys relevant
to A are still valid for the join result: we have not altered the order of
the tuples from A.  Even more interesting, if there was an equivalence clause
A.X=B.Y, and A.X was a pathkey for the outer relation A, then we can assert
that B.Y is a pathkey for the join result; X was ordered before and still
is, and the joined values of Y are equal to the joined values of X, so Y
must now be ordered too.  This is true even though we used neither an
explicit sort nor a mergejoin on Y.  (Note: hash joins cannot be counted
on to preserve the order of their outer relation, because the executor
might decide to "batch" the join, so we always set pathkeys to NIL for
a hashjoin path.)

An outer join doesn't preserve the ordering of its nullable input
relation(s), because it might insert nulls at random points in the
ordering.  We don't need to think about this explicitly in the PathKey
representation, because a PathKey representing a post-join variable
will contain varnullingrel bits, making it not equal to a PathKey
representing the pre-join value.

In general, we can justify using EquivalenceClasses as the basis for
pathkeys because, whenever we scan a relation containing multiple
EquivalenceClass members or join two relations each containing
EquivalenceClass members, we apply restriction or join clauses derived from
the EquivalenceClass.  This guarantees that any two values listed in the
EquivalenceClass are in fact equal in all tuples emitted by the scan or
join, and therefore that if the tuples are sorted by one of the values,
they can be considered sorted by any other as well.  It does not matter
whether the test clause is used as a mergeclause, or merely enforced
after-the-fact as a qpqual filter.

Note that there is no particular difficulty in labeling a path's sort
order with a PathKey referencing an EquivalenceClass that contains
variables not yet joined into the path's output.  We can simply ignore
such entries as not being relevant (yet).  This makes it possible to
use the same EquivalenceClasses throughout the join planning process.
In fact, by being careful not to generate multiple identical PathKey
objects, we can reduce comparison of EquivalenceClasses and PathKeys
to simple pointer comparison, which is a huge savings because add_path
has to make a large number of PathKey comparisons in deciding whether
competing Paths are equivalently sorted.

Pathkeys are also useful to represent an ordering that we wish to achieve,
since they are easily compared to the pathkeys of a potential candidate
path.  So, SortGroupClause lists are turned into pathkeys lists for use
inside the optimizer.

An additional refinement we can make is to insist that canonical pathkey
lists (sort orderings) do not mention the same EquivalenceClass more than
once.  For example, in all these cases the second sort column is redundant,
because it cannot distinguish values that are the same according to the
first sort column:
	SELECT ... ORDER BY x, x
	SELECT ... ORDER BY x, x DESC
	SELECT ... WHERE x = y ORDER BY x, y
Although a user probably wouldn't write "ORDER BY x,x" directly, such
redundancies are more probable once equivalence classes have been
considered.  Also, the system may generate redundant pathkey lists when
computing the sort ordering needed for a mergejoin.  By eliminating the
redundancy, we save time and improve planning, since the planner will more
easily recognize equivalent orderings as being equivalent.

Another interesting property is that if the underlying EquivalenceClass
contains a constant, then the pathkey is completely redundant and need not
be sorted by at all!  Every interesting row must contain the same value,
so there's no need to sort.  This might seem pointless because users
are unlikely to write "... WHERE x = 42 ORDER BY x", but it allows us to
recognize when particular index columns are irrelevant to the sort order:
if we have "... WHERE x = 42 ORDER BY y", scanning an index on (x,y)
produces correctly ordered data without a sort step.  We used to have very
ugly ad-hoc code to recognize that in limited contexts, but discarding
constant ECs from pathkeys makes it happen cleanly and automatically.


Order of processing for EquivalenceClasses and PathKeys
-------------------------------------------------------

As alluded to above, there is a specific sequence of phases in the
processing of EquivalenceClasses and PathKeys during planning.  During the
initial scanning of the query's quals (deconstruct_jointree followed by
reconsider_outer_join_clauses), we construct EquivalenceClasses based on
mergejoinable clauses found in the quals.  At the end of this process,
we know all we can know about equivalence of different variables, so
subsequently there will be no further merging of EquivalenceClasses.
At that point it is possible to consider the EquivalenceClasses as
"canonical" and build canonical PathKeys that reference them.  At this
time we construct PathKeys for the query's ORDER BY and related clauses.
(Any ordering expressions that do not appear elsewhere will result in
the creation of new EquivalenceClasses, but this cannot result in merging
existing classes, so canonical-ness is not lost.)

Because all the EquivalenceClasses are known before we begin path
generation, we can use them as a guide to which indexes are of interest:
if an index's column is not mentioned in any EquivalenceClass then that
index's sort order cannot possibly be helpful for the query.  This allows
short-circuiting of much of the processing of create_index_paths() for
irrelevant indexes.

There are some cases where planner.c constructs additional
EquivalenceClasses and PathKeys after query_planner has completed.
In these cases, the extra ECs/PKs are needed to represent sort orders
that were not considered during query_planner.  Such situations should be
minimized since it is impossible for query_planner to return a plan
producing such a sort order, meaning an explicit sort will always be needed.
Currently this happens only for queries involving multiple window functions
with different orderings, for which extra sorts are needed anyway.


Parameterized Paths
-------------------

The naive way to join two relations using a clause like WHERE A.X = B.Y
is to generate a nestloop plan like this:

	NestLoop
		Filter: A.X = B.Y
		-> Seq Scan on A
		-> Seq Scan on B

We can make this better by using a merge or hash join, but it still
requires scanning all of both input relations.  If A is very small and B is
very large, but there is an index on B.Y, it can be enormously better to do
something like this:

	NestLoop
		-> Seq Scan on A
		-> Index Scan using B_Y_IDX on B
			Index Condition: B.Y = A.X

Here, we are expecting that for each row scanned from A, the nestloop
plan node will pass down the current value of A.X into the scan of B.
That allows the indexscan to treat A.X as a constant for any one
invocation, and thereby use it as an index key.  This is the only plan type
that can avoid fetching all of B, and for small numbers of rows coming from
A, that will dominate every other consideration.  (As A gets larger, this
gets less attractive, and eventually a merge or hash join will win instead.
So we have to cost out all the alternatives to decide what to do.)

It can be useful for the parameter value to be passed down through
intermediate layers of joins, for example:

	NestLoop
		-> Seq Scan on A
		Hash Join
			Join Condition: B.Y = C.W
			-> Seq Scan on B
			-> Index Scan using C_Z_IDX on C
				Index Condition: C.Z = A.X

If all joins are plain inner joins then this is usually unnecessary,
because it's possible to reorder the joins so that a parameter is used
immediately below the nestloop node that provides it.  But in the
presence of outer joins, such join reordering may not be possible.

Also, the bottom-level scan might require parameters from more than one
other relation.  In principle we could join the other relations first
so that all the parameters are supplied from a single nestloop level.
But if those other relations have no join clause in common (which is
common in star-schema queries for instance), the planner won't consider
joining them directly to each other.  In such a case we need to be able
to create a plan like

NestLoop -> Seq Scan on SmallTable1 A NestLoop -> Seq Scan on SmallTable2 B -> Index Scan using XYIndex on LargeTable C Index Condition: C.X = A.AID and C.Y = B.BID

したがって、プランをこのように見せるような結合順序の制約がない場合でも、結合を介して A.AID を渡すことをいとわないはずです。

バージョン 9.2 より前では、Postgres はこのような種類のネストループクエリの計画と実行にアドホックな手法を使用しており、それらの手法では複数の結合レベルにわたってパラメータを下方に渡すことを処理できませんでした。

このようなクエリを計画するために、現在では「パラメータ化されたパス（parameterized path）」という概念を使用しています。これは、パスによってスキャンされないリレーションへの結合句を利用するパスです。上の 2 つ目の例では、次のような処理を行う可能性を表すパスを構築します。

-> Index Scan using C_Z_IDX on C Index Condition: C.Z = A.X

このパスは、リレーション A によってパラメータ化されているものとしてマークされます（これは C の可能なアクセスの1つに過ぎず、通常のパラメータ化されていないシーケンシャルスキャンや、おそらくその他の可能性も依然として存在することに注意してください）。パラメータ化マーカーは、パスを B に結合することを妨げないため、結合リレーション {B C} に対して生成されるパスの 1 つは以下を表すことになります。

Hash Join Join Condition: B.Y = C.W -> Seq Scan on B -> Index Scan using C_Z_IDX on C Index Condition: C.Z = A.X

このパスは依然として A によってパラメータ化されているものとしてマークされます。{B C} を A と結合して完全な結合ツリーを形成しようとする際、このようなパスはネストループ結合の内側としてのみ使用でき、他の可能な結合タイプでは無視されます。そのため、上記のクエリプランを表す結合パスが形成され、パラメータ化されていないスキャンから構築されたパスと通常の方法で競合することになります。

特定のリレーションに対する通常のパスはすべて同じ行のセットを生成しますが（すべて同じ制限句のセットを適用する必要があるため）、パラメータ化されたパスは、処理すべき追加の句を持っているため、パラメータ化されていないパスよりも通常は少ない行数を生成します。これは、生成される行数を追加のメリットの指標として考慮しなければならないことを意味します。別のパスよりもコストがかかるものの、生成する行数が少ないパスは、中間結合レベルでより少ない行数によって作業量を節約できる可能性があるため、保持されなければなりません。（パラメータのソースに直ちに結合される場合は、何も節約されません。）

コスト見積もりの​​ルールを比較的シンプルに保つため、同じパラメータ化を持つ特定のリレーションのすべてのパス（つまり、パラメータを提供する外部リレーションのセットが同じもの）は、同じ行数の見積もりを持たなければならないという実装上の制約を設けています。これは、そのような各パスが、指定された外部リレーションで使用可能な*すべての*結合句を適用することを主張することで正当化されます。例えば、異なるパスでインデックス句として使用する異なる結合句を選択する場合がありますが、返される行数のセットが一定に保つように、同じ外部リレーションから利用可能な他のすべての結合句をフィルター条件として適用する必要があります。この制約は、完成したプランの品質を低下させることはありません。これは、移動可能な結合句を常に可能な限り低い評価レベルにプッシュダウンすべきであるということを意味しており、いずれにせよそれは良いことです。この制約は、特に add_path_precheck における結合パスの事前フィルタリングをサポートする上で役立ちます。このルールがないと、行数の見積もりを計算する前にパラメータ化されたパスを拒否することが決してできなくなり、事前フィルタリングメカニズムの価値が大幅に低下することになります。

計画時間を制限するため、不当に多数のパラメータ化されたパスが生成されるのを避けなければなりません。これを行うには、インデックススキャンに対してのみパラメータ化されたリレーションスキャンパスを生成し、さらに適切な結合句が利用可能なインデックスに対してのみ生成するようにします。また、考慮されるパラメータ化されたパスの数を制限しようとする結合計画のヒューリスティクスもあります。

特に、パラメータ化された結合ステップ（下位の結合の入力にパラメータを提供するネストループの下位で発生するもの）に対して、マージ結合よりもハッシュ結合を優先するという意図的なポリシー上の決定がなされています。マージ結合を完全に無視するわけではありませんが、joinpath.c は、パラメータ化された入力を持つ潜在的なマージ結合の空間を完全に探索するわけではありません。また、add_path はパラメータ化されたパスにパスキーがないものとして扱うため、コストと行数のみで競合し、特別なソート順序を生成するための優先権は得られません。これにより、明示的なソートステップなしでマージを実行するのに役立つ可能性があったパスを破棄する可能性があるため、マージ結合に対する追加のバイアスが生じます。パラメータ化されたパスは最終的にネストループの内側で使用される必要があり、そのソート順序は重要ではないため、これらの選択はクエリの最終的な出力順序に対する要件には影響を与えず、下位レベルでのマージ結合の使用を困難にするだけです。計画作業における節約はそれを正当化します。

同様に、パラメータ化されたパスは、低いスタートアップコストを持つことに対して add_path で通常は優先権を与えられません。ネストループの内側にある場合、それはほとんど価値がないため、そのためだけに余分なパスを保持する価値はないように思われます。例外として、SEMI または ANTI 結合の RHS リレーションのパラメータ化されたパスの場合があります。これらのケースでは、最初のマッチ後に内部スキャンを停止できるため、気にするべきなのはトータルコストではなく主にスタートアップコストです。

LATERAL サブクエリ ------------------

9.3 以降では、FROM 内のサブクエリ（および FROM 内の関数）からの SQL 標準の LATERAL 参照をサポートしています。オプティマイザは、lateral 参照を含む RTE に対してパラメータ化されたパスを生成することによってこれらを実装します。そのような場合、そのリレーションの*すべての*パスは、少なくともその lateral 参照で使用されるリレーションのセットによってパラメータ化されます（そして順番に、そのようなサブクエリを含む結合リレーションは、パラメータ化されていないパスを全く持たない可能性があります）。ただし、パラメータ化されたパスに対して上記で行われた他のすべてのコメントは引き続き適用されます。特に、そのような各パスは、それにプッシュダウンできる結合句を引き続き強制することが期待されるため、同じパラメータ化を持つすべてのパスは同じ行数を持ちます。

また、オプティマイザによる LATERAL サブクエリの平坦化（親クエリへのプルアップ）も許可されていますが、これは、そのクエリ条件のレベル以下にある最も低いアウター結合の外側にあるリレーションを参照するような lateral 参照を JOIN/ON 条件内に持ち込まない場合に限られます。そのような条件のセマンティクスは不明確になります。この制約があっても、LATERAL サブクエリのプルアップにより、構文上のスコープ外のリレーションに対する lateral 参照を含む PlaceHolderVar が作成される可能性があることに注意してください。私たちは引き続きそのような PHV をその構文上の場所またはそれ以下で評価しますが、プランノードの条件またはターゲットリストにそのような PHV が存在する場合、そのノードは、lateral 参照を提供するリレーションに対してネストループ結合の内側に現れる必要があります。（おそらく、その機能が動作するようになったので、プルアップの制約を緩和できるでしょうか？）

条件句に対するセキュリティレベルの制約 ------------------------------------------

行レベルセキュリティとセキュリティバリアビューを効率的にサポートするため、条件句（RestrictInfo ノード）に "security_level" フィールドのマークを付けます。基本的な概念は、より低い security_level を持つ条件が、より高い security_level を持つ条件よりも先に評価されなければならないということです。これにより、機密データを露出させる可能性のある「漏洩しやすい（leaky）」条件が、セキュリティ機密行をフィルタリングすることになっているセキュリティバリア条件がチェックされるまで評価されないことが保証されます。しかし、多くの条件式は「漏洩防止（leakproof）」、つまり、それらが使用する関数がデータを露出させない信頼できるものです。不必要に非効率なプランを避けるため、たとえ別の条件よりも構文上の security_level が高くても、漏洩防止条件はセキュリティレベルの考慮によって遅延させられません。

RLS またはセキュリティバリアビューを使用しないクエリでは、すべての条件の security_level が 0 になるため、これらの制約はどれも機能しません。条件式の leakproof 性をチェックする必要さえないのです。

セキュリティバリア条件がある場合、それらの security_level は 0 になり（バリアのレイヤーが複数ある場合はさらに高くなる可能性があります）、クエリテキストからの通常の条件には、バリア条件に使用された最も高いレベルよりも 1 つ高い security_level が割り当てられます。

EquivalenceClass 処理によって新しい条件句が生成されるとき、それらに security_level を割り当てる必要があります。これが見た目以上に厄介です。最初に思い浮かぶ直感としては、EquivalenceClass のソース条件の中から見つかった最大のレベルを使用するのが安全であるということですが、それは全く安全ではありません。なぜなら、セキュリティバリア条件の不要な遅延を許容してしまうからです。バリア条件「t.x = t.y」に加えてクエリ条件「t.x = constant」があり、さらにバリア条件がチェックされる前に評価してはならない別のクエリ条件「leaky_function(t.z)」があると仮定します。 EC条件を「t.x = constant AND t.y = constant」に置き換えることになる EC {t.x, t.y, constant} が存在することになります（後者の条件により、元の条件からは決して発見できなかった t.y のインデックスの使用が可能になるため、この動作を諦めることも望みません）。これらの生成された条件にクエリ条件と同じ security_level が割り当てられた場合、leaky_function 条件が最初に評価され、leaky_function がバリア条件を通過しない可能性のある行のデータを見ることが可能になります。

代わりに、ECでのセキュリティレベルの処理は次のように機能します。

  • 条件が漏洩防止（leakproof）であるか security_level が 0 でない限り、そもそも EC のソース句として受け入れられません。
  • EC から派生した条件には、EC のソース句の中で見つかった最小の（最大ではない）security_level が割り当てられます。
  • EC のソース句で見つかった最大の security_level が 0 より大きい場合、派生条件に選択される等価演算子は漏洩防止でなければなりません。そのような演算子が見つからない場合、EC は「破損（broken）」として扱われ、追加の派生条件なしでソース句を出力することにフォールバックします。

これらのルールを合わせることで、信頼できない条件句（security_level が 0 より大きいもの）が EC に漏洩しやすい派生句を生成させないことが保証されます。これにより、派生句に対して最大ではなく最小の security_level を使用することが安全になります。これらのルールは、派生句を全く生成できないことにより、貧弱なプランをもたらす可能性がありますが、実際にはほとんどの btree 等価演算子が漏洩防止であるため、そのリスクはわずかです。また、レベルゼロの条件に対して例外を設けることにより、バリア条件が存在しない場合にプランの品質低下が発生しないことが保証されます。

すべての条件にセキュリティレベルが割り当てられたら、バリア条件の順序付け制約の強制は 2 つのルールに帰着します。

  • テーブルスキャンプランノードは、漏洩防止であるか、または同じプランノードで実行される予定の他のどの条件よりも高くない security_level を持たない限り、条件を早期実行のために選択してはなりません（たとえば、インデックススキャンのインデックス修飾子としてそれらを使用することなど）。（条件を早期実行のために選択しても問題ないかどうかをチェックするには、ユーティリティ関数 restriction_is_securely_promotable() を使用してください。）
  • 条件のリストの通常の実行は、同じセキュリティルールを満たす順序、すなわち、漏洩防止でない限り、より高い security_level が後で評価されなければならないという順序でそれらを実行しなければなりません。（これは createplan.c の order_qual_clauses() によって 1 つの場所で処理されます。）

order_qual_clauses() は、漏洩防止条件に対して正確に何をすべきかを決定するためにヒューリスティクスを使用します。通常、明確な理由なしに条件の順序を再並べ替えしないようにソートが安定していることに注意しながら、security_level、次にコスト順に条件をソートします。しかし、これにより、より高い security_level を持つ安価な条件の前に、非常に高価な条件が実行される結果になる可能性があります。 安価な条件が漏洩しやすい場合は選択の余地がありませんが、それが漏洩防止であれば、最初に置くことができます。漏洩防止条件は security_level が 0 であるかのようにソートすることを選択しますが、そのコストが 10 * cpu_operator_cost よりも低い場合に限られます。この制約は、高価な条件を漏洩防止であるという理由だけで最初に実行してしまうという逆の問題を緩和します。

結合条件のセキュリティレベルが混在する場合に、結合条件の安全な処理をサポートするためには追加のルールが必要になります。例えば、情報漏洩の恐れがあるより高いセキュリティレベルの条件が、より低いセキュリティレベルの他の条件よりも低い結合レベルで評価されるのを防ぐ必要があります。現在、セキュリティ優先の条件はRLSポリシーやセキュリティバリアビューからの単一テーブルの制限条件に限られ、セキュリティバリアビューのサブクエリは親クエリに平坦化されないため、これを考慮する必要はありません。したがって、セキュリティ優先の条件の強制はテーブルスキャンレベルでしか行われません。結合条件間でのセキュリティレベルの安全な処理に関する追加ルールがあれば、セキュリティバリアビューを親クエリに平坦化できるようになり、条件評価の必要な順序を維持しつつ、プランニングの柔軟性を高めることができるはずです。しかし、それは後の話になります。

スキャン/結合プランニングの後 -----------------------

ここまでは、スキャン/結合プランニング、つまりSQLクエリのFROM句とWHERE句の実装についてのみ議論してきました。しかし、プランナーはGROUP BY、集約、その他のクエリの上位機能に対処する方法も決定しなければなりません。多くの場合、これらのステップを実行する方法は複数あり、最適化の選択肢が存在します。これらのステップは、スキャン/結合プランニングと同様に、ステップを実行するさまざまな方法を表すPathを構築し、最もコストの低いPathを選択することによって処理されます。

すべてのPathには「親」としてのRelOptInfoが必要なため、これらの上位処理ステップの出力を表すRelOptInfoを作成します。これらのRelOptInfoはほとんどがダミーですが、そのpathlistリストには各ステップで有用とみなされたすべてのPathが保持されます。現在、上位プランニング中にこれらタイプの追加のRelOptInfoを作成する場合があります。

UPPERREL_SETOP UNION/INTERSECT/EXCEPTの結果（存在する場合） UPPERREL_PARTIAL_GROUP_AGG 部分的なグループ化/集約の結果（存在する場合） UPPERREL_GROUP_AGG グループ化/集約の結果（存在する場合） UPPERREL_WINDOW ウィンドウ関数の結果（存在する場合） UPPERREL_PARTIAL_DISTINCT 部分的な「SELECT DISTINCT」の結果（存在する場合） UPPERREL_DISTINCT 「SELECT DISTINCT」の結果（存在する場合） UPPERREL_ORDERED ORDER BYの結果（存在する場合） UPPERREL_FINAL 残りのトップレベルのアクションの結果（存在する場合）

UPPERREL_FINALは、最終的な処理ステップ（現在はLockRows (SELECT FOR UPDATE)、LIMIT/OFFSET、およびModifyTable）を表すために使用されます。これらのステップが実行される順序には柔軟性がないため、このステージをより細かく小分けする必要はありません。

これらの「上位リレーション」は、上記のUPPERREL列挙値とrelidsセットによって識別されます。これにより、同じ種類の上位リレーションを複数存在させることができます。同じ種類の上位リレーションを複数必要としない場合は、relidsにNULLを使用します。実際、現在ではrelidsセットは常にNULLであるため痕跡的なものとなっていますが、将来的には変更されることが想定されています。例えば、集合演算のプランニングにおいては、互いに競合するPathの特定のグループに結合されたリーフSELECTのどのサブセットをrelidsが表しているかを示すために、relidsが必要になる場合があります。

subquery_planner()の結果は、常にNULLのrelidsを持つUPPERREL_FINALリレーションに格納されたPathのセットとして返されます。他の種類の上位リレーションは、特定のクエリで必要な場合にのみ作成されます。

並列クエリと部分パス --------------------------------

並列クエリとは、クエリ全体またはクエリの一部によって実行される必要がある作業を分割し、その作業の一部を1つ以上のワーカープロセス（並列ワーカーと呼ばれる）によって実行できるようにするものです。並列ワーカーは動的バックグラウンドワーカーのサブタイプです。詳細な説明については src/backend/access/transam/README.parallel を参照してください。並列クエリに関する学術文献によると、並列実行戦略は本質的に2つのカテゴリに分けることができます。クエリの実行が複数のステージに分割され、各ステージが別々のプロセスによって処理されるパイプライン並列性と、データが複数のプロセス間で分割され、各プロセスがそのサブセットを処理するパーティション並列性です。しかし、文献によれば、パイプライン並列性による利得は、パイプラインのストールを回避することが難しいため、非常に限定的なことが多いとされています。そのため、現時点ではこの技術を使用するクエリプランの生成は試みていません。

代わりに、ベーステーブルがパーティション分割されていることを必要としないパーティション並列性に焦点を当てています。これに必要なのは、(1)リレーションに関与する少なくとも1つのベーステーブルからのデータを複数のプロセス間で分割する方法が存在すること、(2)各プロセスが独自のデータ部分を処理できるようにすること、そして(3)結果を収集することの3点のみです。要件(2)および(3)は、任意の数のワーカープロセスを起動し、そのすべてにおいて、また子プロセスがリーダーを忙しく保つのに十分なデータを生成していない場合はおそらくリーダーにおいても、単一の子プランを実行するエグゼキューターノードGather（またはGatherMerge）によって満たされます。要件(1)はテーブルスキャンノードによって処理されます。parallel_aware = trueを指定して呼び出された場合、このノードは実質的にブロック単位でテーブルをパーティション分割し、そのスキャンノードが実行される各ワーカーでリレーションからのタプルのサブセットを返します。

非並列アクセス方法で行うのと同様に、並列プランで使用できるアクセス戦略を表すPathを構築します。これらは本質的に非並列プランで使用可能な戦略と同じですが、重要な違いがあります。Gatherノードの下で実行されるパスは、すべての結果ではなく、各ワーカーにおけるクエリ結果のサブセットのみを返します。実際に実行できるパスを形成するには、Gatherノードの（かなり大きな）コストを考慮に入れる必要があります。このような理由などから、Gatherノードの下で実行することを意図したパス（各ワーカーで結果のサブセットのみを返すため「部分（partial）」パスと呼ぶ）は、通常のパスとは別々に保持する必要があります（RelOptInfoのpartial_pathlistと add_partial_path関数を参照してください）。

並列クエリを効果的にするための鍵の1つは、クエリのできるだけ多くを並列で実行することです。したがって、Gatherステージをプランのトップにできる限り近づくまで延期することが一般的に望ましいと予想されます。より多くの作業をGatherの下に押し下げることができるケースの範囲を広げ、（それらのコストを正確に算定することは）当分の間私たちを忙しさと共にあり続けるでしょう。

パーティション単位の結合（Partitionwise joins） -----------------------------------

同様にパーティション分割された2つのテーブル間の結合は、結合するテーブルのパーティションキー間に等価結合条件が存在する場合、それらの一致するパーティション間の結合に分解できます。パーティションキー間の等価結合は、あるパーティション分割されたテーブル内の特定の行に対するすべての結合相手が、もう一方のパーティション分割されたテーブルの対応するパーティション内になければならないことを意味します。このため、パーティション分割されたテーブル間の結合を、一致するパーティション間の結合に分解することができます。結果として得られる結合は、結合するリレーションと同じ方法でパーティション分割されるため、パーティションキー間に等価結合条件を持つ、同様にパーティション分割されたテーブル間のN方向の結合を、その一致するパーティション間のN方向の結合に分解することができます。パーティション分割されたテーブル間の結合をそのパーティション間の結合に分解するこの手法は、パーティション単位の結合（partitionwise join）と呼ばれます。「パーティション分割されたリレーション」という用語は、パーティション分割されたテーブル、または互換性のあるパーティション分割されたテーブル間の結合のどちらに対しても使用します。

結合するリレーションのパーティション境界が正確に同じでない場合でも、高度なパーティションマッチングアルゴリズムを使用することで、パーティション単位の結合を適用できます。このアルゴリズムは、両方の結合リレーションについて、一方の結合リレーションのすべてのパーティションが、もう一方の結合リレーションの最大で1つのパーティションにのみ一致するかどうかをチェックします。そのような場合、結合リレーション間の結合を、一致するパーティション間の結合に分解できます。その後、結合リレーションをパーティション分割されたものとみなすことができます。このアルゴリズムは、結合を計算するためのパーティション単位の結合を可能にするために、一致するパーティションのペアと、結合リレーションのパーティション境界を生成します。このアルゴリズムは partition_bounds_merge() に実装されています。このようにパーティション分割されたとみなされるN方向の結合リレーションにおいて、すべての結合リレーションのペアがパーティション単位の結合を使用できるわけではありません。例えば、次のような場合です。

(A leftjoin B on (Pab)) innerjoin C on (Pac)

ここで、A、B、Cはパーティション分割されたテーブルであり、AはBおよびCと比較して余分なパーティションを持っています。結合 {A B} についてパーティション単位の結合を考慮する場合、Aの余分なパーティションにはヌル許容側に一致するパーティションがありません。これは、現在のパーティション単位の結合の実装では処理できないケースです。したがって、{A B} はパーティション分割されているとはみなされず、3方向の結合のために考慮される {A B} とCのペアはパーティション単位の結合を使用できません。一方、{A C} とBのペアはパーティション単位の結合を使用できます。なぜなら、{A C} は余分なパーティションを排除することでパーティション分割されているとみなされるためです（外部結合の順序変更に関する同一性1を参照してください）。N方向の結合でパーティション単位の結合を使用できるかどうかは、両方ともパーティション分割されておりパーティション単位の結合を使用できる、最初に現れた結合リレーションのペアに基づいて決定されます。

パーティション分割されたリレーションのパーティションプロパティは、その RelOptInfo に格納されます。パーティションキーのデータ型に関する情報は PartitionSchemeData 構造体に格納されます。プランナーは正準パーティションスキーム（異なる PartitionSchemeData オブジェクト）のリストを維持し、同じパーティションスキームを持つ任意の2つのパーティション分割されたリレーションの RelOptInfo が同じ PartitionSchemeData オブジェクトを指すようにします。これにより、PartitionSchemeData オブジェクトによって消費されるメモリが削減され、結合リレーションのパーティションスキームを簡単に比較できるようになります。

パーティション単位の集約/グループ化（Partitionwise aggregates/grouping） -------------------------------------------------------------------

GROUP BY句がすべてのパーティションキーを含んでいる場合、特定のグループに属するすべての行は単一のパーティションから来なければなりません。したがって、集約は各パーティションに対して完全に個別に実行できます。そうでない場合は、各パーティションに対して部分集約を計算し、個々のパーティションからの結果をアペンドした後に最終処理を行うことができます。パーティション分割されたリレーションに対する集約またはグループ化を、そのパーティションに対する集約またはグループ化に分解するこの手法は、パーティション単位の集約（partitionwise aggregation）と呼ばれます。特にパーティションキーがGROUP BY句と一致する場合、これは通常の方法よりも大幅に高速になる可能性があります。

積極的集約（Eager aggregation） ---------------------------

積極的集約は、集約を結合の向こう側に部分的にプッシュし、すべてのリレーションが結合された後にそれをファイナライズするクエリ最適化手法です。積極的集約により、結合への入力行数を削減できるため、結果としてより優れた全体的なプランが得られる可能性があります。

この変換が正しいことを証明するために、まず内部結合のみが関与するケースを考えます。この場合、FROM句のテーブルを2つのグループに分割します。少なくとも1つの集約列を含むグループと、集約列を全く含まないグループです。各グループは、そのグループ内のテーブルの直積によって形成される単一のリレーションとして扱うことができます。したがって、一般性を失うことなく、FROM句にはちょうど2つのリレーション、R1とR2が含まれていると仮定できます。ここで、R1はすべての集約列を含むリレーションを表し、R2は集約列を一切含まないリレーションを表します。

クエリが次の形式であるとします。

SELECT G, AGG(A) FROM R1 JOIN R2 ON J GROUP BY G;

ここで、GはR1および/またはR2の列を含む可能性のあるグループ化キーのセットです。AGG(A)はR1の列Aに対する集約関数です。JはR1とR2の間の結合条件です。

積極的集約の変換は次のようになります。

GROUP BY G, AGG(A) on (R1 JOIN R2 ON J) = GROUP BY G, AGG(agg_A) on ((GROUP BY G1, AGG(A) AS agg_A on R1) JOIN R2 ON J)

この等価性は、以下の条件下で成り立ちます。

1) AGG は分解可能であり、つまり、部分集約とそれに続く最終集約の 2 つの段階で計算できること。 2) R1 の事前集約で使用される集合 G1 には以下が含まれる:

  • グルーピングキー G の一部である R1 のすべての列、および
  • 結合条件 J に現れる R1 のすべての列。

    • 3) G1 内の任意の列に対するグルーピング演算子は、結合条件 J 内のその列で使用される演算子と互換性がある必要がある。

G1 には、グルーピングキー G または結合条件 J のいずれかに現れる R1 のすべての列が含まれているため、互換性のある演算子が使用されていると仮定すると、各部分グループ内のすべての行は、グルーピングキーと R1 由来の結合関連列の両方について同一の値を持つ。 結果として、部分グループ内の行は、集約への貢献度や結合における挙動の点において区別がつかない。 これにより、同じ部分グループ内のすべての行が同じ「運命」を共有することが保証される: それらはすべて一致するか、あるいは R2 内の特定の行との一致に失敗するか的確に一致する。 集約関数 AGG は分解可能であるため、結合後に部分結果を集約することは、完全結合後に集約するのと同じ最終結果をもたらし、それによってクエリのセマンティクスが保持される。 証明終了。

外部結合が存在する場合、結合順序の制約と外部結合における NULL 拡張のセマンティクスにより、状況はより複雑になる。 結合順序の制約のために、少なくとも 1 つの集約列を含むリレーションを単一のリレーションとして扱うことができない場合、部分集約パスは生成されず、したがってこの変換は適用できない。 それ以外の場合は、すべての集約列を含むリレーションを R1 とし、残りのリレーションを R2, R3, ... とする。 内部結合の場合から、前述の条件下で以下の等価性が成り立つ:

GROUP BY G, AGG(A) on (R1 JOIN R2 JOIN R3 ...) = GROUP BY G, AGG(agg_A) on ((GROUP BY G1, AGG(A) AS agg_A on R1) JOIN R2 JOIN R3 ...)

外部結合が関与する場合に正しさを維持するには、追加の条件が必要となる:

4) R1 は、いかなる外部結合の NULL 許容側にあってはならない。

この条件により、R1 に対する部分集約が、外部結合によって導入される NULL 拡張行を抑制しないことが保証される。 R1 が外部結合の NULL 許容側にある場合、外部結合によって生成された NULL 拡張行は部分集約を実行する際には利用できなくなるが、非先行集約 (non-eager-aggregation) プランではこれらの行がトップレベルの集約で利用可能である。 この場合に部分集約をプッシュダウンすると、行が予期したのとは異なる方法でグルーピングされたり、集約関数から不正確な値が生成されたりする可能性がある。

セミ結合とアンチ結合にも同様の制限が課される。 そのような結合はその内部行を結合出力に残さないため、内部側で計算された部分集約は結合を生き延びることができず、最終集約によって結合することができない。 したがって、セミ結合やアンチ結合の内部側に部分集約をプッシュダウンすることはしない。 (外部結合から縮小されたアンチ結合はその内部側を NULL 拡張するため、その内部リレーションは上記の外部結合条件によってすでに除外されている。ここで具体的に対象としているのは、EXISTS、IN、NOT EXISTS、または NOT IN サブリンクから形成されるような、その内部側を NULL 拡張しないセミ結合やアンチ結合である。)

結合ツリーの構築中、各ベースリレーションまたは結合リレーションを評価して、先行集約 (eager aggregation) を適用できるかどうかを判断する。 可能であれば、「グループ化されたリレーション (grouped relation)」と呼ばれる個別の RelOptInfo を作成し、非グループ化パスの上にソート済みおよびハッシュ済みの部分集約パスを追加してグループ化パスを生成する。 プランニング時間を制限するため、このステップでは最も安価な、または適切にソートされた非グループ化パスのみを考慮する。

グループ化パスを生成するもう一つの方法は、グループ化されたリレーションとグループ化されていないリレーションを結合することである。 2 つのグループ化されたリレーション同士の結合は現在サポートされていない。

プランニング時間をさらに制限するため、現在では、行数を大幅に削減できる結合ツリー内の最も低い実行可能なレベルにのみ部分集約をプッシュダウンする戦略を採用している。 この戦略はまた、同じグループ化されたリレーションに対するすべてのグループ化パスが同じ行のセットを生成することを保証するのにも役立ち、これはプランナーの基本仮定をサポートする上で重要である。

最上位の結合リレーションに対してグループ化されたリレーションを生成した場合は、最後にそのパスを確定させる必要がある。 最終的なパスは、通常のプランニングから構築されたパスと通常の方法で競合する。
