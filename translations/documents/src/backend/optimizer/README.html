Optimizer

これらのディレクトリは、パーサーから返されたQuery構造体を受け取り、エグゼキューターが使用するプランを生成します。/planディレクトリは実際の出力プランを生成し、/pathコードはテーブルを結合するためのすべての可能な方法を生成し、/prepは特殊なケースに対するさまざまな前処理ステップを処理します。/utilはユーティリティ関係です。/geqoは個別の「遺伝的最適化」プランナーです。これは、可能な結合ツリーをすべて網羅的に検討するのではなく、結合ツリー空間を半ランダムに検索します（ただし、/geqoによって検討される各結合は、パスを作成するために/pathに渡されるため、GEQOモードでも、特定の結合ペアごとに可能なすべての実装パスが検討されます）。

Paths and Join Pairs

計画/最適化のプロセス中に、クエリを実行するさまざまな方法を表す「Path」ツリーを構築します。目的のリレーションを生成する最もコストの低いPathを選択し、エグゼキューターに渡すPlanに変換します（PathツリーとPlanツリーの間にはほぼ1対1の対応関係がありますが、Pathノードには計画時には不要な情報が省略され、エグゼキューターには不要だが計画には必要な情報が含まれています）。

オプティマイザーは、クエリで使用される各ベースリレーションに対してRelOptInfo構造体を構築します。ベースリレーションは、プリミティブテーブル、またはプランナーの別の再帰的呼び出しによって計画されるサブクエリのサブセレクトのいずれかです。RelOptInfoは、計画中に検討される各結合リレーションに対しても構築されます。結合リレーションは、単にベースリレーションの組み合わせです。指定されたベースリレーションのセットに対して結合RelOptInfoは1つだけ存在します。たとえば、結合 {A B C} は、最初にAとBを結合してからCを追加した場合でも、最初にBとCを結合してからAを追加した場合でも、同じRelOptInfoで表されます。結合リレーションを構築するこれらの異なる手段は、Pathとして表されます。各RelOptInfoについて、そのリレーションのスキャンまたは結合を実装する妥当な方法を表すPathのリストを構築します。リレーションのすべての妥当なPathを検討したら、プランナーのコスト見積もりに従って最もコストの低いものを選択します。最終的なプランは、クエリのすべてのベースリレーションを含むRelOptInfoの最もコストの低いPathから導出されます。

プリミティブテーブルリレーションの可能なPathには、古き良きシーケンシャルスキャンに加え、テーブルに存在する任意のインデックスに対するインデックススキャン、さらに1つ以上のインデックスを使用したビットマップインデックススキャンが含まれます。関数RTEなどの特殊化されたRTEタイプには、可能なPathが1つしかない場合があります。

結合は常にかつて2つのRelOptInfoを使用して発生します。1つは外側、もう1つは内側です。外側は内側での値のルックアップを駆動します。ネストループでは、内側での値のルックアップは、一致する内側の行をそれぞれ見つけるために、外側のタプルごとに内側のパスを1回スキャンすることによって発生します。マージジョインでは、内側と外側の行が順序付けられ、順序通りにアクセスされるため、結合全体を実行するのに必要なスキャンは1回だけです。内側と外側の両方のパスが同期してスキャンされます（マージジョインでは内側と外側の間に大きな違いはありません...）。ハッシュジョインでは、最初に内側がスキャンされてそのすべての行がハッシュテーブルに登録され、次に外側がスキャンされて行ごとに結合キーがハッシュテーブルでルックアップされます。

結合リレーションのPathは、実際にはツリー構造であり、最上位のPathノードは最後に適用された結合メソッドを表します。これには、2つの入力リレーションに使用されるスキャンまたは結合メソッドを表す左サブパスと右サブパスがあります。

Join Tree Construction

オプティマイザーは、クエリの実行方法を多かれ少なかれ網羅的に検索することにより、最適なクエリプランを生成します。最適なPathツリーは、再帰的なプロセスによって見つかります。

1) クエリ内の各ベースリレーションを取得し、そのRelOptInfo構造体を作成します。シーケンシャルスキャンやインデックススキャンなど、リレーションにアクセスする可能性のある有用な方法をすべて見つけ、それらの方法を表すPathを作成します。特定のリレーションに対して作成されたすべてのPathは、そのRelOptInfo.pathlistに配置されます。（実際には、パスリストに入る前に、明らかに劣る代替手段であるPathは破棄されます。パスリストに行き着くのは、リレーションの潜在的に有用なソート順序とパラメータ化のそれぞれを生成する最も安価な方法です。）また、このリレーションに関係するすべての結合句を含むRelOptInfo.joininfoリストを作成します。たとえば、WHERE句 "tab1.col1 = tab2.col1" は、tab1とtab2の両方のjoininfoリストのエントリを生成します。

クエリ内にベースリレーションが1つしかない場合は、これで完了です。それ以外の場合は、ベースリレーションを単一の結合リレーションに結合する方法を考え出す必要があります。

2) 通常、明示的なJOIN句は、結合するリレーションのリストを持つだけになるように「平坦化」されます。ただし、FULL OUTER JOIN句は決して平坦化されず、join_collapse_limitまたはfrom_collapse_limitの制限によって平坦化プロセスが停止された場合、他の種類のJOINも平坦化されない可能性があります。したがって、任意の順序で結合するリレーションのリストを含む計画問題に帰着します。ここで、個々のアイテムは、その兄弟と結合することを検討する前に結合する必要があるサブリストである可能性があります。これらのサブ問題は、ボトムアップで再帰的に処理します。結合リストの構造は可能な結合順序を制約しますが、各結合での結合実装方法（ネストループ、マージ、ハッシュ）を制約せず、各結合でどのリレーションが外側または内側と見なされるかも指定しません。Pathsを構築する際に、これらすべての可能性を検討します。実行可能な結合方法ごとにPathを生成し、最もコストの低いPathを選択します。

したがって、各計画問題について、ベースリレーションまたはサブ結合リストごとに構築された結合リレーションのいずれかであるリレーションのリストを持つことになります。プランナーが適切とみなす任意の順序で、これらのリレーションを結合できます。標準の（GEQOではない）プランナーは、これを次のように実行します。

使用可能な結合句がある各RelOptInfoを他の各RelOptInfoと結合することを検討し、そのような各ペアの可能な結合方法ごとにPathを生成します。（結合句のないRelOptInfoがある場合、句のないデカルト積結合を生成する以外の選択肢がないため、そのリレーションを使用可能な他の各リレーションと結合することを検討します。ただし、結合句が存在する場合は、使用可能な結合句を使用する結合のみを検討します。なお、外部結合やIN/EXISTS句によって誘発される結合順序の制限もチェックされ、それらの制限によって句のない結合を強制される場合に実行可能な結合順序が見つかるようにします。）

リスト内のリレーションが2つだけの場合は、これで完了です。結合RelOptInfoの最も安いパスを選択するだけです。3つ以上ある場合は、結合RelOptInfo同士を結合して、3つ以上のリストアイテムを表す結合RelOptInfoを作る方法を検討する必要があります。

結合ツリーは「動的計画法」アルゴリズムを使用して構築されます。最初のパス（すでに説明した）では、正確に2つのリストアイテムを表す結合リレーションを作成する方法を検討します。2回目のパスでは、正確に3つのリストアイテムを表す結合リレーションを作る方法を検討し、次のパスでは4つのアイテム、というようになります。最後のパスでは、すべてのリストアイテムを含む最終的な結合リレーションを作る方法を検討します。当然ながら、この最上位レベルの結合リレーションは1つしか存在できませんが、下位レベルでは複数の結合リレーションが存在する可能性があります。各レベルでは、最初のレベルで説明したように、可能であれば使用可能な結合句に従う結合を使用します。

例:

SELECT * FROM tab1, tab2, tab3, tab4 WHERE tab1.col = tab2.col AND tab2.col = tab3.col AND tab3.col = tab4.col

テーブル 1、2、3、4 は次のように結合されます: {1 2},{2 3},{3 4} {1 2 3},{2 3 4} {1 2 3 4}

SELECT * FROM tab1, tab2, tab3, tab4 WHERE tab1.col = tab2.col AND tab1.col = tab3.col AND tab1.col = tab4.col

テーブル 1、2、3、4 は次のように結合されます: {1 2},{1 3},{1 4} {1 2 3},{1 3 4},{1 2 4} {1 2 3 4}

これらの各例において、結合句がないため、他の結合順序の可能性は除外されます。（実際には、EquivalenceClassesを使用することで、より多くの結合順序を許可する追加の結合句を推論できますが、ここでは例の単純さを保つためにそれを無視しています。）

左偏向プラン（上位結合の外側リレーションは結合リレーションですが、内側は常に単一のリストアイテムです）、右偏向プラン（外側リレーションは常に単一のアイテムです）、および木構造プラン（内側と外側の両方がそれ自体で結合になり得ます）を検討します。たとえば、{1 2 3 4}を構築する場合、{1 2 3}と{4}の結合（左偏向）、{4}と{1 2 3}の結合（右偏向）、および{1 2}と{3 4}の結合（木構造）などを検討します。結合ツリー走査コードはこれらの潜在的な結合の組み合わせを1つずつ生成しますが、結合されたベースリレーションの同じセットを生成するすべての方法は同じRelOptInfoを共有するため、同等の結合リレーションを生成する異なる結合の組み合わせから生成されたパスはadd_path()で競合します。

動的計画法のアプローチには、すぐには分からない重要な特性があります。それは、そのリレーションを含むリレーションのパスを構築する前に、特定のリレーションのすべてのパスの構築が完了するということです。これは、高レベルのリレーションがそれを知る必要が生じる前に、各リレーションの「最も安いパス」を確実に対象として特定できることを意味します。また、同じリレーションの別のパスの方が優れていることが判明したときに、高レベルの結合パスにそのパスへの参照がすでに含まれているのではないかと心配することなく、パスを安全に破棄できます。これがないと、パスのメモリ管理ははるかに複雑になります。

最終的な結合リレーションを構築したら、その最も安いパスか、あるいは目的の順序を持つ最も安いパス（それが他の最も安いパスにソートを適用するよりも安い場合）を使用します。

クエリに片側外部結合（LEFTまたはRIGHT結合）、あるいはセミジョインまたはアンチジョインに変換されたINまたはEXISTS WHERE句が含まれている場合、可能な結合順序の一部が不正になる可能性があります。これらは、提案された結合が不正かどうかを確認するために、join_is_legalにそのような「特殊な」結合のサイドリストを参照させることで除外されます。（同じ参照により、有効な結合（つまりJOIN_INNER、JOIN_LEFTなど）に対してどの結合スタイルを適用すべきかを確認できます。）

Valid OUTER JOIN Optimizations

プランナーによる外部結合の並び替えの扱いは、次の同一性に基づいています。

1. (A leftjoin B on (Pab)) innerjoin C on (Pac) = (A innerjoin C on (Pac)) leftjoin B on (Pab)

ここで、PacはAとCなどを参照する述語です（この場合、PacがBを参照できないことは明らかです。そうでない場合、変換は無意味になります）。

2. (A leftjoin B on (Pab)) leftjoin C on (Pac) = (A leftjoin C on (Pac)) leftjoin B on (Pab)

3. (A leftjoin B on (Pab)) leftjoin C on (Pbc) = A leftjoin (B leftjoin C on (Pbc)) on (Pab)

同一性3は、述語Pbcがすべての値がNULLであるBの行に対して失敗する場合にのみ成り立ちます（つまり、PbcはBの少なくとも1つのカラムに対して厳密です）。Pbcが厳密でない場合、最初の形式では、2番目の形式ではそれらのエントリがNULLになる場所で、非NULLのCカラムを持ついくつかの行が生成される可能性があります。

RIGHT JOINは、2つの入力テーブルを入れ替えた後のLEFT JOINと同等であるため、右結合に対しても同じ同一性が機能します。

機能し*ない*ケースの例として、内部結合を外部結合のNULL許容側に移動したり、そこから外に移動したりすることが挙げられます。

A leftjoin (B join C on (Pbc)) on (Pab) != (A leftjoin B on (Pab)) join C on (Pbc)

セミジョインの動作は少し異なります。セミジョインは、別のセミジョイン、左結合、またはアンチジョインの左側の内部または外部に関連付け直すことはできますが、右側に関連付け直すことはできません。同様に、内部結合、左結合、またはアンチジョインは、セミジョインの左側に結びつけて関連付け直すことはできますが、右側に関連付け直すことはできません。

ANTIジョインはLEFTジョインとほぼ同様に動作しますが、Cへのジョインがアンチジョインである場合、恒等式3が成り立たなくなります（Pbcが厳密（strict）である場合や、もう一方のジョインがレフトジョインである場合とアンチジョインである場合の両方において）。したがって、関連する句が厳密であっても、アンチジョインをレフトジョインまたはアンチジョインのRHS（右側）の内外に再配置することはできません。

現在のコードは、FULL JOINの順序変更をまったく試みません。FULL JOINの順序付けは、ジョインツリーを「joinlist」表現に変換する際にFULL JOINノードをコラプス（平坦化）しないことによって強制されます。他のタイプのJOINノードは通常、ジョイン順序の探索に完全に組み込まれるようにコラプスされます。不正なジョイン順序の生成を避けるため、プランナはインナージョイン以外のジョインごとにSpecialJoinInfoノードを作成し、join_is_legalがこのリストをチェックして、提案されたジョインが正当であるかどうかを判断します。

SpecialJoinInfoノードに格納されるのは、外部ジョインを形成するためにジョインの両側で必要となる最小のRelidのセットです。これらは最小値であることに注意してください。OJ（外部ジョイン）の構文上のリレーションに他のリレーションをジョインすることは正当である可能性があるため、明示的な最大値はありません。恒等式1および2に従い、FULL以外のジョインはOJの左側に自由に結合（結合法則を適用）できますが、右側には結合できない場合があります。したがって、join_is_legalによって強制される制限は、提案されたジョインが、RHSの境界内または一部が境界内にあるリレーションを境界外のリレーションとジョインできないということです。ただし、提案されたジョインが恒等式3を使用してSpecialJoinInfoのRHSに結合できるLEFTジョインである場合は除きます。

最小Relidセットの使用にはいくつかの落とし穴があります。例えば、次のようなクエリを考えてみましょう。 A leftjoin (B leftjoin (C innerjoin D) on (Pbcd)) on Pa ここで、PaはB/C/Dをまったく参照していません。この場合、単純な計算では、上のleftjoin ofの最小LHSは{A}、最小RHSは{C,D}になります（インナージョインはleftjoinのRHSの外に結合できないことが分かっており、そのリレーションIDをleftjoinの最小RHSに含めることでそれを強制するためです）。そして、下のleftjoinの最小LHSは{B}、最小RHSは{C,D}になります。このような情報が与えられると、join_is_legalは上のジョインを下のジョインのRHSに結合しても問題ないと判断し、クエリを以下のように変換してしまいます。 B leftjoin (A leftjoin (C innerjoin D) on Pa) on (Pbcd) これは完全に誤った結果をもたらします。これを防ぐため、上のジョインの最小RHSにBを強制的に含めるようにします。これはおそらく過度に制限的ですが、このようなケースは頻繁に発生しないため、より複雑なシステムを開発する価値があるかどうかは明らかではありません。

サブクエリの引き上げ（Pulling Up Subqueries）

上で説明したように、レンジテーブルに現れるサブクエリは独立して計画され、外部クエリの計画中は「ブラックボックス」として扱われます。これは、サブクエリが集約、GROUP、またはDISTINCTなどの機能を使用する場合に必要です。しかし、サブクエリが単なる単純なスキャンやジョインである場合、サブクエリをブラックボックスとして扱うと、計画探索空間全体の一部として考慮する場合と比較して、劣ったプランが生成される可能性があります。そのため、計画プロセスの開始時に、プランナは単純なサブクエリを探し、それらをメインクエリのジョインツリーに引き上げます。

サブクエリを引き上げると、ジョインツリーの最上部より下にFROMリストのジョインが現れることがあります。各FROMリストは、上述の動的計画法による探索手法を使用して計画されます。

サブクエリの引き上げによって、あるFROMリストが別のFROMリストの直接の子として生成された場合、これら2つのFROMリストをマージできます。これが完了すると、サブクエリは外部クエリの完全に不可欠な一部となり、ジョインツリーの探索空間をまったく制約しなくなります。しかし、動的計画法による探索の実行時間は考慮されるFROM項目的数に対して指数関数的であるため、計画時間が好ましくないほど増加する可能性があります。したがって、マージした結果、1つのリスト内のFROM項目が多すぎるようになる場合は、FROMリストをマージしません。

VarとPlaceHolderVar

Varノードは、単にテーブル列参照のパースツリー表現です。しかし、外部ジョインが存在する場合、その概念は見た目よりも微妙です。Varをnullに強制する可能性のある外部ジョインの「上」と「下」でのVarの値を区別する必要があります。例として、以下を考えてみましょう。

SELECT * FROM t1 LEFT JOIN t2 ON (t1.x = t2.y) WHERE foo(t2.z)

（foo()は厳密（strict）ではないと仮定します。これにより、レフトジョインを通常のジョインに還元することはできません。）単純な実装では、foo(t2.z)の呼び出しをt2のスキャンまで押し下げようとするかもしれませんが、それは正しくありません。なぜなら、(a) null拡張されたジョイン行に対してfoo()が実際に受け取るべき値はNULLであり、(b) foo()が偽を返した場合、t1の行をジョインから完全に抑制すべきであり、null拡張されたt2の行と一緒に出力すべきではないからです。一方で、クエリが以下のようであれば、その呼び出しをスキャンレベルまで押し下げることが正しく（かつ望ましく）なります。

SELECT * FROM t1 LEFT JOIN t2 ON (t1.x = t2.y AND foo(t2.z))

これにより、レフトジョインのON句内の「t2.z」を、JOIN句の外の「t2.z」とは異なる値として考える動機が生まれます。前者はリレーションスキャンレベルで見たt2.zと同一視できますが、後者は同一視できません。

別の例は、EquivalenceClasses（後述）に関連して発生します。以下が与えられたとします。

SELECT * FROM t1 LEFT JOIN t2 ON (t1.x = t2.y) WHERE t1.x = 42

私たちはEquivalenceClassの仕組みを使用して「t2.y = 42」を導出し、それをt2のスキャンの制約句として使用したいと考えます。（これは機能します。なぜなら、yが42と異なるt2の行はクエリ結果に影響を与えないからです。）しかし、すべてのジョインされた行においてt2.yがt1.xと等しくなると結論付けるのは誤りです。この問題に対する解決策の一部は、ON句内の「t2.y」はリレーションスキャンレベルのt2.yの値を参照するが、ジョインされた行でyが持つ値（そこではt1.xと等しくなるのではなくNULLになる可能性があります）は参照しないとみなすことです。

したがって、Varノードは「varnullingrels」で装飾されます。これは、クエリ内でVarが現れる時点で、そのVarをnullにする可能性のある外部ジョインのレンジテーブルインデックスのセットです。（順序付きリストではなくセットを使用するのは、どのジョインが値をnullに強制したかは重要ではないため問題ありません。また、これにより異なる外部ジョイン順序を考慮するときに表現を変更する必要がなくなります。）上記の例では、レフトジョインはt1をnullにしないため、t1.xのすべての出現でvarnullingrelsは空になります。JOIN ON句内のt2参照も、空のvarnullingrelsを持ちます。しかし、JOIN句の外では、t2を参照するすべてのVarは、JOINのレンジテーブルエントリ（RTE）のインデックスを含むvarnullingrelsを持つため、スキャンレベルで表示されるt2の値とは異なる可能性があると理解されます。WHERE句のt2.zにJOINのRTインデックスをラベル付けすることで、そのfoo(t2.z)の出現をt2のスキャンレベルに押し下げることができないことを認識できます。つまり、その値はスキャンレベルでは評価できず、ジョインが実行された後にのみ評価できます。

LEFTおよびRIGHT外部ジョインの場合、ジョインのnullable（nullになり得る）側から取得されたVarのみが、そのジョインのRTインデックスでマークされます。FULLジョインの場合、両方の入力からのVarがマークされます。（このようなマーク付けでは、Varがフルジョインのどちらの側から来たかを判断することはできませんが、その情報は必要に応じて他の場所で見つけることができます。）

概念的には、空でないvarnullingrelsを持つVarは、以下のように考えることができます。 CASE WHEN any-of-these-outer-joins-produced-a-null-extended-row THEN NULL ELSE the-scan-level-value-of-the-column END これは概念上のものに過ぎず、そのような計算が明示的に行われることはありません。完成したプランでは、スキャンレベルのプランノードに現れるVarは実際のテーブル列の値を表しますが、上位レベルのVarは常に下位レベルのプランノードの出力への参照です。ジョインノードがnull拡張された行を出力するとき、入力から値をコピーするのではなく、関連する出力列に対して単にnullを返します。この計算を明示的に行う必要はまったくないため、外部ジョインのどちらの側がnull拡張されたかを区別する必要はありません。区別が必要であれば、FULL JOINの場合に不可欠な情報になっていたはずです。

外部ジョインの恒等式3（上述）は、この状況を少し複雑にします。以下の形式では、 A leftjoin (B leftjoin C on (Pbc)) on (Pab) Pbc句とPab句内のすべてのVarは空のvarnullingrelsを持ちますが、もし以下から開始すると、 (A leftjoin B on (Pab)) leftjoin C on (Pbc) パーサはPbcのBのVarにA/BジョインのRTインデックスをマークしているため、この形式は最初の形式と人為的に異なるものになります。議論のために、このマークをアスタリスクで表すことにします。 (A leftjoin B on (Pab)) leftjoin C on (Pb*c) これに対処するため、これらのジョインの入れ替えが正当であることを検出したら、パーサが作成したBのVarにおいて最初のジョインのRTインデックスを削除または追加することにより、そのON句のPbc形式とPb*c形式の両方を生成します。BとCをジョインするプランステップのパスを生成する際、AがすでにBにジョインされているかどうかに応じて、適切な形式のみを関連するジョイン条件（join qual）として含めます。

また、恒等式3により「レフトジョインのRTインデックス」自体が少し曖昧な概念になることにも注意が必要です。各ジョインRTEの構文上のスコープは、パーサによってどの形式が生成されたかに依存するためです。私たちは、レフトジョインのアイデンティティはその最小の右側入力リレーションのセットによって決定されると考えることで、これを解決します。恒等式3で許可される両方の形式において、最初のジョインは最小RHSがBであり、2番目のジョインは最小RHSがCであると識別できます。

もう一つ注意すべき点は、元のパーサ入力が恒等式3の最初の形式であった場合、ネストされたJOIN句の外側に現れるCのVarは両方のレフトジョインによってnull化されるとマークされますが、パーサ入力が2番目の形式であった場合、そのようなVarは2番目のジョインによってのみnull化されるとマークされることです。これは実際にはセマンティクス上の問題ではありません。そのようなVarはクエリの上位部分全体で同じようにマークされるため、すべてequal()に見え、これは正しい動作です。また、JOIN ON句内やこれらのジョインの下に現れるCのVarとはequal()には見えません。しかし、ジョインリレーションの出力を表すVarを構築する際には、それらのvarnullingrelsが構文上のジョイン順序と一致する値に設定されていることを確認する必要があります。これにより、クエリの上位部分にある既存のVarとequal()に見えるようになります。

外部ジョインは、サブクエリの引き上げの処理も複雑にします。以下を考えてみましょう。

SELECT ..., ss.x FROM tab1 LEFT JOIN (SELECT *, 42 AS x FROM tab2) ss ON ...

前述のようにサブクエリを引き上げられるようにしたいのですが、最上位のSELECTリストにある「ss.x」Varを単に定数42に置き換えることはできません。そうすると、null拡張されたジョイン行でNULLを出力するのではなく、常に42を出力することになってしまいます。

これを解決するために、PlaceHolderVarという概念を導入します。PlaceHolderVarはVarに似ており、その値はリレーションスキャンレベルで発生し、その後、より上位レベルの外部ジョインによって強制的にnullにされる可能性があります。そのため、PlaceHolderVarはVarと同様にnull化を行うリレーションIDのセットを保持します。元の値がテーブルから取得されるVarとは異なり、PlaceHolderVarの元の値はクエリによって決定される式（この例では「42」）によって定義されます。そのため、PlaceHolderVarをその式を子とするノードとして表現します。サブクエリの引き上げにおいて、空でないvarnullingrelsを持つサブクエリ参照Varを、単なるVarではない式で置き換える必要がある場合は常に、PlaceHolderVarを挿入します。（置き換え後の式が引き上げられたVarである場合は、置き換えられたVarのvarnullingrelsをそのセットに追加するだけで済みます。また、置き換えられたVarのvarnullingrelsが空である場合は、PlaceHolderVarは必要ありません。値をnullに強制するものが何もないため、引き上げられた式をそのまま使用して問題ありません。）完成したプランでは、PlaceHolderVarは評価されるべきプランレベルにおける単なる内包された式になり、その後、上位レベルでの出現は下位プランレベルのその出力列へのVar参照に置き換えられます。これにより、通常のVarと同様に、外部ジョインで適切な場合に値がnullになります。したがって、PlaceHolderVarがプランナの外部で見られることはありません。

PlaceHolderVar（PHV）は、別の意味でもVarより複雑です。 元の値をベースレベルのリレーションスキャンではなく、結合（join）で計算する必要がある場合があります。これは、プルアップされたサブクエリに結合が含まれている場合に発生する可能性があります。このため、PHVは、使用される前に計算できるようにするために、本来は存在しない結合順序の制約を作成することがあります。PHVの式にはLATERAL参照を含めることもでき、これによって以下で説明する複雑さが生じます。

Relation Identification and Qual Clause Placement

WHEREまたはJOIN/ONから取得されたqual句は、その句で使用されているすべてのリレーションを含む、最も低いスキャンまたは結合レベルで適用できます。この目的のために、varnullingrelsまたはphnullingrelsにリストされている外部結合がその句で使用されているとみなします。なぜなら、そのようなVarがNULLになったかどうかがわかるまで、qualの結果を正しく計算できないからです。

この一般的なルールの唯一の例外は、非退化（non-degenerate）な外部JOIN/ONのqual（結合の非NULL可能側を参照するもの）は、NULL可能側を参照していなくても、その結合より下で適用することはできないということです。これを非NULL可能側にプッシュダウンすると、結合の結果から行が消失してしまい、NULL拡張された行として表示されなくなってしまいます。これに対処するため、そのようなqualを特定した際、結合の最小入力relidセットを、そのqualが使用しているとみなされるリレーションのセットに人為的に追加し、まさにその結合レベルで評価されるように強制します。リレーションをまったく言及しない外部結合のqualについても同様のことが行われます。

外部結合を実行する結合プランノードにqual句を付加する場合、そのqual句がvarnullingrelsまたはphnullingrelsセットでその外部結合を参照していない場合は「結合句（join clause）」（つまり、結合がNULL拡張を実行する前に適用される）とみなされ、その外部結合を参照している場合は「フィルタ句（filter clause）」（NULL拡張の後に適用される）とみなされます。その外部結合のJOIN/ONに元々存在していたqual句は、パーサがそのVarのいずれにも外部結合を参照しているというマークを付けないため、最初のカテゴリに分類されます。上位のON句やWHERE句から元々来たqual句は、NULL可能側のVarのいずれかを参照している場合、それらのVarにパーサによってそのマークが付けられるため、外部結合を参照しているとみなされます。しかし、そのようなqualがNULL可能側のVarをまったく参照していない場合は、非NULL可能側にプッシュダウンして構わないため、そもそも結合ノードには付加されません。

これらのことから、プランナ内では、結合リレーションを、それらが含むベースリレーションのRTインデックスと外部結合のRTインデックスのセットによって識別することになります。そうすることで、qual句によって使用されるリレーションのセットを、結合リレーションのrelidセットと直接比較して、句をどこに配置すべきかを判断できます。これらの識別セットは一意です。なぜなら、任意のベースリレーションの集合に対して、そのベースリレーションの集合を結合する過程で実行されるべき有効な外部結合のセットは1つしか存在しないからです（適用する順序は、上述のように異なる場合がありますが）。

SEMI結合は、パーサではなくプランナによって作成される成果物であるため、RTインデックスを持ちません。（それらのレンジテーブルエントリを作成することもできますが、現時点ではその必要はないようです。）これはqualの配置において問題にはなりません。なぜなら、セミ結合のNULL可能側は結合の上位から参照できないため、varnullingrelsやphnullingrelsでそれを引用する必要がまったくないからです。また、セミ結合が完了したかどうかは、結合に含まれるベースリレーションのセットに暗黙的に含まれているため、結合リレーションの識別においても問題にはなりません。

いつものように、外部結合の恒等式3（identity 3）が事態を複雑にします。もし、 (A leftjoin B on (Pab)) leftjoin C on (Pbc) から開始する場合、パーサはこれらの結合の上位に現れるすべてのCのVarに、B/C結合のRTインデックスをマークします。ここで、 A leftjoin (B leftjoin C on (Pbc)) on (Pab) に変換すると、そのようなVarのみを使用する句は、プッシュダウンされて下位のB/C結合でフィルタ句（結合句ではなく）として適用できるように見えます。しかし、*これは正しい答えを与えない可能性があります*。なぜなら、その句は、A/B結合が実行されるとNULLに置き換えられるCのVarに対して、非NULLの値を参照してしまう可能性があるからです。これに対処するため、プッシュダウンされた結合はB/C結合の処理を完全に完了していないため、その外部結合のrelidを自身のrelidセットに含める資格がないとみなします。A/B結合を形成するときに、両方の外部結合のrelidがそのrelidセットに追加され、その後、上位の句が正しい結合レベルで適用されます。（なお、恒等式3が逆方向に適用される場合は問題ありません。2番目の形式から開始した場合、上位のCのVarには両方の外部結合のrelidがマークされているため、2番目に適用される結合よりも下に下がることはできません。）同様に、プッシュダウンされた結合の出力を表すVarは、上位の結合が実行されるまで、その結合のnullingrelビットを取得しません。

qual句の配置にはもう1つの複雑さがあります。これは、前述のように外部結合句の複数のバージョンを作成した場合に発生します（つまり、外部結合の恒等式3で見られる同じ句の「Pbc」形式と「Pb*c」形式の両方がある場合です）。外部結合を形成するとき、冗長なバージョンの句のうち1つだけを適用したいと考えます。A/B結合をまだ計算していない状態でB/C結合を形成している場合、「Pb*c」形式の必要とするrelidセットに入力に含まれていないA/B結合のrelidが含まれているため、これを拒否するのは簡単です。しかし、A/Bの後にB/Cを形成する場合、そのテストで判断できる限りでは、両方の形式の句が適用可能になってしまいます。より注意深く見て、「Pbc」句の形式が、もはや直接アクセスできないリレーションBを参照していることに気づく必要があります。このようなチェックはリレーションごとのRelOptInfo.nulling_relidsデータを使用して実行できますが、さまざまな結合パスを検討する際に何度も繰り返すのは煩わしいほどコストがかかります。これをシンプルかつ確実にするために、冗長な句の各バリアントバージョン（クローン）に対して「incompatible_relids」セットを計算します。incompatible_relidsにリストされている外部結合のrelidのいずれかが、現在の結合より下で既に計算されている場合、クローン句は適用されるべきではありません。

オプティマイザは、パスによって返されるタプルの順序を気にするために、かなりの時間を費やします。これが有用である理由は、パスのソート順序を知ることで、そのパスをマージ結合の左右の入力として使用し、明示的なソートステップを回避できる可能性があるからです。ネステッドループやハッシュ結合は、入力の順序をそれほど気にしませんが、マージ結合は適切にソートされた入力を必要とします。したがって、最適化プロセス中に生成されるすべてのパスには、上位レベルのマージで利用できるように、ソート順序（判明している範囲で）がマークされます。

最終的なパスがすでに適切な順序になっている場合、ユーザーの ORDER BY 句を実装するために明示的なソートステップを回避することも可能です。 そのため、ソート順序はトップレベルにおいても重要です。 grouping_planner() は、希望する順序に一致するソート順序を持つ最もコストの低いパスを探し、 そのコストと、全体で最もコストの低いパスを使用してその上で明示的なソートを行った場合のコストを比較します。

特定の RelOptInfo のパスを生成する際、同じまたはより良いソート順序を持つ別の既知のパスよりも コストが高い場合、そのパスは破棄されます。 （明示的なソートなしで）特定のソート順序を実現する唯一既知の方法であるパスは、決して破棄されません。 このようにして、上のレベルでは、入力用に保持された任意のパスから選択できるため、 ソートなしでマージ結合を構築する自由度が最大になります。

EquivalenceClasses

クエリの条件（qual）句に対する deconstruct_jointree() のスキャン中に、 マージ結合可能な等価句 A = B を探します。 見つかった場合、それらが等しいことを記録するために、式 A と B を含む EquivalenceClass を作成します。 後で別の等価句 B = C が見つかった場合は、{A B} の既存の EquivalenceClass に C を追加します。 これにより、2つの既存の EquivalenceClasses をマージする必要が生じる場合があります。 スキャンの終了時には、互いに推移的に等しいことが既知である値のセットが得られます。 したがって、任意のペアの値を制限句または結合句としての比較に使用できます（もちろん、 これらの値がスキャンまたは結合時に利用可能な場合）。 さらに、それらすべてをテストする必要はなく、そのような比較を1つだけテストすれば十分です。 したがって、等価句は標準的な条件（qual）分散プロセスから削除されます。 代わりに、制限句または結合句のリストを準備するときに、各 EquivalenceClass を調べて 句に寄与できるかどうかを確認し、可能であれば比較する値の適切なペアを選択します。 たとえば、A のリレーションと C のリレーションを結合しようとしている場合、 元のクエリのどこにも明示的に現れていなかったとしても、句 A = C を生成できます。 これにより、デカルト積結合を必要とするとして本来なら拒否されていたであろう結合パスを探索できるようになります。

EquivalenceClass に擬似定数式（つまり、現在のクエリレベルの Vars や Aggs、 または変動関数を含まない式）が含まれている場合があります。 この場合、結合句を動的に生成する方針には従わず、代わりに、 クラスの変数メンバーのいずれかを最初に計算できる場所に制限句「var = const」を動的に生成します。 たとえば、A = B および B = 42 がある場合、効果的に制限句 A = 42 および B = 42 を生成し、 その後、リレーションが結合されるときに結合句 A = B を明示的にテストする手間を省くことができます。 実質的に、すべてのクラスメンバーをリレーションスキャンレベルでテストできるため、結合テストの必要はまったくありません。

EquivalenceClass の正確な技術的解釈は、 そのメンバー値のうち複数の値を計算できるどのプランノードにおいても、 値がすべて等しくない出力行はクエリ結果に影響を与えることなく破棄できる、ということを主張するものです。 （プランのすべてのレベルで EquivalenceClasses を強制することを要求しているため、 子孫のいずれかによって計算可能であった値の等価性を結合が再チェックする必要はありません。）

ただし、外部結合はこの状況をかなり複雑にします。 理論的には、外部結合条件に現れるマージ結合可能な等価句を EquivalenceClasses のソースとして使用できますが、 深刻な困難があります。それは、結果として得られる推論がどこでも有効であるとは限らないということです。 たとえば、次のような場合です。

SELECT * FROM a LEFT JOIN b ON (a.x = b.y AND a.x = 42);

b.y = 42 を安全に導出し、それを B のスキャンで使用できます。なぜなら、 b.y = 42 を持たない B の行は結合結果に寄与しないためです。 しかし、A のスキャンで a.x = 42 を適用することはできません。 適用すると、結合結果に現れるべき行が削除されてしまうためです。 a.x = 42 を外部結合条件として適用することはできます（その場合、a.x = b.y もチェックする必要はなくなります）。 しかし、これはまだ実装されていません。

関連する問題として、外部結合の下に現れる定数は、見た目ほど定数ではないということがあります。 通常、「A = 1」と「B = 1」が見つかった場合、A と B を同じ EquivalenceClass に入れても問題ありません。 しかし、次を考えてみてください。

SELECT * FROM a LEFT JOIN (SELECT * FROM b WHERE b.z = 1) b ON (a.x = b.y) WHERE a.x = 1;

a.x = b.z と結論付けるのは重大な誤りであるため、単一の EquivalenceClass {a.x b.z 1} を形成することはできません。

これにより、EquivalenceClasses が「結合ドメイン（join domains）」内で適用されるものと見なすようになります。 結合ドメインとは、互いに内部結合されているリレーションのセットです。 （この目的のために、セミジョインは内部結合であるかのように扱うことができます。） トップレベルの結合 domain があり、クエリ内の各外部結合が、 その NULL 許容側を含む新しい結合ドメインを作成します。 フル結合は、各側に1つずつ、合計2つの結合ドメインを作成します。 WHERE から生成された EquivalenceClasses は、トップレベルの結合ドメインに関連付けられます。 外部結合の ON 句から生成された EquivalenceClasses は、その外部結合によって作成されたドメインに関連付けられます。 内部結合またはセミ結合の ON 句から生成された EquivalenceClasses は、 構文的に最もネストが深い結合ドメインに関連付けられます。

これらのドメインを定義することで、定数が同じ結合ドメイン内の句から来ている場合にのみ EquivalenceClass メンバーと一致すると見なすことにより、 「あまり定数ではない定数」の問題を解決できます。 上記の例では、これは {a.x 1} と {b.z 1} を別々の EquivalenceClasses として保持し、 誤ってマージしないことを意味します。 Vars（または Vars を含む式）については、これについて心配する必要はありません。 なぜなら、異なる結合ドメインからの「同じ」カラムへの参照は異なる varnullingrels を持つため、 いずれにせよ equal() にならないからです。

将来的に、結合ドメインの概念により、マージ結合可能な外部結合条件を EquivalenceClasses のソースとして扱うことができるようになるかもしれません。 そのアイデアは、そのようなクラスから派生した条件は、 適切な結合ドメイン内にあるスキャンまたは結合においてのみ強制できるというものです。 ただし、詳細が見た目よりも難しいため、これはまだ実装されていません。

もう一つの教育的な例は次のとおりです。

SELECT * FROM a LEFT JOIN (SELECT * FROM b JOIN c ON b.y = c.z WHERE b.y = 10) ss ON a.x = ss.y ORDER BY ss.y;

EquivalenceClass {b.y c.z 10} を形成し、それにより C のスキャン時に c.z = 10 を適用し、 また B のスキャン時に b.y = 10 を適用できるため、内部結合でチェックする必要のある句はなくなります。 左側結合の句「a.x = ss.y」（実際には「a.x = b.y」）は等価句とは見なされないため、 a.x をその同じ EquivalenceClass に挿入しません。 もし挿入した場合、a.x = 10 と誤って結論付けてしまいます。 ただし、A のスキャン時に a.x = 10 を適用することを避けられれば、将来的にそれが可能になるかもしれません。 原則として、EquivalenceClass が {B,C} 結合ドメイン内のみで適用されることに注目することで、それが可能です。

また、ORDER BY 内の ss.y は実際には b.y*（つまり、b.y の NULL 化された可能性のある形式）であるため、 下位の EquivalenceClass の b.y メンバーと混同されないことにも注意してください。 したがって、ss.y が定数に等しいと誤って結論付けることはありません。 もしそれが真であれば、ORDER BY のためのソートが不要であると思い込ませることになります （以下の PathKeys の議論を参照してください）。 代わりに、b.y* のみを含む個別の EquivalenceClass が存在し、 それが要求されるソート順序を記述する PathKey の基礎を形成します。

このバリアントも考慮してください。

SELECT * FROM a LEFT JOIN (SELECT * FROM b JOIN c ON b.y = c.z WHERE b.y = 10) ss ON a.x = ss.y WHERE a.x = 42;

依然として EquivalenceClass {b.y c.z 10} が形成され、さらに 異なる結合ドメインに属する EquivalenceClass {a.x 42} が存在します。 「a.x = b.y」を使用してこれらのクラスをマージすることはできません。 ただし、その外部結合句を既存の EquivalenceClasses と比較して、 派生句「b.y = 42」を形成することができます。 これを下位の結合ドメイン内での有効な等価性として扱うことができます （そのドメインの行で b.y = 42 を持たないものは外部結合の結果に寄与できないため）。 これにより、下位の EquivalenceClass は {42 b.y c.z 10} となり、 10 = 42 という矛盾が生じます。 これにより、プランナーは B/C 結合をまったく計算する必要がないと推論できます。 その結合ドメイン全体の 結果を空に強制することができます。 （これはゲーティング Result フィルターとして実装されます。通常、 潜在的な矛盾は単なる Const ではなく Param 値を伴うため、 実行時にチェックする必要があるためです。 結合ドメインを使用して、ゲーティング条件を配置する結合レベルを決定できます。）

ID 3 に従って外部結合を並べ替える際には、追加の複雑さがあります。 そのような結合について考慮する2つの選択肢を思い出してください。

A leftjoin (B leftjoin C on (Pbc)) on (Pab) (A leftjoin B on (Pab)) leftjoin C on (Pb*c)

ここで、アスタリスクは B の Vars上の varnullingrels マーカーを示します。 Pbc がマージ結合可能な句である（またはそれを含む）場合、次のようなものになります。

A leftjoin (B leftjoin C on (b.b = c.c)) on (Pab) (A leftjoin B on (Pab)) leftjoin C on (b.b* = c.c)

b.b と c.c を結ぶ EquivalenceClause を生成できますが、 その後 b.b* と c.c も結ぼうとすると、 b.b と b.b* が等しいという（プランツリーの一部において少なくとも）無意味な結論に至ってしまいます。 いずれにせよ、そのようなものから導き出せる結論は、大部分が重複するものです。 b.b* を含む条件はこの結合ネスティングの下で計算することはできませんが、 計算できる条件は、b.b/c.c の組み合わせから得られるものと重複します。 したがって、b.b と c.c を結ぶ EquivalenceClause を生成することを選択しますが、 「b.b* = c.c」は単なる通常の句として処理されます。

マージ結合で機能するソート順序を決定するのを助けるために、 各マージ結合可能な句に、その左側および右側の入力の EquivalenceClasses の印を付けます。 等価句の場合、これらは当然同じ EquivalenceClass です。 等価句ではないマージ結合可能な句（外部結合条件など）の場合、 左側および右側の入力用に2つの別個の EquivalenceClasses を生成します。 これにより、単一アイテムの等価「クラス」が作成される可能性がありますが、 他の等価句が後で同じ式に関係していることが判明した場合は、 もちろんこれらは依然としてマージの対象となります。

単一アイテムの EquivalenceClass を形成するもう1つの方法は、 希望するソート順序を表す PathKey の作成時です（下記参照）。 これは、ORDER BY または GROUP BY キーがどの等価句にも言及されていない場合に発生します。 そのようなクエリでソート順序について推論する必要があり、 ソート順序の表現は EquivalenceClass に依存する PathKey であるため、 EquivalenceClass を作成する必要があります。 これは上記の場合とは少し異なります。 なぜなら、そのような EquivalenceClass には集約関数や変動関数が含まれている可能性があるためです。 （変動関数を含む句は、そのトップオペレータがマージ結合可能であっても、 マージ結合可能とは見なされないため、 変動関数が他の方法で EquivalenceClasses に入り込む方法はありません。 集約は WHERE では完全に禁止されているため、 マージ結合可能な句に見つかることはありません。） これは、一貫した PathKey 表現を維持するための単なる利便性であり、 そのような EquivalenceClass が他のものとマージされることはありません。 特に、単一アイテムの EquivalenceClass {a.x} は、 a.x = a.x という主張を意味するものでは*ない*ことに注意してください。 これの実用的な影響は、a.x が NULL になり得るということです。

An EquivalenceClassには、それが表す等価性が実際に何を「意味」するのかを決定する、btree opfamilyのOIDのリストも含まれています。EquivalenceClassに寄与するすべての等価句は、同じopfamilyのセットに属する等価演算子を持っていなければなりません。（注意：ほとんどの場合、特定の等価演算子は1つのファミリーにのみ属しますが、複数のファミリーに属することもあり得ます。マージジョインの目的で、いずれかのファミリーに属するインデックスを利用できるようにするために、すべてのファミリーを追跡しています。）

同様の理由から、EquivalenceClassのデータ型が照合順序（collation）を考慮するものである場合、それは特定の照合順序にも関連付けられます。

EquivalenceClassには「em_is_child」メンバーを含めることができます。これは、appendrelの親リレーションのVarを含むメンバーのコピーであり、等価な子リレーションの変数または式を含むように置き換えられたものです。これらのメンバーはEquivalenceClassの「完全な」メンバーではなく、クラス全体のプロパティには一切影響しません。これらは、子リレーションの式とEquivalenceClassとのマッチングを簡素化するためだけに保持されています。EquivalenceClassに対するほとんどの操作では、子メンバーを参照する必要はありません。

PathKeys

PathKeysデータ構造は、特定のPathによって生成されるタプルのソート順序に関して判明している情報を表します。パスのpathkeysフィールドはPathKeyノードのリストであり、n番目の項目は結果のn番目のソートキーを表します。各PathKeyには以下のフィールドが含まれます。

  • EquivalenceClassへの参照
  • btree opfamilyのOID（EC内のいずれかと一致する必要があります）
  • ソート方向（昇順または降順）
  • nulls-first-or-lastフラグ

EquivalenceClassは、ソート対象の値を表します。EquivalenceClassの様々なメンバーは、opfamilyに従って等価であることが分かっているため、それらのいずれかでソートされたパスは、他のいずれかでソートされたパスでもあると見なすことができます。これが、単一のメンバーではなくEquivalenceClass全体を参照することの正当性です。

単一/ベースリレーションのRelOptInfoにおいて、Pathはリレーションをスキャンする様々な方法と、その結果得られるタプルの順序を表します。シーケンシャルスキャンのPathはNILのpathkeysを持ち、これは既知の順序がないことを示します。インデックススキャンは、選択されたインデックスの順序（存在する場合）を表すPath.pathkeysを持ちます。単一キーのインデックスは単一のPathKeyリストを作成しますが、複数列インデックスはキーインデックス列ごとに1つの要素を持つリストを生成します。カバリングインデックスのINCLUDE句で指定された非キー列は、インデックスの順序に影響を与えないため、リストに対応するPathKeyを持ちません。（実際には、インデックスは前方または後方のいずれの方向にもスキャンできるため、生成可能なソート順序は2つあり、PathKeyリストも2つ存在します。）

ビットマップスキャンは、その結果の全体的な順序について何も言えないため、NILのpathkeysを持つことに注意してください。また、順序付けられていないタイプのインデックスに対するインデックススキャンもNILのpathkeysを生成します。ただし、明示的なソートを行うことで、いつでもpathkeyを作成できます。Sortプランの出力に対するpathkeysは、使用されたソートキーフィールドと順序付け演算子を表すだけです。

結合（join）を考慮すると、話はより面白くなります。mergeclause A.X = B.Yを使用してAとBの間でマージジョインを行うと仮定します。マージジョインの出力はXでソートされますが、同時にYでもソートされます。これも、XとYの両方を含むEquivalenceClassを参照するPathKeyによって表すことができます。

もう少し考えると、ネストループジョインもソートされた出力を生成できることが明らかになります。例えば、外側リレーションAと内側リレーションBの間でネストループジョインを行う場合、Aに関連するすべてのpathkeysは結合結果に対しても有効です。Aからのタプルの順序は変更されていないからです。さらに興味深いことに、等価句A.X=B.Yが存在し、A.Xが外側リレーションAのpathkeyであった場合、B.Yが結合結果のpathkeyであると主張できます。Xは以前に順序付けられており、現在もそうであり、結合されたYの値は結合されたXの値と等しいため、Yも順序付けられている必要があります。これは、Yに対して明示的なソートもマージジョインも使用していない場合でも真となります。（注意：ハッシュジョインは、エグゼキュータが結合を「バッチ処理」することを決定する可能性があるため、外側リレーションの順序を維持することは期待できません。そのため、ハッシュジョインパスのpathkeysは常にNILに設定します。）

外部結合（outer join）は、ソート順のランダムな位置にNULLを挿入する可能性があるため、NULLになり得る入力リレーションの順序を維持しません。PathKeyの表現においてこれを明示的に考慮する必要はありません。結合後の変数を表すPathKeyにはvarnullingrelビットが含まれるため、結合前の値を表すPathKeyとは等しくなくなるからです。

一般に、pathkeysの基礎としてEquivalenceClassesを使用することは正当化できます。なぜなら、複数のEquivalenceClassメンバーを含むリレーションをスキャンする場合や、それぞれがEquivalenceClassメンバーを含む2つのリレーションを結合する場合、常にEquivalenceClassから派生した制限句または結合句を適用するからです。これにより、EquivalenceClassにリストされている任意の2つの値が、スキャンまたは結合によって出力されるすべてのタプルにおいて実際に等しいことが保証されます。したがって、タプルがそれらの値のいずれかでソートされている場合、他のいずれの値でもソートされていると見なすことができます。テスト句がmergeclauseとして使用されるか、単にqpqualフィルターとして事後的に適用されるかは関係ありません。

パスの出力にまだ結合されていない変数を含むEquivalenceClassを参照するPathKeyを使用して、パスのソート順をラベル付けすることには、特に困難はありません。そのようなエントリは（まだ）関連性がないものとして単に無視できます。これにより、結合計画プロセス全体で同じEquivalenceClassesを使用することが可能になります。実際、複数の同一のPathKeyオブジェクトを生成しないように注意することで、EquivalenceClassesとPathKeysの比較を単純なポインタ比較に削減できます。これは、競合するPathが同等にソートされているかどうかを判断する際に、add_pathが大量のPathKey比較を行う必要があるため、非常に大きな節約になります。

Pathkeysは、達成したい順序を表すのにも便利です。潜在的な候補パスのpathkeysと簡単に比較できるからです。そのため、SortGroupClauseリストはオプティマイザ内部で使用するためにpathkeysリストに変換されます。

さらに行える改善として、正規のpathkeyリスト（ソート順序）が同じEquivalenceClassを複数回参照しないようにすることが挙げられます。例えば、以下のすべてのケースにおいて、2番目のソート列は冗長です。なぜなら、最初のソート列に従って同じである値を区別できないからです。 SELECT ... ORDER BY x, x SELECT ... ORDER BY x, x DESC SELECT ... WHERE x = y ORDER BY x, y ユーザーが直接「ORDER BY x,x」と書くことはおそらくないでしょうが、等価クラスが考慮されると、このような冗長性が発生する可能性が高くなります。また、システムはマージジョインに必要なソート順序を計算する際に、冗長なpathkeyリストを生成することがあります。冗長性を排除することで、プランナーが同等の順序を同等であると認識しやすくなり、時間を節約し、計画を改善できます。

もう一つの興味深い特性は、基礎となるEquivalenceClassに定数が含まれている場合、そのpathkeyは完全に冗長であり、ソートする必要がまったくないということです。関心のあるすべての行は同じ値を含んでいるはずなので、ソートする必要はありません。ユーザーが「... WHERE x = 42 ORDER BY x」と書く可能性は低いため、これは無意味に思えるかもしれませんが、特定のインデックス列がソート順序に関係ないことを認識できるようになります。例えば、「... WHERE x = 42 ORDER BY y」がある場合、(x,y)のインデックスをスキャンすると、ソートステップなしで正しくソートされたデータが生成されます。以前は、限られたコンテキストでこれを認識するために非常に見苦しいアドホックなコードがありましたが、pathkeysから定数ECを破棄することで、これがクリーンかつ自動的に行われるようになります。

Order of processing for EquivalenceClasses and PathKeys

上で触れたように、計画中のEquivalenceClassesとPathKeysの処理には特定のフェーズの順序があります。クエリのqualの初期スキャン（deconstruct_jointreeに続くreconsider_outer_join_clauses）の間に、qualで見つかったマージ結合可能な句に基づいてEquivalenceClassesを構築します。このプロセスの終了時点で、異なる変数の等価性について判明し得るすべてのことが分かっているため、その後EquivalenceClassesがさらにマージされることはありません。その時点で、EquivalenceClassesを「正規（canonical）」と見なし、それらを参照する正規 of PathKeysを構築することが可能になります。この時に、クエリのORDER BYおよび関連する句のPathKeysを構築します。（他に出現しない順序付け式は新しいEquivalenceClassesの作成につながりますが、これにより既存のクラスがマージされることはないため、正規性は失われません。）

パス生成を開始する前にすべてのEquivalenceClassesが判明しているため、それらをどのインデックスが関心の対象であるかのガイドとして使用できます。インデックスの列がいずれのEquivalenceClassにも言及されていない場合、そのインデックスのソート順序がクエリに役立つ可能性はありません。これにより、無関係なインデックスに対するcreate_index_paths()の処理の多くをショートサーキット（早期終了）させることができます。

query_plannerが完了した後に、planner.cが追加のEquivalenceClassesおよびPathKeysを構築するケースがいくつかあります。これらのケースでは、query_planner中に考慮されなかったソート順序を表すために、追加のEC/PKが必要になります。このような状況は最小限に抑えるべきです。なぜなら、query_plannerがそのようなソート順序を生成するプランを返すことは不可能であり、常に明示的なソートが必要になることを意味するからです。現在、これは異なる順序を持つ複数のウィンドウ関数を含むクエリでのみ発生し、これらにはいずれにせよ追加のソートが必要です。

Parameterized Paths

WHERE A.X = B.Yのような句を使用して2つのリレーションを結合する素朴な方法は、以下のようなnestloopプランを生成することです。

NestLoop Filter: A.X = B.Y -> Seq Scan on A -> Seq Scan on B

マージ結合やハッシュ結合を使用することでこれを改善できますが、それでも両方の入力リレーションのすべてをスキャンする必要があります。Aが非常に小さく、Bが非常に大きいが、B.Yにインデックスがある場合、以下のようにする方がはるかに優れている可能性があります。

NestLoop -> Seq Scan on A -> Index Scan using B_Y_IDX on B Index Condition: B.Y = A.X

ここでは、Aからスキャンされた各行について、nestloopプランノードがA.Xの現在の値をBのスキャンに引き渡すことを期待しています。これにより、インデックススキャンは1回の呼び出しにおいてA.Xを定数として扱うことができ、それによってインデックスキーとして使用できます。これはBのすべてをフェッチすることを回避できる唯一のプランタイプであり、Aから取得される行数が少ない場合は、これが他のすべての考慮事項よりも優先されます。（Aが大きくなるにつれて、これは魅力的ではなくなり、最終的にはマージ結合またはハッシュ結合が代わりに有利になります。そのため、何を行うかを決定するために、すべての代替案のコストを計算する必要があります。）

パラメータ値が結合の中間レイヤーを介して引き渡されることが有用な場合もあります。例えば：

NestLoop -> Seq Scan on A Hash Join Join Condition: B.Y = C.W -> Seq Scan on B -> Index Scan using C_Z_IDX on C Index Condition: C.Z = A.X

すべての結合が通常の内部結合である場合、パラメータを提供するnestloopノードの直下でパラメータが使用されるように結合を並べ替えることができるため、これは通常不要です。しかし、外部結合が存在する場合、そのような結合の並べ替えは不可能な場合があります。

また、最下レベルのスキャンが、複数の他のリレーションからのパラメータを必要とする場合もあります。原理的には、すべてのパラメータが単一のnestloopレベルから提供されるように、最初に他のリレーションを結合することもできます。しかし、それらの他のリレーションに共通の結合句がない場合（例えばスタースキーマクエリでは一般的です）、プランナーはそれらを直接結合することを考慮しません。このような場合、以下のようなプランを作成できる必要があります。

NestLoop -> Seq Scan on SmallTable1 A NestLoop -> Seq Scan on SmallTable2 B -> Index Scan using XYIndex on LargeTable C Index Condition: C.X = A.AID and C.Y = B.BID

したがって、プランをこのように見せるような結合順序の制約がない場合でも、結合を介して A.AID を渡すことをいとわないはずです。

バージョン 9.2 より前では、Postgres はこのような種類のネストループクエリの計画と実行にアドホックな手法を使用しており、それらの手法では複数の結合レベルにわたってパラメータを下方に渡すことを処理できませんでした。

このようなクエリを計画するために、現在では「パラメータ化されたパス（parameterized path）」という概念を使用しています。これは、パスによってスキャンされないリレーションへの結合句を利用するパスです。上の 2 つ目の例では、次のような処理を行う可能性を表すパスを構築します。

-> Index Scan using C_Z_IDX on C Index Condition: C.Z = A.X

このパスは、リレーション A によってパラメータ化されているものとしてマークされます（これは C の可能なアクセスの1つに過ぎず、通常のパラメータ化されていないシーケンシャルスキャンや、おそらくその他の可能性も依然として存在することに注意してください）。パラメータ化マーカーは、パスを B に結合することを妨げないため、結合リレーション {B C} に対して生成されるパスの 1 つは以下を表すことになります。

Hash Join Join Condition: B.Y = C.W -> Seq Scan on B -> Index Scan using C_Z_IDX on C Index Condition: C.Z = A.X

このパスは依然として A によってパラメータ化されているものとしてマークされます。{B C} を A と結合して完全な結合ツリーを形成しようとする際、このようなパスはネストループ結合の内側としてのみ使用でき、他の可能な結合タイプでは無視されます。そのため、上記のクエリプランを表す結合パスが形成され、パラメータ化されていないスキャンから構築されたパスと通常の方法で競合することになります。

特定のリレーションに対する通常のパスはすべて同じ行のセットを生成しますが（すべて同じ制限句のセットを適用する必要があるため）、パラメータ化されたパスは、処理すべき追加の句を持っているため、パラメータ化されていないパスよりも通常は少ない行数を生成します。これは、生成される行数を追加のメリットの指標として考慮しなければならないことを意味します。別のパスよりもコストがかかるものの、生成する行数が少ないパスは、中間結合レベルでより少ない行数によって作業量を節約できる可能性があるため、保持されなければなりません。（パラメータのソースに直ちに結合される場合は、何も節約されません。）

コスト見積もりの​​ルールを比較的シンプルに保つため、同じパラメータ化を持つ特定のリレーションのすべてのパス（つまり、パラメータを提供する外部リレーションのセットが同じもの）は、同じ行数の見積もりを持たなければならないという実装上の制約を設けています。これは、そのような各パスが、指定された外部リレーションで使用可能な*すべての*結合句を適用することを主張することで正当化されます。例えば、異なるパスでインデックス句として使用する異なる結合句を選択する場合がありますが、返される行数のセットが一定に保つように、同じ外部リレーションから利用可能な他のすべての結合句をフィルター条件として適用する必要があります。この制約は、完成したプランの品質を低下させることはありません。これは、移動可能な結合句を常に可能な限り低い評価レベルにプッシュダウンすべきであるということを意味しており、いずれにせよそれは良いことです。この制約は、特に add_path_precheck における結合パスの事前フィルタリングをサポートする上で役立ちます。このルールがないと、行数の見積もりを計算する前にパラメータ化されたパスを拒否することが決してできなくなり、事前フィルタリングメカニズムの価値が大幅に低下することになります。

計画時間を制限するため、不当に多数のパラメータ化されたパスが生成されるのを避けなければなりません。これを行うには、インデックススキャンに対してのみパラメータ化されたリレーションスキャンパスを生成し、さらに適切な結合句が利用可能なインデックスに対してのみ生成するようにします。また、考慮されるパラメータ化されたパスの数を制限しようとする結合計画のヒューリスティクスもあります。

特に、パラメータ化された結合ステップ（下位の結合の入力にパラメータを提供するネストループの下位で発生するもの）に対して、マージ結合よりもハッシュ結合を優先するという意図的なポリシー上の決定がなされています。マージ結合を完全に無視するわけではありませんが、joinpath.c は、パラメータ化された入力を持つ潜在的なマージ結合の空間を完全に探索するわけではありません。また、add_path はパラメータ化されたパスにパスキーがないものとして扱うため、コストと行数のみで競合し、特別なソート順序を生成するための優先権は得られません。これにより、明示的なソートステップなしでマージを実行するのに役立つ可能性があったパスを破棄する可能性があるため、マージ結合に対する追加のバイアスが生じます。パラメータ化されたパスは最終的にネストループの内側で使用される必要があり、そのソート順序は重要ではないため、これらの選択はクエリの最終的な出力順序に対する要件には影響を与えず、下位レベルでのマージ結合の使用を困難にするだけです。計画作業における節約はそれを正当化します。

同様に、パラメータ化されたパスは、低いスタートアップコストを持つことに対して add_path で通常は優先権を与えられません。ネストループの内側にある場合、それはほとんど価値がないため、そのためだけに余分なパスを保持する価値はないように思われます。例外として、SEMI または ANTI 結合の RHS リレーションのパラメータ化されたパスの場合があります。これらのケースでは、最初のマッチ後に内部スキャンを停止できるため、気にするべきなのはトータルコストではなく主にスタートアップコストです。

LATERAL サブクエリ

9.3 以降では、FROM 内のサブクエリ（および FROM 内の関数）からの SQL 標準の LATERAL 参照をサポートしています。オプティマイザは、lateral 参照を含む RTE に対してパラメータ化されたパスを生成することによってこれらを実装します。そのような場合、そのリレーションの*すべての*パスは、少なくともその lateral 参照で使用されるリレーションのセットによってパラメータ化されます（そして順番に、そのようなサブクエリを含む結合リレーションは、パラメータ化されていないパスを全く持たない可能性があります）。ただし、パラメータ化されたパスに対して上記で行われた他のすべてのコメントは引き続き適用されます。特に、そのような各パスは、それにプッシュダウンできる結合句を引き続き強制することが期待されるため、同じパラメータ化を持つすべてのパスは同じ行数を持ちます。

また、オプティマイザによる LATERAL サブクエリの平坦化（親クエリへのプルアップ）も許可されていますが、これは、そのクエリ条件のレベル以下にある最も低いアウター結合の外側にあるリレーションを参照するような lateral 参照を JOIN/ON 条件内に持ち込まない場合に限られます。そのような条件のセマンティクスは不明確になります。この制約があっても、LATERAL サブクエリのプルアップにより、構文上のスコープ外のリレーションに対する lateral 参照を含む PlaceHolderVar が作成される可能性があることに注意してください。私たちは引き続きそのような PHV をその構文上の場所またはそれ以下で評価しますが、プランノードの条件またはターゲットリストにそのような PHV が存在する場合、そのノードは、lateral 参照を提供するリレーションに対してネストループ結合の内側に現れる必要があります。（おそらく、その機能が動作するようになったので、プルアップの制約を緩和できるでしょうか？）

条件句に対するセキュリティレベルの制約

行レベルセキュリティとセキュリティバリアビューを効率的にサポートするため、条件句（RestrictInfo ノード）に "security_level" フィールドのマークを付けます。基本的な概念は、より低い security_level を持つ条件が、より高い security_level を持つ条件よりも先に評価されなければならないということです。これにより、機密データを露出させる可能性のある「漏洩しやすい（leaky）」条件が、セキュリティ機密行をフィルタリングすることになっているセキュリティバリア条件がチェックされるまで評価されないことが保証されます。しかし、多くの条件式は「漏洩防止（leakproof）」、つまり、それらが使用する関数がデータを露出させない信頼できるものです。不必要に非効率なプランを避けるため、たとえ別の条件よりも構文上の security_level が高くても、漏洩防止条件はセキュリティレベルの考慮によって遅延させられません。

RLS またはセキュリティバリアビューを使用しないクエリでは、すべての条件の security_level が 0 になるため、これらの制約はどれも機能しません。条件式の leakproof 性をチェックする必要さえないのです。

セキュリティバリア条件がある場合、それらの security_level は 0 になり（バリアのレイヤーが複数ある場合はさらに高くなる可能性があります）、クエリテキストからの通常の条件には、バリア条件に使用された最も高いレベルよりも 1 つ高い security_level が割り当てられます。

EquivalenceClass 処理によって新しい条件句が生成されるとき、それらに security_level を割り当てる必要があります。これが見た目以上に厄介です。最初に思い浮かぶ直感としては、EquivalenceClass のソース条件の中から見つかった最大のレベルを使用するのが安全であるということですが、それは全く安全ではありません。なぜなら、セキュリティバリア条件の不要な遅延を許容してしまうからです。バリア条件「t.x = t.y」に加えてクエリ条件「t.x = constant」があり、さらにバリア条件がチェックされる前に評価してはならない別のクエリ条件「leaky_function(t.z)」があると仮定します。 EC条件を「t.x = constant AND t.y = constant」に置き換えることになる EC {t.x, t.y, constant} が存在することになります（後者の条件により、元の条件からは決して発見できなかった t.y のインデックスの使用が可能になるため、この動作を諦めることも望みません）。これらの生成された条件にクエリ条件と同じ security_level が割り当てられた場合、leaky_function 条件が最初に評価され、leaky_function がバリア条件を通過しない可能性のある行のデータを見ることが可能になります。

代わりに、ECでのセキュリティレベルの処理は次のように機能します。

  • 条件が漏洩防止（leakproof）であるか security_level が 0 でない限り、そもそも EC のソース句として受け入れられません。
  • EC から派生した条件には、EC のソース句の中で見つかった最小の（最大ではない）security_level が割り当てられます。
  • EC のソース句で見つかった最大の security_level が 0 より大きい場合、派生条件に選択される等価演算子は漏洩防止でなければなりません。そのような演算子が見つからない場合、EC は「破損（broken）」として扱われ、追加の派生条件なしでソース句を出力することにフォールバックします。

これらのルールを合わせることで、信頼できない条件句（security_level が 0 より大きいもの）が EC に漏洩しやすい派生句を生成させないことが保証されます。これにより、派生句に対して最大ではなく最小の security_level を使用することが安全になります。これらのルールは、派生句を全く生成できないことにより、貧弱なプランをもたらす可能性がありますが、実際にはほとんどの btree 等価演算子が漏洩防止であるため、そのリスクはわずかです。また、レベルゼロの条件に対して例外を設けることにより、バリア条件が存在しない場合にプランの品質低下が発生しないことが保証されます。

すべての条件にセキュリティレベルが割り当てられたら、バリア条件の順序付け制約の強制は 2 つのルールに帰着します。

  • テーブルスキャンプランノードは、漏洩防止であるか、または同じプランノードで実行される予定の他のどの条件よりも高くない security_level を持たない限り、条件を早期実行のために選択してはなりません（たとえば、インデックススキャンのインデックス修飾子としてそれらを使用することなど）。（条件を早期実行のために選択しても問題ないかどうかをチェックするには、ユーティリティ関数 restriction_is_securely_promotable() を使用してください。）
  • 条件のリストの通常の実行は、同じセキュリティルールを満たす順序、すなわち、漏洩防止でない限り、より高い security_level が後で評価されなければならないという順序でそれらを実行しなければなりません。（これは createplan.c の order_qual_clauses() によって 1 つの場所で処理されます。）

order_qual_clauses() は、漏洩防止条件に対して正確に何をすべきかを決定するためにヒューリスティクスを使用します。通常、明確な理由なしに条件の順序を再並べ替えしないようにソートが安定していることに注意しながら、security_level、次にコスト順に条件をソートします。しかし、これにより、より高い security_level を持つ安価な条件の前に、非常に高価な条件が実行される結果になる可能性があります。 安価な条件が漏洩しやすい場合は選択の余地がありませんが、それが漏洩防止であれば、最初に置くことができます。漏洩防止条件は security_level が 0 であるかのようにソートすることを選択しますが、そのコストが 10 * cpu_operator_cost よりも低い場合に限られます。この制約は、高価な条件を漏洩防止であるという理由だけで最初に実行してしまうという逆の問題を緩和します。

結合条件のセキュリティレベルが混在する場合に、結合条件の安全な処理をサポートするためには追加のルールが必要になります。例えば、情報漏洩の恐れがあるより高いセキュリティレベルの条件が、より低いセキュリティレベルの他の条件よりも低い結合レベルで評価されるのを防ぐ必要があります。現在、セキュリティ優先の条件はRLSポリシーやセキュリティバリアビューからの単一テーブルの制限条件に限られ、セキュリティバリアビューのサブクエリは親クエリに平坦化されないため、これを考慮する必要はありません。したがって、セキュリティ優先の条件の強制はテーブルスキャンレベルでしか行われません。結合条件間でのセキュリティレベルの安全な処理に関する追加ルールがあれば、セキュリティバリアビューを親クエリに平坦化できるようになり、条件評価の必要な順序を維持しつつ、プランニングの柔軟性を高めることができるはずです。しかし、それは後の話になります。

スキャン/結合プランニングの後

ここまでは、スキャン/結合プランニング、つまりSQLクエリのFROM句とWHERE句の実装についてのみ議論してきました。しかし、プランナーはGROUP BY、集約、その他のクエリの上位機能に対処する方法も決定しなければなりません。多くの場合、これらのステップを実行する方法は複数あり、最適化の選択肢が存在します。これらのステップは、スキャン/結合プランニングと同様に、ステップを実行するさまざまな方法を表すPathを構築し、最もコストの低いPathを選択することによって処理されます。

すべてのPathには「親」としてのRelOptInfoが必要なため、これらの上位処理ステップの出力を表すRelOptInfoを作成します。これらのRelOptInfoはほとんどがダミーですが、そのpathlistリストには各ステップで有用とみなされたすべてのPathが保持されます。現在、上位プランニング中にこれらタイプの追加のRelOptInfoを作成する場合があります。

UPPERREL_SETOP UNION/INTERSECT/EXCEPTの結果（存在する場合） UPPERREL_PARTIAL_GROUP_AGG 部分的なグループ化/集約の結果（存在する場合） UPPERREL_GROUP_AGG グループ化/集約の結果（存在する場合） UPPERREL_WINDOW ウィンドウ関数の結果（存在する場合） UPPERREL_PARTIAL_DISTINCT 部分的な「SELECT DISTINCT」の結果（存在する場合） UPPERREL_DISTINCT 「SELECT DISTINCT」の結果（存在する場合） UPPERREL_ORDERED ORDER BYの結果（存在する場合） UPPERREL_FINAL 残りのトップレベルのアクションの結果（存在する場合）

UPPERREL_FINALは、最終的な処理ステップ（現在はLockRows (SELECT FOR UPDATE)、LIMIT/OFFSET、およびModifyTable）を表すために使用されます。これらのステップが実行される順序には柔軟性がないため、このステージをより細かく小分けする必要はありません。

これらの「上位リレーション」は、上記のUPPERREL列挙値とrelidsセットによって識別されます。これにより、同じ種類の上位リレーションを複数存在させることができます。同じ種類の上位リレーションを複数必要としない場合は、relidsにNULLを使用します。実際、現在ではrelidsセットは常にNULLであるため痕跡的なものとなっていますが、将来的には変更されることが想定されています。例えば、集合演算のプランニングにおいては、互いに競合するPathの特定のグループに結合されたリーフSELECTのどのサブセットをrelidsが表しているかを示すために、relidsが必要になる場合があります。

subquery_planner()の結果は、常にNULLのrelidsを持つUPPERREL_FINALリレーションに格納されたPathのセットとして返されます。他の種類の上位リレーションは、特定のクエリで必要な場合にのみ作成されます。

並列クエリと部分パス

並列クエリとは、クエリ全体またはクエリの一部によって実行される必要がある作業を分割し、その作業の一部を1つ以上のワーカープロセス（並列ワーカーと呼ばれる）によって実行できるようにするものです。並列ワーカーは動的バックグラウンドワーカーのサブタイプです。詳細な説明については src/backend/access/transam/README.parallel を参照してください。並列クエリに関する学術文献によると、並列実行戦略は本質的に2つのカテゴリに分けることができます。クエリの実行が複数のステージに分割され、各ステージが別々のプロセスによって処理されるパイプライン並列性と、データが複数のプロセス間で分割され、各プロセスがそのサブセットを処理するパーティション並列性です。しかし、文献によれば、パイプライン並列性による利得は、パイプラインのストールを回避することが難しいため、非常に限定的なことが多いとされています。そのため、現時点ではこの技術を使用するクエリプランの生成は試みていません。

代わりに、ベーステーブルがパーティション分割されていることを必要としないパーティション並列性に焦点を当てています。これに必要なのは、(1)リレーションに関与する少なくとも1つのベーステーブルからのデータを複数のプロセス間で分割する方法が存在すること、(2)各プロセスが独自のデータ部分を処理できるようにすること、そして(3)結果を収集することの3点のみです。要件(2)および(3)は、任意の数のワーカープロセスを起動し、そのすべてにおいて、また子プロセスがリーダーを忙しく保つのに十分なデータを生成していない場合はおそらくリーダーにおいても、単一の子プランを実行するエグゼキューターノードGather（またはGatherMerge）によって満たされます。要件(1)はテーブルスキャンノードによって処理されます。parallel_aware = trueを指定して呼び出された場合、このノードは実質的にブロック単位でテーブルをパーティション分割し、そのスキャンノードが実行される各ワーカーでリレーションからのタプルのサブセットを返します。

非並列アクセス方法で行うのと同様に、並列プランで使用できるアクセス戦略を表すPathを構築します。これらは本質的に非並列プランで使用可能な戦略と同じですが、重要な違いがあります。Gatherノードの下で実行されるパスは、すべての結果ではなく、各ワーカーにおけるクエリ結果のサブセットのみを返します。実際に実行できるパスを形成するには、Gatherノードの（かなり大きな）コストを考慮に入れる必要があります。このような理由などから、Gatherノードの下で実行することを意図したパス（各ワーカーで結果のサブセットのみを返すため「部分（partial）」パスと呼ぶ）は、通常のパスとは別々に保持する必要があります（RelOptInfoのpartial_pathlistと add_partial_path関数を参照してください）。

並列クエリを効果的にするための鍵の1つは、クエリのできるだけ多くを並列で実行することです。したがって、Gatherステージをプランのトップにできる限り近づくまで延期することが一般的に望ましいと予想されます。より多くの作業をGatherの下に押し下げることができるケースの範囲を広げ、（それらのコストを正確に算定することは）当分の間私たちを忙しさと共にあり続けるでしょう。

パーティション単位の結合（Partitionwise joins）

同様にパーティション分割された2つのテーブル間の結合は、結合するテーブルのパーティションキー間に等価結合条件が存在する場合、それらの一致するパーティション間の結合に分解できます。パーティションキー間の等価結合は、あるパーティション分割されたテーブル内の特定の行に対するすべての結合相手が、もう一方のパーティション分割されたテーブルの対応するパーティション内になければならないことを意味します。このため、パーティション分割されたテーブル間の結合を、一致するパーティション間の結合に分解することができます。結果として得られる結合は、結合するリレーションと同じ方法でパーティション分割されるため、パーティションキー間に等価結合条件を持つ、同様にパーティション分割されたテーブル間のN方向の結合を、その一致するパーティション間のN方向の結合に分解することができます。パーティション分割されたテーブル間の結合をそのパーティション間の結合に分解するこの手法は、パーティション単位の結合（partitionwise join）と呼ばれます。「パーティション分割されたリレーション」という用語は、パーティション分割されたテーブル、または互換性のあるパーティション分割されたテーブル間の結合のどちらに対しても使用します。

結合するリレーションのパーティション境界が正確に同じでない場合でも、高度なパーティションマッチングアルゴリズムを使用することで、パーティション単位の結合を適用できます。このアルゴリズムは、両方の結合リレーションについて、一方の結合リレーションのすべてのパーティションが、もう一方の結合リレーションの最大で1つのパーティションにのみ一致するかどうかをチェックします。そのような場合、結合リレーション間の結合を、一致するパーティション間の結合に分解できます。その後、結合リレーションをパーティション分割されたものとみなすことができます。このアルゴリズムは、結合を計算するためのパーティション単位の結合を可能にするために、一致するパーティションのペアと、結合リレーションのパーティション境界を生成します。このアルゴリズムは partition_bounds_merge() に実装されています。このようにパーティション分割されたとみなされるN方向の結合リレーションにおいて、すべての結合リレーションのペアがパーティション単位の結合を使用できるわけではありません。例えば、次のような場合です。

(A leftjoin B on (Pab)) innerjoin C on (Pac)

ここで、A、B、Cはパーティション分割されたテーブルであり、AはBおよびCと比較して余分なパーティションを持っています。結合 {A B} についてパーティション単位の結合を考慮する場合、Aの余分なパーティションにはヌル許容側に一致するパーティションがありません。これは、現在のパーティション単位の結合の実装では処理できないケースです。したがって、{A B} はパーティション分割されているとはみなされず、3方向の結合のために考慮される {A B} とCのペアはパーティション単位の結合を使用できません。一方、{A C} とBのペアはパーティション単位の結合を使用できます。なぜなら、{A C} は余分なパーティションを排除することでパーティション分割されているとみなされるためです（外部結合の順序変更に関する同一性1を参照してください）。N方向の結合でパーティション単位の結合を使用できるかどうかは、両方ともパーティション分割されておりパーティション単位の結合を使用できる、最初に現れた結合リレーションのペアに基づいて決定されます。

パーティション分割されたリレーションのパーティションプロパティは、その RelOptInfo に格納されます。パーティションキーのデータ型に関する情報は PartitionSchemeData 構造体に格納されます。プランナーは正準パーティションスキーム（異なる PartitionSchemeData オブジェクト）のリストを維持し、同じパーティションスキームを持つ任意の2つのパーティション分割されたリレーションの RelOptInfo が同じ PartitionSchemeData オブジェクトを指すようにします。これにより、PartitionSchemeData オブジェクトによって消費されるメモリが削減され、結合リレーションのパーティションスキームを簡単に比較できるようになります。

パーティション単位の集約/グループ化（Partitionwise aggregates/grouping）

GROUP BY句がすべてのパーティションキーを含んでいる場合、特定のグループに属するすべての行は単一のパーティションから来なければなりません。したがって、集約は各パーティションに対して完全に個別に実行できます。そうでない場合は、各パーティションに対して部分集約を計算し、個々のパーティションからの結果をアペンドした後に最終処理を行うことができます。パーティション分割されたリレーションに対する集約またはグループ化を、そのパーティションに対する集約またはグループ化に分解するこの手法は、パーティション単位の集約（partitionwise aggregation）と呼ばれます。特にパーティションキーがGROUP BY句と一致する場合、これは通常の方法よりも大幅に高速になる可能性があります。

積極的集約（Eager aggregation）

積極的集約は、集約を結合の向こう側に部分的にプッシュし、すべてのリレーションが結合された後にそれをファイナライズするクエリ最適化手法です。積極的集約により、結合への入力行数を削減できるため、結果としてより優れた全体的なプランが得られる可能性があります。

この変換が正しいことを証明するために、まず内部結合のみが関与するケースを考えます。この場合、FROM句のテーブルを2つのグループに分割します。少なくとも1つの集約列を含むグループと、集約列を全く含まないグループです。各グループは、そのグループ内のテーブルの直積によって形成される単一のリレーションとして扱うことができます。したがって、一般性を失うことなく、FROM句にはちょうど2つのリレーション、R1とR2が含まれていると仮定できます。ここで、R1はすべての集約列を含むリレーションを表し、R2は集約列を一切含まないリレーションを表します。

クエリが次の形式であるとします。

SELECT G, AGG(A) FROM R1 JOIN R2 ON J GROUP BY G;

ここで、GはR1および/またはR2の列を含む可能性のあるグループ化キーのセットです。AGG(A)はR1の列Aに対する集約関数です。JはR1とR2の間の結合条件です。

積極的集約の変換は次のようになります。

GROUP BY G, AGG(A) on (R1 JOIN R2 ON J)

GROUP BY G, AGG(agg_A) on ((GROUP BY G1, AGG(A) AS agg_A on R1) JOIN R2 ON J)

この等価性は、以下の条件下で成り立ちます。

1) AGGは分解可能（decomposable）です。つまり、部分集約（partial aggregation）とそれに続く最終集約（final aggregation）の2つの段階で計算できます。 2) R1の事前集約で使用される集合G1には以下が含まれます。

  • グルーピングキーGの一部であるR1のすべての列、および
  • 結合条件Jに現れるR1のすべての列。

    • 3) G1内の任意の列のグルーピング演算子は、結合条件Jでその列に使用される演算子と互換性がなければなりません。

G1には、グルーピングキーGまたは結合条件Jのいずれかに現れるR1のすべての列が含まれるため、互換性のある演算子が使用されていると仮定すると、各部分グループ内のすべての行は、グルーピングキーとR1からの結合に関連する列の両方について同一の値を持つことになります。その結果、部分グループ内の行は、集約への寄与および結合における動作の観点から区別がつきません。これにより、同じ部分グループ内のすべての行が同じ「運命」を共有することが保証されます。つまり、R2の特定の行に対して、すべてが一致するか、すべてが一致しないかのいずれかになります。集約関数AGGは分解可能であるため、結合の後に部分結果を集約すると、完全な結合の後に集約するのと同じ最終結果が得られ、クエリのセマンティクスが維持されます。証明終了（Q.E.D.）。

外部結合が存在する場合、結合順序の制約と外部結合におけるNULL拡張のセマンティクスにより、状況はより複雑になります。結合順序の制約のために、少なくとも1つの集約列を含むリレーションを単一のリレーションとして扱えない場合、部分集約パスは生成されず、したがってこの変換は適用できません。そうでない場合、R1を集約列をすべて含むリレーションとし、R2、R3、...を残りのリレーションとします。内部結合の場合から、前述の条件下で、以下の等価性が成り立ちます。

GROUP BY G, AGG(A) on (R1 JOIN R2 JOIN R3 ...)

GROUP BY G, AGG(agg_A) on ((GROUP BY G1, AGG(A) AS agg_A on R1) JOIN R2 JOIN R3 ...)

外部結合が関与する場合に正しさを維持するために、追加の条件が必要になります。

4) R1は、いかなる外部結合のNULL可能（nullable）側にあってはなりません。

この条件により、R1に対する部分集約が、外部結合によって導入されるNULL拡張された行を抑制しないことが保証されます。R1が外部結合のNULL可能側にある場合、外部結合によって生成されるNULL拡張された行は、部分集約を実行するときには利用できませんが、先行集約（eager aggregation）を行わないプランでは、これらの行は最上位の集約で利用可能です。この場合に部分集約を押し下げると、行が期待とは異なる方法でグループ化されたり、集約関数から不正確な値が生成されたりする可能性があります。

セミ結合（semi join）とアンチ結合（anti join）も同様の制限を課します。このような結合は、結合出力においてそのインナー（inner）側の行を保持しないため、インナー側で計算された部分集約は結合を生き残ることができず、最終集約によって結合されることもありません。したがって、部分集約をセミ/アンチ結合のインナー側に押し下げることはしません。（外部結合から変換されたアンチ結合はインナー側をNULL拡張するため、そのインナーリレーションは上記の外部結合条件によってすでに除外されています。ここで特に扱うケースは、EXISTS、IN、NOT EXISTS、またはNOT INサブリンクから形成されるものなど、インナー側をNULL拡張しないセミ/アンチ結合です。）

結合ツリーの構築中に、先行集約を適用できるかどうかを判断するために、各ベースリレーションまたは結合リレーションを評価します。実行可能な場合、「グループ化されたリレーション（grouped relation）」と呼ばれる個別のRelOptInfoを作成し、グループ化されていないパスの上にソートおよびハッシュされた部分集約パスを追加することで、グループ化されたパスを生成します。計画時間を制限するため、このステップでは最も安価な、または適切にソートされたグループ化されていないパスのみを考慮します。

グループ化されたパスを生成する別の方法は、グループ化されたリレーションとグループ化されていないリレーションを結合することです。2つのグループ化されたリレーションを結合することは、現在はサポートされていません。

計画時間をさらに制限するため、現在は、部分集約を行数の大幅な削減が得られる結合ツリー内の実行可能な最も低いレベルにのみ押し下げる戦略を採用しています。この戦略は、同じグループ化されたリレーションに対するすべてのグループ化されたパスが同じ行のセットを生成することを保証するのにも役立ちます。これは、プランナの基本的な前提をサポートするために重要です。

最上位の結合リレーションに対してグループ化されたリレーションを生成した場合、最後にそのパスを確定させる必要があります。最終的なパスは、通常の計画から構築されたパスと通常の方法で競合します。
