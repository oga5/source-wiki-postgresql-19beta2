src/backend/nodes/README

Node Structures ===============

Introduction ------------

Postgresは、パースツリー、プランツリー、およびエグゼキュータ状態ツリーを構成するために「ノード」タイプを使用します。このようなツリーに現れる可能性のあるすべてのオブジェクトは、ノードタイプとして宣言される必要があります。さらに、パース/プラン/実行ノードツリーの一部ではないいくつかのオブジェクトタイプも、識別目的でNodeTagを受け取ります。これは通常、同じポインタを介して複数のオブジェクトタイプを渡したいAPIに関与しているためです。

ノード構造体は、最初のフィールドがNodeTag型である、昔ながらのプレーンなC構造体です。「継承」は慣例によって実現されます。最初のフィールドは、代わりに別のノードタイプにすることもできます。

ノードタイプは通常、copyObject()によるコピー、equal()による比較、outNode()によるシリアライズ、およびnodeRead()によるデシリアライズのサポートを備えています。一部のクラスのNodeでは、これらのサポート関数のすべてが必要なわけではありません。たとえば、エグゼキュータ状態ノードは現在、それらのいずれも必要としません。システムに関する限り、出力関数と読み込み関数は、カタログに格納されるパースツリーに現れる可能性のあるノードタイプと、パラレルワーカーに渡すためにシリアライズされるプランツリーノードに対してのみ必要です。しかし、デバッグに非常に便利であるため、他のいくつかのノードタイプに対しても出力関数を提供しています。現在、このようなカバレッジは生のパースツリーとほとんどのプランナデータ構造に対して存在します。ただし、生のパースツリーの出力カバレッジは不完全です。特に、ユーティリティ文はほとんどサポートされていません。

Relevant Files --------------

ノード構造体を操作するためのユーティリティ関数は、このディレクトリにあります。一部のサポート関数はgen_node_support.plスクリプトによって自動生成され、その他の関数は手動でメンテナンスされます。サポート関数の自動生成を制御するために、ノードタイプとノードフィールドにpg_node_attr()仕様のアノテーションを付けることができます。詳細なドキュメントについてはsrc/include/nodes/nodes.hを参照してください。

FILES IN THIS DIRECTORY (src/backend/nodes/)

General-purpose node manipulation functions: copyfuncs.c - ノードツリーをコピーする (*) equalfuncs.c - 2つのノードツリーを比較する (*) outfuncs.c - ノードツリーをテキスト表現に変換する (*) readfuncs.c - テキスト表現をノードツリーに戻す (*) makefuncs.c - いくつかの一般的なノードタイプの作成関数 nodeFuncs.c - その他のいくつかの汎用操作関数 queryjumblefuncs.c - クエリジャンブリング用のノードツリーを計算する (*)

(*) - これらのファイルのほとんどの関数はgen_node_support.plによって生成され、そこで#includeされます。

Specialized manipulation functions: bitmapset.c - Bitmapsetのサポート list.c - 汎用リストのサポート multibitmapset.c - List-of-Bitmapsetのサポート params.c - Paramのサポート tidbitmap.c - TIDBitmapのサポート value.c - 値ノードのサポート

FILES IN src/include/nodes/

Node definitions primarily appear in: nodes.h - ノードタグ（NodeTag）を定義する (*) primnodes.h - プリミティブノード parsenodes.h - パースツリーノード pathnodes.h - パスツリーノードおよびプランナ内部構造体 plannodes.h - プランツリーノード execnodes.h - エグゼキュータノード memnodes.h - メモリノード pg_list.h - 汎用リスト

(*) - gen_node_support.plによって生成されたファイルも#includeします。

Steps to Add a Node -------------------

ノードFooを定義したいとします。

1. 適切なinclude/nodes/???.hファイルに構造体定義を追加します。 たとえばPlanノードから継承する場合は、構造体定義の最初のフィールドとしてPlanを配置します。（T_Fooタグは自動的に作成されます。） 2. copyfuncs.funcs.c、equalfuncs.funcs.c、outfuncs.funcs.c、queryjumblefuncs.funcs.c、およびreadfuncs.funcs.cで生成されたサポート関数が正しく見えるか確認します。必要に応じて属性を追加して結果を制御します。（一部のクラスのノードタイプでは、すべてのサポート関数が必要なわけではありません。関連するノードタイプと同様のノード属性を使用してください。） 3. 必要に応じてnodeFuncs.cの関数にcaseを追加します。新しいノードタイプについて認識させる必要がある場所は、他にもたくさんあるでしょう。触るべきすべての場所を見つけるための最善の方法は、1つか2つの類似した既存のノードタイプへの参照をgrepすることです。 （頻繁に作成されるノードを除き、makefuncs.cに作成関数をわざわざ書く必要はありません。） 4. debug_copy_parse_plan_trees、debug_write_read_parse_plan_trees、およびdebug_raw_expression_coverage_testを使用して新しいコードをテストし、必要なすべての場所にサポートが追加されていることを確認することを検討してください（たとえば、PG_TEST_INITDB_EXTRA_OPTS='-c debug_...=on'を指定してテストを実行します）。

新しいノードタイプを追加すると、既存のタグに関連付けられた数値が移動するため、これを行った後はツリー全体を再コンパイルする必要があります。（通常は--enable-dependが役立ちます。）ただし、数値がディスクに書き込まれることはないため、initdbは強制されません。しかし、ノードタイプの変更や削除は、通常、システムカタログに格納されているシリアライズされたノードツリーの解釈に影響を与えるため、initdbを強制するカタログバージョンの変更を伴う必要があります。（たとえばPlanノードのように、格納されたパースツリーにノードタイプが一切現れない場合は、それを変更するためにcatversionの変更は必要ありません。）
