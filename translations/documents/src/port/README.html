src/port/README

libpgport

libpgport は特別な動作をする必要があります。ライブラリとアプリケーションの両方に機能を提供するためです。しかし、2つの複雑な点があります:

1) ライブラリは、ライブラリとまったく同じフラグでコンパイルされたオブジェクトファイルを使用する必要があります。libpgport は同じフラグを使用しない可能性があるため、個々のライブラリ用にオブジェクトファイルを再コンパイルする必要があります。これを行うには、リンク行から -lpgport を削除します:

# Need to recompile any libpgport object files LIBS := $(filter-out -lpgport, $(LIBS))

そして、オブジェクトファイルを再コンパイルするためのインフラストラクチャを追加します:

OBJS= execute.o typename.o descriptor.o data.o error.o prepare.o memory.o \ connect.o misc.o path.o exec.o \ $(filter strlcat.o, $(LIBOBJS))

問題は、どのオブジェクトファイルを追加する必要があるかのテストが行われないことですが、不足している機能は通常、ユーザーアプリケーションのリンク時に判明します。

2) アプリケーションの場合は、-lpq の前に -lpgport を使用するため、libpgport からの静的ファイルが最初にリンクされます。これにより、アプリケーションが libpq によって *使用* されるものの libpq からエクスポートされることを意図していないシンボルに依存するのを防ぎます。libpq の libpgport の使用方法は時間の経過とともに変化するため、そのような依存関係は問題になります。Windows、Linux、AIX、および macOS では、エクスポートリストを使用して libpq がエクスポートするシンボルを制御しています。
