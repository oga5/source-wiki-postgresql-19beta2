src/test/isolation/README

Isolation tests ===============

このディレクトリには、PostgreSQLにおける同時実行動作のテストセットが含まれています。これらのテストは、相互に作用する複数のトランザクションを実行する必要があり、これには複数の同時接続の管理が必要となるため、通常の pg_regress プログラムを使用してテストすることはできません。「isolation」という名前は、元々の動機がシリアライザブル（serializable）分離レベルをテストすることであった事実に由来していますが、他の種類の同時実行動作のテストも追加されています。

現在のビルドツリーに対してテストを実行するには、以下を入力します。 make check あるいは、既存のインストールに対して実行するには、以下を入力します。 make installcheck （これは、libpqが想定するデフォルトのポートでサーバーに接続します。これを制御するために、環境変数で PGPORT などを設定できます。）

インストールされたサーバーに対して特定のテストのみを実行するには、以下のようにします。 ./pg_isolation_regress fk-contention fk-deadlock （利用可能なテストについては specs/ サブディレクトリを確認してください）。

一部のテストでは、サーバーの max_prepared_transactions パラメータが少なくとも3に設定されている必要があります。そのため、これらはデフォルトでは実行されません。テスト実行にこれらを含めるには、サーバー設定が正しいことを確認した上で、以下を使用します。 make check-prepared-txns または make installcheck-prepared-txns （「check」の場合にこれを調整するには TEMP_CONFIG を参照してください）。

重複するトランザクションを伴うテストを定義するために、カスタム構文を使用したテスト仕様ファイルを使用します。これについては次のセクションで説明します。新しいテストを追加するには、specs/ サブディレクトリにスペックファイルを配置し、expected/ サブディレクトリに期待される出力を追加し、isolation_schedule ファイルにテスト名を追加します。

isolationtester は、libpq を使用して複数の接続を開き、スペックファイルで指定されたテストを実行するプログラムです。libpq 接続文字列は、接続先のサーバーとデータベースを指定します。それ以外の場合は、環境変数から派生したデフォルト値が使用されます。

pg_isolation_regress は pg_regress に類似したツールですが、テストの実行に psql を使用する代わりに isolationtester を使用します。pg_regress とまったく同じコマンドライン引数を受け入れます。

デフォルトでは、isolationtester は任意の1つのテストステップが完了するまで最大360秒（6分）待機します。これを調整する必要がある場合は、環境変数 PG_TEST_TIMEOUT_DEFAULT に、希望するタイムアウト（秒単位）の半分の値を設定します。

Test specification ==================

各アイソレーションテストは、specs サブディレクトリに保存されている仕様ファイルによって定義されます。テスト仕様は、いくつかのSQL「ステップ」を定義し、それらを「セッション」（1つのセッションのすべてのステップが同じバックエンドで実行されます）にグループ化し、実行されるステップの「順列（permutations）」または順序を指定します。

テスト仕様は、以下の順序で4つの部分から構成されます。

setup { <SQL> }

指定されたSQLブロックは、テストを実行する前に（順列ごとに）1回実行されます。テスト用のテーブルやその他の必要なオブジェクトはここで作成します。この部分は任意です。必要に応じて複数の setup ブロックを使用できます。それぞれは指定された順序で個別に実行されます。（複数の setup ブロックが許可されている理由は、各ブロックが単一の PQexec 送信として実行され、VACUUM などの一部のステートメントは、そのようなブロック内で他のステートメントと組み合わせることができないためです。）

teardown { <SQL> }

teardown SQLブロックは、テスト終了後に1回実行されます。これを使用して、次の順列の準備としてクリーンアップを行います（例：setup で作成されたテストテーブルのドロップなど）。この部分は任意です。

session <name>

通常、スペックファイルには複数の「session」部分があります。各セッションは独自の接続で実行されます。セッション部分は、setup、teardown、および1つ以上の「step」の3つの部分から構成されます。セッションごとの setup および teardown 部分は、上述のテストごとの setup および teardown と同じ構文ですが、各セッション内で実行されます。例えば、setup 部分にはトランザクションを開始するための「BEGIN」コマンドを含めることができます。

各ステップの構文は以下の通りです。

step <name> { <SQL> }

ここで、<name> はこのステップを識別する名前であり、<SQL> はステップ内で実行されるSQLステートメント（またはセミコロンで区切られた複数のステートメント）です。ステップ名は、スペックファイル全体で一意である必要があります。

permutation <step name> ...

permutation 行は、その順序で実行されるステップのリストを指定します。任意の数の permutation 行を記述できます。permutation 行が指定されていない場合、テストプログラムは各セッションからのステップのすべての可能なインターリーブ（任意の1つのセッションのステップを順番に実行する）を自動的に実行します。手動で指定された「permutation」行のステップリストは、実際には利用可能なステップの順列である必要はないことに注意してください。例えば、一部のステップを複数回繰り返したり、他のステップを除外したりすることができます。また、各ステップ名には、以下で説明する括弧で囲まれたいくつかのマーカーを注記することができます。

セッション名とステップ名は、プレーンまたはダブルクォーテーションで囲まれたSQL識別子です。標準SQLとの違いは、大文字小文字の変換が行われないことです。そのため、クォーテーションで囲むかどうかに関わらず、FOO と "FOO" は同じ名前ですが、FOO と Foo は異なる名前になります。アイソレーションテストのキーワード（「permutation」など）を名前として使用する場合は、クォーテーションを使用する必要があります。

「#」文字はコメントの開始を表し、行末まで続きます。（ただし、これは <SQL> ブロック内では機能しません。そこでは通常のSQLコメント規則を使用してください。）

<SQL> ブロック内に「}」文字を含める方法はありません。

セッションステップの各順列（スペックファイルで手動で指定されたもの、または自動生成されたもののいずれであっても）について、isolation tester はメインの setup 部分、次にセッションごとの setup 部分、次に選択されたセッションステップ、次にセッションごとの teardown、最後にメインの teardown スクリプトを実行します。選択された各ステップは、そのセッションに関連付けられた接続に送信されます。メインの setup および teardown スクリプトは、別の「control」セッションで実行されます。

Support for blocking commands =============================

各ステップには、さらなるアクションが実行されるまでブロックするコマンドが含まれる場合があります（多くの場合、他のセッションがそのブロックを解除するステップを実行するか、デッドロックを引き起こします）。この機能を使用するテストは、有効な順列、すなわちブロックされたセッションがコマンドを実行することを想定しない順列を手動で指定する必要があります。テストがそのルールに従わない場合、isolationtester は 2 * PG_TEST_TIMEOUT_DEFAULT 秒後にそれをキャンセルします。キャンセルが機能しない場合、isolationtester は合計 4 * PG_TEST_TIMEOUT_DEFAULT 秒後に異常終了します。無効な順列のテストは、アイソレーションテストの実行に非常に長い時間がかかる可能性があり、有用なテスト目的を果たさないため、避けるべきです。

isolationtester は、pg_locks ビューで待機中（waiting）として表示されているかどうかを確認することによってコマンドがブロックされたことを認識することに注意してください。したがって、ヘビーウェイトロック（heavyweight locks）でのブロックのみが検出されます。

Dealing with race conditions ============================

場合によっては、タイミングの問題により、テストスクリプトに対する isolationtester の出力が変化することがあります。これに対処する1つの方法は、バリアントの期待値ファイル（expected-files）を作成することです。これは、foo.spec のバリアントが foo_1.out、foo_2.out などの名前になるという通常のPGの慣例に従います。しかし、余分なファイルはメンテナンスの邪魔になるため、この方法は推奨されません。代わりに、permutation 行にリストされている一部のステップ名に特別なマーカーを適用することで、通常はテスト出力を安定させることができます。

順列エントリの一般的な形式は以下の通りです。

<step name> [ ( <marker> [ , <marker> ... ] ) ]

ここで、各マーカーは「ブロッキング条件」を定義します。すべてのブロッキング条件が満たされるまで、そのステップは完了したと報告されません。使用可能なマーカーは以下の通りです。

* <other step name> <other step name> notices <n>

mystep(*) などのアスタリスクマーカーは、後で待機中として検出されるかどうかに関わらず、ステップが起動されるとすぐに isolationtester にそのステップを「待機中（waiting）」として報告させます。これは、ステップの速度と isolationtester のステータス監視クエリの相対的な速度に応じて、待機中と報告されることもあれば、即座に完了したと報告されることもあるケースを安定させるのに役立ちます。

ステップ名のみで構成されるマーカーは、その他方のステップが完了するまで、このステップが完了したと報告されないことを示します。これにより、2つのクエリがどちらの順序でも完了するように見えるケースを安定させることができます。このステップは、他方のステップが完了する前に*起動*できることに注意してください。（現在の順列で他方のステップが複数回使用されている場合、それらのインスタンスのいずれかがアクティブである間、このステップは完了できません。）

「<other step name> notices <n>」（ここで <n> は正の整数）という形式のマーカーは、このステップが起動された時点から数えて、他方のステップのセッションが少なくとも <n> 個の NOTICE メッセージを返すまで、このステップが完了したと報告されないことを示します。これは、ステップが実際に完了する前に NOTICE メッセージを返すことがあり、それらのメッセージを他のステップの完了と同期させる必要があるケースを安定させるのに役立ちます。

これらのマーカーはステップの完了の報告を遅らせるだけであり、ステップの起動を遅らせることはできないことに注意してください。isolationtester は、(A) 同じセッションのすべての前のステップが完了し、かつ (B) 順列内の直前のステップが完了したか、またはブロックされたとみなされた時点で、すぐに順列内の次のステップを起動します。この目的において、「ブロックされたとみなされる」とは、データベースロックで待機していることが確認されたか、あるいは完了しているがその完了報告がこれらのマーカーのいずれかによって遅延されていることを意味します。

場合によっては、ブロックされたとみなされた可能性のある別のセッションのステップが完了するまで、ステップを起動しないことが重要です。例えば、セッションAのステップ s1 がセッションBのステップ s2 に対するキャンセルを発行している場合、s1 が確実に完了するまでBの次のステップを起動しない方がよいでしょう。s1 がブロック可能である場合、問題が発生する可能性があります。それを防ぐ最善の方法は、セッションAに空のステップを作成し、次のセッションBのステップの直前に、マーカーなしでそれを実行することです。空のステップは s1 が完了するまで起動できず、その結果、次のセッションBのステップは空のステップが終了するまで起動できません。
