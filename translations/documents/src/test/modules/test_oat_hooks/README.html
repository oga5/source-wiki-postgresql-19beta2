概要 ========

このテストモジュール「test_oat_hooks」は、オブジェクトアクセスフック（OAT）を使用して強制アクセス制御（MAC）を適用する方法の例です。

テスト戦略は次のとおりです。このモジュールがロードされると、さまざまなタイプのフックを登録します（以下を参照）。各フックを制御するためのGUCが定義されており、フックが起動されたアクションを許可するか拒否するかを決定します。もう1つの追加のGUCが、フックの冗長性を制御します。GUCのデフォルトはpermissive/quietであり、これにより、レグレーションテストが開始されるまでの間にログにノイズを生成したり、アクティビティを拒否したりすることなく、モジュールをロードできます。テストが開始されると、SETコマンドを使用してロギングを有効にし、各フックの寛容/制限動作を制御します。スーパーユーザと一般ユーザの両方の権限で、さまざまなSQLステートメントが実行されます。出力は期待される出力と比較され、フックが期待通りの順序で動作し、起動されたことを検証します。

ユーザはOATフックに対する他のシステムフックの起動順序を気にする可能性があるため、このモジュールではProcessUtilityフックとExecutorCheckPermsフックも登録され、独自のロギングと許可/拒否動作を備えています。

SUSET test configuration GUCs =============================

以下の設定パラメータ（GUC）は、このテストモジュールのObject Access Type（OAT）、Process Utility、およびExecutor Check Permissionsフックを制御します。一般的なパターンとして、各フックには対応するGUCがあり、フックが呼び出された操作を許可するか拒否するかを制御します。実際のOATフックは、単なる「allow-all」対「deny-all」よりもきめ細かな制御を提供するべきですが、テスト用としてはこれで十分です。

これらのフックがアクションを許可した場合でも、コアの権限システムがアクションを拒否する可能性があることに注意してください。コアの権限システムに対するフックの起動順序は、アクションが拒否される前にどのNOTICEメッセージが出力されるかから推測できます。

各フックは、スーパーユーザ以外のユーザによって実行されるすべての操作に対して、許可または拒否の設定を適用します。

  • test_oat_hooks.deny_set_variable

object_access_hook_str MAC関数が、設定パラメータを設定する試みを拒否するかどうかを制御します。

  • test_oat_hooks.deny_alter_system

object_access_hook_str MAC関数が、設定パラメータを設定するalter systemの試みを拒否するかどうかを制御します。

  • test_oat_hooks.deny_object_access

object_access_hook MAC関数が、呼び出されたすべての操作を拒否するかどうかを制御します。

  • test_oat_hooks.deny_exec_perms

exec_check_perms MAC関数が、呼び出されたすべての操作を拒否するかどうかを制御します。

  • test_oat_hooks.deny_utility_commands

ProcessUtility_hook関数が、呼び出されたすべての操作を拒否するかどうかを制御します。

  • test_oat_hooks.audit

各フックが、試行ごとに成功または失敗のステータスとともにNOTICEメッセージをログに記録するかどうかを制御します。このGUCをクリアまたは設定すること自体が、新しい設定が有効になる前（ただし後ではない）、または後（ただし前ではない）に表示されるNOTICEメッセージを生成する場合があることに注意してください。

Functions =========

モジュールは、以下の名前でフックを登録します：

  • REGRESS_object_access_hook
  • REGRESS_object_access_hook_str
  • REGRESS_exec_check_perms
  • REGRESS_utility_command
