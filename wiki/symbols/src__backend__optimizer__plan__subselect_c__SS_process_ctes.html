Assert(root->cte_plan_ids == NIL);

foreach(lc, root->parse->cteList) { CommonTableExpr *cte = (CommonTableExpr *) lfirst(lc); CmdType cmdType = ((Query *) cte->ctequery)->commandType; Query *subquery; PlannerInfo *subroot; RelOptInfo *final_rel; Path *best_path; Plan *plan; SubPlan *splan; int paramid;

/*

  • Ignore SELECT CTEs that are not actually referenced anywhere.

    • */ if (cte->cterefcount == 0 && cmdType == CMD_SELECT) { /* Make a dummy entry in cte_plan_ids */ root->cte_plan_ids = lappend_int(root->cte_plan_ids, -1); continue; }

/*

  • Consider inlining the CTE (creating RTE_SUBQUERY RTE(s)) instead of
  • implementing it as a separately-planned CTE.

    • *

  • We cannot inline if any of these conditions hold:

    • *

  • 1. The user said not to (the CTEMaterializeAlways option).

    • *

  • 2. The CTE is recursive.

    • *

  • 3. The CTE has side-effects; this includes either not being a plain
  • SELECT, or containing volatile functions. Inlining might change
  • the side-effects, which would be bad.

    • *

  • 4. The CTE is multiply-referenced and contains a self-reference to
  • a recursive CTE outside itself. Inlining would result in multiple
  • recursive self-references, which we don't support.

    • *

  • Otherwise, we have an option whether to inline or not. That should
  • always be a win if there's just a single reference, but if the CTE
  • is multiply-referenced then it's unclear: inlining adds duplicate
  • computations, but the ability to absorb restrictions from the outer
  • query level could outweigh that. We do not have nearly enough
  • information at this point to tell whether that's true, so we let
  • the user express a preference. Our default behavior is to inline
  • only singly-referenced CTEs, but a CTE marked CTEMaterializeNever
  • will be inlined even if multiply referenced.

    • *

  • Note: we check for volatile functions last, because that's more
  • expensive than the other tests needed.

    • */ ~~~

目的

クエリの WITH リスト（CTE）を走査し、各共通表式（CTE）をインライン展開するか、あるいは独立した InitPlan（CTE_SUBLINK）として計画を作成・登録するかを決定し処理する。

入力と出力

  • 引数: PlannerInfo *root
  • 戻り値: なし (void)

前提条件と不変条件

  • 処理開始時、root->cte_plan_ids は NIL であること。
  • 現在のクエリレベルでは plan_params が使用されていないこと。

アルゴリズムまたは振る舞い

1. **ループ処理**: root->parse->cteList 内の各 CommonTableExpr エントリを foreach ループで順に走査する。 2. **未使用 SELECT CTE のスキップ**:

  • 参照回数 (cterefcount) が 0 であり、かつコマンド種別が CMD_SELECT の場合、インライン化や計画作成を行わない。
  • root->cte_plan_ids にダミーのエントリ -1 を追加して次の反復へ進む。

    • 3. **インライン化の判定**:

  • 以下の条件をすべて満たす場合、CTE を RTE_SUBQUERY として親クエリにインライン展開する。
  • ユーザー指定が CTEMaterializeNever、またはデフォルト（CTEMaterializeDefault）かつ参照回数が 1 であること。
  • 再帰的（cterecursive）ではないこと。
  • コマンド種別がプレーンな CMD_SELECT であること。
  • DML を含まないこと (!contain_dml)。
  • 参照回数が 1 以下であるか、あるいは外部への再帰的自己参照を含まないこと (!contain_outer_selfref)。
  • volatile 関数を含まないこと (!contain_volatile_functions)。
  • インライン化された場合は inline_cte(root, cte) を呼び出し、root->cte_plan_ids に -1 を追加して次へ進む。

    • 4. **独立した CTE プランの生成**:

  • ソースの Query ノードをコピーする。
  • subquery_planner を呼び出して CTE クエリのパスとサブプランナ情報（subroot）を生成する。
  • fetch_upper_rel および create_plan を用いて、最安パスから実行プラン (Plan) を構築する。

    • 5. **SubPlan ノードの構築と登録**:

  • SubPlan ノード（splan）を新しく割り当て、subLinkType = CTE_SUBLINK や列型情報を設定する。
  • assign_special_exec_param でパラメータ ID を割り当て、splan->setParam に登録する。
  • 生成された plan、best_path、subroot をそれぞれ root->glob の対応するグローバルリストに付加する。
  • splan を root->init_plans に追加し、そのプラン ID を root->cte_plan_ids に記録する。
  • 最後に cost_subplan を呼び出してコスト見積もりを埋める。

失敗モードと境界条件

  • クエリのプラン作成中に予期せぬ外部参照が検出され root->plan_params が非 NIL になった場合、elog(ERROR) によりエラーを送出する。
