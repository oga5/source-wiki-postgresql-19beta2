src/backend/optimizer/path/allpaths.c

概要

src/backend/optimizer/path/allpaths.c は、PostgreSQLオプティマイザにおいてクエリ処理のための可能な検索パス（Access Paths）を発見・構築する中心的なルーチン群を所有する。クエリのすべてのベースリレーションおよび結合ツリー全体に対するパス生成のエントリポイントを提供し、パーティション分割テーブル、継承関係、サブクエリ、各種RTE（Range Table Entry）、およびプッシュダウン制約の評価を管理する。

モジュール内での役割

src/backend/optimizer/path サブシステム内において、本ファイルは個別のリレーションに対するサイズ見積もりとパス構築の調整役を務める。隣接する costsize.c（コスト計算）、indxpath.c（インデックスパス生成）、joinpath.c（結合パス生成）などと連携し、生成されたパス群に対してプラグイン（set_rel_pathlist_hook や join_search_hook）の介入機会を提供しつつ、最終的な結合探索（standard_join_search）へ繋げる。

責務

  • ベースリレーション・初期処理: クエリ内の全ベースリレーションに対し、ファストスタートの考慮、サイズ見積もり（行数・幅）、パラレル実行可能性の判定を統括する。
  • 多様なRTE型のパス生成: 通常のテーブル、外部テーブル、サンプリング、継承/パーティション、サブクエリ、関数、VALUES、CTE、名前付きタプルストア、Result等に応じたサイズおよびパス構築関数への振り分けを行う。
  • アペンドおよびマージアペンドパスの管理: 継承テーブルやパーティションテーブルにおける子リレーション群のパスを集約し、通常の Append、Parallel Append、MergeAppend、および順序付きアペンドパスを構築する。
  • サブクエリのプッシュダウン解析と最適化: サブクエリに対する WHERE や HAVING 句の安全なプッシュダウン（subquery_is_pushdown_safe、qual_is_pushdown_safe）および未使用出力列の削除を管理する。
  • 結合探索の駆動: ジョインリスト（joinlist）を元にした単一リレーションの構築（make_one_rel）と動的計画法による標準結合探索（standard_join_search）を統括する。

重要なシンボル

コアエントリポイント・探索制御

  • function make_one_rel: クエリ全体のjoinlistを受け取り、ベースリレーションのサイズ見積もり、アペンド/グループ関係の構築、および make_rel_from_joinlist を通じた全体の結合パス探索を実行して単一の最適化された RelOptInfo を返す。
  • function standard_join_search: 動子計画法を用いた標準的な結合探索を行う。levels_needed に従ってレベルごとに join_search_one_level を呼び出し、パーティション分割結合パスやGatherパスを生成して最上位の結合リレーションを導出する。

ベースリレーション・サイズ見積もり

  • function set_base_rel_consider_startup: セミ/アンチ結合のRHSにある単一ベースリレーションに対して consider_param_startup フラグを有効化し、ファストスタート計画の検討を促す。
  • function set_base_rel_sizes: 各ベースリレーション（RELOPT_BASEREL）に対して並列実行の適格性を判定した上でサイズ見積もり（set_rel_size）を実行する。
  • function setup_simple_grouped_rels: 集約式およびグループ化式が存在する場合に、オプティマイザが事前集約（eager aggregation）用の単純グループ化リレーションを構築する。
  • function set_base_rel_pathlists: 各ベースリレーションに対するスキャンパス（シーケンシャルスキャン、インデックススキャン等）のリストを構築する。

サブクエリプッシュダウン・安全性検証

  • struct pushdown_safety_info: サブクエリのターゲットリスト列が条件プッシュダウンに対して安全であるかの理由をビットマスク（unsafeFlags）および volatile/leaky のフラグで追跡するワークスペース構造体。
  • enum pushdown_safe_type: クエリ条件がサブクエリへのプッシュダウンに対して安全か（PUSHDOWN_SAFE）、安全でないか（PUSHDOWN_UNSAFE）、またはWindowClauseの実行条件として機能するか（PUSHDOWN_WINDOWCLAUSE_RUNCOND）を表す列挙型。
  • function HAVING: （※文脈上のシンボル参照）SQLの HAVING 句に関する処理やグループ化の文脈に関与する内部概念またはマクロ/関数参照のプレースホルダ。
  • function WHERE: （※文脈上のシンボル参照）SQLの WHERE 句の処理や条件プッシュダウン対象の述語評価に関与する概念。
  • function RelOptInfo: （※インデックスシンボル）クエリ内のリレーション（ベース、結合、アペンド等）のメタデータ、パスリスト、コスト、サイズ見積もりを保持するコアデータ構造。
  • function RestrictInfo: （※インデックスシンボル）修飾句（制約・結合条件）のラップ構造体。

制御フローとデータフロー

1. 初期化とサイズ見積もりフェーズ:

  • make_one_rel() が呼び出されると、set_base_rel_consider_startup() で高速起動プランの対象をマークし、set_base_rel_sizes() で各ベースリレーションの行数・幅を見積もる。
  • 継承テーブルやパーティションテーブルの場合は、set_append_rel_size() が再帰的に呼び出され、子リレーションのサイズ集約と制約除外（Constraint Exclusion）による不要な子除外が行われる。

    • 2. パス生成フェーズ:

  • set_base_rel_pathlists() により各ベースリレーションのアクセスパス（SeqScan, IndexScan, ForeignScanなど）が生成される。
  • サブクエリRTEの場合、set_subquery_pathlist() 内でサブクエリの複製が行われ、安全性が検証された上で上位の制限句がサブクエリ側へプッシュダウン（subquery_push_qual）される。その後、サブプランが計画され、SubqueryScanPath が親リレーションに追加される。

    • 3. 結合およびグループ化フェーズ:

  • make_rel_from_joinlist() が joinlist を解析し、1つの場合はそのまま、複数の場合は standard_join_search()（またはGEQO / プラグイン）へ移行する。
  • standard_join_search() は動的計画法のループ（レベル 2 から levels_needed まで）を実行し、各レベルの結合リレーションに対してパーティション分割結合パス（generate_partitionwise_join_paths）やGatherパス（generate_useful_gather_paths）、グループ化パス（generate_grouped_paths）を付与して最適経路を選択する。

読者向けメモ

  • メモリ管理とライフタイム: プライニング処理中に作成される Query 構造体の複製（サブクエリの処理時）や safetyInfo->unsafeFlags などのアロケーションは、適切なMemoryContext（通常はPlannerContext）上で管理される。不要になった作業用メモリは適宜 pfree される。
  • 制約除外とダミーリレーション: relation_excluded_by_constraints により不要と判定されたリレーションは、空の AppendPath を持つダミーリレーション（IS_DUMMY_REL）としてマークされ、以後のパス生成から除外される。
  • 並列処理の制約: consider_parallel フラグは、一時テーブル、並列制限付き関数、非安全なFDW、または安全でないリスト/結合条件が含まれない場合にのみ有効化され、Gather / Gather Merge パスの生成に利用される。
