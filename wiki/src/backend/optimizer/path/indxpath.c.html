src/backend/optimizer/path/indxpath.c

概要

src/backend/optimizer/path/indxpath.c は、PostgreSQLのオプティマイザサブシステムにおいて、与えたリレーションに対して利用可能なインデックスを判定し、IndexPath や各種ビットマップパス（BitmapIndexScan, BitmapHeapPath, BitmapAndPath, BitmapOrPath）を生成するコアロジックを所有する大規模なソースファイルである。クエリの制限条件（Restriction）、結合条件（Join）、同値クラス（EquivalenceClass）、およびソート順序（PathKeys）や部分インデックス述語（Partial Index Predicates）を検査・照合し、最適なインデックスアクセス経路を構築する。

モジュール内での役割

src/backend/optimizer/path ディレクトリの中で、本ファイルはクエリの WHERE 節や結合条件を特定のインデックスの列や式にマッピングする処理を担当する。前段の allpaths.c や equivclass.c が生成した情報や RelOptInfo を受け取り、後続のコスト見積もり（costsize.c）およびパス選択フェーズに渡すインデックスパス群の基盤を提供する。

責務

  • **インデックスパスの生成**: リレーションの indexlist に含まれる各インデックスについて、制限条件や結合条件を満たす IndexPath や並行インデックススキャン（Parallel Index Scan）の候補を構築する。
  • **条件照合（Clause Matching）**: 制限条件、結合条件、EquivalenceClass、Boolean式、OpExpr、FuncExpr、ScalarArrayOpExpr（SAOP）、RowCompareExpr、NullTestなどを対象インデックスのキー列にマッチさせる。
  • **ビットマップパスの構成**: BitmapAndPath や BitmapOrPath を生成するため、複数のインデックスパスやOR句の枝を統合し、重複の排除やコストに基づいた最適化（choose_bitmap_and）を行う。
  • **部分インデックスの評価**: check_index_predicates により、部分インデックスの述語がクエリの条件によって満たされているか（predOK）を検証する。
  • **一意性判定**: relation_has_unique_index_for を通じて、指定された関係が等価条件により最大1行に絞り込まれるかを判定する。

重要なシンボル

列挙型・データ構造

  • ScanTypeControl: インデックススキャン種別を制御する列挙型（ST_INDEXSCAN: amgettuple 必須, ST_BITMAPSCAN: amgetbitmap 必須, ST_ANYSCAN: どちらでも可）。
  • IndexClauseSet: 各インデックス列（INDEX_MAX_KEYS）ごとの IndexClause リストを保持し、空でないかを管理する構造体。
  • PathClauseUsage: choose_bitmap_and() 内でパスが使用するWHERE句や述語を保持・分類する構造体。
  • ec_member_matches_arg: ec_member_matches_indexcol コールバック用の引数構造体。
  • OrArgIndexMatch: group_similar_or_args() で類似したOR句の引数とインデックス列のマッチング情報を保持する構造体。

主要エントリーポイント関数

  • create_index_paths(PlannerInfo *root, RelOptInfo *rel): リレーションのインデックスリストを走査し、通常およびパラメータ化されたインデックスパス、ビットマップパスを生成して add_path に登録する主入口。
  • check_index_predicates(PlannerInfo *root, RelOptInfo *rel): リレーションの各部分インデックスの述語が満たされているかを検証し、predOK および indrestrictinfo を設定する。
  • relation_has_unique_index_for(PlannerInfo *root, RelOptInfo *rel, List *restrictlist, List **extra_clauses): リレーションが一意インデックスによって高々1行に限定されるかを判定する。
  • match_index_to_operand(Node *operand, int indexcol, IndexOptInfo *index): インデックスのキー/式とクエリ側のオペランド（Var等）との一致を汎用的に判定する（selfuncs.c でも使用）。

条件マッチング・パス構築ヘルパー関数

  • match_clause_to_indexcol(...) / match_opclause_to_indexcol(...) / match_funcclause_to_indexcol(...): 各種式（演算子、関数、SAOP、行比較、OR等）をインデックス列にマッピング。
  • build_index_paths(...): 指定されたインデックスと句のセットから、正順・逆順・並行の IndexPath リストを構築。
  • generate_bitmap_or_paths(...): OR句から BitmapOrPath を生成。
  • choose_bitmap_and(...): 複数のビットマップパスから最適なサブセットを選び、重複排除とコスト比較を経て単一のパス（または BitmapAndPath）を返す。

制御フローとデータフロー

1. **初期スキャン**: create_index_paths が呼び出されると、リレーションの rel->indexlist 内の各インデックスをループ処理する。 2. **制限条件のマッチング**: match_restriction_clauses_to_index により、ベースリレーションの制限条件をインデックス列に照合し、IndexClauseSet（rclauseset）を構築する。 3. **パスの構築 (非パラメータ化)**: get_index_paths を経由して build_index_paths を呼び出し、利用可能なインデックススキャンパスを生成する。得られたパスのうち、amhasgettuple を満たすものは add_path でリレーションに追加され、ビットマップ対応のものは bitindexpaths に蓄積される。 4. **結合条件・EquivalenceClassのマッチング**: 自由結合条件および同値クラスから導出される結合条件を match_join_clauses_to_index および match_eclass_clauses_to_index で収集し、consider_index_join_clauses を通じてパラメータ化されたインデックスパスを生成する。 5. **OR句の処理**: generate_bitmap_or_paths および group_similar_or_args により、OR条件や類似引数をグループ化し、ビットマップORパスを生成する。 6. **ビットマップANDの統合**: 蓄積されたビットマップパス群は choose_bitmap_and に送られ、冗長なパスの除去、コスト昇順ソート、およびコスト削減効果に基づく AND 結合（BitmapAndPath）の選択が行われる。最終的な BitmapHeapPath が add_path に登録される。

読者向けメモ

  • **メモリ管理**: プランナのメモリコンテキスト（PlannerContext）上で動作し、大量のリスト（List）やビットマップセット（Bitmapset）を動的に割り当てる。一部のヘルパー（classify_index_clause_usage 等）では、O(N^2) の最悪挙動を避けるために条件数（100件超など）による安全弁や打ち切りヒューリスティックが実装されている。
  • **可逆性とロス性**: サポート関数や行比較の拡張（expand_indexqual_rowcompare）等で、インデックス条件が不完全な場合は lossy = true としてマークされ、ビットマップスキャン等で適切に処理される。
