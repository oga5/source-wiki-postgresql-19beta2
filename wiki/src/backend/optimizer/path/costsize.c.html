src/backend/optimizer/path/costsize.c

概要

costsize.c は、PostgreSQLオプティマイザにおけるコストモデルおよびサイズ推定の中核を担うソースファイルです。各種実行パス（Path 構造体およびその派生）に対して、起動コスト（startup_cost）、総コスト（total_cost）、出力行数（rows）、およびタプル幅（width）を算出する計算エンジンを提供します。

ディスクI/O（シーケンシャル/ランダムアクセス）、CPU演算、メモリ使用量、およびパラレル実行に伴うオーバーヘッドをモデル化し、プランナーが最も効率的な実行計画を選択するための共通の評価尺度を算出します。

モジュール内での役割

src/backend/optimizer/path ディレクトリにおいて、物理的・論理的な評価基準を提供する「計算機」として機能します。 allpaths.c（ベースリレーションのスキャンパス生成）や joinpath.c（結合パスの生成）などのパス生成モジュールから直接呼び出され、生成された代替パスのコストとサイズをその場で計算・設定します。これにより、オプティマイザは異なるアクセス手法や結合順序のコストを公平に比較し、不要なパスを早期に切り捨てる（枝刈りする）ことが可能になります。

責務

1. スキャンパスのコスト算出 (Scan Path Costing)

  • **物理スキャンの評価**: シーケンシャルスキャン、インデックススキャン、ビットマップヒープスキャン、TIDスキャン、サンプルスキャンなどのコストを算出します。
  • **キャッシュ効果のモデル化**: Mackert-Lohman公式（index_pages_fetched）を用いて、インデックスやテーブルのページがバッファキャッシュにヒットする確率を考慮した、現実的なディスクI/Oコストを推定します。

2. 結合パスのコスト算出 (Join Path Costing)

  • **3大結合アルゴリズムの評価**: ネステッドループ結合、マージ結合、ハッシュ結合のコストを算出します。
  • **2段階評価プロトコル**: 結合パスの生成効率を向上させるため、軽量な下限コストを見積もる初期評価（initial_cost_*）と、詳細な条件評価やリソース制限を加味する最終評価（final_cost_*）の2段階で計算を行います。
  • **特殊な結合のサポート**: セミ結合（SEMI）、アンチ結合（ANTI）、およびインナーユニーク結合における、インナースキャンの早期終了効果（SemiAntiJoinFactors）をモデル化します。

3. 中間・上層操作のコスト算出 (Upper/Intermediate Path Costing)

  • **データ加工操作の評価**: ソート（通常およびインクリメンタル）、集約（Agg）、ウィンドウ関数（WindowAgg）、グループ化（Group）、Append/MergeAppend、Materialize、Memoize などのコストを算出します。
  • **メモリ溢れ（Spill）のシミュレーション**: ソートやハッシュ集約において、推定データサイズが work_mem や hash_mem を超過する場合に発生する、一時ファイルへの書き出し・読み戻しに伴うディスクI/OおよびCPUコストを算入します。

4. サイズと幅の推定 (Size and Width Estimation)

  • **行数（カーディナリティ）推定**: 制限条件（Qual）の選択度（Selectivity）を適用し、各リレーションや結合結果の出力行数を推定します。
  • **外部キー（FK）の活用**: 複数カラムの結合において、外部キー制約（ForeignKeyOptInfo）の存在を検知し、属性間の相関関係を考慮した高精度な結合選択度を算出します。
  • **タプル幅の算出とキャッシュ**: 各属性の統計情報やデータ型から平均バイト幅を算出し、リレーション（RelOptInfo）やターゲットリスト（PathTarget）にキャッシュします。

5. パラレル実行のコスト調整 (Parallel Costing)

  • **並列除数の計算**: パラレルワーカー数とリーダープロセスの関与度（parallel_leader_participation）に基づき、実質的な並列効果を示す除数（get_parallel_divisor）を算出します。
  • **コストと行数の按分**: 算出した除数を用いて、ワーカー間で分散されるCPUコストの削減や、ワーカーごとの部分出力行数を調整します。

重要なシンボル

コストパラメータ（GUC設定値）

  • seq_page_cost / random_page_cost: 順次/ランダムページフェッチの基準コスト。
  • cpu_tuple_cost / cpu_index_tuple_cost: 1タプルあたりのCPU処理コスト（ヒープ/インデックス）。
  • cpu_operator_cost: 演算子や関数の評価に伴うCPUコスト。
  • parallel_tuple_cost / parallel_setup_cost: パラレル実行時のタプル転送および共有メモリセットアップコスト。
  • effective_cache_size: PostgreSQLとOSが利用可能なディスクキャッシュの推定ページ数。

スキャンコスト評価関数

  • cost_seqscan: シーケンシャルスキャンのコストを算出。
  • cost_index: インデックススキャン（およびインデックスオンリースキャン）のコストを算出。
  • cost_bitmap_heap_scan: ビットマップインデックススキャンと、それに続くヒープアクセスの統合コストを算出。
  • cost_tidscan / cost_tidrangescan: CTID直接指定および範囲指定スキャンのコストを算出。

結合コスト評価関数（2段階評価）

  • initial_cost_nestloop / final_cost_nestloop: ネステッドループ結合の初期/最終コスト。
  • initial_cost_mergejoin / final_cost_mergejoin: マージ結合の初期/最終コスト。インナー側のマテリアライズ（materialize_inner）の要否もここで決定します。
  • initial_cost_hashjoin / final_cost_hashjoin: ハッシュ結合の初期/最終コスト。バッチ数（num_batches）の決定や、MCV（最頻値）バケットのメモリ溢れによるペナルティ付与を行います。

中間処理コスト評価関数

  • cost_sort / cost_incremental_sort: 通常ソートおよびインクリメンタルソートのコスト。
  • cost_agg: 集約処理（Plain, Sorted, Hashed, Mixed）のコスト。ハッシュ集約のディスク溢れ（Multi-batch）もシミュレートします。
  • cost_windowagg: ウィンドウ関数のコスト。
  • cost_material: Materializeノードのコスト。

サイズ・幅推定およびユーティリティ

  • set_baserel_size_estimates / set_joinrel_size_estimates: ベース/結合リレーションの行数・幅の初期推定。
  • get_foreign_key_join_selectivity: 外部キー制約に基づく結合選択度の算出。
  • set_rel_width / set_pathtarget_cost_width: タプル幅の算出とキャッシュ。
  • clamp_row_est / clamp_width_est: 推定行数（最低1.0行、最大 1e100）および幅（最大 MaxAllocSize）を安全な範囲にクランプ。
  • index_pages_fetched: Mackert-Lohman公式に基づく、キャッシュを考慮したページフェッチ数の計算。

制御フローとデータフロー

1. サイズと幅の決定フロー

パスを生成する前段階、または結合ツリーを構築する際に、リレーションの基本スペックが決定されます。

[set_baserel_size_estimates]
   │
   ├──> [clauselist_selectivity] ──> 制限条件から出力行数(rows)を決定
   ├──> [cost_qual_eval] ──────────> 制限条件の評価コスト(baserestrictcost)を算出
   └──> [set_rel_width] ───────────> 各属性の平均幅を合算し、reltarget->width にキャッシュ

2. 結合コストの2段階評価フロー

結合パスの探索空間は膨大であるため、プランナーは以下のフローで不要なパスを高速に枝刈りします。

[joinpath.c などの呼び出し元]
   │
   ├──> [initial_cost_hashjoin] (例)
   │       │
   │       └──> 結合条件の評価を無視した、極めて軽量な下限コスト(total_cost)を算出
   │
   ├──> (枝刈り判定: 既存の最良パスより明らかに高価なら、ここで探索を打ち切り)
   │
   └──> [final_cost_hashjoin] (例)
           │
           ├──> [cost_qual_eval] ──> 結合条件(hashclauses, joinrestrictinfo)の評価コストを厳密に計算
           ├──> [estimate_hash_bucket_stats] ──> ハッシュバケットの偏り(Skew)やサイズを考慮
           └──> 最終的な startup_cost / total_cost を Path 構造体に直接書き込み

3. メモリ溢れ（Spill）を伴うデータフロー（Sort / HashAgg）

ソートやハッシュ集約では、推定データサイズと利用可能メモリを比較するデータフローが存在します。

[データサイズ算出: relation_byte_size(rows, width)]
   │
   ▼
[制限値(work_mem / hash_mem)と比較]
   │
   ├─ (メモリ内収容可能) ──> I/Oコストはゼロ。純粋なCPUコスト(比較・ハッシュ演算)のみ加算。
   │
   └─ (メモリ超過: Spill発生)
           │
           ├──> 推定ページ数(page_size)を算出
           ├──> 一時ファイルへの書き込み(seq_page_cost * ページ数)を startup_cost に加算
           └──> 一時ファイルからの読み戻し(seq_page_cost * ページ数)を run_cost に加算

直接依存

本ファイルは、オプティマイザの内部データ構造やシステムカタログ情報に深く依存しています。

  • optimizer/cost.h: コスト計算用のデータ構造（JoinCostWorkspace, QualCost など）の定義。
  • optimizer/pathnode.h / paths.h: Path, IndexPath, JoinPath などのパス表現。
  • utils/selfuncs.h: 選択度（Selectivity）やヒストグラムなどの統計情報アクセス。
  • utils/spccache.h: テーブルスペースごとのページコスト（seq_page_cost 等のオーバーライド値）の取得。
  • executor/nodeHash.h / nodeAgg.h: ハッシュテーブルサイズ（ExecChooseHashTableSize）やハッシュ集約制限の算出。

関連コード

  • src/backend/optimizer/path/allpaths.c: ベースリレーションに対するスキャンパスの生成。
  • src/backend/optimizer/path/joinpath.c: 各種結合パスの生成とコスト評価関数の呼び出し。
  • src/backend/optimizer/path/clausesel.c: 選択度計算の実装。

読者向けメモ

メモリ所有権と破壊的更新

  • 本ファイル内のほぼすべての cost_XXX および final_cost_XXX 関数は、戻り値を返しません。第1引数として渡された Path（またはその派生構造体）の startup_cost, total_cost, rows, disabled_nodes フィールドを**直接書き換える（破壊的変更）**仕様となっています。
  • cached_scansel は、計算したマージ結合選択度（MergeScanSelCache）を PlannerInfo->planner_cxt（プランナ全体の長寿命なメモリコンテキスト）にスイッチして確保し、RestrictInfo->scansel_cache にキャッシュします。これにより、同一クエリの探索プロセス中での重複計算を防止しています。

不変条件とエッジケースの処理

  • **行数推定のクランプ**: clamp_row_est は、推定行数が NaN や無限大になることを防ぎ、最低でも 1.0 行、最大でも MAXIMUM_ROWCOUNT (1e100) の範囲に収まるようにします。これにより、コスト計算におけるゼロ除算やオーバーフローを防止しています。
  • **GUC無効化時の挙動**: enable_seqscan = false などの設定がある場合、以前はコストに巨大な定数（disable_cost）を直接加算していましたが、現在は disabled_nodes カウントをインクリメントする方式に移行しています。プランナーはコストが同等の場合、disabled_nodes がより少ないパスを優先します。

意図的に省略されている領域

  • **外部テーブル（Foreign Table）のサイズ見積もり**: set_foreign_size_estimates では、1000行という固定のダミー値を設定するのみで、実際の見積もりは各外部データラッパー（FDW）の GetForeignRelSize コールバックに完全に委ねられています。
