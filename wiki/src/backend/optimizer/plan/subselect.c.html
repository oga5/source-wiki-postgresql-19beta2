src/backend/optimizer/plan/subselect.c

概要

src/backend/optimizer/plan/subselect.c は、PostgreSQLのクエリ最適化フェーズにおいて、SubLink（式中の副問合せ）や共通表式（CTE）を実行可能な計画ノード（SubPlan や InitPlan）または結合（Join）へと変換・最適化するための主要な処理を担うソースファイルです。FROM句内のサブクエリ（RTE_SUBQUERY）は対象外であり、WHERE句やSELECTターゲットリストなどの式に含まれる副問合せの処理に特化しています。

モジュール内での役割

本ファイルは src/backend/optimizer/plan モジュールの一部として、プランナのメインルーチン（planner.c）や結合ツリーのプルアップ処理（prepjointree.c）と密接に連携します。パーサから渡された抽象的な SubLink や CTE を、エグゼキュータが実行可能な具体的な SubPlan や InitPlan にコンパイルし、パラメータ（PARAM_EXEC）の依存関係（extParam/allParam）を解決してプランツリーをファイナライズする役割を持ちます。

責務

本ファイルが持つ責務は、以下の役割グループに大別されます。

1. SubLinkのSubPlan/InitPlan変換

  • **計画の生成**: SubLink 内の副問合せに対して subquery_planner を再帰的に呼び出し、最適な物理パスおよびプランを生成する。
  • **InitPlanへの変換**: 外部参照（相関関係）を持たない、または間接的な相関のみを持つ副問合せ（EXISTS、EXPR、ARRAY、ROWCOMPARE、MULTIEXPR）を、クエリ実行開始時に1回だけ評価される InitPlan に変換し、結果を Param ノードに置き換える。
  • **ハッシュサブプランの判定**: ANY（IN）サブプランにおいて、パラメータ依存がなく、演算子がハッシュ可能で、かつ推定サイズが hash_mem に収まる場合にハッシュテーブルの使用（useHashTable = true）を決定する。

2. CTE（Common Table Expression）の処理

  • **インライン化の評価**: WITH 句で定義された各CTEについて、参照回数、再帰の有無、副作用（DMLや volatile 関数）の有無を検証し、可能であれば RTE_SUBQUERY として親クエリにインライン展開する。
  • **CTEのInitPlan化**: インライン化できないCTE、またはマテリアライズが指定されたCTEを、独立した InitPlan（CTE_SUBLINK）として登録する。

3. サブクエリの結合（Join）変換

  • **Semi-Join / Anti-Join へのプルアップ**: ANY または EXISTS サブリンクを、親クエリの JoinExpr（JOIN_SEMI または JOIN_ANTI）に変換して結合ツリーに統合する。
  • **VALUES句の最適化**: VALUES 句を持つ単一カラムのサブクエリを、定数配列に対する ScalarArrayOpExpr（ANY (ARRAY[...])）に変換する。

4. パラメータ管理とファイナライズ

  • **相関変数の置換**: サブクエリ内の上位クエリへの参照（Var、PlaceHolderVar、Aggref など）を、実行時パラメータ（Param）に置換する。
  • **プランのファイナライズ**: プランツリー全体を再帰的に走査し、各プランノードが依存する外部パラメータ（extParam）と、自身および子ノードが使用する全パラメータ（allParam）のビットマップを確定させる。

重要なシンボル

SubLink変換・構築

  • make_subplan: SubLink を受け取り、サブクエリの計画（Plan）を作成して build_subplan を呼び出す。EXISTS の場合は AlternativeSubPlan（通常実行とハッシュ実行の選択肢）の生成も試みる。
  • build_subplan: Plan や Path から SubPlan ノードを構築し、InitPlan への変換やハッシュ化の適格性を判定して初期化する。
  • convert_testexpr: パーサが生成した PARAM_SUBLINK を、実際の実行用パラメータ（PARAM_EXEC）や変数（Var）に置換する。

CTE処理

  • SS_process_ctes: クエリの WITH リストを走査し、各CTEをインライン化するか、あるいは InitPlan として計画するかを決定・処理する。
  • inline_cte: 対象のCTE参照を RTE_SUBQUERY に書き換え、親クエリのレンジテーブルにインライン展開する。

結合変換

  • convert_ANY_sublink_to_join: ANY サブリンクを Semi-Join または Anti-Join に変換する。
  • convert_EXISTS_sublink_to_join: EXISTS サブリンクを Semi-Join または Anti-Join に変換する。
  • simplify_EXISTS_query: EXISTS サブクエリ内の不要なターゲットリスト、ORDER BY、DISTINCT、LIMIT などを除去してクエリを単純化する。
  • convert_VALUES_to_ANY: VALUES サブクエリを ScalarArrayOpExpr に変換する。

パラメータ管理・ファイナライズ

  • SS_replace_correlation_vars: 上位クエリへの相関参照を Param に置換する。
  • SS_process_sublinks: 式ツリー内の SubLink を再帰的にスキャンして SubPlan に置換する。
  • SS_finalize_plan / finalize_plan: プランツリーを再帰走査し、各ノードの extParam と allParam を確定する。
  • finalize_primnode: 式ツリー内の PARAM_EXEC パラメータIDを収集する。

制御フローとデータフロー

1. SubLinkの処理フロー

[SS_process_sublinks] (式ツリーの走査)
        │
        ▼
[make_subplan] ──(コピー)──> [simplify_EXISTS_query] (EXISTSの単純化)
        │
        ├─> [subquery_planner] (サブクエリの計画・パス生成)
        │
        ▼
[build_subplan]
        │
        ├─> [generate_subquery_params] (出力列に対応するPARAM_EXECの生成)
        ├─> [convert_testexpr] (PARAM_SUBLINKをPARAM_EXECに置換)
        │
        ├─> (パラメータ依存なし ＆ InitPlan化可能)
        │         └─> InitPlanとして登録、結果用Paramを返す
        │
        └─> (パラメータ依存あり ＆ ANYサブリンク ＆ ハッシュ可能)
                  └─> useHashTable = true に設定

2. EXISTSサブリンクの結合変換フロー

pull_up_sublinks から呼び出され、EXISTS を結合に変換します。 1. **事前チェック**: サブクエリに WITH 句（CTE）が含まれていないこと、および WHERE 句に親クエリへの相関参照が含まれていることを確認する。 2. **クエリの単純化**: simplify_EXISTS_query を呼び出し、ターゲットリストを空（NIL）にする。 3. **レンジテーブルのマージ**: サブクエリのレンジテーブル（rtable）を親クエリにマージする。この際、OffsetVarNodes および IncrementVarSublevelsUp を使用して、サブクエリ内の Var ノードのインデックス（varno）とレベル（varlevelsup）を親クエリの環境に合わせて調整する。 4. **JoinExprの構築**: 結合タイプを JOIN_SEMI（NOT 下の場合は JOIN_ANTI）とし、調整された WHERE 句を結合条件（quals）とする JoinExpr を構築して返す。

3. プランのファイナライズフロー

プランツリー全体の構築完了後、SS_finalize_plan から finalize_plan が再帰的に呼び出されます。 1. **initPlanの解析**: ノードにアタッチされた initPlan の extParam（外部依存）と setParam（出力パラメータ）を収集する。 2. **式の走査**: finalize_primnode を用いて、ターゲットリストや qual などの式に含まれる PARAM_EXEC のIDを Bitmapset に集約する。 3. **子ノードの再帰処理**: lefttree および righttree に対して finalize_plan を再帰呼び出しし、返されたパラメータ集合をマージする。

  • NestLoop の場合、右側の子プランに渡される nestParams は、このノードの外部依存（extParam）からは除外される（bms_difference）。

    • 4. **パラメータの確定**: 収集されたパラメータIDから、このノードの allParam（自身と子孫が使用する全パラメータ）と extParam（外部から供給されるべきパラメータ）を計算し、プランノードに書き込む。

直接依存

本ファイルは、以下のヘッダおよびモジュールに直接依存しています。

  • nodes/nodeFuncs.h, optimizer/clauses.h: 式ツリーの走査（expression_tree_walker/mutator）やクエリの正規化。
  • optimizer/planner.h: subquery_planner によるサブクエリの計画生成。
  • optimizer/paramassign.h: 実行時パラメータ（PARAM_EXEC）の割り当て（generate_new_exec_param など）。
  • optimizer/cost.h: サブプランのコスト見積もり（cost_subplan）。
  • utils/syscache.h, utils/lsyscache.h: 演算子のハッシュ可能性や厳密性（strictness）を検証するためのシステムカタログアクセス。

読者向けメモ

  • **メモリ管理とオブジェクト複製**: プランナはクエリツリーに対して破壊的な変更を加えるため、make_subplan や SS_process_ctes では copyObject を使用してクエリツリーの複製を作成してから処理を行います。これらのメモリはすべてプランナのメモリコンテキスト（PlannerInfo のスコープ）で管理されます。
  • **CTEインライン化の制約**: CTEのインライン化は最適化の幅を広げますが、複数回参照されるCTEにおいて副作用（DMLや volatile 関数）がある場合、または再帰的な場合は、セマンティクス維持のためにインライン化が厳格に禁止されます。
  • **ハッシュ化の前提条件**: ANY サブプランをハッシュ結合のように実行する（useHashTable = true）ためには、演算子が「厳密（strict）」かつ「ハッシュ可能」であり、かつ非ヌル入力に対して NULL を返さないという不変条件（Invariant）を満たす必要があります。
  • **ファイナライズの順序**: finalize_plan は、プランツリーにアタッチされた initPlan や subplan 自体のファイナライズがすでに完了していることを前提として動作します。
