src/backend/optimizer/plan/planner.c

概要

クエリ最適化の外部インターフェースであり、PostgreSQLオプティマイザの中心的なコーディネーターとして機能します。パース木（Queryツリー）を入力として受け取り、スキャン、結合、集約、ウインドウ関数、並び替え、LIMIT/OFFSET、および書き込み処理（INSERT/UPDATE/DELETE/MERGE）を包括してコストベースのパス探索を行い、最終的な実行計画ツリー（PlannedStmt）を構築します。

モジュール内での役割

src/backend/optimizer/plan ディレクトリ配下において、クエリ全体のプランニングライフサイクルを総括する最上位のエントリポイントです。下位モジュール（query_planner、createplan、subselect、setrefs など）や各種フックを連携させ、クエリレベルの再帰的探索、グループ化・集約パスの生成、並列クエリの制御を行います。

責務

  • **クエリプランニングの統括**: planner() および standard_planner() を通じて全体の初期化、並列モードの判定、subquery_planner() の呼び出し、および最終計画の構築を行う。
  • **サブクエリと式の前処理**: subquery_planner() においてCTEの処理、サブリンクの引き上げ（Pull-up）、範囲テーブル（RTE）の展開、式の前処理（定数たたみ込みや正規化）を実行する。
  • **グループ化・集約・ウインドウ処理**: グループ化セット（Grouping Sets）、通常のGROUP BY、HAVING句のプッシュダウン、およびウインドウ関数やDISTINCT、ORDER BYのパス生成を組織化する。
  • **プラグインとフックの管理**: planner_hook、planner_setup_hook、planner_shutdown_hook、create_upper_paths_hook を介した拡張モジュールへの介入ポイントを提供する。

重要なシンボル

データ構造

  • grouping_sets_data: グループ化セット（Grouping Sets）のロールアップ、ハッシュセット、未ソート／未ハッシュ参照などの情報を保持する構造体。
  • WindowClauseSortData: ウインドウ関数の並び替え（WindowClause reordering）中に、パーティショニングおよびオーダー順プレフィックスでソートするために一時的に使用する構造体。
  • standard_qp_extra: standard_qp_callback に渡されるパススルーデータで、アクティブなウインドウ、グループ化セットデータ、セット操作ステートを保持する。
  • having_grouping_ctx: find_having_conflicts における expression_has_grouping_conflict コールバック用のコンテキスト（QueryおよびグループRTEインデックスを保持）。

主要エントリーポイントと処理関数

  • standard_planner: プランナーの標準的な実行本体。PlannerGlobal の初期化、並列クエリの可否判断、subquery_planner() の呼び出し、最終的なパスから Plan への変換および参照解決（set_plan_references）を行う。
  • subquery_planner: サブクエリ（およびトップレベルクエリ）ごとのプランニングを担当。CTE、RTE展開、サブリンク引き上げ、式前処理、および grouping_planner() の呼び出しを行う。
  • preprocess_expression: ターゲットリスト、WHERE、HAVING、LIMIT等の式に対し、結合エイリアスの展開、定数畳み込み、Qualの正規化、SubLinkからSubPlanへの変換、相関変数置換を適用する。
  • preprocess_qual_conditions: 結合ツリー（jointree）を再帰的に走査し、各層の条件式に対して preprocess_expression を適用する。
  • find_having_conflicts: HAVING句の等価演算子がGROUP BYのそれと矛盾し、WHERE句へのプッシュダウンが不可能な条件を特定する。
  • having_var_grouping_eqop: find_having_conflicts 用のコールバック。指定されたVarに対応するGROUP BYの等価演算子を返す。
  • group_var_eqop: 指定されたグループVar（RTE_GROUP）のattnoに対応する SortGroupClause の等価演算子（eqop）を復元する。
  • preprocess_phv_expression: プルアップされた PlaceHolderVar 式に対する前処理を行う。

制御フローとデータフロー

1. **初期化フェーズ (planner / standard_planner)**:

  • PlannerGlobal を割り当て、バインドパラメータや並列クエリの有効性を評価。
  • planner_setup_hook が設定されていれば呼び出し。

    • 2. **クエリ解析と前処理 (subquery_planner)**:

  • CTEの処理、MERGE文の変換、RTEの展開（preprocess_relation_rtes）、サブリンクの引き上げ（pull_up_sublinks）を実施。
  • preprocess_expression および preprocess_qual_conditions により、式ツリーを正規化・定数畳み込み・サブプラン化。
  • HAVING句のプッシュダウン可能性の判定（find_having_conflicts）と不要な結合の削減（reduce_outer_joins）。

    • 3. **集約・グループ化・ウインドウ・並び替えパスの構築 (grouping_planner)**:

  • query_planner を呼び出してスキャン・結合部分のパスを生成。
  • ターゲットリストを PathTarget に変換し、SRF（集合返却関数）が含まれる場合は分割・調整。
  • グループ化（create_grouping_paths）、ウインドウ関数（create_window_paths）、DISTINCT（create_distinct_paths）、ORDER BY（create_ordered_paths）の各アッパレル（UpperRel）パスを構築。

    • 4. **最終計画への変換**:

  • ロック行（LockRows）、LIMIT（Limit）、書き込み（ModifyTable）の各パスを積層。
  • create_plan で Path を Plan に変換し、set_plan_references で最終的なプランツリーとRTE/Param参照を解決して PlannedStmt を生成。

読者向けメモ

  • **メモリ管理とライフサイクル**: PlannerGlobal はクエリの全レベル（サブクエリを含む）で共有され、PlannerInfo はクエリレベルごとに独立して割り当てられる。GEQOなどの特殊なコンテキストでは、適切なメモリコンテキストの切り替えが必要となる。
  • **副作用に関する注意**: standard_planner() および関連ルーチンは入力の Query 構造体を破壊的変更（スクリブル）するため、プラグインなどで複数回プランニングを行う場合は Query ツリーのコピーが必須となる。
  • **網羅性**: このファイルは数千行に及ぶ巨大なソースファイルであるが、アッパレル（UpperRel）ごとのパス生成関数群（Grouping, Window, Distinct, Ordered）は一貫したパターン（make_pathtarget -> create_*_paths -> set_cheapest）に従って組織化されている。
