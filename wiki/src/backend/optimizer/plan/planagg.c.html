src/backend/optimizer/plan/planagg.c

概要

src/backend/optimizer/plan/planagg.c は、PostgreSQLのオプティマイザにおいて、MIN および MAX 集約関数をインデックススキャンと LIMIT 1 を用いた効率的な副問い合わせ（InitPlan）に書き換える特例的プランニング（MIN/MAX最適化）を所有する。全行スキャンが必要な通常の集約プランに比べ、適切なインデックスが存在する場合に劇的な性能向上をもたらす。

モジュール内での役割

本ファイルは src/backend/optimizer/plan モジュールの一部として、grouping_planner() から呼び出され、集約クエリの事前処理（preprocess_minmax_aggregates）を行う。通常の集約パス生成とは別に MinMaxAggPath を構築し、UPPERREL_GROUP_AGG 上位リレーションに追加することで、標準的な集約実装とコスト競合させる。

責務

  • クエリが MIN/MAX 最適化の要件（単一テーブル、GROUP BYなし、ウィンドウ関数なし、CTEなし等）を満たすか検証する。
  • 条件に合致する場合、各集約式に対応する MinMaxAggInfo を構築し、集約関数のソート演算子と等価演算子を特定する。
  • 対象クエリの状態をクローンして調整し、col IS NOT NULL の付与、ORDER BY、LIMIT 1 を持つ仮想的な副問い合わせ（subroot）を構築する。
  • query_planner() を直接呼び出してインデックススキャンパスを生成し、最適な部分取得パス（fractional path）を選択する。
  • 最終的に MinMaxAggPath を生成し、UPPERREL_GROUP_AGG へ登録する。

重要なシンボル

集約前処理・エントリポイント

  • preprocess_minmax_aggregates(PlannerInfo *root)
  • grouping_planner() から呼び出されるエントリポイント。クエリ構造（集約の有無、単一リレーション、GROUP BY/ウィンドウ関数/CTEの不在）を検証し、すべての集約が MIN/MAX である場合に MinMaxAggPath を作成して UPPERREL_GROUP_AGG に追加する。

検証・カタログ操作

  • can_minmax_aggs(PlannerInfo *root, List **context)
  • root->agginfos を走査し、すべての集約参照が引数1つ、ORDER BY なし、FILTER なし、かつミュータブル関数や行型を含まない純粋な MIN/MAX 集約であるかを検証する。成功した場合は MinMaxAggInfo のリストを構築する。
  • fetch_agg_sort_op(Oid aggfnoid)
  • pg_aggregate システムカタログ（AGGFNOID キャッシュ）から集約関数に対応するソート演算子（aggsortop）の OID を取得する。

副問い合わせパス構築

  • build_minmax_path(PlannerInfo *root, MinMaxAggInfo *mminfo, Oid eqop, Oid sortop, bool reverse_sort, bool nulls_first)
  • 現在のクエリレベルの状態をコピー・変形（変数レベルの繰り上げ、col IS NOT NULL 条件の追加、ORDER BY と LIMIT 1 の設定）し、query_planner() を呼び出してソート済みインデックススキャンパスを取得する。
  • minmax_qp_callback(PlannerInfo *root, void *extra)
  • query_planner() 実行時のコールバック。group_pathkeys などをクリアし、ソート句に基づいた query_pathkeys を設定する。

データ構造・型

  • MinMaxAggInfo
  • 個々の MIN/MAX 集約に関するメタデータ（関数 OID、ソート演算子、対象式、構築された subroot、パス、コスト、出力用 Param）を保持する構造体。
  • MinMaxAggPath
  • 最適化された MIN/MAX サブプランを表す Path ノード（定義自体は別ファイルだが本ファイルでインスタンス化され使用される）。
  • MAX / MIN
  • （索引付きシンボルとしてのマクロまたは関数参照。クエリ内の集約種別を識別するために概念的に関与）

制御フローとデータフロー

1. **事前検証フェーズ**: preprocess_minmax_aggregates() が呼び出され、parse->hasAggs の確認や、GROUP BY、ウィンドウ関数、CTE、複数テーブル結合の有無をチェックして不適格なクエリを早期に除外する。 2. **集約検査**: can_minmax_aggs() が各 Aggref を検査し、すべての集約が MIN/MAX であることを確認するとともに、fetch_agg_sort_op() でソート演算子を取得して MinMaxAggInfo リストを作成する。 3. **サブプラン構築フェーズ**: 各 MinMaxAggInfo に対し build_minmax_path() が実行される：

  • 現在の PlannerInfo を palloc で複製し、変数レベルを IncrementVarSublevelsUp で1つ引き上げる。
  • ターゲットリストを単一の集約対象式に絞り込み、IS NOT NULL 条件をジョイントリーの quals に追加する。
  • ORDER BY 句と LIMIT 1 相当の制限（limitCount = 1）を構成する。
  • query_planner() と minmax_qp_callback() を呼び出してインデックススキャン等のパスを探索する。
  • get_cheapest_fractional_path_for_pathkeys() を用いて、1行取得に最もコストが低いパス（sorted_path）を選択し、プロジェクションを適用する。

    • 4. **パス登録フェーズ**: すべての集約のインデックスパスが正常に構築できたら、SS_make_initplan_output_param() で出力用 Param を割り当て、create_minmaxagg_path() で MinMaxAggPath を生成して UPPERREL_GROUP_AGG 上位リレーションへ登録する。

読者向けメモ

  • **メモリ管理**: build_minmax_path() 内では PlannerInfo やクエリツリーのディープコピー（copyObject）が多用される。これらは通常のプランニングコンテキスト上で割り当てられる。
  • **並列安全性**: 生成される MinMaxAggPath は現在パラレルセーフではないため、並列クエリプランの一部としては実行されない。
  • **インプレースクローン**: サブクエリ生成時に元の PlannerInfo を memcpy した上で query_level をインクリメントし、変数参照レベルを調整することで、通常の副問い合わせプランニングと同等の環境を擬似的に作り出している。
