src/backend/optimizer/plan/planagg.c

概要

src/backend/optimizer/plan/planagg.c は、PostgreSQLのオプティマイザーにおいて集約クエリに対する特殊な最適化、具体的には MIN / MAX 集約関数をインデックススキャンと LIMIT 1 を利用したサブクエリ（InitPlan）に置き換える処理を担当します。全行スキャンを伴う通常の集約プランに比べ、適切なインデックスが存在する場合に劇的な性能向上の可能性があります。

モジュール内での役割

src/backend/optimizer/plan モジュールの主要な一角として、grouping_planner() から呼び出され、標準的な集約プラン構築前の前処理段階で動作します。対象クエリ条件に合致する MIN / MAX 集約を見つけ出し、最適化可能であれば MinMaxAggPath を生成して UPPERREL_GROUP_AGG 上位リレーションに追加します。

責務

  • クエリが MIN / MAX 最適化の前提条件を満たしているかの判定（単一テーブル、GROUP BYなし、ウィンドウ関数なし、CTEなし等）。
  • 各 MIN / MAX 集約に対するソート演算子の検証およびサブクエリ用 PlannerInfo の構築。
  • インデックススキャンと LIMIT 1 を用いたサブプラン（InitPlan）アクセスパスの探索と評価。
  • 最適化成功時に出力用 Param の作成と MinMaxAggPath の登録。

重要なシンボル

公開（外部から呼び出される）シンボル

  • preprocess_minmax_aggregates(PlannerInfo *root)
  • **ライフサイクル / アクセス**: クエリのグループ化処理の直前（grouping_planner 内）から呼ばれる。
  • **役割**: クエリが MIN / MAX 最適化の要件を満たすか検証し、全集約が最適化可能であれば MinMaxAggPath を構築して上流リレーションに追加する。

静的（モジュール内）ヘルパーシンボル

  • can_minmax_aggs(PlannerInfo *root, List **context)
  • **役割**: root->agginfos を走査し、すべての集約が引数を1つ持つ純粋な MIN / MAX 集約（可変関数や行型を含まない）であるかを検証し、MinMaxAggInfo リストを構築する。
  • build_minmax_path(PlannerInfo *root, MinMaxAggInfo *mminfo, Oid eqop, Oid sortop, bool reverse_sort, bool nulls_first)
  • **役割**: 現在のクエリ状態をクローン・改変して仮想的なサブクエリ (SELECT col FROM tab WHERE col IS NOT NULL ... ORDER BY col ... LIMIT 1) を作成し、query_planner を実行して最適なプレソートパスを取得・コスト評価する。
  • minmax_qp_callback(PlannerInfo *root, void *extra)
  • **役割**: query_planner 用のコールバック。ソート句から query_pathkeys を設定する。
  • fetch_agg_sort_op(Oid aggfnoid)
  • **役割**: pg_aggregate システムカタログから指定された集約関数のソート演算子 (aggsortop) OID を取得する。

制御フローとデータフロー

1. **事前条件のチェック**: preprocess_minmax_aggregates が parse->hasAggs の有無、groupClause、hasWindowFuncs、cteList、単一テーブル制約などを順にチェックし、違反していれば早期リターンする。 2. **集約の検証**: can_minmax_aggs で各集約を走査。fetch_agg_sort_op を使ってカタログから aggsortop を取得し、可変関数や行型でないことを確認した上で MinMaxAggInfo を生成する。 3. **サブプラン（パス）の構築**: 各 MinMaxAggInfo について build_minmax_path を呼び出す。

  • 親の PlannerInfo をコピーして subroot を作成し、Var のサブレベルをインクリメント。
  • ターゲットリストを単一の集約対象式に書き換え、IS NOT NULL 条件と ORDER BY および LIMIT 1 (limit_tuples = 1.0) を付与。
  • query_planner を実行し、最安の分数パス（get_cheapest_fractional_path_for_pathkeys）を選択。

    • 4. **パスの登録**: すべての MIN / MAX 集約でインデックススキャンパスが得られた場合、SS_make_initplan_output_param でパラメータを割り当て、create_minmaxagg_path で生成した MinMaxAggPath を UPPERREL_GROUP_AGG の grouped_rel に追加する。

読者向けメモ

  • **メモリ管理とライフサイクル**: build_minmax_path 内では palloc_object(PlannerInfo) および copyObject を多用してサブクエリのコンテキストを動的に構築する。失敗時や未使用時も含めてメモリコンテキスト管理に依存する。
  • **インバリアントと制約**: 対象クエリは厳格に単一テーブル（またはフラット化された UNION ALL 継承親）であり、GROUP BY、ウィンドウ関数、FOR UPDATE、CTE、FILTER 句を含まない場合にのみ本最適化が適用される。
  • **並列性**: 生成される MinMaxAggPath は現状パラレルセーフではないため、並列実行プランの候補にはならない。
