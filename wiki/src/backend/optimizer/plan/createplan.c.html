src/backend/optimizer/plan/createplan.c

概要

createplan.c は、PostgreSQLのオプティマイザが選択した最適なアクセスパス（Path ツリー）を、実行エンジン（Executor）が解釈・実行可能な計画（Plan ツリー）へと変換する再帰的ビルダーです。 プランニングフェーズの最終段階として、物理的なスキャン、結合、ソート、集約などの各実行ノードを生成し、ターゲットリスト（tlist）やフィルタ条件（quals）を適切に配置・調整する極めて重要な役割を担っています。

モジュール内での役割

本ファイルは src/backend/optimizer/plan ディレクトリに属し、planner.c が決定した「最も低コストなパス（best_path）」を入力として受け取ります。 ここで生成される Plan ツリー内の変数参照（Var）は、まだパーサが解析した時点の番号（varno）を維持しています。これらは後続の setrefs.c フェーズによって、実行時に適切なタプルスロットを指す参照（OUTER_VAR や INNER_VAR など）へと書き換えられます。

責務

createplan.c の膨大なロジックは、以下の役割グループに整理されます。

1. 計画ツリーの再帰的ディスパッチ

  • 入力された Path の pathtype（ノード種別）を判別し、対応するプラン生成関数へ処理を振り分けます。
  • スタックオーバーフローを防ぐための深度チェック（check_stack_depth()）を走査の起点で行います。

2. ターゲットリスト（tlist）と射影（Projection）の最適化

  • 呼び出し元が要求するフラグ（CP_EXACT_TLIST, CP_SMALL_TLIST, CP_LABEL_TLIST, CP_IGNORE_TLIST）に基づき、不要な列の評価や転送を削減します。
  • 物理的なタプル構造をそのまま利用できる場合（use_physical_tlist が真の場合）は、不要な射影処理をバイパスしてエグゼキュータのオーバーヘッドを削減します。
  • 射影能力を持たない実行ノード（Sort や Material など）の直前で射影が必要になった場合、Result ノードを動的に挿入（inject_projection_plan）します。

3. スキャン・結合・集約プランの具現化

  • **スキャン**: SeqScan, IndexScan, BitmapHeapScan, ForeignScan, CustomScan などの具体的なスキャン計画を構築します。
  • **結合**: NestLoop, MergeJoin, HashJoin の各結合プランを構築し、内側・外側の子プランを再帰的に生成します。
  • **集約・ウィンドウ**: Agg（Grouping Sets を含む）、WindowAgg、Group などのプランを構築し、ソート順やグループ化キーのメタデータを設定します。

4. 条件式（Quals）の整理とパラメータ置換

  • 実行時に一度だけ評価すればよい擬似定数条件（Pseudoconstant Quals）を検出し、プランの上部にゲーティング用の Result ノードを挿入（create_gating_plan）します。
  • ネストループ結合の内側プランにおいて、外側リレーションの変数をパラメータ（Param）に置き換える処理（replace_nestloop_params）を制御します。
  • インデックススキャンにおいて、テーブルの属性参照をインデックスの属性参照（INDEX_VAR）に書き換えます（fix_indexqual_references）。

5. 物理ノードの構築（make_xxx 関数群）

  • 各 Plan ノード（SeqScan, IndexScan, NestLoop, HashJoin など）のメモリ領域を確保し、実行に必要なフィールドを初期化する低レベルなビルダー群を提供します。

重要なシンボル

エントリポイントとディスパッチャ

  • Plan *create_plan(PlannerInfo *root, Path *best_path)
  • 外部（主に planner.c）から呼ばれるメインエントリポイント。最上位プランの生成後、ターゲットリストの装飾情報の復元（apply_tlist_labeling）や initPlan のアタッチ（SS_attach_initplans）を行います。
  • static Plan *create_plan_recurse(PlannerInfo *root, Path *best_path, int flags)
  • 再帰処理の中核。best_path->pathtype に応じて適切な create_xxx_plan 関数を呼び出します。

ターゲットリスト制御フラグ

  • CP_EXACT_TLIST (0x0001): パスのターゲットリストと完全に一致する tlist の生成を要求します。
  • CP_SMALL_TLIST (0x0002): メモリ消費を抑えるため、必要最小限の列（幅の狭い tlist）を優先します（Sort や Hash で使用）。
  • CP_LABEL_TLIST (0x0004): ソートやグループ化に必要な sortgroupref ラベルの付与を要求します。
  • CP_IGNORE_TLIST (0x0008): 呼び出し側が後で tlist を差し替えるため、tlist の生成をスキップします。

主要なプラン生成ヘルパー

  • static Plan *create_scan_plan(PlannerInfo *root, Path *best_path, int flags)
  • ベースリレーションに対する各種スキャンプランの生成を統括します。
  • static Plan *create_join_plan(PlannerInfo *root, JoinPath *best_path)
  • NestLoop, MergeJoin, HashJoin の生成をディスパッチします。
  • static Plan *create_projection_plan(PlannerInfo *root, ProjectionPath *best_path, int flags)
  • 射影を行うプランを生成します。不要な場合は子プランに tlist を直接割り当て、必要な場合は Result ノードを挿入します。

パラメータ・参照調整

  • static Node *replace_nestloop_params(PlannerInfo *root, Node *expr)
  • 式の中にある外側リレーションの Var や PlaceHolderVar を Param に置換します。
  • static void fix_indexqual_references(...)
  • インデックス条件式内のテーブル変数参照を、インデックス列の相対位置（INDEX_VAR）に変換します。

制御フローとデータフロー

1. 全体制御フロー

create_plan から始まる再帰的なツリー変換のフローは以下の通りです。

[planner.c]
     │
     ▼
[create_plan] ──(初期化)
     │
     ▼
[create_plan_recurse] <───────────────────────────────┐ (再帰呼び出し)
     │                                                │
     ├─► [create_scan_plan] ──────────────────────────┤
     │                                                │
     ├─► [create_join_plan]                           │
     │    ├─► [create_nestloop_plan] ──► [recurse] ───┤
     │    ├─► [create_mergejoin_plan] ─► [recurse] ───┤
     │    └─► [create_hashjoin_plan] ──► [recurse] ───┤
     │                                                │
     ├─► [create_append_plan] ─────────► [recurse] ───┤
     └─► [create_projection_plan] ─────► [recurse] ───┘
     │
     ▼
(最上位プランの調整)
 ├─► apply_tlist_labeling (列名などの装飾情報を復元)
 └─► SS_attach_initplans (initPlan のアタッチ)
     │
     ▼
[Plan ツリーの返却]

2. データフローと主要なデータ構造の相互作用

  • **Path から Plan へのコスト情報の引き継ぎ**:
  • copy_generic_path_info(Plan *dest, Path *src) を使用して、Path 構築時に計算済みのコスト（startup_cost, total_cost）、行数（rows）、幅（width）、並列実行フラグ（parallel_safe, parallel_aware）を Plan ノードにそのままコピーします。**本ファイル内でコストの再計算は行いません。**
  • **ネストループパラメータの伝播**:
  • NestLoop プラン生成時、identify_current_nestloop_params によって必要なパラメータ（NestLoopParam）が特定され、root->curOuterParams から消費されます。
  • パラメータ化されたインナースキャン側では、replace_nestloop_params が式中の該当変数を Param ノードに書き換えます。
  • **インデックス参照の書き換え**:
  • IndexPath から IndexScan または IndexOnlyScan を生成する際、fix_indexqual_references がインデックスキーを varno = INDEX_VAR、varattno = (インデックス列番号 + 1) の Var ノードに変換し、エグゼキュータがインデックス物理タプルから直接値を抽出できるようにします。

本ファイルは、オプティマイザの他のサブシステムやパーサ、カタログ情報に深く依存しています。

  • optimizer/restrictinfo.h: 制限条件（RestrictInfo）の解析と操作。
  • optimizer/tlist.h: ターゲットリストの操作（build_physical_tlist など）。

  • optimizer/subselect.h: initPlan や SubPlan の作成・アタッチ（SS_attach_initplans）。
  • nodes/makefuncs.h: makeNode や各種 make_xxx による物理ノード生成。

読者向けメモ

メモリ所有権とライフタイム

  • 本ファイル内で生成されるすべての Plan ノード、ターゲットリスト、および修飾式（quals）は、プランナーのメモリコンテキスト（通常は PlannerContext）に割り当てられます。
  • これらのメモリ領域は、クエリのプランニングが完了し、ポータル（Portal）または実行エンジンにプランが引き渡されて実行が終了するまで保持されます。

重要な不変条件（Invariants）

  • **コスト計算の禁止**: make_xxx 関数群やプラン生成ヘルパーは、独自のコスト計算ロジックを持ってはなりません。コストはすべて Path 段階で確定している必要があり、ここでは単にコピー（copy_generic_path_info）するか、ソートなどの一部の例外的な動的挿入ノードに対して cost_sort などのコスト算出関数を呼び出してラベル付け（label_sort_with_costsize）するのみに留めます。
  • **変数参照の未解決性**: 生成された Plan 内の Var ノードは、依然として範囲テーブル（Range Table）のインデックスを保持しており、実行時にアウター/インナータプルを指す OUTER_VAR (65000) や INNER_VAR (65001) にはなっていません。この変換は必ず setrefs.c で行われます。

省略された領域について

  • 個々の make_xxx 関数（例: make_functionscan, make_valuesscan など）の内部における、構造体メンバーへの単純な代入処理の詳細は、定型的かつ自明なノード初期化であるため、本ドキュメントでは説明を省略しています。
