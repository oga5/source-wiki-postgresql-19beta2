src/backend/optimizer/util/plancat.c

概要

src/backend/optimizer/util/plancat.c は、PostgreSQLのオプティマイザが実行計画（プラン）の作成やコスト見積もりを行うために、システムカタログ（リレーション、インデックス、制約、拡張統計情報、パーティショニング情報など）から必要なメタデータを安全に参照・抽出し、プランナ用のデータ構造に変換するためのインターフェースを提供するソースファイルです。

モジュール内での役割

本ファイルは src/backend/optimizer/util ディレクトリに位置し、オプティマイザの各フェーズ（パス生成、コスト見積もり、制約除外など）と、データベースのメタデータを管理するリレーションキャッシュ（Relcache）やシステムカタログとの間の仲介役（ラッパー）として機能します。

プランナの上流プロセスから呼び出され、カタログの生データをプランナが扱いやすい構造体（RelOptInfo、IndexOptInfo、StatisticExtInfo など）にロード・初期化して引き渡す役割を担います。

責務

本ファイルの所有する責務は、以下の4つの役割グループに大別されます。

1. リレーションおよびインデックスのメタデータ構築

  • **基本情報のロード**: 指定されたリレーションOIDから、属性範囲（min_attr, max_attr）、テーブルスペース、並列ワーカー数などの基本属性を RelOptInfo に設定します。
  • **インデックス情報の構築**: テーブルに定義された有効なインデックスを走査し、キー属性、演算子クラス、ソート順序、インデックス式、インデックス述語などを格納した IndexOptInfo のリストを構築します。
  • **外部キー情報の収集**: 他のリレーションとの結合最適化に利用するため、有効な外部キー制約（ForeignKeyOptInfo）をロードして PlannerInfo->fkey_list に追加します。

2. 制約およびパーティション情報の抽出と評価

  • **制約の抽出と正規化**: チェック制約や NOT NULL 制約を抽出し、定数式畳み込み（eval_const_expressions）や変数番号の付け替え（ChangeVarNodes）を行ってプランナが比較可能な形式に正規化します。
  • **制約除外（Constraint Exclusion）の判定**: クエリの制限事項（baserestrictinfo）とテーブルの制約が矛盾しているかを評価し、矛盾している場合はそのリレーションのスキャンをスキップ可能と判定します。
  • **パーティション情報のセットアップ**: パーティションテーブルに対して、パーティションスキーマ、境界情報、パーティションキー式、パーティション制約をロードして RelOptInfo に設定します。

3. 一意インデックスの推論（ON CONFLICT）

  • **アービタイザインデックスの特定**: ON CONFLICT 句で指定された属性リストや制約名に基づき、競合解決の判断基準として使用可能な一意インデックス（または除外制約インデックス）をカタログから推論・特定します。

4. コスト・選択率・行数の見積もり支援

  • **サイズ見積もり**: テーブルやインデックスの物理ページ数、タプル数、および可視マップに基づく全可視ページ割合（allvisfrac）を見積もります。
  • **選択率の計算**: 制限演算子、結合演算子、またはブーリアン関数の選択率（Selectivity）を、カタログに登録されたオプティマイザサポート関数や選択率見積もり関数を呼び出して計算します。
  • **関数コストと行数の取得**: 関数の実行コスト（起動コストおよびタプルごとのコスト）や、セット返却関数（SRF）が返す見積もり行数を取得します。

重要なシンボル

リレーション・インデックス情報取得

  • **get_relation_info** (関数)

    • リレーションのカタログ情報を取得し、RelOptInfo のフィールド（インデックスリスト、拡張統計情報、FDWルーチン、並列ワーカー数など）を初期化する中核エントリーポイント。

  • **estimate_rel_size** (関数)

    • テーブル、インデックス、または外部テーブルの物理ページ数、タプル数、および可視化率を見積もる。

  • **get_relation_notnullatts** / **find_relation_notnullatts** (関数)

    • リレーションの NOT NULL 制約が定義された列番号のビットマップを抽出し、プランニングスコープ内のハッシュテーブルでキャッシュ・検索する。

  • **NotnullHashEntry** (構造体)

    • NOT NULL 列ビットマップをリレーションOIDごとにキャッシュするためのハッシュエントリ。

一意性・制約評価

  • **infer_arbiter_indexes** (関数)

    • ON CONFLICT 句の競合解決で使用する一意インデックスを推論・決定する。

  • **relation_excluded_by_constraints** (関数)

    • 制約除外（Constraint Exclusion）を適用し、クエリの制限事項とテーブル制約の矛盾からスキャンを省略可能か判定する。

  • **get_relation_constraints** (関数)

    • 検証済みのチェック制約、NOT NULL 制約、およびパーティション制約を収集し、プランナ用に正規化したリストを返す。

ターゲットリスト構築

  • **build_physical_tlist** (関数)

    • リレーション、サブクエリ、関数、CTEなどの物理的な列順序に一致するターゲットリスト（TargetEntry のリスト）を構築する。

  • **build_index_tlist** (関数)

    • インデックスの列（単純な列または式）に対応するターゲットリストを構築する。

選択率・コスト計算

  • **restriction_selectivity** / **join_selectivity** / **function_selectivity** (関数)

    • 演算子や関数の選択率を、システムカタログに登録された制限・結合選択率関数やサポート関数を呼び出して取得する。

  • **add_function_cost** / **get_function_rows** (関数)

    • 関数の実行コストや、セット返却関数が返す行数を見積もる。

制御フローとデータフロー

1. リレーション情報構築フロー (get_relation_info)

get_relation_info が呼び出されると、以下の流れで RelOptInfo が構築されます。

[get_relation_info]
  │
  ├── 1. table_open(relationObjectId, NoLock)
  │      (リカバリ中の臨時/ログなしテーブルへのアクセス制限などの安全性をチェック)
  │
  ├── 2. estimate_rel_size() ──> ページ数、タプル数、可視化率を見積もり RelOptInfo に設定
  │
  ├── 3. find_relation_notnullatts() ──> NOT NULL 列のビットマップをロード
  │
  ├── 4. RelationGetIndexList() ──> インデックス OID リストを取得
  │      │
  │      └── 各インデックスについてループ:
  │            ├── index_open(indexoid, rellockmode)
  │            ├── 有効性チェック (indisvalid, indcheckxmin)
  │            ├── IndexOptInfo 構造体の割り当てと初期化
  │            ├── インデックスキー、演算子家族、順序情報のコピー
  │            ├── ChangeVarNodes() & eval_const_expressions()
  │            │     (インデックス式・述語の変数番号を親テーブルの varno に書き換え、定数畳み込み)
  │            ├── build_index_tlist() ──> インデックスのターゲットリストを構築
  │            ├── インデックスサイズの見積もり (RelationGetNumberOfBlocks / estimate_rel_size)
  │            └── index_close(..., NoLock)
  │
  ├── 5. get_relation_statistics() ──> 拡張統計情報 (StatisticExtInfo) のロード
  │
  ├── 6. get_relation_foreign_keys() ──> 外部キー情報をロードし root->fkey_list に追加
  │
  ├── 7. (パーティションテーブルの場合) set_relation_partition_info()
  │      └── パーティションスキーマ、境界情報、キー式、パーティション制約を設定
  │
  └── 8. table_close(relation, NoLock)

2. 制約除外フロー (relation_excluded_by_constraints)

クエリの制限事項とテーブル制約を比較し、スキャンをスキップできるかを判定します。

[relation_excluded_by_constraints]
  │
  ├── 1. baserestrictinfo に定数 FALSE または NULL が含まれているかチェック
  │      └── 含まれていれば即座に true (スキャン不要) を返す
  │
  ├── 2. constraint_exclusion GUC パラメータのチェック
  │      └── OFF の場合、または PARTITION で対象がパーティション以外の場合は false を返す
  │
  ├── 3. 制限事項から揮発性（mutable）関数を含むものを除外し、
  │      predicate_refuted_by(safe_restrictions, safe_restrictions, true) で自己矛盾をチェック
  │
  ├── 4. get_relation_constraints() を呼び出して、適用可能な制約式リストを取得
  │      (チェック制約、NOT NULL 制約、パーティション制約を収集・正規化)
  │
  ├── 5. 制約式から揮発性関数を含むものを除外 (safe_constraints)
  │
  ├── 6. predicate_refuted_by(safe_constraints, rel->baserestrictinfo, false) を実行
  │      (制約条件がクエリの制限事項によって完全に否定されるかを強い否定で検証)
  │
  └── 7. 矛盾が証明されれば true、そうでなければ false を返す

読者向けメモ

メモリ管理とライフサイクル

  • get_relation_info や infer_arbiter_indexes などの内部で割り当てられる各種構造体（IndexOptInfo、ForeignKeyOptInfo、StatisticExtInfo など）やリストは、プランナのメモリコンテキスト（CurrentMemoryContext）で確保されます。これらはクエリのプランニングが完了するまで保持され、プランニング終了時に一括して解放されます。

ロックの不変条件

  • 本ファイル内の関数（table_open や index_open など）でリレーションやインデックスをオープンする際、原則として **NoLock** または呼び出し元から引き継いだロックモード（rellockmode）を使用します。
  • これは、パーサ、リライタ、あるいはプランナの上流フェーズ（expand_inherited_rtentry など）で、対象リレーションに対する適切なロックが既に取得されているという強い前提に基づいています。関数内での明示的なロック解放（table_close や index_close でのロック解除）は行われません。

エッジケースと制限事項

  • **リカバリ中の制限**: スタンバイ（リカバリ中）サーバでは、一時テーブル（temporary）やログなしテーブル（unlogged）はディスク上の状態が不確定であるため、アクセスしようとすると ERRCODE_FEATURE_NOT_SUPPORTED エラーをスローします。
  • **ON CONFLICT でのインデックス有効性**: ON CONFLICT のアービタイザ推論（infer_arbiter_indexes）では、同時実行中の REINDEX CONCURRENTLY を考慮するため、indisvalid が偽であっても indisready が真であれば候補として評価します。ただし、最終的な候補リストの中に少なくとも1つは有効な（indisvalid が真の）インデックスが含まれている必要があります。
  • **省略された領域**: 本ファイルはカタログからの「情報取得」に特化しているため、取得したインデックス情報を用いた具体的なパス生成ロジック（indxpath.c）や、詳細なコスト計算アルゴリズム（costsize.c）の具体的な実装は含まれておらず、それらは各専門モジュールに委ねられています。
