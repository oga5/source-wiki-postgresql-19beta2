src/backend/optimizer/util/plancat.c

概要

src/backend/optimizer/util/plancat.c は、PostgreSQLのオプティマイザ（Planner）がプラン作成時に必要とするカタログ情報（リレーション定義、インデックス、制約、拡張統計情報、パーティショニングスキーマ、および関数や演算子の選択性・コスト）をストレージ/リキャッシュから取得・抽象化して提供する中核ソースファイルである。

モジュール内での役割

src/backend/optimizer/util ディレクトリ配下に位置し、主にリレーションやインデックスのメタデータを RelOptInfo や IndexOptInfo などのプランナ内部データ構造へ結びつけるインターフェースとして機能する。costsize.c や indxpath.c などの他のオプティマイザモジュール群が必要とする物理的・統計的特性を供給する。

責務

  • **リレーションメタデータの構築**: リレーション（通常表、外部表、パーティション表）を開き、属性範囲、サイズ、並列ワーカー数、インデックス一覧、拡張統計情報、外部キー情報を RelOptInfo に設定する。
  • **インデックス情報の収集**: テーブル上の有効なインデックスを走査し、B-tree演算子族、式、述語、一意性フラグなどを解決して IndexOptInfo リストを構築する。
  • **制約とNOT NULLの処理**: チェック制約や NOT NULL 制約を取得し、プランナでの比較用に varno の書き換えや定数畳み込み、正規化を行う。
  • **制約除外（Constraint Exclusion）の判定**: リレーションの制約やベース制限句を用いて、スキャンが不要かを判定する。
  • **一意インデックスの推論（Arbiter Inference）**: ON CONFLICT 句（UPSERT）の指定に基づき、仕様に合致する一意インデックスを特定する。
  • **選択性・コスト・行数の見積もり**: 演算子、関数、ジョブ、リストに関する選択性関数（oprrest / oprjoin）やサポート関数を呼び出してコスト・行数・選択性を推計する。

重要なシンボル

リレーションおよびインデックス情報構築

  • RelOptInfo: プランナがクエリ内の各リレーションに関して保持する最適化情報構造体。本ファイルで基本属性・インデックス・統計情報・パーティション情報が埋め込まれる。
  • TargetEntry: クエリやターゲットリスト内の個々の式に対応するノード構造体。
  • get_relation_info: 指定されたリレーションのOIDと RelOptInfo を受け取り、属性範囲、インデックス、統計情報、外部キー、パーティション情報を一括取得して設定する。
  • estimate_rel_size: テーブル、インデックス、外部テーブルのページ数、タプル数、全可視フラクション（allvisfrac）を推計する。
  • get_rel_data_width: リレーションの平均タプルデータ幅を計算し、キャッシュ（attr_widths）を利用・更新する。
  • get_relation_data_width: get_rel_data_width の外部API版。リレーションを一時的にオープンして幅を計算する。

制約・NULL制約・除外処理

  • NotnullHashEntry: リレーションIDと NOT NULL カラムのビットマップ（notnullattnums）を紐付けるハッシュエントリ構造体。
  • get_relation_notnullatts: リレーションの NOT NULL 制約情報をスキャンし、PlannerInfo のハッシュテーブルにキャッシュする。
  • find_relation_notnullatts: キャッシュから指定リレーションの NOT NULL 属性ビットマップを検索・返却する。
  • relation_excluded_by_constraints: 制限句や制約条件を基に、矛盾や制約違反によりリレーションスキャン自体を省略可能か判定する。

UPSERT推論

  • infer_arbiter_indexes: ON CONFLICT 句の競合解決（Arbiter）仕様に一致する一意インデックス群のOIDリストを決定・返却する。
  • infer_collation_opclass_match: インデックスの属性や式が、推論指定された照合順序（Collation）および演算子クラス（Opclass）に合致するか検証する。

制御フローとデータフロー

1. **リレーション情報のロード (get_relation_info)**:

  • table_open でリレーションの relcache エントリーを取得し、回復処理中の一時・非永続テーブルアクセスなどの安全性を検証する。
  • estimate_rel_size を呼び出してページ数・タプル数を見積もり、有効なインデックス群を走査して IndexOptInfo を構築・連結する。
  • 外部表（RELKIND_FOREIGN_TABLE）やパーティションテーブルの場合は、対応する FDW ルーチンやパーティション記述子・制約を設定する。

    • 2. **制約除外 (relation_excluded_by_constraints)**:

  • リレーションのベース制限句（baserestrictinfo）に矛盾する定数（FALSE や NULL）が含まれていないか走査する。
  • predicate_refuted_by を用いて、制限句同士またはテーブルのチェック制約・NOT NULL 制約と制限句の間の矛盾を論理的に検証し、スキャン除外の可否を決定する。

    • 3. **インデックス推論 (infer_arbiter_indexes)**:

  • onConflict->arbiterElems または命名された制約からターゲットの属性・式を抽出し、対象テーブルの有効なインデックス一覧を走査する。
  • 式の一致、infer_collation_opclass_match による照合順序/演算子クラスの一致、部分インデックスの述語包含関係（predicate_implied_by）を検証して適合するインデックスを決定する。

読者向けメモ

  • **メモリ所有権**: get_relation_info 等で構築される IndexOptInfo, RelOptInfo の各種配列やリストは、通常プランナのメモリコンテキスト（PlannerInfo が紐づくコンテキスト）上に割り当てられ、プランナのライフサイクルに従う。
  • **ロックの前提**: 呼び出し元がすでにリリースのリレーションに対する適切なロック（リライターや expand_inherited_rtentry によって取得済み）を保持しているため、本ファイル内の多くの関数は NoLock で table_open を行っている。
  • **インデックス順序の歴史的理由**: get_relation_info 内のインデックスリスト追加には lcons() が使われており、同一評価のインデックス間でのプランナ挙動の互換性を維持している。
