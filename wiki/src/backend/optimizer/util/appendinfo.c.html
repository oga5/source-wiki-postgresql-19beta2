src/backend/optimizer/util/appendinfo.c

概要

src/backend/optimizer/util/appendinfo.c は、PostgreSQLのオプティマイザにおいて、継承ツリーや UNION ALL サブクエリ（アペンドリレーション）の親リレーションと子リレーションの間で、式や属性番号、リレーション識別子（Relids）をマッピング・変換するためのルーチン群を提供します。また、UPDATE、DELETE、MERGE 操作で使用される行識別子（Row-identity 変数 / ROWID_VAR）の管理も行います。

モジュール内での役割

src/backend/optimizer/util ディレクトリ配下に属し、主にプランナのプリプロセッサやアペンド関係のサイズ・パス構築フェーズにおいて、親テーブル基準で構築されたクエリツリーや式を各子テーブル（パーティションや継承子）向けに書き換える役割を担います。

責務

  • **アペンドリレーション情報の構築**: 親・子リレーション間のメタデータや列のマッピングを保持する AppendRelInfo ノードの生成。
  • **式・属性の変換（単一および多階層）**: 親リレーションの Var や属性番号を、対応する子リレーションの Var や属性番号へ変換する（adjust_appendrel_attrs, adjust_inherited_attnums）。
  • **リレーション識別子（Relids）の調整**: プランナが扱う Relids（Bitmapset）内の親テーブルの RT インデックスを子テーブルのものに置換する（adjust_child_relids）。
  • **行識別子変数（Row Identity Variables）の管理**: UPDATE/DELETE/MERGE で必要となる ctid や wholerow などの行特定用変数を管理し、ROWID_VAR を介して各子リレーションへ伝播・展開する仕組みを提供する。

重要なシンボル

1. 構造体

  • adjust_appendrel_attrs_context: adjust_appendrel_attrs_mutator がツリー走査時に参照するコンテキスト。PlannerInfo *root, int nappinfos, AppendRelInfo **appinfos を保持する。

2. アペンドリレーション情報・属性変換ファミリ

  • make_append_rel_info: 親・子リレーションのペアから AppendRelInfo ノードを構築し、列の翻訳リストを初期化する。
  • make_inh_translation_list: 継承関係やパーティションの子リレーションについて、親の列から子の列への逆引き配列（parent_colnos）および翻訳済み変数リスト（translated_vars）を構築する（内部関数）。
  • adjust_appendrel_attrs: 指定された式またはクエリ内の親リレーションを指す Var などを子リレーション向けにコピー・変換するエントリーポイント。
  • adjust_appendrel_attrs_mutator: expression_tree_mutator のコールバック関数。Var, PlaceHolderVar, RestrictInfo, PathTarget などを走査し、親リレーションから子リレーションへの置換を再帰的に適用する。
  • adjust_appendrel_attrs_multilevel: 複数階層（中間親を挟む）をまたいで子リレーションまで属性変換を適用する。

3. Relids および属性番号調整ファミリ

  • adjust_child_relids: Relids（Bitmapset）内の親 relid を対応する子の relid に置換する。
  • adjust_child_relids_multilevel: 複数階層をまたいで Relids の置換を行う。
  • adjust_inherited_attnums: 属性番号の整数リストを親から子へ翻訳する。
  • adjust_inherited_attnums_multilevel: 複数階層をまたいで属性番号リストの翻訳を行う。

4. 行識別子（Row Identity）管理ファミリ

  • add_row_identity_var: UPDATE/DELETE/MERGE クエリで用いる行識別子列を登録する。既存の同名・同内容の識別子があれば共有し、なければ ROWID_VAR を用いたプレースホルダとして root->row_identity_vars に追加する。
  • add_row_identity_columns: 対象リレーションの種別（通常テーブル、マテリアライズドビュー、パーティションテーブル、外部テーブル）やトリガーの有無に応じて、ctid や wholerow などの標準的な行識別子を登録する。
  • distribute_row_identity_vars: 継承された UPDATE/DELETE/MERGE において、特定された行識別子変数を最上位のターゲットリレーションの reltarget に強制的に組み込み、後続の展開フェーズで子リレーションに継承させる。

制御フローとデータフロー

1. **初期化・構造生成**:

  • プランナが継承ツリーを展開する際、親・子のリレーション関係ごとに make_append_rel_info が呼ばれ、列名・型・照合順序の一致を確認しながら AppendRelInfo が作成される。

    • 2. **式の変換フロー**:

  • adjust_appendrel_attrs が呼び出されると、内部で adjust_appendrel_attrs_mutator が起動する。
  • 式ツリー内の Var ノードに遭遇した場合、保持する appinfos 配列と照合し、一致すれば appinfo->translated_vars から子テーブル用の Var（または ConvertRowtypeExpr や RowExpr）を取得・置換する。
  • RestrictInfo や PathTarget などのオプティマイザ固有ノードも同様に走査され、内部の clause_relids や式が子リレーション向けに調整される。

    • 3. **行識別子のフロー**:

  • add_row_identity_columns により ctid や wholerow が add_row_identity_var を通じて登録され、クエリの processed_tlist に ROWID_VAR を参照するエントリとして追加される。
  • その後 distribute_row_identity_vars が呼ばれ、プランの構築過程で各子リレーションに対応する実変数へ置き換えられる。

読者向けメモ

  • **メモリ管理**: find_appinfos_by_relids や adjust_appendrel_attrs_multilevel などで動的に割り当てられた配列（palloc 製）は、呼び出し側または処理完了後に pfree される設計になっています。
  • **制約事項**: adjust_appendrel_attrs はサブリンクがサブプランに変換された後のフェーズで適用されるため、Query ノードや SubLink ノードへの再帰処理は想定されていません（ソース内の Assert(!IsA(node, Query)) 等でガードされています）。
