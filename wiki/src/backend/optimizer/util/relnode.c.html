src/backend/optimizer/util/relnode.c

概要

src/backend/optimizer/util/relnode.c は、PostgreSQLのクエリパーサとオプティマイザにおいて、問い合わせ内の関係（Relation）を表す RelOptInfo ノード、結合関係、および上限関係（Upper Relation）の検索、構築、管理を行う中心的なソースファイルです。ベース関係配列の初期化、結合関係の作成、パーティション分割された結合（Partitionwise Join）の判定・設定、および早期集約（Eager Aggregation）の解析とターゲット構築を担います。

モジュール内での役割

オプティマイザの util サブシステム内において、本書で扱う relnode.c は、プランナが使用する内部データ構造（特に RelOptInfo）のライフサイクル管理の基盤を提供します。周辺の pathnode.c、clauses.c、restrictinfo.c と緊密に連携し、コスト見積もりやパス生成の前提となるリレーションのメタデータや制約リストを供給します。

責務

  • リレーション配列の管理: ベース関係、範囲変数（RTE）、および追加リレーション（AppendRelInfo）を高速にアクセスするための配列（simple_rel_array, simple_rte_array, append_rel_array）のセットアップと動的拡張。
  • ベース関係ノードの構築: テーブル、サブクエリ、関数などの各RTEに対する RelOptInfo の生成と初期化、プラグイン用フックの適用、およびダミー関係の判定。
  • 結合関係の構築とハッシュ化: 2つのリレーションから結合関係（RelOptInfo）を導出・検索し、効率的な検索のための補助ハッシュテーブル（JoinHashEntry）の構築。
  • 制約と結合情報の処理: 結合関係における制約リスト（restrictlist）および結合リスト（joininfo）の構築と重複排除。
  • パーティション分割結合のサポート: パーティションスキームのマッチング確認と、等価結合条件に基づくパーティション分割結合の初期化。
  • 早期集約（Eager Aggregation）の管理: 部分集約をベース関係や結合関係のレベルで早期にプッシュダウン可能か判定し、対応する RelAggInfo やターゲットを構築する。

重要なシンボル

リレーション管理・検索

  • RelOptInfo: クエリの最適化対象となる単一の関係、結合関係、または上限関係の特性（コスト、パス、ターゲットリスト、制約など）を保持する中心的な構造体。
  • simple_rel_array: 範囲変数インデックス（RTインデックス）をキーとしてベース関係の RelOptInfo に迅速にアクセスするための配列。
  • simple_rte_array: RTインデックスから対応する RangeTblEntry を迅速に引くための配列。
  • append_rel_array: 子テーブル（継承やUNION ALLの展開先）の AppendRelInfo にアクセスするための配列。
  • setup_simple_rel_arrays: クエリの rtable および append_rel_list を走査して、simple_rel_array、simple_rte_array、append_rel_array を初期化・割り当てする。
  • expand_planner_arrays: 継承の展開などでRTE数が増加した際に、プランナの各配列サイズを動的に拡張する。
  • find_base_rel: 指定された relid に対応する既存のベース関係/その他の関係の RelOptInfo を取得する（存在しない場合はエラー）。
  • find_base_rel_noerr: エラーを発生させずにベース関係を検索し、存在しない場合は NULL を返す。
  • find_base_rel_ignore_join: 外部結合の relid を無視してベース関係を安全に検索する。

結合関係の構築とハッシュ

  • JoinHashEntry: 結合関係の迅速なルックアップを行うためのハッシュテーブルのエントリ構造体。join_relids（ハッシュキー）と join_rel へのポインタを保持する。
  • build_join_rel: 2つの子リレーションから新しい結合関係（RELOPT_JOINREL）を構築、または既存のものを返し、制約リストや並列安全性、パーティション情報を設定する。
  • find_join_rel: 結合対象の relids セットに一致する結合関係を、リスト線形探索またはハッシュテーブル（root->join_rel_hash）から高速に検索する。

シリアル番号・インデックス関連

  • rinfo_serial: 制限事項（RestrictInfo）のシリアル番号（※本ファイルや関連処理において制限・制約の追跡に利用される）。

制御フローとデータフロー

1. プランナ初期化時: setup_simple_rel_arrays が呼び出され、クエリの rtable を基に simple_rel_array と simple_rte_array がアロケートされる。append_rel_list が存在する場合は append_rel_array も構築される。 2. スキャン段階: オプティマイザが各ベース関係の最適化を行う際、build_simple_rel が呼び出されて RelOptInfo がインスタンス化され、カタログ情報の取得（get_relation_info）やプラグインフックの適用が行われる。 3. 結合探索段階: ボトムアップの結合探索中に build_join_rel が呼ばれ、既存の結合関係が find_join_rel（または必要に応じて build_join_rel_hash で作成されたハッシュ）で検索される。存在しない場合は新規作成され、build_joinrel_restrictlist や build_joinrel_joinlist により制約事項と結合情報が整理される。 4. パーティションおよび早期集約の評価: 結合関係やベース関係に対して build_joinrel_partition_info や create_rel_agg_info が実行され、条件を満たす場合はパーティション分割結合やプッシュダウン可能な部分集約のパスが組み込まれる。

読者向けメモ

  • メモリ管理: RelOptInfo や関連する配列（simple_rel_array など）は、プランナの実行コンテキスト（通常は PlannerInfo が割り当てられたメモリコンテキスト）上で palloc / palloc0 を用いて割り当てられます。
  • ハッシュ化の閾値: find_join_rel 内において、結合関係のリスト長が 32 を超えた場合に自動的に build_join_rel_hash が呼び出され、O(1) のハッシュルックアップに切り替わります。
  • プレースホルダと変数安全性: 外部結合やグループ化のコンテキストにおいて、変数の varnullingrels や phnullingrels の操作が行われるため、結合順序の変更に伴う NULL 拡張の整合性が厳密に維持されます。
