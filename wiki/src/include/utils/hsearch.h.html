src/include/utils/hsearch.h

概要

PostgreSQL のダイナミックハッシュテーブル (dynahash.c) の公開インターフェース定義を提供するヘッダーファイルです。メモリ内および共有メモリ上のハッシュテーブル作成、検索、走査、ライフサイクル管理などの型や関数プロトタイプを定義しています。

モジュール内での役割

src/include/utils サブシステムの一部として、PostgreSQL 内部で頻繁に使用される汎用ハッシュ機構の契約を定義します。実装コード本体は含まれておらず、定義はすべて dynahash.c に委譲されています。

責務

  • ハッシュテーブルの構築・操作に必要なコールバック関数型（比較、コピー、ハッシュ値計算、アロケーション）の定義。
  • ハッシュエントリの内部表現（HASHELEMENT）と制御構造体（HASHCTL, HASH_SEQ_STATUS 等）のレイアウト提供。
  • ハッシュアクション種別（HASHACTION）および設定用フラグ（HASH_*）のマクロ定義。
  • ハッシュテーブルの検索、走査、統計、トランザクション連動処理のエントリポイント宣言。

重要なシンボル

コールバックおよび基本型

  • HashAllocFunc: カスタムメモリ割り当て関数のシグネチャ。カスタムアロケータを使用する場合、デフォルトのアロケータとは異なり個別解放関数APIが存在しないため、テーブル全体破棄以外での個別解放制限に注意が必要です。
  • Size: オブジェクトサイズやキー長を表す符号なし整数型（通常 size_t 相当）。

ハッシュ構造体・制御定義

  • HASHELEMENT: バケット内の次のエントリへのポインタ（link）と、エントリのハッシュ関数結果（hashvalue）を保持するハッシュエントリのプライベートプレフィックス。ユーザーデータの直前に配置されます。
  • HASHHDR: ハッシュテーブルのヘッダー構造体（不透明型）。詳細は dynahash.c にカプセル化されています。
  • HTAB: ハッシュテーブル全体の制御構造体（不透明型）。
  • HASHCTL: hash_create に渡すパラメータ構造体。HASH_* フラグの指定に応じて、パーティション数、キーサイズ、エントリサイズ、カスタム関数、メモリコンテキスト、共有メモリ位置などを設定します。

列挙型・状態管理

  • HASHACTION: hash_search の動作を指定する列挙型。HASH_FIND（検索）、HASH_ENTER（挿入または既存返却）、HASH_REMOVE（削除）、HASH_ENTER_NULL（キーが見つからない場合に NULL を許容する挿入）を定義します。
  • HASH_SEQ_STATUS: ハッシュテーブルの順次走査（シーケンシャルスキャン）の状態を保持する構造体。

主要操作関数

  • hash_create: 指定されたパラメータとフラグに基づき、新しいハッシュテーブルを作成して HTAB ポインタを返します。
  • hash_get_num_entries: ハッシュテーブルに現在格納されているエントリの総数を返します。
  • hash_stats: 指定したハッシュテーブルの使用統計情報をログやデバッグ出力に出力します。
  • hash_update_hash_key: 既存のエントリのハッシュキーを新しいキーに更新します。

制御フローとデータフロー

  • **ハッシュテーブル作成**: 呼び出し元が HASHCTL に必要なフィールドを設定し、対応する HASH_* フラグを立てて hash_create を呼び出します。これにより初期化された HTAB が返されます。
  • **検索と操作**: hash_search または hash_search_with_hash_value に HTAB、キーポインタ、HASHACTION を渡すことで、エントリの検索・追加・削除が行われます。見つかったかどうかは foundPtr を通じて通知されます。
  • **順次走査**: hash_seq_init または hash_seq_init_with_hash_value で HASH_SEQ_STATUS を初期化した後、hash_seq_search を繰り返し呼び出すことで全バケットのエントリを走査し、最後に hash_seq_term で終了処理を行います。
  • **トランザクション統合**: AtEOXact_HashTables および AtEOSubXact_HashTables により、トランザクションやサブトランザクションの終了時（コミット/アボート）に紐付くハッシュテーブルのクリーンアップや整合性が保たれます。

読者向けメモ

  • **メモリレイアウト**: HASHELEMENT の直後に呼び出し側のデータが MAXALIGN 境界で配置され、ハッシュキーは通常そのデータ構造の先頭に位置する設計になっています。
  • **メモリオーナーシップ**: デフォルト以外のカスタムアロケータを使用する場合、個別エントリ単位の解放 API が存在しないため、hash_destroy による一括破棄が前提となります。
