Overview

このシステムは何か

postgresql-19beta2 は、2575個の索引済みファイルと310個の推定モジュールを持つ、高度に拡張可能で堅牢なオープンソースのリレーショナルデータベース管理システム（RDBMS）です。

アーキテクチャ概観

本システムは、クライアント接続の受付とプロセス管理を行う src/backend/postmaster、SQLクエリの解析を行う src/backend/parser、実行プランを生成する src/backend/optimizer、プランを実行する src/backend/executor、メタデータを管理する src/backend/catalog、トランザクションとWALを管理する src/backend/access/transam、そして低水準のバッファ・ストレージ制御を行う src/backend/storage の各コンポーネントが、ディレクトリ構造とモジュール境界に沿って階層的に結合されています。

実行時ライフサイクル

1. **起動と初期化**: src/backend/main/main.c の main 関数から開始され、環境の初期化を経て src/backend/postmaster/postmaster.c がスーパーバイザ（Postmaster）として起動します。 2. **プロセスフォーク**: Postmaster は、バックグラウンドプロセス（src/backend/postmaster/checkpointer.c, src/backend/postmaster/bgwriter.c, src/backend/postmaster/autovacuum.c 等）を起動し、クライアントからの接続要求に応じてバックエンドプロセスをフォークします。 3. **リクエストディスパッチ**: フォークされたバックエンドでは、src/backend/tcop/postgres.c がメインループとなり、クライアントからのクエリを受信・解析します。 4. **クエリ処理パイプライン**:

  • src/backend/parser/parser.c によりパースツリーが生成され、意味解析（src/backend/parser/analyze.c）が行われます。
  • src/include/optimizer/planner.h に定義されたプランナーインターフェースを介して最適化され、実行プランが作成されます。
  • src/backend/executor/execMain.c により実行プランが実行され、必要に応じて src/backend/access や src/backend/storage を介してデータが読み書きされます。

  6. File: src/backend/executor/nodeHash.c制御フローとデータフロー

    1. **初期化**:

    • ExecInitHash でプラン状態が作られ、親の nodeHashjoin.c から ExecHashTableCreate が呼ばれて HashJoinTable とメモリコンテキスト（hashCxt, batchCxt, spillCxt）が構築される。

      • 2. **構築フェーズ (MultiExecHash)**:

    • **パラレル非依存 (MultiExecPrivateHash)**: 外側サブプランからタプルをフェッチし、ハッシュ値を計算。スキューバケットまたは通常バケットに挿入（ExecHashTableInsert）。メモリ上限を超えた場合は ExecHashIncreaseNumBatches によりバッチ数を倍増させ、溢れたタプルを一時ファイル（innerBatchFile）へスピルする。
    • **パラレル対応 (MultiExecParallelHash)**: バリア同期（build_barrier）を用いて複数バックエンドで協調動作。共有ハッシュテーブル（バッチ0）への挿入（ExecParallelHashTableInsert）を行い、必要に応じてバッチ数やバケット数を拡大・再パーティション化する。

      • 3. **プローブおよび後処理**:

    • 構築完了後、親のハッシュ結合ノードがバケットスキャン（ExecScanHashBucket 等）を行い結合を実行する。終了時は ExecEndHash および ExecShutdownHash でリソースとインストルメンテーションが回収される。
  7. File: src/backend/executor/nodeHashjoin.c制御フローとデータフロー

    1. **初期化 (ExecInitHashJoin)**:

    • 結合条件（joinqual）、フィルタ条件（otherqual）、ハッシュキーとハッシュ関数を初期化します。
    • outerPlan と innerPlan（Hashノード）を初期化し、必要に応じて欠損行（null fill）用のスロットを割り当てます。

      • 2. **実行ループ (ExecHashJoinImpl のステートマシン)**:

    • HJ_BUILD_HASHTABLE: 初回のみ、Hashノードを実行してハッシュテーブルを構築します。並列の場合はバリア（build_barrier）を用いて協調動作します。
    • HJ_NEED_NEW_OUTER: 外側リレーションからタプルを取得し、ハッシュ値を計算します。現在のバッチに属さない場合は一時ファイルへスポート（ExecHashJoinSaveTuple）し、次の外側タプルへ進みます。
    • HJ_SCAN_BUCKET: ハッシュテーブルの対応するバケツをスキャンして候補タプルを探し、結合条件（joinqual）および非結合条件（otherqual）を評価してマッチすれば射影結果（ExecProject）を返します。
    • HJ_FILL_OUTER_TUPLE / HJ_FILL_INNER_TUPLES / HJ_FILL_OUTER_NULL_TUPLES / HJ_FILL_INNER_NULL_TUPLES: 外部結合やアンチ結合において、マッチしなかった行や null キー行を補完・出力します。
    • HJ_NEED_NEW_BATCH: 現在のバッチが終了した場合、次のバッチが存在すれば ExecHashJoinNewBatch（または並列版）を呼び出して次の内側バッチをハッシュテーブルに再ロードし、外側ファイルを開き直します。

  11. File: src/backend/optimizer/geqo/geqo_eval.c制御フローとデータフロー

    1. **エントリー（geqo_eval）**:

    • geqo_main.c 等から呼び出され、専用の GEQO メモリコンテキストを作成。
    • PlannerInfo 内の join_rel_list の長さを保存し、join_rel_hash を一時的に退避（評価中の破壊的変更を防ぐため）。

      • 2. **ツリー構築（gimme_tree）**:

    • ツアー内の各遺伝子（リレーションID）を順に読み込み、サイズ1の Clump を作成。
    • merge_clump を呼び出し、desirable_join が真（結合条件あり）となる既存クランプと優先的にマージ。

      • 3. **強制マージ（Force Join）**:

    • ツアー走査後、複数のクランプが残っている場合（結合条件がない孤立したリレーションなど）、force = true で merge_clump を再実行し、直積を許容して1つのクランプに強制結合。

      • 4. **コスト算出とクリーンアップ**:

    • 最終的に1つの結合リレーションに統合できれば、その最安パスのコスト（cheapest_total_path->total_cost）を適応度として返却。失敗した場合は DBL_MAX を返却。
    • 退避していた join_rel_list を元の長さに切り詰め、GEQO メモリコンテキストを削除。
  12. File: src/backend/optimizer/geqo/geqo_main.c制御フローとデータフロー

    1. **初期化フェーズ**:

    • GetPlannerExtensionId を通じて拡張IDを取得し、プライベートデータと乱数シード（geqo_set_seed）を設定。
    • gimme_pool_size と gimme_number_generations でGAの規模を決定。
    • alloc_pool と random_init_pool により個体群プールを作成し、sort_pool で適合度順にソート。

      • 2. **世代交代ループ**:

    • geqo_selection を呼び出し、親個体（momma, daddy）を選択。
    • 条件付きコンパイル（ERX, PMX, CX, PX, OX1, OX2 のいずれか）に応じて、対応する交叉関数を実行して子個体（kid）を生成。
    • geqo_eval で子個体のフィットネス（コスト）を評価し、spread_chromo でプールへ挿入。

      • 3. **終了フェーズ**:

    • プールの先頭（最良の個体）から gimme_tree を使って最適な RelOptInfo クエリツリーを復元。
    • 割り当てられた個体・プール・テーブル等のメモリを解放し、結果のプランを返却。
