3Plan Advice
4===========
5
6This module implements a mini-language for "plan advice" that allows for
7control of certain key planner decisions. Goals include (1) enforcing plan
8stability (my previous plan was good and I would like to keep getting a
9similar one) and (2) allowing users to experiment with plans other than
10the one preferred by the optimizer. Non-goals include (1) controlling
11every possible planner decision and (2) forcing consideration of plans
12that the optimizer rejects for reasons other than cost. (There is some
13room for bikeshedding about what exactly this non-goal means: what if
14we skip path generation entirely for a certain case on the theory that
15we know it cannot win on cost? Does that count as a cost-based rejection
16even though no cost was ever computed?)
17
18Generally, plan advice is a series of whitespace-separated advice items,
19each of which applies an advice tag to a list of advice targets. For
20example, "SEQ_SCAN(foo) HASH_JOIN(bar@ss)" contains two items of advice,
21the first of which applies the SEQ_SCAN tag to "foo" and the second of
22which applies the HASH_JOIN tag to "bar@ss". In this simple example, each
23target identifies a single relation; see "Relation Identifiers", below.
24Advice tags can also be applied to groups of relations; for example,
25"HASH_JOIN(baz (bletch quux))" applies the HASH_JOIN tag to the single
26relation identifier "baz" as well as to the 2-item list containing
27"bletch" and "quux".
28
29Critically, this module knows both how to generate plan advice from an
30already-existing plan, and also how to enforce it during future planning
31cycles. Everything it does is intended to be "round-trip safe": if you
32generate advice from a plan and then feed that back into a future planning
33cycle, each piece of advice should be guaranteed to apply to exactly the
34same part of the query from which it was generated without ambiguity or
35guesswork, and it should successfully enforce the same planning decision that
36led to it being generated in the first place. Note that there is no
37intention that these guarantees hold in the presence of intervening DDL;
38e.g. if you change the properties of a function so that a subquery is no
39longer inlined, or if you drop an index named in the plan advice, the advice
40isn't going to work any more. That's expected.
41
42This module aims to force the planner to follow any provided advice without
43regard to whether it appears to be good advice or bad advice. If the
44user provides bad advice, whether derived from a previously-generated plan
45or manually written, they may get a bad plan. We regard this as user error,
46not a defect in this module. It seems likely that applying advice
47judiciously and only when truly required to avoid problems will be a more
48successful strategy than applying it with a broad brush, but users are free
49to experiment with whatever strategies they think best.

51Relation Identifiers
52====================
53
54Uniquely identifying the part of a query to which a certain piece of
55advice applies is harder than it sounds. Our basic approach is to use
56relation aliases as a starting point, and then disambiguate. There are
57three ways that the same relation alias can occur multiple times:
58
591. It can appear in more than one subquery.
60
612. It can appear more than once in the same subquery,
62   e.g. (foo JOIN bar) x JOIN foo.
63
643. The table can be partitioned.
65
66Any combination of these things can occur simultaneously. Therefore, our
67general syntax for a relation identifier is:
68
69alias_name#occurrence_number/partition_schema.partition_name@plan_name
70
71All components except for the alias_name are optional and included only
72when required. When a component is omitted, the associated punctuation
73must also be omitted. Occurrence numbers are counted ignoring children of
74partitioned tables. When the generated occurrence number is 1, we omit
75the occurrence number. The partition schema and partition name are included
76only for children of partitioned tables. In generated advice, the
77partition_schema is always included whenever there is a partition_name,
78but user-written advice may mention the name and omit the schema. The
79plan_name is omitted for the top-level PlannerInfo.

81Scan Advice
82===========
83
84For many types of scan, no advice is generated or possible; for instance,
85a subquery is always scanned using a subquery scan. While that scan may be
86elided via setrefs processing, this doesn't change the fact that only one
87basic approach exists. Hence, scan advice applies mostly to relations, which
88can be scanned in multiple ways.
89
90We tend to think of a scan as targeting a single relation, and that's
91normally the case, but it doesn't have to be. For instance, if a join is
92proven empty, the whole thing may be replaced with a single Result node
93which, in effect, is a degenerate scan of every relation in the collapsed
94portion of the join tree. Similarly, it's possible to inject a custom scan
95in such a way that it replaces an entire join. If we ever emit advice
96for these cases, it would target sets of relation identifiers surrounded
97by parentheses, e.g., SOME_SORT_OF_SCAN(foo (bar baz)) would mean that
98the given scan type would be used for foo as a single relation and also the
99combination of bar and baz as a join product. We have no such cases at
100present.
101
102For index and index-only scans, both the relation being scanned and the
103index or indexes being used must be specified. For example, INDEX_SCAN(foo
104foo_a_idx bar bar_b_idx) indicates that an index scan (not an index-only
105scan) should be used on foo_a_idx when scanning foo, and that an index scan
106should be used on bar_b_idx when scanning bar.
107
108Bitmap heap scans currently do not allow for an index specification:
109BITMAP_HEAP_SCAN(foo bar) simply means that each of foo and bar should use
110some sort of bitmap heap scan.
111
112There is a special DO_NOT_SCAN() advice tag which says that a certain
113relation shouldn't be scanned at all. This is used to control which of
114two choices is selected when an AlternativeSubPlan is resolved, and
115whether or not a MinMaxAggPath is chosen. Control over upper planner
116behavior is generally out-of-scope at the moment, but these cases had
117to be handled to prevent test_plan_advice failures in the buildfarm.
118
119Join Order Advice
120=================
121
122The JOIN_ORDER tag specifies the order in which several tables that are
123part of the same join problem should be joined. Each subquery (except for
124those that are inlined) is a separate join problem. Within a subquery,
125partitionwise joins can create additional, separate join problems. Hence,
126queries involving partitionwise joins may use JOIN_ORDER() many times.
127
128We take the canonical join structure to be an outer-deep tree, so
129JOIN_ORDER(t1 t2 t3) says that t1 is the driving table and should be joined
130first to t2 and then to t3. If the join problem involves additional tables,
131they can be joined in any order after the join between t1, t2, and t3 has
132been constructed. Generated join advice always mentions all tables
133in the join problem, but manually written join advice need not do so.
134
135For trees which are not outer-deep, parentheses can be used. For example,
136JOIN_ORDER(t1 (t2 t3)) says that the top-level join should have t1 on the
137outer side and a join between t2 and t3 on the inner side. That join should
138be constructed so that t2 is on the outer side and t3 is on the inner side.
139
140In some cases, it's not possible to fully specify the join order in this way.
141For example, if t2 and t3 are being scanned by a single custom scan or foreign
142scan, or if a partitionwise join is being performed between those tables, then
143it's impossible to say that t2 is the outer table and t3 is the inner table,
144or the other way around; it's just undefined. In such cases, we generate
145join advice that uses curly braces, intending to indicate a lack of ordering:
146JOIN_ORDER(t1 {t2 t3}) says that the uppermost join should have t1 on the outer
147side and some kind of join between t2 and t3 on the inner side, but without
148saying how that join must be performed or anything about which relation should
149appear on which side of the join, or even whether this kind of join has sides.
150
151Join Method Advice
152==================
153
154Tags such as NESTED_LOOP_PLAIN specify the method that should be used to
155perform a certain join. More specifically, NESTED_LOOP_PLAIN(x (y z)) says
156that the plan should put the relation whose identifier is "x" on the inner
157side of a plain nested loop (one without materialization or memoization)
158and that it should also put a join between the relation whose identifier is
159"y" and the relation whose identifier is "z" on the inner side of a nested
160loop. Hence, for an N-table join problem, there will be N-1 pieces of join
161method advice; no join method advice is required for the outermost
162table in the join problem.
163
164Considering that we have both join order advice and join method advice,
165it might seem natural to say that NESTED_LOOP_PLAIN(x) should be redefined
166to mean that x should appear by itself on one side or the other of a nested
167loop, rather than specifically on the inner side, but this definition appears
168useless in practice. It gives the planner too much freedom to do things that
169bear little resemblance to what the user probably had in mind. This makes
170only a limited amount of practical difference in the case of a merge join or
171unparameterized nested loop, but for a parameterized nested loop or a hash
172join, the two sides are treated very differently, and saying that a certain
173relation should be involved in one of those operations without saying which
174role it should take isn't saying much.
175
176This choice of definition implies that join method advice also imposes some
177join order constraints. For example, given a join between foo and bar,
178HASH_JOIN(bar) implies that foo is the driving table. Otherwise, it would
179be impossible to put bar beneath the inner side of a Hash Join.
180
181Note that, given this definition, it's reasonable to consider deleting the
182join order advice but applying the join method advice. For example,
183consider a star schema with tables fact, dim1, dim2, dim3, dim4, and dim5.
184The automatically generated advice might specify JOIN_ORDER(fact dim1 dim3
185dim4 dim2 dim5) HASH_JOIN(dim2 dim4) NESTED_LOOP_PLAIN(dim1 dim3 dim5).
186Deleting the JOIN_ORDER advice allows the planner to reorder the joins
187however it likes while still forcing the same choice of join method. This
188seems potentially useful, and is one reason why a unified syntax that controls
189both join order and join method in a single locution was not chosen.
190
191Advice Completeness
192===================
193
194An essential guiding principle is that no inference may be made on the basis
195of the absence of advice. The user is entitled to remove any portion of the
196generated advice which they deem unsuitable or counterproductive and the
197result should only be to increase the flexibility afforded to the planner.
198This means that if advice can say that a certain optimization or technique
199should be used, it should also be able to say that the optimization or
200technique should not be used. We should never assume that the absence of an
201instruction to do a certain thing means that it should not be done; all
202instructions must be explicit.
203
204Semijoin Uniqueness
205===================
206
207Faced with a semijoin, the planner considers both a direct implementation
208and a plan where the one side is made unique and then an inner join is
209performed. We emit SEMIJOIN_UNIQUE() advice when this transformation occurs
210and SEMIJOIN_NON_UNIQUE() advice when it doesn't. These items work like
211join method advice: the inner side of the relevant join is named, and the
212chosen join order must be compatible with the advice having some effect.
213
214Partitionwise
215=============
216
217PARTITIONWISE() advice can be used to specify both those partitionwise joins
218which should be performed and those which should not be performed; the idea
219is that each argument to PARTITIONWISE specifies a set of relations that
220should be scanned partitionwise after being joined to each other and nothing
221else. Hence, for example, PARTITIONWISE((t1 t2) t3) specifies that the
222query should contain a partitionwise join between t1 and t2 and that t3
223should not be part of any partitionwise join. If there are no other rels
224in the query, specifying just PARTITIONWISE((t1 t2)) would have the same
225effect, since there would be no other rels to which t3 could be joined in
226a partitionwise fashion.
227
228Parallel Query (Gather, etc.)
229=============================
230
231Each argument to GATHER() or GATHER_MERGE() is a single relation or an
232exact set of relations on top of which a Gather or Gather Merge node,
233respectively, should be placed. Each argument to NO_GATHER() is a single
234relation that should not appear beneath any Gather or Gather Merge node;
235that is, parallelism should not be used.
236
237Implicit Join Order Constraints
238===============================
239
240When JOIN_ORDER() advice is not provided for a particular join problem,
241other pieces of advice may still incidentally constrain the join order.
242For example, a user who specifies HASH_JOIN((foo bar)) is explicitly saying
243that there should be a hash join with exactly foo and bar on the inner
244side of it, but that also implies that foo and bar must be joined to
245each other before either of them is joined to anything else. Otherwise,
246the join the user is attempting to constrain won't actually occur in the
247query, which ends up looking like the system has just decided to ignore
248the advice altogether.

250Future Work
251===========
252
253We don't handle choice of aggregation: it would be nice to be able to force
254sorted or grouped aggregation. I'm guessing this can be left to future work.
255
256More seriously, we don't know anything about eager aggregation, which could
257have a large impact on the shape of the plan tree. XXX: This needs some study
258to determine how large a problem it is, and might need to be fixed sooner
259rather than later.
260
261We don't offer any control over estimates, only outcomes. It seems like a
262good idea to incorporate that ability at some future point, as pg_hint_plan
263does. However, since the primary goal of the initial development work is to be
264able to induce the planner to recreate a desired plan that worked well in
265the past, this has not been included in the initial development effort.
