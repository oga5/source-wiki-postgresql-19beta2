3<sect1 id="btree-gist" xreflabel="btree_gist">
4 <title>btree_gist &mdash; GiST operator classes with B-tree behavior</title>
5
6 <indexterm zone="btree-gist">
7  <primary>btree_gist</primary>
8 </indexterm>
9
10 <para>
11  <filename>btree_gist</filename> provides GiST index operator classes that
12  implement B-tree equivalent behavior for the data types
13  <type>int2</type>, <type>int4</type>, <type>int8</type>, <type>float4</type>,
14  <type>float8</type>, <type>numeric</type>, <type>timestamp with time zone</type>,
15  <type>timestamp without time zone</type>, <type>time with time zone</type>,
16  <type>time without time zone</type>, <type>date</type>, <type>interval</type>,
17  <type>oid</type>, <type>money</type>, <type>char</type>,
18  <type>varchar</type>, <type>text</type>, <type>bytea</type>, <type>bit</type>,
19  <type>varbit</type>, <type>macaddr</type>, <type>macaddr8</type>, <type>inet</type>,
20  <type>cidr</type>, <type>uuid</type>, <type>bool</type> and all <type>enum</type> types.
21 </para>
22
23 <para>
24  In general, these operator classes will not outperform the equivalent
25  standard B-tree index methods, and they lack one major feature of the
26  standard B-tree code: the ability to enforce uniqueness.  However,
27  they provide some other features that are not available with a B-tree
28  index, as described below.  Also, these operator classes are useful
29  when a multicolumn GiST index is needed, wherein some of the columns
30  are of data types that are only indexable with GiST but other columns
31  are just simple data types.  Lastly, these operator classes are useful for
32  GiST testing and as a base for developing other GiST operator classes.
33 </para>
34
35 <para>
36  In addition to the typical B-tree search operators, <filename>btree_gist</filename>
37  also provides index support for <literal>&lt;&gt;</literal> (<quote>not
38  equals</quote>). This may be useful in combination with an
39  <link linkend="sql-createtable-exclude">exclusion constraint</link>,
40  as described below.
41 </para>
42
43 <para>
44  Also, for data types for which there is a natural distance metric,
45  <filename>btree_gist</filename> defines a distance operator <literal>&lt;-&gt;</literal>,
46  and provides GiST index support for nearest-neighbor searches using
47  this operator.  Distance operators are provided for
48  <type>int2</type>, <type>int4</type>, <type>int8</type>, <type>float4</type>,
49  <type>float8</type>, <type>timestamp with time zone</type>,
50  <type>timestamp without time zone</type>,
51  <type>time without time zone</type>, <type>date</type>, <type>interval</type>,
52  <type>oid</type>, and <type>money</type>.
53 </para>
54
55 <para>
56  By default <filename>btree_gist</filename> builds <acronym>GiST</acronym> index with
57  <function>sortsupport</function> in <firstterm>sorted</firstterm> mode. This usually results in
58  much faster index built speed. It is still possible to revert to buffered built strategy
59  by using the <literal>buffering</literal> parameter when creating the index.
60 </para>
61
62 <para>
63  This module is considered <quote>trusted</quote>, that is, it can be
64  installed by non-superusers who have <literal>CREATE</literal> privilege
65  on the current database.
66 </para>
67
68 <sect2 id="btree-gist-example-usage">
69  <title>Example Usage</title>
70
71  <para>
72   Simple example using <literal>btree_gist</literal> instead of <literal>btree</literal>:
73  </para>
74
75<programlisting>
76CREATE TABLE test (a int4);
77-- create index
78CREATE INDEX testidx ON test USING GIST (a);
79-- query
80SELECT * FROM test WHERE a &lt; 10;
81-- nearest-neighbor search: find the ten entries closest to "42"
82SELECT *, a &lt;-&gt; 42 AS dist FROM test ORDER BY a &lt;-&gt; 42 LIMIT 10;
83</programlisting>
84
85  <para>
86   Use an <link linkend="sql-createtable-exclude">exclusion
87   constraint</link> to enforce the rule that a cage at a zoo
88   can contain only one kind of animal:
89  </para>
90
91<programlisting>
92=&gt; CREATE TABLE zoo (
93  cage   INTEGER,
94  animal TEXT,
95  EXCLUDE USING GIST (cage WITH =, animal WITH &lt;&gt;)
96);
97
98=&gt; INSERT INTO zoo VALUES(123, 'zebra');
99INSERT 0 1
100=&gt; INSERT INTO zoo VALUES(123, 'zebra');
101INSERT 0 1
102=&gt; INSERT INTO zoo VALUES(123, 'lion');
103ERROR:  conflicting key value violates exclusion constraint "zoo_cage_animal_excl"
104DETAIL:  Key (cage, animal)=(123, lion) conflicts with existing key (cage, animal)=(123, zebra).
105=&gt; INSERT INTO zoo VALUES(124, 'lion');
106INSERT 0 1
107</programlisting>

111 <sect2 id="btree-gist-inet-indexes">
112  <title><literal>btree_gist</literal> Indexes
113   on <type>inet</type>/<type>cidr</type> Columns</title>
114
115  <para>
116   The <literal>gist_inet_ops</literal> and <literal>gist_cidr_ops</literal>
117   operator classes provided by <literal>btree_gist</literal> have been
118   shown to be unreliable: index searches may fail to find relevant rows due
119   to approximations used in creating the index entries.  This is unfixable
120   without redefining the contents of indexes that use these opclasses.
121   Therefore, these opclasses are being deprecated in favor of the built-in
122   GiST <literal>inet_ops</literal> opclass, which does not share the design
123   flaw.
124  </para>
125
126  <para>
127   As a first step, <productname>PostgreSQL</productname> version 19 removes
128   the default-opclass marking from <literal>gist_inet_ops</literal>
129   and <literal>gist_cidr_ops</literal>, instead
130   marking <literal>inet_ops</literal> as default for <type>inet</type>
131   and <type>cidr</type> columns.  This will result in transparently
132   substituting <literal>inet_ops</literal> for the faulty opclasses in most
133   contexts.  It is still possible to create indexes using the faulty
134   opclasses, if really necessary, by explicitly specifying which opclass to
135   use; for example
136<programlisting>
137CREATE TABLE mytable (addr inet);
138CREATE INDEX dubious_index ON mytable USING GIST (addr gist_inet_ops);
139</programlisting>
140  </para>
141
142  <para>
143   However, <application>pg_upgrade</application> cannot handle this change
144   due to implementation limitations.  If asked to upgrade a pre-v19
145   database that contains <literal>gist_inet_ops</literal>
146   or <literal>gist_cidr_ops</literal>
147   indexes, <application>pg_upgrade</application> will fail and tell you to
148   replace those indexes before upgrading.  This would look approximately
149   like
150<programlisting>
151CREATE INDEX good_index ON mytable USING GIST (addr inet_ops);
152DROP INDEX bad_index;
153</programlisting>
154  </para>
