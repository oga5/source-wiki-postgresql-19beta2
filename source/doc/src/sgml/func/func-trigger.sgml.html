4  <para>
5   While many uses of triggers involve user-written trigger functions,
6   <productname>PostgreSQL</productname> provides a few built-in trigger
7   functions that can be used directly in user-defined triggers.  These
8   are summarized in <xref linkend="builtin-triggers-table"/>.
9   (Additional built-in trigger functions exist, which implement foreign
10   key constraints and deferred index constraints.  Those are not documented
11   here since users need not use them directly.)
12  </para>

94   <para>
95      The <function>suppress_redundant_updates_trigger</function> function,
96      when applied as a row-level <literal>BEFORE UPDATE</literal> trigger,
97      will prevent any update that does not actually change the data in the
98      row from taking place.  This overrides the normal behavior which always
99      performs a physical row update
100      regardless of whether or not the data has changed. (This normal behavior
101      makes updates run faster, since no checking is required, and is also
102      useful in certain cases.)
103    </para>
104
105    <para>
106      Ideally, you should avoid running updates that don't actually
107      change the data in the record. Redundant updates can cost considerable
108      unnecessary time, especially if there are lots of indexes to alter,
109      and space in dead rows that will eventually have to be vacuumed.
110      However, detecting such situations in client code is not
111      always easy, or even possible, and writing expressions to detect
112      them can be error-prone. An alternative is to use
113      <function>suppress_redundant_updates_trigger</function>, which will skip
114      updates that don't change the data. You should use this with care,
115      however. The trigger takes a small but non-trivial time for each record,
116      so if most of the records affected by updates do actually change,
117      use of this trigger will make updates run slower on average.
118    </para>
119
120    <para>
121      The <function>suppress_redundant_updates_trigger</function> function can be
122      added to a table like this:
123<programlisting>
124CREATE TRIGGER z_min_update
125BEFORE UPDATE ON tablename
126FOR EACH ROW EXECUTE FUNCTION suppress_redundant_updates_trigger();
127</programlisting>
128      In most cases, you need to fire this trigger last for each row, so that
129      it does not override other triggers that might wish to alter the row.
130      Bearing in mind that triggers fire in name order, you would therefore
131      choose a trigger name that comes after the name of any other trigger
132      you might have on the table.  (Hence the <quote>z</quote> prefix in the
133      example.)
134    </para>
