583   <para>
584    <function>pg_current_wal_lsn</function> displays the current write-ahead
585    log write location in the same format used by the above functions.
586    Similarly, <function>pg_current_wal_insert_lsn</function> displays the
587    current write-ahead log insertion location
588    and <function>pg_current_wal_flush_lsn</function> displays the current
589    write-ahead log flush location. The insertion location is
590    the <quote>logical</quote> end of the write-ahead log at any instant,
591    while the write location is the end of what has actually been written out
592    from the server's internal buffers, and the flush location is the last
593    location known to be written to durable storage. The write location is the
594    end of what can be examined from outside the server, and is usually what
595    you want if you are interested in archiving partially-complete write-ahead
596    log files.  The insertion and flush locations are made available primarily
597    for server debugging purposes.  These are all read-only operations and do
598    not require superuser permissions.
599   </para>
600
601   <para>
602    You can use <function>pg_walfile_name_offset</function> to extract the
603    corresponding write-ahead log file name and byte offset from
604    a <type>pg_lsn</type> value.  For example:
605<programlisting>
606postgres=# SELECT * FROM pg_walfile_name_offset((pg_backup_stop()).lsn);
607        file_name         | file_offset
608--------------------------+-------------
609 00000001000000000000000D |     4039624
610(1 row)
611</programlisting>
612    Similarly, <function>pg_walfile_name</function> extracts just the write-ahead log file name.
613   </para>
614
615   <para>
616    <function>pg_split_walfile_name</function> is useful to compute a
617    <acronym>LSN</acronym> from a file offset and WAL file name, for example:

891  <sect2 id="functions-snapshot-synchronization">
892   <title>Snapshot Synchronization Functions</title>
893
894   <para>
895    <productname>PostgreSQL</productname> allows database sessions to synchronize their
896    snapshots. A <firstterm>snapshot</firstterm> determines which data is visible to the
897    transaction that is using the snapshot. Synchronized snapshots are
898    necessary when two or more sessions need to see identical content in the
899    database. If two sessions just start their transactions independently,
900    there is always a possibility that some third transaction commits
901    between the executions of the two <command>START TRANSACTION</command> commands,
902    so that one session sees the effects of that transaction and the other
903    does not.
904   </para>
905
906   <para>
907    To solve this problem, <productname>PostgreSQL</productname> allows a transaction to
908    <firstterm>export</firstterm> the snapshot it is using.  As long as the exporting
909    transaction remains open, other transactions can <firstterm>import</firstterm> its
910    snapshot, and thereby be guaranteed that they see exactly the same view
911    of the database that the first transaction sees.  But note that any
912    database changes made by any one of these transactions remain invisible
913    to the other transactions, as is usual for changes made by uncommitted
914    transactions.  So the transactions are synchronized with respect to
915    pre-existing data, but act normally for changes they make themselves.
916   </para>
917
918   <para>
919    Snapshots are exported with the <function>pg_export_snapshot</function> function,
920    shown in <xref linkend="functions-snapshot-synchronization-table"/>, and
921    imported with the <xref linkend="sql-set-transaction"/> command.
922   </para>

2874  <sect2 id="functions-advisory-locks">
2875   <title>Advisory Lock Functions</title>
2876
2877   <para>
2878    The functions shown in <xref linkend="functions-advisory-locks-table"/>
2879    manage advisory locks.  For details about proper use of these functions,
2880    see <xref linkend="advisory-locks"/>.
2881   </para>
2882
2883   <para>
2884    All these functions are intended to be used to lock application-defined
2885    resources, which can be identified either by a single 64-bit key value or
2886    two 32-bit key values (note that these two key spaces do not overlap).
2887    If another session already holds a conflicting lock on the same resource
2888    identifier, the functions will either wait until the resource becomes
2889    available, or return a <literal>false</literal> result, as appropriate for
2890    the function.
2891    Locks can be either shared or exclusive: a shared lock does not conflict
2892    with other shared locks on the same resource, only with exclusive locks.
2893    Locks can be taken at session level (so that they are held until released
2894    or the session ends) or at transaction level (so that they are held until
2895    the current transaction ends; there is no provision for manual release).
2896    Multiple session-level lock requests stack, so that if the same resource
2897    identifier is locked three times there must then be three unlock requests
2898    to release the resource in advance of session end.
2899   </para>
