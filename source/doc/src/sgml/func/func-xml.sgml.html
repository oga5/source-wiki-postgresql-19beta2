3  <title>XML Functions</title>
4
5  <indexterm>
6   <primary>XML Functions</primary>
7  </indexterm>
8
9  <para>
10   The functions and function-like expressions described in this
11   section operate on values of type <type>xml</type>.  See <xref
12   linkend="datatype-xml"/> for information about the <type>xml</type>
13   type.  The function-like expressions <function>xmlparse</function>
14   and <function>xmlserialize</function> for converting to and from
15   type <type>xml</type> are documented there, not in this section.
16  </para>
17
18  <para>
19   Use of most of these functions
20   requires <productname>PostgreSQL</productname> to have been built
21   with <command>configure --with-libxml</command>.
22  </para>
23
24  <sect2 id="functions-producing-xml">
25   <title>Producing XML Content</title>
26
27   <para>
28    A set of functions and function-like expressions is available for
29    producing XML content from SQL data.  As such, they are
30    particularly suitable for formatting query results into XML
31    documents for processing in client applications.
32   </para>
33
34  <sect3 id="functions-producing-xml-xmltext">
35    <title><literal>xmltext</literal></title>
36
37    <indexterm>
38     <primary>xmltext</primary>
39    </indexterm>
40
41<synopsis>
42<function>xmltext</function> ( <type>text</type> ) <returnvalue>xml</returnvalue>
43</synopsis>
44
45    <para>
46     The function <function>xmltext</function> returns an XML value with a single
47     text node containing the input argument as its content. Predefined entities
48     like ampersand (<literal><![CDATA[&]]></literal>), left and right angle brackets
49     (<literal><![CDATA[< >]]></literal>), and quotation marks (<literal><![CDATA[""]]></literal>)
50     are escaped.
51    </para>
52
53    <para>
54     Example:
55<screen><![CDATA[
56SELECT xmltext('< foo & bar >');
57         xmltext
58-------------------------
59 &lt; foo &amp; bar &gt;
60]]></screen>
61    </para>
62   </sect3>

64   <sect3 id="functions-producing-xml-xmlcomment">
65    <title><literal>xmlcomment</literal></title>
66
67    <indexterm>
68     <primary>xmlcomment</primary>
69    </indexterm>
70
71<synopsis>
72<function>xmlcomment</function> ( <type>text</type> ) <returnvalue>xml</returnvalue>
73</synopsis>
74
75    <para>
76     The function <function>xmlcomment</function> creates an XML value
77     containing an XML comment with the specified text as content.
78     The text cannot contain <quote><literal>--</literal></quote> or end with a
79     <quote><literal>-</literal></quote>, otherwise the resulting construct
80     would not be a valid XML comment.
81     If the argument is null, the result is null.
82    </para>
83
84    <para>
85     Example:
86<screen><![CDATA[
87SELECT xmlcomment('hello');
88
89  xmlcomment
90--------------
91 <!--hello-->
92]]></screen>
93    </para>
94   </sect3>

96   <sect3 id="functions-producing-xml-xmlconcat">
97    <title><literal>xmlconcat</literal></title>
98
99    <indexterm>
100     <primary>xmlconcat</primary>
101    </indexterm>
102
103<synopsis>
104<function>xmlconcat</function> ( <type>xml</type> <optional>, ...</optional> ) <returnvalue>xml</returnvalue>
105</synopsis>
106
107    <para>
108     The function <function>xmlconcat</function> concatenates a list
109     of individual XML values to create a single value containing an
110     XML content fragment.  Null values are omitted; the result is
111     only null if there are no nonnull arguments.
112    </para>
113
114    <para>
115     Example:
116<screen><![CDATA[
117SELECT xmlconcat('<abc/>', '<bar>foo</bar>');
118
119      xmlconcat
120----------------------
121 <abc/><bar>foo</bar>
122]]></screen>
123    </para>
124
125    <para>
126     XML declarations, if present, are combined as follows.  If all
127     argument values have the same XML version declaration, that
128     version is used in the result, else no version is used.  If all
129     argument values have the standalone declaration value
130     <quote>yes</quote>, then that value is used in the result.  If
131     all argument values have a standalone declaration value and at
132     least one is <quote>no</quote>, then that is used in the result.
133     Else the result will have no standalone declaration.  If the
134     result is determined to require a standalone declaration but no
135     version declaration, a version declaration with version 1.0 will
136     be used because XML requires an XML declaration to contain a
137     version declaration.  Encoding declarations are ignored and
138     removed in all cases.
139    </para>
140
141    <para>
142     Example:
143<screen><![CDATA[
144SELECT xmlconcat('<?xml version="1.1"?><foo/>', '<?xml version="1.1" standalone="no"?><bar/>');
145
146             xmlconcat
147-----------------------------------
148 <?xml version="1.1"?><foo/><bar/>
149]]></screen>
150    </para>
151   </sect3>

153   <sect3 id="functions-producing-xml-xmlelement">
154    <title><literal>xmlelement</literal></title>
155
156   <indexterm>
157    <primary>xmlelement</primary>
158   </indexterm>
159
160<synopsis>
161<function>xmlelement</function> ( <literal>NAME</literal> <replaceable>name</replaceable> <optional>, <literal>XMLATTRIBUTES</literal> ( <replaceable>attvalue</replaceable> <optional> <literal>AS</literal> <replaceable>attname</replaceable> </optional> <optional>, ...</optional> ) </optional> <optional>, <replaceable>content</replaceable> <optional>, ...</optional></optional> ) <returnvalue>xml</returnvalue>
162</synopsis>
163
164    <para>
165     The <function>xmlelement</function> expression produces an XML
166     element with the given name, attributes, and content.
167     The <replaceable>name</replaceable>
168     and <replaceable>attname</replaceable> items shown in the syntax are
169     simple identifiers, not values.  The <replaceable>attvalue</replaceable>
170     and <replaceable>content</replaceable> items are expressions, which can
171     yield any <productname>PostgreSQL</productname> data type.  The
172     argument(s) within <literal>XMLATTRIBUTES</literal> generate attributes
173     of the XML element; the <replaceable>content</replaceable> value(s) are
174     concatenated to form its content.
175    </para>
176
177    <para>
178     Examples:
179<screen><![CDATA[
180SELECT xmlelement(NAME foo);
181
182 xmlelement
183------------
184 <foo/>
185
186SELECT xmlelement(NAME foo, xmlattributes('xyz' AS bar));
187
188    xmlelement
189------------------
190 <foo bar="xyz"/>
191
192SELECT xmlelement(NAME foo, xmlattributes(current_date AS bar), 'cont', 'ent');
193
194             xmlelement
195-------------------------------------
196 <foo bar="2007-01-26">content</foo>
197]]></screen>
198    </para>
199
200    <para>
201     Element and attribute names that are not valid XML names are
202     escaped by replacing the offending characters by the sequence
203     <literal>_x<replaceable>HHHH</replaceable>_</literal>, where
204     <replaceable>HHHH</replaceable> is the character's Unicode
205     codepoint in hexadecimal notation.  For example:
206<screen><![CDATA[
207SELECT xmlelement(NAME "foo$bar", xmlattributes('xyz' AS "a&b"));
208
209            xmlelement
210----------------------------------
211 <foo_x0024_bar a_x0026_b="xyz"/>
212]]></screen>
213    </para>
214
215    <para>
216     An explicit attribute name need not be specified if the attribute
217     value is a column reference, in which case the column's name will
218     be used as the attribute name by default.  In other cases, the
219     attribute must be given an explicit name.  So this example is
220     valid:
221<screen>
222CREATE TABLE test (a xml, b xml);
223SELECT xmlelement(NAME test, xmlattributes(a, b)) FROM test;
224</screen>
225     But these are not:
226<screen>
227SELECT xmlelement(NAME test, xmlattributes('constant'), a, b) FROM test;
228SELECT xmlelement(NAME test, xmlattributes(func(a, b))) FROM test;
229</screen>
230    </para>
231
232    <para>
233     Element content, if specified, will be formatted according to
234     its data type.  If the content is itself of type <type>xml</type>,
235     complex XML documents can be constructed.  For example:
236<screen><![CDATA[
237SELECT xmlelement(NAME foo, xmlattributes('xyz' AS bar),
238                            xmlelement(NAME abc),
239                            xmlcomment('test'),
240                            xmlelement(NAME xyz));
241
242                  xmlelement
243----------------------------------------------
244 <foo bar="xyz"><abc/><!--test--><xyz/></foo>
245]]></screen>
246
247     Content of other types will be formatted into valid XML character
248     data.  This means in particular that the characters &lt;, &gt;,
249     and &amp; will be converted to entities.  Binary data (data type
250     <type>bytea</type>) will be represented in base64 or hex
251     encoding, depending on the setting of the configuration parameter
252     <xref linkend="guc-xmlbinary"/>.  The particular behavior for
253     individual data types is expected to evolve in order to align the
254     PostgreSQL mappings with those specified in SQL:2006 and later,
255     as discussed in <xref linkend="functions-xml-limits-casts"/>.
256    </para>
257   </sect3>

259   <sect3 id="functions-producing-xml-xmlforest">
260    <title><literal>xmlforest</literal></title>
261
262   <indexterm>
263    <primary>xmlforest</primary>
264   </indexterm>
265
266<synopsis>
267<function>xmlforest</function> ( <replaceable>content</replaceable> <optional> <literal>AS</literal> <replaceable>name</replaceable> </optional> <optional>, ...</optional> ) <returnvalue>xml</returnvalue>
268</synopsis>
269
270    <para>
271     The <function>xmlforest</function> expression produces an XML
272     forest (sequence) of elements using the given names and content.
273     As for <function>xmlelement</function>,
274     each <replaceable>name</replaceable> must be a simple identifier, while
275     the <replaceable>content</replaceable> expressions can have any data
276     type.
277    </para>
278
279    <para>
280     Examples:
281<screen>
282SELECT xmlforest('abc' AS foo, 123 AS bar);
283
284          xmlforest
285------------------------------
286 &lt;foo&gt;abc&lt;/foo&gt;&lt;bar&gt;123&lt;/bar&gt;
287
288
289SELECT xmlforest(table_name, column_name)
290FROM information_schema.columns
291WHERE table_schema = 'pg_catalog';
292
293                                xmlforest
294------------------------------------&zwsp;-----------------------------------
295 &lt;table_name&gt;pg_authid&lt;/table_name&gt;&zwsp;&lt;column_name&gt;rolname&lt;/column_name&gt;
296 &lt;table_name&gt;pg_authid&lt;/table_name&gt;&zwsp;&lt;column_name&gt;rolsuper&lt;/column_name&gt;
297 ...
298</screen>
299
300     As seen in the second example, the element name can be omitted if
301     the content value is a column reference, in which case the column
302     name is used by default.  Otherwise, a name must be specified.
303    </para>
304
305    <para>
306     Element names that are not valid XML names are escaped as shown
307     for <function>xmlelement</function> above.  Similarly, content
308     data is escaped to make valid XML content, unless it is already
309     of type <type>xml</type>.
310    </para>
311
312    <para>
313     Note that XML forests are not valid XML documents if they consist
314     of more than one element, so it might be useful to wrap
315     <function>xmlforest</function> expressions in
316     <function>xmlelement</function>.
317    </para>
318   </sect3>

354    <title><literal>xmlroot</literal></title>
355
356   <indexterm>
357    <primary>xmlroot</primary>
358   </indexterm>
359
360<synopsis>
361<function>xmlroot</function> ( <type>xml</type>, <literal>VERSION</literal> {<type>text</type>|<literal>NO VALUE</literal>} <optional>, <literal>STANDALONE</literal> {<literal>YES</literal>|<literal>NO</literal>|<literal>NO VALUE</literal>} </optional> ) <returnvalue>xml</returnvalue>

363

366     of the root node of an XML value.  If a version is specified,

370    </para>

373<screen><![CDATA[
374SELECT xmlroot(xmlparse(document '<?xml version="1.1"?><content>abc</content>'),
375               version '1.0', standalone yes);
376
377                xmlroot
378----------------------------------------
379 <?xml version="1.0" standalone="yes"?>
380 <content>abc</content>
381]]></screen>
382    </para>

385   <sect3 id="functions-xml-xmlagg">
386    <title><literal>xmlagg</literal></title>
387
388    <indexterm>
389     <primary>xmlagg</primary>
390    </indexterm>
391
392<synopsis>
393<function>xmlagg</function> ( <type>xml</type> ) <returnvalue>xml</returnvalue>
394</synopsis>
395
396    <para>
397     The function <function>xmlagg</function> is, unlike the other
398     functions described here, an aggregate function.  It concatenates the
399     input values to the aggregate function call,
400     much like <function>xmlconcat</function> does, except that concatenation
401     occurs across rows rather than across expressions in a single row.
402     See <xref linkend="functions-aggregate"/> for additional information
403     about aggregate functions.
404    </para>
405
406    <para>
407     Example:
408<screen><![CDATA[
409CREATE TABLE test (y int, x xml);
410INSERT INTO test VALUES (1, '<foo>abc</foo>');
411INSERT INTO test VALUES (2, '<bar/>');
412SELECT xmlagg(x) FROM test;
413        xmlagg
414----------------------
415 <foo>abc</foo><bar/>
416]]></screen>
417    </para>
418
419    <para>
420     To determine the order of the concatenation, an <literal>ORDER BY</literal>
421     clause may be added to the aggregate call as described in
422     <xref linkend="syntax-aggregates"/>. For example:
423
424<screen><![CDATA[
425SELECT xmlagg(x ORDER BY y DESC) FROM test;
426        xmlagg
427----------------------
428 <bar/><foo>abc</foo>
429]]></screen>
430    </para>
431
432    <para>
433     The following non-standard approach used to be recommended
434     in previous versions, and may still be useful in specific
435     cases:
436
437<screen><![CDATA[
438SELECT xmlagg(x) FROM (SELECT * FROM test ORDER BY y DESC) AS tab;
439        xmlagg
440----------------------
441 <bar/><foo>abc</foo>
442]]></screen>
443    </para>

493   <sect3 id="xml-exists">
494    <title><literal>XMLEXISTS</literal></title>
495
496    <indexterm>
497     <primary>XMLEXISTS</primary>
498    </indexterm>
499
500<synopsis>
501<function>XMLEXISTS</function> ( <type>text</type> <literal>PASSING</literal> <optional><literal>BY</literal> {<literal>REF</literal>|<literal>VALUE</literal>}</optional> <type>xml</type> <optional><literal>BY</literal> {<literal>REF</literal>|<literal>VALUE</literal>}</optional> ) <returnvalue>boolean</returnvalue>
502</synopsis>
503
504    <para>
505     The function <function>xmlexists</function> evaluates an XPath 1.0
506     expression (the first argument), with the passed XML value as its context
507     item.  The function returns false if the result of that evaluation
508     yields an empty node-set, true if it yields any other value.  The
509     function returns null if any argument is null.  A nonnull value
510     passed as the context item must be an XML document, not a content
511     fragment or any non-XML value.
512    </para>
513
514    <para>
515     Example:
516     <screen><![CDATA[
517SELECT xmlexists('//town[text() = ''Toronto'']' PASSING BY VALUE '<towns><town>Toronto</town><town>Ottawa</town></towns>');
518
519 xmlexists
520------------
521 t
522(1 row)
523]]></screen>
524    </para>
525
526    <para>
527     The <literal>BY REF</literal> and <literal>BY VALUE</literal> clauses
528     are accepted in <productname>PostgreSQL</productname>, but are ignored,
529     as discussed in <xref linkend="functions-xml-limits-postgresql"/>.
530    </para>
531
532    <para>
533     In the SQL standard, the <function>xmlexists</function> function
534     evaluates an expression in the XML Query language,
535     but <productname>PostgreSQL</productname> allows only an XPath 1.0
536     expression, as discussed in
537     <xref linkend="functions-xml-limits-xpath1"/>.
538    </para>
539   </sect3>

541   <sect3 id="xml-is-well-formed">
542    <title><literal>xml_is_well_formed</literal></title>
543
544    <indexterm>
545     <primary>xml_is_well_formed</primary>
546    </indexterm>
547
548    <indexterm>
549     <primary>xml_is_well_formed_document</primary>
550    </indexterm>
551
552    <indexterm>
553     <primary>xml_is_well_formed_content</primary>
554    </indexterm>
555
556<synopsis>
557<function>xml_is_well_formed</function> ( <type>text</type> ) <returnvalue>boolean</returnvalue>
558<function>xml_is_well_formed_document</function> ( <type>text</type> ) <returnvalue>boolean</returnvalue>
559<function>xml_is_well_formed_content</function> ( <type>text</type> ) <returnvalue>boolean</returnvalue>
560</synopsis>
561
562    <para>
563     These functions check whether a <type>text</type> string represents
564     well-formed XML, returning a Boolean result.
565     <function>xml_is_well_formed_document</function> checks for a well-formed
566     document, while <function>xml_is_well_formed_content</function> checks
567     for well-formed content.  <function>xml_is_well_formed</function> does
568     the former if the <xref linkend="guc-xmloption"/> configuration
569     parameter is set to <literal>DOCUMENT</literal>, or the latter if it is set to
570     <literal>CONTENT</literal>.  This means that
571     <function>xml_is_well_formed</function> is useful for seeing whether
572     a simple cast to type <type>xml</type> will succeed, whereas the other two
573     functions are useful for seeing whether the corresponding variants of
574     <function>XMLPARSE</function> will succeed.
575    </para>
576
577    <para>
578     Examples:
579
580<screen><![CDATA[
581SET xmloption TO DOCUMENT;
582SELECT xml_is_well_formed('<>');
583 xml_is_well_formed
584--------------------
585 f
586(1 row)
587
588SELECT xml_is_well_formed('<abc/>');
589 xml_is_well_formed
590--------------------
591 t
592(1 row)
593
594SET xmloption TO CONTENT;
595SELECT xml_is_well_formed('abc');
596 xml_is_well_formed
597--------------------
598 t
599(1 row)
600
601SELECT xml_is_well_formed_document('<pg:foo xmlns:pg="http://postgresql.org/stuff">bar</pg:foo>');
602 xml_is_well_formed_document
603-----------------------------
604 t
605(1 row)
606
607SELECT xml_is_well_formed_document('<pg:foo xmlns:pg="http://postgresql.org/stuff">bar</my:foo>');
608 xml_is_well_formed_document
609-----------------------------
610 f
611(1 row)
612]]></screen>
613
614     The last example shows that the checks include whether
615     namespaces are correctly matched.
616    </para>
617   </sect3>

620  <sect2 id="functions-xml-processing">
621   <title>Processing XML</title>
622
623   <para>
624    To process values of data type <type>xml</type>, PostgreSQL offers
625    the functions <function>xpath</function> and
626    <function>xpath_exists</function>, which evaluate XPath 1.0
627    expressions, and the <function>XMLTABLE</function>
628    table function.
629   </para>
630
631   <sect3 id="functions-xml-processing-xpath">
632    <title><literal>xpath</literal></title>
633
634    <indexterm>
635     <primary>XPath</primary>
636    </indexterm>
637
638<synopsis>
639<function>xpath</function> ( <parameter>xpath</parameter> <type>text</type>, <parameter>xml</parameter> <type>xml</type> <optional>, <parameter>nsarray</parameter> <type>text[]</type> </optional> ) <returnvalue>xml[]</returnvalue>
640</synopsis>
641
642    <para>
643     The function <function>xpath</function> evaluates the XPath 1.0
644     expression <parameter>xpath</parameter> (given as text)
645     against the XML value
646     <parameter>xml</parameter>.  It returns an array of XML values
647     corresponding to the node-set produced by the XPath expression.
648     If the XPath expression returns a scalar value rather than a node-set,
649     a single-element array is returned.
650    </para>
651
652    <para>
653     The second argument must be a well formed XML document. In particular,
654     it must have a single root node element.
655    </para>
656
657    <para>
658     The optional third argument of the function is an array of namespace
659     mappings.  This array should be a two-dimensional <type>text</type> array with
660     the length of the second axis being equal to 2 (i.e., it should be an
661     array of arrays, each of which consists of exactly 2 elements).
662     The first element of each array entry is the namespace name (alias), the
663     second the namespace URI. It is not required that aliases provided in
664     this array be the same as those being used in the XML document itself (in
665     other words, both in the XML document and in the <function>xpath</function>
666     function context, aliases are <emphasis>local</emphasis>).
667    </para>
668
669    <para>
670     Example:
671<screen><![CDATA[
672SELECT xpath('/my:a/text()', '<my:a xmlns:my="http://example.com">test</my:a>',
673             ARRAY[ARRAY['my', 'http://example.com']]);
674
675 xpath
676--------
677 {test}
678(1 row)
679]]></screen>
680    </para>
681
682    <para>
683     To deal with default (anonymous) namespaces, do something like this:
684<screen><![CDATA[
685SELECT xpath('//mydefns:b/text()', '<a xmlns="http://example.com"><b>test</b></a>',
686             ARRAY[ARRAY['mydefns', 'http://example.com']]);
687
688 xpath
689--------
690 {test}
691(1 row)
692]]></screen>
693    </para>
694   </sect3>

696   <sect3 id="functions-xml-processing-xpath-exists">
697    <title><literal>xpath_exists</literal></title>
698
699    <indexterm>
700     <primary>xpath_exists</primary>
701    </indexterm>

703<synopsis>

708     The function <function>xpath_exists</function> is a specialized form
709     of the <function>xpath</function> function.  Instead of returning the
710     individual XML values that satisfy the XPath 1.0 expression, this function
711     returns a Boolean indicating whether the query was satisfied or not
712     (specifically, whether it produced any value other than an empty node-set).

714     except that it also offers support for a namespace mapping argument.
715    </para>

719<screen><![CDATA[
720SELECT xpath_exists('/my:a/text()', '<my:a xmlns:my="http://example.com">test</my:a>',

724--------------

726(1 row)

731   <sect3 id="functions-xml-processing-xmltable">
732    <title><literal>xmltable</literal></title>
733
734    <indexterm>
735     <primary>xmltable</primary>
736    </indexterm>
737
738    <indexterm zone="functions-xml-processing-xmltable">
739     <primary>table function</primary>
740     <secondary>XMLTABLE</secondary>
741    </indexterm>
742
743<synopsis>
744<function>XMLTABLE</function> (
745    <optional> <literal>XMLNAMESPACES</literal> ( <replaceable>namespace_uri</replaceable> <literal>AS</literal> <replaceable>namespace_name</replaceable> <optional>, ...</optional> ), </optional>
746    <replaceable>row_expression</replaceable> <literal>PASSING</literal> <optional><literal>BY</literal> {<literal>REF</literal>|<literal>VALUE</literal>}</optional> <replaceable>document_expression</replaceable> <optional><literal>BY</literal> {<literal>REF</literal>|<literal>VALUE</literal>}</optional>
747    <literal>COLUMNS</literal> <replaceable>name</replaceable> { <replaceable>type</replaceable> <optional><literal>PATH</literal> <replaceable>column_expression</replaceable></optional> <optional><literal>DEFAULT</literal> <replaceable>default_expression</replaceable></optional> <optional><literal>NOT NULL</literal> | <literal>NULL</literal></optional>
748                  | <literal>FOR ORDINALITY</literal> }
749            <optional>, ...</optional>
750) <returnvalue>setof record</returnvalue>
751</synopsis>
752
753    <para>
754     The <function>xmltable</function> expression produces a table based
755     on an XML value, an XPath filter to extract rows, and a
756     set of column definitions.
757     Although it syntactically resembles a function, it can only appear
758     as a table in a query's <literal>FROM</literal> clause.
759    </para>
760
761    <para>
762     The optional <literal>XMLNAMESPACES</literal> clause gives a
763     comma-separated list of namespace definitions, where
764     each <replaceable>namespace_uri</replaceable> is a <type>text</type>
765     expression and each <replaceable>namespace_name</replaceable> is a simple
766     identifier.  It specifies the XML namespaces used in the document and
767     their aliases. A default namespace specification is not currently
768     supported.
769    </para>
770
771    <para>
772     The required <replaceable>row_expression</replaceable> argument is an
773     XPath 1.0 expression (given as <type>text</type>) that is evaluated,
774     passing the XML value <replaceable>document_expression</replaceable> as
775     its context item, to obtain a set of XML nodes. These nodes are what
776     <function>xmltable</function> transforms into output rows. No rows
777     will be produced if the <replaceable>document_expression</replaceable>
778     is null, nor if the <replaceable>row_expression</replaceable> produces
779     an empty node-set or any value other than a node-set.
780    </para>
781
782    <para>
783     <replaceable>document_expression</replaceable> provides the context
784     item for the <replaceable>row_expression</replaceable>. It must be a
785     well-formed XML document; fragments/forests are not accepted.
786     The <literal>BY REF</literal> and <literal>BY VALUE</literal> clauses
787     are accepted but ignored, as discussed in
788     <xref linkend="functions-xml-limits-postgresql"/>.
789    </para>
790
791    <para>
792     In the SQL standard, the <function>xmltable</function> function
793     evaluates expressions in the XML Query language,
794     but <productname>PostgreSQL</productname> allows only XPath 1.0
795     expressions, as discussed in
796     <xref linkend="functions-xml-limits-xpath1"/>.
797    </para>
798
799    <para>
800     The required <literal>COLUMNS</literal> clause specifies the
801     column(s) that will be produced in the output table.
802     See the syntax summary above for the format.
803     A name is required for each column, as is a data type
804     (unless <literal>FOR ORDINALITY</literal> is specified, in which case
805     type <type>integer</type> is implicit).  The path, default and
806     nullability clauses are optional.
807    </para>
808
809    <para>
810     A column marked <literal>FOR ORDINALITY</literal> will be populated
811     with row numbers, starting with 1, in the order of nodes retrieved from
812     the <replaceable>row_expression</replaceable>'s result node-set.
813     At most one column may be marked <literal>FOR ORDINALITY</literal>.
814    </para>
815
816    <note>
817     <para>
818      XPath 1.0 does not specify an order for nodes in a node-set, so code
819      that relies on a particular order of the results will be
820      implementation-dependent.  Details can be found in
821      <xref linkend="xml-xpath-1-specifics"/>.
822     </para>
823    </note>
824
825    <para>
826     The <replaceable>column_expression</replaceable> for a column is an
827     XPath 1.0 expression that is evaluated for each row, with the current
828     node from the <replaceable>row_expression</replaceable> result as its
829     context item, to find the value of the column.  If
830     no <replaceable>column_expression</replaceable> is given, then the
831     column name is used as an implicit path.
832    </para>
833
834    <para>
835     If a column's XPath expression returns a non-XML value (which is limited
836     to string, boolean, or double in XPath 1.0) and the column has a
837     PostgreSQL type other than <type>xml</type>, the column will be set
838     as if by assigning the value's string representation to the PostgreSQL
839     type.  (If the value is a boolean, its string representation is taken
840     to be <literal>1</literal> or <literal>0</literal> if the output
841     column's type category is numeric, otherwise <literal>true</literal> or
842     <literal>false</literal>.)
843    </para>
844
845    <para>
846     If a column's XPath expression returns a non-empty set of XML nodes
847     and the column's PostgreSQL type is <type>xml</type>, the column will
848     be assigned the expression result exactly, if it is of document or
849     content form.
850     <footnote>
851      <para>
852       A result containing more than one element node at the top level, or
853       non-whitespace text outside of an element, is an example of content form.
854       An XPath result can be of neither form, for example if it returns an
855       attribute node selected from the element that contains it. Such a result
856       will be put into content form with each such disallowed node replaced by
857       its string value, as defined for the XPath 1.0
858       <function>string</function> function.
859      </para>
860     </footnote>
861    </para>
862
863    <para>
864     A non-XML result assigned to an <type>xml</type> output column produces
865     content, a single text node with the string value of the result.
866     An XML result assigned to a column of any other type may not have more than
867     one node, or an error is raised. If there is exactly one node, the column
868     will be set as if by assigning the node's string
869     value (as defined for the XPath 1.0 <function>string</function> function)
870     to the PostgreSQL type.
871    </para>
872
873    <para>
874     The string value of an XML element is the concatenation, in document order,
875     of all text nodes contained in that element and its descendants. The string
876     value of an element with no descendant text nodes is an
877     empty string (not <literal>NULL</literal>).
878     Any <literal>xsi:nil</literal> attributes are ignored.
879     Note that the whitespace-only <literal>text()</literal> node between two non-text
880     elements is preserved, and that leading whitespace on a <literal>text()</literal>
881     node is not flattened.
882     The XPath 1.0 <function>string</function> function may be consulted for the
883     rules defining the string value of other XML node types and non-XML values.
884    </para>
885
886    <para>
887     The conversion rules presented here are not exactly those of the SQL
888     standard, as discussed in <xref linkend="functions-xml-limits-casts"/>.
889    </para>
890
891    <para>
892     If the path expression returns an empty node-set
893     (typically, when it does not match)
894     for a given row, the column will be set to <literal>NULL</literal>, unless
895     a <replaceable>default_expression</replaceable> is specified; then the
896     value resulting from evaluating that expression is used.
897    </para>
898
899    <para>
900     A <replaceable>default_expression</replaceable>, rather than being
901     evaluated immediately when <function>xmltable</function> is called,
902     is evaluated each time a default is needed for the column.
903     If the expression qualifies as stable or immutable, the repeat
904     evaluation may be skipped.
905     This means that you can usefully use volatile functions like
906     <function>nextval</function> in
907     <replaceable>default_expression</replaceable>.
908    </para>
909
910    <para>
911     Columns may be marked <literal>NOT NULL</literal>. If the
912     <replaceable>column_expression</replaceable> for a <literal>NOT
913     NULL</literal> column does not match anything and there is
914     no <literal>DEFAULT</literal> or
915     the <replaceable>default_expression</replaceable> also evaluates to null,
916     an error is reported.
917    </para>
918
919    <para>
920     Examples:
921  <screen><![CDATA[
922CREATE TABLE xmldata AS SELECT
923xml $$
924<ROWS>
925  <ROW id="1">
926    <COUNTRY_ID>AU</COUNTRY_ID>

1022   <para>
1023    The following functions map the contents of relational tables to
1024    XML values.  They can be thought of as XML export functionality:
1025<synopsis>
1026<function>table_to_xml</function> ( <parameter>table</parameter> <type>regclass</type>, <parameter>nulls</parameter> <type>boolean</type>,
1027               <parameter>tableforest</parameter> <type>boolean</type>, <parameter>targetns</parameter> <type>text</type> ) <returnvalue>xml</returnvalue>
1028<function>query_to_xml</function> ( <parameter>query</parameter> <type>text</type>, <parameter>nulls</parameter> <type>boolean</type>,
1029               <parameter>tableforest</parameter> <type>boolean</type>, <parameter>targetns</parameter> <type>text</type> ) <returnvalue>xml</returnvalue>
1030<function>cursor_to_xml</function> ( <parameter>cursor</parameter> <type>refcursor</type>, <parameter>count</parameter> <type>integer</type>, <parameter>nulls</parameter> <type>boolean</type>,
1031                <parameter>tableforest</parameter> <type>boolean</type>, <parameter>targetns</parameter> <type>text</type> ) <returnvalue>xml</returnvalue>
1032</synopsis>
1033   </para>
1034
1035   <para>
1036    <function>table_to_xml</function> maps the content of the named
1037    table, passed as parameter <parameter>table</parameter>.  The
1038    <type>regclass</type> type accepts strings identifying tables using the
1039    usual notation, including optional schema qualification and
1040    double quotes (see <xref linkend="datatype-oid"/> for details).
1041    <function>query_to_xml</function> executes the
1042    query whose text is passed as parameter
1043    <parameter>query</parameter> and maps the result set.
1044    <function>cursor_to_xml</function> fetches the indicated number of
1045    rows from the cursor specified by the parameter
1046    <parameter>cursor</parameter>.  This variant is recommended if
1047    large tables have to be mapped, because the result value is built
1048    up in memory by each function.
1049   </para>
1050
1051   <para>
1052    If <parameter>tableforest</parameter> is false, then the resulting
1053    XML document looks like this:
1054<screen><![CDATA[
1055<tablename>
1056  <row>
1057    <columnname1>data</columnname1>
1058    <columnname2>data</columnname2>
1059  </row>
1060
1061  <row>
1062    ...
1063  </row>
1064
1065  ...
1066</tablename>
1067]]></screen>
1068
1069    If <parameter>tableforest</parameter> is true, the result is an
1070    XML content fragment that looks like this:
1071<screen><![CDATA[
1072<tablename>
1073  <columnname1>data</columnname1>
1074  <columnname2>data</columnname2>
1075</tablename>
1076
1077<tablename>
1078  ...
1079</tablename>
1080
1081...
1082]]></screen>
1083
1084    If no table name is available, that is, when mapping a query or a
1085    cursor, the string <literal>table</literal> is used in the first
1086    format, <literal>row</literal> in the second format.
1087   </para>
1088
1089   <para>
1090    The choice between these formats is up to the user.  The first
1091    format is a proper XML document, which will be important in many
1092    applications.  The second format tends to be more useful in the
1093    <function>cursor_to_xml</function> function if the result values are to be
1094    reassembled into one document later on.  The functions for
1095    producing XML content discussed above, in particular
1096    <function>xmlelement</function>, can be used to alter the results
1097    to taste.
1098   </para>
1099
1100   <para>
1101    The data values are mapped in the same way as described for the
1102    function <function>xmlelement</function> above.
1103   </para>
1104
1105   <para>
1106    The parameter <parameter>nulls</parameter> determines whether null
1107    values should be included in the output.  If true, null values in
1108    columns are represented as:
1109<screen><![CDATA[
1110<columnname xsi:nil="true"/>
1111]]></screen>
1112    where <literal>xsi</literal> is the XML namespace prefix for XML
1113    Schema Instance.  An appropriate namespace declaration will be
1114    added to the result value.  If false, columns containing null
1115    values are simply omitted from the output.
1116   </para>
1117
1118   <para>
1119    The parameter <parameter>targetns</parameter> specifies the
1120    desired XML namespace of the result.  If no particular namespace
1121    is wanted, an empty string should be passed.
1122   </para>
