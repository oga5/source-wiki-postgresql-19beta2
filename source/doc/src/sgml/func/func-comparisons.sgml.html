51  <para>
52   This section describes several specialized constructs for making
53   multiple comparisons between groups of values.  These forms are
54   syntactically related to the subquery forms of the previous section,
55   but do not involve subqueries.
56   The forms involving array subexpressions are
57   <productname>PostgreSQL</productname> extensions; the rest are
58   <acronym>SQL</acronym>-compliant.
59   All of the expression forms documented in this section return
60   Boolean (true/false) results.
61  </para>
62
63  <sect2 id="functions-comparisons-in-scalar">
64   <title><literal>IN</literal></title>
65
66<synopsis>
67<replaceable>expression</replaceable> IN (<replaceable>value</replaceable> <optional>, ...</optional>)
68</synopsis>
69
70  <para>
71   The right-hand side is a parenthesized list
72   of expressions.  The result is <quote>true</quote> if the left-hand expression's
73   result is equal to any of the right-hand expressions.  This is a shorthand
74   notation for
75
76<synopsis>
77<replaceable>expression</replaceable> = <replaceable>value1</replaceable>
78OR
79<replaceable>expression</replaceable> = <replaceable>value2</replaceable>
80OR
81...
82</synopsis>
83  </para>
84
85  <para>
86   Note that if the left-hand expression yields null, or if there are
87   no equal right-hand values and at least one right-hand expression yields
88   null, the result of the <token>IN</token> construct will be null, not false.
89   This is in accordance with SQL's normal rules for Boolean combinations
90   of null values.
91  </para>
92  </sect2>
93
94  <sect2 id="functions-comparisons-not-in">
95   <title><literal>NOT IN</literal></title>
96
97<synopsis>
98<replaceable>expression</replaceable> NOT IN (<replaceable>value</replaceable> <optional>, ...</optional>)
99</synopsis>
100
101  <para>
102   The right-hand side is a parenthesized list
103   of expressions.  The result is <quote>true</quote> if the left-hand expression's
104   result is unequal to all of the right-hand expressions.  This is a shorthand
105   notation for
106
107<synopsis>
108<replaceable>expression</replaceable> &lt;&gt; <replaceable>value1</replaceable>
109AND
110<replaceable>expression</replaceable> &lt;&gt; <replaceable>value2</replaceable>
111AND
112...
113</synopsis>
114  </para>
115
116  <para>
117   Note that if the left-hand expression yields null, or if there are
118   no equal right-hand values and at least one right-hand expression yields
119   null, the result of the <token>NOT IN</token> construct will be null, not true
120   as one might naively expect.
121   This is in accordance with SQL's normal rules for Boolean combinations
122   of null values.
123  </para>
124
125  <tip>
126  <para>
127   <literal>x NOT IN y</literal> is equivalent to <literal>NOT (x IN y)</literal> in all
128   cases.  However, null values are much more likely to trip up the novice when
129   working with <token>NOT IN</token> than when working with <token>IN</token>.
130   It is best to express your condition positively if possible.
131  </para>
132  </tip>
133  </sect2>

135  <sect2 id="functions-comparisons-any-some">
136   <title><literal>ANY</literal>/<literal>SOME</literal> (array)</title>
137
138<synopsis>
139<replaceable>expression</replaceable> <replaceable>operator</replaceable> ANY (<replaceable>array expression</replaceable>)
140<replaceable>expression</replaceable> <replaceable>operator</replaceable> SOME (<replaceable>array expression</replaceable>)
141</synopsis>
142
143  <para>
144   The right-hand side is a parenthesized expression, which must yield an
145   array value.
146   The left-hand expression
147   is evaluated and compared to each element of the array using the
148   given <replaceable>operator</replaceable>, which must yield a Boolean
149   result.
150   The result of <token>ANY</token> is <quote>true</quote> if any true result is obtained.
151   The result is <quote>false</quote> if no true result is found (including the
152   case where the array has zero elements).
153  </para>
154
155  <para>
156   If the array expression yields a null array, the result of
157   <token>ANY</token> will be null.  If the left-hand expression yields null,
158   the result of <token>ANY</token> is ordinarily null (though a non-strict
159   comparison operator could possibly yield a different result).
160   Also, if the right-hand array contains any null elements and no true
161   comparison result is obtained, the result of <token>ANY</token>
162   will be null, not false (again, assuming a strict comparison operator).
163   This is in accordance with SQL's normal rules for Boolean combinations
164   of null values.
165  </para>
166
167  <para>
168   <token>SOME</token> is a synonym for <token>ANY</token>.
169  </para>
170  </sect2>

172  <sect2 id="functions-comparisons-all">
173   <title><literal>ALL</literal> (array)</title>
174
175<synopsis>
176<replaceable>expression</replaceable> <replaceable>operator</replaceable> ALL (<replaceable>array expression</replaceable>)
177</synopsis>
178
179  <para>
180   The right-hand side is a parenthesized expression, which must yield an
181   array value.
182   The left-hand expression
183   is evaluated and compared to each element of the array using the
184   given <replaceable>operator</replaceable>, which must yield a Boolean
185   result.
186   The result of <token>ALL</token> is <quote>true</quote> if all comparisons yield true
187   (including the case where the array has zero elements).
188   The result is <quote>false</quote> if any false result is found.
189  </para>
190
191  <para>
192   If the array expression yields a null array, the result of
193   <token>ALL</token> will be null.  If the left-hand expression yields null,
194   the result of <token>ALL</token> is ordinarily null (though a non-strict
195   comparison operator could possibly yield a different result).
196   Also, if the right-hand array contains any null elements and no false
197   comparison result is obtained, the result of <token>ALL</token>
198   will be null, not true (again, assuming a strict comparison operator).
199   This is in accordance with SQL's normal rules for Boolean combinations
200   of null values.
201  </para>
202  </sect2>

204  <sect2 id="row-wise-comparison">
205   <title>Row Constructor Comparison</title>
206
207<synopsis>
208<replaceable>row_constructor</replaceable> <replaceable>operator</replaceable> <replaceable>row_constructor</replaceable>
209</synopsis>
210
211  <para>
212   Each side is a row constructor,
213   as described in <xref linkend="sql-syntax-row-constructors"/>.
214   The two row constructors must have the same number of fields.
215   The given <replaceable>operator</replaceable> is applied to each pair
216   of corresponding fields.  (Since the fields could be of different
217   types, this means that a different specific operator could be selected
218   for each pair.)
219   All the selected operators must be members of some B-tree operator
220   class, or be the negator of an <literal>=</literal> member of a B-tree
221   operator class, meaning that row constructor comparison is only
222   possible when the <replaceable>operator</replaceable> is
223   <literal>=</literal>,
224   <literal>&lt;&gt;</literal>,
225   <literal>&lt;</literal>,
226   <literal>&lt;=</literal>,
227   <literal>&gt;</literal>, or
228   <literal>&gt;=</literal>,
229   or has semantics similar to one of these.
230  </para>
231
232  <para>
233   The <literal>=</literal> and <literal>&lt;&gt;</literal> cases work slightly differently
234   from the others.  Two rows are considered
235   equal if all their corresponding members are non-null and equal; the rows
236   are unequal if any corresponding members are non-null and unequal;
237   otherwise the result of the row comparison is unknown (null).
238  </para>
239
240  <para>
241   For the <literal>&lt;</literal>, <literal>&lt;=</literal>, <literal>&gt;</literal> and
242   <literal>&gt;=</literal> cases, the row elements are compared left-to-right,
243   stopping as soon as an unequal or null pair of elements is found.
244   If either of this pair of elements is null, the result of the
245   row comparison is unknown (null); otherwise comparison of this pair
246   of elements determines the result.  For example,
247   <literal>ROW(1,2,NULL) &lt; ROW(1,3,0)</literal>
248   yields true, not null, because the third pair of elements are not
249   considered.
250  </para>
251
252<synopsis>
253<replaceable>row_constructor</replaceable> IS DISTINCT FROM <replaceable>row_constructor</replaceable>
254</synopsis>
255
256  <para>
257   This construct is similar to a <literal>&lt;&gt;</literal> row comparison,
258   but it does not yield null for null inputs.  Instead, any null value is
259   considered unequal to (distinct from) any non-null value, and any two
260   nulls are considered equal (not distinct).  Thus the result will
261   either be true or false, never null.
262  </para>
263
264<synopsis>
265<replaceable>row_constructor</replaceable> IS NOT DISTINCT FROM <replaceable>row_constructor</replaceable>
266</synopsis>
267
268  <para>
269   This construct is similar to a <literal>=</literal> row comparison,
270   but it does not yield null for null inputs.  Instead, any null value is
271   considered unequal to (distinct from) any non-null value, and any two
272   nulls are considered equal (not distinct).  Thus the result will always
273   be either true or false, never null.
274  </para>

278  <sect2 id="composite-type-comparison">
279   <title>Composite Type Comparison</title>
280
281<synopsis>
282<replaceable>record</replaceable> <replaceable>operator</replaceable> <replaceable>record</replaceable>
283</synopsis>
284
285  <para>
286   The SQL specification requires row-wise comparison to return NULL if the
287   result depends on comparing two NULL values or a NULL and a non-NULL.
288   <productname>PostgreSQL</productname> does this only when comparing the
289   results of two row constructors (as in
290   <xref linkend="row-wise-comparison"/>) or comparing a row constructor
291   to the output of a subquery (as in <xref linkend="functions-subquery"/>).
292   In other contexts where two composite-type values are compared, two
293   NULL field values are considered equal, and a NULL is considered larger
294   than a non-NULL.  This is necessary in order to have consistent sorting
295   and indexing behavior for composite types.
296  </para>
297
298  <para>
299   Each side is evaluated and they are compared row-wise.  Composite type
300   comparisons are allowed when the <replaceable>operator</replaceable> is
301   <literal>=</literal>,
302   <literal>&lt;&gt;</literal>,
303   <literal>&lt;</literal>,
304   <literal>&lt;=</literal>,
305   <literal>&gt;</literal> or
306   <literal>&gt;=</literal>,
307   or has semantics similar to one of these.  (To be specific, an operator
308   can be a row comparison operator if it is a member of a B-tree operator
309   class, or is the negator of the <literal>=</literal> member of a B-tree operator
310   class.)  The default behavior of the above operators is the same as for
311   <literal>IS [ NOT ] DISTINCT FROM</literal> for row constructors (see
312   <xref linkend="row-wise-comparison"/>).
313  </para>
314
315  <para>
316   To support matching of rows which include elements without a default
317   B-tree operator class, the following operators are defined for composite
318   type comparison:
319   <literal>*=</literal>,
320   <literal>*&lt;&gt;</literal>,
321   <literal>*&lt;</literal>,
322   <literal>*&lt;=</literal>,
323   <literal>*&gt;</literal>, and
324   <literal>*&gt;=</literal>.
325   These operators compare the internal binary representation of the two
326   rows.  Two rows might have a different binary representation even
327   though comparisons of the two rows with the equality operator is true.
328   The ordering of rows under these comparison operators is deterministic
329   but not otherwise meaningful.  These operators are used internally
330   for materialized views and might be useful for other specialized
331   purposes such as replication and B-Tree deduplication (see <xref
332   linkend="btree-deduplication"/>).  They are not intended to be
333   generally useful for writing queries, though.
334  </para>
