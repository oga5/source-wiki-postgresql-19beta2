543   <note>
544    <para>
545     <function>current_catalog</function>,
546     <function>current_role</function>,
547     <function>current_schema</function>,
548     <function>current_user</function>,
549     <function>session_user</function>,
550     and <function>user</function> have special syntactic status
551     in <acronym>SQL</acronym>: they must be called without trailing
552     parentheses.  In PostgreSQL, parentheses can optionally be used with
553     <function>current_schema</function>, but not with the others.
554    </para>
555   </note>
556
557   <para>
558    The <function>session_user</function> is normally the user who initiated
559    the current database connection; but superusers can change this setting
560    with <xref linkend="sql-set-session-authorization"/>.
561    The <function>current_user</function> is the user identifier
562    that is applicable for permission checking. Normally it is equal
563    to the session user, but it can be changed with
564    <xref linkend="sql-set-role"/>.
565    It also changes during the execution of
566    functions with the attribute <literal>SECURITY DEFINER</literal>.
567    In Unix parlance, the session user is the <quote>real user</quote> and
568    the current user is the <quote>effective user</quote>.
569    <function>current_role</function> and <function>user</function> are
570    synonyms for <function>current_user</function>.  (The SQL standard draws
571    a distinction between <function>current_role</function>
572    and <function>current_user</function>, but <productname>PostgreSQL</productname>
573    does not, since it unifies users and roles into a single kind of entity.)
574   </para>

579   <title>Access Privilege Inquiry Functions</title>
580
581  <indexterm>
582   <primary>privilege</primary>
583   <secondary>querying</secondary>
584  </indexterm>
585
586  <para>
587   <xref linkend="functions-info-access-table"/> lists functions that
588   allow querying object access privileges programmatically.
589   (See <xref linkend="ddl-priv"/> for more information about
590   privileges.)
591   In these functions, the user whose privileges are being inquired about
592   can be specified by name or by OID
593   (<structname>pg_authid</structname>.<structfield>oid</structfield>), or if
594   the name is given as <literal>public</literal> then the privileges of the
595   PUBLIC pseudo-role are checked.  Also, the <parameter>user</parameter>
596   argument can be omitted entirely, in which case
597   the <function>current_user</function> is assumed.
598   The object that is being inquired about can be specified either by name or
599   by OID, too.  When specifying by name, a schema name can be included if
600   relevant.
601   The access privilege of interest is specified by a text string, which must
602   evaluate to one of the appropriate privilege keywords for the object's type
603   (e.g., <literal>SELECT</literal>).  Optionally, <literal>WITH GRANT
604   OPTION</literal> can be added to a privilege type to test whether the
605   privilege is held with grant option. Also, multiple privilege types can be
606   listed separated by commas, in which case the result will be true if any of
607   the listed privileges is held. (Case of the privilege string is not
608   significant, and extra whitespace is allowed between but not within
609   privilege names.)
610   Some examples:
611<programlisting>
612SELECT has_table_privilege('myschema.mytable', 'select');
613SELECT has_table_privilege('joe', 'mytable', 'INSERT, SELECT WITH GRANT OPTION');
614</programlisting>
615  </para>
