35  <para>
36   To provide native support for JSON data types within the SQL environment,
37   <productname>PostgreSQL</productname> implements the
38   <firstterm>SQL/JSON data model</firstterm>.
39   This model comprises sequences of items. Each item can hold SQL scalar
40   values, with an additional SQL/JSON null value, and composite data structures
41   that use JSON arrays and objects. The model is a formalization of the implied
42   data model in the JSON specification
43   <ulink url="https://datatracker.ietf.org/doc/html/rfc7159">RFC 7159</ulink>.
44  </para>
45
46  <para>
47   SQL/JSON allows you to handle JSON data alongside regular SQL data,
48   with transaction support, including:
49
50  <itemizedlist>
51   <listitem>
52    <para>
53     Uploading JSON data into the database and storing it in
54     regular SQL columns as character or binary strings.
55    </para>
56   </listitem>
57   <listitem>
58    <para>
59     Generating JSON objects and arrays from relational data.
60    </para>
61   </listitem>
62   <listitem>
63    <para>
64     Querying JSON data using SQL/JSON query functions and
65     SQL/JSON path language expressions.
66    </para>
67   </listitem>
68  </itemizedlist>
69  </para>
70
71  <para>
72   To learn more about the SQL/JSON standard, see
73   <xref linkend="sqltr-19075-6"/>. For details on JSON types
74   supported in <productname>PostgreSQL</productname>,
75   see <xref linkend="datatype-json"/>.
76  </para>

1854 <sect2 id="functions-sqljson-path">
1855  <title>The SQL/JSON Path Language</title>
1856
1857  <indexterm zone="functions-sqljson-path">
1858   <primary>SQL/JSON path language</primary>
1859  </indexterm>
1860
1861  <para>
1862   SQL/JSON path expressions specify item(s) to be retrieved
1863   from a JSON value, similarly to XPath expressions used
1864   for access to XML content. In <productname>PostgreSQL</productname>,
1865   path expressions are implemented as the <type>jsonpath</type>
1866   data type and can use any elements described in
1867   <xref linkend="datatype-jsonpath"/>.
1868  </para>
1869
1870  <para>
1871   JSON query functions and operators
1872   pass the provided path expression to the <firstterm>path engine</firstterm>
1873   for evaluation. If the expression matches the queried JSON data,
1874   the corresponding JSON item, or set of items, is returned.
1875   If there is no match, the result will be <literal>NULL</literal>,
1876   <literal>false</literal>, or an error, depending on the function.
1877   Path expressions are written in the SQL/JSON path language
1878   and can include arithmetic expressions and functions.
1879  </para>
1880
1881  <para>
1882   A path expression consists of a sequence of elements allowed
1883   by the <type>jsonpath</type> data type.
1884   The path expression is normally evaluated from left to right, but
1885   you can use parentheses to change the order of operations.
1886   If the evaluation is successful, a sequence of JSON items is produced,
1887   and the evaluation result is returned to the JSON query function
1888   that completes the specified computation.
1889  </para>
1890
1891  <para>
1892   To refer to the JSON value being queried (the
1893   <firstterm>context item</firstterm>), use the <literal>$</literal> variable
1894   in the path expression. The first element of a path must always
1895   be <literal>$</literal>. It can be followed by one or more
1896   <link linkend="type-jsonpath-accessors">accessor operators</link>,
1897   which go down the JSON structure level by level to retrieve sub-items
1898   of the context item. Each accessor operator acts on the
1899   result(s) of the previous evaluation step, producing zero, one, or more
1900   output items from each input item.
1901  </para>
1902
1903  <para>
1904   For example, suppose you have some JSON data from a GPS tracker that you
1905   would like to parse, such as:
1906<programlisting>
1907SELECT '{
1908  "track": {
1909    "segments": [
1910      {
1911        "location":   [ 47.763, 13.4034 ],
1912        "start time": "2018-10-14 10:05:14",
1913        "HR": 73
1914      },
1915      {
1916        "location":   [ 47.706, 13.2635 ],
1917        "start time": "2018-10-14 10:39:21",
1918        "HR": 135
1919      }
1920    ]
1921  }
1922}' AS json \gset
1923</programlisting>
1924   (The above example can be copied-and-pasted
1925   into <application>psql</application> to set things up for the following
1926   examples.  Then <application>psql</application> will
1927   expand <literal>:'json'</literal> into a suitably-quoted string
1928   constant containing the JSON value.)
1929  </para>
1930
1931  <para>
1932   To retrieve the available track segments, you need to use the
1933   <literal>.<replaceable>key</replaceable></literal> accessor
1934   operator to descend through surrounding JSON objects, for example:
1935<screen>
1936<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments');</userinput>
1937                                                                         jsonb_path_query
1938-----------------------------------------------------------&zwsp;-----------------------------------------------------------&zwsp;---------------------------------------------
1939 [{"HR": 73, "location": [47.763, 13.4034], "start time": "2018-10-14 10:05:14"}, {"HR": 135, "location": [47.706, 13.2635], "start time": "2018-10-14 10:39:21"}]
1940</screen>
1941  </para>
1942
1943  <para>
1944   To retrieve the contents of an array, you typically use the
1945   <literal>[*]</literal> operator.
1946   The following example will return the location coordinates for all
1947   the available track segments:
1948<screen>
1949<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments[*].location');</userinput>
1950 jsonb_path_query
1951-------------------
1952 [47.763, 13.4034]
1953 [47.706, 13.2635]
1954</screen>
1955   Here we started with the whole JSON input value (<literal>$</literal>),
1956   then the <literal>.track</literal> accessor selected the JSON object
1957   associated with the <literal>"track"</literal> object key, then
1958   the <literal>.segments</literal> accessor selected the JSON array
1959   associated with the <literal>"segments"</literal> key within that
1960   object, then the <literal>[*]</literal> accessor selected each element
1961   of that array (producing a series of items), then
1962   the <literal>.location</literal> accessor selected the JSON array
1963   associated with the <literal>"location"</literal> key within each of
1964   those objects.  In this example, each of those objects had
1965   a <literal>"location"</literal> key; but if any of them did not,
1966   the <literal>.location</literal> accessor would have simply produced no
1967   output for that input item.
1968  </para>
1969
1970  <para>
1971   To return the coordinates of the first segment only, you can
1972   specify the corresponding subscript in the <literal>[]</literal>
1973   accessor operator. Recall that JSON array indexes are 0-relative:
1974<screen>
1975<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments[0].location');</userinput>
1976 jsonb_path_query
1977-------------------
1978 [47.763, 13.4034]
1979</screen>
1980  </para>
1981
1982  <para>
1983   The result of each path evaluation step can be processed
1984   by one or more of the <type>jsonpath</type> operators and methods
1985   listed in <xref linkend="functions-sqljson-path-operators"/>.
1986   Each method name must be preceded by a dot. For example,
1987   you can get the size of an array:
1988<screen>
1989<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments.size()');</userinput>
1990 jsonb_path_query
1991------------------
1992 2
1993</screen>
1994   More examples of using <type>jsonpath</type> operators
1995   and methods within path expressions appear below in
1996   <xref linkend="functions-sqljson-path-operators"/>.
1997  </para>
1998
1999  <para>
2000   A path can also contain
2001   <firstterm>filter expressions</firstterm> that work similarly to the
2002   <literal>WHERE</literal> clause in SQL. A filter expression begins with
2003   a question mark and provides a condition in parentheses:
2004
2005<synopsis>
2006? (<replaceable>condition</replaceable>)
2007</synopsis>
2008  </para>
2009
2010  <para>
2011   Filter expressions must be written just after the path evaluation step
2012   to which they should apply. The result of that step is filtered to include
2013   only those items that satisfy the provided condition. SQL/JSON defines
2014   three-valued logic, so the condition can
2015   produce <literal>true</literal>, <literal>false</literal>,
2016   or <literal>unknown</literal>. The <literal>unknown</literal> value
2017   plays the same role as SQL <literal>NULL</literal> and can be tested
2018   for with the <literal>IS UNKNOWN</literal> predicate. Further path
2019   evaluation steps use only those items for which the filter expression
2020   returned <literal>true</literal>.
2021  </para>
2022
2023  <para>
2024   The functions and operators that can be used in filter expressions are
2025   listed in <xref linkend="functions-sqljson-filter-ex-table"/>.  Within a
2026   filter expression, the <literal>@</literal> variable denotes the value
2027   being considered (i.e., one result of the preceding path step).  You can
2028   write accessor operators after <literal>@</literal> to retrieve component
2029   items.
2030  </para>
2031
2032  <para>
2033   For example, suppose you would like to retrieve all heart rate values higher
2034   than 130. You can achieve this as follows:
2035<screen>
2036<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments[*].HR ? (@ &gt; 130)');</userinput>
2037 jsonb_path_query
2038------------------
2039 135
2040</screen>
2041  </para>
2042
2043  <para>
2044   To get the start times of segments with such values, you have to
2045   filter out irrelevant segments before selecting the start times, so the
2046   filter expression is applied to the previous step, and the path used
2047   in the condition is different:
2048<screen>
2049<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments[*] ? (@.HR &gt; 130)."start time"');</userinput>
2050   jsonb_path_query
2051-----------------------
2052 "2018-10-14 10:39:21"
2053</screen>
2054  </para>
2055
2056  <para>
2057   You can use several filter expressions in sequence, if required.
2058   The following example selects start times of all segments that
2059   contain locations with relevant coordinates and high heart rate values:
2060<screen>
2061<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments[*] ? (@.location[1] &lt; 13.4) ? (@.HR &gt; 130)."start time"');</userinput>
2062   jsonb_path_query
2063-----------------------
2064 "2018-10-14 10:39:21"
2065</screen>
2066  </para>
2067
2068  <para>
2069   Using filter expressions at different nesting levels is also allowed.
2070   The following example first filters all segments by location, and then
2071   returns high heart rate values for these segments, if available:
2072<screen>
2073<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments[*] ? (@.location[1] &lt; 13.4).HR ? (@ &gt; 130)');</userinput>
2074 jsonb_path_query
2075------------------
2076 135
2077</screen>
2078  </para>
2079
2080  <para>
2081   You can also nest filter expressions within each other.
2082   This example returns the size of the track if it contains any
2083   segments with high heart rate values, or an empty sequence otherwise:
2084<screen>
2085<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track ? (exists(@.segments[*] ? (@.HR &gt; 130))).segments.size()');</userinput>
2086 jsonb_path_query
2087------------------
2088 2
2089</screen>
2090  </para>

2096    language has the following deviations from the SQL/JSON standard.
2097   </para>
2098
2099   <sect4 id="functions-sqljson-check-expressions">
2100   <title>Boolean Predicate Check Expressions</title>
2101    <para>
2102     As an extension to the SQL standard,
2103     a <productname>PostgreSQL</productname> path expression can be a
2104     Boolean predicate, whereas the SQL standard allows predicates only within
2105     filters. While SQL-standard path expressions return the relevant
2106     element(s) of the queried JSON value, predicate check expressions
2107     return the single three-valued <type>jsonb</type> result of the
2108     predicate: <literal>true</literal>,
2109     <literal>false</literal>, or <literal>null</literal>.
2110     For example, we could write this SQL-standard filter expression:
2111<screen>
2112<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments ?(@[*].HR &gt; 130)');</userinput>
2113                                jsonb_path_query
2114-----------------------------------------------------------&zwsp;----------------------
2115 {"HR": 135, "location": [47.706, 13.2635], "start time": "2018-10-14 10:39:21"}
2116</screen>
2117     The similar predicate check expression simply
2118     returns <literal>true</literal>, indicating that a match exists:
2119<screen>
2120<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', '$.track.segments[*].HR &gt; 130');</userinput>
2121 jsonb_path_query
2122------------------
2123 true
2124</screen>
2125     </para>
2126
2127     <note>
2128      <para>
2129       Predicate check expressions are required in the
2130       <literal>@@</literal> operator (and the
2131       <function>jsonb_path_match</function> function), and should not be used
2132       with the <literal>@?</literal> operator (or the
2133       <function>jsonb_path_exists</function> function).
2134      </para>
2135     </note>
2136    </sect4>

2148   <sect3 id="functions-sqljson-strict-and-lax-modes">
2149   <title>Strict and Lax Modes</title>
2150    <para>
2151     When you query JSON data, the path expression may not match the
2152     actual JSON data structure. An attempt to access a non-existent
2153     member of an object or element of an array is defined as a
2154     structural error. SQL/JSON path expressions have two modes
2155     of handling structural errors:
2156    </para>
2157
2158   <itemizedlist>
2159    <listitem>
2160     <para>
2161      lax (default) &mdash; the path engine implicitly adapts
2162      the queried data to the specified path.
2163      Any structural errors that cannot be fixed as described below
2164      are suppressed, producing no match.
2165     </para>
2166    </listitem>
2167    <listitem>
2168     <para>
2169      strict &mdash; if a structural error occurs, an error is raised.
2170     </para>
2171    </listitem>
2172   </itemizedlist>
2173
2174   <para>
2175    Lax mode facilitates matching of a JSON document and path
2176    expression when the JSON data does not conform to the expected schema.
2177    If an operand does not match the requirements of a particular operation,
2178    it can be automatically wrapped as an SQL/JSON array, or unwrapped by
2179    converting its elements into an SQL/JSON sequence before performing
2180    the operation. Also, comparison operators automatically unwrap their
2181    operands in lax mode, so you can compare SQL/JSON arrays
2182    out-of-the-box. An array of size 1 is considered equal to its sole element.
2183    Automatic unwrapping is not performed when:
2184    <itemizedlist>
2185     <listitem>
2186      <para>
2187       The path expression contains <literal>type()</literal> or
2188       <literal>size()</literal> methods that return the type
2189       and the number of elements in the array, respectively.
2190      </para>
2191     </listitem>
2192     <listitem>
2193      <para>
2194       The queried JSON data contain nested arrays. In this case, only
2195       the outermost array is unwrapped, while all the inner arrays
2196       remain unchanged. Thus, implicit unwrapping can only go one
2197       level down within each path evaluation step.
2198      </para>
2199     </listitem>
2200    </itemizedlist>
2201   </para>
2202
2203   <para>
2204    For example, when querying the GPS data listed above, you can
2205    abstract from the fact that it stores an array of segments
2206    when using lax mode:
2207<screen>
2208<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', 'lax $.track.segments.location');</userinput>
2209 jsonb_path_query
2210-------------------
2211 [47.763, 13.4034]
2212 [47.706, 13.2635]
2213</screen>
2214   </para>
2215
2216   <para>
2217    In strict mode, the specified path must exactly match the structure of
2218    the queried JSON document, so using this path
2219    expression will cause an error:
2220<screen>
2221<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', 'strict $.track.segments.location');</userinput>
2222ERROR:  jsonpath member accessor can only be applied to an object
2223</screen>
2224    To get the same result as in lax mode, you have to explicitly unwrap the
2225    <literal>segments</literal> array:
2226<screen>
2227<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', 'strict $.track.segments[*].location');</userinput>
2228 jsonb_path_query
2229-------------------
2230 [47.763, 13.4034]
2231 [47.706, 13.2635]
2232</screen>
2233   </para>
2234
2235   <para>
2236    The unwrapping behavior of lax mode can lead to surprising results. For
2237    instance, the following query using the <literal>.**</literal> accessor
2238    selects every <literal>HR</literal> value twice:
2239<screen>
2240<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', 'lax $.**.HR');</userinput>
2241 jsonb_path_query
2242------------------
2243 73
2244 135
2245 73
2246 135
2247</screen>
2248    This happens because the <literal>.**</literal> accessor selects both
2249    the <literal>segments</literal> array and each of its elements, while
2250    the <literal>.HR</literal> accessor automatically unwraps arrays when
2251    using lax mode. To avoid surprising results, we recommend using
2252    the <literal>.**</literal> accessor only in strict mode. The
2253    following query selects each <literal>HR</literal> value just once:
2254<screen>
2255<prompt>=&gt;</prompt> <userinput>SELECT jsonb_path_query(:'json', 'strict $.**.HR');</userinput>
2256 jsonb_path_query
2257------------------
2258 73
2259 135
2260</screen>
2261   </para>
2262
2263   <para>
2264    The unwrapping of arrays can also lead to unexpected results. Consider this
2265    example, which selects all the <literal>location</literal> arrays:

3257   <sect3 id="jsonpath-regular-expressions">
3258    <title>SQL/JSON Regular Expressions</title>
3259
3260    <indexterm zone="jsonpath-regular-expressions">
3261     <primary><literal>LIKE_REGEX</literal></primary>
3262     <secondary>in SQL/JSON</secondary>
3263    </indexterm>
3264
3265    <para>
3266     SQL/JSON path expressions allow matching text to a regular expression
3267     with the <literal>like_regex</literal> filter.  For example, the
3268     following SQL/JSON path query would case-insensitively match all
3269     strings in an array that start with an English vowel:
3270<programlisting>
3271$[*] ? (@ like_regex "^[aeiou]" flag "i")
3272</programlisting>
3273    </para>
3274
3275    <para>
3276     The optional <literal>flag</literal> string may include one or more of
3277     the characters
3278     <literal>i</literal> for case-insensitive match,
3279     <literal>m</literal> to allow <literal>^</literal>
3280     and <literal>$</literal> to match at newlines,
3281     <literal>s</literal> to allow <literal>.</literal> to match a newline,
3282     and <literal>q</literal> to quote the whole pattern (reducing the
3283     behavior to a simple substring match).
3284    </para>
3285
3286    <para>
3287     The SQL/JSON standard borrows its definition for regular expressions
3288     from the <literal>LIKE_REGEX</literal> operator, which in turn uses the
3289     XQuery standard.  PostgreSQL does not currently support the
3290     <literal>LIKE_REGEX</literal> operator.  Therefore,
3291     the <literal>like_regex</literal> filter is implemented using the
3292     POSIX regular expression engine described in
3293     <xref linkend="posix-syntax-details"/>.  This leads to various minor
3294     discrepancies from standard SQL/JSON behavior, which are cataloged in
3295     <xref linkend="posix-vs-xquery"/>.
3296     Note, however, that the flag-letter incompatibilities described there
3297     do not apply to SQL/JSON, as it translates the XQuery flag letters to
3298     match what the POSIX engine expects.
3299    </para>
3300
3301    <para>
3302     Keep in mind that the pattern argument of <literal>like_regex</literal>
3303     is a JSON path string literal, written according to the rules given in
3304     <xref linkend="datatype-jsonpath"/>.  This means in particular that any
3305     backslashes you want to use in the regular expression must be doubled.
3306     For example, to match string values of the root document that contain
3307     only digits:
3308<programlisting>
3309$.* ? (@ like_regex "^\\d+$")
3310</programlisting>
3311    </para>

3604
3605  <para>
3606   <function>JSON_TABLE</function> is an SQL/JSON function which
3607   queries <acronym>JSON</acronym> data
3608   and presents the results as a relational view, which can be accessed as a
3609   regular SQL table. You can use <function>JSON_TABLE</function> inside
3610   the <literal>FROM</literal> clause of a <literal>SELECT</literal>,
3611   <literal>UPDATE</literal>, or <literal>DELETE</literal> and as data source
3612   in a <literal>MERGE</literal> statement.
3613  </para>
3614
3615  <para>
3616   Taking JSON data as input, <function>JSON_TABLE</function> uses a JSON path
3617   expression to extract a part of the provided data to use as a
3618   <firstterm>row pattern</firstterm> for the constructed view.  Each SQL/JSON
3619   value given by the row pattern serves as source for a separate row in the
3620   constructed view.
3621  </para>
3622
3623  <para>
3624   To split the row pattern into columns, <function>JSON_TABLE</function>
3625   provides the <literal>COLUMNS</literal> clause that defines the
3626   schema of the created view. For each column, a separate JSON path expression
3627   can be specified to be evaluated against the row pattern to get an SQL/JSON
3628   value that will become the value for the specified column in a given output
3629   row.
3630  </para>
3631
3632  <para>
3633   JSON data stored at a nested level of the row pattern can be extracted using
3634   the <literal>NESTED PATH</literal> clause.  Each
3635   <literal>NESTED PATH</literal> clause can be used to generate one or more
3636   columns using the data from a nested level of the row pattern.  Those
3637   columns can be specified using a <literal>COLUMNS</literal> clause that
3638   looks similar to the top-level COLUMNS clause.  Rows constructed from
3639   NESTED COLUMNS are called <firstterm>child rows</firstterm> and are joined
3640   against the row constructed from the columns specified in the parent
3641   <literal>COLUMNS</literal> clause to get the row in the final view.  Child
3642   columns themselves may contain a <literal>NESTED PATH</literal>
3643   specification thus allowing to extract data located at arbitrary nesting
3644   levels.  Columns produced by multiple <literal>NESTED PATH</literal>s at the
3645   same level are considered to be <firstterm>siblings</firstterm> of each
3646   other and their rows after joining with the parent row are combined using
3647   UNION.
3648  </para>
3649
3650  <para>
3651   The rows produced by <function>JSON_TABLE</function> are laterally
3652   joined to the row that generated them, so you do not have to explicitly join
3653   the constructed view with the original table holding <acronym>JSON</acronym>
3654   data.
3655  </para>
