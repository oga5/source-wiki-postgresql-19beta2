21 <sect1 id="queries-overview">
22  <title>Overview</title>
23
24  <para>
25   The process of retrieving or the command to retrieve data from a
26   database is called a <firstterm>query</firstterm>.  In SQL the
27   <link linkend="sql-select"><command>SELECT</command></link> command is
28   used to specify queries.  The general syntax of the
29   <command>SELECT</command> command is
30<synopsis>
31<optional>WITH <replaceable>with_queries</replaceable></optional> SELECT <replaceable>select_list</replaceable> FROM <replaceable>table_expression</replaceable> <optional><replaceable>sort_specification</replaceable></optional>
32</synopsis>
33   The following sections describe the details of the select list, the
34   table expression, and the sort specification.  <literal>WITH</literal>
35   queries are treated last since they are an advanced feature.
36  </para>
37
38  <para>
39   A simple kind of query has the form:
40<programlisting>
41SELECT * FROM table1;
42</programlisting>
43  Assuming that there is a table called <literal>table1</literal>,
44  this command would retrieve all rows and all user-defined columns from
45  <literal>table1</literal>.  (The method of retrieval depends on the
46  client application.  For example, the
47  <application>psql</application> program will display an ASCII-art
48  table on the screen, while client libraries will offer functions to
49  extract individual values from the query result.)  The select list
50  specification <literal>*</literal> means all columns that the table
51  expression happens to provide.  A select list can also select a
52  subset of the available columns or make calculations using the
53  columns.  For example, if
54  <literal>table1</literal> has columns named <literal>a</literal>,
55  <literal>b</literal>, and <literal>c</literal> (and perhaps others) you can make
56  the following query:
57<programlisting>
58SELECT a, b + c FROM table1;
59</programlisting>
60  (assuming that <literal>b</literal> and <literal>c</literal> are of a numerical
61  data type).
62  See <xref linkend="queries-select-lists"/> for more details.
63 </para>
64
65 <para>
66  <literal>FROM table1</literal> is a simple kind of
67  table expression: it reads just one table.  In general, table
68  expressions can be complex constructs of base tables, joins, and
69  subqueries.  But you can also omit the table expression entirely and
70  use the <command>SELECT</command> command as a calculator:
71<programlisting>
72SELECT 3 * 4;
73</programlisting>
74  This is more useful if the expressions in the select list return
75  varying results.  For example, you could call a function this way:
76<programlisting>
77SELECT random();
78</programlisting>
79  </para>
80 </sect1>

83 <sect1 id="queries-table-expressions">
84  <title>Table Expressions</title>
85
86  <indexterm zone="queries-table-expressions">
87   <primary>table expression</primary>
88  </indexterm>
89
90  <para>
91   A <firstterm>table expression</firstterm> computes a table.  The
92   table expression contains a <literal>FROM</literal> clause that is
93   optionally followed by <literal>WHERE</literal>, <literal>GROUP BY</literal>, and
94   <literal>HAVING</literal> clauses.  Trivial table expressions simply refer
95   to a table on disk, a so-called base table, but more complex
96   expressions can be used to modify or combine base tables in various
97   ways.
98  </para>
99
100  <para>
101   The optional <literal>WHERE</literal>, <literal>GROUP BY</literal>, and
102   <literal>HAVING</literal> clauses in the table expression specify a
103   pipeline of successive transformations performed on the table
104   derived in the <literal>FROM</literal> clause.  All these transformations
105   produce a virtual table that provides the rows that are passed to
106   the select list to compute the output rows of the query.
107  </para>
108
109  <sect2 id="queries-from">
110   <title>The <literal>FROM</literal> Clause</title>
111
112   <para>
113    The <link linkend="sql-from"><literal>FROM</literal></link> clause derives a
114    table from one or more other tables given in a comma-separated
115    table reference list.
116<synopsis>
117FROM <replaceable>table_reference</replaceable> <optional>, <replaceable>table_reference</replaceable> <optional>, ...</optional></optional>
118</synopsis>
119
120    A table reference can be a table name (possibly schema-qualified),
121    or a derived table such as a subquery, a <literal>JOIN</literal> construct, or
122    complex combinations of these.  If more than one table reference is
123    listed in the <literal>FROM</literal> clause, the tables are cross-joined
124    (that is, the Cartesian product of their rows is formed; see below).
125    The result of the <literal>FROM</literal> list is an intermediate virtual
126    table that can then be subject to
127    transformations by the <literal>WHERE</literal>, <literal>GROUP BY</literal>,
128    and <literal>HAVING</literal> clauses and is finally the result of the
129    overall table expression.
130   </para>
131
132   <indexterm>
133    <primary>ONLY</primary>
134   </indexterm>
135
136   <para>
137    When a table reference names a table that is the parent of a
138    table inheritance hierarchy, the table reference produces rows of
139    not only that table but all of its descendant tables, unless the
140    key word <literal>ONLY</literal> precedes the table name.  However, the
141    reference produces only the columns that appear in the named table
142    &mdash; any columns added in subtables are ignored.
143   </para>
144
145   <para>
146    You can write <literal>*</literal> after the table name to explicitly
147    specify that descendant tables are included, which is the opposite of
148    <literal>ONLY</literal>.  There is no real reason to write
149    <literal>*</literal> any more, because searching descendant tables has
150    been the default behavior since <productname>PostgreSQL</productname>
151    version 10.  However, it remains supported for compatibility with older
152    releases.
153   </para>

155   <sect3 id="queries-join">
156    <title>Joined Tables</title>
157
158    <indexterm zone="queries-join">
159     <primary>join</primary>
160    </indexterm>
161
162    <para>
163     A joined table is a table derived from two other (real or
164     derived) tables according to the rules of the particular join
165     type.  Inner, outer, and cross-joins are available.
166     The general syntax of a joined table is
167<synopsis>
168<replaceable>T1</replaceable> <replaceable>join_type</replaceable> <replaceable>T2</replaceable> <optional> <replaceable>join_condition</replaceable> </optional>
169</synopsis>
170     Joins of all types can be chained together, or nested: either or
171     both <replaceable>T1</replaceable> and
172     <replaceable>T2</replaceable> can be joined tables.  Parentheses
173     can be used around <literal>JOIN</literal> clauses to control the join
174     order.  In the absence of parentheses, <literal>JOIN</literal> clauses
175     nest left-to-right.
176    </para>
177
178    <variablelist>
179     <title>Join Types</title>
180
181     <varlistentry>
182      <term>Cross join
183      <indexterm>
184       <primary>join</primary>
185       <secondary>cross</secondary>
186      </indexterm>
187
188      <indexterm>
189       <primary>cross join</primary>
190      </indexterm>
191      </term>
192
193      <listitem>
194<synopsis>
195<replaceable>T1</replaceable> CROSS JOIN <replaceable>T2</replaceable>
196</synopsis>
197
198       <para>
199        For every possible combination of rows from
200        <replaceable>T1</replaceable> and
201        <replaceable>T2</replaceable> (i.e., a Cartesian product),
202        the joined table will contain a
203        row consisting of all columns in <replaceable>T1</replaceable>
204        followed by all columns in <replaceable>T2</replaceable>.  If
205        the tables have N and M rows respectively, the joined
206        table will have N * M rows.
207       </para>
208
209       <para>
210        <literal>FROM <replaceable>T1</replaceable> CROSS JOIN
211        <replaceable>T2</replaceable></literal> is equivalent to
212        <literal>FROM <replaceable>T1</replaceable> INNER JOIN
213        <replaceable>T2</replaceable> ON TRUE</literal> (see below).
214        It is also equivalent to
215        <literal>FROM <replaceable>T1</replaceable>,
216        <replaceable>T2</replaceable></literal>.
217        <note>
218        <para>
219         This latter equivalence does not hold exactly when more than two
220         tables appear, because <literal>JOIN</literal> binds more tightly than
221         comma.  For example
222         <literal>FROM <replaceable>T1</replaceable> CROSS JOIN
223         <replaceable>T2</replaceable> INNER JOIN <replaceable>T3</replaceable>
224         ON <replaceable>condition</replaceable></literal>
225         is not the same as
226         <literal>FROM <replaceable>T1</replaceable>,
227         <replaceable>T2</replaceable> INNER JOIN <replaceable>T3</replaceable>
228         ON <replaceable>condition</replaceable></literal>
229         because the <replaceable>condition</replaceable> can
230         reference <replaceable>T1</replaceable> in the first case but not
231         the second.
232        </para>
233        </note>
234       </para>
235      </listitem>
236     </varlistentry>
237
238     <varlistentry>
239      <term>Qualified joins
240      <indexterm>
241       <primary>join</primary>
242       <secondary>outer</secondary>
243      </indexterm>
244
245      <indexterm>
246       <primary>outer join</primary>
247      </indexterm>
248      </term>
249
250      <listitem>
251<synopsis>
252<replaceable>T1</replaceable> { <optional>INNER</optional> | { LEFT | RIGHT | FULL } <optional>OUTER</optional> } JOIN <replaceable>T2</replaceable> ON <replaceable>boolean_expression</replaceable>
253<replaceable>T1</replaceable> { <optional>INNER</optional> | { LEFT | RIGHT | FULL } <optional>OUTER</optional> } JOIN <replaceable>T2</replaceable> USING ( <replaceable>join column list</replaceable> )
254<replaceable>T1</replaceable> NATURAL { <optional>INNER</optional> | { LEFT | RIGHT | FULL } <optional>OUTER</optional> } JOIN <replaceable>T2</replaceable>
255</synopsis>
256
257       <para>
258        The words <literal>INNER</literal> and
259        <literal>OUTER</literal> are optional in all forms.
260        <literal>INNER</literal> is the default;
261        <literal>LEFT</literal>, <literal>RIGHT</literal>, and
262        <literal>FULL</literal> imply an outer join.
263       </para>
264
265       <para>
266        The <firstterm>join condition</firstterm> is specified in the
267        <literal>ON</literal> or <literal>USING</literal> clause, or implicitly by
268        the word <literal>NATURAL</literal>.  The join condition determines
269        which rows from the two source tables are considered to
270        <quote>match</quote>, as explained in detail below.
271       </para>
272
273       <para>
274        The possible types of qualified join are:
275
276       <variablelist>
277        <varlistentry>
278         <term><literal>INNER JOIN</literal></term>
279
280         <listitem>
281          <para>
282           For each row R1 of T1, the joined table has a row for each
283           row in T2 that satisfies the join condition with R1.
284          </para>
285         </listitem>
286        </varlistentry>
287
288        <varlistentry>
289         <term><literal>LEFT OUTER JOIN</literal>
290         <indexterm>
291          <primary>join</primary>
292          <secondary>left</secondary>
293         </indexterm>
294
295         <indexterm>
296          <primary>left join</primary>
297         </indexterm>
298         </term>
299
300         <listitem>
301          <para>
302           First, an inner join is performed.  Then, for each row in
303           T1 that does not satisfy the join condition with any row in
304           T2, a joined row is added with null values in columns of
305           T2.  Thus, the joined table always has at least
306           one row for each row in T1.
307          </para>
308         </listitem>
309        </varlistentry>
310
311        <varlistentry>
312         <term><literal>RIGHT OUTER JOIN</literal>
313         <indexterm>
314          <primary>join</primary>
315          <secondary>right</secondary>
316         </indexterm>
317
318         <indexterm>
319          <primary>right join</primary>
320         </indexterm>
321         </term>
322
323         <listitem>
324          <para>
325           First, an inner join is performed.  Then, for each row in
326           T2 that does not satisfy the join condition with any row in
327           T1, a joined row is added with null values in columns of
328           T1.  This is the converse of a left join: the result table
329           will always have a row for each row in T2.
330          </para>
331         </listitem>
332        </varlistentry>
333
334        <varlistentry>
335         <term><literal>FULL OUTER JOIN</literal></term>
336
337         <listitem>
338          <para>
339           First, an inner join is performed.  Then, for each row in
340           T1 that does not satisfy the join condition with any row in
341           T2, a joined row is added with null values in columns of
342           T2.  Also, for each row of T2 that does not satisfy the
343           join condition with any row in T1, a joined row with null
344           values in the columns of T1 is added.
345          </para>
346         </listitem>
347        </varlistentry>
348       </variablelist>
349       </para>
350
351       <para>
352        The <literal>ON</literal> clause is the most general kind of join
353        condition: it takes a Boolean value expression of the same
354        kind as is used in a <literal>WHERE</literal> clause.  A pair of rows
355        from <replaceable>T1</replaceable> and <replaceable>T2</replaceable> match if the
356        <literal>ON</literal> expression evaluates to true.
357       </para>
358
359       <para>
360        The <literal>USING</literal> clause is a shorthand that allows you to take
361        advantage of the specific situation where both sides of the join use
362        the same name for the joining column(s).  It takes a
363        comma-separated list of the shared column names
364        and forms a join condition that includes an equality comparison
365        for each one.  For example, joining <replaceable>T1</replaceable>
366        and <replaceable>T2</replaceable> with <literal>USING (a, b)</literal> produces
367        the join condition <literal>ON <replaceable>T1</replaceable>.a
368        = <replaceable>T2</replaceable>.a AND <replaceable>T1</replaceable>.b
369        = <replaceable>T2</replaceable>.b</literal>.
370       </para>
371
372       <para>
373        Furthermore, the output of <literal>JOIN USING</literal> suppresses
374        redundant columns: there is no need to print both of the matched
375        columns, since they must have equal values.  While <literal>JOIN
376        ON</literal> produces all columns from <replaceable>T1</replaceable> followed by all
377        columns from <replaceable>T2</replaceable>, <literal>JOIN USING</literal> produces one
378        output column for each of the listed column pairs (in the listed
379        order), followed by any remaining columns from <replaceable>T1</replaceable>,
380        followed by any remaining columns from <replaceable>T2</replaceable>.
381       </para>
382
383       <para>
384        <indexterm>
385         <primary>join</primary>
386         <secondary>natural</secondary>
387        </indexterm>
388        <indexterm>
389         <primary>natural join</primary>
390        </indexterm>
391        Finally, <literal>NATURAL</literal> is a shorthand form of
392        <literal>USING</literal>: it forms a <literal>USING</literal> list
393        consisting of all column names that appear in both
394        input tables.  As with <literal>USING</literal>, these columns appear
395        only once in the output table.  If there are no common
396        column names, <literal>NATURAL JOIN</literal> behaves like
397        <literal>CROSS JOIN</literal>.
398       </para>
399
400       <note>
401        <para>
402         <literal>USING</literal> is reasonably safe from column changes
403         in the joined relations since only the listed columns
404         are combined.  <literal>NATURAL</literal> is considerably more risky since
405         any schema changes to either relation that cause a new matching
406         column name to be present will cause the join to combine that new
407         column as well.
408        </para>
409       </note>
410      </listitem>
411     </varlistentry>
412    </variablelist>
413
414    <para>
415     To put this together, assume we have tables <structname>t1</structname>:
416<programlisting>
417 num | name
418-----+------
419   1 | a
420   2 | b
421   3 | c
422</programlisting>
423     and <structname>t2</structname>:
424<programlisting>
425 num | value
426-----+-------
427   1 | xxx
428   3 | yyy
429   5 | zzz
430</programlisting>
431     then we get the following results for the various joins:
432<screen>

440   2 | b    |   3 | yyy
441   2 | b    |   5 | zzz
442   3 | c    |   1 | xxx
443   3 | c    |   3 | yyy
444   3 | c    |   5 | zzz
445(9 rows)
446
447<prompt>=&gt;</prompt> <userinput>SELECT * FROM t1 INNER JOIN t2 ON t1.num = t2.num;</userinput>

449-----+------+-----+-------

502
503    <para>
504     The join condition specified with <literal>ON</literal> can also contain
505     conditions that do not relate directly to the join.  This can
506     prove useful for some queries but needs to be thought out
507     carefully.  For example:
508<screen>
509<prompt>=&gt;</prompt> <userinput>SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num AND t2.value = 'xxx';</userinput>
510 num | name | num | value
511-----+------+-----+-------
512   1 | a    |   1 | xxx
513   2 | b    |     |
514   3 | c    |     |
515(3 rows)
516</screen>
517     Notice that placing the restriction in the <literal>WHERE</literal> clause
518     produces a different result:
519<screen>
520<prompt>=&gt;</prompt> <userinput>SELECT * FROM t1 LEFT JOIN t2 ON t1.num = t2.num WHERE t2.value = 'xxx';</userinput>
521 num | name | num | value
522-----+------+-----+-------
523   1 | a    |   1 | xxx
524(1 row)
525</screen>
526     This is because a restriction placed in the <literal>ON</literal>
527     clause is processed <emphasis>before</emphasis> the join, while
528     a restriction placed in the <literal>WHERE</literal> clause is processed
529     <emphasis>after</emphasis> the join.
530     That does not matter with inner joins, but it matters a lot with outer
531     joins.
532    </para>

535   <sect3 id="queries-table-aliases">
536    <title>Table and Column Aliases</title>
537
538    <indexterm zone="queries-table-aliases">
539     <primary>alias</primary>
540     <secondary>in the FROM clause</secondary>
541    </indexterm>
542
543    <indexterm>
544     <primary>label</primary>
545     <see>alias</see>
546    </indexterm>
547
548    <para>
549     A temporary name can be given to tables and complex table
550     references to be used for references to the derived table in
551     the rest of the query.  This is called a <firstterm>table
552     alias</firstterm>.
553    </para>
554
555    <para>
556     To create a table alias, write
557<synopsis>
558FROM <replaceable>table_reference</replaceable> AS <replaceable>alias</replaceable>
559</synopsis>
560     or
561<synopsis>
562FROM <replaceable>table_reference</replaceable> <replaceable>alias</replaceable>
563</synopsis>
564     The <literal>AS</literal> key word is optional noise.
565     <replaceable>alias</replaceable> can be any identifier.
566    </para>
567
568    <para>
569     A typical application of table aliases is to assign short
570     identifiers to long table names to keep the join clauses
571     readable.  For example:
572<programlisting>
573SELECT * FROM some_very_long_table_name s JOIN another_fairly_long_name a ON s.id = a.num;
574</programlisting>
575    </para>
576
577    <para>
578     The alias becomes the new name of the table reference so far as the
579     current query is concerned &mdash; it is not allowed to refer to the
580     table by the original name elsewhere in the query.  Thus, this is not
581     valid:
582<programlisting>
583SELECT * FROM my_table AS m WHERE my_table.a &gt; 5;    -- wrong
584</programlisting>
585    </para>
586
587    <para>
588     Table aliases are mainly for notational convenience, but it is
589     necessary to use them when joining a table to itself, e.g.:
590<programlisting>
591SELECT * FROM people AS mother JOIN people AS child ON mother.id = child.mother_id;
592</programlisting>
593    </para>
594
595    <para>
596     Parentheses are used to resolve ambiguities.  In the following example,
597     the first statement assigns the alias <literal>b</literal> to the second
598     instance of <literal>my_table</literal>, but the second statement assigns the
599     alias to the result of the join:
600<programlisting>
601SELECT * FROM my_table AS a CROSS JOIN my_table AS b ...
602SELECT * FROM (my_table AS a CROSS JOIN my_table) AS b ...
603</programlisting>
604    </para>
605
606    <para>
607     Another form of table aliasing gives temporary names to the columns of
608     the table, as well as the table itself:
609<synopsis>
610FROM <replaceable>table_reference</replaceable> <optional>AS</optional> <replaceable>alias</replaceable> ( <replaceable>column1</replaceable> <optional>, <replaceable>column2</replaceable> <optional>, ...</optional></optional> )
611</synopsis>
612     If fewer column aliases are specified than the actual table has
613     columns, the remaining columns are not renamed.  This syntax is
614     especially useful for self-joins or subqueries.
615    </para>
616
617    <para>
618     When an alias is applied to the output of a <literal>JOIN</literal>
619     clause, the alias hides the original
620     name(s) within the <literal>JOIN</literal>.  For example:
621<programlisting>
622SELECT a.* FROM my_table AS a JOIN your_table AS b ON ...
623</programlisting>
624     is valid SQL, but:
625<programlisting>
626SELECT a.* FROM (my_table AS a JOIN your_table AS b ON ...) AS c
627</programlisting>
628     is not valid; the table alias <literal>a</literal> is not visible
629     outside the alias <literal>c</literal>.
630    </para>
631   </sect3>

633   <sect3 id="queries-subqueries">
634    <title>Subqueries</title>
635
636    <indexterm zone="queries-subqueries">
637     <primary>subquery</primary>
638    </indexterm>
639
640    <para>
641     Subqueries specifying a derived table must be enclosed in
642     parentheses.  They may be assigned a table alias name, and optionally
643     column alias names (as in <xref linkend="queries-table-aliases"/>).
644     For example:
645<programlisting>
646FROM (SELECT * FROM table1) AS alias_name
647</programlisting>
648    </para>
649
650    <para>
651     This example is equivalent to <literal>FROM table1 AS
652     alias_name</literal>.  More interesting cases, which cannot be
653     reduced to a plain join, arise when the subquery involves
654     grouping or aggregation.
655    </para>
656
657    <para>
658     A subquery can also be a <command>VALUES</command> list:
659<programlisting>
660FROM (VALUES ('anne', 'smith'), ('bob', 'jones'), ('joe', 'blow'))
661     AS names(first, last)
662</programlisting>
663     Again, a table alias is optional.  Assigning alias names to the columns
664     of the <command>VALUES</command> list is optional, but is good practice.
665     For more information see <xref linkend="queries-values"/>.
666    </para>
667
668    <para>
669     According to the SQL standard, a table alias name must be supplied
670     for a subquery.  <productname>PostgreSQL</productname>
671     allows <literal>AS</literal> and the alias to be omitted, but
672     writing one is good practice in SQL code that might be ported to
673     another system.
674    </para>
675   </sect3>

677   <sect3 id="queries-tablefunctions">
678    <title>Table Functions</title>
679
680    <indexterm zone="queries-tablefunctions"><primary>table function</primary></indexterm>
681
682    <indexterm zone="queries-tablefunctions">
683     <primary>function</primary>
684     <secondary>in the FROM clause</secondary>
685    </indexterm>
686
687    <para>
688     Table functions are functions that produce a set of rows, made up
689     of either base data types (scalar types) or composite data types
690     (table rows).  They are used like a table, view, or subquery in
691     the <literal>FROM</literal> clause of a query. Columns returned by table
692     functions can be included in <literal>SELECT</literal>,
693     <literal>JOIN</literal>, or <literal>WHERE</literal> clauses in the same manner
694     as columns of a table, view, or subquery.
695    </para>
696
697    <para>
698     Table functions may also be combined using the <literal>ROWS FROM</literal>
699     syntax, with the results returned in parallel columns; the number of
700     result rows in this case is that of the largest function result, with
701     smaller results padded with null values to match.
702    </para>
703
704<synopsis>
705<replaceable>function_call</replaceable> <optional>WITH ORDINALITY</optional> <optional><optional>AS</optional> <replaceable>table_alias</replaceable> <optional>(<replaceable>column_alias</replaceable> <optional>, ... </optional>)</optional></optional>
706ROWS FROM( <replaceable>function_call</replaceable> <optional>, ... </optional> ) <optional>WITH ORDINALITY</optional> <optional><optional>AS</optional> <replaceable>table_alias</replaceable> <optional>(<replaceable>column_alias</replaceable> <optional>, ... </optional>)</optional></optional>
707</synopsis>
708
709    <para>
710     If the <literal>WITH ORDINALITY</literal> clause is specified, an
711     additional column of type <type>bigint</type> will be added to the
712     function result columns.  This column numbers the rows of the function
713     result set, starting from 1. (This is a generalization of the
714     SQL-standard syntax for <literal>UNNEST ... WITH ORDINALITY</literal>.)
715     By default, the ordinal column is called <literal>ordinality</literal>, but
716     a different column name can be assigned to it using
717     an <literal>AS</literal> clause.
718    </para>
719
720    <para>
721     The special table function <literal>UNNEST</literal> may be called with
722     any number of array parameters, and it returns a corresponding number of
723     columns, as if <literal>UNNEST</literal>
724     (<xref linkend="functions-array"/>) had been called on each parameter
725     separately and combined using the <literal>ROWS FROM</literal> construct.
726    </para>
727
728<synopsis>
729UNNEST( <replaceable>array_expression</replaceable> <optional>, ... </optional> ) <optional>WITH ORDINALITY</optional> <optional><optional>AS</optional> <replaceable>table_alias</replaceable> <optional>(<replaceable>column_alias</replaceable> <optional>, ... </optional>)</optional></optional>
730</synopsis>
731
732    <para>
733     If no <replaceable>table_alias</replaceable> is specified, the function
734     name is used as the table name; in the case of a <literal>ROWS FROM()</literal>
735     construct, the first function's name is used.
736    </para>
737
738    <para>
739     If column aliases are not supplied, then for a function returning a base
740     data type, the column name is also the same as the function name.  For a
741     function returning a composite type, the result columns get the names
742     of the individual attributes of the type.
743    </para>
744
745    <para>
746     Some examples:
747<programlisting>
748CREATE TABLE foo (fooid int, foosubid int, fooname text);
749
750CREATE FUNCTION getfoo(int) RETURNS SETOF foo AS $$
751    SELECT * FROM foo WHERE fooid = $1;
752$$ LANGUAGE SQL;
753
754SELECT * FROM getfoo(1) AS t1;
755
756SELECT * FROM foo
757    WHERE foosubid IN (
758                        SELECT foosubid
759                        FROM getfoo(foo.fooid) z
760                        WHERE z.fooid = foo.fooid
761                      );
762
763CREATE VIEW vw_getfoo AS SELECT * FROM getfoo(1);
764
765SELECT * FROM vw_getfoo;
766</programlisting>
767    </para>
768
769    <para>
770     In some cases it is useful to define table functions that can
771     return different column sets depending on how they are invoked.
772     To support this, the table function can be declared as returning
773     the pseudo-type <type>record</type> with no <literal>OUT</literal>
774     parameters.  When such a function is used in
775     a query, the expected row structure must be specified in the
776     query itself, so that the system can know how to parse and plan
777     the query.  This syntax looks like:
778    </para>
779
780<synopsis>
781<replaceable>function_call</replaceable> <optional>AS</optional> <replaceable>alias</replaceable> (<replaceable>column_definition</replaceable> <optional>, ... </optional>)
782<replaceable>function_call</replaceable> AS <optional><replaceable>alias</replaceable></optional> (<replaceable>column_definition</replaceable> <optional>, ... </optional>)
783ROWS FROM( ... <replaceable>function_call</replaceable> AS (<replaceable>column_definition</replaceable> <optional>, ... </optional>) <optional>, ... </optional> )
784</synopsis>
785
786    <para>
787     When not using the <literal>ROWS FROM()</literal> syntax,
788     the <replaceable>column_definition</replaceable> list replaces the column
789     alias list that could otherwise be attached to the <literal>FROM</literal>
790     item; the names in the column definitions serve as column aliases.
791     When using the <literal>ROWS FROM()</literal> syntax,
792     a <replaceable>column_definition</replaceable> list can be attached to
793     each member function separately; or if there is only one member function
794     and no <literal>WITH ORDINALITY</literal> clause,
795     a <replaceable>column_definition</replaceable> list can be written in
796     place of a column alias list following <literal>ROWS FROM()</literal>.
797    </para>
798
799    <para>
800     Consider this example:
801<programlisting>
802SELECT *
803    FROM dblink('dbname=mydb', 'SELECT proname, prosrc FROM pg_proc')
804      AS t1(proname name, prosrc text)
805    WHERE proname LIKE 'bytea%';
806</programlisting>
807     The <xref linkend="contrib-dblink-function"/> function
808     (part of the <xref linkend="dblink"/> module) executes
809     a remote query.  It is declared to return
810     <type>record</type> since it might be used for any kind of query.
811     The actual column set must be specified in the calling query so
812     that the parser knows, for example, what <literal>*</literal> should
813     expand to.
814    </para>
815
816    <para>
817     This example uses <literal>ROWS FROM</literal>:
818<programlisting>
819SELECT *
820FROM ROWS FROM
821    (
822        json_to_recordset('[{"a":40,"b":"foo"},{"a":"100","b":"bar"}]')
823            AS (a INTEGER, b TEXT),
824        generate_series(1, 3)
825    ) AS x (p, q, s)
826ORDER BY p;
827
828  p  |  q  | s
829-----+-----+---
830  40 | foo | 1
831 100 | bar | 2
832     |     | 3
833</programlisting>
834     It joins two functions into a single <literal>FROM</literal>
835     target.  <function>json_to_recordset()</function> is instructed
836     to return two columns, the first <type>integer</type>
837     and the second <type>text</type>.  The result of
838     <function>generate_series()</function> is used directly.
839     The <literal>ORDER BY</literal> clause sorts the column values
840     as integers.
841    </para>
842   </sect3>

844   <sect3 id="queries-lateral">
845    <title><literal>LATERAL</literal> Subqueries</title>
846
847    <indexterm zone="queries-lateral">
848     <primary>LATERAL</primary>
849     <secondary>in the FROM clause</secondary>
850    </indexterm>
851
852    <para>
853     Subqueries appearing in <literal>FROM</literal> can be
854     preceded by the key word <literal>LATERAL</literal>.  This allows them to
855     reference columns provided by preceding <literal>FROM</literal> items.
856     (Without <literal>LATERAL</literal>, each subquery is
857     evaluated independently and so cannot cross-reference any other
858     <literal>FROM</literal> item.)
859    </para>
860
861    <para>
862     Table functions appearing in <literal>FROM</literal> can also be
863     preceded by the key word <literal>LATERAL</literal>, but for functions the
864     key word is optional; the function's arguments can contain references
865     to columns provided by preceding <literal>FROM</literal> items in any case.
866    </para>
867
868    <para>
869     A <literal>GRAPH_TABLE</literal> <literal>FROM</literal> item can also
870     always contain lateral references.
871    </para>
872
873    <para>
874     A <literal>LATERAL</literal> item can appear at the top level in the
875     <literal>FROM</literal> list, or within a <literal>JOIN</literal> tree.  In the latter
876     case it can also refer to any items that are on the left-hand side of a
877     <literal>JOIN</literal> that it is on the right-hand side of.
878    </para>
879
880    <para>
881     When a <literal>FROM</literal> item contains <literal>LATERAL</literal>
882     cross-references, evaluation proceeds as follows: for each row of the
883     <literal>FROM</literal> item providing the cross-referenced column(s), or
884     set of rows of multiple <literal>FROM</literal> items providing the
885     columns, the <literal>LATERAL</literal> item is evaluated using that
886     row or row set's values of the columns.  The resulting row(s) are
887     joined as usual with the rows they were computed from.  This is
888     repeated for each row or set of rows from the column source table(s).
889    </para>
890
891    <para>
892     A trivial example of <literal>LATERAL</literal> is
893<programlisting>
894SELECT * FROM foo, LATERAL (SELECT * FROM bar WHERE bar.id = foo.bar_id) ss;
895</programlisting>
896     This is not especially useful since it has exactly the same result as
897     the more conventional
898<programlisting>
899SELECT * FROM foo, bar WHERE bar.id = foo.bar_id;
900</programlisting>
901     <literal>LATERAL</literal> is primarily useful when the cross-referenced
902     column is necessary for computing the row(s) to be joined.  A common
903     application is providing an argument value for a set-returning function.
904     For example, supposing that <function>vertices(polygon)</function> returns the
905     set of vertices of a polygon, we could identify close-together vertices
906     of polygons stored in a table with:
907<programlisting>
908SELECT p1.id, p2.id, v1, v2
909FROM polygons p1, polygons p2,
910     LATERAL vertices(p1.poly) v1,
911     LATERAL vertices(p2.poly) v2
912WHERE (v1 &lt;-&gt; v2) &lt; 10 AND p1.id != p2.id;
913</programlisting>
914     This query could also be written
915<programlisting>
916SELECT p1.id, p2.id, v1, v2
917FROM polygons p1 CROSS JOIN LATERAL vertices(p1.poly) v1,
918     polygons p2 CROSS JOIN LATERAL vertices(p2.poly) v2
919WHERE (v1 &lt;-&gt; v2) &lt; 10 AND p1.id != p2.id;
920</programlisting>
921     or in several other equivalent formulations.  (As already mentioned,
922     the <literal>LATERAL</literal> key word is unnecessary in this example, but
923     we use it for clarity.)
924    </para>
925
926    <para>
927     It is often particularly handy to <literal>LEFT JOIN</literal> to a
928     <literal>LATERAL</literal> subquery, so that source rows will appear in
929     the result even if the <literal>LATERAL</literal> subquery produces no
930     rows for them.  For example, if <function>get_product_names()</function> returns
931     the names of products made by a manufacturer, but some manufacturers in
932     our table currently produce no products, we could find out which ones
933     those are like this:
934<programlisting>
935SELECT m.name
936FROM manufacturers m LEFT JOIN LATERAL get_product_names(m.id) pname ON true
937WHERE pname IS NULL;
938</programlisting>
939    </para>
940   </sect3>

943  <sect2 id="queries-where">
944   <title>The <literal>WHERE</literal> Clause</title>
945
946   <indexterm zone="queries-where">
947    <primary>WHERE</primary>
948   </indexterm>
949
950   <para>
951    The syntax of the <link linkend="sql-where"><literal>WHERE</literal></link>
952    clause is
953<synopsis>
954WHERE <replaceable>search_condition</replaceable>
955</synopsis>
956    where <replaceable>search_condition</replaceable> is any value
957    expression (see <xref linkend="sql-expressions"/>) that
958    returns a value of type <type>boolean</type>.
959   </para>
960
961   <para>
962    After the processing of the <literal>FROM</literal> clause is done, each
963    row of the derived virtual table is checked against the search
964    condition.  If the result of the condition is true, the row is
965    kept in the output table, otherwise (i.e., if the result is
966    false or null) it is discarded.  The search condition typically
967    references at least one column of the table generated in the
968    <literal>FROM</literal> clause; this is not required, but otherwise the
969    <literal>WHERE</literal> clause will be fairly useless.
970   </para>
971
972   <note>
973    <para>
974     The join condition of an inner join can be written either in
975     the <literal>WHERE</literal> clause or in the <literal>JOIN</literal> clause.
976     For example, these table expressions are equivalent:
977<programlisting>
978FROM a, b WHERE a.id = b.id AND b.val &gt; 5
979</programlisting>
980     and:
981<programlisting>
982FROM a INNER JOIN b ON (a.id = b.id) WHERE b.val &gt; 5
983</programlisting>
984     or perhaps even:
985<programlisting>
986FROM a NATURAL JOIN b WHERE b.val &gt; 5
987</programlisting>
988     Which one of these you use is mainly a matter of style.  The
989     <literal>JOIN</literal> syntax in the <literal>FROM</literal> clause is
990     probably not as portable to other SQL database management systems,
991     even though it is in the SQL standard.  For
992     outer joins there is no choice:  they must be done in
993     the <literal>FROM</literal> clause.  The <literal>ON</literal> or <literal>USING</literal>
994     clause of an outer join is <emphasis>not</emphasis> equivalent to a
995     <literal>WHERE</literal> condition, because it results in the addition
996     of rows (for unmatched input rows) as well as the removal of rows
997     in the final result.
998    </para>
999   </note>
1000
1001   <para>
1002    Here are some examples of <literal>WHERE</literal> clauses:
1003<programlisting>
1004SELECT ... FROM fdt WHERE c1 &gt; 5
1005
1006SELECT ... FROM fdt WHERE c1 IN (1, 2, 3)
1007
1008SELECT ... FROM fdt WHERE c1 IN (SELECT c1 FROM t2)
1009
1010SELECT ... FROM fdt WHERE c1 IN (SELECT c3 FROM t2 WHERE c2 = fdt.c1 + 10)
1011
1012SELECT ... FROM fdt WHERE c1 BETWEEN (SELECT c3 FROM t2 WHERE c2 = fdt.c1 + 10) AND 100
1013
1014SELECT ... FROM fdt WHERE EXISTS (SELECT c1 FROM t2 WHERE c2 &gt; fdt.c1)
1015</programlisting>
1016    <literal>fdt</literal> is the table derived in the
1017    <literal>FROM</literal> clause. Rows that do not meet the search
1018    condition of the <literal>WHERE</literal> clause are eliminated from
1019    <literal>fdt</literal>. Notice the use of scalar subqueries as
1020    value expressions.  Just like any other query, the subqueries can
1021    employ complex table expressions.  Notice also how
1022    <literal>fdt</literal> is referenced in the subqueries.
1023    Qualifying <literal>c1</literal> as <literal>fdt.c1</literal> is only necessary
1024    if <literal>c1</literal> is also the name of a column in the derived
1025    input table of the subquery.  But qualifying the column name adds
1026    clarity even when it is not needed.  This example shows how the column
1027    naming scope of an outer query extends into its inner queries.
1028   </para>
1029  </sect2>

1032  <sect2 id="queries-group">
1033   <title>The <literal>GROUP BY</literal> and <literal>HAVING</literal> Clauses</title>
1034
1035   <indexterm zone="queries-group">
1036    <primary>GROUP BY</primary>
1037   </indexterm>
1038
1039   <indexterm zone="queries-group">
1040    <primary>grouping</primary>
1041   </indexterm>
1042
1043   <para>
1044    After passing the <literal>WHERE</literal> filter, the derived input
1045    table might be subject to grouping, using the <literal>GROUP BY</literal>
1046    clause, and elimination of group rows using the <literal>HAVING</literal>
1047    clause.
1048   </para>
1049
1050<synopsis>
1051SELECT <replaceable>select_list</replaceable>
1052    FROM ...
1053    <optional>WHERE ...</optional>
1054    GROUP BY <replaceable>grouping_column_reference</replaceable> <optional>, <replaceable>grouping_column_reference</replaceable></optional>...
1055</synopsis>
1056
1057   <para>
1058    The <link linkend="sql-groupby"><literal>GROUP BY</literal></link> clause is
1059    used to group together those rows in a table that have the same
1060    values in all the columns listed. The order in which the columns
1061    are listed does not matter.  The effect is to combine each set
1062    of rows having common values into one group row that
1063    represents all rows in the group.  This is done to
1064    eliminate redundancy in the output and/or compute aggregates that
1065    apply to these groups.  For instance:
1066<screen>
1067<prompt>=&gt;</prompt> <userinput>SELECT * FROM test1;</userinput>
1068 x | y
1069---+---
1070 a | 3
1071 c | 2
1072 b | 5
1073 a | 1
1074(4 rows)
1075
1076<prompt>=&gt;</prompt> <userinput>SELECT x FROM test1 GROUP BY x;</userinput>
1077 x
1078---
1079 a
1080 b
1081 c
1082(3 rows)
1083</screen>
1084   </para>
1085
1086   <para>
1087    In the second query, we could not have written <literal>SELECT *
1088    FROM test1 GROUP BY x</literal>, because there is no single value
1089    for the column <structfield>y</structfield> that could be associated with each
1090    group.  The grouped-by columns can be referenced in the select list since
1091    they have a single value in each group.
1092   </para>
1093
1094   <para>
1095    In general, if a table is grouped, columns that are not
1096    listed in <literal>GROUP BY</literal> cannot be referenced except in aggregate
1097    expressions.  An example with aggregate expressions is:
1098<screen>
1099<prompt>=&gt;</prompt> <userinput>SELECT x, sum(y) FROM test1 GROUP BY x;</userinput>
1100 x | sum
1101---+-----
1102 a |   4
1103 b |   5
1104 c |   2
1105(3 rows)
1106</screen>
1107    Here <literal>sum</literal> is an aggregate function that
1108    computes a single value over the entire group.  More information
1109    about the available aggregate functions can be found in <xref
1110    linkend="functions-aggregate"/>.
1111   </para>
1112
1113   <tip>
1114    <para>
1115     Grouping without aggregate expressions effectively calculates the
1116     set of distinct values in a column.  This can also be achieved
1117     using the <literal>DISTINCT</literal> clause (see <xref
1118     linkend="queries-distinct"/>).
1119    </para>
1120   </tip>
1121
1122   <para>
1123    Here is another example:  it calculates the total sales for each
1124    product (rather than the total sales of all products):
1125<programlisting>
1126SELECT product_id, p.name, (sum(s.units) * p.price) AS sales
1127    FROM products p LEFT JOIN sales s USING (product_id)
1128    GROUP BY product_id, p.name, p.price;
1129</programlisting>
1130    In this example, the columns <literal>product_id</literal>,
1131    <literal>p.name</literal>, and <literal>p.price</literal> must be
1132    in the <literal>GROUP BY</literal> clause since they are referenced in
1133    the query select list (but see below).  The column
1134    <literal>s.units</literal> does not have to be in the <literal>GROUP
1135    BY</literal> list since it is only used in an aggregate expression
1136    (<literal>sum(...)</literal>), which represents the sales
1137    of a product.  For each product, the query returns a summary row about
1138    all sales of the product.
1139   </para>
1140
1141   <indexterm><primary>functional dependency</primary></indexterm>
1142
1143   <para>
1144    If the products table is set up so that, say,
1145    <literal>product_id</literal> is the primary key, then it would be
1146    enough to group by <literal>product_id</literal> in the above example,
1147    since name and price would be <firstterm>functionally
1148    dependent</firstterm> on the product ID, and so there would be no
1149    ambiguity about which name and price value to return for each product
1150    ID group.
1151   </para>
1152
1153   <para>
1154    In strict SQL, <literal>GROUP BY</literal> can only group by columns of
1155    the source table, but <productname>PostgreSQL</productname> extends
1156    this to also allow <literal>GROUP BY</literal> to group by columns in the
1157    select list.  Grouping by value expressions instead of simple
1158    column names is also allowed (but <literal>GROUP BY</literal>
1159    expressions cannot contain aggregate functions or window functions).
1160   </para>
1161
1162   <para>
1163    PostgreSQL also supports the syntax <literal>GROUP BY ALL</literal>,
1164    which is equivalent to explicitly writing all select-list entries that
1165    do not contain either an aggregate function referring to the same query level or a window function.
1166    This can greatly simplify ad-hoc exploration of data.
1167    As an example, these queries are equivalent:
1168<screen>
1169<prompt>=&gt;</prompt> <userinput>SELECT a, b, a + b, sum(c) FROM test1 GROUP BY ALL;</userinput>
1170 a | b | ?column? | sum
1171---+---+----------+----
1172 1 | 4 |        5 |  9
1173 2 | 5 |        7 | 12
1174 3 | 6 |        9 | 15
1175(3 rows)
1176
1177<prompt>=&gt;</prompt> <userinput>SELECT a, b, a + b, sum(c) FROM test1 GROUP BY a, b, a + b;</userinput>
1178 a | b | ?column? | sum
1179---+---+----------+----
1180 1 | 4 |        5 |  9
1181 2 | 5 |        7 | 12
1182 3 | 6 |        9 | 15
1183(3 rows)
1184</screen>
1185   </para>
1186
1187   <indexterm>
1188    <primary>HAVING</primary>
1189   </indexterm>
1190
1191   <para>
1192    If a table has been grouped using <literal>GROUP BY</literal>,
1193    but only certain groups are of interest, the
1194    <literal>HAVING</literal> clause can be used, much like a
1195    <literal>WHERE</literal> clause, to eliminate groups from the result.
1196    The syntax is:
1197<synopsis>
1198SELECT <replaceable>select_list</replaceable> FROM ... <optional>WHERE ...</optional> GROUP BY ... HAVING <replaceable>boolean_expression</replaceable>
1199</synopsis>
1200    Expressions in the <literal>HAVING</literal> clause can refer both to
1201    grouped expressions and to ungrouped expressions (which necessarily
1202    involve an aggregate function).
1203   </para>
1204
1205   <para>
1206    Example:
1207<screen>
1208<prompt>=&gt;</prompt> <userinput>SELECT x, sum(y) FROM test1 GROUP BY x HAVING sum(y) &gt; 3;</userinput>
1209 x | sum
1210---+-----
1211 a |   4
1212 b |   5
1213(2 rows)
1214
1215<prompt>=&gt;</prompt> <userinput>SELECT x, sum(y) FROM test1 GROUP BY x HAVING x &lt; 'c';</userinput>
1216 x | sum
1217---+-----
1218 a |   4
1219 b |   5
1220(2 rows)
1221</screen>
1222   </para>
1223
1224   <para>
1225    Again, a more realistic example:
1226<programlisting>
1227SELECT product_id, p.name, (sum(s.units) * (p.price - p.cost)) AS profit
1228    FROM products p LEFT JOIN sales s USING (product_id)
1229    WHERE s.date &gt; CURRENT_DATE - INTERVAL '4 weeks'
1230    GROUP BY product_id, p.name, p.price, p.cost
1231    HAVING sum(p.price * s.units) &gt; 5000;
1232</programlisting>
1233    In the example above, the <literal>WHERE</literal> clause is selecting
1234    rows by a column that is not grouped (the expression is only true for
1235    sales during the last four weeks), while the <literal>HAVING</literal>
1236    clause restricts the output to groups with total gross sales over
1237    5000.  Note that the aggregate expressions do not necessarily need
1238    to be the same in all parts of the query.
1239   </para>
1240
1241   <para>
1242    If a query contains aggregate function calls, but no <literal>GROUP BY</literal>
1243    clause, grouping still occurs: the result is a single group row (or
1244    perhaps no rows at all, if the single row is then eliminated by
1245    <literal>HAVING</literal>).
1246    The same is true if it contains a <literal>HAVING</literal> clause, even
1247    without any aggregate function calls or <literal>GROUP BY</literal> clause.
1248   </para>
1249  </sect2>

1251  <sect2 id="queries-grouping-sets">
1252   <title><literal>GROUPING SETS</literal>, <literal>CUBE</literal>, and <literal>ROLLUP</literal></title>
1253
1254   <indexterm zone="queries-grouping-sets">
1255    <primary>GROUPING SETS</primary>
1256   </indexterm>
1257   <indexterm zone="queries-grouping-sets">
1258    <primary>CUBE</primary>
1259   </indexterm>
1260   <indexterm zone="queries-grouping-sets">
1261    <primary>ROLLUP</primary>
1262   </indexterm>
1263
1264   <para>
1265    More complex grouping operations than those described above are possible
1266    using the concept of <firstterm>grouping sets</firstterm>.  The data selected by
1267    the <literal>FROM</literal> and <literal>WHERE</literal> clauses is grouped separately
1268    by each specified grouping set, aggregates computed for each group just as
1269    for simple <literal>GROUP BY</literal> clauses, and then the results returned.
1270    For example:
1271<screen>
1272<prompt>=&gt;</prompt> <userinput>SELECT * FROM items_sold;</userinput>
1273 brand | size | sales
1274-------+------+-------
1275 Foo   | L    |  10
1276 Foo   | M    |  20
1277 Bar   | M    |  15
1278 Bar   | L    |  5
1279(4 rows)
1280
1281<prompt>=&gt;</prompt> <userinput>SELECT brand, size, sum(sales) FROM items_sold GROUP BY GROUPING SETS ((brand), (size), ());</userinput>
1282 brand | size | sum
1283-------+------+-----
1284 Foo   |      |  30
1285 Bar   |      |  20
1286       | L    |  15
1287       | M    |  35
1288       |      |  50
1289(5 rows)
1290</screen>
1291   </para>
1292
1293   <para>
1294    Each sublist of <literal>GROUPING SETS</literal> may specify zero or more columns
1295    or expressions and is interpreted the same way as though it were directly
1296    in the <literal>GROUP BY</literal> clause.  An empty grouping set means that all
1297    rows are aggregated down to a single group (which is output even if no
1298    input rows were present), as described above for the case of aggregate
1299    functions with no <literal>GROUP BY</literal> clause.
1300   </para>
1301
1302   <para>
1303    References to the grouping columns or expressions are replaced
1304    by null values in result rows for grouping sets in which those
1305    columns do not appear.  To distinguish which grouping a particular output
1306    row resulted from, see <xref linkend="functions-grouping-table"/>.
1307   </para>
1308
1309   <para>
1310    A shorthand notation is provided for specifying two common types of grouping set.
1311    A clause of the form
1312<programlisting>
1313ROLLUP ( <replaceable>e1</replaceable>, <replaceable>e2</replaceable>, <replaceable>e3</replaceable>, ... )
1314</programlisting>
1315    represents the given list of expressions and all prefixes of the list including
1316    the empty list; thus it is equivalent to
1317<programlisting>
1318GROUPING SETS (
1319    ( <replaceable>e1</replaceable>, <replaceable>e2</replaceable>, <replaceable>e3</replaceable>, ... ),
1320    ...
1321    ( <replaceable>e1</replaceable>, <replaceable>e2</replaceable> ),
1322    ( <replaceable>e1</replaceable> ),
1323    ( )
1324)
1325</programlisting>
1326    This is commonly used for analysis over hierarchical data; e.g., total
1327    salary by department, division, and company-wide total.
1328   </para>
1329
1330   <para>
1331    A clause of the form
1332<programlisting>
1333CUBE ( <replaceable>e1</replaceable>, <replaceable>e2</replaceable>, ... )
1334</programlisting>
1335    represents the given list and all of its possible subsets (i.e., the power
1336    set).  Thus
1337<programlisting>
1338CUBE ( a, b, c )
1339</programlisting>
1340    is equivalent to
1341<programlisting>
1342GROUPING SETS (
1343    ( a, b, c ),
1344    ( a, b    ),
1345    ( a,    c ),
1346    ( a       ),
1347    (    b, c ),
1348    (    b    ),
1349    (       c ),
1350    (         )
1351)
1352</programlisting>
1353   </para>
1354
1355   <para>
1356    The individual elements of a <literal>CUBE</literal> or <literal>ROLLUP</literal>
1357    clause may be either individual expressions, or sublists of elements in
1358    parentheses.  In the latter case, the sublists are treated as single
1359    units for the purposes of generating the individual grouping sets.
1360    For example:
1361<programlisting>
1362CUBE ( (a, b), (c, d) )
1363</programlisting>
1364    is equivalent to
1365<programlisting>
1366GROUPING SETS (
1367    ( a, b, c, d ),
1368    ( a, b       ),
1369    (       c, d ),
1370    (            )
1371)
1372</programlisting>
1373    and
1374<programlisting>
1375ROLLUP ( a, (b, c), d )
1376</programlisting>
1377    is equivalent to
1378<programlisting>
1379GROUPING SETS (
1380    ( a, b, c, d ),
1381    ( a, b, c    ),
1382    ( a          ),
1383    (            )
1384)
1385</programlisting>
1386   </para>
1387
1388   <para>
1389    The <literal>CUBE</literal> and <literal>ROLLUP</literal> constructs can be used either
1390    directly in the <literal>GROUP BY</literal> clause, or nested inside a
1391    <literal>GROUPING SETS</literal> clause.  If one <literal>GROUPING SETS</literal> clause
1392    is nested inside another, the effect is the same as if all the elements of
1393    the inner clause had been written directly in the outer clause.
1394   </para>
1395
1396   <para>
1397    If multiple grouping items are specified in a single <literal>GROUP BY</literal>
1398    clause, then the final list of grouping sets is the Cartesian product of the
1399    individual items.  For example:
1400<programlisting>
1401GROUP BY a, CUBE (b, c), GROUPING SETS ((d), (e))
1402</programlisting>
1403    is equivalent to
1404<programlisting>
1405GROUP BY GROUPING SETS (
1406    (a, b, c, d), (a, b, c, e),
1407    (a, b, d),    (a, b, e),
1408    (a, c, d),    (a, c, e),
1409    (a, d),       (a, e)
1410)
1411</programlisting>
1412   </para>
1413
1414   <para>
1415    <indexterm zone="queries-grouping-sets">
1416     <primary>ALL</primary>
1417     <secondary>GROUP BY ALL</secondary>
1418    </indexterm>
1419    <indexterm zone="queries-grouping-sets">
1420     <primary>DISTINCT</primary>
1421     <secondary>GROUP BY DISTINCT</secondary>
1422    </indexterm>
1423    When specifying multiple grouping items together, the final set of grouping
1424    sets might contain duplicates. For example:
1425<programlisting>
1426GROUP BY ROLLUP (a, b), ROLLUP (a, c)
1427</programlisting>
1428    is equivalent to
1429<programlisting>
1430GROUP BY GROUPING SETS (
1431    (a, b, c),
1432    (a, b),
1433    (a, b),
1434    (a, c),
1435    (a),
1436    (a),
1437    (a, c),
1438    (a),
1439    ()
1440)
1441</programlisting>
1442    If these duplicates are undesirable, they can be removed using the
1443    <literal>DISTINCT</literal> clause directly on the <literal>GROUP BY</literal>.
1444    Therefore:
1445<programlisting>
1446GROUP BY <emphasis>DISTINCT</emphasis> ROLLUP (a, b), ROLLUP (a, c)
1447</programlisting>
1448    is equivalent to
1449<programlisting>
1450GROUP BY GROUPING SETS (
1451    (a, b, c),
1452    (a, b),
1453    (a, c),
1454    (a),
1455    ()
1456)
1457</programlisting>
1458    This is not the same as using <literal>SELECT DISTINCT</literal> because the output
1459    rows may still contain duplicates.  If any of the ungrouped columns contains NULL,
1460    it will be indistinguishable from the NULL used when that same column is grouped.
1461   </para>
1462
1463  <note>
1464   <para>
1465    The construct <literal>(a, b)</literal> is normally recognized in expressions as
1466    a <link linkend="sql-syntax-row-constructors">row constructor</link>.
1467    Within the <literal>GROUP BY</literal> clause, this does not apply at the top
1468    levels of expressions, and <literal>(a, b)</literal> is parsed as a list of
1469    expressions as described above.  If for some reason you <emphasis>need</emphasis>
1470    a row constructor in a grouping expression, use <literal>ROW(a, b)</literal>.
1471   </para>
1472  </note>

1475  <sect2 id="queries-window">
1476   <title>Window Function Processing</title>
1477
1478   <indexterm zone="queries-window">
1479    <primary>window function</primary>
1480    <secondary>order of execution</secondary>
1481   </indexterm>
1482
1483   <para>
1484    If the query contains any window functions (see
1485    <xref linkend="tutorial-window"/>,
1486    <xref linkend="functions-window"/> and
1487    <xref linkend="syntax-window-functions"/>), these functions are evaluated
1488    after any grouping, aggregation, and <literal>HAVING</literal> filtering is
1489    performed.  That is, if the query uses any aggregates, <literal>GROUP
1490    BY</literal>, or <literal>HAVING</literal>, then the rows seen by the window functions
1491    are the group rows instead of the original table rows from
1492    <literal>FROM</literal>/<literal>WHERE</literal>.
1493   </para>
1494
1495   <para>
1496    When multiple window functions are used, all the window functions having
1497    equivalent <literal>PARTITION BY</literal> and <literal>ORDER BY</literal>
1498    clauses in their window definitions are guaranteed to see the same
1499    ordering of the input rows, even if the <literal>ORDER BY</literal> does
1500    not uniquely determine the ordering.
1501    However, no guarantees are made about the evaluation of functions having
1502    different <literal>PARTITION BY</literal> or <literal>ORDER BY</literal> specifications.
1503    (In such cases a sort step is typically required between the passes of
1504    window function evaluations, and the sort is not guaranteed to preserve
1505    ordering of rows that its <literal>ORDER BY</literal> sees as equivalent.)
1506   </para>
1507
1508   <para>
1509    Currently, window functions always require presorted data, and so the
1510    query output will be ordered according to one or another of the window
1511    functions' <literal>PARTITION BY</literal>/<literal>ORDER BY</literal> clauses.
1512    It is not recommended to rely on this, however.  Use an explicit
1513    top-level <literal>ORDER BY</literal> clause if you want to be sure the
1514    results are sorted in a particular way.
1515   </para>

1521  <title>Select Lists</title>
1522
1523  <indexterm>
1524   <primary>SELECT</primary>
1525   <secondary>select list</secondary>
1526  </indexterm>
1527
1528  <para>
1529   As shown in the previous section,
1530   the table expression in the <command>SELECT</command> command
1531   constructs an intermediate virtual table by possibly combining
1532   tables, views, eliminating rows, grouping, etc.  This table is
1533   finally passed on to processing by the <firstterm>select list</firstterm>.  The select
1534   list determines which <emphasis>columns</emphasis> of the
1535   intermediate table are actually output.
1536  </para>
1537
1538  <sect2 id="queries-select-list-items">
1539   <title>Select-List Items</title>
1540
1541   <indexterm>
1542    <primary>*</primary>
1543   </indexterm>
1544
1545   <para>
1546    The simplest kind of select list is <literal>*</literal> which
1547    emits all columns that the table expression produces.  Otherwise,
1548    a select list is a comma-separated list of value expressions (as
1549    defined in <xref linkend="sql-expressions"/>).  For instance, it
1550    could be a list of column names:
1551<programlisting>
1552SELECT a, b, c FROM ...
1553</programlisting>
1554     The columns names <literal>a</literal>, <literal>b</literal>, and <literal>c</literal>
1555     are either the actual names of the columns of tables referenced
1556     in the <literal>FROM</literal> clause, or the aliases given to them as
1557     explained in <xref linkend="queries-table-aliases"/>.  The name
1558     space available in the select list is the same as in the
1559     <literal>WHERE</literal> clause, unless grouping is used, in which case
1560     it is the same as in the <literal>HAVING</literal> clause.
1561   </para>
1562
1563   <para>
1564    If more than one table has a column of the same name, the table
1565    name must also be given, as in:
1566<programlisting>
1567SELECT tbl1.a, tbl2.a, tbl1.b FROM ...
1568</programlisting>
1569    When working with multiple tables, it can also be useful to ask for
1570    all the columns of a particular table:
1571<programlisting>
1572SELECT tbl1.*, tbl2.a FROM ...
1573</programlisting>
1574    See <xref linkend="rowtypes-usage"/> for more about
1575    the <replaceable>table_name</replaceable><literal>.*</literal> notation.
1576   </para>
1577
1578   <para>
1579    If an arbitrary value expression is used in the select list, it
1580    conceptually adds a new virtual column to the returned table.  The
1581    value expression is evaluated once for each result row, with
1582    the row's values substituted for any column references.  But the
1583    expressions in the select list do not have to reference any
1584    columns in the table expression of the <literal>FROM</literal> clause;
1585    they can be constant arithmetic expressions, for instance.
1586   </para>
1587  </sect2>

1590   <title>Column Labels</title>
1591
1592   <indexterm zone="queries-column-labels">
1593    <primary>alias</primary>
1594    <secondary>in the select list</secondary>
1595   </indexterm>
1596
1597   <para>
1598    The entries in the select list can be assigned names for subsequent
1599    processing, such as for use in an <literal>ORDER BY</literal> clause
1600    or for display by the client application.  For example:
1601<programlisting>
1602SELECT a AS value, b + c AS sum FROM ...
1603</programlisting>
1604   </para>
1605
1606   <para>
1607    If no output column name is specified using <literal>AS</literal>,
1608    the system assigns a default column name.  For simple column references,
1609    this is the name of the referenced column.  For function
1610    calls, this is the name of the function.  For complex expressions,
1611    the system will generate a generic name.
1612   </para>
1613
1614   <para>
1615    The <literal>AS</literal> key word is usually optional, but in some
1616    cases where the desired column name matches a
1617    <productname>PostgreSQL</productname> key word, you must write
1618    <literal>AS</literal> or double-quote the column name in order to
1619    avoid ambiguity.
1620    (<xref linkend="sql-keywords-appendix"/> shows which key words
1621    require <literal>AS</literal> to be used as a column label.)
1622    For example, <literal>FROM</literal> is one such key word, so this
1623    does not work:
1624<programlisting>
1625SELECT a from, b + c AS sum FROM ...
1626</programlisting>
1627    but either of these do:
1628<programlisting>
1629SELECT a AS from, b + c AS sum FROM ...
1630SELECT a "from", b + c AS sum FROM ...
1631</programlisting>
1632    For greatest safety against possible
1633    future key word additions, it is recommended that you always either
1634    write <literal>AS</literal> or double-quote the output column name.
1635   </para>
1636
1637   <note>
1638    <para>
1639     The naming of output columns here is different from that done in
1640     the <literal>FROM</literal> clause (see <xref
1641     linkend="queries-table-aliases"/>).  It is possible
1642     to rename the same column twice, but the name assigned in
1643     the select list is the one that will be passed on.
1644    </para>
1645   </note>

1648  <sect2 id="queries-distinct">
1649   <title><literal>DISTINCT</literal></title>
1650
1651   <indexterm zone="queries-distinct">
1652    <primary>ALL</primary>
1653    <secondary>SELECT ALL</secondary>
1654   </indexterm>
1655   <indexterm zone="queries-distinct">
1656    <primary>DISTINCT</primary>
1657    <secondary>SELECT DISTINCT</secondary>
1658   </indexterm>
1659
1660   <indexterm zone="queries-distinct">
1661    <primary>duplicates</primary>
1662   </indexterm>
1663
1664   <para>
1665    After the select list has been processed, the result table can
1666    optionally be subject to the elimination of duplicate rows.  The
1667    <literal>DISTINCT</literal> key word is written directly after
1668    <literal>SELECT</literal> to specify this:
1669<synopsis>
1670SELECT DISTINCT <replaceable>select_list</replaceable> ...
1671</synopsis>
1672    (Instead of <literal>DISTINCT</literal> the key word <literal>ALL</literal>
1673    can be used to specify the default behavior of retaining all rows.)
1674   </para>
1675
1676   <indexterm>
1677    <primary>null value</primary>
1678    <secondary sortas="DISTINCT">in DISTINCT</secondary>
1679   </indexterm>
1680
1681   <para>
1682    Obviously, two rows are considered distinct if they differ in at
1683    least one column value.  Null values are considered equal in this
1684    comparison.
1685   </para>
1686
1687   <para>
1688    Alternatively, an arbitrary expression can determine what rows are
1689    to be considered distinct:
1690<synopsis>
1691SELECT DISTINCT ON (<replaceable>expression</replaceable> <optional>, <replaceable>expression</replaceable> ...</optional>) <replaceable>select_list</replaceable> ...
1692</synopsis>
1693    Here <replaceable>expression</replaceable> is an arbitrary value
1694    expression that is evaluated for all rows.  A set of rows for
1695    which all the expressions are equal are considered duplicates, and
1696    only the first row of the set is kept in the output.  Note that
1697    the <quote>first row</quote> of a set is unpredictable unless the
1698    query is sorted on enough columns to guarantee a unique ordering
1699    of the rows arriving at the <literal>DISTINCT</literal> filter.
1700    (<literal>DISTINCT ON</literal> processing occurs after <literal>ORDER
1701    BY</literal> sorting.)
1702   </para>
1703
1704   <para>
1705    The <literal>DISTINCT ON</literal> clause is not part of the SQL standard
1706    and is sometimes considered bad style because of the potentially
1707    indeterminate nature of its results.  With judicious use of
1708    <literal>GROUP BY</literal> and subqueries in <literal>FROM</literal>, this
1709    construct can be avoided, but it is often the most convenient
1710    alternative.
1711   </para>

1716 <sect1 id="queries-union">
1717  <title>Combining Queries (<literal>UNION</literal>, <literal>INTERSECT</literal>, <literal>EXCEPT</literal>)</title>
1718
1719  <indexterm zone="queries-union">
1720   <primary>UNION</primary>
1721  </indexterm>
1722  <indexterm zone="queries-union">
1723   <primary>INTERSECT</primary>
1724  </indexterm>
1725  <indexterm zone="queries-union">
1726   <primary>EXCEPT</primary>
1727  </indexterm>
1728  <indexterm zone="queries-union">
1729   <primary>set union</primary>
1730  </indexterm>
1731  <indexterm zone="queries-union">
1732   <primary>set intersection</primary>
1733  </indexterm>
1734  <indexterm zone="queries-union">
1735   <primary>set difference</primary>
1736  </indexterm>
1737  <indexterm zone="queries-union">
1738   <primary>set operation</primary>
1739  </indexterm>
1740
1741  <para>
1742   The results of two queries can be combined using the set operations
1743   union, intersection, and difference.  The syntax is
1744<synopsis>
1745<replaceable>query1</replaceable> UNION <optional>ALL</optional> <replaceable>query2</replaceable>
1746<replaceable>query1</replaceable> INTERSECT <optional>ALL</optional> <replaceable>query2</replaceable>
1747<replaceable>query1</replaceable> EXCEPT <optional>ALL</optional> <replaceable>query2</replaceable>
1748</synopsis>
1749   where <replaceable>query1</replaceable> and
1750   <replaceable>query2</replaceable> are queries that can use any of
1751   the features discussed up to this point.
1752  </para>
1753
1754  <para>
1755   <literal>UNION</literal> effectively appends the result of
1756   <replaceable>query2</replaceable> to the result of
1757   <replaceable>query1</replaceable> (although there is no guarantee
1758   that this is the order in which the rows are actually returned).
1759   Furthermore, it eliminates duplicate rows from its result, in the same
1760   way as <literal>DISTINCT</literal>, unless <literal>UNION ALL</literal> is used.
1761  </para>
1762
1763  <para>
1764   <literal>INTERSECT</literal> returns all rows that are both in the result
1765   of <replaceable>query1</replaceable> and in the result of
1766   <replaceable>query2</replaceable>.  Duplicate rows are eliminated
1767   unless <literal>INTERSECT ALL</literal> is used.
1768  </para>
1769
1770  <para>
1771   <literal>EXCEPT</literal> returns all rows that are in the result of
1772   <replaceable>query1</replaceable> but not in the result of
1773   <replaceable>query2</replaceable>.  (This is sometimes called the
1774   <firstterm>difference</firstterm> between two queries.)  Again, duplicates
1775   are eliminated unless <literal>EXCEPT ALL</literal> is used.
1776  </para>
1777
1778  <para>
1779   In order to calculate the union, intersection, or difference of two
1780   queries, the two queries must be <quote>union compatible</quote>,
1781   which means that they return the same number of columns and
1782   the corresponding columns have compatible data types, as
1783   described in <xref linkend="typeconv-union-case"/>.
1784  </para>
1785
1786  <para>
1787   Set operations can be combined, for example
1788<synopsis>
1789<replaceable>query1</replaceable> UNION <replaceable>query2</replaceable> EXCEPT <replaceable>query3</replaceable>
1790</synopsis>
1791   which is equivalent to
1792<synopsis>
1793(<replaceable>query1</replaceable> UNION <replaceable>query2</replaceable>) EXCEPT <replaceable>query3</replaceable>
1794</synopsis>
1795   As shown here, you can use parentheses to control the order of
1796   evaluation.  Without parentheses, <literal>UNION</literal>
1797   and <literal>EXCEPT</literal> associate left-to-right,
1798   but <literal>INTERSECT</literal> binds more tightly than those two
1799   operators.  Thus
1800<synopsis>
1801<replaceable>query1</replaceable> UNION <replaceable>query2</replaceable> INTERSECT <replaceable>query3</replaceable>
1802</synopsis>
1803   means
1804<synopsis>
1805<replaceable>query1</replaceable> UNION (<replaceable>query2</replaceable> INTERSECT <replaceable>query3</replaceable>)
1806</synopsis>
1807   You can also surround an individual <replaceable>query</replaceable>
1808   with parentheses.  This is important if
1809   the <replaceable>query</replaceable> needs to use any of the clauses
1810   discussed in following sections, such as <literal>LIMIT</literal>.
1811   Without parentheses, you'll get a syntax error, or else the clause will
1812   be understood as applying to the output of the set operation rather
1813   than one of its inputs.  For example,
1814<synopsis>
1815SELECT a FROM b UNION SELECT x FROM y LIMIT 10
1816</synopsis>
1817   is accepted, but it means
1818<synopsis>
1819(SELECT a FROM b UNION SELECT x FROM y) LIMIT 10
1820</synopsis>
1821   not
1822<synopsis>
1823SELECT a FROM b UNION (SELECT x FROM y LIMIT 10)
1824</synopsis>
1825  </para>
1826 </sect1>

1829 <sect1 id="queries-order">
1830  <title>Sorting Rows (<literal>ORDER BY</literal>)</title>
1831
1832  <indexterm zone="queries-order">
1833   <primary>sorting</primary>
1834  </indexterm>
1835
1836  <indexterm zone="queries-order">
1837   <primary>ORDER BY</primary>
1838  </indexterm>
1839
1840  <para>
1841   After a query has produced an output table (after the select list
1842   has been processed) it can optionally be sorted.  If sorting is not
1843   chosen, the rows will be returned in an unspecified order.  The actual
1844   order in that case will depend on the scan and join plan types and
1845   the order on disk, but it must not be relied on.  A particular
1846   output ordering can only be guaranteed if the sort step is explicitly
1847   chosen.
1848  </para>
1849
1850  <para>
1851   The <literal>ORDER BY</literal> clause specifies the sort order:
1852<synopsis>
1853SELECT <replaceable>select_list</replaceable>
1854    FROM <replaceable>table_expression</replaceable>
1855    ORDER BY <replaceable>sort_expression1</replaceable> <optional>ASC | DESC</optional> <optional>NULLS { FIRST | LAST }</optional>
1856             <optional>, <replaceable>sort_expression2</replaceable> <optional>ASC | DESC</optional> <optional>NULLS { FIRST | LAST }</optional> ...</optional>
1857</synopsis>
1858   The sort expression(s) can be any expression that would be valid in the
1859   query's select list.  An example is:
1860<programlisting>
1861SELECT a, b FROM table1 ORDER BY a + b, c;
1862</programlisting>
1863   When more than one expression is specified,
1864   the later values are used to sort rows that are equal according to the
1865   earlier values.  Each expression can be followed by an optional
1866   <literal>ASC</literal> or <literal>DESC</literal> keyword to set the sort direction to
1867   ascending or descending.  <literal>ASC</literal> order is the default.
1868   Ascending order puts smaller values first, where
1869   <quote>smaller</quote> is defined in terms of the
1870   <literal>&lt;</literal> operator.  Similarly, descending order is
1871   determined with the <literal>&gt;</literal> operator.
1872    <footnote>
1873     <para>
1874      Actually, <productname>PostgreSQL</productname> uses the <firstterm>default B-tree
1875      operator class</firstterm> for the expression's data type to determine the sort
1876      ordering for <literal>ASC</literal> and <literal>DESC</literal>.  Conventionally,
1877      data types will be set up so that the <literal>&lt;</literal> and
1878      <literal>&gt;</literal> operators correspond to this sort ordering,
1879      but a user-defined data type's designer could choose to do something
1880      different.
1881     </para>
1882    </footnote>
1883  </para>
1884
1885  <para>
1886   The <literal>NULLS FIRST</literal> and <literal>NULLS LAST</literal> options can be
1887   used to determine whether nulls appear before or after non-null values
1888   in the sort ordering.  By default, null values sort as if larger than any
1889   non-null value; that is, <literal>NULLS FIRST</literal> is the default for
1890   <literal>DESC</literal> order, and <literal>NULLS LAST</literal> otherwise.
1891  </para>
1892
1893  <para>
1894   Note that the ordering options are considered independently for each
1895   sort column.  For example <literal>ORDER BY x, y DESC</literal> means
1896   <literal>ORDER BY x ASC, y DESC</literal>, which is not the same as
1897   <literal>ORDER BY x DESC, y DESC</literal>.
1898  </para>
1899
1900  <para>
1901   A <replaceable>sort_expression</replaceable> can also be the column label or number
1902   of an output column, as in:
1903<programlisting>
1904SELECT a + b AS sum, c FROM table1 ORDER BY sum;
1905SELECT a, max(b) FROM table1 GROUP BY a ORDER BY 1;
1906</programlisting>
1907   both of which sort by the first output column.  Note that an output
1908   column name has to stand alone, that is, it cannot be used in an expression
1909   &mdash; for example, this is <emphasis>not</emphasis> correct:
1910<programlisting>
1911SELECT a + b AS sum, c FROM table1 ORDER BY sum + c;          -- wrong
1912</programlisting>
1913   This restriction is made to reduce ambiguity.  There is still
1914   ambiguity if an <literal>ORDER BY</literal> item is a simple name that
1915   could match either an output column name or a column from the table
1916   expression.  The output column is used in such cases.  This would
1917   only cause confusion if you use <literal>AS</literal> to rename an output
1918   column to match some other table column's name.
1919  </para>
1920
1921  <para>
1922   <literal>ORDER BY</literal> can be applied to the result of a
1923   <literal>UNION</literal>, <literal>INTERSECT</literal>, or <literal>EXCEPT</literal>
1924   combination, but in this case it is only permitted to sort by
1925   output column names or numbers, not by expressions.
1926  </para>
1927 </sect1>

1930 <sect1 id="queries-limit">
1931  <title><literal>LIMIT</literal> and <literal>OFFSET</literal></title>
1932
1933  <indexterm zone="queries-limit">
1934   <primary>LIMIT</primary>
1935  </indexterm>
1936
1937  <indexterm zone="queries-limit">
1938   <primary>OFFSET</primary>
1939  </indexterm>
1940
1941  <para>
1942   <literal>LIMIT</literal> and <literal>OFFSET</literal> allow you to retrieve just
1943   a portion of the rows that are generated by the rest of the query:
1944<synopsis>
1945SELECT <replaceable>select_list</replaceable>
1946    FROM <replaceable>table_expression</replaceable>
1947    <optional> ORDER BY ... </optional>
1948    <optional> LIMIT { <replaceable class="parameter">count</replaceable> | ALL } </optional>
1949    <optional> OFFSET <replaceable class="parameter">start</replaceable> </optional>
1950</synopsis>
1951  </para>
1952
1953  <para>
1954   If a limit count is given, no more than that many rows will be
1955   returned (but possibly fewer, if the query itself yields fewer rows).
1956   <literal>LIMIT ALL</literal> is the same as omitting the <literal>LIMIT</literal>
1957   clause, as is <literal>LIMIT</literal> with a NULL argument.
1958  </para>
1959
1960  <para>
1961   <literal>OFFSET</literal> says to skip that many rows before beginning to
1962   return rows.  <literal>OFFSET 0</literal> is the same as omitting the
1963   <literal>OFFSET</literal> clause, as is <literal>OFFSET</literal> with a NULL argument.
1964  </para>
1965
1966  <para>
1967   If both <literal>OFFSET</literal>
1968   and <literal>LIMIT</literal> appear, then <literal>OFFSET</literal> rows are
1969   skipped before starting to count the <literal>LIMIT</literal> rows that
1970   are returned.
1971  </para>
1972
1973  <para>
1974   When using <literal>LIMIT</literal>, it is important to use an
1975   <literal>ORDER BY</literal> clause that constrains the result rows into a
1976   unique order.  Otherwise you will get an unpredictable subset of
1977   the query's rows. You might be asking for the tenth through
1978   twentieth rows, but tenth through twentieth in what ordering? The
1979   ordering is unknown, unless you specified <literal>ORDER BY</literal>.
1980  </para>
1981
1982  <para>
1983   The query optimizer takes <literal>LIMIT</literal> into account when
1984   generating query plans, so you are very likely to get different
1985   plans (yielding different row orders) depending on what you give
1986   for <literal>LIMIT</literal> and <literal>OFFSET</literal>.  Thus, using
1987   different <literal>LIMIT</literal>/<literal>OFFSET</literal> values to select
1988   different subsets of a query result <emphasis>will give
1989   inconsistent results</emphasis> unless you enforce a predictable
1990   result ordering with <literal>ORDER BY</literal>.  This is not a bug; it
1991   is an inherent consequence of the fact that SQL does not promise to
1992   deliver the results of a query in any particular order unless
1993   <literal>ORDER BY</literal> is used to constrain the order.
1994  </para>
1995
1996  <para>
1997   The rows skipped by an <literal>OFFSET</literal> clause still have to be
1998   computed inside the server; therefore a large <literal>OFFSET</literal>
1999   might be inefficient.
2000  </para>
2001 </sect1>

2010
2011  <para>
2012   <literal>VALUES</literal> provides a way to generate a <quote>constant table</quote>
2013   that can be used in a query without having to actually create and populate
2014   a table on-disk.  The syntax is
2015<synopsis>
2016VALUES ( <replaceable class="parameter">expression</replaceable> [, ...] ) [, ...]
2017</synopsis>

2019   The lists must all have the same number of elements (i.e., the number
2020   of columns in the table), and corresponding entries in each list must
2021   have compatible data types.  The actual data type assigned to each column
2022   of the result is determined using the same rules as for <literal>UNION</literal>
2023   (see <xref linkend="typeconv-union-case"/>).
2024  </para>

2028<programlisting>

2030</programlisting>

2033   equivalent to:
2034<programlisting>
2035SELECT 1 AS column1, 'one' AS column2
2036UNION ALL
2037SELECT 2, 'two'
2038UNION ALL
2039SELECT 3, 'three';
2040</programlisting>

2042   By default, <productname>PostgreSQL</productname> assigns the names
2043   <literal>column1</literal>, <literal>column2</literal>, etc. to the columns of a

2047   list, like this:
2048<programlisting>
2049=&gt; SELECT * FROM (VALUES (1, 'one'), (2, 'two'), (3, 'three')) AS t (num,letter);
2050 num | letter
2051-----+--------
2052   1 | one
2053   2 | two
2054   3 | three
2055(3 rows)
2056</programlisting>
2057  </para>

2062<synopsis>
2063SELECT <replaceable>select_list</replaceable> FROM <replaceable>table_expression</replaceable>
2064</synopsis>
2065   and can appear anywhere a <literal>SELECT</literal> can.  For example, you can
2066   use it as part of a <literal>UNION</literal>, or attach a
2067   <replaceable>sort_specification</replaceable> (<literal>ORDER BY</literal>,
2068   <literal>LIMIT</literal>, and/or <literal>OFFSET</literal>) to it.  <literal>VALUES</literal>
2069   is most commonly used as the data source in an <command>INSERT</command> command,
2070   and next most commonly as a subquery.
2071  </para>

2074   For more information see <xref linkend="sql-values"/>.

2081  <title><literal>WITH</literal> Queries (Common Table Expressions)</title>
2082
2083  <indexterm zone="queries-with">
2084   <primary>WITH</primary>
2085   <secondary>in SELECT</secondary>
2086  </indexterm>
2087
2088  <indexterm>
2089   <primary>common table expression</primary>
2090   <see>WITH</see>
2091  </indexterm>
2092
2093  <para>
2094   <literal>WITH</literal> provides a way to write auxiliary statements for use in a
2095   larger query.  These statements, which are often referred to as Common
2096   Table Expressions or <acronym>CTE</acronym>s, can be thought of as defining
2097   temporary tables that exist just for one query.  Each auxiliary statement
2098   in a <literal>WITH</literal> clause can be a <command>SELECT</command>,
2099   <command>INSERT</command>, <command>UPDATE</command>, <command>DELETE</command>,
2100   or <command>MERGE</command>; and the
2101   <literal>WITH</literal> clause itself is attached to a primary statement that can
2102   also be a <command>SELECT</command>, <command>INSERT</command>, <command>UPDATE</command>,
2103   <command>DELETE</command>, or <command>MERGE</command>.
2104  </para>
2105
2106 <sect2 id="queries-with-select">
2107   <title><command>SELECT</command> in <literal>WITH</literal></title>
2108
2109  <para>
2110   The basic value of <command>SELECT</command> in <literal>WITH</literal> is to
2111   break down complicated queries into simpler parts.  An example is:
2112
2113<programlisting>
2114WITH regional_sales AS (
2115    SELECT region, SUM(amount) AS total_sales
2116    FROM orders
2117    GROUP BY region
2118), top_regions AS (
2119    SELECT region
2120    FROM regional_sales
2121    WHERE total_sales &gt; (SELECT SUM(total_sales)/10 FROM regional_sales)
2122)
2123SELECT region,
2124       product,
2125       SUM(quantity) AS product_units,
2126       SUM(amount) AS product_sales
2127FROM orders
2128WHERE region IN (SELECT region FROM top_regions)
2129GROUP BY region, product;
2130</programlisting>
2131
2132   which displays per-product sales totals in only the top sales regions.
2133   The <literal>WITH</literal> clause defines two auxiliary statements named
2134   <structname>regional_sales</structname> and <structname>top_regions</structname>,
2135   where the output of <structname>regional_sales</structname> is used in
2136   <structname>top_regions</structname> and the output of <structname>top_regions</structname>
2137   is used in the primary <command>SELECT</command> query.
2138   This example could have been written without <literal>WITH</literal>,
2139   but we'd have needed two levels of nested sub-<command>SELECT</command>s.  It's a bit
2140   easier to follow this way.
2141  </para>
2142 </sect2>

2144 <sect2 id="queries-with-recursive">
2145  <title>Recursive Queries</title>
2146
2147  <para>
2148   <indexterm>
2149    <primary>RECURSIVE</primary>
2150    <secondary>in common table expressions</secondary>
2151   </indexterm>
2152   The optional <literal>RECURSIVE</literal> modifier changes <literal>WITH</literal>
2153   from a mere syntactic convenience into a feature that accomplishes
2154   things not otherwise possible in standard SQL.  Using
2155   <literal>RECURSIVE</literal>, a <literal>WITH</literal> query can refer to its own
2156   output.  A very simple example is this query to sum the integers from 1
2157   through 100:
2158
2159<programlisting>
2160WITH RECURSIVE t(n) AS (
2161    VALUES (1)
2162  UNION ALL
2163    SELECT n+1 FROM t WHERE n &lt; 100
2164)
2165SELECT sum(n) FROM t;
2166</programlisting>
2167
2168   The general form of a recursive <literal>WITH</literal> query is always a
2169   <firstterm>non-recursive term</firstterm>, then <literal>UNION</literal> (or
2170   <literal>UNION ALL</literal>), then a
2171   <firstterm>recursive term</firstterm>, where only the recursive term can contain
2172   a reference to the query's own output.  Such a query is executed as
2173   follows:
2174  </para>
2175
2176  <procedure>
2177   <title>Recursive Query Evaluation</title>
2178
2179   <step performance="required">
2180    <para>
2181     Evaluate the non-recursive term.  For <literal>UNION</literal> (but not
2182     <literal>UNION ALL</literal>), discard duplicate rows.  Include all remaining
2183     rows in the result of the recursive query, and also place them in a
2184     temporary <firstterm>working table</firstterm>.
2185    </para>
2186   </step>
2187
2188   <step performance="required">
2189    <para>
2190     So long as the working table is not empty, repeat these steps:
2191    </para>
2192    <substeps>
2193     <step performance="required">
2194      <para>
2195       Evaluate the recursive term, substituting the current contents of
2196       the working table for the recursive self-reference.
2197       For <literal>UNION</literal> (but not <literal>UNION ALL</literal>), discard
2198       duplicate rows and rows that duplicate any previous result row.
2199       Include all remaining rows in the result of the recursive query, and
2200       also place them in a temporary <firstterm>intermediate table</firstterm>.
2201      </para>
2202     </step>
2203
2204     <step performance="required">
2205      <para>
2206       Replace the contents of the working table with the contents of the
2207       intermediate table, then empty the intermediate table.
2208      </para>
2209     </step>
2210    </substeps>
2211   </step>
2212  </procedure>
2213
2214  <note>
2215   <para>
2216    While <literal>RECURSIVE</literal> allows queries to be specified
2217    recursively, internally such queries are evaluated iteratively.
2218   </para>
2219  </note>
2220
2221  <para>
2222   In the example above, the working table has just a single row in each step,
2223   and it takes on the values from 1 through 100 in successive steps.  In
2224   the 100th step, there is no output because of the <literal>WHERE</literal>
2225   clause, and so the query terminates.
2226  </para>
2227
2228  <para>
2229   Recursive queries are typically used to deal with hierarchical or
2230   tree-structured data.  A useful example is this query to find all the
2231   direct and indirect sub-parts of a product, given only a table that
2232   shows immediate inclusions:
2233
2234<programlisting>
2235WITH RECURSIVE included_parts(sub_part, part, quantity) AS (
2236    SELECT sub_part, part, quantity FROM parts WHERE part = 'our_product'
2237  UNION ALL
2238    SELECT p.sub_part, p.part, p.quantity * pr.quantity
2239    FROM included_parts pr, parts p
2240    WHERE p.part = pr.sub_part
2241)
2242SELECT sub_part, SUM(quantity) AS total_quantity
2243FROM included_parts
2244GROUP BY sub_part
2245</programlisting>
2246  </para>
2247
2248  <sect3 id="queries-with-search">
2249   <title>Search Order</title>
2250
2251   <para>
2252    When computing a tree traversal using a recursive query, you might want to
2253    order the results in either depth-first or breadth-first order.  This can
2254    be done by computing an ordering column alongside the other data columns
2255    and using that to sort the results at the end.  Note that this does not
2256    actually control in which order the query evaluation visits the rows; that
2257    is as always in SQL implementation-dependent.  This approach merely
2258    provides a convenient way to order the results afterwards.
2259   </para>
2260
2261   <para>
2262    To create a depth-first order, we compute for each result row an array of
2263    rows that we have visited so far.  For example, consider the following
2264    query that searches a table <structname>tree</structname> using a
2265    <structfield>link</structfield> field:
2266
2267<programlisting>
2268WITH RECURSIVE search_tree(id, link, data) AS (
2269    SELECT t.id, t.link, t.data
2270    FROM tree t
2271  UNION ALL
2272    SELECT t.id, t.link, t.data
2273    FROM tree t, search_tree st
2274    WHERE t.id = st.link
2275)
2276SELECT * FROM search_tree;
2277</programlisting>
2278
2279    To add depth-first ordering information, you can write this:
2280
2281<programlisting>
2282WITH RECURSIVE search_tree(id, link, data, <emphasis>path</emphasis>) AS (
2283    SELECT t.id, t.link, t.data, <emphasis>ARRAY[t.id]</emphasis>
2284    FROM tree t
2285  UNION ALL
2286    SELECT t.id, t.link, t.data, <emphasis>path || t.id</emphasis>
2287    FROM tree t, search_tree st
2288    WHERE t.id = st.link
2289)
2290SELECT * FROM search_tree <emphasis>ORDER BY path</emphasis>;
2291</programlisting>
2292   </para>
2293
2294   <para>
2295    In the general case where more than one field needs to be used to identify
2296    a row, use an array of rows.  For example, if we needed to track fields
2297    <structfield>f1</structfield> and <structfield>f2</structfield>:
2298
2299<programlisting>
2300WITH RECURSIVE search_tree(id, link, data, <emphasis>path</emphasis>) AS (
2301    SELECT t.id, t.link, t.data, <emphasis>ARRAY[ROW(t.f1, t.f2)]</emphasis>
2302    FROM tree t
2303  UNION ALL
2304    SELECT t.id, t.link, t.data, <emphasis>path || ROW(t.f1, t.f2)</emphasis>
2305    FROM tree t, search_tree st
2306    WHERE t.id = st.link
2307)
2308SELECT * FROM search_tree <emphasis>ORDER BY path</emphasis>;
2309</programlisting>
2310   </para>
2311
2312   <tip>
2313    <para>
2314     Omit the <literal>ROW()</literal> syntax in the common case where only one
2315     field needs to be tracked.  This allows a simple array rather than a
2316     composite-type array to be used, gaining efficiency.
2317    </para>
2318   </tip>
2319
2320   <para>
2321    To create a breadth-first order, you can add a column that tracks the depth
2322    of the search, for example:
2323
2324<programlisting>
2325WITH RECURSIVE search_tree(id, link, data, <emphasis>depth</emphasis>) AS (
2326    SELECT t.id, t.link, t.data, <emphasis>0</emphasis>
2327    FROM tree t
2328  UNION ALL
2329    SELECT t.id, t.link, t.data, <emphasis>depth + 1</emphasis>
2330    FROM tree t, search_tree st
2331    WHERE t.id = st.link
2332)
2333SELECT * FROM search_tree <emphasis>ORDER BY depth</emphasis>;
2334</programlisting>
2335
2336    To get a stable sort, add data columns as secondary sorting columns.
2337   </para>
2338
2339   <tip>
2340    <para>
2341     The recursive query evaluation algorithm produces its output in
2342     breadth-first search order.  However, this is an implementation detail and
2343     it is perhaps unsound to rely on it.  The order of the rows within each
2344     level is certainly undefined, so some explicit ordering might be desired
2345     in any case.
2346    </para>
2347   </tip>
2348
2349   <para>
2350    There is built-in syntax to compute a depth- or breadth-first sort column.
2351    For example:
2352
2353<programlisting>
2354WITH RECURSIVE search_tree(id, link, data) AS (
2355    SELECT t.id, t.link, t.data
2356    FROM tree t
2357  UNION ALL
2358    SELECT t.id, t.link, t.data
2359    FROM tree t, search_tree st
2360    WHERE t.id = st.link
2361) <emphasis>SEARCH DEPTH FIRST BY id SET ordercol</emphasis>
2362SELECT * FROM search_tree ORDER BY ordercol;
2363
2364WITH RECURSIVE search_tree(id, link, data) AS (
2365    SELECT t.id, t.link, t.data
2366    FROM tree t
2367  UNION ALL
2368    SELECT t.id, t.link, t.data
2369    FROM tree t, search_tree st
2370    WHERE t.id = st.link
2371) <emphasis>SEARCH BREADTH FIRST BY id SET ordercol</emphasis>
2372SELECT * FROM search_tree ORDER BY ordercol;
2373</programlisting>
2374    This syntax is internally expanded to something similar to the above
2375    hand-written forms.  The <literal>SEARCH</literal> clause specifies whether
2376    depth- or breadth first search is wanted, the list of columns to track for
2377    sorting, and a column name that will contain the result data that can be
2378    used for sorting.  That column will implicitly be added to the output rows
2379    of the CTE.
2380   </para>
2381  </sect3>

2383  <sect3 id="queries-with-cycle">
2384   <title>Cycle Detection</title>
2385
2386  <para>
2387   When working with recursive queries it is important to be sure that
2388   the recursive part of the query will eventually return no tuples,
2389   or else the query will loop indefinitely.  Sometimes, using
2390   <literal>UNION</literal> instead of <literal>UNION ALL</literal> can accomplish this
2391   by discarding rows that duplicate previous output rows.  However, often a
2392   cycle does not involve output rows that are completely duplicate: it may be
2393   necessary to check just one or a few fields to see if the same point has
2394   been reached before.  The standard method for handling such situations is
2395   to compute an array of the already-visited values.  For example, consider again
2396   the following query that searches a table <structname>graph</structname> using a
2397   <structfield>link</structfield> field:
2398
2399<programlisting>
2400WITH RECURSIVE search_graph(id, link, data, depth) AS (
2401    SELECT g.id, g.link, g.data, 0
2402    FROM graph g
2403  UNION ALL
2404    SELECT g.id, g.link, g.data, sg.depth + 1
2405    FROM graph g, search_graph sg
2406    WHERE g.id = sg.link
2407)
2408SELECT * FROM search_graph;
2409</programlisting>
2410
2411   This query will loop if the <structfield>link</structfield> relationships contain
2412   cycles.  Because we require a <quote>depth</quote> output, just changing
2413   <literal>UNION ALL</literal> to <literal>UNION</literal> would not eliminate the looping.
2414   Instead we need to recognize whether we have reached the same row again
2415   while following a particular path of links.  We add two columns
2416   <structfield>is_cycle</structfield> and <structfield>path</structfield> to the loop-prone query:
2417
2418<programlisting>
2419WITH RECURSIVE search_graph(id, link, data, depth, <emphasis>is_cycle, path</emphasis>) AS (
2420    SELECT g.id, g.link, g.data, 0,
2421      <emphasis>false,
2422      ARRAY[g.id]</emphasis>
2423    FROM graph g
2424  UNION ALL
2425    SELECT g.id, g.link, g.data, sg.depth + 1,
2426      <emphasis>g.id = ANY(path),
2427      path || g.id</emphasis>
2428    FROM graph g, search_graph sg
2429    WHERE g.id = sg.link <emphasis>AND NOT is_cycle</emphasis>
2430)
2431SELECT * FROM search_graph;
2432</programlisting>
2433
2434   Aside from preventing cycles, the array value is often useful in its own
2435   right as representing the <quote>path</quote> taken to reach any particular row.
2436  </para>
2437
2438  <para>
2439   In the general case where more than one field needs to be checked to
2440   recognize a cycle, use an array of rows.  For example, if we needed to
2441   compare fields <structfield>f1</structfield> and <structfield>f2</structfield>:
2442
2443<programlisting>
2444WITH RECURSIVE search_graph(id, link, data, depth, <emphasis>is_cycle, path</emphasis>) AS (
2445    SELECT g.id, g.link, g.data, 0,
2446      <emphasis>false,
2447      ARRAY[ROW(g.f1, g.f2)]</emphasis>
2448    FROM graph g
2449  UNION ALL
2450    SELECT g.id, g.link, g.data, sg.depth + 1,
2451      <emphasis>ROW(g.f1, g.f2) = ANY(path),
2452      path || ROW(g.f1, g.f2)</emphasis>
2453    FROM graph g, search_graph sg
2454    WHERE g.id = sg.link <emphasis>AND NOT is_cycle</emphasis>
2455)
2456SELECT * FROM search_graph;
2457</programlisting>
2458  </para>
2459
2460  <tip>
2461   <para>
2462    Omit the <literal>ROW()</literal> syntax in the common case where only one field
2463    needs to be checked to recognize a cycle.  This allows a simple array
2464    rather than a composite-type array to be used, gaining efficiency.
2465   </para>
2466  </tip>
2467
2468  <para>
2469   There is built-in syntax to simplify cycle detection.  The above query can
2470   also be written like this:
2471<programlisting>
2472WITH RECURSIVE search_graph(id, link, data, depth) AS (
2473    SELECT g.id, g.link, g.data, 1
2474    FROM graph g
2475  UNION ALL
2476    SELECT g.id, g.link, g.data, sg.depth + 1
2477    FROM graph g, search_graph sg
2478    WHERE g.id = sg.link
2479) <emphasis>CYCLE id SET is_cycle USING path</emphasis>
2480SELECT * FROM search_graph;
2481</programlisting>
2482   and it will be internally rewritten to the above form.  The
2483   <literal>CYCLE</literal> clause specifies first the list of columns to
2484   track for cycle detection, then a column name that will show whether a
2485   cycle has been detected, and finally the name of another column that will track the
2486   path.  The cycle and path columns will implicitly be added to the output
2487   rows of the CTE.
2488  </para>
2489
2490  <tip>
2491   <para>
2492    The cycle path column is computed in the same way as the depth-first
2493    ordering column show in the previous section.  A query can have both a
2494    <literal>SEARCH</literal> and a <literal>CYCLE</literal> clause, but a
2495    depth-first search specification and a cycle detection specification would
2496    create redundant computations, so it's more efficient to just use the
2497    <literal>CYCLE</literal> clause and order by the path column.  If
2498    breadth-first ordering is wanted, then specifying both
2499    <literal>SEARCH</literal> and <literal>CYCLE</literal> can be useful.
2500   </para>
2501  </tip>
2502
2503  <para>
2504   A helpful trick for testing queries
2505   when you are not certain if they might loop is to place a <literal>LIMIT</literal>
2506   in the parent query.  For example, this query would loop forever without
2507   the <literal>LIMIT</literal>:
2508
2509<programlisting>
2510WITH RECURSIVE t(n) AS (
2511    SELECT 1
2512  UNION ALL
2513    SELECT n+1 FROM t
2514)
2515SELECT n FROM t <emphasis>LIMIT 100</emphasis>;
2516</programlisting>
2517
2518   This works because <productname>PostgreSQL</productname>'s implementation
2519   evaluates only as many rows of a <literal>WITH</literal> query as are actually
2520   fetched by the parent query.  Using this trick in production is not
2521   recommended, because other systems might work differently.  Also, it
2522   usually won't work if you make the outer query sort the recursive query's
2523   results or join them to some other table, because in such cases the
2524   outer query will usually try to fetch all of the <literal>WITH</literal> query's
2525   output anyway.
2526  </para>
2527  </sect3>
2528 </sect2>

2530 <sect2 id="queries-with-cte-materialization">
2531  <title>Common Table Expression Materialization</title>
2532
2533  <para>
2534   A useful property of <literal>WITH</literal> queries is that they are
2535   normally evaluated only once per execution of the parent query, even if
2536   they are referred to more than once by the parent query or
2537   sibling <literal>WITH</literal> queries.
2538   Thus, expensive calculations that are needed in multiple places can be
2539   placed within a <literal>WITH</literal> query to avoid redundant work.  Another
2540   possible application is to prevent unwanted multiple evaluations of
2541   functions with side-effects.
2542   However, the other side of this coin is that the optimizer is not able to
2543   push restrictions from the parent query down into a multiply-referenced
2544   <literal>WITH</literal> query, since that might affect all uses of the
2545   <literal>WITH</literal> query's output when it should affect only one.
2546   The multiply-referenced <literal>WITH</literal> query will be
2547   evaluated as written, without suppression of rows that the parent query
2548   might discard afterwards.  (But, as mentioned above, evaluation might stop
2549   early if the reference(s) to the query demand only a limited number of
2550   rows.)
2551  </para>
2552
2553  <para>
2554   However, if a <literal>WITH</literal> query is non-recursive and
2555   side-effect-free (that is, it is a <literal>SELECT</literal> containing
2556   no volatile functions) then it can be folded into the parent query,
2557   allowing joint optimization of the two query levels.  By default, this
2558   happens if the parent query references the <literal>WITH</literal> query
2559   just once, but not if it references the <literal>WITH</literal> query
2560   more than once.  You can override that decision by
2561   specifying <literal>MATERIALIZED</literal> to force separate calculation
2562   of the <literal>WITH</literal> query, or by specifying <literal>NOT
2563   MATERIALIZED</literal> to force it to be merged into the parent query.
2564   The latter choice risks duplicate computation of
2565   the <literal>WITH</literal> query, but it can still give a net savings if
2566   each usage of the <literal>WITH</literal> query needs only a small part
2567   of the <literal>WITH</literal> query's full output.
2568  </para>
2569
2570  <para>
2571   A simple example of these rules is
2572<programlisting>
2573WITH w AS (
2574    SELECT * FROM big_table
2575)
2576SELECT * FROM w WHERE key = 123;
2577</programlisting>
2578   This <literal>WITH</literal> query will be folded, producing the same
2579   execution plan as
2580<programlisting>
2581SELECT * FROM big_table WHERE key = 123;
2582</programlisting>
2583   In particular, if there's an index on <structfield>key</structfield>,
2584   it will probably be used to fetch just the rows having <literal>key =
2585   123</literal>.  On the other hand, in
2586<programlisting>
2587WITH w AS (
2588    SELECT * FROM big_table
2589)
2590SELECT * FROM w AS w1 JOIN w AS w2 ON w1.key = w2.ref
2591WHERE w2.key = 123;
2592</programlisting>
2593   the <literal>WITH</literal> query will be materialized, producing a
2594   temporary copy of <structname>big_table</structname> that is then
2595   joined with itself &mdash; without benefit of any index.  This query
2596   will be executed much more efficiently if written as
2597<programlisting>
2598WITH w AS NOT MATERIALIZED (
2599    SELECT * FROM big_table
2600)
2601SELECT * FROM w AS w1 JOIN w AS w2 ON w1.key = w2.ref
2602WHERE w2.key = 123;
2603</programlisting>
2604   so that the parent query's restrictions can be applied directly
2605   to scans of <structname>big_table</structname>.
2606  </para>
2607
2608  <para>
2609   An example where <literal>NOT MATERIALIZED</literal> could be
2610   undesirable is
2611<programlisting>
2612WITH w AS (
2613    SELECT key, very_expensive_function(val) AS f FROM some_table
2614)
2615SELECT * FROM w AS w1 JOIN w AS w2 ON w1.f = w2.f;
2616</programlisting>
2617   Here, materialization of the <literal>WITH</literal> query ensures
2618   that <function>very_expensive_function</function> is evaluated only
2619   once per table row, not twice.
2620  </para>
2621
2622  <para>
2623   The examples above only show <literal>WITH</literal> being used with
2624   <command>SELECT</command>, but it can be attached in the same way to
2625   <command>INSERT</command>, <command>UPDATE</command>,
2626   <command>DELETE</command>, or <command>MERGE</command>.
2627   In each case it effectively provides temporary table(s) that can
2628   be referred to in the main command.
2629  </para>
2630 </sect2>

2632 <sect2 id="queries-with-modifying">
2633   <title>Data-Modifying Statements in <literal>WITH</literal></title>
2634
2635   <para>
2636    You can use data-modifying statements (<command>INSERT</command>,
2637    <command>UPDATE</command>, <command>DELETE</command>, or
2638    <command>MERGE</command>) in <literal>WITH</literal>.  This
2639    allows you to perform several different operations in the same query.
2640    An example is:
2641
2642<programlisting>
2643WITH moved_rows AS (
2644    DELETE FROM products
2645    WHERE
2646        "date" &gt;= '2010-10-01' AND
2647        "date" &lt; '2010-11-01'
2648    RETURNING *
2649)
2650INSERT INTO products_log
2651SELECT * FROM moved_rows;
2652</programlisting>
2653
2654    This query effectively moves rows from <structname>products</structname> to
2655    <structname>products_log</structname>.  The <command>DELETE</command> in <literal>WITH</literal>
2656    deletes the specified rows from <structname>products</structname>, returning their
2657    contents by means of its <literal>RETURNING</literal> clause; and then the
2658    primary query reads that output and inserts it into
2659    <structname>products_log</structname>.
2660   </para>
2661
2662   <para>
2663    A fine point of the above example is that the <literal>WITH</literal> clause is
2664    attached to the <command>INSERT</command>, not the sub-<command>SELECT</command> within
2665    the <command>INSERT</command>.  This is necessary because data-modifying
2666    statements are only allowed in <literal>WITH</literal> clauses that are attached
2667    to the top-level statement.  However, normal <literal>WITH</literal> visibility
2668    rules apply, so it is possible to refer to the <literal>WITH</literal>
2669    statement's output from the sub-<command>SELECT</command>.
2670   </para>
2671
2672   <para>
2673    Data-modifying statements in <literal>WITH</literal> usually have
2674    <literal>RETURNING</literal> clauses (see <xref linkend="dml-returning"/>),
2675    as shown in the example above.
2676    It is the output of the <literal>RETURNING</literal> clause, <emphasis>not</emphasis> the
2677    target table of the data-modifying statement, that forms the temporary
2678    table that can be referred to by the rest of the query.  If a
2679    data-modifying statement in <literal>WITH</literal> lacks a <literal>RETURNING</literal>
2680    clause, then it forms no temporary table and cannot be referred to in
2681    the rest of the query.  Such a statement will be executed nonetheless.
2682    A not-particularly-useful example is:
2683
2684<programlisting>
2685WITH t AS (
2686    DELETE FROM foo
2687)
2688DELETE FROM bar;
2689</programlisting>
2690
2691    This example would remove all rows from tables <structname>foo</structname> and
2692    <structname>bar</structname>.  The number of affected rows reported to the client
2693    would only include rows removed from <structname>bar</structname>.
2694   </para>
2695
2696   <para>
2697    Recursive self-references in data-modifying statements are not
2698    allowed.  In some cases it is possible to work around this limitation by
2699    referring to the output of a recursive <literal>WITH</literal>, for example:
2700
2701<programlisting>
2702WITH RECURSIVE included_parts(sub_part, part) AS (
2703    SELECT sub_part, part FROM parts WHERE part = 'our_product'
2704  UNION ALL
2705    SELECT p.sub_part, p.part
2706    FROM included_parts pr, parts p
2707    WHERE p.part = pr.sub_part
2708)
2709DELETE FROM parts
2710  WHERE part IN (SELECT part FROM included_parts);
2711</programlisting>
2712
2713    This query would remove all direct and indirect subparts of a product.
2714   </para>
2715
2716   <para>
2717    Data-modifying statements in <literal>WITH</literal> are executed exactly once,
2718    and always to completion, independently of whether the primary query
2719    reads all (or indeed any) of their output.  Notice that this is different
2720    from the rule for <command>SELECT</command> in <literal>WITH</literal>: as stated in the
2721    previous section, execution of a <command>SELECT</command> is carried only as far
2722    as the primary query demands its output.
2723   </para>
2724
2725   <para>
2726    The sub-statements in <literal>WITH</literal> are executed concurrently with
2727    each other and with the main query.  Therefore, when using data-modifying
2728    statements in <literal>WITH</literal>, the order in which the specified updates
2729    actually happen is unpredictable.  All the statements are executed with
2730    the same <firstterm>snapshot</firstterm> (see <xref linkend="mvcc"/>), so they
2731    cannot <quote>see</quote> one another's effects on the target tables.  This
2732    alleviates the effects of the unpredictability of the actual order of row
2733    updates, and means that <literal>RETURNING</literal> data is the only way to
2734    communicate changes between different <literal>WITH</literal> sub-statements and
2735    the main query.  An example of this is that in
2736
2737<programlisting>
2738WITH t AS (
2739    UPDATE products SET price = price * 1.05
2740    RETURNING *
2741)
2742SELECT * FROM products;
2743</programlisting>
2744
2745    the outer <command>SELECT</command> would return the original prices before the
2746    action of the <command>UPDATE</command>, while in
2747
2748<programlisting>
2749WITH t AS (
2750    UPDATE products SET price = price * 1.05
2751    RETURNING *
2752)
2753SELECT * FROM t;
2754</programlisting>
2755
2756    the outer <command>SELECT</command> would return the updated data.
2757   </para>
2758
2759   <para>
2760    Trying to update the same row twice in a single statement is not
2761    supported.  Only one of the modifications takes place, but it is not easy
2762    (and sometimes not possible) to reliably predict which one.  This also
2763    applies to deleting a row that was already updated in the same statement:
2764    only the update is performed.  Therefore you should generally avoid trying
2765    to modify a single row twice in a single statement.  In particular avoid
2766    writing <literal>WITH</literal> sub-statements that could affect the same rows
2767    changed by the main statement or a sibling sub-statement.  The effects
2768    of such a statement will not be predictable.
2769   </para>
2770
2771   <para>
2772    At present, any table used as the target of a data-modifying statement in
2773    <literal>WITH</literal> must not have a conditional rule, nor an <literal>ALSO</literal>
2774    rule, nor an <literal>INSTEAD</literal> rule that expands to multiple statements.
2775   </para>

2782  <title>Graph Queries</title>
2783
2784  <para>
2785   This section describes the sublanguage for querying property graphs,
2786   defined as described in <xref linkend="ddl-property-graphs"/>.
2787  </para>
2788
2789  <sect2 id="queries-graph-overview">
2790   <title>Overview</title>
2791
2792   <para>
2793    Consider this example from <xref linkend="ddl-property-graphs"/>:
2794<programlisting>
2795-- get list of customers active today
2796SELECT customer_name FROM GRAPH_TABLE (myshop MATCH (c IS customers)-[IS customer_orders]->(o IS orders WHERE o.ordered_when = current_date) COLUMNS (c.name AS customer_name));
2797</programlisting>
2798    The graph query part happens inside the <literal>GRAPH_TABLE</literal>
2799    construct.  As far as the rest of the query is concerned, this acts like a
2800    table function in that it produces a computed table as output.  Like other
2801    <literal>FROM</literal> clause elements, table alias and column alias
2802    names can be assigned to the result, and the result can be joined with
2803    other tables, subsequently filtered, and so on, for example:
2804<programlisting>
2805SELECT ... FROM GRAPH_TABLE (mygraph MATCH ... COLUMNS (...)) AS myresult (a, b, c) JOIN othertable USING (a) WHERE b > 0 ORDER BY c;
2806</programlisting>
2807   </para>
2808
2809   <para>
2810    The <literal>GRAPH_TABLE</literal> clause consists of the graph name,
2811    followed by the keyword <literal>MATCH</literal>, followed by a graph
2812    pattern expression (see below), followed by the keyword
2813    <literal>COLUMNS</literal> and a column list.
2814   </para>
2815  </sect2>
2816
2817  <sect2 id="queries-graph-patterns">
2818   <title>Graph Patterns</title>
2819
2820   <para>
2821    The core of the graph querying functionality is the graph pattern, which
2822    appears after the keyword <literal>MATCH</literal>.  Formally, a graph
2823    pattern consists of one or more path patterns.  A path is a sequence of
2824    graph elements, starting and ending with a vertex and alternating between
2825    vertices and edges.  A path pattern is a syntactic expressions that
2826    matches paths.
2827   </para>
2828
2829   <para>
2830    A path pattern thus matches a sequence of vertices and edges.  The
2831    simplest possible path pattern is
2832<programlisting>
2833()
2834</programlisting>
2835    which matches a single vertex.  The next simplest pattern would be
2836<programlisting>
2837()-[]->()
2838</programlisting>
2839    which matches a vertex followed by an edge followed by a vertex.  The
2840    characters <literal>()</literal> are a vertex pattern and the characters
2841    <literal>-[]-></literal> are an edge pattern.
2842   </para>
2843
2844   <para>
2845    These characters can also be separated by whitespace, for example:
2846<programlisting>
2847( ) - [ ] - > ( )
2848</programlisting>
2849   </para>
2850
2851   <tip>
2852    <para>
2853     A way to remember these symbols is that in visual representations of
2854     property graphs, vertices are usually circles (like
2855     <literal>()</literal>) and edges have rectangular labels (like
2856     <literal>[]</literal>).
2857    </para>
2858   </tip>
2859
2860   <para>
2861    The above patterns would match any vertex, or any two vertices connected
2862    by any edge, which isn't very interesting.  Normally, we want to search
2863    for elements (vertices and edges) that have certain characteristics.
2864    These characteristics are written in between the parentheses or brackets.
2865    (This is also called an element pattern filler.)  Typically, we would
2866    search for elements with a certain label.  This is written by <literal>IS
2867    <replaceable>labelname</replaceable></literal>.  For example, this would
2868    match all vertices with the label <literal>person</literal>:
2869<programlisting>
2870(IS person)
2871</programlisting>
2872    The next
2873    example would match a vertex with the label <literal>person</literal>
2874    connected to a vertex with the label <literal>account</literal> connected
2875    by an edge with the label <literal>has</literal>.
2876<programlisting>
2877(IS person)-[IS has]->(IS account)
2878</programlisting>
2879    Multiple labels can also be matched, using <quote>or</quote> semantics:
2880<programlisting>
2881(IS person)-[IS has]->(IS account|creditcard)
2882</programlisting>
2883   </para>
2884
2885   <para>
2886    Recall that edges are directed.  The other direction is also possible in a
2887    path pattern, for example:
2888<programlisting>
2889(IS account)&lt;-[IS has]-(IS person)
2890</programlisting>
2891    It is also possible to match both directions:
2892<programlisting>
2893(IS person)-[IS is_friend_of]-(IS person)
2894</programlisting>
2895    This has a meaning of <quote>or</quote>: An edge in either direction would
2896    match.
2897   </para>
2898
2899   <para>
2900    In many cases, the edge patterns don't need a filler.  (All the filtering
2901    then happens on the vertices.)  For these cases, an abbreviated edge
2902    pattern syntax is available that omits the brackets, for example:
2903<programlisting>
2904(IS person)->(IS account)
2905(IS account)&lt;-(IS person)
2906(IS person)-(IS person)
2907</programlisting>
2908    As is often the case, abbreviated syntax can make expressions more compact
2909    but also sometimes harder to understand.
2910   </para>
2911
2912   <para>
2913    Furthermore, it is possible to define graph pattern variables in the path
2914    pattern expressions.  These are bound to the matched elements and can be
2915    used to refer to the property values from those elements.  The most
2916    important use is to use them in the <literal>COLUMNS</literal> clause to
2917    define the tabular result of the <literal>GRAPH_TABLE</literal> clause.
2918    For example (assuming appropriate definitions of the property graph as
2919    well as the underlying tables):
2920<programlisting>
2921GRAPH_TABLE (mygraph MATCH (p IS person)-[h IS has]->(a IS account)
2922             COLUMNS (p.name AS person_name, h.since AS has_account_since, a.num AS account_number)
2923</programlisting>
2924    <literal>WHERE</literal> clauses can be used inside element patterns to
2925    filter matches:
2926<programlisting>
2927(IS person)-[IS has]->(a IS account WHERE a.type = 'savings')
2928</programlisting>
2929   </para>
