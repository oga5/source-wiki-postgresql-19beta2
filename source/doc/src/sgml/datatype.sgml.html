326  <para>
327   Each data type has an external representation determined by its input
328   and output functions.  Many of the built-in types have
329   obvious external formats.  However, several types are either unique
330   to <productname>PostgreSQL</productname>, such as geometric
331   paths, or have several possible formats, such as the date
332   and time types.
333   Some of the input and output functions are not invertible, i.e.,
334   the result of an output function might lose accuracy when compared to
335   the original input.

477    <para>
478     The types <type>smallint</type>, <type>integer</type>, and
479     <type>bigint</type> store whole numbers, that is, numbers without
480     fractional components, of various ranges.  Attempts to store
481     values outside of the allowed range will result in an error.
482    </para>
483
484    <para>
485     The type <type>integer</type> is the common choice, as it offers
486     the best balance between range, storage size, and performance.
487     The <type>smallint</type> type is generally only used if disk
488     space is at a premium.  The <type>bigint</type> type is designed to be
489     used when the range of the <type>integer</type> type is insufficient.
490    </para>
491
492    <para>
493     <acronym>SQL</acronym> only specifies the integer types
494     <type>integer</type> (or <type>int</type>),
495     <type>smallint</type>, and <type>bigint</type>.  The
496     type names <type>int2</type>, <type>int4</type>, and
497     <type>int8</type> are extensions, which are also used by some
498     other <acronym>SQL</acronym> database systems.
499    </para>

503   <sect2 id="datatype-numeric-decimal">
504    <title>Arbitrary Precision Numbers</title>
505
506    <indexterm>
507     <primary>numeric (data type)</primary>
508    </indexterm>
509
510   <indexterm>
511    <primary>arbitrary precision numbers</primary>
512   </indexterm>
513
514    <indexterm>
515     <primary>decimal</primary>
516     <see>numeric</see>
517    </indexterm>
518
519    <para>
520     The type <type>numeric</type> can store numbers with a
521     very large number of digits. It is especially recommended for
522     storing monetary amounts and other quantities where exactness is
523     required.  Calculations with <type>numeric</type> values yield exact
524     results where possible, e.g.,  addition, subtraction, multiplication.
525     However, calculations on <type>numeric</type> values are very slow
526     compared to the integer types, or to the floating-point types
527     described in the next section.
528    </para>
529
530    <para>
531     We use the following terms below:  The
532     <firstterm>precision</firstterm> of a <type>numeric</type>
533     is the total count of significant digits in the whole number,
534     that is, the number of digits to both sides of the decimal point.
535     The <firstterm>scale</firstterm> of a <type>numeric</type> is the
536     count of decimal digits in the fractional part, to the right of the
537     decimal point.  So the number 23.5141 has a precision of 6 and a
538     scale of 4.  Integers can be considered to have a scale of zero.
539    </para>
540
541    <para>
542     Both the maximum precision and the maximum scale of a
543     <type>numeric</type> column can be
544     configured.  To declare a column of type <type>numeric</type> use
545     the syntax:
546<programlisting>
547NUMERIC(<replaceable>precision</replaceable>, <replaceable>scale</replaceable>)
548</programlisting>
549     The precision must be positive, while the scale may be positive or
550     negative (see below).  Alternatively:
551<programlisting>
552NUMERIC(<replaceable>precision</replaceable>)
553</programlisting>
554     selects a scale of 0.  Specifying:
555<programlisting>
556NUMERIC
557</programlisting>
558     without any precision or scale creates an <quote>unconstrained
559     numeric</quote> column in which numeric values of any length can be
560     stored, up to the implementation limits.  A column of this kind will
561     not coerce input values to any particular scale, whereas
562     <type>numeric</type> columns with a declared scale will coerce
563     input values to that scale.  (The <acronym>SQL</acronym> standard
564     requires a default scale of 0, i.e., coercion to integer
565     precision.  We find this a bit useless.  If you're concerned
566     about portability, always specify the precision and scale
567     explicitly.)
568    </para>
569
570    <note>
571     <para>
572      The maximum precision that can be explicitly specified in
573      a <type>numeric</type> type declaration is 1000.  An
574      unconstrained <type>numeric</type> column is subject to the limits
575      described in <xref linkend="datatype-numeric-table"/>.
576     </para>
577    </note>
578
579    <para>
580     If the scale of a value to be stored is greater than the declared
581     scale of the column, the system will round the value to the specified
582     number of fractional digits.  Then, if the number of digits to the
583     left of the decimal point exceeds the declared precision minus the
584     declared scale, an error is raised.
585     For example, a column declared as
586<programlisting>
587NUMERIC(3, 1)
588</programlisting>
589     will round values to 1 decimal place and can store values between
590     -99.9 and 99.9, inclusive.
591    </para>
592
593    <para>
594     Beginning in <productname>PostgreSQL</productname> 15, it is allowed
595     to declare a <type>numeric</type> column with a negative scale.  Then
596     values will be rounded to the left of the decimal point.  The
597     precision still represents the maximum number of non-rounded digits.
598     Thus, a column declared as
599<programlisting>
600NUMERIC(2, -3)
601</programlisting>
602     will round values to the nearest thousand and can store values
603     between -99000 and 99000, inclusive.
604     It is also allowed to declare a scale larger than the declared
605     precision.  Such a column can only hold fractional values, and it
606     requires the number of zero digits just to the right of the decimal
607     point to be at least the declared scale minus the declared precision.
608     For example, a column declared as
609<programlisting>
610NUMERIC(3, 5)
611</programlisting>
612     will round values to 5 decimal places and can store values between
613     -0.00999 and 0.00999, inclusive.
614    </para>
615
616    <note>
617     <para>
618      <productname>PostgreSQL</productname> permits the scale in a
619      <type>numeric</type> type declaration to be any value in the range
620      -1000 to 1000.  However, the <acronym>SQL</acronym> standard requires
621      the scale to be in the range 0 to <replaceable>precision</replaceable>.
622      Using scales outside that range may not be portable to other database
623      systems.
624     </para>
625    </note>
626
627    <para>
628     Numeric values are physically stored without any extra leading or
629     trailing zeroes.  Thus, the declared precision and scale of a column
630     are maximums, not fixed allocations.  (In this sense the <type>numeric</type>
631     type is more akin to <type>varchar(<replaceable>n</replaceable>)</type>
632     than to <type>char(<replaceable>n</replaceable>)</type>.)  The actual storage
633     requirement is two bytes for each group of four decimal digits,
634     plus three to eight bytes overhead.
635    </para>

652    <para>
653     In addition to ordinary numeric values, the <type>numeric</type> type
654     has several special values:
655<literallayout>
656<literal>Infinity</literal>
657<literal>-Infinity</literal>
658<literal>NaN</literal>
659</literallayout>
660     These are adapted from the IEEE 754 standard, and represent
661     <quote>infinity</quote>, <quote>negative infinity</quote>, and
662     <quote>not-a-number</quote>, respectively. When writing these values
663     as constants in an SQL command, you must put quotes around them,
664     for example <literal>UPDATE table SET x = '-Infinity'</literal>.
665     On input, these strings are recognized in a case-insensitive manner.
666     The infinity values can alternatively be spelled <literal>inf</literal>
667     and <literal>-inf</literal>.
668    </para>
669
670    <para>
671     The infinity values behave as per mathematical expectations.  For
672     example, <literal>Infinity</literal> plus any finite value equals
673     <literal>Infinity</literal>, as does <literal>Infinity</literal>
674     plus <literal>Infinity</literal>; but <literal>Infinity</literal>
675     minus <literal>Infinity</literal> yields <literal>NaN</literal> (not a
676     number), because it has no well-defined interpretation.  Note that an
677     infinity can only be stored in an unconstrained <type>numeric</type>
678     column, because it notionally exceeds any finite precision limit.
679    </para>
680
681    <para>
682     The <literal>NaN</literal> (not a number) value is used to represent
683     undefined calculational results.  In general, any operation with
684     a <literal>NaN</literal> input yields another <literal>NaN</literal>.
685     The only exception is when the operation's other inputs are such that
686     the same output would be obtained if the <literal>NaN</literal> were to
687     be replaced by any finite or infinite numeric value; then, that output
688     value is used for <literal>NaN</literal> too.  (An example of this
689     principle is that <literal>NaN</literal> raised to the zero power
690     yields one.)
691    </para>
692
693    <note>
694     <para>

739    <title>Floating-Point Types</title>
740
741    <indexterm zone="datatype-float">
742     <primary>real</primary>
743    </indexterm>
744
745    <indexterm zone="datatype-float">
746     <primary>double precision</primary>
747    </indexterm>

757    </indexterm>

759    <indexterm zone="datatype-float">
760     <primary>floating point</primary>
761    </indexterm>
762
763    <para>
764     The data types <type>real</type> and <type>double precision</type> are
765     inexact, variable-precision numeric types. On all currently supported
766     platforms, these types are implementations of <acronym>IEEE</acronym>
767     Standard 754 for Binary Floating-Point Arithmetic (single and double
768     precision, respectively), to the extent that the underlying processor,
769     operating system, and compiler support it.
770    </para>
771
772    <para>
773     Inexact means that some values cannot be converted exactly to the
774     internal format and are stored as approximations, so that storing
775     and retrieving a value might show slight discrepancies.
776     Managing these errors and how they propagate through calculations
777     is the subject of an entire branch of mathematics and computer
778     science and will not be discussed here, except for the
779     following points:
780     <itemizedlist>
781      <listitem>
782       <para>
783        If you require exact storage and calculations (such as for
784        monetary amounts), use the <type>numeric</type> type instead.
785       </para>
786      </listitem>
787
788      <listitem>
789       <para>
790        If you want to do complicated calculations with these types
791        for anything important, especially if you rely on certain
792        behavior in boundary cases (infinity, underflow), you should
793        evaluate the implementation carefully.
794       </para>
795      </listitem>
796
797      <listitem>
798       <para>
799        Comparing two floating-point values for equality might not
800        always work as expected.
801       </para>
802      </listitem>
803     </itemizedlist>
804    </para>
805
806    <para>
807     On all currently supported platforms, the <type>real</type> type has a
808     range of around 1E-37 to 1E+37 with a precision of at least 6 decimal
809     digits. The <type>double precision</type> type has a range of around
810     1E-307 to 1E+308 with a precision of at least 15 digits. Values that are
811     too large or too small will cause an error. Rounding might take place if
812     the precision of an input number is too high. Numbers too close to zero
813     that are not representable as distinct from zero will cause an underflow
814     error.
815    </para>
816
817    <para>
818     By default, floating point values are output in text form in their
819     shortest precise decimal representation; the decimal value produced is
820     closer to the true stored binary value than to any other value
821     representable in the same binary precision. (However, the output value is
822     currently never <emphasis>exactly</emphasis> midway between two
823     representable values, in order to avoid a widespread bug where input
824     routines do not properly respect the round-to-nearest-even rule.) This value will
825     use at most 17 significant decimal digits for <type>float8</type>
826     values, and at most 9 digits for <type>float4</type> values.
827    </para>
828
829    <note>
830     <para>
831      This shortest-precise output format is much faster to generate than the
832      historical rounded format.
833     </para>
834    </note>
835
836    <para>
837     For compatibility with output generated by older versions
838     of <productname>PostgreSQL</productname>, and to allow the output
839     precision to be reduced, the <xref linkend="guc-extra-float-digits"/>
840     parameter can be used to select rounded decimal output instead. Setting a
841     value of 0 restores the previous default of rounding the value to 6
842     (for <type>float4</type>) or 15 (for <type>float8</type>)
843     significant decimal digits. Setting a negative value reduces the number
844     of digits further; for example -2 would round output to 4 or 13 digits
845     respectively.
846    </para>
847
848    <para>
849     Any value of <xref linkend="guc-extra-float-digits"/> greater than 0
850     selects the shortest-precise format.
851    </para>
852
853    <note>
854     <para>
855      Applications that wanted precise values have historically had to set
856      <xref linkend="guc-extra-float-digits"/> to 3 to obtain them. For
857      maximum compatibility between versions, they should continue to do so.
858     </para>
859    </note>
860
861    <indexterm>
862     <primary>infinity</primary>
863     <secondary>floating point</secondary>
864    </indexterm>
865
866    <indexterm>
867     <primary>not a number</primary>
868     <secondary>floating point</secondary>
869    </indexterm>
870
871    <para>
872     In addition to ordinary numeric values, the floating-point types
873     have several special values:
874<literallayout>
875<literal>Infinity</literal>
876<literal>-Infinity</literal>
877<literal>NaN</literal>
878</literallayout>
879     These represent the IEEE 754 special values
880     <quote>infinity</quote>, <quote>negative infinity</quote>, and
881     <quote>not-a-number</quote>, respectively. When writing these values
882     as constants in an SQL command, you must put quotes around them,
883     for example <literal>UPDATE table SET x = '-Infinity'</literal>.  On input,
884     these strings are recognized in a case-insensitive manner.
885     The infinity values can alternatively be spelled <literal>inf</literal>
886     and <literal>-inf</literal>.
887    </para>
888
889    <note>
890     <para>
891      IEEE 754 specifies that <literal>NaN</literal> should not compare equal
892      to any other floating-point value (including <literal>NaN</literal>).
893      In order to allow floating-point values to be sorted and used
894      in tree-based indexes, <productname>PostgreSQL</productname> treats
895      <literal>NaN</literal> values as equal, and greater than all
896      non-<literal>NaN</literal> values.
897     </para>
898    </note>
899
900    <para>
901     <productname>PostgreSQL</productname> also supports the SQL-standard
902     notations <type>float</type> and
903     <type>float(<replaceable>p</replaceable>)</type> for specifying
904     inexact numeric types.  Here, <replaceable>p</replaceable> specifies
905     the minimum acceptable precision in <emphasis>binary</emphasis> digits.
906     <productname>PostgreSQL</productname> accepts
907     <type>float(1)</type> to <type>float(24)</type> as selecting the
908     <type>real</type> type, while
909     <type>float(25)</type> to <type>float(53)</type> select
910     <type>double precision</type>.  Values of <replaceable>p</replaceable>
911     outside the allowed range draw an error.
912     <type>float</type> with no precision specified is taken to mean
913     <type>double precision</type>.
914    </para>

965     <type>bigserial</type> are not true types, but merely
966     a notational convenience for creating unique identifier columns
967     (similar to the <literal>AUTO_INCREMENT</literal> property
968     supported by some other databases). In the current
969     implementation, specifying:
970
971<programlisting>
972CREATE TABLE <replaceable class="parameter">tablename</replaceable> (
973    <replaceable class="parameter">colname</replaceable> SERIAL
974);
975</programlisting>
976
977     is equivalent to specifying:
978
979<programlisting>
980CREATE SEQUENCE <replaceable class="parameter">tablename</replaceable>_<replaceable class="parameter">colname</replaceable>_seq AS integer;
981CREATE TABLE <replaceable class="parameter">tablename</replaceable> (
982    <replaceable class="parameter">colname</replaceable> integer NOT NULL DEFAULT nextval('<replaceable class="parameter">tablename</replaceable>_<replaceable class="parameter">colname</replaceable>_seq')
983);
984ALTER SEQUENCE <replaceable class="parameter">tablename</replaceable>_<replaceable class="parameter">colname</replaceable>_seq OWNED BY <replaceable class="parameter">tablename</replaceable>.<replaceable class="parameter">colname</replaceable>;
985</programlisting>

988     values to be assigned from a sequence generator.  A <literal>NOT NULL</literal>
989     constraint is applied to ensure that a null value cannot be
990     inserted.  (In most cases you would also want to attach a
991     <literal>UNIQUE</literal> or <literal>PRIMARY KEY</literal> constraint to prevent
992     duplicate values from being inserted by accident, but this is
993     not automatic.)  Lastly, the sequence is marked as <quote>owned by</quote>
994     the column, so that it will be dropped if the column or table is dropped.
995    </para>

998      <para>
999        Because <type>smallserial</type>, <type>serial</type> and
1000        <type>bigserial</type> are implemented using sequences, there may
1001        be "holes" or gaps in the sequence of values which appears in the
1002        column, even if no rows are ever deleted.  A value allocated
1003        from the sequence is still "used up" even if a row containing that
1004        value is never successfully inserted into the table column.  This
1005        may happen, for example, if the inserting transaction rolls back.
1006        See <literal>nextval()</literal> in <xref linkend="functions-sequence"/>
1007        for details.
1008      </para>
1009    </note>

1015     either by excluding the column from the list of columns in
1016     the <command>INSERT</command> statement, or through the use of
1017     the <literal>DEFAULT</literal> key word.

1024     the same way, except that they create a <type>bigint</type>

1026     the use of more than 2<superscript>31</superscript> identifiers over the

1029     create a <type>smallint</type> column.

1036     will force removal of the column default expression.

1291    maximum value that will be allowed for <replaceable>n</replaceable> in the data
1292    type declaration is less than that. It wouldn't be useful to
1293    change this because with multibyte character encodings the number of
1294    characters and bytes can be quite different. If you desire to
1295    store long strings with no specific upper limit, use
1296    <type>text</type> or <type>character varying</type> without a length
1297    specifier, rather than making up an arbitrary length limit.)
1298   </para>

1300   <tip>
1301    <para>

1303     apart from increased storage space when using the blank-padded
1304     type, and a few extra CPU cycles to check the length when storing into
1305     a length-constrained column.  While
1306     <type>character(<replaceable>n</replaceable>)</type> has performance
1307     advantages in some other database systems, there is no such advantage in
1308     <productname>PostgreSQL</productname>; in fact
1309     <type>character(<replaceable>n</replaceable>)</type> is usually the slowest of
1310     the three because of its additional storage costs.  In most situations
1311     <type>text</type> or <type>character varying</type> should be used
1312     instead.
1313    </para>
1314   </tip>

1318    the syntax of string literals, and to <xref linkend="functions"/>

1320   </para>

1445   <para>
1446    A binary string is a sequence of octets (or bytes).  Binary
1447    strings are distinguished from character strings in two
1448    ways.  First, binary strings specifically allow storing
1449    octets of value zero and other <quote>non-printable</quote>
1450    octets (usually, octets outside the decimal range 32 to 126).
1451    Character strings disallow zero octets, and also disallow any
1452    other octet values and sequences of octet values that are invalid
1453    according to the database's selected character set encoding.
1454    Second, operations on binary strings process the actual bytes,
1455    whereas the processing of character strings depends on locale settings.
1456    In short, binary strings are appropriate for storing data that the
1457    programmer thinks of as <quote>raw bytes</quote>, whereas character
1458    strings are appropriate for storing text.
1459   </para>
1460
1461   <para>
1462    The <type>bytea</type> type supports two
1463    formats for input and output: <quote>hex</quote> format
1464    and <productname>PostgreSQL</productname>'s historical
1465    <quote>escape</quote> format.  Both
1466    of these are always accepted on input.  The output format depends
1467    on the configuration parameter <xref linkend="guc-bytea-output"/>;
1468    the default is hex.  (Note that the hex format was introduced in
1469    <productname>PostgreSQL</productname> 9.0; earlier versions and some
1470    tools don't understand it.)
1471   </para>
1472
1473   <para>
1474    The <acronym>SQL</acronym> standard defines a different binary
1475    string type, called <type>BLOB</type> or <type>BINARY LARGE
1476    OBJECT</type>.  The input format is different from
1477    <type>bytea</type>, but the provided functions and operators are
1478    mostly the same.
1479   </para>

1481  <sect2 id="datatype-binary-bytea-hex-format">
1482   <title><type>bytea</type> Hex Format</title>
1483
1484   <para>
1485    The <quote>hex</quote> format encodes binary data as 2 hexadecimal digits
1486    per byte, most significant nibble first.  The entire string is
1487    preceded by the sequence <literal>\x</literal> (to distinguish it
1488    from the escape format).  In some contexts, the initial backslash may
1489    need to be escaped by doubling it
1490    (see <xref linkend="sql-syntax-strings"/>).
1491    For input, the hexadecimal digits can
1492    be either upper or lower case, and whitespace is permitted between
1493    digit pairs (but not within a digit pair nor in the starting
1494    <literal>\x</literal> sequence).
1495    The hex format is compatible with a wide
1496    range of external applications and protocols, and it tends to be
1497    faster to convert than the escape format, so its use is preferred.
1498   </para>
1499
1500   <para>
1501    Example:
1502<programlisting>
1503SET bytea_output = 'hex';
1504
1505SELECT '\xDEADBEEF'::bytea;
1506   bytea
1507------------
1508 \xdeadbeef
1509</programlisting>
1510   </para>
1511  </sect2>

1513  <sect2 id="datatype-binary-bytea-escape-format">
1514   <title><type>bytea</type> Escape Format</title>
1515
1516   <para>
1517    The <quote>escape</quote> format is the traditional
1518    <productname>PostgreSQL</productname> format for the <type>bytea</type>
1519    type.  It
1520    takes the approach of representing a binary string as a sequence
1521    of ASCII characters, while converting those bytes that cannot be
1522    represented as an ASCII character into special escape sequences.
1523    If, from the point of view of the application, representing bytes
1524    as characters makes sense, then this representation can be
1525    convenient.  But in practice it is usually confusing because it
1526    fuzzes up the distinction between binary strings and character
1527    strings, and also the particular escape mechanism that was chosen is
1528    somewhat unwieldy.  Therefore, this format should probably be avoided
1529    for most new applications.
1530   </para>

1538    octal value and precede it by a backslash.

2182    <title>Time Stamps</title>
2183
2184    <indexterm>
2185     <primary>timestamp</primary>
2186    </indexterm>
2187
2188    <indexterm>
2189     <primary>timestamp with time zone</primary>

2193     <primary>timestamp without time zone</primary>
2194    </indexterm>
2195
2196     <para>
2197      Valid input for the time stamp types consists of the concatenation
2198      of a date and a time, followed by an optional time zone,
2199      followed by an optional <literal>AD</literal> or <literal>BC</literal>.
2200      (Alternatively, <literal>AD</literal>/<literal>BC</literal> can appear
2201      before the time zone, but this is not the preferred ordering.)
2202      Thus:
2203
2204<programlisting>
22051999-01-08 04:05:06
2206</programlisting>
2207      and:
2208<programlisting>
22091999-01-08 04:05:06 -8:00
2210</programlisting>
2211
2212      are valid values, which follow the <acronym>ISO</acronym> 8601
2213      standard.  In addition, the common format:
2214<programlisting>
2215January 8 04:05:06 1999 PST
2216</programlisting>
2217      is supported.
2218     </para>
2219
2220     <para>
2221      The <acronym>SQL</acronym> standard differentiates
2222      <type>timestamp without time zone</type>
2223      and <type>timestamp with time zone</type> literals by the presence of a
2224      <quote>+</quote> or <quote>-</quote> symbol and time zone offset after
2225      the time.  Hence, according to the standard,
2226
2227<programlisting>
2228TIMESTAMP '2004-10-19 10:23:54'
2229</programlisting>
2230
2231      is a <type>timestamp without time zone</type>, while
2232
2233<programlisting>
2234TIMESTAMP '2004-10-19 10:23:54+02'
2235</programlisting>
2236
2237      is a <type>timestamp with time zone</type>.
2238      <productname>PostgreSQL</productname> never examines the content of a
2239      literal string before determining its type, and therefore will treat
2240      both of the above as <type>timestamp without time zone</type>.  To
2241      ensure that a literal is treated as <type>timestamp with time
2242      zone</type>, give it the correct explicit type:
2243
2244<programlisting>
2245TIMESTAMP WITH TIME ZONE '2004-10-19 10:23:54+02'
2246</programlisting>
2247     </para>
2248
2249     <para>
2250      In a value that has been determined to be <type>timestamp without time
2251      zone</type>, <productname>PostgreSQL</productname> will silently ignore
2252      any time zone indication.
2253      That is, the resulting value is derived from the date/time
2254      fields in the input string, and is not adjusted for time zone.
2255     </para>
2256
2257     <para>
2258      For <type>timestamp with time zone</type> values, an input string
2259      that includes an explicit time zone will be converted to UTC
2260      (<glossterm linkend="glossary-utc">Universal Coordinated
2261      Time</glossterm>) using the appropriate offset
2262      for that time zone.  If no time zone is stated in the input string,
2263      then it is assumed to be in the time zone indicated by the system's
2264      <xref linkend="guc-timezone"/> parameter, and is converted to UTC using the
2265      offset for the <varname>timezone</varname> zone.
2266      In either case, the value is stored internally as UTC, and the
2267      originally stated or assumed time zone is not retained.
2268     </para>
2269
2270     <para>
2271      When a <type>timestamp with time
2272      zone</type> value is output, it is always converted from UTC to the
2273      current <varname>timezone</varname> zone, and displayed as local time in that
2274      zone.  To see the time in another time zone, either change
2275      <varname>timezone</varname> or use the <literal>AT TIME ZONE</literal> construct
2276      (see <xref linkend="functions-datetime-zoneconvert"/>).
2277     </para>
2278
2279     <para>
2280      Conversions between <type>timestamp without time zone</type> and
2281      <type>timestamp with time zone</type> normally assume that the
2282      <type>timestamp without time zone</type> value should be taken or given
2283      as <varname>timezone</varname> local time.  A different time zone can
2284      be specified for the conversion using <literal>AT TIME ZONE</literal>.
2285     </para>

2526     east of Greenwich.  The offset will be shown
2527     as <replaceable>hh</replaceable> (hours only) if it is an integral
2528     number of hours, else
2529     as <replaceable>hh</replaceable>:<replaceable>mm</replaceable> if it
2530     is an integral number of minutes, else as

2534     adoption of standardized time zones.)

2536     abbreviation if one is in common use in the current zone.  Otherwise
2537     it appears as a signed numeric offset in ISO 8601 basic format
2538     (<replaceable>hh</replaceable> or <replaceable>hhmm</replaceable>).

2540     IANA time zone database entry currently selected by the
2541     <xref linkend="guc-timezone"/> run-time parameter; they are not
2542     affected by the <xref linkend="guc-timezone-abbreviations"/> setting.

2551     client.

2561   <sect2 id="datatype-timezones">
2562    <title>Time Zones</title>
2563
2564    <indexterm zone="datatype-timezones">
2565     <primary>time zone</primary>
2566    </indexterm>
2567
2568   <para>
2569    Time zones, and time-zone conventions, are influenced by
2570    political decisions, not just earth geometry. Time zones around the
2571    world became somewhat standardized during the 1900s,
2572    but continue to be prone to arbitrary changes, particularly with
2573    respect to daylight-savings rules.
2574    <productname>PostgreSQL</productname> uses the widely-used
2575    IANA (Olson) time zone database for information about
2576    historical time zone rules.  For times in the future, the assumption
2577    is that the latest known rules for a given time zone will
2578    continue to be observed indefinitely far into the future.
2579   </para>
2580
2581    <para>
2582     <productname>PostgreSQL</productname> endeavors to be compatible with
2583     the <acronym>SQL</acronym> standard definitions for typical usage.
2584     However, the <acronym>SQL</acronym> standard has an odd mix of date and
2585     time types and capabilities. Two obvious problems are:
2586
2587     <itemizedlist>
2588      <listitem>
2589       <para>
2590        Although the <type>date</type> type
2591        cannot have an associated time zone, the
2592        <type>time</type> type can.
2593        Time zones in the real world have little meaning unless
2594        associated with a date as well as a time,
2595        since the offset can vary through the year with daylight-saving
2596        time boundaries.
2597       </para>
2598      </listitem>
2599
2600      <listitem>
2601       <para>
2602        The default time zone is specified as a constant numeric offset
2603        from <acronym>UTC</acronym>. It is therefore impossible to adapt to
2604        daylight-saving time when doing date/time arithmetic across
2605        <acronym>DST</acronym> boundaries.
2606       </para>
2607      </listitem>
2608
2609     </itemizedlist>
2610    </para>
2611
2612    <para>
2613     To address these difficulties, we recommend using date/time types
2614     that contain both date and time when using time zones. We
2615     do <emphasis>not</emphasis> recommend using the type <type>time with
2616     time zone</type> (though it is supported by
2617     <productname>PostgreSQL</productname> for legacy applications and
2618     for compliance with the <acronym>SQL</acronym> standard).
2619     <productname>PostgreSQL</productname> assumes
2620     your local time zone for any type containing only date or time.
2621    </para>
2622
2623    <para>
2624     All timezone-aware dates and times are stored internally in
2625     <acronym>UTC</acronym>.  They are converted to local time
2626     in the zone specified by the <xref linkend="guc-timezone"/> configuration
2627     parameter before being displayed to the client.
2628    </para>
2629
2630    <para>
2631     <productname>PostgreSQL</productname> allows you to specify time zones in
2632     three different forms:
2633     <itemizedlist>
2634      <listitem>
2635       <para>
2636        A full time zone name, for example <literal>America/New_York</literal>.
2637        The recognized time zone names are listed in the
2638        <literal>pg_timezone_names</literal> view (see <xref
2639        linkend="view-pg-timezone-names"/>).
2640        <productname>PostgreSQL</productname> uses the widely-used IANA
2641        time zone data for this purpose, so the same time zone
2642        names are also recognized by other software.
2643       </para>
2644      </listitem>
2645      <listitem>
2646       <para>
2647        A time zone abbreviation, for example <literal>PST</literal>.  Such a
2648        specification merely defines a particular offset from UTC, in
2649        contrast to full time zone names which can imply a set of daylight
2650        savings transition rules as well.  The recognized abbreviations
2651        are listed in the <literal>pg_timezone_abbrevs</literal> view (see <xref
2652        linkend="view-pg-timezone-abbrevs"/>).  You cannot set the
2653        configuration parameters <xref linkend="guc-timezone"/> or
2654        <xref linkend="guc-log-timezone"/> to a time
2655        zone abbreviation, but you can use abbreviations in
2656        date/time input values and with the <literal>AT TIME ZONE</literal>
2657        operator.
2658       </para>
2659      </listitem>
2660      <listitem>
2661       <para>
2662        In addition to the timezone names and abbreviations,
2663        <productname>PostgreSQL</productname> will accept POSIX-style time zone
2664        specifications, as described in
2665        <xref linkend="datetime-posix-timezone-specs"/>.  This option is not
2666        normally preferable to using a named time zone, but it may be
2667        necessary if no suitable IANA time zone entry is available.
2668       </para>
2669      </listitem>
2670     </itemizedlist>
2671
2672     In short, this is the difference between abbreviations
2673     and full names: abbreviations represent a specific offset from UTC,
2674     whereas many of the full names imply a local daylight-savings time
2675     rule, and so have two possible UTC offsets.  As an example,
2676     <literal>2014-06-04 12:00 America/New_York</literal> represents noon local
2677     time in New York, which for this particular date was Eastern Daylight
2678     Time (UTC-4).  So <literal>2014-06-04 12:00 EDT</literal> specifies that
2679     same time instant.  But <literal>2014-06-04 12:00 EST</literal> specifies
2680     noon Eastern Standard Time (UTC-5), regardless of whether daylight
2681     savings was nominally in effect on that date.
2682    </para>
2683
2684    <note>
2685     <para>
2686      The sign in POSIX-style time zone specifications has the opposite meaning
2687      of the sign in ISO-8601 datetime values.  For example, the POSIX time zone
2688      for <literal>2014-06-04 12:00+04</literal> would be UTC-4.
2689     </para>
2690    </note>
2691
2692    <para>
2693     To complicate matters, some jurisdictions have used the same timezone
2694     abbreviation to mean different UTC offsets at different times; for
2695     example, in Moscow <literal>MSK</literal> has meant UTC+3 in some years and
2696     UTC+4 in others.  <productname>PostgreSQL</productname> interprets such
2697     abbreviations according to whatever they meant (or had most recently
2698     meant) on the specified date; but, as with the <literal>EST</literal> example
2699     above, this is not necessarily the same as local civil time on that date.
2700    </para>
2701
2702    <para>
2703     In all cases, timezone names and abbreviations are recognized
2704     case-insensitively.  (This is a change from <productname>PostgreSQL</productname>
2705     versions prior to 8.2, which were case-sensitive in some contexts but
2706     not others.)
2707    </para>
2708
2709    <para>
2710     Neither timezone names nor abbreviations are hard-wired into the server;
2711     they are obtained from configuration files stored under
2712     <filename>.../share/timezone/</filename> and <filename>.../share/timezonesets/</filename>
2713     of the installation directory
2714     (see <xref linkend="datetime-config-files"/>).
2715    </para>
2716
2717    <para>
2718     The <xref linkend="guc-timezone"/> configuration parameter can
2719     be set in the file <filename>postgresql.conf</filename>, or in any of the
2720     other standard ways described in <xref linkend="runtime-config"/>.
2721     There are also some special ways to set it:
2722
2723     <itemizedlist>
2724      <listitem>
2725       <para>
2726        The <acronym>SQL</acronym> command <command>SET TIME ZONE</command>
2727        sets the time zone for the session.  This is an alternative spelling
2728        of <command>SET TIMEZONE TO</command> with a more SQL-spec-compatible syntax.
2729       </para>
2730      </listitem>
2731
2732      <listitem>
2733       <para>
2734        The <envar>PGTZ</envar> environment variable is used by
2735        <application>libpq</application> clients
2736        to send a <command>SET TIME ZONE</command>
2737        command to the server upon connection.
2738       </para>
2739      </listitem>
2740     </itemizedlist>
2741    </para>

2751     <para>
2752      <type>interval</type> values can be written using the following
2753      verbose syntax:
2754
2755<synopsis>
2756<optional>@</optional> <replaceable>quantity</replaceable> <replaceable>unit</replaceable> <optional><replaceable>quantity</replaceable> <replaceable>unit</replaceable>...</optional> <optional><replaceable>direction</replaceable></optional>
2757</synopsis>
2758
2759     where <replaceable>quantity</replaceable> is a number (possibly signed);
2760     <replaceable>unit</replaceable> is <literal>microsecond</literal>,
2761     <literal>millisecond</literal>, <literal>second</literal>,
2762     <literal>minute</literal>, <literal>hour</literal>, <literal>day</literal>,
2763     <literal>week</literal>, <literal>month</literal>, <literal>year</literal>,
2764     <literal>decade</literal>, <literal>century</literal>, <literal>millennium</literal>,
2765     or abbreviations or plurals of these units;
2766     <replaceable>direction</replaceable> can be <literal>ago</literal> or
2767     empty.  The at sign (<literal>@</literal>) is optional noise.  The amounts
2768     of the different units are implicitly added with appropriate
2769     sign accounting.  <literal>ago</literal> negates all the fields.
2770     This syntax is also used for interval output, if
2771     <xref linkend="guc-intervalstyle"/> is set to
2772     <literal>postgres_verbose</literal>.
2773    </para>
2774
2775    <para>
2776     Quantities of days, hours, minutes, and seconds can be specified without
2777     explicit unit markings.  For example, <literal>'1 12:59:10'</literal> is read
2778     the same as <literal>'1 day 12 hours 59 min 10 sec'</literal>.  Also,
2779     a combination of years and months can be specified with a dash;
2780     for example <literal>'200-10'</literal> is read the same as <literal>'200 years
2781     10 months'</literal>.  (These shorter forms are in fact the only ones allowed
2782     by the <acronym>SQL</acronym> standard, and are used for output when
2783     <varname>IntervalStyle</varname> is set to <literal>sql_standard</literal>.)
2784    </para>
2785
2786    <para>
2787     Interval values can also be written as ISO 8601 time intervals, using
2788     either the <quote>format with designators</quote> of the standard's section
2789     4.4.3.2 or the <quote>alternative format</quote> of section 4.4.3.3.  The
2790     format with designators looks like this:

2856    <para>
2857     When writing an interval constant with a <replaceable>fields</replaceable>

2859     defined with a <replaceable>fields</replaceable> specification, the interpretation of
2860     unmarked quantities depends on the <replaceable>fields</replaceable>.  For
2861     example <literal>INTERVAL '1' YEAR</literal> is read as 1 year, whereas
2862     <literal>INTERVAL '1'</literal> means 1 second.  Also, field values
2863     <quote>to the right</quote> of the least significant field allowed by the
2864     <replaceable>fields</replaceable> specification are silently discarded.  For
2865     example, writing <literal>INTERVAL '1 day 2:03:04' HOUR TO MINUTE</literal>
2866     results in dropping the seconds field, but not the day field.
2867    </para>

2869    <para>
2870     According to the <acronym>SQL</acronym> standard all fields of an interval
2871     value must have the same sign, so a leading negative sign applies to all
2872     fields; for example the negative sign in the interval literal
2873     <literal>'-1 2:03:04'</literal> applies to both the days and hour/minute/second
2874     parts.  <productname>PostgreSQL</productname> allows the fields to have different
2875     signs, and traditionally treats each field in the textual representation
2876     as independently signed, so that the hour/minute/second part is
2877     considered positive in this example.  If <varname>IntervalStyle</varname> is
2878     set to <literal>sql_standard</literal> then a leading sign is considered
2879     to apply to all fields (but only if no additional signs appear).
2880     Otherwise the traditional <productname>PostgreSQL</productname> interpretation is
2881     used.  To avoid ambiguity, it's recommended to attach an explicit sign
2882     to each field if any field is negative.
2883    </para>

2885    <para>
2886     Internally, <type>interval</type> values are stored as three integral
2887     fields: months, days, and microseconds.  These fields are kept
2888     separate because the number of days in a month varies, while a day
2889     can have 23 or 25 hours if a daylight savings time transition is
2890     involved.  An interval input string that uses other units is
2891     normalized into this format, and then reconstructed in a standardized
2892     way for output, for example:
2893
2894<programlisting>
2895SELECT '2 years 15 months 100 weeks 99 hours 123456789 milliseconds'::interval;
2896               interval
2897---------------------------------------
2898 3 years 3 mons 700 days 133:17:36.789
2899</programlisting>

2902     kept separate, while the smaller and larger time units were
2903     combined and normalized.
2904    </para>

2908     weeks'</literal> or <literal>'01:02:03.45'</literal>.  However,

2910     fractional values must be converted into smaller
2911     units.  Fractional parts of units greater than months are rounded to
2912     be an integer number of months, e.g. <literal>'1.5 years'</literal>
2913     becomes <literal>'1 year 6 mons'</literal>.  Fractional parts of
2914     weeks and days are computed to be an integer number of days and
2915     microseconds, assuming 30 days per month and 24 hours per day, e.g.,
2916     <literal>'1.75 months'</literal> becomes <literal>1 mon 22 days
2917     12:00:00</literal>.  Only seconds will ever be shown as fractional
2918     on output.

3116   <para>

3120   </para>

3140    Leading or trailing whitespace is ignored, and case does not matter.
3141   </para>
3142
3143   <para>
3144    The datatype output function for type <type>boolean</type> always emits
3145    either <literal>t</literal> or <literal>f</literal>, as shown in

3153CREATE TABLE test1 (a boolean, b text);

3160 f | non est
3161

3164---+---------

3171    the preferred (<acronym>SQL</acronym>-compliant) method for writing
3172    Boolean constants in SQL queries.  But you can also use the string
3173    representations by following the generic string-literal constant syntax
3174    described in <xref linkend="sql-syntax-constants-generic"/>, for
3175    example <literal>'yes'::boolean</literal>.
3176   </para>

3203   <para>
3204    Enumerated (enum) types are data types that
3205    comprise a static, ordered set of values.
3206    They are equivalent to the <type>enum</type>
3207    types supported in a number of programming languages. An example of an enum

3212   <sect2 id="datatype-enum-declaration">
3213    <title>Declaration of Enumerated Types</title>
3214
3215    <para>
3216     Enum types are created using the <xref
3217     linkend="sql-createtype"/> command,
3218     for example:
3219
3220<programlisting>
3221CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy');
3222</programlisting>
3223
3224     Once created, the enum type can be used in table and function
3225     definitions much like any other type:
3226<programlisting>
3227CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy');
3228CREATE TABLE person (
3229    name text,
3230    current_mood mood
3231);
3232INSERT INTO person VALUES ('Moe', 'happy');
3233SELECT * FROM person WHERE current_mood = 'happy';
3234 name | current_mood
3235------+--------------
3236 Moe  | happy
3237(1 row)
3238</programlisting>
3239    </para>
3240    </sect2>

3242    <sect2 id="datatype-enum-ordering">
3243     <title>Ordering</title>
3244
3245     <para>
3246      The ordering of the values in an enum type is the
3247      order in which the values were listed when the type was created.
3248      All standard comparison operators and related
3249      aggregate functions are supported for enums.  For example:
3250
3251<programlisting>
3252INSERT INTO person VALUES ('Larry', 'sad');
3253INSERT INTO person VALUES ('Curly', 'ok');
3254SELECT * FROM person WHERE current_mood > 'sad';
3255 name  | current_mood
3256-------+--------------
3257 Moe   | happy
3258 Curly | ok
3259(2 rows)
3260
3261SELECT * FROM person WHERE current_mood > 'sad' ORDER BY current_mood;
3262 name  | current_mood
3263-------+--------------
3264 Curly | ok
3265 Moe   | happy
3266(2 rows)
3267
3268SELECT name
3269FROM person
3270WHERE current_mood = (SELECT MIN(current_mood) FROM person);
3271 name
3272-------
3273 Larry
3274(1 row)
3275</programlisting>
3276     </para>
3277   </sect2>

3279   <sect2 id="datatype-enum-type-safety">
3280    <title>Type Safety</title>
3281
3282    <para>
3283     Each enumerated data type is separate and cannot
3284     be compared with other enumerated types.  See this example:
3285
3286<programlisting>
3287CREATE TYPE happiness AS ENUM ('happy', 'very happy', 'ecstatic');
3288CREATE TABLE holidays (
3289    num_weeks integer,
3290    happiness happiness
3291);
3292INSERT INTO holidays(num_weeks,happiness) VALUES (4, 'happy');
3293INSERT INTO holidays(num_weeks,happiness) VALUES (6, 'very happy');
3294INSERT INTO holidays(num_weeks,happiness) VALUES (8, 'ecstatic');
3295INSERT INTO holidays(num_weeks,happiness) VALUES (2, 'sad');
3296ERROR:  invalid input value for enum happiness: "sad"
3297SELECT person.name, holidays.num_weeks FROM person, holidays
3298  WHERE person.current_mood = holidays.happiness;
3299ERROR:  operator does not exist: mood = happiness
3300</programlisting>
3301    </para>
3302
3303    <para>
3304     If you really need to do something like that, you can either
3305     write a custom operator or add explicit casts to your query:
3306
3307<programlisting>
3308SELECT person.name, holidays.num_weeks FROM person, holidays
3309  WHERE person.current_mood::text = holidays.happiness::text;
3310 name | num_weeks
3311------+-----------
3312 Moe  |         4
3313(1 row)

3315</programlisting>

3319   <sect2 id="datatype-enum-implementation-details">
3320    <title>Implementation Details</title>
3321
3322    <para>
3323     Enum labels are case sensitive, so
3324     <type>'happy'</type> is not the same as <type>'HAPPY'</type>.
3325     White space in the labels is significant too.
3326    </para>
3327
3328    <para>
3329     Although enum types are primarily intended for static sets of values,
3330     there is support for adding new values to an existing enum type, and for
3331     renaming values (see <xref linkend="sql-altertype"/>).  Existing values
3332     cannot be removed from an enum type, nor can the sort ordering of such
3333     values be changed, short of dropping and re-creating the enum type.
3334    </para>

3338     value's textual label is limited by the <symbol>NAMEDATALEN</symbol>

3340     builds this means at most 63 bytes.
3341    </para>
3342
3343    <para>
3344     The translations from internal enum values to textual labels are
3345     kept in the system catalog
3346     <link linkend="catalog-pg-enum"><structname>pg_enum</structname></link>.
3347     Querying this catalog directly can be useful.
3348    </para>

3758    <title><type>inet</type></title>
3759
3760    <indexterm>
3761     <primary>inet (data type)</primary>
3762    </indexterm>
3763
3764    <para>
3765     The <type>inet</type> type holds an IPv4 or IPv6 host address, and
3766     optionally its subnet, all in one field.
3767     The subnet is represented by the number of network address bits
3768     present in the host address (the
3769     <quote>netmask</quote>).  If the netmask is 32 and the address is IPv4,
3770     then the value does not indicate a subnet, only a single host.
3771     In IPv6, the address length is 128 bits, so 128 bits specify a
3772     unique host address.  Note that if you
3773     want to accept only networks, you should use the
3774     <type>cidr</type> type rather than <type>inet</type>.
3775    </para>
3776
3777    <para>
3778      The input format for this type is
3779      <replaceable class="parameter">address/y</replaceable>
3780      where
3781      <replaceable class="parameter">address</replaceable>
3782      is an IPv4 or IPv6 address and
3783      <replaceable class="parameter">y</replaceable>
3784      is the number of bits in the netmask.  If the
3785      <replaceable class="parameter">/y</replaceable>
3786      portion is omitted, the
3787      netmask is taken to be 32 for IPv4 or 128 for IPv6,
3788      so the value represents
3789      just a single host.  On display, the
3790      <replaceable class="parameter">/y</replaceable>
3791      portion is suppressed if the netmask specifies a single host.
3792    </para>

3940    <title><type>macaddr</type></title>
3941
3942    <indexterm>
3943     <primary>macaddr (data type)</primary>
3944    </indexterm>
3945
3946    <indexterm>
3947     <primary>MAC address</primary>
3948     <see>macaddr</see>
3949    </indexterm>
3950
3951    <para>
3952     The <type>macaddr</type> type stores MAC addresses, known for example
3953     from Ethernet card hardware addresses (although MAC addresses are
3954     used for other purposes as well).  Input is accepted in the
3955     following formats:
3956
3957     <simplelist>
3958      <member><literal>'08:00:2b:01:02:03'</literal></member>
3959      <member><literal>'08-00-2b-01-02-03'</literal></member>
3960      <member><literal>'08002b:010203'</literal></member>
3961      <member><literal>'08002b-010203'</literal></member>
3962      <member><literal>'0800.2b01.0203'</literal></member>
3963      <member><literal>'0800-2b01-0203'</literal></member>
3964      <member><literal>'08002b010203'</literal></member>
3965     </simplelist>
3966
3967     These examples all specify the same address.  Upper and
3968     lower case is accepted for the digits
3969     <literal>a</literal> through <literal>f</literal>.  Output is always in the
3970     first of the forms shown.
3971    </para>
3972
3973    <para>
3974     IEEE Standard 802-2001 specifies the second form shown (with hyphens)
3975     as the canonical form for MAC addresses, and specifies the first
3976     form (with colons) as used with bit-reversed, MSB-first notation, so that
3977     08-00-2b-01-02-03 = 10:00:D4:80:40:C0.  This convention is widely
3978     ignored nowadays, and it is relevant only for obsolete network
3979     protocols (such as Token Ring).  PostgreSQL makes no provisions
3980     for bit reversal; all accepted formats use the canonical LSB
3981     order.
3982    </para>
3983
3984    <para>
3985     The remaining five input formats are not part of any standard.
3986    </para>

3989   <sect2 id="datatype-macaddr8">
3990    <title><type>macaddr8</type></title>
3991
3992    <indexterm>
3993     <primary>macaddr8 (data type)</primary>
3994    </indexterm>
3995
3996    <indexterm>
3997     <primary>MAC address (EUI-64 format)</primary>
3998     <see>macaddr</see>
3999    </indexterm>
4000
4001    <para>
4002     The <type>macaddr8</type> type stores MAC addresses in EUI-64
4003     format, known for example from Ethernet card hardware addresses
4004     (although MAC addresses are used for other purposes as well).
4005     This type can accept both 6 and 8 byte length MAC addresses
4006     and stores them in 8 byte length format.  MAC addresses given
4007     in 6 byte format will be stored in 8 byte length format with the
4008     4th and 5th bytes set to FF and FE, respectively.
4009
4010     Note that IPv6 uses a modified EUI-64 format where the 7th bit
4011     should be set to one after the conversion from EUI-48.  The
4012     function <function>macaddr8_set7bit</function> is provided to make this
4013     change.
4014
4015     Generally speaking, any input which is comprised of pairs of hex
4016     digits (on byte boundaries), optionally separated consistently by
4017     one of <literal>':'</literal>, <literal>'-'</literal> or <literal>'.'</literal>, is
4018     accepted.  The number of hex digits must be either 16 (8 bytes) or
4019     12 (6 bytes).  Leading and trailing whitespace is ignored.
4020
4021     The following are examples of input formats that are accepted:
4022
4023     <simplelist>
4024      <member><literal>'08:00:2b:01:02:03:04:05'</literal></member>
4025      <member><literal>'08-00-2b-01-02-03-04-05'</literal></member>
4026      <member><literal>'08002b:0102030405'</literal></member>
4027      <member><literal>'08002b-0102030405'</literal></member>
4028      <member><literal>'0800.2b01.0203.0405'</literal></member>
4029      <member><literal>'0800-2b01-0203-0405'</literal></member>
4030      <member><literal>'08002b01:02030405'</literal></member>
4031      <member><literal>'08002b0102030405'</literal></member>
4032     </simplelist>
4033
4034     These examples all specify the same address.  Upper and
4035     lower case is accepted for the digits
4036     <literal>a</literal> through <literal>f</literal>.  Output is always in the
4037     first of the forms shown.
4038    </para>
4039
4040    <para>
4041     The last six input formats shown above are not part of any standard.
4042    </para>
4043
4044    <para>
4045     To convert a traditional 48 bit MAC address in EUI-48 format to
4046     modified EUI-64 format to be included as the host portion of an
4047     IPv6 address, use <function>macaddr8_set7bit</function> as shown:
4048
4049<programlisting>
4050SELECT macaddr8_set7bit('08:00:2b:01:02:03');
4051<computeroutput>

4053-------------------------
4054 0a:00:2b:ff:fe:01:02:03
4055(1 row)

4066   <title>Bit String Types</title>
4067
4068   <indexterm zone="datatype-bit">
4069    <primary>bit string</primary>
4070    <secondary>data type</secondary>
4071   </indexterm>
4072
4073   <para>
4074    Bit strings are strings of 1's and 0's.  They can be used to store
4075    or visualize bit masks.  There are two SQL bit types:
4076    <type>bit(<replaceable>n</replaceable>)</type> and <type>bit
4077    varying(<replaceable>n</replaceable>)</type>, where
4078    <replaceable>n</replaceable> is a positive integer.
4079   </para>
4080
4081   <para>
4082    <type>bit</type> type data must match the length
4083    <replaceable>n</replaceable> exactly; it is an error to attempt to
4084    store shorter or longer bit strings.  <type>bit varying</type> data is
4085    of variable length up to the maximum length
4086    <replaceable>n</replaceable>; longer strings will be rejected.
4087    Writing <type>bit</type> without a length is equivalent to
4088    <literal>bit(1)</literal>, while <type>bit varying</type> without a length
4089    specification means unlimited length.
4090   </para>
4091
4092   <note>
4093    <para>
4094     If one explicitly casts a bit-string value to
4095     <type>bit(<replaceable>n</replaceable>)</type>, it will be truncated or
4096     zero-padded on the right to be exactly <replaceable>n</replaceable> bits,
4097     without raising an error.  Similarly,
4098     if one explicitly casts a bit-string value to
4099     <type>bit varying(<replaceable>n</replaceable>)</type>, it will be truncated
4100     on the right if it is more than <replaceable>n</replaceable> bits.
4101    </para>
4102   </note>
4103
4104   <para>
4105    Refer to <xref
4106    linkend="sql-syntax-bit-strings"/> for information about the syntax
4107    of bit string constants.  Bit-logical operators and string
4108    manipulation functions are available; see <xref
4109    linkend="functions-bitstring"/>.
4110   </para>
4111
4112   <example>
4113    <title>Using the Bit String Types</title>
4114
4115<programlisting>
4116CREATE TABLE test (a BIT(3), b BIT VARYING(5));
4117INSERT INTO test VALUES (B'101', B'00');
4118INSERT INTO test VALUES (B'10', B'101');
4119<computeroutput>
4120ERROR:  bit string length 2 does not match type bit(3)
4121</computeroutput>
4122INSERT INTO test VALUES (B'10'::bit(3), B'101');
4123SELECT * FROM test;
4124<computeroutput>
4125  a  |  b
4126-----+-----
4127 101 | 00
4128 100 | 101
4129</computeroutput>
4130</programlisting>
4131   </example>
4132
4133   <para>
4134    A bit string value requires 1 byte for each group of 8 bits, plus
4135    5 or 8 bytes overhead depending on the length of the string
4136    (but long values may be compressed or moved out-of-line, as explained
4137    in <xref linkend="datatype-character"/> for character strings).
4138   </para>

4142   <title>Text Search Types</title>
4143
4144   <indexterm zone="datatype-textsearch">
4145    <primary>full text search</primary>

4147   </indexterm>
4148
4149   <indexterm zone="datatype-textsearch">
4150    <primary>text search</primary>
4151    <secondary>data types</secondary>
4152   </indexterm>
4153
4154   <para>
4155    <productname>PostgreSQL</productname> provides two data types that
4156    are designed to support full text search, which is the activity of
4157    searching through a collection of natural-language <firstterm>documents</firstterm>
4158    to locate those that best match a <firstterm>query</firstterm>.
4159    The <type>tsvector</type> type represents a document in a form optimized
4160    for text search; the <type>tsquery</type> type similarly represents
4161    a text query.
4162    <xref linkend="textsearch"/> provides a detailed explanation of this
4163    facility, and <xref linkend="functions-textsearch"/> summarizes the
4164    related functions and operators.
4165   </para>
4166
4167   <sect2 id="datatype-tsvector">
4168    <title><type>tsvector</type></title>
4169
4170    <indexterm>
4171     <primary>tsvector (data type)</primary>
4172    </indexterm>
4173
4174    <para>
4175     A <type>tsvector</type> value is a sorted list of distinct
4176     <firstterm>lexemes</firstterm>, which are words that have been
4177     <firstterm>normalized</firstterm> to merge different variants of the same word
4178     (see <xref linkend="textsearch"/> for details).  Sorting and
4179     duplicate-elimination are done automatically during input, as shown in
4180     this example:
4181
4182<programlisting>
4183SELECT 'a fat cat sat on a mat and ate a fat rat'::tsvector;
4184                      tsvector
4185----------------------------------------------------
4186 'a' 'and' 'ate' 'cat' 'fat' 'mat' 'on' 'rat' 'sat'
4187</programlisting>
4188
4189     To represent
4190     lexemes containing whitespace or punctuation, surround them with quotes:
4191
4192<programlisting>
4193SELECT $$the lexeme '    ' contains spaces$$::tsvector;
4194                 tsvector
4195-------------------------------------------
4196 '    ' 'contains' 'lexeme' 'spaces' 'the'
4197</programlisting>
4198
4199     (We use dollar-quoted string literals in this example and the next one
4200     to avoid the confusion of having to double quote marks within the
4201     literals.)  Embedded quotes and backslashes must be doubled:
4202
4203<programlisting>
4204SELECT $$the lexeme 'Joe''s' contains a quote$$::tsvector;
4205                    tsvector
4206------------------------------------------------
4207 'Joe''s' 'a' 'contains' 'lexeme' 'quote' 'the'
4208</programlisting>
4209
4210     Optionally, integer <firstterm>positions</firstterm>
4211     can be attached to lexemes:
4212
4213<programlisting>
4214SELECT 'a:1 fat:2 cat:3 sat:4 on:5 a:6 mat:7 and:8 ate:9 a:10 fat:11 rat:12'::tsvector;
4215                                  tsvector
4216-------------------------------------------------------------------&zwsp;------------
4217 'a':1,6,10 'and':8 'ate':9 'cat':3 'fat':2,11 'mat':7 'on':5 'rat':12 'sat':4
4218</programlisting>
4219
4220     A position normally indicates the source word's location in the
4221     document.  Positional information can be used for
4222     <firstterm>proximity ranking</firstterm>.  Position values can
4223     range from 1 to 16383; larger numbers are silently set to 16383.
4224     Duplicate positions for the same lexeme are discarded.
4225    </para>
4226
4227    <para>
4228     Lexemes that have positions can further be labeled with a
4229     <firstterm>weight</firstterm>, which can be <literal>A</literal>,
4230     <literal>B</literal>, <literal>C</literal>, or <literal>D</literal>.
4231     <literal>D</literal> is the default and hence is not shown on output:
4232
4233<programlisting>
4234SELECT 'a:1A fat:2B,4C cat:5D'::tsvector;
4235          tsvector
4236----------------------------
4237 'a':1A 'cat':5 'fat':2B,4C
4238</programlisting>
4239
4240     Weights are typically used to reflect document structure, for example
4241     by marking title words differently from body words.  Text search
4242     ranking functions can assign different priorities to the different
4243     weight markers.
4244    </para>
4245
4246    <para>
4247     It is important to understand that the
4248     <type>tsvector</type> type itself does not perform any word
4249     normalization; it assumes the words it is given are normalized
4250     appropriately for the application.  For example,
4251
4252<programlisting>
4253SELECT 'The Fat Rats'::tsvector;
4254      tsvector
4255--------------------
4256 'Fat' 'Rats' 'The'
4257</programlisting>
4258
4259     For most English-text-searching applications the above words would
4260     be considered non-normalized, but <type>tsvector</type> doesn't care.
4261     Raw document text should usually be passed through
4262     <function>to_tsvector</function> to normalize the words appropriately
4263     for searching:
4264
4265<programlisting>
4266SELECT to_tsvector('english', 'The Fat Rats');
4267   to_tsvector
4268-----------------
4269 'fat':2 'rat':3
4270</programlisting>
4271

4277   <sect2 id="datatype-tsquery">
4278    <title><type>tsquery</type></title>
4279
4280    <indexterm>
4281     <primary>tsquery (data type)</primary>
4282    </indexterm>
4283
4284    <para>
4285     A <type>tsquery</type> value stores lexemes that are to be
4286     searched for, and can combine them using the Boolean operators
4287     <literal>&amp;</literal> (AND), <literal>|</literal> (OR), and
4288     <literal>!</literal> (NOT), as well as the phrase search operator
4289     <literal>&lt;-&gt;</literal> (FOLLOWED BY).  There is also a variant
4290     <literal>&lt;<replaceable>N</replaceable>&gt;</literal> of the FOLLOWED BY
4291     operator, where <replaceable>N</replaceable> is an integer constant that
4292     specifies the distance between the two lexemes being searched
4293     for.  <literal>&lt;-&gt;</literal> is equivalent to <literal>&lt;1&gt;</literal>.
4294    </para>
4295
4296    <para>
4297     Parentheses can be used to enforce grouping of these operators.
4298     In the absence of parentheses, <literal>!</literal> (NOT) binds most tightly,
4299     <literal>&lt;-&gt;</literal> (FOLLOWED BY) next most tightly, then
4300     <literal>&amp;</literal> (AND), with <literal>|</literal> (OR) binding
4301     the least tightly.
4302    </para>
4303
4304    <para>
4305     Here are some examples:
4306
4307<programlisting>
4308SELECT 'fat &amp; rat'::tsquery;
4309    tsquery
4310---------------
4311 'fat' &amp; 'rat'
4312
4313SELECT 'fat &amp; (rat | cat)'::tsquery;
4314          tsquery
4315---------------------------
4316 'fat' &amp; ( 'rat' | 'cat' )
4317
4318SELECT 'fat &amp; rat &amp; ! cat'::tsquery;
4319        tsquery
4320------------------------
4321 'fat' &amp; 'rat' &amp; !'cat'
4322</programlisting>
4323    </para>
4324
4325    <para>
4326     Optionally, lexemes in a <type>tsquery</type> can be labeled with
4327     one or more weight letters, which restricts them to match only
4328     <type>tsvector</type> lexemes with one of those weights:
4329
4330<programlisting>
4331SELECT 'fat:ab &amp; cat'::tsquery;
4332    tsquery
4333------------------
4334 'fat':AB &amp; 'cat'
4335</programlisting>
4336    </para>
4337
4338    <para>
4339     Also, lexemes in a <type>tsquery</type> can be labeled with <literal>*</literal>
4340     to specify prefix matching:
4341<programlisting>
4342SELECT 'super:*'::tsquery;
4343  tsquery
4344-----------
4345 'super':*
4346</programlisting>
4347     This query will match any word in a <type>tsvector</type> that begins
4348     with <quote>super</quote>.
4349    </para>
4350
4351    <para>
4352     Quoting rules for lexemes are the same as described previously for
4353     lexemes in <type>tsvector</type>; and, as with <type>tsvector</type>,
4354     any required normalization of words must be done before converting
4355     to the <type>tsquery</type> type.  The <function>to_tsquery</function>
4356     function is convenient for performing such normalization:
4357
4358<programlisting>
4359SELECT to_tsquery('Fat:ab &amp; Cats');
4360    to_tsquery
4361------------------
4362 'fat':AB &amp; 'cat'
4363</programlisting>
4364
4365     Note that <function>to_tsquery</function> will process prefixes in the same way
4366     as other words, which means this comparison returns true:
4367
4368<programlisting>
4369SELECT to_tsvector( 'postgraduate' ) @@ to_tsquery( 'postgres:*' );
4370 ?column?
4371----------
4372 t
4373</programlisting>
4374     because <literal>postgres</literal> gets stemmed to <literal>postgr</literal>:
4375<programlisting>
4376SELECT to_tsvector( 'postgraduate' ), to_tsquery( 'postgres:*' );
4377  to_tsvector  | to_tsquery
4378---------------+------------
4379 'postgradu':1 | 'postgr':*
4380</programlisting>
4381     which will match the stemmed form of <literal>postgraduate</literal>.
4382    </para>

4388  <sect1 id="datatype-uuid">
4389   <title><acronym>UUID</acronym> Type</title>
4390
4391   <indexterm zone="datatype-uuid">
4392    <primary>UUID</primary>
4393   </indexterm>
4394
4395   <para>
4396    The data type <type>uuid</type> stores Universally Unique Identifiers
4397    (UUID) as defined by <ulink url="https://datatracker.ietf.org/doc/html/rfc9562">RFC 9562</ulink>,
4398    ISO/IEC 9834-8:2005, and related standards.
4399    (Some systems refer to this data type as a globally unique identifier, or
4400    GUID,<indexterm><primary>GUID</primary></indexterm> instead.)  This
4401    identifier is a 128-bit quantity that is generated by an algorithm chosen
4402    to make it very unlikely that the same identifier will be generated by
4403    anyone else in the known universe using the same algorithm.  Therefore,
4404    for distributed systems, these identifiers provide a better uniqueness
4405    guarantee than sequence generators, which
4406    are only unique within a single database.
4407   </para>
4408
4409   <para>
4410    RFC 9562 defines 8 different UUID versions.  Each version has specific requirements
4411    for generating new UUID values, and each version provides distinct benefits and drawbacks.
4412    <productname>PostgreSQL</productname> provides native support for generating UUIDs
4413    using the UUIDv4 and UUIDv7 algorithms.  Alternatively, UUID values can be generated
4414    outside of the database using any algorithm.  The data type <type>uuid</type> can be used
4415    to store any UUID, regardless of the origin and the UUID version.
4416   </para>
4417
4418   <para>
4419    A UUID is written as a sequence of lower-case hexadecimal digits,
4420    in several groups separated by hyphens, specifically a group of 8
4421    digits followed by three groups of 4 digits followed by a group of
4422    12 digits, for a total of 32 digits representing the 128 bits.  An
4423    example of a UUID in this standard form is:
4424<programlisting>
4425a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11
4426</programlisting>
4427    <productname>PostgreSQL</productname> also accepts the following
4428    alternative forms for input:
4429    use of upper-case digits, the standard format surrounded by
4430    braces, omitting some or all hyphens, adding a hyphen after any
4431    group of four digits.  Examples are:
4432<programlisting>
4433A0EEBC99-9C0B-4EF8-BB6D-6BB9BD380A11
4434{a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11}
4435a0eebc999c0b4ef8bb6d6bb9bd380a11
4436a0ee-bc99-9c0b-4ef8-bb6d-6bb9-bd38-0a11
4437{a0eebc99-9c0b4ef8-bb6d6bb9-bd380a11}
4438</programlisting>
4439    Output is always in the standard form.
4440   </para>
4441
4442   <para>
4443    It is possible to cast <type>uuid</type> values to and from type
4444    <type>bytea</type>. This is useful for using functions such as
4445    <function>encode()</function> and <function>decode()</function>
4446    with UUID values. For example:
4447<programlisting>
4448encode('1ea3d64c-bc40-4cc3-84bb-6b11ee31e5c2'::uuid::bytea, 'base64')
4449decode('HqPWTLxATMOEu2sR7jHlwg==', 'base64')::uuid
4450</programlisting>
4451   </para>
4452
4453   <para>
4454    See <xref linkend="functions-uuid"/> for how to generate a UUID in
4455    <productname>PostgreSQL</productname>.
4456   </para>

4572   <sect2 id="datatype-xml-encoding-handling">
4573    <title>Encoding Handling</title>
4574   <para>
4575    Care must be taken when dealing with multiple character encodings
4576    on the client, server, and in the XML data passed through them.
4577    When using the text mode to pass queries to the server and query
4578    results to the client (which is the normal mode), PostgreSQL
4579    converts all character data passed between the client and the
4580    server and vice versa to the character encoding of the respective
4581    end; see <xref linkend="multibyte"/>.  This includes string
4582    representations of XML values, such as in the above examples.
4583    This would ordinarily mean that encoding declarations contained in
4584    XML data can become invalid as the character data is converted
4585    to other encodings while traveling between client and server,
4586    because the embedded encoding declaration is not changed.  To cope
4587    with this behavior, encoding declarations contained in
4588    character strings presented for input to the <type>xml</type> type
4589    are <emphasis>ignored</emphasis>, and content is assumed
4590    to be in the current server encoding.  Consequently, for correct
4591    processing, character strings of XML data must be sent
4592    from the client in the current client encoding.  It is the
4593    responsibility of the client to either convert documents to the
4594    current client encoding before sending them to the server, or to
4595    adjust the client encoding appropriately.  On output, values of
4596    type <type>xml</type> will not have an encoding declaration, and
4597    clients should assume all data is in the current client
4598    encoding.
4599   </para>
4600
4601   <para>
4602    When using binary mode to pass query parameters to the server
4603    and query results back to the client, no encoding conversion
4604    is performed, so the situation is different.  In this case, an
4605    encoding declaration in the XML data will be observed, and if it
4606    is absent, the data will be assumed to be in UTF-8 (as required by
4607    the XML standard; note that PostgreSQL does not support UTF-16).
4608    On output, data will have an encoding declaration
4609    specifying the client encoding, unless the client encoding is
4610    UTF-8, in which case it will be omitted.
4611   </para>
4612
4613   <para>
4614    Needless to say, processing XML data with PostgreSQL will be less
4615    error-prone and more efficient if the XML data encoding, client encoding,
4616    and server encoding are the same.  Since XML data is internally
4617    processed in UTF-8, computations will be most efficient if the
4618    server encoding is also UTF-8.
4619   </para>
4620
4621   <caution>
4622    <para>
4623     Some XML-related functions may not work at all on non-ASCII data
4624     when the server encoding is not UTF-8.  This is known to be an
4625     issue for <function>xmltable()</function> and <function>xpath()</function> in particular.
4626    </para>
4627   </caution>

4630   <sect2 id="datatype-xml-accessing-xml-values">
4631   <title>Accessing XML Values</title>
4632
4633   <para>
4634    The <type>xml</type> data type is unusual in that it does not
4635    provide any comparison operators.  This is because there is no
4636    well-defined and universally useful comparison algorithm for XML
4637    data.  One consequence of this is that you cannot retrieve rows by
4638    comparing an <type>xml</type> column against a search value.  XML
4639    values should therefore typically be accompanied by a separate key
4640    field such as an ID.  An alternative solution for comparing XML
4641    values is to convert them to character strings first, but note
4642    that character string comparison has little to do with a useful
4643    XML comparison method.
4644   </para>
4645
4646   <para>
4647    Since there are no comparison operators for the <type>xml</type>
4648    data type, it is not possible to create an index directly on a
4649    column of this type.  If speedy searches in XML data are desired,
4650    possible workarounds include casting the expression to a
4651    character string type and indexing that, or indexing an XPath
4652    expression.  Of course, the actual query would have to be adjusted
4653    to search by the indexed expression.
4654   </para>
4655
4656   <para>
4657    The text-search functionality in PostgreSQL can also be used to speed
4658    up full-document searches of XML data.  The necessary
4659    preprocessing support is, however, not yet available in the PostgreSQL
4660    distribution.

4674   <title>Domain Types</title>
4675
4676   <indexterm zone="domains">
4677    <primary>domain</primary>
4678   </indexterm>
4679
4680   <indexterm zone="domains">
4681    <primary>data type</primary>
4682    <secondary>domain</secondary>
4683   </indexterm>
4684
4685   <para>
4686    A <firstterm>domain</firstterm> is a user-defined data type that is
4687    based on another <firstterm>underlying type</firstterm>.  Optionally,
4688    it can have constraints that restrict its valid values to a subset of
4689    what the underlying type would allow.  Otherwise it behaves like the
4690    underlying type &mdash; for example, any operator or function that
4691    can be applied to the underlying type will work on the domain type.
4692    The underlying type can be any built-in or user-defined base type,
4693    enum type, array type, composite type, range type, or another domain.
4694   </para>
4695
4696   <para>
4697    For example, we could create a domain over integers that accepts only
4698    positive integers:
4699<programlisting>
4700CREATE DOMAIN posint AS integer CHECK (VALUE &gt; 0);
4701CREATE TABLE mytable (id posint);
4702INSERT INTO mytable VALUES(1);   -- works
4703INSERT INTO mytable VALUES(-1);  -- fails
4704</programlisting>
4705   </para>
4706
4707   <para>
4708    When an operator or function of the underlying type is applied to a
4709    domain value, the domain is automatically down-cast to the underlying
4710    type.  Thus, for example, the result of <literal>mytable.id - 1</literal>
4711    is considered to be of type <type>integer</type> not <type>posint</type>.
4712    We could write <literal>(mytable.id - 1)::posint</literal> to cast the
4713    result back to <type>posint</type>, causing the domain's constraints
4714    to be rechecked.  In this case, that would result in an error if the
4715    expression had been applied to an <structfield>id</structfield> value of
4716    1.  Assigning a value of the underlying type to a field or variable of
4717    the domain type is allowed without writing an explicit cast, but the
4718    domain's constraints will be checked.
4719   </para>
4720
4721   <para>
4722    For additional information see <xref linkend="sql-createdomain"/>.
4723   </para>

4974   <para>
4975    All of the OID alias types for objects that are grouped by namespace
4976    accept schema-qualified names, and will
4977    display schema-qualified names on output if the object would not
4978    be found in the current search path without being qualified.
4979    For example, <literal>myschema.mytable</literal> is acceptable input
4980    for <type>regclass</type> (if there is such a table).  That value
4981    might be output as <literal>myschema.mytable</literal>, or
4982    just <literal>mytable</literal>, depending on the current search path.
4983    The <type>regproc</type> and <type>regoper</type> alias types will only
4984    accept input names that are unique (not overloaded), so they are
4985    of limited use; for most uses <type>regprocedure</type> or
4986    <type>regoperator</type> are more appropriate.  For <type>regoperator</type>,
4987    unary operators are identified by writing <literal>NONE</literal> for the unused
4988    operand.
4989   </para>
4990
4991   <para>
4992    The input functions for these types allow whitespace between tokens,
4993    and will fold upper-case letters to lower case, except within double
4994    quotes; this is done to make the syntax rules similar to the way
4995    object names are written in SQL.  Conversely, the output functions
4996    will use double quotes if needed to make the output be a valid SQL
4997    identifier.  For example, the OID of a function
4998    named <literal>Foo</literal> (with upper case <literal>F</literal>)
4999    taking two integer arguments could be entered as
5000    <literal>' "Foo" ( int, integer ) '::regprocedure</literal>.  The
5001    output would look like <literal>"Foo"(integer,integer)</literal>.
5002    Both the function name and the argument type names could be
5003    schema-qualified, too.
5004   </para>

5006   <para>
5007    Many built-in <productname>PostgreSQL</productname> functions accept
5008    the OID of a table, or another kind of database object, and for
5009    convenience are declared as taking <type>regclass</type> (or the
5010    appropriate OID alias type).  This means you do not have to look up
5011    the object's OID by hand, but can just enter its name as a string
5012    literal.  For example, the <function>nextval(regclass)</function> function
5013    takes a sequence relation's OID, so you could call it like this:
5014<programlisting>
5015nextval('foo')              <lineannotation>operates on sequence <literal>foo</literal></lineannotation>
5016nextval('FOO')              <lineannotation>same as above</lineannotation>
5017nextval('"Foo"')            <lineannotation>operates on sequence <literal>Foo</literal></lineannotation>
5018nextval('myschema.foo')     <lineannotation>operates on <literal>myschema.foo</literal></lineannotation>
5019nextval('"myschema".foo')   <lineannotation>same as above</lineannotation>
5020nextval('foo')              <lineannotation>searches search path for <literal>foo</literal></lineannotation>
5021</programlisting>
5022   </para>
5023
5024   <note>
5025    <para>
5026     When you write the argument of such a function as an unadorned
5027     literal string, it becomes a constant of type <type>regclass</type>
5028     (or the appropriate type).
5029     Since this is really just an OID, it will track the originally
5030     identified object despite later renaming, schema reassignment,
5031     etc.  This <quote>early binding</quote> behavior is usually desirable for
5032     object references in column defaults and views.  But sometimes you might
5033     want <quote>late binding</quote> where the object reference is resolved
5034     at run time.  To get late-binding behavior, force the constant to be
5035     stored as a <type>text</type> constant instead of <type>regclass</type>:
5036<programlisting>
5037nextval('foo'::text)      <lineannotation><literal>foo</literal> is looked up at runtime</lineannotation>
5038</programlisting>
5039     The <function>to_regclass()</function> function and its siblings
5040     can also be used to perform run-time lookups.  See
5041     <xref linkend="functions-info-catalog-table"/>.
5042    </para>
5043   </note>
5044
5045   <para>
5046    Another practical example of use of <type>regclass</type>
5047    is to look up the OID of a table listed in
5048    the <literal>information_schema</literal> views, which don't supply
5049    such OIDs directly.  One might for example wish to call
5050    the <function>pg_relation_size()</function> function, which requires
5051    the table OID.  Taking the above rules into account, the correct way
5052    to do that is
5053<programlisting>
5054SELECT table_schema, table_name,
5055       pg_relation_size((quote_ident(table_schema) || '.' ||
5056                         quote_ident(table_name))::regclass)
5057FROM information_schema.tables
5058WHERE ...
5059</programlisting>
5060    The <function>quote_ident()</function> function will take care of
5061    double-quoting the identifiers where needed.  The seemingly easier
5062<programlisting>
5063SELECT pg_relation_size(table_name)
5064FROM information_schema.tables
5065WHERE ...
5066</programlisting>
5067    is <emphasis>not recommended</emphasis>, because it will fail for
5068    tables that are outside your search path or have names that require
5069    quoting.
5070   </para>
5071
5072   <para>
5073    An additional property of most of the OID alias types is the creation of
5074    dependencies.  If a
5075    constant of one of these types appears in a stored expression
5076    (such as a column default expression or view), it creates a dependency
5077    on the referenced object.  For example, if a column has a default
5078    expression <literal>nextval('my_seq'::regclass)</literal>,
5079    <productname>PostgreSQL</productname>
5080    understands that the default expression depends on the sequence
5081    <literal>my_seq</literal>, so the system will not let the sequence
5082    be dropped without first removing the default expression.  The
5083    alternative of <literal>nextval('my_seq'::text)</literal> does not
5084    create a dependency.
5085    (<type>regdatabase</type> and <type>regrole</type> are exceptions to this
5086    property.  Constants of these types are not allowed in stored expressions.)
5087   </para>
5088
5089   <para>
5090    Another identifier type used by the system is <type>xid</type>, or transaction
5091    (abbreviated <abbrev>xact</abbrev>) identifier.  This is the data type of the system columns
5092    <structfield>xmin</structfield> and <structfield>xmax</structfield>.  Transaction identifiers are 32-bit quantities.
5093    In some contexts, a 64-bit variant <type>xid8</type> is used.  Unlike
5094    <type>xid</type> values, <type>xid8</type> values increase strictly
5095    monotonically and cannot be reused in the lifetime of a database
5096    cluster.  See <xref linkend="transaction-id"/> for more details.
5097   </para>
5098
5099   <para>
5100    A third identifier type used by the system is <type>cid</type>, or
5101    command identifier.  This is the data type of the system columns
5102    <structfield>cmin</structfield> and <structfield>cmax</structfield>. Command identifiers are also 32-bit quantities.
5103   </para>
5104
5105   <para>
5106    A final identifier type used by the system is <type>tid</type>, or tuple
5107    identifier (row identifier).  This is the data type of the system column
5108    <structfield>ctid</structfield>.  A tuple ID is a pair
5109    (block number, tuple index within block) that identifies the
5110    physical location of the row within its table.
5111   </para>

5120   <title><type>pg_lsn</type> Type</title>
5121
5122   <indexterm zone="datatype-pg-lsn">
5123    <primary>pg_lsn</primary>
5124   </indexterm>
5125
5126   <para>
5127    The <type>pg_lsn</type> data type can be used to store LSN (Log Sequence
5128    Number) data which is a pointer to a location in the WAL. This type is a
5129    representation of <type>XLogRecPtr</type> and an internal system type of
5130    <productname>PostgreSQL</productname>.
5131   </para>
5132
5133   <para>
5134    Internally, an LSN is a 64-bit integer, representing a byte position in
5135    the write-ahead log stream.  It is printed as two hexadecimal numbers of
5136    up to 8 digits each, separated by a slash; for example,
5137    <literal>16/B374D848</literal>.  The <type>pg_lsn</type> type supports the
5138    standard comparison operators, like <literal>=</literal> and
5139    <literal>&gt;</literal>.  Two LSNs can be subtracted using the
5140    <literal>-</literal> operator; the result is the number of bytes separating
5141    those write-ahead log locations.  Also the number of bytes can be
5142    added into and subtracted from LSN using the
5143    <literal>+(pg_lsn,numeric)</literal> and
5144    <literal>-(pg_lsn,numeric)</literal> operators, respectively. Note that
5145    the calculated LSN should be in the range of <type>pg_lsn</type> type,
5146    i.e., between <literal>0/00000000</literal> and
5147    <literal>FFFFFFFF/FFFFFFFF</literal>.
5148   </para>
