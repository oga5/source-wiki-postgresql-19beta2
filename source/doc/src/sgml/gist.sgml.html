11<sect2 id="gist-intro">
12 <title>Introduction</title>
13
14 <para>
15   <acronym>GiST</acronym> stands for Generalized Search Tree.  It is a
16   balanced, tree-structured access method, that acts as a base template in
17   which to implement arbitrary indexing schemes. B-trees, R-trees and many
18   other indexing schemes can be implemented in <acronym>GiST</acronym>.
19 </para>
20
21 <para>
22  One advantage of <acronym>GiST</acronym> is that it allows the development
23  of custom data types with the appropriate access methods, by
24  an expert in the domain of the data type, rather than a database expert.
25 </para>
26
27  <para>
28    Some of the information here is derived from the University of California
29    at Berkeley's GiST Indexing Project
30    <ulink url="http://gist.cs.berkeley.edu/">web site</ulink> and
31    Marcel Kornacker's thesis,
32    <ulink url="http://www.sai.msu.su/~megera/postgres/gist/papers/concurrency/access-methods-for-next-generation.pdf.gz">
33    Access Methods for Next-Generation Database Systems</ulink>.
34    The <acronym>GiST</acronym>
35    implementation in <productname>PostgreSQL</productname> is primarily
36    maintained by Teodor Sigaev and Oleg Bartunov, and there is more
37    information on their
38    <ulink url="http://www.sai.msu.su/~megera/postgres/gist/">web site</ulink>.
39  </para>

221<sect2 id="gist-extensibility">
222 <title>Extensibility</title>
223
224 <para>
225   Traditionally, implementing a new index access method meant a lot of
226   difficult work.  It was necessary to understand the inner workings of the
227   database, such as the lock manager and Write-Ahead Log.  The
228   <acronym>GiST</acronym> interface has a high level of abstraction,
229   requiring the access method implementer only to implement the semantics of
230   the data type being accessed.  The <acronym>GiST</acronym> layer itself
231   takes care of concurrency, logging and searching the tree structure.
232 </para>
233
234 <para>
235   This extensibility should not be confused with the extensibility of the
236   other standard search trees in terms of the data they can handle.  For
237   example, <productname>PostgreSQL</productname> supports extensible B-trees
238   and hash indexes. That means that you can use
239   <productname>PostgreSQL</productname> to build a B-tree or hash over any
240   data type you want. But B-trees only support range predicates
241   (<literal>&lt;</literal>, <literal>=</literal>, <literal>&gt;</literal>),
242   and hash indexes only support equality queries.
243 </para>
244
245 <para>
246   So if you index, say, an image collection with a
247   <productname>PostgreSQL</productname> B-tree, you can only issue queries
248   such as <quote>is imagex equal to imagey</quote>, <quote>is imagex less
249   than imagey</quote> and <quote>is imagex greater than imagey</quote>.
250   Depending on how you define <quote>equals</quote>, <quote>less than</quote>
251   and <quote>greater than</quote> in this context, this could be useful.
252   However, by using a <acronym>GiST</acronym> based index, you could create
253   ways to ask domain-specific questions, perhaps <quote>find all images of
254   horses</quote> or <quote>find all over-exposed images</quote>.
255 </para>
256
257 <para>
258   All it takes to get a <acronym>GiST</acronym> access method up and running
259   is to implement several user-defined methods, which define the behavior of
260   keys in the tree. Of course these methods have to be pretty fancy to
261   support fancy queries, but for all the standard queries (B-trees,
262   R-trees, etc.) they're relatively straightforward. In short,
263   <acronym>GiST</acronym> combines extensibility along with generality, code
264   reuse, and a clean interface.
265  </para>
266
267 <para>
268   There are five methods that an index operator class for
269   <acronym>GiST</acronym> must provide, and seven that are optional.
270   Correctness of the index is ensured
271   by proper implementation of the <function>same</function>, <function>consistent</function>
272   and <function>union</function> methods, while efficiency (size and speed) of the
273   index will depend on the <function>penalty</function> and <function>picksplit</function>
274   methods.
275   Two optional methods are <function>compress</function> and
276   <function>decompress</function>, which allow an index to store keys that
277   are of a different type than the data it indexes, or are a compressed
278   representation of that type.
279   The optional eighth method <function>distance</function> is needed
280   if the operator class wishes to support ordered scans (nearest-neighbor
281   searches). The optional ninth method <function>fetch</function> is needed if the
282   operator class wishes to support index-only scans, except when the
283   <function>compress</function> method is omitted. The optional tenth method
284   <function>options</function> is needed if the operator class has
285   user-specified parameters.
286   The optional eleventh method <function>sortsupport</function> is used to
287   speed up building a <acronym>GiST</acronym> index.
288   The optional twelfth method <function>stratnum</function> is used to
289   translate compare types (from
290   <filename>src/include/access/cmptype.h</filename>) into strategy numbers
291   used by the operator class.  This lets the core code look up operators for
292   temporal constraint indexes.
293   All these methods are described in more detail below.
294 </para>
295
296 <variablelist>
297    <varlistentry>
298     <term><function>consistent</function></term>
299     <listitem>
300      <para>
301       Given an index entry <literal>p</literal> and a query value <literal>q</literal>,
302       this function determines whether the index entry is
303       <quote>consistent</quote> with the query; that is, could the predicate
304       <quote><replaceable>indexed_column</replaceable>
305       <replaceable>indexable_operator</replaceable> <literal>q</literal></quote> be true for
306       any row represented by the index entry?  For a leaf index entry this is
307       equivalent to testing the indexable condition, while for an internal
308       tree node this determines whether it is necessary to scan the subtree
309       of the index represented by the tree node.  When the result is
310       <literal>true</literal>, a <literal>recheck</literal> flag must also be returned.
311       This indicates whether the predicate is certainly true or only possibly
312       true.  If <literal>recheck</literal> = <literal>false</literal> then the index has
313       tested the predicate condition exactly, whereas if <literal>recheck</literal>
314       = <literal>true</literal> the row is only a candidate match.  In that case the
315       system will automatically evaluate the
316       <replaceable>indexable_operator</replaceable> against the actual row value to see
317       if it is really a match.  This convention allows
318       <acronym>GiST</acronym> to support both lossless and lossy index
319       structures.
320      </para>
321
322      <para>
323        The <acronym>SQL</acronym> declaration of the function must look like this:
324
325<programlisting>
326CREATE OR REPLACE FUNCTION my_consistent(internal, data_type, smallint, oid, internal)
327RETURNS bool
328AS 'MODULE_PATHNAME'
329LANGUAGE C STRICT;
330</programlisting>
331
332        And the matching code in the C module could then follow this skeleton:
333
334<programlisting>
335PG_FUNCTION_INFO_V1(my_consistent);
336
337Datum
338my_consistent(PG_FUNCTION_ARGS)
339{
340    GISTENTRY  *entry = (GISTENTRY *) PG_GETARG_POINTER(0);
341    data_type  *query = PG_GETARG_DATA_TYPE_P(1);
342    StrategyNumber strategy = (StrategyNumber) PG_GETARG_UINT16(2);
343#ifdef NOT_USED
344    Oid         subtype = PG_GETARG_OID(3);
345#endif
346    bool       *recheck = (bool *) PG_GETARG_POINTER(4);
347    data_type  *key = DatumGetDataType(entry-&gt;key);
348    bool        retval;
349
350    /*
351     * determine return value as a function of strategy, key and query.
352     *
353     * Use GIST_LEAF(entry) to know where you're called in the index tree,
354     * which comes handy when supporting the = operator for example (you could
355     * check for non empty union() in non-leaf nodes and equality in leaf
356     * nodes).
357     */
358
359    *recheck = true;        /* or false if check is exact */
360
361    PG_RETURN_BOOL(retval);
362}
363</programlisting>
364
365       Here, <varname>key</varname> is an element in the index and <varname>query</varname>
366       the value being looked up in the index. The <literal>StrategyNumber</literal>
367       parameter indicates which operator of your operator class is being
368       applied &mdash; it matches one of the operator numbers in the
369       <command>CREATE OPERATOR CLASS</command> command.
370      </para>
371
372      <para>
373       Depending on which operators you have included in the class, the data
374       type of <varname>query</varname> could vary with the operator, since it will
375       be whatever type is on the right-hand side of the operator, which might
376       be different from the indexed data type appearing on the left-hand side.
377       (The above code skeleton assumes that only one type is possible; if
378       not, fetching the <varname>query</varname> argument value would have to depend
379       on the operator.)  It is recommended that the SQL declaration of
380       the <function>consistent</function> function use the opclass's indexed data
381       type for the <varname>query</varname> argument, even though the actual type
382       might be something else depending on the operator.
383      </para>
384
385     </listitem>
386    </varlistentry>
387
388    <varlistentry>
389     <term><function>union</function></term>
390     <listitem>
391      <para>
392       This method consolidates information in the tree.  Given a set of
393       entries, this function generates a new index entry that represents
394       all the given entries.
395      </para>
396
397      <para>
398        The <acronym>SQL</acronym> declaration of the function must look like this:
399
400<programlisting>
401CREATE OR REPLACE FUNCTION my_union(internal, internal)
402RETURNS storage_type
403AS 'MODULE_PATHNAME'
404LANGUAGE C STRICT;
405</programlisting>
406
407        And the matching code in the C module could then follow this skeleton:
408
409<programlisting>
410PG_FUNCTION_INFO_V1(my_union);
411
412Datum
413my_union(PG_FUNCTION_ARGS)
414{
415    GistEntryVector *entryvec = (GistEntryVector *) PG_GETARG_POINTER(0);
416    GISTENTRY  *ent = entryvec-&gt;vector;
417    data_type  *out,
418               *tmp,
419               *old;
420    int         numranges,
421                i = 0;
422
423    numranges = entryvec-&gt;n;
424    tmp = DatumGetDataType(ent[0].key);
425    out = tmp;
426
427    if (numranges == 1)
428    {
429        out = data_type_deep_copy(tmp);
430
431        PG_RETURN_DATA_TYPE_P(out);
432    }
433
434    for (i = 1; i &lt; numranges; i++)
435    {
436        old = out;
437        tmp = DatumGetDataType(ent[i].key);
438        out = my_union_implementation(out, tmp);
439    }
440
441    PG_RETURN_DATA_TYPE_P(out);
442}
443</programlisting>
444      </para>
445
446      <para>
447        As you can see, in this skeleton we're dealing with a data type
448        where <literal>union(X, Y, Z) = union(union(X, Y), Z)</literal>. It's easy
449        enough to support data types where this is not the case, by
450        implementing the proper union algorithm in this
451        <acronym>GiST</acronym> support method.
452      </para>
453
454      <para>
455        The result of the <function>union</function> function must be a value of the
456        index's storage type, whatever that is (it might or might not be
457        different from the indexed column's type).  The <function>union</function>
458        function should return a pointer to newly <function>palloc()</function>ed
459        memory. You can't just return the input value as-is, even if there is
460        no type change.
461      </para>
462
463      <para>
464       As shown above, the <function>union</function> function's
465       first <type>internal</type> argument is actually
466       a <structname>GistEntryVector</structname> pointer.  The second argument is a
467       pointer to an integer variable, which can be ignored.  (It used to be
468       required that the <function>union</function> function store the size of its
469       result value into that variable, but this is no longer necessary.)
470      </para>
471     </listitem>
472    </varlistentry>
473
474    <varlistentry>
475     <term><function>compress</function></term>
476     <listitem>
477      <para>
478       Converts a data item into a format suitable for physical storage in
479       an index page.
480       If the <function>compress</function> method is omitted, data items are stored
481       in the index without modification.
482      </para>
483
484      <para>
485       Use the <literal>STORAGE</literal> option of the <command>CREATE
486       OPERATOR CLASS</command> command to define the data type that is
487       stored in the index, if it is different from the data type being
488       indexed.  Be aware however that the <literal>STORAGE</literal> data
489       type is only used to define the physical properties of the index
490       entries (their <replaceable>typlen</replaceable>,
491       <replaceable>typbyval</replaceable>,
492       and <replaceable>typalign</replaceable> attributes).  What is
493       actually in the index datums is under the control of the
494       <function>compress</function> and <function>decompress</function>
495       methods, so long as the stored datums match those properties.
496       It is allowed for <function>compress</function> to produce different
497       representations for leaf keys than for keys on higher-level index
498       pages, so long as both representations match
499       the <literal>STORAGE</literal> data type.
500      </para>
501
502      <para>
503        The <acronym>SQL</acronym> declaration of the function must look like this:
504
505<programlisting>
506CREATE OR REPLACE FUNCTION my_compress(internal)
507RETURNS internal
508AS 'MODULE_PATHNAME'
509LANGUAGE C STRICT;
510</programlisting>
511
512        And the matching code in the C module could then follow this skeleton:
513
514<programlisting>
515PG_FUNCTION_INFO_V1(my_compress);
516
517Datum
518my_compress(PG_FUNCTION_ARGS)
519{

1193     <listitem>
1194      <para>
1195       Given a <literal>CompareType</literal> value from
1196       <filename>src/include/access/cmptype.h</filename>, returns a strategy
1197       number used by this operator class for matching functionality.  The
1198       function should return <literal>InvalidStrategy</literal> if the
1199       operator class has no matching strategy.
1200      </para>
1201
1202      <para>
1203       This is used for temporal index constraints (i.e., <literal>PRIMARY
1204       KEY</literal> and <literal>UNIQUE</literal>).  If the operator class
1205       provides this function and it returns results for
1206       <literal>COMPARE_EQ</literal>, it can be used in the
1207       non-<literal>WITHOUT OVERLAPS</literal> part(s) of an index constraint.
1208      </para>
1209
1210      <para>
1211       This support function corresponds to the index access method callback
1212       function <structfield>amtranslatecmptype</structfield> (see <xref
1213       linkend="index-functions"/>).  The
1214       <structfield>amtranslatecmptype</structfield> callback function for
1215       GiST indexes merely calls down to the
1216       <function>translate_cmptype</function> support function of the
1217       respective operator family, since the GiST index access method has no
1218       fixed strategy numbers itself.
1219      </para>
1220
1221      <para>
1222       The <acronym>SQL</acronym> declaration of the function must look like
1223       this:
1224
1225<programlisting>
1226CREATE OR REPLACE FUNCTION my_translate_cmptype(integer)
1227RETURNS smallint
1228AS 'MODULE_PATHNAME'
1229LANGUAGE C STRICT;
1230</programlisting>
1231
1232       And the operator family registration must look like this:
1233<programlisting>
1234ALTER OPERATOR FAMILY my_opfamily USING gist ADD
1235    FUNCTION 12 ("any", "any") my_translate_cmptype(int);
1236</programlisting>
1237      </para>
1238
1239       <para>
1240        The matching code in the C module could then follow this skeleton:
1241
1242<programlisting>
1243PG_FUNCTION_INFO_V1(my_translate_cmptype);
1244
1245Datum
1246my_translate_cmptype(PG_FUNCTION_ARGS)
1247{
1248    CompareType cmptype = PG_GETARG_INT32(0);
1249    StrategyNumber ret = InvalidStrategy;
1250
1251    switch (cmptype)
1252    {
1253        case COMPARE_EQ:
1254            ret = BTEqualStrategyNumber;
1255    }
1256
1257    PG_RETURN_UINT16(ret);
1258}
1259</programlisting>
1260      </para>
1261
1262      <para>
1263       One translation function is provided by
1264       <productname>PostgreSQL</productname>:
1265       <literal>gist_translate_cmptype_common</literal> is for operator classes that
1266       use the <literal>RT*StrategyNumber</literal> constants.
1267       The <literal>btree_gist</literal>
1268       extension defines a second translation function,
1269       <literal>gist_translate_cmptype_btree</literal>, for operator classes that use
1270       the <literal>BT*StrategyNumber</literal> constants.
1271      </para>
1272     </listitem>
1273    </varlistentry>
1274  </variablelist>
1275
1276  <para>
1277   All the GiST support methods are normally called in short-lived memory
1278   contexts; that is, <varname>CurrentMemoryContext</varname> will get reset after
1279   each tuple is processed.  It is therefore not very important to worry about
1280   pfree'ing everything you palloc.  However, in some cases it's useful for a
1281   support method to cache data across repeated calls.  To do that, allocate
1282   the longer-lived data in <literal>fcinfo-&gt;flinfo-&gt;fn_mcxt</literal>, and
1283   keep a pointer to it in <literal>fcinfo-&gt;flinfo-&gt;fn_extra</literal>.  Such
1284   data will survive for the life of the index operation (e.g., a single GiST
1285   index scan, index build, or index tuple insertion).  Be careful to pfree
1286   the previous value when replacing a <literal>fn_extra</literal> value, or the leak
1287   will accumulate for the duration of the operation.
1288  </para>

1294
1295 <sect3 id="gist-buffering-build">
1296  <title>GiST Index Build Methods</title>
1297
1298  <para>
1299   The simplest way to build a GiST index is just to insert all the entries,
1300   one by one.  This tends to be slow for large indexes, because if the
1301   index tuples are scattered across the index and the index is large enough
1302   to not fit in cache, a lot of random I/O will be
1303   needed.  <productname>PostgreSQL</productname> supports two alternative
1304   methods for initial build of a GiST index: <firstterm>sorted</firstterm>
1305   and <firstterm>buffered</firstterm> modes.
1306  </para>
1307
1308  <para>
1309   The sorted method is only available if each of the opclasses used by the
1310   index provides a <function>sortsupport</function> function, as described
1311   in <xref linkend="gist-extensibility"/>.  If they do, this method is
1312   usually the best, so it is used by default.
1313  </para>
1314
1315  <para>
1316   The buffered method works by not inserting tuples directly into the index
1317   right away.  It can dramatically reduce the amount of random I/O needed
1318   for non-ordered data sets.  For well-ordered data sets the benefit is
1319   smaller or non-existent, because only a small number of pages receive new
1320   tuples at a time, and those pages fit in cache even if the index as a
1321   whole does not.
1322  </para>
1323
1324  <para>
1325   The buffered method needs to call the <function>penalty</function>
1326   function more often than the simple method does, which consumes some
1327   extra CPU resources. Also, the buffers need temporary disk space, up to
1328   the size of the resulting index. Buffering can also influence the quality
1329   of the resulting index, in both positive and negative directions. That
1330   influence depends on various factors, like the distribution of the input
1331   data and the operator class implementation.
1332  </para>
1333
1334  <para>
1335   If sorting is not possible, then by default a GiST index build switches
1336   to the buffering method when the index size reaches
1337   <xref linkend="guc-effective-cache-size"/>.  Buffering can be manually
1338   forced or prevented by the <literal>buffering</literal> parameter to the
1339   CREATE INDEX command.  The default behavior is good for most cases, but
1340   turning buffering off might speed up the build somewhat if the input data
1341   is ordered.
1342  </para>
