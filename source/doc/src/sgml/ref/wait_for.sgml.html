17 <refnamediv>
18  <refname>WAIT FOR</refname>
19  <refpurpose>wait for WAL to reach a target <acronym>LSN</acronym></refpurpose>
20 </refnamediv>
21
22 <refsynopsisdiv>
23<synopsis>
24WAIT FOR LSN '<replaceable class="parameter">lsn</replaceable>'
25    [ WITH ( <replaceable class="parameter">option</replaceable> [, ...] ) ]
26
27<phrase>where <replaceable class="parameter">option</replaceable> can be:</phrase>
28
29    MODE '<replaceable class="parameter">mode</replaceable>'
30    TIMEOUT '<replaceable class="parameter">timeout</replaceable>'
31    NO_THROW
32
33<phrase>and <replaceable class="parameter">mode</replaceable> can be:</phrase>
34
35    standby_replay | standby_write | standby_flush | primary_flush
36</synopsis>
37 </refsynopsisdiv>
38
39 <refsect1>
40  <title>Description</title>
41
42  <para>
43   Waits until the specified <parameter>lsn</parameter> is reached
44   according to the specified <parameter>mode</parameter>,
45   which determines whether to wait for WAL to be written, flushed, or replayed.
46   If no <parameter>timeout</parameter> is specified or it is set to
47   zero, this command waits indefinitely for the
48   <parameter>lsn</parameter>.
49  </para>
50
51  <para>
52   On timeout, an error is emitted unless <literal>NO_THROW</literal>
53   is specified in the WITH clause. For standby modes
54   (<literal>standby_replay</literal>, <literal>standby_write</literal>,
55   <literal>standby_flush</literal>), an error is also emitted if the
56   server is promoted before the <parameter>lsn</parameter> is reached.
57   If <parameter>NO_THROW</parameter> is specified, the command returns
58   a status string instead of throwing errors.
59  </para>
60
61  <para>
62   The possible return values are <literal>success</literal>,
63   <literal>timeout</literal>, and <literal>not in recovery</literal>.
64  </para>
65 </refsect1>

67 <refsect1>
68  <title>Parameters</title>
69
70  <variablelist>
71   <varlistentry>
72    <term><replaceable class="parameter">lsn</replaceable></term>
73    <listitem>
74     <para>
75      Specifies the target <acronym>LSN</acronym> to wait for.
76     </para>
77    </listitem>
78   </varlistentry>
79
80   <varlistentry>
81    <term><literal>WITH ( <replaceable class="parameter">option</replaceable> [, ...] )</literal></term>
82    <listitem>
83     <para>
84      This clause specifies optional parameters for the wait operation.
85      The following parameters are supported:
86
87      <variablelist>
88       <varlistentry>
89        <term><literal>MODE</literal> '<replaceable class="parameter">mode</replaceable>'</term>
90        <listitem>
91         <para>
92          Specifies the type of LSN processing to wait for. If not specified,
93          the default is <literal>standby_replay</literal>. The valid modes are:
94         </para>
95         <itemizedlist>
96          <listitem>
97           <para>
98            <literal>standby_replay</literal>: Wait for the LSN to be replayed
99            (applied to the database) on a standby server. After successful
100            completion, <function>pg_last_wal_replay_lsn()</function> will
101            return a value greater than or equal to the target LSN. This mode
102            can only be used during recovery.
103           </para>
104          </listitem>
105          <listitem>
106           <para>
107            <literal>standby_write</literal>: Wait for the WAL containing the
108            LSN to be written to disk on a standby server, but not yet
109            necessarily flushed.  This is faster than
110            <literal>standby_flush</literal> but provides weaker durability
111            guarantees since the data may still be in operating system
112            buffers.  This is satisfied by WAL already present on the
113            standby from a base backup, archive restore, or prior
114            streaming, as well as WAL newly received from the primary.
115            This mode can only be used during recovery.
116           </para>
117          </listitem>
118          <listitem>
119           <para>
120            <literal>standby_flush</literal>: Wait for the WAL containing the
121            LSN to be flushed to disk on a standby server.  This provides
122            a durability guarantee without waiting for the WAL to be
123            applied.  This is satisfied by WAL already present on the
124            standby from a base backup, archive restore, or prior
125            streaming, as well as WAL newly received from the primary.
126            This mode can only be used during recovery.
127           </para>
128          </listitem>
129          <listitem>
130           <para>
131            <literal>primary_flush</literal>: Wait for the WAL containing the
132            LSN to be flushed to disk on a primary server. After successful
133            completion, <function>pg_current_wal_flush_lsn()</function> will
134            return a value greater than or equal to the target LSN. This mode
135            can only be used on a primary server (not during recovery).
136           </para>
137          </listitem>
138         </itemizedlist>
139        </listitem>
140       </varlistentry>
141
142       <varlistentry>
143        <term><literal>TIMEOUT</literal> '<replaceable class="parameter">timeout</replaceable>'</term>
144        <listitem>
145         <para>
146          When specified and <parameter>timeout</parameter> is greater than zero,
147          the command waits until <parameter>lsn</parameter> is reached or
148          the specified <parameter>timeout</parameter> has elapsed.
149         </para>
150         <para>
151          The <parameter>timeout</parameter> might be given as integer number of
152          milliseconds.  Also it might be given as string literal with
153          integer number of milliseconds or a number with unit
154          (see <xref linkend="config-setting-names-values"/>).
155         </para>
156        </listitem>
157       </varlistentry>
158
159       <varlistentry>
160        <term><literal>NO_THROW</literal></term>
161        <listitem>
162         <para>
163          Specify to not throw an error in the case of timeout or
164          running on the primary.  In this case the result status can be get from
165          the return value.
166         </para>
167        </listitem>
168       </varlistentry>
169      </variablelist>
170     </para>
171    </listitem>
172   </varlistentry>
173  </variablelist>

177  <title>Outputs</title>
178
179  <variablelist>
180   <varlistentry>
181    <term><literal>success</literal></term>
182    <listitem>
183     <para>
184      This return value denotes that we have successfully reached
185      the target <parameter>lsn</parameter>.
186     </para>
187    </listitem>
188   </varlistentry>
189
190   <varlistentry>
191    <term><literal>timeout</literal></term>
192    <listitem>
193     <para>
194      This return value denotes that the timeout happened before reaching
195      the target <parameter>lsn</parameter>.
196     </para>
197    </listitem>
198   </varlistentry>
199
200   <varlistentry>
201    <term><literal>not in recovery</literal></term>
202    <listitem>
203     <para>
204      This return value denotes that the database server is not in a recovery
205      state. This might mean either the database server was not in recovery
206      at the moment of receiving the command (i.e., executed on a primary),
207      or it was promoted before reaching the target <parameter>lsn</parameter>.
208      In the promotion case, this status indicates a timeline change occurred,
209      and the application should re-evaluate whether the target LSN is still
210      relevant.
211     </para>
212    </listitem>
213   </varlistentry>
214  </variablelist>

217 <refsect1>
218  <title>Notes</title>
219  <para>
220   <command>WAIT FOR</command> must be executed as a top-level command.
221   It cannot be executed from a function, procedure, or
222   <command>DO</command> block. It also requires that no active or
223   registered snapshot be held, and therefore cannot be used in contexts
224   where such a snapshot must remain active, including transactions running
225   at isolation levels higher than <literal>READ COMMITTED</literal>.
226  </para>
227
228  <para>
229   <command>WAIT FOR</command> waits until the specified
230   <parameter>lsn</parameter> is reached according to the specified
231   <parameter>mode</parameter>. The <literal>standby_replay</literal> mode
232   waits for the LSN to be replayed (applied to the database), which is
233   useful to achieve read-your-writes consistency while using an async
234   replica for reads and the primary for writes. The
235   <literal>standby_flush</literal> mode waits for the WAL to be flushed
236   to durable storage on the replica, or to have already been replayed
237   from WAL present on the standby. The <literal>standby_write</literal> mode
238   waits for the WAL to be written to the operating system, or to have
239   already been replayed, which is faster than flush for newly received
240   WAL but provides weaker durability guarantees. The
241   <literal>primary_flush</literal> mode waits for WAL to be flushed on
242   a primary server. In all cases, the <acronym>LSN</acronym> of the last
243   modification should be stored on the client application side or the
244   connection pooler side.
245  </para>
246
247  <para>
248   The standby modes (<literal>standby_replay</literal>,
249   <literal>standby_write</literal>, <literal>standby_flush</literal>)
250   can only be used during recovery, and <literal>primary_flush</literal>
251   can only be used on a primary server. Using the wrong mode for the
252   current server state will result in an error. If a standby is promoted
253   while waiting with a standby mode, the command will return
254   <literal>not in recovery</literal> (or throw an error if
255   <literal>NO_THROW</literal> is not specified). Promotion creates a new
256   timeline, and the LSN being waited for may refer to WAL from the old
257   timeline.
258  </para>
259
260  <para>
261   <command>WAIT FOR</command> compares only the numeric
262   <acronym>LSN</acronym>; it has no notion of which timeline a WAL
263   record belongs to.  This matters when a standby continues recovery
264   across an upstream timeline switch &mdash; for example, a cascading
265   standby whose upstream gets promoted.  In that case
266   <command>WAIT FOR</command> will return <literal>success</literal>
267   as soon as the position used by the selected wait mode reaches or
268   passes the numeric <acronym>LSN</acronym>, regardless of which
269   timeline that <acronym>LSN</acronym> belongs to.  Applications that need to
270   confirm the target refers to the expected timeline must validate
271   the timeline themselves.
272  </para>
273
274  <para>
275   On a standby server, <command>WAIT FOR</command> sessions may be
276   interrupted by recovery conflicts.  Some recovery conflicts are
277   unavoidable: for example, replaying a tablespace drop resolves
278   conflicts by terminating all backends, regardless of what they are
279   doing.  Applications using <command>WAIT FOR</command> on a standby
280   should be prepared to handle such interruptions, for example by
281   retrying the command or falling back to an alternative mechanism.
282  </para>
283
284</refsect1>

286 <refsect1>
287  <title>Examples</title>
288
289  <para>
290   You can use <command>WAIT FOR</command> command to wait for
291   the <type>pg_lsn</type> value.  For example, an application could update
292   the <literal>movie</literal> table and get the <acronym>lsn</acronym> after
293   changes just made.  This example uses <function>pg_current_wal_insert_lsn</function>
294   on primary server to get the <acronym>lsn</acronym> given that
295   <varname>synchronous_commit</varname> could be set to
296   <literal>off</literal>.
297
298   <programlisting>
299postgres=# UPDATE movie SET genre = 'Dramatic' WHERE genre = 'Drama';
300UPDATE 100
301postgres=# SELECT pg_current_wal_insert_lsn();
302 pg_current_wal_insert_lsn
303---------------------------
304 0/306EE20
305(1 row)
306</programlisting>
307
308   Then an application could run <command>WAIT FOR</command>
309   with the <parameter>lsn</parameter> obtained from primary.  After that the
310   changes made on primary should be guaranteed to be visible on replica.
311
312<programlisting>
313postgres=# WAIT FOR LSN '0/306EE20';
314 status
315---------
316 success
317(1 row)
318postgres=# SELECT * FROM movie WHERE genre = 'Drama';
319 genre
320-------
321(0 rows)
322</programlisting>
323  </para>
324
325  <para>
326   Wait for flush (data durable on replica):
327
328<programlisting>
329postgres=# WAIT FOR LSN '0/306EE20' WITH (MODE 'standby_flush');
330 status
331---------
332 success
333(1 row)
334</programlisting>
335  </para>
336
337  <para>
338   Wait for write with timeout:
339
340<programlisting>
341postgres=# WAIT FOR LSN '0/306EE20' WITH (MODE 'standby_write', TIMEOUT '100ms', NO_THROW);
342 status
343---------
344 success
345(1 row)
346</programlisting>
347  </para>
348
349  <para>
350   Wait for flush on primary:
351
352<programlisting>
353postgres=# WAIT FOR LSN '0/306EE20' WITH (MODE 'primary_flush');
354 status
355---------
356 success
357(1 row)
358</programlisting>
359  </para>
360
361  <para>
362   If the target LSN is not reached before the timeout, an error is thrown:
363
364<programlisting>
365postgres=# WAIT FOR LSN '0/306EE20' WITH (TIMEOUT '0.1s');
366ERROR:  timed out while waiting for target LSN 0/306EE20 to be replayed; current replay LSN 0/306EA60
367</programlisting>
368  </para>
369
370  <para>
371   The same example uses <command>WAIT FOR</command> with
372   <parameter>NO_THROW</parameter> option:
373
374<programlisting>
375postgres=# WAIT FOR LSN '0/306EE20' WITH (TIMEOUT '100ms', NO_THROW);
376 status
377---------
378 timeout
379(1 row)
380</programlisting>
381  </para>
