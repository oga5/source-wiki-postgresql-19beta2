39 <refsect1>
40  <title>Description</title>
41
42  <para>
43   <command>REPACK</command> reclaims storage occupied by dead
44   tuples. Unlike <command>VACUUM</command>, it does so by rewriting the
45   entire contents of the table specified
46   by <replaceable class="parameter">table_name</replaceable> into a new disk
47   file with no extra space (except for the space guaranteed by
48   the <literal>fillfactor</literal> storage parameter), allowing unused space
49   to be returned to the operating system.
50  </para>
51
52  <para>
53   Without
54   a <replaceable class="parameter">table_name</replaceable>, <command>REPACK</command>
55   processes every table and materialized view in the current database that
56   the current user has the <literal>MAINTAIN</literal> privilege on. This
57   form of <command>REPACK</command> cannot be executed inside a transaction
58   block.  Also, this form is not allowed if
59   the <literal>CONCURRENTLY</literal> option is used.
60  </para>
61
62  <para>
63   If a <literal>USING INDEX</literal> clause is specified, the rows are
64   physically reordered based on information from an index.  Please see the
65   notes on clustering below.
66  </para>
67
68  <para>
69   When a table is being repacked, an <literal>ACCESS EXCLUSIVE</literal> lock
70   is acquired on it. This prevents any other database operations (both reads
71   and writes) from operating on the table until the <command>REPACK</command>
72   is finished. If you want to keep the table accessible during the repacking,
73   consider using the <literal>CONCURRENTLY</literal> option.
74  </para>
75
76  <refsect2 id="sql-repack-notes-on-clustering" xreflabel="Notes on Clustering">
77   <title>Notes on Clustering</title>
78
79   <para>
80    If the <literal>USING INDEX</literal> clause is specified, the rows in
81    the table are stored in the order that the index specifies;
82    <firstterm>clustering</firstterm>, because rows are physically clustered
83    afterwards.
84    If an index name is specified in the command, the order implied by that
85    index is used, and that index is configured as the index to cluster on.
86    (This also applies to an index given to the <command>CLUSTER</command>
87    command.)
88    If no index name is specified, then the index that has
89    been configured as the index to cluster on is used; an
90    error is thrown if none has.
91    An index can be set manually using <command>ALTER TABLE ... CLUSTER ON</command>,
92    and reset with <command>ALTER TABLE ... SET WITHOUT CLUSTER</command>.
93   </para>
94
95   <para>
96    If no table name is specified in <command>REPACK USING INDEX</command>,
97    all tables which have a clustering index defined and which the calling
98    user has privileges for are processed.
99   </para>
100
101   <para>
102    Clustering is a one-time operation: when the table is
103    subsequently updated, the changes are not clustered.  That is, no attempt
104    is made to store new or updated rows according to their index order.  (If
105    one wishes, one can periodically recluster by issuing the command again.
106    Also, setting the table's <literal>fillfactor</literal> storage parameter
107    to less than 100% can aid in preserving cluster ordering during updates,
108    since updated rows are kept on the same page if enough space is available
109    there.)
110   </para>
111
112   <para>
113    In cases where you are accessing single rows randomly within a table, the
114    actual order of the data in the table is unimportant. However, if you tend
115    to access some data more than others, and there is an index that groups
116    them together, you will benefit from using clustering.  If
117    you are requesting a range of indexed values from a table, or a single
118    indexed value that has multiple rows that match,
119    clustering will help because once the index identifies the
120    table page for the first row that matches, all other rows that match are
121    probably already on the same table page, and so you save disk accesses and
122    speed up the query.
123   </para>
124
125   <para>
126    <command>REPACK</command> can re-sort the table using either an index scan
127    on the specified index (if the index is a b-tree), or a sequential scan
128    followed by sorting.  It will attempt to choose the method that will be
129    faster, based on planner cost parameters and available statistical
130    information.
131   </para>
132
133   <para>
134    Because the planner records statistics about the ordering of tables, it is
135    advisable to
136    run <link linkend="sql-analyze"><command>ANALYZE</command></link> on the
137    newly repacked table.  Otherwise, the planner might make poor choices of
138    query plans.
139   </para>
140  </refsect2>

142  <refsect2 id="sql-repack-notes-on-resources" xreflabel="Notes on Resources">
143   <title>Notes on Resources</title>
144
145   <para>
146    When an index scan or a sequential scan without sort is used, a temporary
147    copy of the table is created that contains the table data in the index
148    order.  Temporary copies of each index on the table are created as well.
149    Therefore, you need free space on disk at least equal to the sum of the
150    table size and the index sizes.
151   </para>
152
153   <para>
154    When a sequential scan and sort is used, a temporary sort file is also
155    created, so that the peak temporary space requirement is as much as double
156    the table size, plus the index sizes.  This method is often faster than
157    the index scan method, but if the disk space requirement is intolerable,
158    you can disable this choice by temporarily setting
159    <xref linkend="guc-enable-sort"/> to <literal>off</literal>.
160   </para>
161
162   <para>
163    It is advisable to set <xref linkend="guc-maintenance-work-mem"/> to a
164    reasonably large value (but not more than the amount of RAM you can
165    dedicate to the <command>REPACK</command> operation) before repacking.
166   </para>
167  </refsect2>

174  <variablelist>
175   <varlistentry>
176    <term><replaceable class="parameter">table_name</replaceable></term>
177    <listitem>
178     <para>
179      The name (possibly schema-qualified) of a table.
180     </para>
181    </listitem>
182   </varlistentry>
183
184   <varlistentry>
185    <term><replaceable class="parameter">column_name</replaceable></term>
186    <listitem>
187     <para>
188      The name of a specific column to analyze. Defaults to all columns.
189      If a column list is specific, <literal>ANALYZE</literal> must also
190      be specified.
191     </para>
192    </listitem>
193   </varlistentry>
194
195   <varlistentry>
196    <term><replaceable class="parameter">index_name</replaceable></term>
197    <listitem>
198     <para>
199      The name of an index.
200     </para>
201    </listitem>
202   </varlistentry>
203
204   <varlistentry>
205    <term><literal>CONCURRENTLY</literal></term>
206    <listitem>
207     <para>
208      Allow other transactions to use the table while it is being repacked.
209     </para>
210
211     <para>
212      Internally, <command>REPACK</command> copies the contents of the table
213      (ignoring dead tuples) into a new file, sorted by the specified index,
214      and also creates a new file for each index. Then it swaps the old and
215      new files for the table and all the indexes, and deletes the old
216      files. The <literal>ACCESS EXCLUSIVE</literal> lock is needed to make
217      sure that the old files do not change during the processing because the
218      changes would get lost due to the swap.
219     </para>
220
221     <para>
222      With the <literal>CONCURRENTLY</literal> option, the <literal>ACCESS
223      EXCLUSIVE</literal> lock is only acquired to swap the table and index
224      files. The data changes that took place during the creation of the new
225      table and index files are captured using logical decoding
226      (<xref linkend="logicaldecoding"/>) and applied before
227      the <literal>ACCESS EXCLUSIVE</literal> lock is requested. Thus the lock
228      is typically held only for the time needed to swap the files, which
229      should be pretty short. However, the time might still be noticeable if
230      too many data changes have been done to the table while
231      <command>REPACK</command> was waiting for the lock: those changes must
232      be processed just before the files are swapped, while the
233      <literal>ACCESS EXCLUSIVE</literal> lock is being held.
234     </para>
235
236     <para>
237      Note that <command>REPACK</command> with the
238      <literal>CONCURRENTLY</literal> option does not try to order the rows
239      inserted into the table after the repacking started. Also
240      note <command>REPACK</command> might fail to complete due to DDL
241      commands executed on the table by other transactions during the
242      repacking.
243     </para>
244
245     <note>
246      <para>
247       In addition to the temporary space requirements explained in
248       <xref linkend="sql-repack-notes-on-resources"/>,
249       the <literal>CONCURRENTLY</literal> option can add to the usage of
250       temporary space a bit more. The reason is that other transactions can
251       perform DML operations which cannot be applied to the new file until
252       <command>REPACK</command> has copied all the existing tuples from the
253       old file. Thus the tuples inserted into the old file during the copying
254       are also stored separately in a temporary file, until they can be
255       processed.
256      </para>
257     </note>
258
259     <para>
260      The <literal>CONCURRENTLY</literal> option cannot be used in the
261      following cases:
262
263      <itemizedlist>
264       <listitem>
265        <para>
266          The table is <literal>UNLOGGED</literal>.
267        </para>
268       </listitem>
269
270       <listitem>
271        <para>
272          The table is partitioned.
273        </para>
274       </listitem>
275
276       <listitem>
277        <para>
278         The table lacks a primary key and index-based replica identity.
279        </para>
280       </listitem>
281
282       <listitem>
283        <para>
284          The table is a system catalog or a <acronym>TOAST</acronym> table.
285        </para>
286       </listitem>
287
288       <listitem>
289        <para>
290         <command>REPACK</command> is executed inside a transaction block.
291        </para>
292       </listitem>
293
294       <listitem>
295        <para>
296         The <link linkend="guc-max-repack-replication-slots"><varname>max_repack_replication_slots</varname></link>
297         configuration parameter does not allow for the creation of an
298         additional replication slot.
299        </para>
300       </listitem>
301      </itemizedlist>
302     </para>
303
304     <warning>
305      <para>
306       <command>REPACK</command> with the <literal>CONCURRENTLY</literal>
307       option is not MVCC-safe, see <xref linkend="mvcc-caveats"/> for
308       details.
309      </para>
310     </warning>
311
312    </listitem>
313   </varlistentry>

352 <refsect1>
353  <title>Notes</title>
354
355   <para>
356    To repack a table, one must have the <literal>MAINTAIN</literal> privilege
357    on the table.
358   </para>
359
360   <para>
361    While <command>REPACK</command> is running, the <xref
362    linkend="guc-search-path"/> is temporarily changed to <literal>pg_catalog,
363    pg_temp</literal>.
364   </para>
365
366  <para>
367    Each backend running <command>REPACK</command> will report its progress
368    in the <structname>pg_stat_progress_repack</structname> view. See
369    <xref linkend="repack-progress-reporting"/> for details.
370  </para>
371
372   <para>
373    Repacking a partitioned table repacks each of its partitions. If an index
374    is specified, each partition is repacked using the partition of that
375    index. <command>REPACK</command> on a partitioned table cannot be executed
376    inside a transaction block.
377   </para>
378
379 </refsect1>

381 <refsect1>
382  <title>Examples</title>
383
384  <para>
385   Repack the table <literal>employees</literal>:
386<programlisting>
387REPACK employees;
388</programlisting>
389  </para>
390
391  <para>
392   Repack the table <literal>employees</literal> on the basis of its
393   index <literal>employees_ind</literal> (since an index is specified, this is
394   effectively clustering):
395<programlisting>
396REPACK employees USING INDEX employees_ind;
397</programlisting>
398  </para>
399
400  <para>
401   Repack the <literal>employees</literal> table following the same index
402   as was used before, in concurrent mode:
403<programlisting>
404REPACK (CONCURRENTLY) employees USING INDEX;
405</programlisting>
406  </para>
407
408  <para>
409   Repack the table <literal>cases</literal> on physical ordering,
410   running an <command>ANALYZE</command> on the given columns once
411   repacking is done, showing informational messages:
412<programlisting>
413REPACK (ANALYZE, VERBOSE) cases (district, case_nr);
414</programlisting>
415  </para>
416
417  <para>
418   Repack all tables in the database on which you have
419   the <literal>MAINTAIN</literal> privilege:
420<programlisting>
421REPACK;
422</programlisting>
423  </para>
424
425  <para>
426   Repack all tables for which a clustering index has previously been
427   configured on which you have the <literal>MAINTAIN</literal> privilege,
428   showing informational messages:
429<programlisting>
430REPACK (VERBOSE) USING INDEX;
431</programlisting>
432  </para>
