40 <refsect1>
41  <title>Description</title>
42
43  <para>
44   <application>pg_rewind</application> is a tool for synchronizing a PostgreSQL cluster
45   with another copy of the same cluster, after the clusters' timelines have
46   diverged. A typical scenario is to bring an old primary server back online
47   after failover as a standby that follows the new primary.
48  </para>
49
50  <para>
51   After a successful rewind, the state of the target data directory is
52   analogous to a base backup of the source data directory. Unlike taking
53   a new base backup or using a tool like <application>rsync</application>,
54   <application>pg_rewind</application> does not require comparing or copying
55   unchanged relation blocks in the cluster:
56  </para>
57  <itemizedlist>
58   <listitem>
59    <para>
60     Only changed blocks from existing relation files are copied.
61    </para>
62   </listitem>
63   <listitem>
64    <para>
65     WAL segments prior to the point where the source and target servers
66     have diverged are not copied. WAL segments generated after the source
67     and target servers have diverged are copied in full.
68    </para>
69   </listitem>
70   <listitem>
71    <para>
72     All other files, including new relation files and configuration files,
73     are copied in full.
74    </para>
75   </listitem>
76  </itemizedlist>
77  <para>
78   As such, the rewind operation is significantly faster than other
79   approaches when the database is large and only a small fraction of blocks
80   differ between the clusters.
81  </para>
82
83  <para>
84   <application>pg_rewind</application> examines the timeline histories of the source
85   and target clusters to determine the point where they diverged, and
86   expects to find WAL in the target cluster's <filename>pg_wal</filename> directory
87   reaching all the way back to the point of divergence. The point of divergence
88   can be found either on the target timeline, the source timeline, or their common
89   ancestor. In the typical failover scenario where the target cluster was
90   shut down soon after the divergence, this is not a problem, but if the
91   target cluster ran for a long time after the divergence, its old WAL
92   files might no longer be present. In this case, you can manually copy them
93   from the WAL archive to the <filename>pg_wal</filename> directory, or run
94   <application>pg_rewind</application> with the <literal>-c</literal> option to
95   automatically retrieve them from the WAL archive. The use of
96   <application>pg_rewind</application> is not limited to failover, e.g.,  a standby
97   server can be promoted, run some write transactions, and then rewound
98   to become a standby again.
99  </para>
100
101  <para>
102   After running <application>pg_rewind</application>, WAL replay needs to
103   complete for the data directory to be in a consistent state. When the
104   target server is started again it will enter archive recovery and replay
105   all WAL generated in the source server from the last checkpoint before
106   the point of divergence. If some of the WAL was no longer available in the
107   source server when <application>pg_rewind</application> was run, and
108   therefore could not be copied by the <application>pg_rewind</application>
109   session, it must be made available when the target server is started.
110   This can be done by creating a <filename>recovery.signal</filename> file
111   in the target data directory and by configuring a suitable
112   <xref linkend="guc-restore-command"/> in
113   <filename>postgresql.conf</filename>.
114  </para>
115
116  <para>
117   <application>pg_rewind</application> requires that the target server either has
118   the <xref linkend="guc-wal-log-hints"/> option enabled
119   in <filename>postgresql.conf</filename> or data checksums enabled when
120   the cluster was initialized with <application>initdb</application> (the
121   default).  <xref linkend="guc-full-page-writes"/> must also be set to
122   <literal>on</literal>, but is enabled by default.
123  </para>
124
125  <warning>
126   <title>Warning: Failures While Rewinding</title>
127   <para>
128    If <application>pg_rewind</application> fails while processing, then
129    the data folder of the target is likely not in a state that can be
130    recovered.  In such a case, taking a new fresh backup is recommended.
131   </para>
132
133   <para>
134    As <application>pg_rewind</application> copies configuration files
135    entirely from the source, it may be required to correct the configuration
136    used for recovery before restarting the target server, especially if
137    the target is reintroduced as a standby of the source. If you restart
138    the server after the rewind operation has finished but without configuring
139    recovery, the target may again diverge from the primary.
140   </para>
141
142   <para>
143    <application>pg_rewind</application> will fail immediately if it finds
144    files it cannot write directly to.  This can happen for example when
145    the source and the target server use the same file mapping for read-only
146    SSL keys and certificates.  If such files are present on the target server
147    it is recommended to remove them before running
148    <application>pg_rewind</application>.  After doing the rewind, some of
149    those files may have been copied from the source, in which case it may
150    be necessary to remove the data copied and restore back the set of links
151    used before the rewind.
152   </para>
153  </warning>

157  <title>Options</title>
158
159   <para>
160    <application>pg_rewind</application> accepts the following command-line
161    arguments:
162
163    <variablelist>
164     <varlistentry>
165      <term><option>-D <replaceable class="parameter">datadir</replaceable></option></term>
166      <term><option>--target-pgdata=<replaceable class="parameter">datadir</replaceable></option></term>
167      <listitem>
168       <para>
169        This option specifies the target data directory that is synchronized
170        with the source. The target server must be shut down cleanly before
171        running <application>pg_rewind</application>
172       </para>
173      </listitem>
174     </varlistentry>
175
176     <varlistentry>
177      <term><option>--source-pgdata=<replaceable class="parameter">datadir</replaceable></option></term>
178      <listitem>
179       <para>
180        Specifies the file system path to the data directory of the source
181        server to synchronize the target with. This option requires the
182        source server to be cleanly shut down.
183       </para>
184      </listitem>
185     </varlistentry>
186
187     <varlistentry>
188      <term><option>--source-server=<replaceable class="parameter">connstr</replaceable></option></term>
189      <listitem>
190       <para>
191        Specifies a libpq connection string to connect to the source
192        <productname>PostgreSQL</productname> server to synchronize the target
193        with. The connection must be a normal (non-replication) connection
194        with a role having sufficient permissions to execute the functions
195        used by <application>pg_rewind</application> on the source server
196        (see Notes section for details) or a superuser role.  This option
197        requires the source server to be running and accepting connections.
198       </para>
199      </listitem>
200     </varlistentry>
201
202     <varlistentry>
203      <term><option>-R</option></term>
204      <term><option>--write-recovery-conf</option></term>
205      <listitem>
206       <para>
207        Create <filename>standby.signal</filename> and append connection
208        settings to <filename>postgresql.auto.conf</filename> in the output
209        directory.  The dbname will be recorded only if the dbname was
210        specified explicitly in the connection string or <link linkend="libpq-envars">
211        environment variable</link>. <literal>--source-server</literal> is
212        mandatory with this option.
213       </para>
214      </listitem>
215     </varlistentry>

217     <varlistentry>
218      <term><option>-n</option></term>

288       </para>
289      </listitem>
290     </varlistentry>

292     <varlistentry>
293      <term><option>--no-ensure-shutdown</option></term>
294      <listitem>
295       <para>
296        <application>pg_rewind</application> requires that the target server
297        is cleanly shut down before rewinding. By default, if the target server
298        is not shut down cleanly, <application>pg_rewind</application> starts
299        the target server in single-user mode to complete crash recovery first,
300        and stops it.
301        By passing this option, <application>pg_rewind</application> skips
302        this and errors out immediately if the server is not cleanly shut
303        down. Users are expected to handle the situation themselves in that
304        case.
305       </para>

316        links for the WAL directory and each configured tablespace.
317       </para>

320        operating system to synchronize the whole file systems that contain the
321        data directory, the WAL files, and each tablespace.  See
322        <xref linkend="guc-recovery-init-sync-method"/> for information about
323        the caveats to be aware of when using <literal>syncfs</literal>.

327       </para>

364 <refsect1>
365  <title>Notes</title>
366
367  <para>
368   When executing <application>pg_rewind</application> using an online
369   cluster as source, a role having sufficient permissions to execute the
370   functions used by <application>pg_rewind</application> on the source
371   cluster can be used instead of a superuser.  Here is how to create such
372   a role, named <literal>rewind_user</literal> here:
373<programlisting>
374CREATE USER rewind_user LOGIN;
375GRANT EXECUTE ON FUNCTION pg_catalog.pg_ls_dir(text, boolean, boolean) TO rewind_user;
376GRANT EXECUTE ON FUNCTION pg_catalog.pg_stat_file(text, boolean) TO rewind_user;
377GRANT EXECUTE ON FUNCTION pg_catalog.pg_read_binary_file(text) TO rewind_user;
378GRANT EXECUTE ON FUNCTION pg_catalog.pg_read_binary_file(text, bigint, bigint, boolean) TO rewind_user;
379</programlisting>
380  </para>
381
382  <refsect2>
383   <title>How It Works</title>
384
385   <para>
386    The basic idea is to copy all file system-level changes from the source
387    cluster to the target cluster:
388   </para>
389
390   <procedure>
391    <step>
392     <para>
393      Scan the WAL log of the target cluster, starting from the last
394      checkpoint before the point where the source cluster's timeline
395      history forked off from the target cluster. For each WAL record,
396      record each data block that was touched. This yields a list of all
397      the data blocks that were changed in the target cluster, after the
398      source cluster forked off. If some of the WAL files are no longer
399      available, try re-running <application>pg_rewind</application> with
400      the <option>-c</option> option to search for the missing files in
401      the WAL archive.
402     </para>
403    </step>
404    <step>
405     <para>
406      Copy all those changed blocks from the source cluster to
407      the target cluster, either using direct file system access
408      (<option>--source-pgdata</option>) or SQL (<option>--source-server</option>).
409      Relation files are now in a state equivalent to the moment of the last
410      completed checkpoint prior to the point at which the WAL timelines of the
411      source and target diverged plus the current state on the source of any
412      blocks changed on the target after that divergence.
413     </para>
414    </step>
415    <step>
416     <para>
417      Copy all other files, including new relation files, WAL segments,
418      <filename>pg_xact</filename>, and configuration files from the source
419      cluster to the target cluster. Similarly to base backups, the contents
420      of the directories <filename>pg_dynshmem/</filename>,
421      <filename>pg_notify/</filename>, <filename>pg_replslot/</filename>,
422      <filename>pg_serial/</filename>, <filename>pg_snapshots/</filename>,
423      <filename>pg_stat_tmp/</filename>, and <filename>pg_subtrans/</filename>
424      are omitted from the data copied from the source cluster. The files
425      <filename>backup_label</filename>,
426      <filename>tablespace_map</filename>,
427      <filename>pg_internal.init</filename>,
428      <filename>postmaster.opts</filename>,
429      <filename>postmaster.pid</filename> and
430      <filename>.DS_Store</filename> as well as any file or directory
431      beginning with <filename>pgsql_tmp</filename>, are omitted.
432     </para>
433    </step>
434    <step>
435     <para>
436      Create a <filename>backup_label</filename> file to begin WAL replay at
437      the checkpoint created at failover and configure the
438      <filename>pg_control</filename> file with a minimum consistency LSN
439      defined as the result of <literal>pg_current_wal_insert_lsn()</literal>
440      when rewinding from a live source or the last checkpoint LSN when
441      rewinding from a stopped source.
442     </para>
443    </step>
444    <step>
445     <para>
446      When starting the target, <productname>PostgreSQL</productname> replays
447      all the required WAL, resulting in a data directory in a consistent
448      state.
449     </para>
450    </step>
451   </procedure>
