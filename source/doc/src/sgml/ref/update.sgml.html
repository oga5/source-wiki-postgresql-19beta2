25UPDATE [ ONLY ] <replaceable class="parameter">table_name</replaceable> [ * ]

44 <refsect1>
45  <title>Description</title>
46
47  <para>
48   <command>UPDATE</command> changes the values of the specified
49   columns in all rows that satisfy the condition. Only the columns to
50   be modified need be mentioned in the <literal>SET</literal> clause;
51   columns not explicitly modified retain their previous values.
52  </para>
53
54  <para>
55   There are two ways to modify a table using information contained in
56   other tables in the database: using sub-selects, or specifying
57   additional tables in the <literal>FROM</literal> clause. Which
58   technique is more appropriate depends on the specific
59   circumstances.
60  </para>
61
62  <para>
63   The optional <literal>RETURNING</literal> clause causes <command>UPDATE</command>
64   to compute and return value(s) based on each row actually updated.
65   Any expression using the table's columns, and/or columns of other
66   tables mentioned in <literal>FROM</literal>, can be computed.
67   By default, the new (post-update) values of the table's columns are used,
68   but it is also possible to request the old (pre-update) values.
69   The syntax of the <literal>RETURNING</literal> list is identical to that of the
70   output list of <command>SELECT</command>.
71  </para>
72
73  <para>
74   If the <literal>FOR PORTION OF</literal> clause is used, the update will
75   only affect rows that overlap the given portion.  Furthermore, if a row's
76   application time extends outside the <literal>FOR PORTION OF</literal>
77   bounds, then the update will only change the application time within those
78   bounds.  In effect, only the history targeted by <literal>FOR PORTION
79   OF</literal> is updated, and no moments outside.  Furthermore, after a row
80   is updated, the range or multirange is first shrunk so that its application
81   time no longer extends beyond the targeted <literal>FOR PORTION
82   OF</literal> bounds.  Then, new <glossterm
83   linkend="glossary-temporal-leftovers">temporal leftovers</glossterm> might
84   be inserted: rows whose range or multirange receives the remaining
85   application time outside the targeted
86   <literal>FROM</literal>/<literal>TO</literal> bounds, with the original
87   values in their other columns.  For range columns, there will be zero to
88   two inserted records, depending on whether the original application time
89   was completely updated, extended before/after the change, or both.
90   Multiranges never require two temporal leftovers, because one value can
91   always contain whatever application time remains.
92  </para>
93
94  <para>
95   You must have the <literal>UPDATE</literal> privilege on the table,
96   or at least on the column(s) that are listed to be updated.
97   You must also have the <literal>SELECT</literal>
98   privilege on any column whose values are read in the
99   <replaceable class="parameter">expressions</replaceable> or
100   <replaceable class="parameter">condition</replaceable>.
101   When <literal>FOR PORTION OF</literal> is used, the secondary inserts do
102   not require <literal>INSERT</literal> privilege on the table.  (This is
103   because conceptually no new information is being added; the inserted rows
104   only preserve existing data about the untargeted time period.)
105  </para>

351 <refsect1>
352  <title>Outputs</title>
353
354  <para>
355   On successful completion, an <command>UPDATE</command> command returns a command
356   tag of the form
357<screen>
358UPDATE <replaceable class="parameter">count</replaceable>
359</screen>
360   The <replaceable class="parameter">count</replaceable> is the number
361   of rows updated, including matched rows whose values did not change.
362   Note that the number may be less than the number of rows that matched
363   the <replaceable class="parameter">condition</replaceable> when
364   updates were suppressed by a <literal>BEFORE UPDATE</literal> trigger.  If
365   <replaceable class="parameter">count</replaceable> is 0, no rows were
366   updated by the query (this is not considered an error).
367   If <literal>FOR PORTION OF</literal> was used, the
368   <replaceable class="parameter">count</replaceable> does not include
369   <glossterm linkend="glossary-temporal-leftovers">temporal leftovers</glossterm>
370   that were inserted.
371  </para>
372
373  <para>
374   If the <command>UPDATE</command> command contains a <literal>RETURNING</literal>
375   clause, the result will be similar to that of a <command>SELECT</command>
376   statement containing the columns and values defined in the
377   <literal>RETURNING</literal> list, computed over the row(s) updated by the
378   command. If <literal>FOR PORTION OF</literal> was used, the
379   <literal>RETURNING</literal> clause gives one result for each updated row,
380   but does not include inserted
381   <glossterm linkend="glossary-temporal-leftovers">temporal leftovers</glossterm>.
382   The value of the application-time column matches the new value of the updated
383   row(s).
384  </para>

387 <refsect1>
388  <title>Notes</title>
389
390  <para>
391   When a <literal>FROM</literal> clause is present, what essentially happens
392   is that the target table is joined to the tables mentioned in the
393   <replaceable>from_item</replaceable> list, and each output row of the join
394   represents an update operation for the target table.  When using
395   <literal>FROM</literal> you should ensure that the join
396   produces at most one output row for each row to be modified.  In
397   other words, a target row shouldn't join to more than one row from
398   the other table(s).  If it does, then only one of the join rows
399   will be used to update the target row, but which one will be used
400   is not readily predictable.
401  </para>
402
403  <para>
404   Because of this indeterminacy, referencing other tables only within
405   sub-selects is safer, though often harder to read and slower than
406   using a join.
407  </para>
408
409  <para>
410   In the case of a partitioned table, updating a row might cause it to no
411   longer satisfy the partition constraint of the containing partition. In that
412   case, if there is some other partition in the partition tree for which this
413   row satisfies its partition constraint, then the row is moved to that
414   partition. If there is no such partition, an error will occur.  Behind the
415   scenes, the row movement is actually a <command>DELETE</command> and
416   <command>INSERT</command> operation.
417  </para>
418
419  <para>
420   There is a possibility that a concurrent <command>UPDATE</command> or
421   <command>DELETE</command> on the row being moved will get a serialization
422   failure error.  Suppose session 1 is performing an <command>UPDATE</command>
423   on a partition key, and meanwhile a concurrent session 2 for which this
424   row is visible performs an <command>UPDATE</command> or
425   <command>DELETE</command> operation on this row.  In such case,
426   session 2's <command>UPDATE</command> or <command>DELETE</command> will
427   detect the row movement and raise a serialization failure error (which
428   always returns with an SQLSTATE code '40001').  Applications may wish to
429   retry the transaction if this occurs.  In the usual case where the table
430   is not partitioned, or where there is no row movement, session 2 would
431   have identified the newly updated row and carried out the
432   <command>UPDATE</command>/<command>DELETE</command> on this new row
433    version.
434  </para>
435
436  <para>
437   Note that while rows can be moved from local partitions to a foreign-table
438   partition (provided the foreign data wrapper supports tuple routing), they
439   cannot be moved from a foreign-table partition to another partition.
440  </para>
441
442  <para>
443   An attempt of moving a row from one partition to another will fail if a
444   foreign key is found to directly reference an ancestor of the source
445   partition that is not the same as the ancestor that's mentioned in the
446   <command>UPDATE</command> query.
447  </para>
448
449  <para>
450   When <literal>FOR PORTION OF</literal> is used, this can result in users
451   who don't have <literal>INSERT</literal> privileges firing
452   <literal>INSERT</literal> triggers.  This should be considered when
453   using <literal>SECURITY DEFINER</literal> trigger functions.
454  </para>

457 <refsect1>
458  <title>Examples</title>
459
460  <para>
461   Change the word <literal>Drama</literal> to <literal>Dramatic</literal> in the
462   column <structfield>kind</structfield> of the table <structname>films</structname>:
463
464<programlisting>
465UPDATE films SET kind = 'Dramatic' WHERE kind = 'Drama';
466</programlisting>
467  </para>
468
469  <para>
470   Adjust temperature entries and reset precipitation to its default
471   value in one row of the table <structname>weather</structname>:
472
473<programlisting>
474UPDATE weather SET temp_lo = temp_lo+1, temp_hi = temp_lo+15, prcp = DEFAULT
475  WHERE city = 'San Francisco' AND date = '2003-07-03';
476</programlisting>
477  </para>
478
479  <para>
480   Perform the same operation and return the updated entries, and the old
481   precipitation value:
482
483<programlisting>
484UPDATE weather SET temp_lo = temp_lo+1, temp_hi = temp_lo+15, prcp = DEFAULT
485  WHERE city = 'San Francisco' AND date = '2003-07-03'
486  RETURNING temp_lo, temp_hi, prcp, old.prcp AS old_prcp;
487</programlisting>
488  </para>
489
490  <para>
491   Use the alternative column-list syntax to do the same update:
492<programlisting>
493UPDATE weather SET (temp_lo, temp_hi, prcp) = (temp_lo+1, temp_lo+15, DEFAULT)
494  WHERE city = 'San Francisco' AND date = '2003-07-03';
495</programlisting>
496  </para>
497
498  <para>
499   Increment the sales count of the salesperson who manages the
500   account for Acme Corporation, using the <literal>FROM</literal>
501   clause syntax:
502<programlisting>
503UPDATE employees SET sales_count = sales_count + 1 FROM accounts
504  WHERE accounts.name = 'Acme Corporation'
505  AND employees.id = accounts.sales_person;
506</programlisting>
507  </para>
508
509  <para>
510   Perform the same operation, using a sub-select in the
511   <literal>WHERE</literal> clause:
512<programlisting>
513UPDATE employees SET sales_count = sales_count + 1 WHERE id =
514  (SELECT sales_person FROM accounts WHERE name = 'Acme Corporation');
515</programlisting>
516  </para>
517
518  <para>
519   Update contact names in an accounts table to match the currently assigned
520   salespeople:
521<programlisting>
522UPDATE accounts SET (contact_first_name, contact_last_name) =
523    (SELECT first_name, last_name FROM employees
524     WHERE employees.id = accounts.sales_person);
525</programlisting>
526   A similar result could be accomplished with a join:
527<programlisting>
528UPDATE accounts SET contact_first_name = first_name,
529                    contact_last_name = last_name
530  FROM employees WHERE employees.id = accounts.sales_person;
531</programlisting>
532   However, the second query may give unexpected results
533   if <structname>employees</structname>.<structfield>id</structfield> is not a unique key, whereas
534   the first query is guaranteed to raise an error if there are multiple
535   <structfield>id</structfield> matches.  Also, if there is no match for a particular
536   <structname>accounts</structname>.<structfield>sales_person</structfield> entry, the first query
537   will set the corresponding name fields to NULL, whereas the second query
538   will not update that row at all.
539  </para>
540
541  <para>
542   Update statistics in a summary table to match the current data:
543<programlisting>
544UPDATE summary s SET (sum_x, sum_y, avg_x, avg_y) =
545    (SELECT sum(x), sum(y), avg(x), avg(y) FROM data d
546     WHERE d.group_id = s.group_id);
547</programlisting>
548  </para>
549
550  <para>
551   Attempt to insert a new stock item along with the quantity of stock. If
552   the item already exists, instead update the stock count of the existing
553   item. To do this without failing the entire transaction, use savepoints:
554<programlisting>
555BEGIN;
556-- other operations
557SAVEPOINT sp1;
558INSERT INTO wines VALUES('Chateau Lafite 2003', '24');
559-- Assume the above fails because of a unique key violation,
560-- so now we issue these commands:
561ROLLBACK TO sp1;
562UPDATE wines SET stock = stock + 24 WHERE winename = 'Chateau Lafite 2003';
563-- continue with other operations, and eventually
564COMMIT;
565</programlisting>
566  </para>
567
568  <para>
569   Change the <structfield>kind</structfield> column of the table
570   <structname>films</structname> in the row on which the cursor
571   <literal>c_films</literal> is currently positioned:
572<programlisting>
573UPDATE films SET kind = 'Dramatic' WHERE CURRENT OF c_films;
574</programlisting>
575  </para>
576
577  <para>
578   An example of a temporal update:
579<programlisting>
580UPDATE products
581  FOR PORTION OF valid_at FROM '2023-09-01' TO '2025-03-01'
582  SET price = 12.00
583  WHERE product_no = 5;
584</programlisting>
585  </para>
586
587  <para id="update-limit">
588   Updates affecting many rows can have negative effects on system
589   performance, such as table bloat, increased replica lag, and increased
590   lock contention.  In such situations it can make sense to perform the
591   operation in smaller batches, possibly with a <command>VACUUM</command>
592   operation on the table between batches.  While there is
593   no <literal>LIMIT</literal> clause for <command>UPDATE</command>, it is
594   possible to get a similar effect through the use of
595   a <link linkend="queries-with">Common Table Expression</link> and a
596   self-join.  With the standard <productname>PostgreSQL</productname>
597   table access method, a self-join on the system
598   column <link linkend="ddl-system-columns-ctid">ctid</link> is very
599   efficient:
600<programlisting>
601WITH exceeded_max_retries AS (
602  SELECT w.ctid FROM work_item AS w
603    WHERE w.status = 'active' AND w.num_retries &gt; 10
604    ORDER BY w.retry_timestamp
605    FOR UPDATE
606    LIMIT 5000
607)
608UPDATE work_item SET status = 'failed'
609  FROM exceeded_max_retries AS emr
610  WHERE work_item.ctid = emr.ctid;
611</programlisting>
612   This command will need to be repeated until no rows remain to be updated.
613   (This use of <structfield>ctid</structfield> is only safe because
614   the query is repeatedly run, avoiding the problem of changed
615   <structfield>ctid</structfield>s.)
616   Use of an <literal>ORDER BY</literal> clause allows the command to
617   prioritize which rows will be updated; it can also prevent deadlock
618   with other update operations if they use the same ordering.
619   If lock contention is a concern, then <literal>SKIP LOCKED</literal>
620   can be added to the <acronym>CTE</acronym> to prevent multiple commands
621   from updating the same row.  However, then a
622   final <command>UPDATE</command> without <literal>SKIP LOCKED</literal>
623   or <literal>LIMIT</literal> will be needed to ensure that no matching
624   rows were overlooked.
625  </para>

629  <title>Compatibility</title>
630
631  <para>
632   This command conforms to the <acronym>SQL</acronym> standard, except
633   that the <literal>FROM</literal> and <literal>RETURNING</literal> clauses
634   are <productname>PostgreSQL</productname> extensions, as is the ability
635   to use <literal>WITH</literal> with <command>UPDATE</command>.
636  </para>
637
638  <para>
639   Some other database systems offer a <literal>FROM</literal> option in which
640   the target table is supposed to be listed again within <literal>FROM</literal>.
641   That is not how <productname>PostgreSQL</productname> interprets
642   <literal>FROM</literal>.  Be careful when porting applications that use this
643   extension.
644  </para>
645
646  <para>
647   According to the standard, the source value for a parenthesized sub-list of
648   target column names can be any row-valued expression yielding the correct
649   number of columns.  <productname>PostgreSQL</productname> only allows the
650   source value to be a <link linkend="sql-syntax-row-constructors">row
651   constructor</link> or a sub-<literal>SELECT</literal>.  An individual column's
652   updated value can be specified as <literal>DEFAULT</literal> in the
653   row-constructor case, but not inside a sub-<literal>SELECT</literal>.
654  </para>
