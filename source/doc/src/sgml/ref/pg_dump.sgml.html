35 <refsect1 id="pg-dump-description">
36  <title>Description</title>
37
38  <para>
39   <application>pg_dump</application> is a utility for exporting a
40   <productname>PostgreSQL</productname> database. It makes consistent
41   exports even if the database is being used concurrently.
42   <application>pg_dump</application> does not block other users
43   accessing the database (readers or writers).
44   Note, however, that except in simple cases,
45   <application>pg_dump</application> is generally not the right choice for
46   taking regular backups of production databases.  See <xref
47   linkend="backup"/> for further discussion.
48  </para>
49
50  <para>
51   <application>pg_dump</application> only dumps a single database.
52   To export an entire cluster, or to export global objects that are
53   common to all databases in a cluster (such as roles and tablespaces),
54   use <xref linkend="app-pg-dumpall"/>.
55  </para>
56
57  <para>
58   Dumps can be output in script or archive file formats. Script
59   dumps are plain-text files containing the SQL commands required
60   to reconstruct the database to the state it was in at the time it was
61   saved. To restore from such a script, feed it to <xref
62   linkend="app-psql"/>. Script files
63   can be used to reconstruct the database even on other machines and
64   other architectures; with some modifications, even on other SQL
65   database products.
66  </para>
67
68  <para>
69   The alternative archive file formats must be used with
70   <xref linkend="app-pgrestore"/> to rebuild the database.  They
71   allow <application>pg_restore</application> to be selective about
72   what is restored, or even to reorder the items prior to being
73   restored.
74   The archive file formats are designed to be portable across
75   architectures.
76  </para>
77
78  <para>
79   When used with one of the archive file formats and combined with
80   <application>pg_restore</application>,
81   <application>pg_dump</application> provides a flexible archival and
82   transfer mechanism. <application>pg_dump</application> can be used to
83   export an entire database, then <application>pg_restore</application>
84   can be used to examine the archive and/or select which parts of the
85   database are to be restored. The most flexible output file formats are
86   the <quote>custom</quote> format (<option>-Fc</option>) and the
87   <quote>directory</quote> format (<option>-Fd</option>). They allow
88   for selection and reordering of all archived items, support parallel
89   restoration, and are compressed by default. The <quote>directory</quote>
90   format is the only format that supports parallel dumps.
91  </para>
92
93  <para>
94   While running <application>pg_dump</application>, one should examine the
95   output for any warnings (printed on standard error), especially in
96   light of the limitations listed below.
97  </para>
98
99  <warning>
100   <para>
101    Restoring a dump causes the destination to execute arbitrary code of the
102    source superusers' choice.  Partial dumps and partial restores do not limit
103    that.  If the source superusers are not trusted, the dumped SQL statements
104    must be inspected before restoring.  Non-plain-text dumps can be inspected
105    by using <application>pg_restore</application>'s <option>--file</option>
106    option.  Note that the client running the dump and restore need not trust
107    the source or destination superusers.
108   </para>
109  </warning>

378     <varlistentry>
379      <term><option>-j <replaceable class="parameter">njobs</replaceable></option></term>
380      <term><option>--jobs=<replaceable class="parameter">njobs</replaceable></option></term>
381      <listitem>
382       <para>
383        Run the dump in parallel by dumping <replaceable class="parameter">njobs</replaceable>
384        tables simultaneously. This option may reduce the time needed to perform the dump but it also
385        increases the load on the database server. You can only use this option with the
386        directory output format because this is the only output format where multiple processes
387        can write their data at the same time.
388       </para>
389       <para><application>pg_dump</application> will open <replaceable class="parameter">njobs</replaceable>
390        + 1 connections to the database, so make sure your <xref linkend="guc-max-connections"/>
391        setting is high enough to accommodate all connections.
392       </para>
393       <para>
394        Requesting exclusive locks on database objects while running a parallel dump could
395        cause the dump to fail. The reason is that the <application>pg_dump</application> leader process
396        requests shared locks (<link linkend="locking-tables">ACCESS SHARE</link>) on the
397        objects that the worker processes are going to dump later in order to
398        make sure that nobody deletes them and makes them go away while the dump is running.
399        If another client then requests an exclusive lock on a table, that lock will not be
400        granted but will be queued waiting for the shared lock of the leader process to be
401        released. Consequently any other access to the table will not be granted either and
402        will queue after the exclusive lock request. This includes the worker process trying
403        to dump the table. Without any precautions this would be a classic deadlock situation.
404        To detect this conflict, the <application>pg_dump</application> worker process requests another
405        shared lock using the <literal>NOWAIT</literal> option. If the worker process is not granted
406        this shared lock, somebody else must have requested an exclusive lock in the meantime
407        and there is no way to continue with the dump, so <application>pg_dump</application> has no choice
408        but to abort the dump.
409       </para>
410       <para>
411        To perform a parallel dump, the database server needs to support
412        synchronized snapshots, a feature that was introduced in
413        <productname>PostgreSQL</productname> 9.2 for primary servers and 10
414        for standbys. With this feature, database clients can ensure they see
415        the same data set even though they use different connections.
416        <command>pg_dump -j</command> uses multiple database connections; it
417        connects to the database once with the leader process and once again
418        for each worker job. Without the synchronized snapshot feature, the
419        different worker jobs wouldn't be guaranteed to see the same data in
420        each connection, which could lead to an inconsistent backup.
421       </para>
422      </listitem>

1655 <refsect1 id="pg-dump-notes">
1656  <title>Notes</title>
1657
1658  <para>
1659   If your database cluster has any local additions to the <literal>template1</literal> database,
1660   be careful to restore the output of <application>pg_dump</application> into a
1661   truly empty database; otherwise you are likely to get errors due to
1662   duplicate definitions of the added objects.  To make an empty database
1663   without any local additions, copy from <literal>template0</literal> not <literal>template1</literal>,
1664   for example:
1665<programlisting>
1666CREATE DATABASE foo WITH TEMPLATE template0;
1667</programlisting>
1668  </para>
1669
1670  <para>
1671   When options <option>-e</option>, <option>-n</option> or <option>-t</option>
1672   are specified, <application>pg_dump</application> makes no attempt to dump
1673   any other database objects that the selected object(s) might depend upon.
1674   Therefore, there is no guarantee that the results of a dump so generated
1675   can be successfully restored by themselves into a clean database.
1676   For example, if a table whose definition includes a foreign key is
1677   specified to be restored, the table referenced by the foreign key is
1678   not automatically restored.
1679  </para>
1680
1681  <para>
1682   When a dump without schema is chosen and the option <option>--disable-triggers</option>
1683   is used, <application>pg_dump</application> emits commands
1684   to disable triggers on user tables before inserting the data,
1685   and then commands to re-enable them after the data has been
1686   inserted.  If the restore is stopped in the middle, the system
1687   catalogs might be left in the wrong state.
1688  </para>
1689
1690  <para>
1691   When creating an archive (non-text) output file, it is advisable not to
1692   restrict the set of database objects dumped, but instead plan to apply
1693   any desired object filtering when reading the archive
1694   with <application>pg_restore</application>.  This will preserve
1695   flexibility and possibly avoid problems at restore time; for details
1696   see the <xref linkend="app-pgrestore"/> documentation.
1697   In particular, dumping table data without the corresponding table
1698   definition (via <option>--no-schema</option> and related options) is
1699   not recommended.
1700  </para>
1701
1702  <para>
1703   When <option>--statistics</option> is specified,
1704   <command>pg_dump</command> will include most optimizer statistics in the
1705   resulting dump file.  This does not include all statistics, such as
1706   custom statistics added by an extension, or statistics collected by the
1707   cumulative statistics system. Therefore, it may still be useful to
1708   run <command>ANALYZE</command> after restoring from a dump file to ensure
1709   optimal performance; see <xref linkend="vacuum-for-statistics"/> and <xref
1710   linkend="autovacuum"/> for more information.
1711  </para>
1712
1713  <para>
1714   Because <application>pg_dump</application> is used to transfer data
1715   to newer versions of <productname>PostgreSQL</productname>, the output of
1716   <application>pg_dump</application> can be expected to load into
1717   <productname>PostgreSQL</productname> server versions newer than
1718   <application>pg_dump</application>'s version.  <application>pg_dump</application> can also
1719   dump from <productname>PostgreSQL</productname> servers older than its own version.
1720   (Currently, servers back to version 9.2 are supported.)
1721   However, <application>pg_dump</application> cannot dump from
1722   <productname>PostgreSQL</productname> servers newer than its own major version;
1723   it will refuse to even try, rather than risk making an invalid dump.
1724   Also, it is not guaranteed that <application>pg_dump</application>'s output can
1725   be loaded into a server of an older major version &mdash; not even if the
1726   dump was taken from a server of that version.  Loading a dump file
1727   into an older server may require manual editing of the dump file
1728   to remove syntax not understood by the older server.
1729   Use of the <option>--quote-all-identifiers</option> option is recommended
1730   in cross-version cases, as it can prevent problems arising from varying
1731   reserved-word lists in different <productname>PostgreSQL</productname> versions.
1732  </para>
1733
1734  <para>
1735   When dumping logical replication subscriptions,
1736   <application>pg_dump</application> will generate <command>CREATE
1737   SUBSCRIPTION</command> commands that use the <literal>connect = false</literal>
1738   option, so that restoring the subscription does not make remote connections
1739   for creating a replication slot or for initial table copy.  That way, the
1740   dump can be restored without requiring network access to the remote
1741   servers.  It is then up to the user to reactivate the subscriptions in a
1742   suitable way.  If the involved hosts have changed, the connection
1743   information might have to be changed.  It might also be appropriate to
1744   truncate the target tables before initiating a new full table copy.  If users
1745   intend to copy initial data during refresh they must create the slot with
1746   <literal>two_phase = false</literal>.  After the initial sync, the
1747   <link linkend="sql-createsubscription-params-with-two-phase"><literal>two_phase</literal></link>
1748   option will be automatically enabled by the subscriber if the subscription
1749   had been originally created with <literal>two_phase = true</literal> option.
1750  </para>
1751
1752  <para>
1753   It is generally recommended to use the <option>-X</option>
1754   (<option>--no-psqlrc</option>) option when restoring a database from a
1755   plain-text <application>pg_dump</application> script to ensure a clean
1756   restore process and prevent potential conflicts with
1757   non-default <application>psql</application> configurations.
1758  </para>
