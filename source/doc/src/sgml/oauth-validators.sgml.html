3<chapter id="oauth-validators">
4 <title>OAuth Validator Modules</title>
5 <indexterm zone="oauth-validators">
6  <primary>OAuth Validators</primary>
7 </indexterm>
8 <para>
9  <productname>PostgreSQL</productname> provides infrastructure for creating
10  custom modules to perform server-side validation of OAuth bearer tokens.
11  Because OAuth implementations vary so wildly, and bearer token validation is
12  heavily dependent on the issuing party, the server cannot check the token
13  itself; validator modules provide the integration layer between the server
14  and the OAuth provider in use.
15 </para>
16 <para>
17  OAuth validator modules must at least consist of an initialization function
18  (see <xref linkend="oauth-validator-init"/>) and the required callback for
19  performing validation (see <xref linkend="oauth-validator-callback-validate"/>).
20 </para>
21 <warning>
22  <para>
23   Since a misbehaving validator might let unauthorized users into the database,
24   correct implementation is crucial for server safety. See
25   <xref linkend="oauth-validator-design"/> for design considerations.
26  </para>
27 </warning>
28
29 <sect1 id="oauth-validator-design">
30  <title>Safely Designing a Validator Module</title>
31  <warning>
32   <para>
33    Read and understand the entirety of this section before implementing a
34    validator module. A malfunctioning validator is potentially worse than no
35    authentication at all, both because of the false sense of security it
36    provides, and because it may contribute to attacks against other pieces of
37    an OAuth ecosystem.
38   </para>
39  </warning>
40
41  <sect2 id="oauth-validator-design-responsibilities">
42   <title>Validator Responsibilities</title>
43   <para>
44    Although different modules may take very different approaches to token
45    validation, implementations generally need to perform three separate
46    actions:
47   </para>
48   <variablelist>
49    <varlistentry>
50     <term>Validate the Token</term>
51     <listitem>
52      <para>
53       The validator must first ensure that the presented token is in fact a
54       valid Bearer token for use in client authentication. The correct way to
55       do this depends on the provider, but it generally involves either
56       cryptographic operations to prove that the token was created by a trusted
57       party (offline validation), or the presentation of the token to that
58       trusted party so that it can perform validation for you (online
59       validation).
60      </para>
61      <para>
62       Online validation, usually implemented via
63       <ulink url="https://datatracker.ietf.org/doc/html/rfc7662">OAuth Token
64       Introspection</ulink>, requires fewer steps of a validator module and
65       allows central revocation of a token in the event that it is stolen
66       or misissued. However, it does require the module to make at least one
67       network call per authentication attempt (all of which must complete
68       within the configured <xref linkend="guc-authentication-timeout"/>).
69       Additionally, your provider may not provide introspection endpoints for
70       use by external resource servers.
71      </para>
72      <para>
73       Offline validation is much more involved, typically requiring a validator
74       to maintain a list of trusted signing keys for a provider and then
75       check the token's cryptographic signature along with its contents.
76       Implementations must follow the provider's instructions to the letter,
77       including any verification of issuer ("where is this token from?"),
78       audience ("who is this token for?"), and validity period ("when can this
79       token be used?"). Since there is no communication between the module and
80       the provider, tokens cannot be centrally revoked using this method;
81       offline validator implementations may wish to place restrictions on the
82       maximum length of a token's validity period.
83      </para>
84      <para>
85       If the token cannot be validated, the module should immediately fail.
86       Further authentication/authorization is pointless if the bearer token
87       wasn't issued by a trusted party.
88      </para>
89     </listitem>
90    </varlistentry>
91    <varlistentry>
92     <term>Authorize the Client</term>
93     <listitem>
94      <para>
95       Next the validator must ensure that the end user has given the client
96       permission to access the server on their behalf. This generally involves
97       checking the scopes that have been assigned to the token, to make sure
98       that they cover database access for the current HBA parameters.
99      </para>
100      <para>
101       The purpose of this step is to prevent an OAuth client from obtaining a
102       token under false pretenses. If the validator requires all tokens to
103       carry scopes that cover database access, the provider should then loudly
104       prompt the user to grant that access during the flow. This gives them the
105       opportunity to reject the request if the client isn't supposed to be
106       using their credentials to connect to databases.
107      </para>
108      <para>
109       While it is possible to establish client authorization without explicit
110       scopes by using out-of-band knowledge of the deployed architecture, doing
111       so removes the user from the loop, which prevents them from catching
112       deployment mistakes and allows any such mistakes to be exploited
113       silently. Access to the database must be tightly restricted to only
114       trusted clients
115       <footnote>
116        <para>
117         That is, "trusted" in the sense that the OAuth client and the
118         <productname>PostgreSQL</productname> server are controlled by the same
119         entity. Notably, the Device Authorization client flow supported by
120         libpq does not usually meet this bar, since it's designed for use by
121         public/untrusted clients.
122        </para>
123       </footnote>
124       if users are not prompted for additional scopes.
125      </para>
126      <para>
127       Even if authorization fails, a module may choose to continue to pull
128       authentication information from the token for use in auditing and
129       debugging.
130      </para>
131     </listitem>
132    </varlistentry>
133    <varlistentry>
134     <term>Authenticate the End User</term>
135     <listitem>
136      <para>
137       Finally, the validator should determine a user identifier for the token,
138       either by asking the provider for this information or by extracting it
139       from the token itself, and return that identifier to the server (which
140       will then make a final authorization decision using the HBA
141       configuration). This identifier will be available within the session via
142       <link linkend="functions-info-session-table"><function>system_user</function></link>
143       and recorded in the server logs if <xref linkend="guc-log-connections"/>
144       is enabled.
145      </para>
146      <para>
147       Different providers may record a variety of different authentication
148       information for an end user, typically referred to as
149       <emphasis>claims</emphasis>. Providers usually document which of these
150       claims are trustworthy enough to use for authorization decisions and
151       which are not. (For instance, it would probably not be wise to use an
152       end user's full name as the identifier for authentication, since many
153       providers allow users to change their display names arbitrarily.)
154       Ultimately, the choice of which claim (or combination of claims) to use
155       comes down to the provider implementation and application requirements.
156      </para>
157      <para>
158       Note that anonymous/pseudonymous login is possible as well, by enabling
159       usermap delegation; see
160       <xref linkend="oauth-validator-design-usermap-delegation"/>.
161      </para>
162     </listitem>
163    </varlistentry>
164   </variablelist>
165  </sect2>

167  <sect2 id="oauth-validator-design-guidelines">
168   <title>General Coding Guidelines</title>
169   <para>
170    Developers should keep the following in mind when implementing token
171    validation:
172   </para>
173   <variablelist>
174    <varlistentry>
175     <term>Token Confidentiality</term>
176     <listitem>
177      <para>
178       Modules should not write tokens, or pieces of tokens, into the server
179       log. This is true even if the module considers the token invalid; an
180       attacker who confuses a client into communicating with the wrong provider
181       should not be able to retrieve that (otherwise valid) token from the
182       disk.
183      </para>
184      <para>
185       Implementations that send tokens over the network (for example, to
186       perform online token validation with a provider) must authenticate the
187       peer and ensure that strong transport security is in use.
188      </para>
189     </listitem>
190    </varlistentry>
191    <varlistentry>
192     <term>Logging</term>
193     <listitem>
194      <para>
195       To simply log the reason for a validation failure, modules may set the
196       freeform <structfield>error_detail</structfield> field during the
197       <link linkend="oauth-validator-callback-validate">validate callback</link>.
198       (<xref linkend="error-style-guide"/> has guidelines for writing good
199       <literal>DETAIL</literal> messages.) <structfield>error_detail</structfield>
200       is printed only to the server log, as part of the final authentication
201       failure message, and it is not shared with the client.
202      </para>
203      <para>
204       Modules may also use the same <link linkend="error-message-reporting">logging
205       facilities</link> as standard extensions; however, the rules for emitting
206       log entries to the client are subtly different during the authentication
207       phase of the connection. Generally speaking, modules should log
208       problems at the <symbol>COMMERROR</symbol> level and return
209       normally, instead of using <symbol>ERROR</symbol>/<symbol>FATAL</symbol>
210       to unwind the stack, to avoid leaking information to unauthenticated
211       clients.
212      </para>
213     </listitem>
214    </varlistentry>
215    <varlistentry>
216     <term>Interruptibility</term>
217     <listitem>
218      <para>
219       Modules must remain interruptible by signals so that the server can
220       correctly handle authentication timeouts and shutdown signals from
221       <application>pg_ctl</application>. For example, blocking calls on sockets
222       should generally be replaced with code that handles both socket events
223       and interrupts without races (see <function>WaitLatchOrSocket()</function>,
224       <function>WaitEventSetWait()</function>, et al), and long-running loops
225       should periodically call <function>CHECK_FOR_INTERRUPTS()</function>.
226       Failure to follow this guidance may result in unresponsive backend
227       sessions.
228      </para>
229     </listitem>
230    </varlistentry>
231    <varlistentry>
232     <term>Testing</term>
233     <listitem>
234      <para>
235       The breadth of testing an OAuth system is well beyond the scope of this
236       documentation, but at minimum, negative testing should be considered
237       mandatory. It's trivial to design a module that lets authorized users in;
238       the whole point of the system is to keep unauthorized users out.
239      </para>
240     </listitem>
241    </varlistentry>
242    <varlistentry>
243     <term>Documentation</term>
244     <listitem>
245      <para>
246       Validator implementations should document the contents and format of the
247       authenticated ID that is reported to the server for each end user, since
248       DBAs may need to use this information to construct pg_ident maps. (For
249       instance, is it an email address? an organizational ID number? a UUID?)
250       They should also document whether or not it is safe to use the module in
251       <symbol>delegate_ident_mapping=1</symbol> mode, and what additional
252       configuration is required in order to do so.
253      </para>
254      <para>
255       If an implementation provides <link linkend="oauth-validator-hba">custom
256       HBA options</link>, the names and syntax of those options should be
257       documented as well.
258      </para>
259     </listitem>
260    </varlistentry>
261   </variablelist>
262  </sect2>

264  <sect2 id="oauth-validator-design-usermap-delegation">
265   <title>Authorizing Users (Usermap Delegation)</title>
266   <para>
267    The standard deliverable of a validation module is the user identifier,
268    which the server will then compare to any configured
269    <link linkend="auth-username-maps"><filename>pg_ident.conf</filename>
270    mappings</link> and determine whether the end user is authorized to connect.
271    However, OAuth is itself an authorization framework, and tokens may carry
272    information about user privileges. For example, a token may be associated
273    with the organizational groups that a user belongs to, or list the roles
274    that a user may assume, and duplicating that knowledge into local usermaps
275    for every server may not be desirable.
276   </para>
277   <para>
278    To bypass username mapping entirely, and have the validator module assume
279    the additional responsibility of authorizing user connections, the HBA may
280    be configured with <xref linkend="auth-oauth-delegate-ident-mapping"/>.
281    The module may then use token scopes or an equivalent method to decide
282    whether the user is allowed to connect under their desired role. The user
283    identifier will still be recorded by the server, but it plays no part in
284    determining whether to continue the connection.
285   </para>
286   <para>
287    Using this scheme, authentication itself is optional. As long as the module
288    reports that the connection is authorized, login will continue even if there
289    is no recorded user identifier at all. This makes it possible to implement
290    anonymous or pseudonymous access to the database, where the third-party
291    provider performs all necessary authentication but does not provide any
292    user-identifying information to the server. (Some providers may create an
293    anonymized ID number that can be recorded instead, for later auditing.)
294   </para>
295   <para>
296    Usermap delegation provides the most architectural flexibility, but it turns
297    the validator module into a single point of failure for connection
298    authorization. Use with caution.
299   </para>
300  </sect2>

303 <sect1 id="oauth-validator-init">
304  <title>Initialization Functions</title>
305  <indexterm zone="oauth-validator-init">
306   <primary>_PG_oauth_validator_module_init</primary>
307  </indexterm>
308  <para>
309   OAuth validator modules are dynamically loaded from the shared
310   libraries listed in <xref linkend="guc-oauth-validator-libraries"/>.
311   Modules are loaded on demand when requested from a login in progress.
312   The normal library search path is used to locate the library. To
313   provide the validator callbacks and to indicate that the library is an OAuth
314   validator module a function named
315   <function>_PG_oauth_validator_module_init</function> must be provided. The
316   return value of the function must be a pointer to a struct of type
317   <structname>OAuthValidatorCallbacks</structname>, which contains a magic
318   number and pointers to the module's token validation functions. The returned
319   pointer must be of server lifetime, which is typically achieved by defining
320   it as a <literal>static const</literal> variable in global scope.
321<programlisting>
322typedef struct OAuthValidatorCallbacks
323{
324    uint32        magic;            /* must be set to PG_OAUTH_VALIDATOR_MAGIC */
325
326    ValidatorStartupCB startup_cb;
327    ValidatorShutdownCB shutdown_cb;
328    ValidatorValidateCB validate_cb;
329} OAuthValidatorCallbacks;
330
331typedef const OAuthValidatorCallbacks *(*OAuthValidatorModuleInit) (void);
332</programlisting>
333
334   Only the <function>validate_cb</function> callback is required, the others
335   are optional.
336  </para>
337 </sect1>

339 <sect1 id="oauth-validator-callbacks">
340  <title>OAuth Validator Callbacks</title>
341  <para>
342   OAuth validator modules implement their functionality by defining a set of
343   callbacks. The server will call them as required to process the
344   authentication request from the user.
345  </para>
346
347  <sect2 id="oauth-validator-callback-startup">
348   <title>Startup Callback</title>
349   <para>
350    The <function>startup_cb</function> callback is executed directly after
351    loading the module. This callback can be used to set up local state,
352    define <link linkend="oauth-validator-hba">custom HBA options</link>, and
353    perform additional initialization if required. If the validator module
354    has state it can use <structfield>state->private_data</structfield> to
355    store it.
356
357<programlisting>
358typedef void (*ValidatorStartupCB) (ValidatorModuleState *state);
359</programlisting>
360   </para>
361  </sect2>
362
363  <sect2 id="oauth-validator-callback-validate">
364   <title>Validate Callback</title>
365   <para>
366    The <function>validate_cb</function> callback is executed during the OAuth
367    exchange when a user attempts to authenticate using OAuth.  Any state set in
368    previous calls will be available in <structfield>state->private_data</structfield>.
369
370<programlisting>
371typedef bool (*ValidatorValidateCB) (const ValidatorModuleState *state,
372                                     const char *token, const char *role,
373                                     ValidatorModuleResult *result);
374</programlisting>
375
376    <replaceable>token</replaceable> will contain the bearer token to validate.
377    <application>PostgreSQL</application> has ensured that the token is well-formed syntactically, but no
378    other validation has been performed.  <replaceable>role</replaceable> will
379    contain the role the user has requested to log in as.  The callback must
380    set output parameters in the <literal>result</literal> struct, which is
381    defined as below:
382
383<programlisting>
384typedef struct ValidatorModuleResult
385{
386    bool        authorized;
387    char       *authn_id;
388    char       *error_detail;
389} ValidatorModuleResult;
390</programlisting>
391
392    The connection will only proceed if the module sets
393    <structfield>result->authorized</structfield> to <literal>true</literal>.  To
394    authenticate the user, the authenticated user name (as determined using the
395    token) shall be palloc'd and returned in the <structfield>result->authn_id</structfield>
396    field.  Alternatively, <structfield>result->authn_id</structfield> may be set to
397    NULL if the token is valid but the associated user identity cannot be
398    determined.  If the validator returns <literal>true</literal> and
399    sets <structfield>result->authn_id</structfield> then the identity appears
400    in the server log when <xref linkend="guc-log-connections"/> includes
401    <literal>authentication</literal>.  This happens before authorization and
402    will log authentication even if the connection is later rejected due to
403    authorization.
404   </para>
405   <para>
406    A validator may return <literal>false</literal> to signal an internal error,
407    in which case the connection fails.  Otherwise the validator should return
408    <literal>true</literal> to indicate that it has processed the token and made
409    an authorization decision.
410   </para>
411   <para>
412    In either failure case (validation error or internal error) the module may
413    store a user-readable reason for the failure in <structfield>result->error_detail</structfield>.
414    This will be printed to the server logs (not sent to the client) as a
415    <literal>DETAIL</literal> entry for the authentication failure. The memory
416    pointed to by <structfield>error_detail</structfield> may be either palloc'd
417    or of static duration. <structfield>error_detail</structfield> is ignored
418    on success.
419   </para>
420   <para>
421    The behavior after <function>validate_cb</function> returns depends on the
422    specific HBA setup.  Normally, the <structfield>result->authn_id</structfield> user
423    name must exactly match the role that the user is logging in as.  (This
424    behavior may be modified with a usermap.)  But when authenticating against
425    an HBA rule with <literal>delegate_ident_mapping</literal> turned on,
426    <productname>PostgreSQL</productname> will not perform any checks on the value of
427    <structfield>result->authn_id</structfield> at all; in this case it is up to the
428    validator to ensure that the token carries enough privileges for the user to
429    log in under the indicated <replaceable>role</replaceable>.
430   </para>
431  </sect2>
432
433  <sect2 id="oauth-validator-callback-shutdown">
434   <title>Shutdown Callback</title>
435   <para>
436    The <function>shutdown_cb</function> callback is executed when the server
437    backend has finished validating tokens for the connection. If the validator
438    module has any allocated state, this callback should free it to avoid
439    resource leaks.
440<programlisting>
441typedef void (*ValidatorShutdownCB) (ValidatorModuleState *state);
442</programlisting>
443   </para>
444  </sect2>

448 <sect1 id="oauth-validator-hba">
449  <title>Custom HBA Options</title>
450
451  <para>
452   Like other preloaded libraries, validator modules may define
453   <link linkend="runtime-config-custom">custom GUC parameters</link> for user
454   configuration in <filename>postgresql.conf</filename>. However, it may be
455   desirable to configure behavior at a more granular level (say, for a
456   particular issuer or a group of users) instead of globally.
457  </para>
458
459  <para>
460   Beginning in <productname>PostgreSQL</productname> 19, validator
461   implementations may define custom options for use inside
462   <filename>pg_hba.conf</filename>. These options are then
463   <link linkend="auth-oauth-validator-option">made available</link> to the user
464   as <literal>validator.<replaceable>option</replaceable></literal>. The API
465   for registering and retrieving custom options is described below.
466  </para>
467
468  <sect2 id="oauth-validator-hba-api">
469   <title>Options API</title>
470    <para>
471     Modules register custom HBA option names during the <function>startup_cb</function>
472     callback, using <function>RegisterOAuthHBAOptions()</function>:
473
474<programlisting>
475/*
476 * Register a list of custom option names for use in pg_hba.conf. For each name
477 * "foo" registered here, that option will be provided as "validator.foo" in
478 * the HBA.
479 *
480 * Valid option names consist of alphanumeric ASCII, underscore (_), and hyphen
481 * (-). Invalid option names will be ignored with a WARNING logged at
482 * connection time.
483 *
484 * This function may only be called during the startup_cb callback. Multiple
485 * calls are permitted, which will append to the existing list of registered
486 * options; options cannot be unregistered.
487 *
488 * Parameters:
489 *
490 * - state: the state pointer passed to the startup_cb callback
491 * - num:   the number of options in the opts array
492 * - opts:  an array of null-terminated option names to register
493 *
494 * The list of option names is copied internally, and the opts array is not
495 * required to remain valid after the call.
496 */
497void RegisterOAuthHBAOptions(ValidatorModuleState *state, int num,
498                             const char *opts[]);
499</programlisting>
500    </para>
501
502    <para>
503     Each option's value, if set, may be later retrieved using
504     <function>GetOAuthHBAOption()</function>:
505
506<programlisting>
507/*
508 * Retrieve the string value of an HBA option which was registered via
509 * RegisterOAuthHBAOptions(). Usable only during validate_cb or shutdown_cb.
510 *
511 * If the user has set the corresponding option in pg_hba.conf, this function
512 * returns that value as a null-terminated string, which must not be modified
513 * or freed. NULL is returned instead if the user has not set this option, if
514 * the option name was not registered, or if this function is incorrectly called
515 * during the startup_cb.
516 *
517 * Parameters:
518 *
519 * - state:   the state pointer passed to the validate_cb/shutdown_cb callback
520 * - optname: the name of the option to retrieve
521 */
522const char *GetOAuthHBAOption(const ValidatorModuleState *state,
523                              const char *optname);
524</programlisting>
525    </para>
526
527    <para>
528     See <xref linkend="oauth-validator-hba-example-usage"/> for sample usage.
529    </para>
530  </sect2>
531
532  <sect2 id="oauth-validator-hba-limitations">
533   <title>Limitations</title>
534   <para>
535    <itemizedlist>
536     <listitem>
537      <para>
538       Option names are limited to ASCII alphanumeric characters,
539       underscores (<literal>_</literal>), and hyphens (<literal>-</literal>).
540      </para>
541     </listitem>
542     <listitem>
543      <para>
544       Option values are always freeform strings (in contrast to custom GUCs,
545       which support numerics, booleans, and enums).
546      </para>
547     </listitem>
548     <listitem>
549      <para>
550       Option names and values cannot be checked by the server during a reload of
551       the configuration. Any unregistered options in <filename>pg_hba.conf</filename>
552       will instead result in connection failures. It is the responsibility of
553       each module to document and verify the syntax of option values as needed.
554       <footnote>
555        <para>
556         If a module finds an invalid option value during <function>validate_cb</function>,
557         it's recommended to <link linkend="oauth-validator-callback-validate">signal
558         an internal error</link> by setting <structfield>result->error_detail</structfield>
559         to a description of the problem and returning <literal>false</literal>.
560        </para>
561       </footnote>
562      </para>
563     </listitem>
564    </itemizedlist>
565   </para>
566  </sect2>

568  <sect2 id="oauth-validator-hba-example-usage">
569   <title>Example Usage</title>
570
571   <para>
572    For a hypothetical module, the options <literal>foo</literal> and
573    <literal>bar</literal> could be registered as follows:
574
575<programlisting>
576static void
577validator_startup(ValidatorModuleState *state)
578{
579    static const char *opts[] = {
580        "foo",      /* description of access privileges */
581        "bar",      /* magic URL for additional administrator powers */
582    };
583
584    RegisterOAuthHBAOptions(state, lengthof(opts), opts);
585
586    /* ...other setup... */
587}
588</programlisting>
589   </para>
590
591   <para>
592    The following sample entries in <filename>pg_hba.conf</filename> can then
593    make use of these options:
594
595<programlisting>
596# TYPE   DATABASE   USER   ADDRESS    METHOD
597hostssl  postgres   admin  0.0.0.0/0  oauth issuer=https://admin.example.com \
598                                            scope="pg-admin openid email" \
599                                            map=oauth-email \
600                                            validator.foo="admin access" \
601                                            validator.bar=https://magic.example.com
602
603hostssl  postgres   all    0.0.0.0/0  oauth issuer=https://www.example.com \
604                                            scope="pg-user openid email" \
605                                            map=oauth-email \
606                                            validator.foo="user access"
607</programlisting>
608   </para>
609
610   <para>
611    The module can retrieve the option settings from the HBA during validation:
612
613<programlisting>
614static bool
615validate_token(const ValidatorModuleState *state,
616               const char *token, const char *role,
617               ValidatorModuleResult *res)
618{
619    const char *foo = GetOAuthHBAOption(state, "foo"); /* "admin access" or "user access" */
620    const char *bar = GetOAuthHBAOption(state, "bar"); /* "https://magic.example.com" or NULL */
621
622    if (bar &amp;&amp; !is_valid_url(bar))
623    {
624        res->error_detail = psprintf("validator.bar (\"%s\") is not a valid URL.", bar);
625        return false;
626    }
627
628    /* proceed to validate token */
629}
