3<chapter id="dml">
4 <title>Data Manipulation</title>
5
6 <para>
7  The previous chapter discussed how to create tables and other
8  structures to hold your data.  Now it is time to fill the tables
9  with data.  This chapter covers how to insert, update, and delete
10  table data.  The chapter
11  after this will finally explain how to extract your long-lost data
12  from the database.
13 </para>
14
15 <sect1 id="dml-insert">
16  <title>Inserting Data</title>
17
18  <indexterm zone="dml-insert">
19   <primary>inserting</primary>
20  </indexterm>
21
22  <indexterm zone="dml-insert">
23   <primary>INSERT</primary>
24  </indexterm>
25
26  <para>
27   When a table is created, it contains no data.  The first thing to
28   do before a database can be of much use is to insert data.  Data is
29   inserted one row at a time.  You can also insert more than one row
30   in a single command, but it is not possible to insert something that
31   is not a complete row.  Even if you know only some column values, a
32   complete row must be created.
33  </para>
34
35  <para>
36   To create a new row, use the <xref linkend="sql-insert"/>
37   command.  The command requires the
38   table name and column values.  For
39   example, consider the products table from <xref linkend="ddl"/>:
40<programlisting>
41CREATE TABLE products (
42    product_no integer,
43    name text,
44    price numeric
45);
46</programlisting>
47   An example command to insert a row would be:
48<programlisting>
49INSERT INTO products VALUES (1, 'Cheese', 9.99);
50</programlisting>
51   The data values are listed in the order in which the columns appear
52   in the table, separated by commas.  Usually, the data values will
53   be literals (constants), but scalar expressions are also allowed.
54  </para>
55
56  <para>
57   The above syntax has the drawback that you need to know the order
58   of the columns in the table.  To avoid this you can also list the
59   columns explicitly.  For example, both of the following commands
60   have the same effect as the one above:
61<programlisting>
62INSERT INTO products (product_no, name, price) VALUES (1, 'Cheese', 9.99);
63INSERT INTO products (name, price, product_no) VALUES ('Cheese', 9.99, 1);
64</programlisting>
65   Many users consider it good practice to always list the column
66   names.
67  </para>
68
69  <para>
70   If you don't have values for all the columns, you can omit some of
71   them.  In that case, the columns will be filled with their default
72   values.  For example:
73<programlisting>
74INSERT INTO products (product_no, name) VALUES (1, 'Cheese');
75INSERT INTO products VALUES (1, 'Cheese');
76</programlisting>
77   The second form is a <productname>PostgreSQL</productname>
78   extension.  It fills the columns from the left with as many values
79   as are given, and the rest will be defaulted.
80  </para>
81
82  <para>
83   For clarity, you can also request default values explicitly, for
84   individual columns or for the entire row:
85<programlisting>
86INSERT INTO products (product_no, name, price) VALUES (1, 'Cheese', DEFAULT);
87INSERT INTO products DEFAULT VALUES;
88</programlisting>
89  </para>
90
91  <para>
92   You can insert multiple rows in a single command:
93<programlisting>
94INSERT INTO products (product_no, name, price) VALUES
95    (1, 'Cheese', 9.99),
96    (2, 'Bread', 1.99),
97    (3, 'Milk', 2.99);
98</programlisting>
99  </para>
100
101  <para>
102   It is also possible to insert the result of a query (which might be no
103   rows, one row, or many rows):
104<programlisting>
105INSERT INTO products (product_no, name, price)
106  SELECT product_no, name, price FROM new_products
107    WHERE release_date = 'today';
108</programlisting>
109   This provides the full power of the SQL query mechanism (<xref
110   linkend="queries"/>) for computing the rows to be inserted.
111  </para>
112
113  <tip>
114   <para>
115    When inserting a lot of data at the same time, consider using
116    the <xref linkend="sql-copy"/> command.
117    It is not as flexible as the <xref linkend="sql-insert"/>
118    command, but is more efficient. Refer
119    to <xref linkend="populate"/> for more information on improving
120    bulk loading performance.
121   </para>
122  </tip>
123 </sect1>
124
125 <sect1 id="dml-update">
126  <title>Updating Data</title>
127
128  <indexterm zone="dml-update">
129   <primary>updating</primary>
130  </indexterm>
131
132  <indexterm zone="dml-update">
133   <primary>UPDATE</primary>
134  </indexterm>
135
136  <para>
137   The modification of data that is already in the database is
138   referred to as updating.  You can update individual rows, all the
139   rows in a table, or a subset of all rows.  Each column can be
140   updated separately; the other columns are not affected.
141  </para>
142
143  <para>
144   To update existing rows, use the <xref linkend="sql-update"/>
145   command.  This requires
146   three pieces of information:
147   <orderedlist spacing="compact">
148    <listitem>
149     <para>The name of the table and column to update</para>
150    </listitem>
151
152    <listitem>
153     <para>The new value of the column</para>
154    </listitem>
155
156    <listitem>
157     <para>Which row(s) to update</para>
158    </listitem>
159   </orderedlist>
160  </para>
161
162  <para>
163   Recall from <xref linkend="ddl"/> that SQL does not, in general,
164   provide a unique identifier for rows.  Therefore it is not
165   always possible to directly specify which row to update.
166   Instead, you specify which conditions a row must meet in order to
167   be updated.  Only if you have a primary key in the table (independent of
168   whether you declared it or not) can you reliably address individual rows
169   by choosing a condition that matches the primary key.
170   Graphical database access tools rely on this fact to allow you to
171   update rows individually.
172  </para>
173
174  <para>
175   For example, this command updates all products that have a price of
176   5 to have a price of 10:
177<programlisting>
178UPDATE products SET price = 10 WHERE price = 5;
179</programlisting>
180    This might cause zero, one, or many rows to be updated.  It is not
181    an error to attempt an update that does not match any rows.
182  </para>
183
184  <para>
185   Let's look at that command in detail. First is the key word
186   <literal>UPDATE</literal> followed by the table name.  As usual,
187   the table name can be schema-qualified, otherwise it is looked up
188   in the path.  Next is the key word <literal>SET</literal> followed
189   by the column name, an equal sign, and the new column value.  The
190   new column value can be any scalar expression, not just a constant.
191   For example, if you want to raise the price of all products by 10%
192   you could use:
193<programlisting>
194UPDATE products SET price = price * 1.10;
195</programlisting>
196   As you see, the expression for the new value can refer to the existing
197   value(s) in the row.  We also left out the <literal>WHERE</literal> clause.
198   If it is omitted, it means that all rows in the table are updated.
199   If it is present, only those rows that match the
200   <literal>WHERE</literal> condition are updated.  Note that the equals
201   sign in the <literal>SET</literal> clause is an assignment while
202   the one in the <literal>WHERE</literal> clause is a comparison, but
203   this does not create any ambiguity.  Of course, the
204   <literal>WHERE</literal> condition does
205   not have to be an equality test.  Many other operators are
206   available (see <xref linkend="functions"/>).  But the expression
207   needs to evaluate to a Boolean result.
208  </para>
209
210  <para>
211   You can update more than one column in an
212   <command>UPDATE</command> command by listing more than one
213   assignment in the <literal>SET</literal> clause.  For example:
214<programlisting>
215UPDATE mytable SET a = 5, b = 3, c = 1 WHERE a &gt; 0;
216</programlisting>
217  </para>
218 </sect1>

220 <sect1 id="dml-delete">
221  <title>Deleting Data</title>
222
223  <indexterm zone="dml-delete">
224   <primary>deleting</primary>
225  </indexterm>
226
227  <indexterm zone="dml-delete">
228   <primary>DELETE</primary>
229  </indexterm>
230
231  <para>
232   So far we have explained how to add data to tables and how to
233   change data.  What remains is to discuss how to remove data that is
234   no longer needed.  Just as adding data is only possible in whole
235   rows, you can only remove entire rows from a table.  In the
236   previous section we explained that SQL does not provide a way to
237   directly address individual rows.  Therefore, removing rows can
238   only be done by specifying conditions that the rows to be removed
239   have to match.  If you have a primary key in the table then you can
240   specify the exact row.  But you can also remove groups of rows
241   matching a condition, or you can remove all rows in the table at
242   once.
243  </para>
244
245  <para>
246   You use the <xref linkend="sql-delete"/>
247   command to remove rows; the syntax is very similar to the
248   <xref linkend="sql-update"/> command.  For instance, to remove all
249   rows from the products table that have a price of 10, use:
250<programlisting>
251DELETE FROM products WHERE price = 10;
252</programlisting>
253  </para>
254
255  <para>
256   If you simply write:
257<programlisting>
258DELETE FROM products;
259</programlisting>
260   then all rows in the table will be deleted!  Caveat programmer.
261  </para>
262 </sect1>
263
264 <sect1 id="dml-application-time-update-delete">
265  <title>Updating and Deleting Temporal Data</title>
266
267  <para>
268   Special syntax is available to update and delete from application-time
269   temporal tables (see <xref linkend="ddl-application-time" />).  (No extra
270   syntax is required to insert into them: the user just provides the
271   application time values like any other column.)  When updating or deleting,
272   the user can target a specific portion of history.  Only rows overlapping
273   that history are affected, and within those rows only the targeted history
274   is changed.  If a row contains more history beyond what is targeted, its
275   application time is reduced to fit within the targeted portion, and new
276   rows are inserted to preserve the history that was not targeted.
277  </para>
278
279  <para>
280   Recall the example table from <xref linkend="temporal-entities-figure" />,
281   containing this data:
282
283<programlisting>
284 product_no | price |        valid_at
285------------+-------+-------------------------
286          5 |  5.00 | [2020-01-01,2022-01-01)
287          5 |  8.00 | [2022-01-01,)
288          6 |  9.00 | [2021-01-01,2024-01-01)
289</programlisting>
290
291   A temporal update might look like this:
292
293<programlisting>
294UPDATE products
295  <emphasis>FOR PORTION OF valid_at FROM '2023-09-01' TO '2025-03-01'</emphasis>
296  SET price = 12.00
297  WHERE product_no = 5;
298</programlisting>
299
300   That command will update the second record for product 5.  It will set the
301   price to 12.00 and the application time to
302   <literal>[2023-09-01,2025-03-01)</literal>.  Then, since the row's
303   application time was originally <literal>[2022-01-01,)</literal>, the
304   command must insert two <glossterm
305   linkend="glossary-temporal-leftovers">temporal leftovers</glossterm>: one
306   for history before September 1, 2023, and another for history since March
307   1, 2025.  After the update, the table has four rows for product 5:
308
309<programlisting>
310 product_no | price |        valid_at
311------------+-------+-------------------------
312          5 |  5.00 | [2020-01-01,2022-01-01)
313          5 |  8.00 | [2022-01-01,2023-09-01)
314          5 | 12.00 | [2023-09-01,2025-03-01)
315          5 |  8.00 | [2025-03-01,)
316          6 |  9.00 | [2021-01-01,2024-01-01)
317</programlisting>
318
319   The new history could be plotted as in <xref linkend="temporal-update-figure"/>.
320  </para>
321
322  <figure id="temporal-update-figure">
323   <title>Temporal Update Example</title>
324   <mediaobject>
325    <imageobject>
326     <imagedata fileref="images/temporal-update.svg" format="SVG" width="100%"/>
327    </imageobject>
328   </mediaobject>
329  </figure>
330
331  <para>
332   Similarly, a specific portion of history may be targeted when deleting rows
333   from a table.  In that case, the original rows are removed, but new
334   <glossterm linkend="glossary-temporal-leftovers">temporal
335   leftovers</glossterm> are inserted to preserve the untouched history.  The
336   syntax for a temporal delete is:
337
338<programlisting>
339DELETE FROM products
340  <emphasis>FOR PORTION OF valid_at FROM '2021-08-01' TO '2023-09-01'</emphasis>
341  WHERE product_no = 5;
342</programlisting>
343
344   Continuing the example, this command would delete two records.  The
345   first record would yield a single temporal leftover, and the second
346   would be deleted entirely.  The rows in the table would now be:
347
348<programlisting>
349 product_no | price |        valid_at
350------------+-------+-------------------------
351          5 |  5.00 | [2020-01-01,2021-08-01)
352          5 | 12.00 | [2023-09-01,2025-03-01)
353          5 |  8.00 | [2025-03-01,)
354          6 |  9.00 | [2021-01-01,2024-01-01)
355</programlisting>
356
357   The new history could be plotted as in <xref linkend="temporal-delete-figure"/>.
358  </para>
359
360  <figure id="temporal-delete-figure">
361   <title>Temporal Delete Example</title>
362   <mediaobject>
363    <imageobject>
364     <imagedata fileref="images/temporal-delete.svg" format="SVG" width="100%"/>
365    </imageobject>
366   </mediaobject>
367  </figure>
368
369  <para>
370   Instead of using the <literal>FROM ... TO ...</literal> syntax, temporal
371   update/delete commands can also give the targeted range/multirange
372   directly, inside parentheses.  For example: <literal>DELETE FROM products
373   FOR PORTION OF valid_at ('[2028-01-01,)') ...</literal>.  This syntax is
374   required when application time is stored in a multirange column.
375  </para>
376
377  <para>
378   When application time is stored in a range type column, zero, one or two
379   temporal leftovers are produced by each row that is updated/deleted.  With
380   a multirange column, only zero or one temporal leftover is produced.  The
381   leftover bounds are computed using <literal>range_minus_multi</literal> and
382   <literal>multirange_minus_multi</literal> (see <xref
383   linkend="functions-range"/>).
384  </para>
385
386  <para>
387   The bounds given to <literal>FOR PORTION OF</literal> must be constant.
388   Functions like <literal>now()</literal> are allowed, but column references
389   are not.
390  </para>
391
392  <para>
393   When temporal leftovers are inserted, all <literal>INSERT</literal>
394   triggers are fired, but permission checks for inserting rows are
395   skipped.
396  </para>
397
398  <para>
399   In <literal>READ COMMITTED</literal> mode, temporal updates and deletes can
400   yield unexpected results when they concurrently touch the same row.  It is
401   possible to lose all or part of the second update or delete.  The scenario
402   is illustrated in <xref linkend="temporal-isolation-figure"/>.  Session 2
403   searches for rows to change, and it finds one that Session 1 has already
404   modified.  It waits for Session 1 to commit. Then it re-checks whether the
405   row still matches its search criteria (including the start/end times
406   targeted by <literal>FOR PORTION OF</literal>).  Session 1 may have changed
407   those times so that they no longer qualify.
408  </para>
409
410  <para>
411   In addition, the temporal leftovers inserted by Session 1 are not visible
412   within Session 2's transaction, because they are not yet committed.
413   Therefore there is nothing for Session 2 to update/delete: neither the
414   modified row nor the leftovers.  The portion of history that Session 2
415   intended to change is not affected.
416  </para>
417
418  <figure id="temporal-isolation-figure">
419   <title>Temporal Isolation Example</title>
420   <mediaobject>
421    <imageobject>
422     <imagedata fileref="images/temporal-isolation.svg" format="SVG" width="35%"/>
423    </imageobject>
424   </mediaobject>
425  </figure>
426
427  <para>
428   To solve these problems, precede every temporal update/delete with a
429   <literal>SELECT FOR UPDATE</literal> matching the same criteria (including
430   the targeted portion of application time).  That way the actual
431   update/delete doesn't begin until the lock is held, and all concurrent
432   leftovers will be visible.  In higher transaction isolation levels, this
433   lock is not required.
434  </para>

437 <sect1 id="dml-returning">
438  <title>Returning Data from Modified Rows</title>
439
440  <indexterm zone="dml-returning">
441   <primary>RETURNING</primary>
442  </indexterm>
443
444  <indexterm zone="dml-returning">
445   <primary>INSERT</primary>
446   <secondary>RETURNING</secondary>
447  </indexterm>
448
449  <indexterm zone="dml-returning">
450   <primary>UPDATE</primary>
451   <secondary>RETURNING</secondary>
452  </indexterm>
453
454  <indexterm zone="dml-returning">
455   <primary>DELETE</primary>
456   <secondary>RETURNING</secondary>
457  </indexterm>
458
459  <indexterm zone="dml-returning">
460   <primary>MERGE</primary>
461   <secondary>RETURNING</secondary>
462  </indexterm>
463
464  <para>
465   Sometimes it is useful to obtain data from modified rows while they are
466   being manipulated.  The <command>INSERT</command>, <command>UPDATE</command>,
467   <command>DELETE</command>, and <command>MERGE</command> commands all have an
468   optional <literal>RETURNING</literal> clause that supports this.  Use
469   of <literal>RETURNING</literal> avoids performing an extra database query to
470   collect the data, and is especially valuable when it would otherwise be
471   difficult to identify the modified rows reliably.
472  </para>
473
474  <para>
475   The allowed contents of a <literal>RETURNING</literal> clause are the same as
476   a <command>SELECT</command> command's output list
477   (see <xref linkend="queries-select-lists"/>).  It can contain column
478   names of the command's target table, or value expressions using those
479   columns.  A common shorthand is <literal>RETURNING *</literal>, which selects
480   all columns of the target table in order.
481  </para>
482
483  <para>
484   In an <command>INSERT</command>, the default data available to
485   <literal>RETURNING</literal> is
486   the row as it was inserted.  This is not so useful in trivial inserts,
487   since it would just repeat the data provided by the client.  But it can
488   be very handy when relying on computed default values.  For example,
489   when using a <link linkend="datatype-serial"><type>serial</type></link>
490   column to provide unique identifiers, <literal>RETURNING</literal> can return
491   the ID assigned to a new row:
492<programlisting>
493CREATE TABLE users (firstname text, lastname text, id serial PRIMARY KEY);
494
495INSERT INTO users (firstname, lastname) VALUES ('Joe', 'Cool') RETURNING id;
496</programlisting>
497   The <literal>RETURNING</literal> clause is also very useful
498   with <literal>INSERT ... SELECT</literal>.
499  </para>
500
501  <para>
502   In an <command>UPDATE</command>, the default data available to
503   <literal>RETURNING</literal> is
504   the new content of the modified row.  For example:
505<programlisting>
506UPDATE products SET price = price * 1.10
507  WHERE price &lt;= 99.99
508  RETURNING name, price AS new_price;
509</programlisting>
510  </para>
511
512  <para>
513   In a <command>DELETE</command>, the default data available to
514   <literal>RETURNING</literal> is
515   the content of the deleted row.  For example:
516<programlisting>
517DELETE FROM products
518  WHERE obsoletion_date = 'today'
519  RETURNING *;
520</programlisting>
521  </para>
522
523  <para>
524   In a <command>MERGE</command>, the default data available to
525   <literal>RETURNING</literal> is
526   the content of the source row plus the content of the inserted, updated, or
527   deleted target row.  Since it is quite common for the source and target to
528   have many of the same columns, specifying <literal>RETURNING *</literal>
529   can lead to a lot of duplicated columns, so it is often more useful to
530   qualify it so as to return just the source or target row.  For example:
531<programlisting>
532MERGE INTO products p USING new_products n ON p.product_no = n.product_no
533  WHEN NOT MATCHED THEN INSERT VALUES (n.product_no, n.name, n.price)
534  WHEN MATCHED THEN UPDATE SET name = n.name, price = n.price
535  RETURNING p.*;
536</programlisting>
537  </para>
538
539  <para>
540   In each of these commands, it is also possible to explicitly return the
541   old and new content of the modified row.  For example:
542<programlisting>
543UPDATE products SET price = price * 1.10
544  WHERE price &lt;= 99.99
545  RETURNING name, old.price AS old_price, new.price AS new_price,
546            new.price - old.price AS price_change;
547</programlisting>
548   In this example, writing <literal>new.price</literal> is the same as
549   just writing <literal>price</literal>, but it makes the meaning clearer.
550  </para>
551
552  <para>
553   This syntax for returning old and new values is available in
554   <command>INSERT</command>, <command>UPDATE</command>,
555   <command>DELETE</command>, and <command>MERGE</command> commands, but
556   typically old values will be <literal>NULL</literal> for an
557   <command>INSERT</command>, and new values will be <literal>NULL</literal>
558   for a <command>DELETE</command>.  However, there are situations where it
559   can still be useful for those commands.  For example, in an
560   <command>INSERT</command> with an
561   <link linkend="sql-on-conflict"><literal>ON CONFLICT DO SELECT/UPDATE</literal></link>
562   clause, the old values will be non-<literal>NULL</literal> for conflicting
563   rows.  Similarly, if a <command>DELETE</command> is turned into an
564   <command>UPDATE</command> by a <link linkend="sql-createrule">rewrite rule</link>,
565   the new values may be non-<literal>NULL</literal>.
566  </para>
567
568  <para>
569   If there are triggers (<xref linkend="triggers"/>) on the target table,
570   the data available to <literal>RETURNING</literal> is the row as modified by
571   the triggers.  Thus, inspecting columns computed by triggers is another
572   common use-case for <literal>RETURNING</literal>.
573  </para>
574
