3<sect1 id="pgplanadvice" xreflabel="pg_plan_advice">
4 <title>pg_plan_advice &mdash; help the planner get the right plan</title>
5
6 <indexterm zone="pgplanadvice">
7  <primary>pg_plan_advice</primary>
8 </indexterm>
9
10 <para>
11  The <filename>pg_plan_advice</filename> module allows key planner decisions
12  to be described, reproduced, and altered using a special-purpose "plan
13  advice" mini-language. It is intended to allow stabilization of plan choices
14  that the user believes to be good, as well as experimentation with plans that
15  the planner believes to be non-optimal.
16 </para>
17
18 <para>
19  Note that, since the planner often makes good decisions, overriding its
20  judgment can easily backfire. For example, if the distribution of the
21  underlying data changes, the planner normally has the option to adjust the
22  plan in an attempt to preserve good performance. If the plan advice prevents
23  this, a very poor plan may be chosen. It is important to use plan advice
24  only when the risks of constraining the planner's choices are outweighed by
25  the benefits.
26 </para>
27
28 <sect2 id="pgplanadvice-getting-started">
29  <title>Getting Started</title>
30
31  <para>
32   First, you must arrange to load the <literal>pg_plan_advice</literal>
33   module. You can do this on a system-wide basis by adding
34   <literal>pg_plan_advice</literal> to
35   <xref linkend="guc-shared-preload-libraries"/> and restarting the
36   server, or by adding it to
37   <xref linkend="guc-session-preload-libraries"/> and starting a new session,
38   or by loading it into an individual session using the
39   <link linkend="sql-load"><literal>LOAD</literal></link> command.
40  </para>
41
42  <para>
43   Once the <literal>pg_plan_advice</literal> module is loaded,
44   <link linkend="sql-explain"><literal>EXPLAIN</literal></link> will support
45   a <literal>PLAN_ADVICE</literal> option. You can use this option to see
46   a plan advice string for the chosen plan. For example:
47  </para>
48
49<programlisting>
50EXPLAIN (COSTS OFF, PLAN_ADVICE)
51        SELECT * FROM join_fact f JOIN join_dim d ON f.dim_id = d.id;
52             QUERY PLAN
53------------------------------------
54 Hash Join
55   Hash Cond: (f.dim_id = d.id)
56   ->  Seq Scan on join_fact f
57   ->  Hash
58         ->  Seq Scan on join_dim d
59 Generated Plan Advice:
60   JOIN_ORDER(f d)
61   HASH_JOIN(d)
62   SEQ_SCAN(f d)
63   NO_GATHER(f d)
64</programlisting>
65
66  <para>
67   In this example, the user has not specified any advice; instead, the
68   planner has been permitted to make whatever decisions it thinks best, and
69   those decisions are memorialized in the form of an advice string.
70   <literal>JOIN_ORDER(f d)</literal> means that <literal>f</literal> should
71   be the driving table, and the first table to which it should be joined is
72   <literal>d</literal>. <literal>HASH_JOIN(d)</literal> means that
73   <literal>d</literal> should appear on the inner side of a hash join.
74   <literal>SEQ_SCAN(f d)</literal> means that both <literal>f</literal>
75   and <literal>d</literal> should be accessed via a sequential scan.
76   <literal>NO_GATHER(f d)</literal> means that neither <literal>f</literal>
77   nor <literal>d</literal> should appear beneath a <literal>Gather</literal>
78   or <literal>Gather Merge</literal> node. For more details on the plan
79   advice mini-language, see the information on
80   <link linkend="pgplanadvice-targets">advice targets</link> and
81   <link linkend="pgplanadvice-tags">advice tags</link>, below.
82  </para>
83
84  <para>
85   Once you have an advice string for a query, you can use it to control how
86   that query is planned. You can do this by setting
87   <literal>pg_plan_advice.advice</literal> to the advice string you've
88   chosen. This can be an advice string that was generated by the system,
89   or one you've written yourself. One good way of creating your own advice
90   string is to take the string generated by the system and pick out just
91   those elements that you wish to enforce. In the example above,
92   <literal>pg_plan_advice</literal> emits advice for the join order, the
93   join method, the scan method, and the use of parallelism, but you might
94   only want to control the join order:
95  </para>
96
97<programlisting>
98SET pg_plan_advice.advice = 'JOIN_ORDER(f d)';
99EXPLAIN (COSTS OFF)
100        SELECT * FROM join_fact f JOIN join_dim d ON f.dim_id = d.id;
101             QUERY PLAN
102------------------------------------
103 Hash Join
104   Hash Cond: (f.dim_id = d.id)
105   ->  Seq Scan on join_fact f
106   ->  Hash
107         ->  Seq Scan on join_dim d
108 Supplied Plan Advice:
109   JOIN_ORDER(f d) /* matched */
110</programlisting>
111
112  <para>
113   Since the <literal>PLAN_ADVICE</literal> option to
114   <literal>EXPLAIN</literal> was not specified, no advice string is generated
115   for the plan. However, the supplied plan advice is still shown so that
116   anyone looking at the <literal>EXPLAIN</literal> output knows that the
117   chosen plan was influenced by plan advice. If information about supplied
118   plan advice is not desired, it can be suppressed by configuring
119   <literal>pg_plan_advice.always_explain_supplied_advice = false</literal>.
120   For each piece of supplied advice, the output shows
121   <link linkend="pgplanadvice-feedback">advice feedback</link> indicating
122   whether or not the advice was successfully applied to the query. In this
123   case, the feedback says <literal>/* matched */</literal>, which means that
124   <literal>f</literal> and <literal>d</literal> were found in the query and
125   that the resulting query plan conforms to the specified advice.
126  </para>
127
128 </sect2>

130 <sect2 id="pgplanadvice-how-it-works">
131  <title>How It Works</title>
132
133  <para>
134   Plan advice is written imperatively; that is, it specifies what should be
135   done. However, at an implementation level,
136   <literal>pg_plan_advice</literal> works by telling the core planner what
137   should not be done. In other words, it operates by constraining the
138   planner's choices, not by replacing it. Therefore, no matter what advice
139   you provide, you will only ever get a plan that the core planner would have
140   considered for the query in question. If you attempt to force what you
141   believe to be the correct plan by supplying an advice string, and the
142   planner still fails to produce the desired plan, this means that either
143   there is a bug in your advice string, or the plan in question was not
144   considered viable by the core planner. This commonly happens for one of two
145   reasons. First, it might be that the planner believes that the plan you're
146   trying to force would be semantically incorrect - that is, it would produce
147   the wrong results - and for that reason it wasn't considered. Second, it
148   might be that the planner rejected the plan you were hoping to generate on
149   some grounds other than cost. For example, given a very simple query such as
150   <literal>SELECT * FROM some_table</literal>, the query planner will
151   decide that the use of an index is worthless here before it performs any
152   costing calculations. You cannot force it to use an index for this query
153   even if you set <literal>enable_seqscan = false</literal>, and you can't
154   force it to use an index using plan advice, either.
155  </para>
156
157  <para>
158   Specifying plan advice should never cause planner failure. However, if you
159   specify plan advice that asks for something impossible, you may get a plan
160   where some plan nodes are flagged as <literal>Disabled: true</literal> in
161   the <literal>EXPLAIN</literal> output. In some cases, such plans will be
162   basically the same plan you would have gotten with no supplied advice at
163   all, but in other cases, they may be much worse. For example:
164  </para>
165
166<programlisting>
167SET pg_plan_advice.advice = 'JOIN_ORDER(x f d)';
168EXPLAIN (COSTS OFF)
169        SELECT * FROM join_fact f JOIN join_dim d ON f.dim_id = d.id;
170                     QUERY PLAN
171----------------------------------------------------
172 Nested Loop
173   Disabled: true
174   ->  Seq Scan on join_fact f
175   ->  Index Scan using join_dim_pkey on join_dim d
176         Index Cond: (id = f.dim_id)
177 Supplied Plan Advice:
178   JOIN_ORDER(x f d) /* partially matched */
179</programlisting>
180
181  <para>
182   Because neither <literal>f</literal> nor <literal>d</literal> is the
183   first table in the <literal>JOIN_ORDER()</literal> specification, the
184   planner disables all direct joins between the two of them, thinking that
185   the join to <literal>x</literal> should happen first. Since planning isn't
186   allowed to fail, a disabled plan between the two relations is eventually
187   selected anyway, but here it's a <literal>Nested Loop</literal> rather than
188   the <literal>Hash Join</literal> that was chosen in the above example where
189   no advice was specified. There are several different ways that this kind
190   of thing can happen; when it does, the resulting plan is generally worse
191   than if no advice had been specified at all. Therefore, it is a good idea
192   to validate that the advice you specify applies to the query to which it
193   is applied and that the results are as expected.
194  </para>
195

198 <sect2 id="pgplanadvice-targets">
199  <title>Advice Targets</title>
200
201  <para>
202   An <firstterm>advice target</firstterm> uniquely identifies a particular
203   instance of a particular relation involved in a particular query. In simple
204   cases, such as the examples shown above, the advice target is simply the
205   relation alias. However, a more complex syntax is required when subqueries
206   are used, when tables are partitioned, or when the same relation alias is
207   mentioned more than once in the same subquery (e.g., <literal>(foo JOIN bar
208   ON foo.a = bar.a) x JOIN foo ON x.b = foo.b</literal>). Any combination of
209   these three things can occur simultaneously: a relation could be mentioned
210   more than once, be partitioned, and be used inside of a subquery.
211  </para>
212
213  <para>
214   Because of this, the general syntax for a relation identifier is:
215  </para>
216
217<programlisting>
218alias_name#occurrence_number/partition_schema.partition_name@plan_name
219</programlisting>
220
221  <para>
222   All components except for the <literal>alias_name</literal> are optional
223   and are included only when required. When a component is omitted, the
224   preceding punctuation must also be omitted. For the first occurrence of a
225   relation within a given subquery, generated advice will omit the occurrence
226   number, but it is legal to write <literal>#1</literal>, if desired. The
227   partition schema and partition name are included only for children of
228   partitioned tables. In generated advice, <literal>pg_plan_advice</literal>
229   always includes both, but it is legal to omit the schema. The plan name is
230   omitted for the top-level plan, and must be included for any subplan.
231  </para>
232
233  <para>
234   It is not always easy to determine the correct advice target by examining
235   the query. For instance, if the planner pulls up a subquery into the parent
236   query level, everything inside of it becomes part of the parent query level,
237   and uses the parent query's subplan name (or no subplan name, if pulled up
238   to the top level). Furthermore, the correct subquery name is sometimes not
239   obvious. For example, when two queries are joined using an operation such as
240   <literal>UNION</literal> or <literal>INTERSECT</literal>, no name for the
241   subqueries is present in the SQL syntax; instead, a system-generated name is
242   assigned to each branch. The easiest way to discover the proper advice
243   targets is to use <literal>EXPLAIN (PLAN_ADVICE)</literal> and examine the
244   generated advice.
245  </para>
246
247 </sect2>

249 <sect2 id="pgplanadvice-tags">
250  <title>Advice Tags</title>
251
252  <para>
253   An <firstterm>advice tag</firstterm> specifies a particular behavior that
254   should be enforced for some portion of the query, such as a particular
255   join order or join method. All advice tags take
256   <link linkend="pgplanadvice-targets">advice targets</link> as arguments,
257   and many allow lists of advice targets, which in some cases can be nested
258   multiple levels deep. Several different classes of advice tags exist,
259   each controlling a different aspect of query planning.
260  </para>
261
262  <sect3 id="pgplanadvice-scan-method">
263  <title>Scan Method Advice</title>
264   <synopsis>
265SEQ_SCAN(<replaceable>target</replaceable> [ ... ])
266TID_SCAN(<replaceable>target</replaceable> [ ... ])
267INDEX_SCAN(<replaceable>target</replaceable> <replaceable>index_name</replaceable> [ ... ])
268INDEX_ONLY_SCAN(<replaceable>target</replaceable> <replaceable>index_name</replaceable> [ ... ])
269FOREIGN_JOIN((<replaceable>target</replaceable> [ ... ]) [ ... ])
270BITMAP_HEAP_SCAN(<replaceable>target</replaceable> [ ... ])
271DO_NOT_SCAN(<replaceable>target</replaceable> [ ... ])</synopsis>
272
273   <para>
274    <literal>SEQ_SCAN</literal> specifies that each target should be
275    scanned using a <literal>Seq Scan</literal>. <literal>TID_SCAN</literal>
276    specifies that each target should be scanned using a
277    <literal>TID Scan</literal> or <literal>TID Range Scan</literal>.
278    <literal>BITMAP_HEAP_SCAN</literal> specifies that each target
279    should be scanned using a <literal>Bitmap Heap Scan</literal>.
280   </para>
281
282   <para>
283    <literal>INDEX_SCAN</literal> specifies that each target should
284    be scanned using an <literal>Index Scan</literal> on the given index
285    name. <literal>INDEX_ONLY_SCAN</literal> is similar, but specifies the
286    use of an <literal>Index Only Scan</literal>. In either case, the index
287    name can be, but does not have to be, schema-qualified.
288   </para>
289
290   <para>
291    <literal>FOREIGN_JOIN</literal> specifies that a join between two or
292    more foreign tables should be pushed down to a remote server so
293    that it can be implemented as a single <literal>Foreign Scan</literal>.
294    Specifying <literal>FOREIGN_JOIN</literal> for a single foreign table is
295    neither necessary nor permissible: a <literal>Foreign Scan</literal> will
296    need to be used regardless. If you want to prevent a join from being
297    pushed down, consider using the <literal>JOIN_ORDER</literal> tag for
298    that purpose.
299   </para>
300
301   <para>
302    <literal>DO_NOT_SCAN</literal> specifies that a particular target
303    should not appear in the final plan at all. In most cases, this is
304    impossible, and will simply cause the scan of the target relation to
305    be marked disabled. However, in certain cases, the planner considers
306    optimizations where a portion of the plan tree is copied and mutated,
307    and then considered as an alternative to the original. In those cases,
308    <literal>DO_NOT_SCAN</literal> can be used to exclude the non-preferred
309    alternative.
310   </para>
311
312   <para>
313    The planner supports many types of scans other than those listed here;
314    however, in most of those cases, there is no meaningful decision to be
315    made, and hence no need for advice. For example, the output of a
316    set-returning function that appears in the <literal>FROM</literal> clause
317    can only ever be scanned using a <literal>Function Scan</literal>, so
318    there is no opportunity for advice to change anything.
319   </para>
320
321  </sect3>
322
323  <sect3 id="pgplanadvice-join-order">
324  <title>Join Order Advice</title>
325   <synopsis>
326JOIN_ORDER(<replaceable>join_order_item</replaceable> [ ... ])
327
328<phrase>where <replaceable>join_order_item</replaceable> is:</phrase>
329
330<replaceable>advice_target</replaceable> |
331( <replaceable>join_order_item</replaceable> [ ... ] ) |
332{ <replaceable>join_order_item</replaceable> [ ... ] }</synopsis>
333
334   <para>
335    When <literal>JOIN_ORDER</literal> is used without any sublists, it
336    specifies an outer-deep join with the first advice target as the driving
337    table, joined to each subsequent advice target in turn in the order
338    specified. For instance, <literal>JOIN_ORDER(a b c)</literal> means that
339    <literal>a</literal> should be the driving table, and that it should be
340    joined first to <literal>b</literal> and then to <literal>c</literal>.
341    If there are more relations in the query than <literal>a</literal>,
342    <literal>b</literal>, and <literal>c</literal>, the rest can be joined
343    afterwards in any manner.
344   </para>
345
346   <para>
347    If a <literal>JOIN_ORDER</literal> list contains a parenthesized sublist,
348    it specifies a non-outer-deep join. The relations in the sublist must first
349    be joined to each other much as if the sublist were a top-level
350    <literal>JOIN_ORDER</literal> list, and the resulting join product must
351    then appear on the inner side of a join at the appropriate point in the
352    join order. For example, <literal>JOIN_ORDER(a (b c) d)</literal> requires
353    a plan of this form:
354   </para>
355
356<programlisting>
357Join
358  ->  Join
359        -> Scan on a
360        -> Join
361             -> Scan on b
362             -> Scan on c
363  ->  Scan on d
364</programlisting>
365
366   <para>
367    If a <literal>JOIN_ORDER</literal> list contains a sublist surrounded by
368    curly braces, this also specifies a non-outer-deep join. However, the join
369    order within the sublist is not constrained. For example, specifying
370    <literal>JOIN_ORDER(a {b c} d)</literal> would allow the scans of
371    <literal>b</literal> and <literal>c</literal> to be swapped in the
372    previous example, which is not allowed when parentheses are used.
373   </para>
374
375   <para>
376    Parenthesized sublists can be arbitrarily nested, but sublists surrounded
377    by curly braces cannot themselves contain sublists.
378   </para>
379
380   <para>
381    Multiple instances of <literal>JOIN_ORDER()</literal> can sometimes be
382    needed in order to fully constrain the join order. This occurs when there
383    are multiple join problems that are optimized separately by the planner.
384    This can happen due to the presence of subqueries, or because there is a
385    partitionwise join. In the latter case, each branch of the partitionwise
386    join can have its own join order, independent of every other branch.
387   </para>
388
389  </sect3>
390
391  <sect3 id="pgplanadvice-join-method">
392  <title>Join Method Advice</title>
393   <synopsis>
394join_method_name(<replaceable>join_method_item</replaceable> [ ... ])
395
396<phrase>where <replaceable>join_method_name</replaceable> is:</phrase>
397
398{ MERGE_JOIN_MATERIALIZE | MERGE_JOIN_PLAIN | NESTED_LOOP_MATERIALIZE | NESTED_LOOP_MEMOIZE | NESTED_LOOP_PLAIN | HASH_JOIN }
399
400<phrase>and <replaceable>join_method_item</replaceable> is:</phrase>
401
402{ <replaceable>advice_target</replaceable> |
403( <replaceable>advice_target</replaceable> [ ... ] ) }</synopsis>
404
405   <para>
406    Join method advice specifies the relation, or set of relations, that should
407    appear on the inner side of a join using the named join method. For
408    example, <literal>HASH_JOIN(a b)</literal> means that each of
409    <literal>a</literal> and <literal>b</literal> should appear on the inner
410    side of a hash join; a conforming plan must contain at least two hash
411    joins, one of which has <literal>a</literal> and nothing else on the
412    inner side, and the other of which has <literal>b</literal> and nothing
413    else on the inner side. On the other hand,
414    <literal>HASH_JOIN((a b))</literal> means that the join product of
415    <literal>a</literal> and <literal>b</literal> should appear together
416    on the inner side of a single hash join.
417   </para>
418
419   <para>
420    Note that join method advice implies a negative join order constraint.
421    Since the named relation or relations must be on the inner side of a join
422    using the specified method, none of them can be the driving table for the
423    entire join problem. Moreover, no relation inside the set should be joined
424    to any relation outside the set until all relations within the set have
425    been joined to each other. For example, if the advice specifies
426    <literal>HASH_JOIN((a b))</literal> and the system begins by joining either
427    of those to some third relation <literal>c</literal>, the resulting
428    plan could never be compliant with the request to put exactly those two
429    relations on the inner side of a hash join. When using both join order
430    advice and join method advice for the same query, it is a good idea to make
431    sure that they do not mandate incompatible join orders.
432   </para>
433
434  </sect3>
435
436  <sect3 id="pgplanadvice-partitionwise">
437  <title>Partitionwise Advice</title>
438   <synopsis>
439PARTITIONWISE(<replaceable>partitionwise_item</replaceable> [ ... ])
440
441<phrase>where <replaceable>partitionwise_item</replaceable> is:</phrase>
442
443{ <replaceable>advice_target</replaceable> |
444( <replaceable>advice_target</replaceable> [ ... ] ) }</synopsis>
445
446   <para>
447    When applied to a single target, <literal>PARTITIONWISE</literal>
448    specifies that the specified table should not be part of any partitionwise
449    join. When applied to a list of targets, <literal>PARTITIONWISE</literal>
450    specifies that exactly that set of relations should be joined in
451    partitionwise fashion. Note that, regardless of what advice is specified,
452    no partitionwise joins will be possible if
453    <literal>enable_partitionwise_join = off</literal>.
454   </para>
455
456  </sect3>

458  <sect3 id="pgplanadvice-semijoin-unique">
459  <title>Semijoin Uniqueness Advice</title>
460   <synopsis>
461SEMIJOIN_UNIQUE(<replaceable>sj_unique_item</replaceable> [ ... ])
462SEMIJOIN_NON_UNIQUE(<replaceable>sj_unique_item</replaceable> [ ... ])
463
464<phrase>where <replaceable>sj_unique_item</replaceable> is:</phrase>
465
466{ <replaceable>advice_target</replaceable> |
467( <replaceable>advice_target</replaceable> [ ... ] ) }</synopsis>
468
469   <para>
470    The planner sometimes has a choice between implementing a semijoin
471    directly and implementing a semijoin by making the nullable side unique
472    and then performing an inner join. <literal>SEMIJOIN_UNIQUE</literal>
473    specifies the latter strategy, while <literal>SEMIJOIN_NON_UNIQUE</literal>
474    specifies the former strategy. In either case, the argument is the single
475    relation or list of relations that appear beneath the nullable side of the
476    join.
477   </para>
478
479  </sect3>

481  <sect3 id="pgplanadvice-parallel-query">
482  <title>Parallel Query Advice</title>
483   <synopsis>
484GATHER(<replaceable>gather_item</replaceable> [ ... ])
485GATHER_MERGE(<replaceable>gather_item</replaceable> [ ... ])
486NO_GATHER(<replaceable>advice_target</replaceable> [ ... ])
487
488<phrase>where <replaceable>gather_item</replaceable> is:</phrase>
489
490{ <replaceable>advice_target</replaceable> |
491( <replaceable>advice_target</replaceable> [ ... ] ) }</synopsis>
492
493   <para>
494    <literal>GATHER</literal> or <literal>GATHER_MERGE</literal> specifies
495    that <literal>Gather</literal> or <literal>Gather Merge</literal>,
496    respectively, should be placed on top of the single relation specified as
497    a target, or on top of the join between the list of relations specified as
498    a target. This means that <literal>GATHER(a b c)</literal> is a request
499    for three different <literal>Gather</literal> nodes, while
500    <literal>GATHER((a b c))</literal> is a request for a single
501    <literal>Gather</literal> node on top of a 3-way join.
502   </para>
503
504   <para>
505    <literal>NO_GATHER</literal> specifies that no <literal>Gather</literal> or
506    <literal>Gather Merge</literal> node should appear above any of the
507    targets, but it only constrains the planning of an individual subquery,
508    and outer subquery levels can still use parallel query. For example,
509    <literal>NO_GATHER(inner_example@any_1)</literal> precludes using a
510    <literal>Parallel Seq Scan</literal> to access the
511    <literal>inner_example</literal> table within the <literal>any_1</literal>
512    subquery, but it does not prevent the planner from placing
513    <literal>SubPlan any_1</literal> beneath a <literal>Gather</literal>
514    or <literal>Gather Merge</literal> node. The following plan is
515    compatible with <literal>NO_GATHER(inner_example@any_1)</literal>, but
516    not with <literal>NO_GATHER(outer_example)</literal>:
517   </para>
518
519<programlisting>
520Finalize Aggregate
521  ->  Gather
522        ->  Partial Aggregate
523              ->  Parallel Seq Scan on outer_example
524                    Filter: (something = (hashed SubPlan any_1).col1)
525                    SubPlan any_1
526                      ->  Seq Scan on inner_example
527                            Filter: (something_else > 100)
528</programlisting>
529
530   <para>
531    Here is the reverse case, that is, a plan compatible with
532    <literal>NO_GATHER(outer_example)</literal> but not with
533    <literal>NO_GATHER(inner_example@any_1)</literal>:
534   </para>
535
536<programlisting>
537Aggregate
538  ->  Seq Scan on outer_example
539        Filter: (something = (hashed SubPlan any_1).col1)
540        SubPlan any_1
541          ->  Gather
542                -> Parallel Seq Scan on inner_example
543                     Filter: (something_else > 100)
544</programlisting>

549 <sect2 id="pgplanadvice-feedback">
550  <title>Advice Feedback</title>
551
552  <para>
553   <literal>EXPLAIN</literal> provides feedback on whether supplied advice was
554   successfully applied to the query in the form of a comment on each piece
555   of supplied advice. For example:
556  </para>
557
558<programlisting>
559SET pg_plan_advice.advice = 'hash_join(f g) join_order(f g) index_scan(f no_such_index)';
560EXPLAIN (COSTS OFF)
561    SELECT * FROM jo_fact f
562    LEFT JOIN jo_dim1 d1 ON f.dim1_id = d1.id
563    LEFT JOIN jo_dim2 d2 ON f.dim2_id = d2.id
564    WHERE val1 = 1 AND val2 = 1;
565                            QUERY PLAN
566-------------------------------------------------------------------
567 Hash Join
568   Hash Cond: ((d1.id = f.dim1_id) AND (d2.id = f.dim2_id))
569   ->  Nested Loop
570         ->  Seq Scan on jo_dim2 d2
571               Filter: (val2 = 1)
572         ->  Materialize
573               ->  Seq Scan on jo_dim1 d1
574                     Filter: (val1 = 1)
575   ->  Hash
576         ->  Seq Scan on jo_fact f
577 Supplied Plan Advice:
578   INDEX_SCAN(f no_such_index) /* matched, inapplicable, failed */
579   HASH_JOIN(f) /* matched */
580   HASH_JOIN(g) /* not matched */
581   JOIN_ORDER(f g) /* partially matched */
582</programlisting>
583
584  <para>
585   For this query, <literal>f</literal> is a valid advice target, but
586   <literal>g</literal> is not. Therefore, the request to place
587   <literal>f</literal> on the inner side of a hash join is listed as
588   <literal>matched</literal>, but the request to place <literal>g</literal>
589   on the inner side of a hash join is listed as
590   <literal>not matched</literal>. The <literal>JOIN_ORDER</literal> advice
591   tag involves one valid target and one invalid target, and so is listed as
592   <literal>partially matched</literal>. Note that
593   <literal>HASH_JOIN(f g)</literal> is actually a request for two logically
594   separate behaviors, so in the feedback it is decomposed into
595   <literal>HASH_JOIN(f)</literal> and <literal>HASH_JOIN(g)</literal>.
596   By contrast, <literal>JOIN_ORDER(f g)</literal> is a single request and
597   appears as-is.
598  </para>
599
600  <para>
601   Advice feedback can include any of the following:
602  </para>
603
604  <itemizedlist>
605
606   <listitem>
607    <para>
608     <literal>matched</literal> means that all of the specified advice targets
609     were observed together during query planning, at a time at which the
610     advice could be enforced.
611    </para>
612   </listitem>
613
614   <listitem>
615    <para>
616     <literal>partially matched</literal> means that some but not all of the
617     specified advice targets were observed during query planning, or all
618     of the advice targets were observed but not together. For example, this
619     may happen if all the targets of <literal>JOIN_ORDER</literal> advice
620     individually match the query, but the proposed join order is not legal.
621    </para>
622   </listitem>
623
624   <listitem>
625    <para>
626     <literal>not matched</literal> means that none of the
627     specified advice targets were observed during query planning. This may
628     happen if the advice simply doesn't match the query, or it may
629     occur if the relevant portion of the query was not planned, perhaps
630     because it was gated by a condition that was simplified to constant false.
631    </para>
632   </listitem>
633
634   <listitem>
635    <para>
636     <literal>inapplicable</literal> means that the advice tag could not
637     be applied to the advice targets for some reason. For example, this will
638     happen if the use of a nonexistent index is requested, or if an attempt
639     is made to control semijoin uniqueness for a non-semijoin.
640    </para>
641   </listitem>
642
643   <listitem>
644    <para>
645     <literal>conflicting</literal> means that two or more pieces of advice
646     request incompatible behaviors. For example, if you advise a sequential
647     scan and an index scan for the same table, both requests will be flagged
648     as conflicting. This also commonly happens if join method advice or
649     semijoin uniqueness advice implies a join order incompatible with the
650     one explicitly specified; see
651     <xref linkend="pgplanadvice-join-method" />.
652    </para>
653   </listitem>
654
655   <listitem>
656    <para>
657     <literal>failed</literal> means that the query plan does not comply with
658     the advice. This only occurs for entries that are also shown as
659     <literal>matched</literal>. It frequently occurs for entries that are
660     also marked as <literal>conflicting</literal> or
661     <literal>inapplicable</literal>. However, it can also occur when the
662     advice is valid insofar as <literal>pg_plan_advice</literal> is able
663     to determine, but the planner is not able to construct a legal
664     plan that can comply with the advice. It is important to note that the
665     sanity checks performed by <literal>pg_plan_advice</literal> are fairly
666     superficial and focused mostly on looking for logical inconsistencies in
667     the advice string; only the planner knows what will actually work.
668    </para>
669   </listitem>
670
671  </itemizedlist>
672
673  <para>
674   All advice should be marked as exactly one of <literal>matched</literal>,
675   <literal>partially matched</literal>, or <literal>not matched</literal>.
676  </para>

790 <sect2 id="pgplanadvice-limitations">
791  <title>Limitations</title>
792
793  <para>
794   It is currently not possible to control any aspect of the planner's behavior
795   with respect to aggregation. This includes both whether aggregates are
796   computed by sorting or hashing, and also whether strategies such as
797   <link linkend="guc-enable-eager-aggregate">eager aggregation</link> or
798   <link linkend="guc-enable-partitionwise-aggregate">partitionwise
799   aggregation</link> are used.
800  </para>
801
802  <para>
803   It also is currently not possible to control any aspect of the planner's
804   behavior with respect to set operations such as <literal>UNION</literal>
805   or <literal>INTERSECT</literal>.
806  </para>
807
808  <para>
809   As discussed above under <link linkend="pgplanadvice-how-it-works">How
810   It Works</link>, the use of plan advice can only affect which plan
811   the planner chooses from among those it believes to be viable. It can never
812   force the choice of a plan which the planner refused to consider in the
813   first place.
814  </para>
